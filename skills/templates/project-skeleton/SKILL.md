# 工程目录骨架与报告落点约定

## 适用场景

- 拿到题目、准备写第一行源之前的那一次目录规划（之后每一次返工都比现在贵）。
- 接手别人的工程：源码、脚本、报告、数据混在根目录，构建命令要靠问原作者。
- 症状级触发：复现说明写不出来（命令对应的目录不存在）；同一份指标在两个地方各一份；
  打包交付时才发现"文档点名的件没随包"；工具报告只有二进制日志，下一轮没人能再读一遍。
- 不适用：单脚本级小活（套骨架是净负担）；上游已经给定目录结构时——照上游，只补本条的三条约定。

## 使用方法

**动手前先查**（一手资料优先级：厂商用户指南/数据手册/接口规范 ＞ 应用笔记 ＞ 教程 ＞ 模型记忆）：
本平台构建流程会产出哪几类报告、每类报告能否直出文本件与默认落点；上游交付要求点名的目录名与件名；
处理器侧应用与上位机脚本各自假设的工程结构。**先跟用户确认**（都是难回退的）：骨架落在哪个位置、
会不会覆盖已有内容、构建脚本跑到哪一步为止、凭据件命名的口径、能否把二进制日志转存成文本。

1. 取本条目 `templates/skeleton.md`：它给出六个区——源（逻辑/约束/上位机/板侧应用四分）、仿真、
   构建脚本与报告落点、板级操作脚本、交付数据（指标表/黄金参考/凭据件）、文档（说明/复现/未决项）。
   每区都写了"放什么 / 不放什么 / 谁读它"，把可变处（方括号占位）逐处替换掉即可。
2. 填**最小可重建清单**：脚本名 + 它做什么 + 产出哪个报告 + 跑完应看到什么，四列都不许空。
   合格判据只有一条：**陌生人照着这张表能从零重建出全部交付数据**。写不出"产出哪个报告"的脚本不进清单。
3. 落三条约定（模板第 3 节有对照表）：
   - **报告统一落文本格式**：工具能出文本就直出；只有二进制日志的，同位置转存一份文本。
     每个文本件头部自带命令、版本、时间戳——否则第二轮就分不清这是哪一次跑的。
   - **凭据件命名带轮次标识**：`<短名>_<轮次标识>_<序号>.<扩展名>`。按轮次标识过滤就能回放整轮的件；
     不带标识必然同名覆盖，旧件被吃掉 ⇒ 那一轮的差分无从谈起。
   - **指路一律用相对位置**：文档、脚本、报告内部引用都写"从工程根出发的相对位置"。
4. 建完立刻做一次**空跑自查**：清单里每条命令在干净树上跑一遍，看三件事——
   产物是否落在约定目录、是否为文本、件内自述路径是否全为相对位置。三条任一不过 = 骨架没建完。

## 失效条件

- **骨架先于内容**：目录建好却长期没有源与产物落进去，空目录本身就会在交付复核里判成占位/死链。
  征兆：某一区连续两轮只有目录没有件——删掉它，别留着当"规划中"。
- **约定漂移**（最常见的失效方式）：新报告落在约定目录之外、凭据件不带轮次标识、文档里出现盘符或
  某台机器的路径。征兆：复现演练里"文档点名的件在盘上"这项开始报红，或同一个指标出现两份不同副本。
- **单命令重建不成立**：多平台/多工具链共用一份骨架时，"一条命令"会分裂成几套。
  做法是清单按平台分行、各自标明适用条件，不要把某一平台的命令写成通用。
- **上游结构冲突**：交付方给死了目录名时，本条降级——只在三条约定上做增量，不要为了整齐重排别人的目录
  （重排会让上游的引用全线失效，代价远大于美观收益）。
- **把骨架当成果**：目录结构不产生任何读数。评审只照说明书跑一遍，跑不通的那一半骨架等于不存在。

## 已验证效果

未量过，属建议（没做过带/不带骨架的干净 A/B）。下面 3 个读数只在同一设计里成立、随设计与平台变，
**不可当普适结论引用**；它们的价值只在"形式可复跑"：

1. 最小清单里"产出报告"栏的空格子数，应为 0（数一遍即得）。
2. 全量文档搜盘符/用户主目录/绝对位置，命中数应为 0。
3. 干净树单次重建演练：清单命令全部跑完、交付数据三项（指标表/黄金参考/凭据件）齐备，
   一轮演练 3/3 才算这条在被执行；读不到任一件 ⇒ 判 `NOT_MEASURED`，不许记成过。
