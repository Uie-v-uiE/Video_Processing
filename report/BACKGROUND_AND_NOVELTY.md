## 1. 为什么做这个题目（实际问题）

嵌入式视觉设备上最常见的取舍是：**显示通路交给处理器，还是交给可编程逻辑。**
处理器路线（ARM + Linux + 网络协议栈 + 显示框架）开发快，但视频流经 CPU/内存两次以上拷贝，
延迟与抖动由操作系统调度决定；而很多展示与检测场景要的恰恰是"网线里进来的画面
立刻、稳定地出现在屏幕上，同时还能做几何/滤波处理"。

本作品选的问题是：**在 Zynq-7000 的 PL 侧做一条不经过处理器、不经过 DDR 数据面依赖的视频
接收—缓存—处理—显示通路**，并把"稳不稳"变成板子自己报出来的数字（而不是人眼看屏幕判断）。

## 3. 创新点（每一条都跟着一个可核查的证据）

1. **把"链路健康"做成硬件自计数的三方可对账数字**，而不是靠人眼看屏幕。
   同一组计数器有三个独立出口：OSD 直接印在屏幕上、AXI GPIO 可被 JTAG `mrd` 读回、
   串口命令可主动清/读。三方读数互相对账 ⇒ "报告里写 0 丢包"变成"你可以自己验证它是 0"。
   证据：`report/OVERNIGHT_LOG.md` R08–R10（板级三态、拔线可逆性、`gapclr` 对账）、
   `src/host/health_read.mjs`、`src/host/ddr_stale.mjs`。
2. **抗乱序、抗丢包的 offset 拼帧协议**（每包自带帧内偏移），比"按序到达"的传输方式
   更适合尽力而为的以太网；并配了**三重提交门限**（行覆盖位图 ∧ 字节预算 ∧ 无坏包标记），
   使得"丢一包 + 一包重复偏移"这种**能被累计字节数伪装成完整**的帧不会提交上屏。
   证据：`skill/udp_offset_reasm.md`、`report/V6_ROOT_CAUSE.md`、`sim/tb_v6_cover_gate.v`。
3. **消隐期内原子提交的 DDR 乒乓 + 拷贝看门狗**：显示侧永远只读一整帧，
   拷贝若赶不上消隐窗口就**整笔作废并保留上一帧**（宁可不动，不可撕裂）。
   看门狗跨时钟域用的是翻转式脉冲同步器（#36 的修法），判据是相位扫描 30/30。
   证据：`report/ARCHITECTURE.md`、`sim/tb_v79_abort_toggle.v`、`sim/tb_v5_vblast.v`。
4. **一条"效果挂在哪个时钟域"的设计规则**：窗口类滤波必须做在**目标域**，
   否则旋转和平滑互相打架（旋转时模糊会跟着抖）。这条规则被固化为可复用的技能与台架。
   证据：`skill/rotate_window_target_domain.md`、`sim/tb_rotate_window.v`。
5. **同一套 RTL 跨器件移植到 UltraScale+ 并收敛**（第二块板 `xcku5p`），
   而且移植过程中发现了原设计里两处"平时不炸、加周期任务就炸"的并发缺陷（#36/#37）。
   证据：`ku5p/README.md` §1（逐条标注"证明/未证明"）、`build/frozen_r21_rx/` 与
   `ku5p/build/frozen_r26/` 的门禁数字。

## 4. 应用价值（不夸大的版本）

适合"网线一头是算力/相机、屏幕一头是人"的展示与调试场景：无人机/机器人图传的落地显示、
多路视频墙、工业检测的即时回看。它的价值点在**可观测性**（画面坏了能立刻区分是链路问题还是
显示问题），不在"我们能播视频"。

**明确不做的**：不做编码（H.264 等），不做网络抗弱网（只做了尽力而为网络下的丢包检测），
不做多路并发解码。这三条都是当前工作量与板子能力的真实边界。
