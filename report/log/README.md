# 工作记录（本目录随包时改名成 report 下的 log 子目录）—— 这十页是什么，怎么读

**先说结论**：想花 5 分钟看懂这个项目是怎么做出来的，读 `report/LLM_COLLAB.md`（四例 + 工作流一节）
与 `report/KNOWN_ISSUES.md`（未修清单与验证边界）就够了。本目录是它们的**原料**：当日流水、
按编号追加的问题账、逐轮版本史。它不修饰，所以也会让你看到我当时判断错在哪里——
这正是它存在的理由：删掉过程，结论就没有可核对的链条了。

**关于这里的路径（2026-10-02 明写）**：本目录里出现的 `build/…txt`、`sim/tb_…v`、`board/…md` 这些名字，
记的是**写下那一天在仓库里**的路径。逐轮工作件（旧台架、旧冻结件、本机串口捕获、二进制）会被清理或不随包，
所以**这些指路不保证在提交包内可解析**，也不是包的完整性判据——导出器每次跑都会把这个数打出来
（`make_submission.sh` 的「台账指路（report/log/）」那一行，只报数不判红）。
要复现读数请走活文档点名的地方：`build/reports/` 里的实现报告 + 根 README 首页那一行（那条有 `metric_recheck` 对回报告）。

| 文件 | 是什么 | 读它的正确方式 |
|---|---|---|
| `ISSUES.md` | 100+ 条问题账：症状 → 假设 → 量到的数 → 为什么这样修 → 还欠什么 | **按编号查，不通读**。交付文档里 `#NNN` 的引用全部指向这里 |
| `OVERNIGHT_LOG.md` | 通宵工作的时间线：每一步的时间、命令、结果、被否掉的推论 | 想知道"某个结论是什么时候变的"就读它；它保留了**当时错的版本** |
| `VERSION_LINEAGE.md` | 哪些文件来自厂商例程、哪些自研、哪些是改造 | 判"原创性"先看这一页 |
| `CONTEST_CHECKLIST.md` | 提交物逐条对照（含赛程指南的真实条款号与权重） | 想知道"这条要求落在哪个文件上" |
| `CHANGELOG_V6.md`、`CHANGELOG_V7.md` | 两个大版本段的变更史 | 只到 V7.9 为止；**此后的版本史在 `OVERNIGHT_LOG.md` 与 `ISSUES.md`**，不要拿它当最新 |
| `V6_ROOT_CAUSE.md`、`V6_BOARD_MEASUREMENT.md` | 第四版数据通路那一族问题的根因分析与板级实测 | 是档案，不是现行结论；现行结论以 `ISSUES.md` 里后续编号为准 |
| `PLAN_V8_SPEC.md` | V8 那一轮的设计意图 | 与实现的差异记在 `ISSUES.md`，两边都要看 |
| `ETH_BRINGUP.md` | 网口从零调通的现场记录 | 含大量"当时以为对、后来被推翻"的判断 |

**为什么这些文件在包里的名字不一样**：仓库里是大写名（`ISSUES.md` 等），导出时统一改小写
以满足 §3.3.5.4 的"文件名纯英文小写"。文件**内容**在导出时一个字都不改——它们是证据。

**已知会腐烂的部分**：这些页里出现的台架名与报告路径，有一部分指向**已经不随包的文件**
（回归台架没进包；留档被展平改名）。这是有意的：历史记录改不得。所以本目录不参与交付包的
死链自检（判据写在 `build/make_submission.sh` 头部第 3 条）——要核对某个数字，请从 report 顶层
那几页出发，那里的每一条指路都被自检要求"在包内解析得出来"。
