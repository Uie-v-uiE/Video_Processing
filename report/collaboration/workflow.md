# 工作流

## 1 分工

主 agent 负责拆任务、读跨文件关系、改代码、跑台架、写文档和装配提交树。只读子 agent 负责单点核查：找文件、查调用、审文档、比对报告。子 agent 的结论回到主 agent，由主 agent 打开文件或看命令输出复核。

## 2 八条规则

1. **先读证据，再提改法。** 不看代码和日志就给方案，通常会在第二轮被现实推翻。
2. **判据先红。** 新增或修改判据时，先做一个能红的反例；第一次跑就绿要查激励是否为空集。
3. **三态判定。** PASS、FAIL、NOT_MEASURED；读不到输入不等于通过，没有判定行的日志只算过程记录。
4. **报告数字回到证据。** 时序看 `build/reports/`，板级看 `board/measured/`，仿真看 `sim/results/`；不能回到证据的数字删掉。
5. **路径走环境变量。** 工具路径、ModelSim、Vitis 工作区都用环境变量传入；脚本不写死本机路径。
6. **改动范围可解释。** 一次只改一条线；顺手重构和顺手改文档要分开，避免把判据变红的原因混在一起。
7. **人工门不代签。** HDMI 画面、比赛模板、页数、提交系统字段由人判断；模型只准备材料和检查项。
8. **交付前复核六层。** 提交树、文档、脚本、证据、归档、Git 各查一遍；没有读数的项标 NOT_MEASURED。

## 3 一次典型闭环

```text
读代码/报告 → 找到可复现的失败或缺口
→ 写判据并确认它能红
→ 改 RTL/PS/脚本
→ 跑台架、实现或上板
→ 把读数写回报告
→ 再跑一次干净环境，确认不是缓存或旧文件造成的假绿
```

## 4 子 agent 的使用边界

- 只读子 agent 可以并行查文档、找文件、比对报告；不拥有最终修改权。
- 写代码的子 agent 必须给出改了哪些文件、跑了什么命令、输出是什么；主 agent 复核实际文件。
- 子 agent 的总结不等于证据；模板化的“已完成”要回到盘上确认。

## 5 交付前的检查顺序

1. 代码和脚本：编译、语法、路径。
2. 仿真：标准回归、完整视频台架、专项日志。
3. 实现：时序、资源、功耗报告。
4. 板级：冷启动、串口、网络、遥测、自检、温度。
5. 文档：数字、路径、死链、版本残留。
6. 归档：release、FIN、Git 分支。

## 6 不做什么

- 不为了让数字好看去放宽约束或删判据。
- 不把台架绿写成板上绿，不把工具估算写成实测。
- 不在提交树里保留旧构建物、临时日志和本机路径。
- 不替人决定比赛模板、页数和提交字段。
