本文按**可复用的判断链**组织，而不是聊天记录流水账：每一节给出触发问题的提示词、
模型给出的关键判断、被板级/仿真数据推翻或证实的过程。凡引用数字均为本文写作时
`report/V6_BOARD_MEASUREMENT.md` 与 `sim/results/` 中的真实测量值。

工具与环境：Qoder 智能体（Claude 系模型）+ Vivado/Vitis 2025.2.1 批处理 + xsim + Node.js
（该机无 python）+ xsdb(JTAG) + 自建 Node UDP 推流工具。板卡 RK-ZYNQ7020-F（`xc7z020clg484-2`）。

## 1. 工作流骨架（固化为技能包 `skill/zynq-video-rtl-debug/`）

```
症状 → 提出可判定的观测（不看屏幕也能判） → 一次只改一个变量 → 仿真复现 → 
改 RTL → 全量回归(28 TB) → 重出 bit/XSA → 上板 → 同一判据复测 → 记 docs/
```

三条硬约束（都是踩出来的）：
1. **先造判据再动手**：不能用「看着好像好了」收敛问题；
2. **单变量**：一次改动必须能被一次测量证伪；
3. **仿真必须用量产几何**（512×300、1392 B 分包、100 MHz/125 MHz/50 MHz 三钟），
   小参数仿真会掩盖缓冲与带宽类问题。

## 2. 三次把结论改对的自我纠错

### 2.1 恒定测试图案掩盖了丢字

- 提示：「用 `--test wordid`（每个 64bit 字的值=它自己的字号）回读 DDR，逐字比对即可定位空洞」。
- 模型据此做了三轮实验，报「bank0 100% 命中」。
- **反例**：肉眼仍见撕裂。原因：`wordid` 每帧内容相同，某字这一帧没写进去时
  旧值恰好等于新值 ⇒ 该方法**结构上无法**发现逐帧丢字。
- 纠正：图案改成 `frameid`（像素值 = 字号 **+ 帧号**），回读时反解
  `n = (value - word_index) mod 65536`，于是「这个字来自第几帧」直接可读。
  第一次 frameid 复测就把最新帧在自己 bank 的占比量化成 42~52%。
- 复用规则：**任何「是否丢数据」的判定，图案必须逐帧变化**（常数图案只能验地址映射）。

### 2.2 xsdb 的 `mrd` 读到的是 A9 的 D-Cache

- 现象：同一块 DDR、期间零流量，三次回读得到三组不同数字。
- 结论：Vitis 应用里 `Xil_DCacheEnable()` 开着，JTAG `mrd` 走 A9 端口 ⇒ 读到缓存。
- 处置：回读前 `targets -set -filter {name =~ "*#0"}; rst -processor`（复位并暂停核心，
  MMU/Cache 随之关闭，DDR 控制器保持已初始化），并且**绝不再 `con`**：
  A9 从复位向量重跑时，若启动引脚是 SD/QSPI，boot ROM 会把卡里的旧 bitstream
  重新刷进 PL，后续测量全部作废。
- 派生陷阱（同一晚踩过）：`ddr_verify` 会把 A9 停住 ⇒ 之后任何一次复测前必须
  重跑 `ps_jtag_boot → program_pl → set_src`，否则量的是「PS 不跑」的工况。

### 2.3 「边推流边回读」让统计整体作废

- 现象：整理数据时发现回读结果的帧号跨度覆盖了几十帧（130..152）。
- 原因：一次回读要几秒，期间 PL 仍在写 DDR ⇒ 每个地址段读到的是**不同时刻**的帧，
  「命中率」变成随机数。
- 处置：测量脚本改成**发完再读**（`src/host/measure_v63.mjs` 默认行为），
  `--live` 只用于看 16bit 粒度探针。

## 3. 一次「测出来却判错」的代价：深度 vs 速率

| 时间线 | 判断 | 证据 | 结果 |
|---|---|---|---|
| 第 1 轮 | 打包器 512 字 FIFO 被显示拷贝挤爆 ⇒ 加深到 2048 | 仿真里 `firstmiss=512` | **失败**：`FW=11` 触发 DRC UTLZ-1（该 FIFO 被综合成触发器，512×96bit ≈ 4.9 万 FDRE） |
| 第 2 轮 | 把缓冲搬到真正映射 BRAM 的 CDC（512→8192）+ 反压 | 仿真 COPY_CYC=67200 时 100% | **上板毫无改善**（仍 42~52%） |
| 第 3 轮 | 深度治不了「平均排空速率不足」；瓶颈是每字等 B 响应 | 丢字率按**包内字节偏移**分带：0–48 B 6.7%、48 B 之后 54~64%；16bit 粒度（18.6% 的 u32 内两个 16bit 属于不同帧） | **成功**：V6.3 流水化写通道后，15/30/60 fps 全部 100.0%，各带 0.0% |

关键方法：把「丢字」按**空间相位**展开（包内偏移、连续游程长度、粒度），
不同机理的签名互斥：
整包丢失 → ≥696 个 16bit 的连续带；端口长时间独占 → 一条长带；
排空速率不足 → 包内固定相位的台阶（本例）；地址/对齐错 → 半字错位或恒定掩码。
这条判据被写成工具 `src/host/ddr_stale.mjs`，是本次定位的决定性一步。

## 4. 被工具链「伪装」成设计缺陷的三件事

1. **xsim 从机模型**：`tb_v6_ingress_integrity` 的从机在 W 到达时用上一拍的 AW 地址，
   且只有 1 个 B 寄存器；流水化 master 一上来就表现为「数据错位 + 打包器永久卡死
   （outst 回绕成 15）」。改成标准握手 + B 移位管道后复现消失。
   ⇒ 规则：看到 master「不排空」，先怀疑从机的 B 计数。
2. **组合 ready 当握手**：`tb_v6_pingpong` 用组合 `svc` 判定 beat 完成，而 DUT 看到的是
   寄存器版 `awready`（晚一拍）⇒ 同一 beat 被数两次 ⇒ 多发一个 B。
3. **Vivado 批处理里调用仿真器**必须 `exec xvlog/xelab/xsim`（直接写命令名会
   `invalid command name`）；`xsim` 只接受 `--testplusarg k=v`，裸 `+k=v` 会被拒。
   另一次真实故障是内存吃紧导致 `ERROR: [Common 17-217] Failed to load feature 'core'`
   （整综合退出），重启同一脚本即通过 ⇒ 长时批处理失败先看 free RAM，不要怀疑 RTL。

## 6. 边界（这套流程不适用的场景）

- 需要肉眼判定的画质问题（缩放走样、色彩、时序抖动）：本文所有判据都只覆盖**数据完整性**；
  右屏细线闪烁最终确认是最近邻缩放走样，与丢字无关，不能用这套方法收敛。
- 无 JTAG 或无第二块网口的平台：`frameid + mrd` 的读回路径不成立，需要换成
  板内比对（PL 内自检 + 计数寄存器）。
- 位宽/分包不规整的协议（载荷非 8 字节倍数）：本流程要求先解决对齐，
  否则 16bit 粒度探针会与打包器部分字互相混淆（V6.1 之前正是这种状态）。

## 10. V7.9 增补（2026-09-23 凌晨，第二块板"开口说话"的一轮）

这一轮的主战场从显示通路移到了网络发送侧（KU5P 遥测 + 主线最后一笔 CDC 账）。
最值得记的是**五次"我自己原来是错的"**，而且每一次都是被工程里的某个环节反驳的：

| # | 我当时断言 | 反驳来自 | 之后写进文档的话 |
|---|-----------|----------|------------------|
| 1 | "10 ns 脉冲被 20 ns 域采，大约会漏一半" | 相位扫描实测：**对齐全对、错开 4 ns 时 0/3** | 形态改成"整体错位时一个都不到"，漏不漏不是"概率"而是相位 |
| 2 | "电平型 3 级同步只会更糟" | 同一张表：电平同步与裸采**逐相位完全一致** | "电平同步修不了它（一样糟）"—— 结论没变，依据换成数字 |
| 3 | "整帧 CRC 余数应该是 0xC704DD7B" | 台架报 FAIL，node 里跑同一算法的**另一份实现**给出 0x2144DF1C（我记的是另一种异或约定） | 检查器先自校 `"123456789"→0xCBF43926`，判据常数必须标"谁算的"，禁止从被测对象回抄 |
| 4 | "36 个字节写 `localparam [4:0] NBYTES = 5'd36` 没问题" | 抓包 dump：载荷从 `55 35 50` 开始、IP 总长 32 | 5 位装不下 36 ⇒ 截成 4；`case` 项 `5'd32` 同理截成 0。判据要写成"IP 总长=20+8+36"这种能被算术式抓住的形式 |
| 5 | "遥测包里的 `bad` 是错包数" | 顺手查"这个数从哪来"：两个板顶层都 `p_good(1'b1)` ⇒ 构造性为 0 | 硬件今晚不动（会碰已上板验过的入口链），先让数字诚实：打印成 `bad≈7(未接FCS判定)` + 登记 ISSUES #38 + 排进下一步第 1 位 |

**这一夜最值得留下的三条方法论**（都已固化成可执行的东西，不靠自觉）：

1. **判据要能自己发现自己的错。** 案例 4 的"平均 < 最小"和案例 1 的"配对集合"都是同一件事：
   与其相信一个数，不如相信"两个独立算法必须给出相容的结果"。所以本仓库现在要求
   每个检查器都带**反例测试**（`--selftest` 里必须有一条"故意算错必须翻红"）。
2. **红项先问"是谁"，再问"怎么修"。** 撤掉观测口是"看起来在修"，`-details` 点名才是"知道是谁"；
   两者代价差 20 分钟，但只有后者能避免"修完还在"。
3. **测量手段也是系统的一部分。** 案例 5、6 都是同一形状：仪器介入改变了被测对象
   （按住内核 / 用一位数字解释四因现象）。判据的写法（采样粒度、是否按住 CPU、是否暂停回放）
   要连同它的**副作用**一起写进文档，否则下一次复现的人会以为是板子不稳定。

**给下一轮的自己的提醒**：`--gapclr` 只清帧间隔统计，`rows_miss_max` 是终身保持的，
所以"缺行峰值 205"这类数字**永远包含本次之前的历史**；引用它必须带上这句限定，
不然就是一句会被评委问倒的假话。
