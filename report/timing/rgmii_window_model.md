## 1. 那条 −2.522 的全部分量（件 `build/evidence/r114_sweepb/rt_tap0_eth_rxc_hold.rpt`，17:40 跑，模型 b）

```
Source      eth_rx_ctl（输入端口，clocked by eth_rxc，rise@0 fall@4 period=8）
Destination u_eth/u_rgmii/u_rgmii_rx/u_iddr_rx_ctl/D（rising-edge IDDR，同一个 eth_rxc）
Requirement 0.000（eth_rxc rise@0 − eth_rxc rise@0）⇒ 同沿检查，不是跨半周期

arrival  3.476 ns = input_delay_min 1.500
                   + IBUF(eth_rx_ctl)     1.321
                   + IDELAYE2 IDATAIN→DATAOUT 0.655
required 5.998 ns = DCD 5.008
                   + Clock Uncertainty 0.835 (= ((TSJ²+TIJ²)^½ + DJ)/2 + PE + UU，UU=0.800 全部来自 rk_zynq7020.xdc:50)
                   + **IDDR (Hold_iddr_C_D) 0.155**        ← 那条"未定"就是它，来自报告正文最后一行
slack    −2.522 = 3.476 − 5.998
```

DCD 那 5.008 的构成也在同一份报告里，逐项对得上：
`IBUF 1.430 + 走线 1.873 + BUFG 0.085 + 走线 1.620 = 5.008`（`BUFG_inst` 就是 `rgmii_rx.v:51` 那一只）。

**所以那 0.155 不是没解释的余数**，是 IDDR 单元自己的 hold 时间；`−2.885`（模型 a，input_delay_min=−0.500）
与 `−2.522`（模型 b，+1.500）的差恰好 2.000 ⇒ 印证计划文件里的 F4：**整条曲线随窗外平移 1:1**。

## 2. 关键结论： deficit 不在数据侧，在"捕获钟被故意挪晚了 5.008 ns"这一项上

把 DCD 拆开看，这 5.008 里 **3.49 是网络延迟**（IBUF+走线+BUFG+走线），而数据侧只有 3.476 的总延迟。
也就是说 IDDR 的 C 脚比 D 脚的数据**晚到 ~1.5 ns**，hold 检查要求"数据不能比沿早到"，于是报负。

而板上不丢包（`bad=0`、1000M 实流量，见 `board/acceptance.md` 与 r92 的签收）的物理解释在同一份数里：
D 脚上的数据在 **[3.476, 7.476]** 这一段是稳定的（下一个符号在 4 ns 后才改变），
捕获沿落在 5.008 ⇒ **距前一次跳变 1.53 ns、距后一次跳变 2.47 ns**，采样点在眼内。
⇒ 这不是"设计坏了没人发现"，是**同一个符号关系在两套口径下的两种读法**：
STA 的 hold 拿"同一 pad 沿"当发射沿，而这套结构是**故意把捕获沿推到数据眼中间**的。

### 为什么只买到 0.759 ——两条都在报告里，不是解释出来的

`io_probe_console.txt` 里那条 I/O hold（±0.5 窗，5 条全是同一族）：

```
Requirement       : -1.000 ns  (mmcm_clk0 rise@3.000ns - eth_rxc fall@4.000ns)
Clock Path Skew   :  5.919 ns  (DCD - SCD - CPR)
Clock Uncertainty :  0.166 ns  ((TSJ^2 + DJ^2)^1/2) / 2 + PE      ← 注意：没有 UU 项
Data Path Delay   :  3.613 ns  (logic 100.000% route 0.000%)
```

1. **`CLKOUT0_PHASE = -225°` 被工具归一化成 `rise@3.000`**（−225° ≡ +135°，mod 8 ns）。
   物理采样点等价（−5 ns 与 +3 ns 是同一个网格点），但 STA 现在拿的是
   `eth_rxc fall@4.000 → mmcm_clk0 rise@3.000` 这**一对沿**（Requirement = −1.000），
   于是"提前 5 ns"在检查里变成了"换了一条参考沿"，净收益只剩 0.759。
2. **更要紧的：那 0.800 的 hold 不确定度**悄悄**脱离了这一族**。
   对照 r114 同一条路（件 `build/evidence/r114_sweepb/rt_tap0_eth_rxc_hold.rpt`）：
   `Clock Uncertainty: 0.835ns (… + UU)`，UU 就是 `rk_zynq7020.xdc:50` 那 0.800；
   现在终点钟是 `mmcm_clk0`，那行只剩 0.166 且**没有 UU** ⇒ `set_clock_uncertainty -hold [get_clocks eth_rxc]`
   **不再覆盖这个域**。也就是说这一刀在"hold 变好"的 0.759 ns 里，有 ~0.67 ns 是**约束作用范围被削弱**换来的，
   不是物理改善。按 H1 的口径这属于"缩小约束作用范围"，**必须进松动台账并要批准人**——
   而它是在我完全没打算放松约束的情况下**自动发生**的。

### 这一页的最终结论（写死，供下一轮直接用）

* **C3/CLKTOPO（MMCM 负相移）判负**：窗没关住（S1 红），且顺带把一条不确定度带踢出了覆盖面 ⇒ 不进主树、不采纳。

  （`-include_generated_clocks`，一条命令一个对象，绝不并名），要么回到 **BUFIO/BUFR 那一族**（计划文件里的 C1，
  预测仍差 ~0.9 ns——但至少它不会造出新的钟对象去拆既有约束的台）。**这条"改钟名会波及所有点名该钟的约束"的清单**
  是本轮最值钱的产出，已记 ISSUES #305。
* 结构改动的证伪成本实测：一次副本树构建 22:54→23:53（含我第一次写错 MMCM 端口的失败滚，#303）≈ **19 分钟**，

### (4) 为什么"再找点"这条路到此为止：把不等式写全

从报告自己的分量（慢角 C_slow = DCD **5.008**、快角 C_fast = DCD **1.597**；数据 D = IBUF+IDELAY，
tap26 时慢 3.613 / 快 3.146）：

先把两条曲线写成实测的直线（斜率与截距都来自上表，不是推的）：

```
HOLD (带 0.800)  = −2.822 + 0.0630·τ   ⇒ 要 ≥ 0 需要 τ ≥ 44.8
HOLD (去掉带)    = −2.022 + 0.0630·τ   ⇒ 要 ≥ 0 需要 τ ≥ 32.1
SETUP            = +2.005 − 0.0920·τ   ⇒ 要 ≥ 0 需要 τ ≤ 21.8        （τ 的合法区间只有 0…31）
```

⇒ hold 要的 τ 与 setup 要的 τ **区间不相交**，带子去不去都一样（32.1 与 21.8 仍然不相交）。

用报告自己的分量再看同一件事，结论一致：**根因不是点没找好，是两条检查用的钟不是同一个数**——
hold 查慢角钟网络（DCD 5.008）、setup 查快角（DCD 1.597），**钟网络的角间差 3.411 ns 远大于
数据路径的角间差 0.467 ns**。数据路径长度是唯一可调量，而它同时受两边约束：

```
带 0.800：  D_slow ≥ 4.763  且  D_fast ≤ 2.762   ⇒ 需要 D_slow/D_fast ≥ 1.73
去掉带子：  D_slow ≥ 3.998  且  D_fast ≤ 2.762   ⇒ 需要 D_slow/D_fast ≥ 1.45
实测（IDELAY 主导）： 3.613 / 3.146 = 1.15      ← 两个门槛都够不着
```

（IDELAY 是模拟延迟线，几乎不随工艺角缩放；只有 IBUF 那一段缩放。⇒ 加更多 IDELAY 只会把比值压得更低。）

把"要多短的钟"写成一条**联合条件**（把 `D_slow = 1.976+0.0630τ`、`D_fast = 0.754+0.0920τ` 代回两个
门槛，τ 有解的充要条件）：

```
0.029 · C_slow + 0.063 · (C_slow − C_fast) ≤ 0.214      （带 0.800 保留）
```

- 今天 `C_slow = 5.008` ⇒ 要求角间差 **≤ 1.09 ns**（实际 3.411）；
- 若换成短钟树 `C_slow ≈ 1.93` ⇒ 容忍角间差 **≤ 2.51 ns**；
- ⇒ 所以"下一刀的靶子"不是单一的"降到 1.2 ns"，而是**同时**把 `C_slow` 拉低与角间差收窄；
  `round_r116.md` §4b 那组具体数（1.93 / 0.65）代回这条不等式：`0.029·1.93 + 0.063·1.28 = 0.137 ≤ 0.214` ✅ 有解。

r92 量过的 BUFIO 慢角 3.171 是一个已知数据点，它的**快角落差未量** ⇒ 那是下一轮第一件要量的事，
不是"再试一次 BUFIO"。

### (6) 角分配这件事我读实了，而且它**加强**而不是削弱上面的结论（01:2x）

同一只 DCP、同一个 `Path Group: eth_rxc`，两类路的角分配是**相反**的（都是报告自己的标题行）：

| 路 | 报告原文 | 数据路径显示值 | 钟路径 DCD |
| --- | --- | --- | --- |
| 内部路 setup | `Setup (Max at **Slow** Process Corner)`（`build/evidence/r115_base/setup_nworst.txt`） | 7.066（慢） | 慢 |
| 内部路 hold | `Hold (Min at **Fast** Process Corner)`（`.../hold_nworst.txt`） | 0.986（快） | 快 |
| **I/O 路 hold（带窗）** | `Hold (Min at **Slow** Process Corner)`（`w3_tap26_hold.txt`） | 3.613（慢） | **5.008 慢** |
| **I/O 路 setup（带窗）** | `Setup (Max at **Fast** Process Corner)`（`w3_tap26_setup.txt`） | 3.146（快） | **1.597 快** |

读法：I/O 路的检查把**钟**放在对该检查最不利的那一角（hold 用慢钟、setup 用快钟），

```
hold  真最坏 = 1.2 + D_fast(3.146) − [5.008 + 0.155 + 0.800] = −1.65   （报告给 −1.185）
setup 真最坏 = 2.8 + D_slow(3.613) − [4 + 1.597 − 0.035 − 0.259] = −0.85 （报告给 −0.386）
```

这条要写在"极限判据"旁边，否则下一轮会有人拿"角分配反了"当理由去改约束或改报告口径。

### (7) 报告最优点与**真实硅片眼心**不是同一个数——这一条登记为未定，不许圆场（01:3x）

§7.5(3) 的 tap 31 是把工具那两条**混合角**检查取到最大最小值得到的。真实硅片只活在**一个**角上，

`Ts ∈ [1.2, 2.8]` = PHY 提前量）：

```
采对沿的充要条件：  |C − D| ≤ 1.2 ns      （两端都要让开，取 Ts 全区间的交集）
```

- 若这颗芯片的 `C ≈ 3.0 ns`（慢 5.008 / 快 1.597 的中间偏快），眼心在 `D ≈ 3.0` ⇒ **τ ≈ 16**，
  而 τ=31 时 `D = 3.93`，离眼心 0.93 ns——**方向上更贴 setup 边，不是更贴中心**。
- 反过来，若这颗芯片的 `C ≈ 2.0`（偏快角），τ=31 的 `D=3.93` 就差 1.93 ns ⇒ 会**错采一个沿**（拿到下一半字节）。
- 现在**没有任何一件**测过这颗芯片的 `C`：报告给的是 min/max 两个角，不是这一颗的实测值。

⇒ 结论：**tap 31 是"报告最好"，不是"硅片最好"**；这一点必须写在采纳理由里，
不能拿 −0.87 冒充"眼心"。板侧 `bad`/`drop_words` 是这件事唯一的裁判，但一次位流只有一个 τ
（`IDELAY_TYPE=FIXED`，运行时改不了）⇒ 想真正量眼心，需要一笔**小改动**：
把这 5 颗 IDELAYE2 换成 `VAR_LOAD`（或加一条 ICAP/AXI 写通路），用串口逐档加载 + 1000M 实流量看 `bad`，
那才是"采样点落没落在眼里"的直接读数（r92/#57 当年写的就是这句话）。**这一笔不在 r116 范围内**，
登记为 r117 的候选，且它需要先有台架/板级判据（不能只改 RTL 就上板）。

| 26（出货值） | 3.61 | [2.41, 4.81] | 2.40 / 3.41 = 70 %（快端差 0.81、慢端差 0.20） |

`set_clock_uncertainty -hold 0.800` 单方面加了 0.8 ns（setup 侧只有 0.035），
两条曲线的交点被这条带子往 setup 方向推了 ~5 拍。

**这一条改变本轮的采纳判断**（写在明处，不留到早上解释）：
`IDELAY_VALUE` 从 26 改到 31 换来的是**报告数字好看 0.315 ns**，代价是**真实角上的鲁棒性 −3 %**
且偏离已被板子证明能跑的 26。**刀 2 因此按"待板侧裁决"处理**：
构建照跑（τ=31 的读数本身是判据 V3 要的那个数），但**只有** 1000M 实流量 `bad=0` 才保留 31；
一旦 `bad>0` 或 `drop_words>0`，立刻回 26（回退是只改一个参数，不需要重新裁决窗）。
