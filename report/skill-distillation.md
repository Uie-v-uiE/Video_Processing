# 技能包的提炼过程

`skill/` 记录的是这个项目在工具、时序、验证和文档上踩过的坑，以及每条坑后来怎么被量出来、怎么被判据挡住。它不是功能清单，也不是把 RTL 再抄一遍。

## 1 从哪些事里总结

来源分四类。

**事故。** 检查脚本在等的判定行没有产出，却仍然报了通过；`catch` 存的是返回码，被误读成一次失败；命令函数存在，但没有接进分派，板上敲命令回“不认”。这类事故写成“症状、原因、下次怎么提前发现”。

**反复出现的症状。** Tcl 查询返回空集合，被当成“对象不存在”，实际可能是查询写错了层；报告字段的位置随工具版本变化，解析脚本却按旧位置硬读。这类问题在不同轮次里重复出现，值得单独成条。

**量出来的差异。** 同一条路径在综合后和布线后的 WNS 不是一回事；同一份设计重跑一次，可能只差一行日期，也可能差出第三种结果。每条都要写清口径，否则“优化了 0.2 ns”可能只是布局摆动的噪声。

**外部资料。** AXI、RGMII、CDC 和时序约束的做法参考了厂商文档和公开的以太网栈实现；哪些采纳、哪些没有采纳、为什么，都留在条目里。

被证伪的判断不删。原来的判断、推翻它的那次运行和最后的结论并排保留，后来的人能看到“当时为什么那么想”，而不是只看到一个正确答案。

## 2 四类内容

赛题要求技能包包含提示词工作流、案例模板、校验脚本和踩坑清单。对应的目录入口：

| 类型 | 目录 | 内容 |
|---|---|---|
| 提示词工作流 | `skill/prompts/` | 从算法描述推软硬件划分、从综合报告定位瓶颈、对抗式评审、从规格到 RTL 清单 |
| 案例模板 | `skill/templates/` | 工程骨架、报告模板、验收与目检卡、声明与证据对照、轮次日记 |
| 校验脚本 | `skill/scripts/` | 寄存器映射检查、时序名册差分、资源/时序检查、指标收集、可复现演练 |
| 踩坑清单 | `skill/pitfalls/` | 构建产物竞争、约束覆盖丢失、文档轮换损伤、包装完整性、假绿判据、Tcl 与探针陷阱 |

其余目录是 `workflow/`、`timing/`、`rtl/`、`runtime/`、`verify/` 和 `_meta/`。`_meta/` 放装配标准、索引生成、自检脚本和写作契约，不是给人读的技巧条目。

## 3 每条怎么验证

验证口径是同一模型、同一上下文、同一工具版本，绕过技能包和使用技能包各跑一次。被控制的变量要列全；两次输入不同，读数就不能相减。

有些检查是确定性的：索引由目录生成，文本编码检查、行号引用检查同一输入跑两次应逐字节一致。有些检查只能做正反例：给一个已知坏的输入，判据必须红；给一个已知好的输入，判据必须绿。做不到这两点的判据，不写成“已验证”。

也有没跑成的地方。旧技能包里的部分自测脚本在重建时被撤下，现在盘上不存在；这些条目只写“当时留下过什么名字”，不假装还能复跑。技能包的索引和装配检查仍然可以跑：

```bash
node skill/_meta/check-skill-package.mjs skill
```

当前 49 个条目、10 类，装配检查通过。索引由 `skill/README.md` 维护，条目文件一律是 `<目录>/SKILL.md`。

## 4 边界

边界分三层。

**恒成立的方法。** 先有能红的判据再改代码；三态判定；读不到不等于通过；一条判据只回答一个问题；差分判据要成对。

**平台相关。** 7 系列的 IDELAY、BUFIO、ODDR 用法不能直接搬到 UltraScale+；AXI GPIO 控制面不能直接套到 MIO。每条技能写清“换平台要改哪几处”。

**工具相关。** Vivado 2025.2.1 的报告形状、xsim 的语法子集、Vitis 的组件 API 都可能在下一次升级时变化。条目里写明工具版本，并提醒“报告字段漂了就重新量形状”。

不写“适用于所有 AMD 器件”。跨板卡的迁移证据目前没有，就写“当前不具备迁移条件，需要第二块板或第二个可套用的子功能”。

## 5 和大模型协作

交付由一个主 agent 加若干只看文件、不共享上下文的子 agent 完成。每个子 agent 的产物落在自己的目录，主 agent 负责装配、复核和发布前检查。子 agent 的自述当待复核的断言处理，不因为“它说做完了”就采信。

原始轨迹留在本机归档，引用时点名条目和可复核文件，不转述成“讨论后决定”。技能包的索引、条目地图和验证记录在 `skill/README.md` 与 `skill/_meta/`。这一章只讲方法，不重复列 49 条条目的名字。
