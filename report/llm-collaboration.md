# 大模型协作记录

这份记录说明模型在项目中参与了什么、哪些建议被采纳、哪些被台架或板上读数否掉，以及最后怎么留下可复核的证据。它不是聊天摘抄，重点在“判断—验证—修正”的链条。

## 1 协作方式

项目采用“主 agent + 只读子 agent”的方式。主 agent 负责拆任务、改代码、跑台架、装配文档；子 agent 只读文件或做单点核查，产物回到主 agent 复核。子 agent 的自述一律当待验证的断言处理，不因为“它说做完了”就采信。

工作循环是固定的：

```text
问题 → 读代码与证据 → 提出候选改法 → 改前判据先红 → 打补丁 → 台架/实现/上板复验 → 记录边界
```

模型主要用在四个位置：读跨文件调用关系、生成候选补丁、补台架与变异对照、把过程记录改写成读者能读的文档。时序签字、人眼验收和“能不能答辩”由人判断，不交给模型。

## 2 案例一：帧提交不能只看字节数

**提示词（节选）**

> 读 `frame_reasm.v`，列出提交一帧需要的条件。只根据 RTL 回答，不要猜。然后给一个台架，证明“字节数够了但行没覆盖全”时不会提交。

**模型回答（摘要）**

模型最初把提交条件概括为“整帧字节数达到 307200，且没有坏包”，漏掉了行覆盖位图。它给出的台架也只检查字节数，判据在错误实现上仍然是绿的。

**修正**

人工把行覆盖位图加回判据：只有所有源行都被覆盖才允许提交。台架改成“字节数够、只覆盖 3/4 行”的激励，并把行计数改成“每写一个字加一”作为变异体。变异体报：

```text
FAIL commit with full byte count but only 3/4 rows
```

恢复源码后通过。这个案例的教训是：模型能读懂单个 always 块，但容易把“跨 always 块维护的状态”漏掉；判据必须由人按设计意图写，不能由模型从代码反推。

## 3 案例二：一行串色的行标签滞后

**提示词（节选）**

> C22 在 0° 下帧顶/帧底各出现 6/48 个满白像素。检查效果链窗口级的行标签是否和内容同拍，给出最小修复，并写一个能红的判据。

**模型回答（摘要）**

模型第一版把 `y_in` 按流水线拍数整体延迟，认为这样就能对齐。台架仍然红：模糊/锐化/Sobel/形态学是窗口级，内容比行标签多滞后一行；只按拍数延迟，帧边界仍会把画布另一端当邻居。

**修正**

在行首采输入行标签历史 `yl1/yl2/yl3`，只对 `STREAM_WRAP=1` 的窗口级使用；行标签与内容在同一行边界对齐。C22 从 6/48 降到 0。

**留下的判据**

C22 不只看最终画面，还逐行比较行标签与内容；如果以后再加窗口级，必须把新级的行滞后计入，否则 C22 会重新红。

## 4 案例三：竖缝抽头晚了两行

**提示词（节选）**

> 旋转时帧尾两整行各 1028 格不符，C31 的 9 位列标签能定位到抽头。查 `fb_bilin` 的结果缓冲和 `seam_src` 的 `sx` 时序，给最小修复。

**模型回答（摘要）**

模型认为 `sx` 与处理链在同一拍，直接把 `sx` 接到 `seam_src` 即可。它忽略了 `fb_bilin` 的结果缓冲让原始像素晚 2 个显示行，竖缝在帧尾会选错抽头。

**修正**

把 `sx` 先过 2 行环（`u_sx_align`，+1.5 块 BRAM），再进 `seam_src`（TAPS=0）。C31 从帧尾两整行各 1028 格不符降到 swap 两态全帧 0。

**代价**

多 1.5 块 BRAM，换来竖缝在旋转边界的正确抽头。这个代价在资源表里单独列出，没有被“效果很好”盖过去。

## 5 案例四：UDP 校验和不能一拍算完

**提示词（节选）**

> 全设计最差路径是 UDP 发送的 IPv4 头校验和，10 项加法在一拍内完成。不要放宽约束，给出拆拍方案和功能复验台架。

**模型回答（摘要）**

模型先建议“把组合逻辑改成一棵更平衡的加法树”，但综合后仍是 6 级 CARRY4，WNS 没有实质改善；它还建议“用 DSP 做加法”，这会引入不必要的 DSP 和跨级延迟。

**修正**

人工把 10 项拆成四拍：第一拍加 5 项，第二拍再加 5 项，第三拍折叠高低半字，第四拍再折叠并取反写回。功能由 `tb_udp_telemetry`、`tb_eth_top_rgmii`、`tb_rows`、`tb_udp_reasm` 复验。WNS 从 1.172 ns 提到 1.341 ns，代价 38 LUT、12 FF。

**留下的判据**

`tb_udp_telemetry` 增加“IP 头 10 个 16 位字相加再折叠，结果应为 `16'hffff`”的判据。故意少加一项时，台架报 `FAIL ip checksum sum=003c`；恢复源码后通过。拆拍不是“看起来对”，而是逐字节和校验和都过。

## 6 案例五：复位树的三个错误直觉

**提示词（节选）**

> 最差路径在复位恢复，`rst_l_sync2` 驱动 3002 个清零端。列出可以试的拓扑，但每条都要给出预期和否决条件。

**模型回答（摘要）**

模型给了三条建议：加 `max_fanout`、用 BUFG 上全局复位网络、把复位拆成局部同步器。前两条听起来都合理，但在实现后测量中都不成立。

**修正**

- `max_fanout` 没有触发复制，触发器数不变，WNS 不动；
- BUFG 把 WNS 从 1.104 ns 拉到 1.078 ns，撤回；
- 给 ARP/ICMP 各加本地同步器，post-route WNS 0.920 ns，比优化前更差，撤回；
- 只复制 link-monitor 的本地复位树，WNS 从 1.104 ns 提到 1.172 ns，保留。

这些“否决”比“采纳”更有价值：它们把复位恢复的边界量出来了。模型可以提出候选拓扑，但不能替实现报告签字。

## 7 案例六：命令实现了，但没接进分派

**提示词（节选）**

> 串口需要能读帧间隔统计。检查 `cmd_link` 是否已经接到命令分派，给出板上验证命令。

**模型回答（摘要）**

模型确认 `cmd_link` 函数存在，输出了 `[LINK]` 格式，便认为功能已经在。实际板上敲 `link` 回的是“不认”，因为 `cmd_link` 没有接进 `dispatch`，帮助行也没有列出来。源码里有函数，不等于固件里有入口。

**修正**

在 `dispatch` 中接上 `link`/`link clr`，补帮助行，重编 PS 应用，经 JTAG 下载后验证：

```text
[LINK] drop=... badpkt=... aborts=... rows_max=... stall=...ms
       gap_last=...ms gap_min=...ms gap_max=...ms gap_sum=...ms gap_valid=1 live=1
```

再停流，`gap_last` 与 `gap_max` 增大；`link clr` 后统计归零。这个案例说明：模型对“函数存在”很敏感，对“调用链是否可达”容易漏；板上敲一条命令比读十遍源码更可靠。

## 8 案例七：文档的机器味

**提示词（节选）**

> 把这份技术文档改成工程读者能读的版本。去掉开头解释文档结构、总结式套话和“值得注意”类句子，去掉版本演进和本机路径，保留数字和证据。不要改变事实。

**模型回答（摘要）**

模型第一版把段落改短了，但仍然保留大量“首先/其次/最后”和“值得注意的是”，还把版本号、日期和本机路径留在表格里。它把“去 AI 味”理解成了“换同义词”，没有理解成“删掉元叙述、只留事实”。

**修正**

人工定了四条规则：

1. 开头直接讲问题，不讲文档结构；
2. 每个数字必须有测量条件和证据，不写“效果显著”；
3. 不写版本演进的流水账，只写优化前/优化后的对比；
4. 不出现本机路径、日期、工具安装路径。

然后按规则重写，并用脚本扫 `rNNN`、日期、盘符和元叙述词。文档的“人味”来自具体判断和代价，不来自把“因此”换成“所以”。

## 9 模型没有做的事

- 没有替人判断时序是否签字；WNS/WHS 以实现报告为准。
- 没有替人看 HDMI 画面；左右同帧、几何一致和 OSD 读数由现场人眼签收。
- 没有替人决定“这个边界能不能接受”；RGMII 保持缺口、BRAM 70%、时延口径都写在 `limits.md`。
- 没有把“台架绿”当成“板上也绿”；仿真、实现、上板分开记录。
