## **[v4] 入包链丢字（拖影 / 黑横纹的真正根因）**

### 27. 静止画面也撕裂，且与上位机速率无关
`frame_reasm` 的「收满一帧」只看累计字节数 ⇒ 丢一包 + 一包重复偏移仍算收满，
把空洞帧 commit 出去。修：commit 需要 `rows_hit==IMG_H` **且** 累计到 `FRAME_BYTES`。

### 28. 每隔一个 16bit 的黑横纹（与推流速率无关）
入包 CDC 读侧被写成「每 3 个 axi 周期取 1 条」= 66 MB/s < GMII 线速 125 MB/s，
单包内就能灌满 512 深缓冲 ⇒ 稳定丢约 46% 的 16bit 字。修：每拍取一条，
且 flush 标记永远给真实数据让路。

### 29. 分包长度不是 8 的倍数 ⇒ 确定性半字错位
1396 B 载荷时包边界落在 64bit 字中间，同一个字被打包器分两次推送、后一次覆盖前一次
⇒ 每帧留下约「每两个包一处」的 4 字节洞，洞里是 0x0000 ⇒ **屏幕上就是均匀散布的黑点**。
同板同 bit 同会话的 A/B（`--test frameid` 200 帧 @15fps，JTAG 回读两个 bank）：

| 分包 | 最新帧 16bit 命中率 | 每帧空洞（16bit 字） |
|---|---|---|
| 1396 B | 99.9% | **222（111 处 × 2）** |
| 1392 B | **100.0%** | 0 ~ 2（仅帧最后一个字的已知残留 #33） |

v6.3 的规避是「载荷取 8 的倍数（1392）」；**v6.4 已在硬件里根治**：打包器按 16bit lane 生成
`WSTRB`（`cur_keep → q_keep → keep_r`），部分字只写自己有效的字节，不再互相覆盖。
板级复测（v6.4 的 bit，仍用 1396 B 分包、200 帧 @15fps）：命中率 **100.0%**、每帧空洞 **0**。
仿真同时补齐了判据：`sim/tb_v6_ingress_integrity.v` 新增 `+MISALIGN`（1396），并把从机改成
按 `WSTRB` 做读-改-写 —— 原来从机无条件整字写入，**根本测不出这种覆盖**。
于是这条 A/B 变得可证明：修复前 `words exact = 38290/38400`、`first bad word = 174`
（正是 `1396/8 = 174.5` 的跨界字，低 4 字节被覆盖成 0）；修复后 38400/38400。
复现命令见 `src/host/HOST_GUIDE.md` §6.1。

### 30. 加深缓冲上板毫无改善（判错方向的教训）
把 CDC 从 512 加深到 8192 并加反压，仿真 100% 但板上仍 42~52%。
**深度只能推迟溢出，改不了平均排空速率**。判据（`src/host/ddr_stale.mjs`）：
丢字率对**包内字节偏移**呈固定台阶（0–48 B 6.7%，之后 54~64%）
⇒ 唯一解释是「每包的包尾排不出去」。

### 31. 打包器每写一个字都要等 B 响应 ⇒ 吞吐被往返延迟钉死
`axi_frame_saver64` 走 `S_AW→S_W→S_B`，在途深度恒为 1 ⇒ 100 MHz/40 拍 ≈ 20 MB/s 上限，
而主机给 15 MB/s 只有 1.3× 余量；显示拷贝在 V-blank 抢同一条 HP0 时往返涨到上百拍
⇒ 平均掉到 15 MB/s 以下 ⇒ 每包包尾按 16bit 粒度被丢。
修（V6.3）：AW/W 同拍挂出各自保持到被接收，`OST=8` 在途，B 只回收计数且**不回绕**
（多回一个 B 会让 `outst` 从 0 回绕成 15 而永久卡死）。
结果：15/30/60 fps 回读全部 100.0%，包内各带 0.0%，半字错帧 0/76800。

### 32. 打包器 FIFO 不能加深（会被综合成触发器）
`q_addr/q_data` 是 512×96bit 的**寄存器阵列**（≈4.9 万 FDRE），`FW=11` 直接
`DRC UTLZ-1: FDRE requires 176092, only 107000 sites`。要加深就加在 BRAM 侧。

### 33. 帧最后 4 字节偶发为 0（已知残留，未修）
某个 bank 最后一个 64bit 字的高半个 u32 读到 0，8 次末帧读数出现 4 次，
15/30/60 fps 都会；下一帧同地址被覆盖 ⇒ 自愈、肉眼不可见；
`tb_v6_ingress_integrity +FULL`（221 包、最后一包 960 B）不复现。
怀疑：最后一拍 `wr_en` 与 `flush` 的竞争导致最后 2 个 16bit 没被推出。

### 34. 测量工具自己会造假（三次误判来源）
`wordid` 恒定图案看不见逐帧丢字；`mrd` 读到 A9 的 D-Cache；**边推流边回读**
让每个地址段读到不同时刻的帧（帧号跨度几十帧）。三条都已在工具里修掉。

### 35. xsim 从机模型把 DUT 伪装成死锁
从机在 W 到达时用上一拍的 AW 地址、只有 1 个 B 寄存器、并用组合 ready 做握手
⇒ 流水化 master 出现「数据错位 + `outst` 回绕 15 + 永久不排空」。
规则：看到 master 不排空，先验从机的 B 计数与握手。

### 36. `copy_abort` 是 1 拍脉冲，却被像素域当电平采样（v7.9 已修，判据见下）

**证据**：`frame_commit_lock.v` 每个 `axi_clk` 周期先把 `copy_abort <= 0`，只在
看门狗到期的那一拍写 1 ⇒ 脉宽 = **1 个 axi 周期 = 10 ns**；消费者
`pl_video_top.v` 的 `eth_has_frame` 在 **50 MHz 像素域**里 `else if (copy_abort)` 直接采样。
**两路时钟是 MMCM 同相出来的 100/50 MHz** ⇒ 脉冲的翻转沿**正好落在**像素域的采样沿上，
收不收得到由建立/保持窗口里的亚稳决定，`report_cdc` 一直把它记成 unsafe。

**现象（如果撞上）**：拷贝超时的确发生了、`copy_overrun` 也会亮 LED，但 `eth_has_frame`
没被清 ⇒ 屏上继续显示上一帧（"看起来冻结"），而不是退回"没有可用帧"的样子。

**一处要撤回的说法**：我原先写"`report_cdc` 一直把它记成 unsafe"，这话**不成立**。
build#17 与 build#18 的 `build/cdc.rpt` **逐行相同（只有时间戳不同）**，而两份里都搜不到
`abort`（也搜不到 `eth_link`/`src_sel` 这类信号名 —— 这份报告只给"时钟对 + 端点数"的汇总粒度，
不点名信号）。⇒ 这条 bug 的证据只有两处：**读代码**（脉宽 10 ns vs 采样沿同相）与
**台架相位扫描**（下表）。教训：`report_cdc` 的行数变化只能证明"某些端点的归类变了"，
不能拿它当"某个具体信号已修好"的凭据；要那种凭据就得看台架。

**测量（`sim/tb_v79_abort_toggle.v`，相位 0..9 ns 扫描，每相位 3 次 abort）**：

| 接法 | 看到的次数 | 说明 |
|------|-----------|------|
| 裸采（改之前） | **27 / 30**，其中 4 ns 那一档 **0 / 3** | 不是"偶尔丢一个"，是**整体错位时一个都不到** |
| 电平型 3 级同步 | **27 / 30**，与裸采**逐相位完全一致** | 只把漏看延后 3 拍，**不是修法** |
| 翻转 + 3 级 + 异拍（本版） | **30 / 30**，十个相位全对 | `frame_commit_lock.abort_tgl` |

**这一条要记下两句诚实话**：① 我原先写的"约一半会被漏掉"是估的，实测是"对齐时全对、
错开 4 ns 时全丢"——形态完全不同，估的那种说法会让人往错的方向找；
② 我原先断言"电平同步只会更糟"，实测是"一样糟"（表里第二行），台架把我的推论否掉了，
所以这里按测量改写。**结论不变但理由变了**：电平同步不能修它，必须用翻转式。
**还有一条最重要的**：0 ns（板上标称同相）这一档仿真里 3/3 全对 ⇒
**这类 bug 的真实形态是"仿真通过、硅片靠运气"**，所以判据不能只看仿真绿不绿。

**修法（v7.9 已落地）**：`frame_commit_lock.v` 里 `copy_abort` 每发生一次翻转 `abort_tgl`
（与本文件像素域→axi 域那一侧的 `blank_tog` 完全对称）；`pl_video_top.v` 用
`(* ASYNC_REG *) ab0/ab1/ab2` 三级 + `ab1 ^ ab2` 出 `copy_abort_pix`，`eth_has_frame` 改用它。
形态就是 `util/ps_publish.v` 已经在本仓库立起来的翻转式模板。
axi 域那侧的 `abort(eth_mode ? copy_abort : 1'b0)` **不动** —— 同域采样不是 CDC。

### 37. 厂商 `eth_ctrl` 的发送仲裁会在帧中间换源（KU5P 侧已换掉，主线 v7.9 已修）

**证据（读代码，改前的原文）**：`src/rtl/eth/eth_ctrl.v` 里控制 `protocol_sw` 的那条 always
```verilog
end else if ((arp_rx_flag && (udp_tx_busy == 1'b0)) ||
             (arp_rx_flag && (icmp_tx_busy == 1'b0))) begin
    protocol_sw <= 2'b0;  arp_tx_en <= 1'b1;
```
那个 **`||`** 说的是"ARP/ICMP 里**有一个**空闲就切到 ARP"。可 `udp_tx_busy`/`icmp_tx_busy`
是**两条独立**的忙线：正在发 UDP 时 `icmp_tx_busy` 必然是 0 ⇒ 条件成立 ⇒ `protocol_sw` 切到 00，
**当前那帧还没发完**，后面剩下的字节就变成了 ARP 应答的字节流（帧长/内容双错，且 CRC 也跟着错源算）。
**主线今天为什么没炸**：主线的 `udp_tx_start_en` 一直 tie 0 ⇒ `udp_tx_busy` 恒 0，
于是这条 OR 恒真 —— 严格说**同样的毛病已经作用在 ping 回包上**（ICMP 应答发一半时来了 ARP 请求就会被切走），
只是窗口只有几十微秒、PC 的 ARP 又稀疏，所以板级没撞见过。
**什么时候一定会炸**：一旦加了周期性发送（KU5P 的每秒遥测把发送占空比从 ~0 变成常态），
撞车概率就变成"每天几次"的量级。

**KU5P 侧的处理（已做，已台架）**：`ku5p/src/rtl/ku5p_tx_arb.v` —— 规则只有一条：
**拿到介质的那帧发完之前谁都不许换**，只接受属于当前 owner 的 `*_done`；请求用脉冲进来、
内部存 pending，空闲时按 ARP > ICMP > UDP 放行。判据在 `sim/tb_ku5p_tx_arb.v`：
T1–T4 验自研仲裁器，**V 组把同一套激励喂给厂商 `eth_ctrl` 做对照**。

**主线的修法（v7.9 已落地，就是本条结案的那部分）—— 两处，不是一处**：

1. 符号：`||` → `&&`，并且切源条件用**同一个**"全部空闲"判据。
2. **只改符号会把 ARP 请求丢掉**。`arp_rx_flag` 只有一拍宽，而"两路都空闲"这一拍往往不成立
   （正在发的那帧还没完）⇒ 请求被吃掉，PC 要等 ARP 超时才重发。所以加了一个 `arp_pend`
   记账位：**先记下来，等介质真的空了再兑现**。

**这条要单独记一笔（我自己的 bug，台架抓到的）**：第一版把 `arp_pend` 写在**单独的 always 块**里，
用 `else if (arp_tx_en)` 清账 —— 非阻塞赋值读的是**上一拍**的 `arp_tx_en`，于是清账晚一拍，
`arp_tx_en` 连高**两拍** ⇒ ARP 发送状态机被重启一次、第 0 字节发了两遍。
台架数出来是 **13 个 ARP 字节而不是 12**（`V ARP 请求没被丢掉 got=13 expect=12`）。
修法：记账和兑现放进**同一个 always**，在授权那一拍同时 `arp_pend <= 1'b0`，
并把 `if (arp_rx_flag) arp_pend <= 1'b1` 放在块尾（同拍"兑现旧账 + 又来新请求"时新请求不会被吃掉）。
⇒ 通用教训：**"改完行为对"和"脉冲宽度对"是两件事**；跨块用非阻塞信号互相清标志，
默认要怀疑晚一拍，判据要包含"这一拍到底高了几拍"。

**台架判据：同一个台架喂四个 `eth_ctrl` 变体，全部实测**（变体在临时目录的副本上改，不动仓库；
厂商原文用 `git show HEAD:src/rtl/eth/eth_ctrl.v` 取）：

| `eth_ctrl` 变体 | `midbad`（帧在飞时别人的字节） | ARP 字节 | UDP 字节 | 结论 |
|---|---|---|---|---|
| 原文 `\|\|` | **3** | 12 | **7** | 换源 1 次 ⇒ 那帧 12 字节只剩 7 |
| 只改 `&&`、无 pending | 0 | **0** | 12 | 不换源了，但 **ARP 请求整笔丢掉** |
| `&&` + 跨 always 块清账 | 0 | **13** | 12 | 授权脉冲高两拍 ⇒ 第 0 字节发了两遍 |
| **本版**（`&&` + 同块记账） | **0** | **12** | **12** | PASS（`flips=1` 是帧边界那一次） |

三条断言必须**一起**看才算过（`midbad==0 && arp==12 && udp==12`）：四个变体各自挂在不同的那一条上 ——
只判 `midbad` 会放走"丢请求"和"多一字节"，只判字节总数会放走"帧中间插别人的字节"
（第一行 UDP=7 而 ARP 仍是 12，只看 ARP 就漏了）。
⇒ 通用做法记进 `skill/arbiter_pending_pulse.md` 与学习文档：**改法有多个候选时，
让同一个台架把每个候选都跑一遍**，比只跑最终版多三倍的说服力，成本是三次 `xvlog`。

**厂商原有、本条没动的一个边界**：两条 ARP 请求落在**同一帧应答时间内**（几十 µs 窗口）会重启
ARP 状态机 —— 改前改后都一样（`arp_rx_flag` 直接触发），PC 的 ARP 重发间隔是秒级，所以现实中
要撞上得有两个主机同时问。真要收口就再补一个 `arp_tx_busy`（`arp_tx_done` 顶层已接好，
`eth_udp_video_top.v:136/169`，只是 `eth_ctrl` 里没用它），代价是"done 没来就永久不再应答"
这种活性风险 —— 那需要板上验证，不适合今晚盲改。

### 38. `frame_reasm.p_good` 在两个板的顶层都硬接 1 ⇒ `stat_bad` 是**死的统计**（发现未修，口径已收紧）

- 证明了：把②从"串行区间比较 + 减法"换成并行 `case`，**真值表完全等价**

  hold 从 +0.043 涨到 +0.066。
- **没证明**任何时序收益：级数 27→27（只少一个 CARRY4），WNS 反而 0.598→0.462。
  而这个数字**不能当结论用** —— 同一条链在 #17/#18/#19 之间已经摆过 +0.447/+1.002/+0.598，
  说明这个设计的**轮次噪声就有 ±0.4 ns 量级**，比我要修的差异大。
  ⇒ 方法论：**"我这笔改动提升了时序"需要多次子/多策略的对照才成立**，一次构建不够。
  （这也是为什么 #20 存档在 `build/exp_r20_glyph/` 而不是进主线数字。）

**为什么留到白天**：真要压这条链，得做**结构改动** —— 把 `chars[]` 变成真 RAM

这些都会**改变延迟** ⇒ 必须同步改顶层 `PROC_LAT` 与配准判据（`tb_osd_lines`、`tb_v5_vblast`），
并且**要上板看文字位置**（OSD 是这次交付里唯一靠人眼验收的部分）。凌晨做不到，就不假装做得到。

**顺带一个反直觉的点，值得写进学习文档**：数组被组合逻辑整片写 ⇒ 摊成"地址与每个下标比一遍"的

### 42. JTAG 回退路径跑不了 PS 应用：CPACR=0 ⇒ 浮点指令陷成 Undefined Instruction（已修，根因见 #44）

**证据链（不是猜的）**：`dow build/ps_app.elf` + `con` 之后 4 秒，`rrd pc` = **0x00000004**，
`cpsr = 0x200001df` ⇒ 处理器处于 **Undefined Instruction 模式**；
`rrd cp15 1` 里 **`cpacr: 00000000`**（cp10/cp11 访问全关），`sctlr` 的 VFP 使能位（bit10）也没置。
⇒ 任何浮点指令立刻陷；app 里算 fps/平均间隔的那段就是浮点。

**为什么"以前能串口"不矛盾**：`ps_jtag_boot.tcl` 与 `board/README.md` 自己写着
"交付态请用 Vitis 里 Run ELF（FSBL）启动 PS；本脚本只是没有 Vitis 时的回退"。
**FSBL 会开 CPACR**，走正式流程时这个问题不存在 —— 所以这不是新引入的回归，
而是**回退路径的能力边界被写得太乐观**（它连"跑不了带浮点的 app"这件事都没记过）。

**两条出路**（都需要人做一次决定，我没顺手改）：
1. 正式流程：Vitis `Run As → Debug`（FSBL + app）。评委复现时也应当走这条，
   `build/gates.sh` 之类的读数不受影响（PL 侧计数器走 JTAG `mrd`，不依赖 PS 应用）。
2. 让 app 自己在启动汇编里开：`MCR p15,0,r0,c1,c0,2` 写 0x00300000 并把 `sctlr` bit10 置上
   ⇒ 从此**任何加载方式**（JTAG dow / FSBL / SD 起）都能跑。代价：要重建 elf（Vitis 平台工程不在本仓库里）。

**我试过并放弃的**：用 xsdb 直接写 CP15（`rwr cp15 cpacr …`、`rwr cp15 1 cpacr …`、
`putregs …` 等 5 种写法）都报 `bad level` / `no register match`；按"三次不停手就换策略"的规矩停手，
不改主线任何东西。**受影响的验证**：SD 播放、`SRC/ZOOM/TH` 串口命令这类要 PS 应用出马的检查项
（§9.5 第 2–6 步）今天没法由我一个人做完 —— 需要你用 Vitis 走一遍。

**2026-09-23 已修（不需要 Vitis，也不需要 FSBL）**：出路②的方向对了，但落点不是"补一条 MCR"。
真因是这个手工链接的镜像**根本没有标准启动**（见 #44），CPACR 只是它暴露出来的第一个症状。
补上标准启动之后：`[BOOT]` 横幅在 COM6 出现、`STAT` 应答、SD 卡挂载成功、回放实测 30.0 fps
（判据与数据见 §19 与 #45 那条的记录方式）。当时的取证顺序值得记下来，因为它决定了我一度走偏：
先看到"发 `SD` 回来的是整条开机横幅"⇒ 以为板子在自己重启 ⇒ 其实是异常落到了 0x0 上
**恰好摆着的代码**（那时 0x0 是我自己加的 FPU 使能桩，末尾 `b _start` ⇒ 看起来就是一次干净重启）。

  5 个文件 4398 帧），因为 `sd_play.c` 里是
  `if (s[kl] == '=' && (s == key ? 1 : (s[-1]==' ' || ...)))` —— `key` 是 `.rodata` 里
  `"FRAMES"` 这个**字面量的地址**，`s` 是串内位置，两者永远不等；于是唯一没被覆盖的情形恰恰是
  "关键字出现在串首"，而调用方为了切分文件名/参数已经把那个空格改写成了 `'\0'`，`s[-1]` 读到
  `0` ⇒ 三个字符都不匹配 ⇒ 每行都判失败。
- 为什么难查：**判据错**和**被判的对象**只能通过同一块板子观察，所以前三次上板我都以为是卡的错。
- 落法：① 判据改成和**被扫描串的起点**比（`s == s0`）；② 给判据自己加测试 ——
  `sd_play.c` 里新增 `meta_selftest()`，三段内置样本（一段必须过、两段必须被拒：
  FILE 行缺 `FRAMES=`、把 `FRAMES=` 写成 `SFRAMES=` 证明行首锚定），跑在真正读卡之前，
  失败时报 `META parser SELF-TEST failed (firmware bug, not the card)`。
  从此 "mount failed" 这句话分得清是固件坏了还是卡不对，**不用把卡拔回 PC 才能判断**。

### 44. 手工链接的 standalone 镜像丢了标准启动（boot.S / asm_vectors.S / translation_table.S）⇒ 四件事一起坏（已修）

`src/ps/lscript_ocm.ld` 当年为了躲开"--gc-sections 把 main 裁光"把 `ENTRY(_vector_table)` 改成了
`ENTRY(_start)`，代价是这三个对象再没人引用、整条启动链被裁掉。一个根因、四个症状（都是今晚撞到的）：

| 缺的东西 | 症状 | 实测证据 |
|---|---|---|
| CPACR/FPEXC（boot.S 负责） | JTAG 起 app：第一条 VFP 指令陷 Undefined | `pc=0x4`、`cpsr` 模式 0x1b、`cpacr=0`（#42） |
| VBAR + 异常向量表 | 异常去执行 0x0 那里恰好摆着的代码，**看起来像一次干净重启** | 发 `SD` 回来的却是整条 `[BOOT]` 横幅（两次，可重复） |
| 各模式栈（ABT/UND/IRQ…） | 想在 handler 里压栈就是"异常里再异常一次" | `boot.S` 里那六段 `ldr r13,=..._stack` 从没跑过 |
| MMU（按 BSP 的恒等映射开） | MMU 关着 ⇒ 非对齐访问必 fault ⇒ newlib `memcpy` 半字快路径炸 | `dfsr=0x801`、出错指令在 `memcpy` 里 |

修法：`build/ps_app.mjs` 显式把三个 `.S` 编进来（`-DSDT` 与 BSP 自己的编译条件一致），
`ENTRY(_boot)` 写在脚本里（试过命令行 `-Wl,-e,_boot`：**被脚本里的 ENTRY 顶掉，readelf 入口悄悄
变成 0x0，一声不响**），并给链接结果加两道哨兵：ELF 入口 == `_boot`、`_vector_table` 必须在 0x0。
`-mno-unaligned-access` 保留：它治的是另一处真实问题（`-O2` 把 `ld32()` 的四个字节读合并成
`ldr r6,[r4,#454]`，objdump 里看得见）。

**一条通用教训**：绕开 IDE 手工搭工具链时，**别只替换入口符号，要把标准启动整条链请回来**；
判据是 `nm` 里必须同时有 `_boot`/`_vector_table`/`MMUTable`，而 `readelf -h` 的入口等于 `_boot`。

### 45. `XSdPs_CfgInitialize` 每个核上电周期只能成功一次；第二次必失败（未修根因，已规避）

- 复现（今晚，同一张卡、同一份 elf）：`rst -processor` + `dow` + `con` 之后第一条 `SD` ⇒
  `FAT32 part_lba=2048 … frames=4398` 全对；随后再发 `SD`（连发三条，间隔 6 s）⇒ 三条都是
  `XSdPs_CfgInitialize failed`。再 `rst -processor` + 重新 `dow` ⇒ 第一条又成功。
  ⇒ 卡没坏、供电没问题，**坏在 PS 侧控制器/驱动状态**，且核复位能恢复。
- 影响：现场演示里"按一下 SD 两次"就会看到 mount failed，而实际帧库还在（`STAT` 仍报 sd=1）。
- 现在做的规避：`sd_mount()` 开头 `if (mounted) return 0;` ⇒ 重复 `SD` 变成幂等（main.c 会再打一次
  挂载表），不再走那条会卡死的重初始化路径。**换卡仍需重启 app**（重新 `dow` 即可，见 `build/tcl/ps_app_reload.tcl`）。
- 留给以后（想修真因才需要）：抓 `XSdPs_CfgInitialize` 内部哪一步超时（它先做 `XSdPs_Reset`
  轮询软件复位位）；怀疑与"上一次会话遗留的多块读/CARD_BUSY 状态 + 4-bit/时钟切换"有关。
  不修不影响交付：正式流程用 FSBL/SD 起，重启是常态。

### 46. 把"自首次播放起的累计平均"当帧率报，读数会离谱 20 倍（已修：窗口速率 + 标签）

`sd_tick()` 每 100 帧打一行统计。原来只有 `avg_fps_milli()` = 累计喂帧数 / **自第一次 PLAY 起**的时间，
分子跨会话累加、分母含停顿 ⇒ 同一时刻板子在 30 fps 跑，屏幕上写 `avg 1.449 fps`。
现在两条分开报并写清含义：`last 100 frames 29.999 fps (since play 29.886)`。
**规则**：任何"平均"数字都要说清分母是什么；能同时给窗口值和累计值时都给，现场不会被人问倒。
帧率本身另有一路独立核对：`STOP` 回报的帧号 / 时长（360 帧 ÷ 12 s = 30.0 fps，见 §19）。

### 48. 固件只读 META.TXT 的第一个扇区 ⇒ 清单被从中间切断，"卡少了 4 个文件"是**假缺口**（已修，板上已复验）

- 本文件与演示脚本、§19 里都写过"卡只拷进 5/9 个文件 = 2099/4398 帧"。**那条判断是错的**：
  今晚把卡插回 PC 逐字节比对后翻案 —— 卡上 `VIDEO000..008.BIN` + `META.TXT` **全在**，
  且与 PC 用 `make_sd_video.mjs` 重新生成的一份 **md5 逐字节相同**（9 个 BIN + META `404d3ba1`）；
  META 自己 `FRAMES=4398` 与 `8×512+FILE8(302)=4398` 自洽。
- 真因在固件：`sd_mount()` 只 `read_secs(..., 1u, Meta)` 而 `Meta[512]`，注释还写着
  "META.TXT 只有一百多字节，读一个扇区就够"。文件实际 712 B ⇒ **第 5 个 FILE 行的数字被切成一半**
  （`FRAMES=512` 读成 `FRAMES=51`）⇒ `Σ FILEn = 4×512+51 = 2099`，于是串口上同时出现
  `files=5 / frames=4398 / Σ=2099`，看起来完全像"拷贝中断"。
- 为什么当时没看穿：刚加的 `Σ vs FRAMES` 校验与 `WARN` 都在**如实报告不一致**，我按字面读了它
  （"卡不全"），却没怀疑**读进来的字节数本身**。⇒ 一条判据只能否定，不能指认凶手；
  "谁生成的这个数"要一路追到读几字节为止。
- 修法（两步，第二步是被自己的判据逼出来的）：
  ① `Meta` 扩到 4096 B，按**目录项里的文件长度**（`DIR_Entry[28..31]`，`dir_lookup` 顺带记进
  `found_size`）算要读几个扇区，读满"首簇内、至多 缓冲区/512 个"，并在 `Meta[found_size]` 补 NUL
  —— 簇尾是上一个文件的垃圾，不给它划终点就会当成清单继续解析。
  ② `meta_trunc` 也按**长度**判（`found_size > sizeof(Meta)`）。当时我先写的是"缓冲尾字节非 0"，
  结果第一版修完 `files=9 / frames=4398` 全对却照样打 `WARN META.TXT longer than the buffer read`
  ——**新判据自己假阳性**（`board/evidence_r29/mount_fixed.txt` 留着这一版）。
  解析器自检同时加两条：`long_ok`（12 个 FILE 行，并把"样本长度 >512"写进断言，样本退化了要看得见）；
  每段样本都在 NUL 之后塞一行假 `FILE99=BOGUS.BIN FRAMES=7` ⇒ "读满簇之后靠 NUL 收口"这件事被每条用例覆盖。
- 验证状态：**板上复验通过** —— 同一张卡 `SD` 打印 `files=9 / frames=4398 / FILE8=302`、`WARN` 消失
  （`board/evidence_r29/mount_fixed2.txt`）。位流与 #23 相同、只有 elf 换版 ⇒ 冻结件里 `ps_app.elf`
  与 md5 随之更新（两版都记在 MANIFEST，最终以仲裁版那一套为准）。

### 49. 片源仲裁：`link_active` 是"曾经收过包"，两个搬运机又没有互锁（RTL 与门禁已完，剩两条眼睛的判据）

**为什么这是一笔独立的账而不是 #47 的余波**：#47 只修了"显示端那块红"，锁本身还在 ——
`pl_video_top` 里 `eth_mode = 3FF(eth_link)` 同时决定 ① 哪台引擎能启动、② 共享 AXI 读口的
六个 mux、③ 帧缓存写口 mux。而 `eth_link` 来自 `link_active = |s_pkts[15:0]`
（eth_udp_video_top.v:369），含义是**"自配置以来收到过任何一个包"**：PC 的 ARP 就够触发，
拔网线也不会回 0，只有重配 PL 才清 ⇒ 现场"推完流再演 SD"必须重配一次（约 1 分钟）。
另外顺手记一条：这条链上从来没有 busy 互锁，两个引擎的 `frame_busy` 一个是空的（`u_aw` 的
`frame_busy()` 悬空）、另一个只喂给 `frame_commit_lock` 看自己 —— 也就是说选择位如果在一次
拷贝中途翻转，会留下半开的 AXI 读突发。老代码靠"ETH 优先 + PS 只在 eth_mode=0 时被允许启动"
侥幸避开，换判据之后这件事不能再靠运气。

**改法**（三层各自做自己那一层的判断，新增 `src/rtl/util/src_arb.v`）：

| 层 | 谁负责 | 判断 |
|---|---|---|
| "活着没" | 快照 lane7.bit3（`link_monitor`，eth_rxc 域） | `stall_ms < LIVE_MS(200 ms)`。**这一位不改**：PS 读回来的语义不能因为仲裁的需要而变。第一版曾为此新加一个 `lm_live` 输出电平（多一条 `have_base` 限定），后面按板级实测推翻，见下面"板级第一版就撞到的" |
| "这句话能不能信" | `src_arb` 的 `eth_tb_ok` | 量 bit3 的那个时基（eth_rxc）没被拉慢、没停（`!(hb_slow \|\| hb_gone)`，来自既有的 `u_lm_axi`，fclk0 域）⇒ **与 bit3 相与之后才允许判 ETH 活**。相与放在 src_arb 里而不是顶层的裸与门，理由见"台架"一条 |
| "能不能换手" | `src_arb`（AXI 域） | 只在 `~row_busy && ~fill_busy` 时改 `owner_eth`；往 PS 方向还要再静默 `T_OFF_CYC=2_000_000`（100 MHz ⇒ 20 ms）⇒ 帧间隔卡在 200 ms 阈值附近时不会来回抢总线 |
| "谁在显示" | `pl_video_top` | `bram_or_hold` 保持 #47 的 `eth_link_pix \| ps_src_seen`（**不动已验过的通路**）；`pub_consume` 从 `!eth_link_pix` 换成 `!owner_eth_pix` —— 用**仲裁结果**而不是再复制一份判据 |

`eth_link` 一路原样保留（OSD/状态与 R08~R10 三条板级结论都挂在它上面），新增的 `eth_live` /
`eth_tb_ok` 是两条 fclk0 域的既有现成信号 ⇒ 顶层不新增跨域配对，`cdc.rpt` 的行数不该变
（门禁里那一栏就是这么判的）。`u_aw.frame_busy` 从悬空改成仲裁输入。

**板级第一版就撞到的（build#24，网线插着）**：停流之后画面**没有**交回 SD，钉在最后一帧、
OSD 的 `STALL` 显示 9999；拔线也不动。当时以为是仲裁没生效，实际是**判据本身在说谎**：
`stall_ms` 的"ms"是从 `eth_rxc` 分出来的，而 RTL8211 断链时**不停 RXC，而是把它拉到 ≈2.5 MHz**
（≈1/48，这条板级事实 2026-09-22 就记进 `snap_cross` 的文件头了，我今晚写仲裁时又把它忘了），
于是 `stall_ms < 200` 会连着十几秒一直为真，`owner_eth` 死死占住搬运机；
`pub_consume` 用的是同一位，于是 SD 的发布也永远不被消费 ⇒ 两个症状同源。
`STALL=9999` 是 OSD 的钉住显示值（`link_monitor` 饱和在 0xFFFF），不是"9999 ms"。
修法就是把"这句话能不能信"做成仲裁的一个输入（上表第二行），而不是去改 `stall_ms` 的算法。

2026-09-24 05:4x：**结案 —— 是固件的字节序 bug，卡从头到尾是好的**

上面那条"最好的假设（簇链指向越界簇）"只对了一半：**簇链没问题，是目录项里的首簇被读错了**。
把它逼出来的不是猜，是让失败行自己报数。

**第一步：给失败加几何量（`read_secs` 的失败分支）**
原来失败只有 `SD read failed` 四个字，任何人都只能猜。改成把 `lba / n / clus / part_end /
IN-RANGE 还是 OUT-OF-RANGE / data_lba / spc` 一起打出来之后，一次 `FRAME3584` 就出了结论
（`board/sd_hotspot_diag.txt` 第 3 行，整份 19 行已读全）：

```
[SDRD!] lba=536959104 n=32 clus=16778886 part_end=62332928 OUT-OF-RANGE (data_lba=34816 spc=32 ...)
```

**第二步：这三个数把因果链一次锁死**

| 量 | 值 | 说明 |
|---|---|---|
| 读到的簇号 | `16778886 = 0x01000686` | 高字是 `0x0100` |
| 把高字两个字节换回来 | `0x00010686 = 67206` | 才是 FAT32 的正确解 |
| 连续布局预测的首簇 | 67205 | 由 `sd_stage_r29` 的文件长度算出（每个文件 9600 簇 × 16 KiB），**只差 1 个簇** |
| 用错簇号算出的 LBA | `34816 + (16778886−2)×32 = 536959104` | 与打印值**逐位相同** ⇒ 从目录项到 LBA 这条链被完整证实 |
| 分区末尾 | `62332928`（32 GB 卡） | ⇒ 这个 LBA 根本不存在，卡拒绝命令是**正确行为** |

缺陷在 `dir_lookup` 的返回式：`DIR_FirstClusterHi` 是偏移 20 的**16 位小端字**，
原来写成 `(d[20]<<24) | (d[21]<<16)` —— 把这一个字里的两个字节按大端拼了。
**为什么只咬第 8 个文件**：首簇 < 65536 时高字是 0，怎么拼都是 0 ⇒ 前 7 个文件全对；
65536 簇 × 16 KiB = 恰好 1 GiB，所以"起点落在数据区 1 GiB 之后"的第一个文件就是 VIDEO007.BIN。
（顺带否掉我自己动过的另一个猜想：不是"LBA 越过 2^30 就坏"—— 1 GiB 那个点落在第 7 个文件**内部**，
回放正常穿过去了；只有**目录项里的高字**才会卡在文件边界上。）

修法：`clus_of()` = `ld16(&d[20]) << 16 | ld16(&d[26])`，`dir_lookup` 改用它。

### 51. 写 `ku5p_cmd` 时撞到的五处"字面量 / 清单 / 算术推断"陷阱（每一处都是台架或报告先红，不是上板才发现）

新模块本身不难，难的是 Verilog 的字面量规则**安静地**改变位宽/位置。四条都值得记，
因为它们的共同点是：**综合不会报错、仿真看起来"差一点点"、上板极难查**。

| # | 陷阱 | 现象（谁先红） | 正确写法 |
|---|---|---|---|
| 1 | 拼接位宽不足时，赋给宽目标是**在高端补零**，不是把内容左对齐 | `localparam [63:0] C = {"SPD999", 8'd0}` 只有 56 位 ⇒ 第一个字节变成 `0x00`、命令短一字节。`tb_v80_ku5p_cmd` 的 A5 那条红，并且因为总账的存在，后面一串判据连锁红 | 拼接必须凑满目标宽度：`{"SPD999", 16'd0}` |
| 2 | `\r` **不是** Verilog 的转义（1364 只认 `\n \t \v \f \a \? \\` 和 `\<八进制>`） | `"CLR\r\n"` 实际是 `'C''L''R''r'` —— 多出一个非空白的 `0x72`，板上有内容但不匹配。B1 那条红 | 需要控制字符就写字节：`{8'h43,8'h4C,8'h52,8'h0D,8'h0A, 24'd0}` |
| 3 | `[base -: width]` 的 base 是**最高位的下标**（含），不是"起始+长度" | `sh_e[(8*n) -: 24]` 整体右移一位：head 读成 `0x29A822` 而不是 `"SPD"`=`0x535044`。A3 起所有 SPD 判据红 | `sh_e[(8*n - 1) -: 24]` |
| 4 | 单台架脚本与全量回归**各有各的编译清单** | `run_one.sh` 跑绿、全量 `run_sim.tcl` 把 `tb_v80_ku5p_cmd` 判 `ELAB_FAIL` —— 红的是清单（新模块没同步加进去），不是 RTL | 加新模块要两处加；两边的文件清单头部都写了这条提醒 |
| 5 | 一句 `v2 * 16'd100` 会被塞进 **DSP48**，而这条锥是收包寄存器 → `cmds_ok` 的 CE | 构建本身**全绿**（0 违例），但 KU5P 的 WNS 从 r23 的 +1.916 掉到 **+0.647**；`ku5p_setup_r31_dsp.rpt` 里最差路径 `Logic Levels: 20 (DSP_ALU=3 DSP_MULTIPLIER=1 …)`，Source/Dest 是 `u_rx_cmd/p_data_reg[5]/C → u_cmd/cmds_ok_reg[5]/CE` ⇒ 一眼认出来是我那条十进制折叠 | **改完反而更差**：把乘法换成移位相加之后 DSP 确实归零（`ku5p_util.rpt` DSPs = 0）、级数 20→14，但 WNS 掉到 **+0.192**（`ku5p_timing.rpt`），最差路径还在 `u_rx_cmd/p_data_reg → u_cmd/cmd_clr_reg` ⇒ **真正的瓶颈不是乘法器，是整条"宽比较"匹配锥**（3 字节 head 比较 + 逐位 digit 判断 + 三向 mux 全挤在一拍里）。下一步（已做完）：把匹配改成**逐字节状态机**（每拍只看刚进来的那个字节，包尾只比状态码）⇒ WNS **+1.985**、最差路径回到厂商 ICMP。三份报告都留档（`ku5p_setup_r31_dsp.rpt` / `ku5p_setup_r31_shift.rpt` / `ku5p_setup.rpt`），而 `tb_v80_ku5p_cmd` 那 35 条判据在三次实现改写里**一个字没动** —— 改的是实现，不是判据 |

顺带一条正向经验：判定"命令收不收"这类**协议**逻辑，把字节流按"最新字节落在最低 8 位"

### 52. 仲裁"停流不交回"的第二条根：长按同步链的**复位值**与源头不一致，上电白送一次长按

- 现象（md5 `c65b547d`，2026-09-24 00:57，第一次无人值守跑 `src/host/arb_handover_test.mjs`；

  也就是说：喂进仲裁的两位判据都在正确工作、并且**已经被看到在正确工作**，仲裁却不肯让位。
  这与 #49 那条"时基说谎"**不是同一件事** —— 同一块板、同一条判据、同一份 json，
  区别只在"有没有把仲裁看到的模式与两个 busy 一起读回来"。
- 只凭 lane30 那三位**分不开四种解释**（模式被钉住 / 时基不可信 / `both_idle` 从不成立 / 判据说谎），

  ⇒ 零新增跨域、`cdc.rpt` 一行没多。这一步就是把"红"变成"红得能定位"的那一步。
- 根因：`lsync`（长按翻转位在像素域的三级同步链）复位成 `3'b111`，而源头 `key_long.tog` 复位是 0。

  ⇒ **上电白送一次"长按"**，模式 AUTO→锁 ETH；而 `sel=锁 ETH` 在 `src_arb` 里是 `force_eth=1`
  ⇒ `owner_eth` 一置就没机会落。板子上电后没人碰过按键，屏幕却永久锁在 ETH —— 与实测一字不差。
- 这条跨域**留在 `cdc.rpt` 的 Warning 里，不再往下压**，理由是具体的：
  `report_cdc -details` 现在给的是 `CDC-6 Warning「Multi-bit synchronized with ASYNC_REG property」`，
  源脚已经是 `u_pl/u_mode/mode_reg[1:0]`（不再是 one-hot）。工具报这条是因为它看见
  "两位总线进一组同步器"，而它**没有办法知道这两位是格雷码**（每次只动一位）。
  也就是说这不是"还没修好"，是"工具的判定能力到此为止"—— 那个性质由台架钉住：
  `tb_v81_test_card` 的 T16/T16b（四步环、每步只动一位）与 `tb_v82_src_mode` 的 T3。
  真要消掉这条 Warning，只有两种假办法（写死例外、或把两位拆成两次单独打拍再合并 —— 后者
  等于把译码搬到目的域外面去绕工具），都不如把性质写进台架。**门禁只判"有没有新增 Critical 配对"，
  Warning 不动它**（见 `build/gates.sh` 第 6 项与 `skill/cdc_pair_baseline_gate.md`）。

- 通用形态：**跨域同步链的复位值必须等于源信号复位之后的值**，否则"复位释放"本身就是一次数据跳变。

### 53. ETH 与 SD 同时在跑时屏幕上两路打架、闪 —— 仲裁七条判据全绿也照样坏，因为它管不到"谁写 DDR"（用户眼睛抓到，机器侧已闭环，只剩眼睛那条）

- 现象（2026-09-24 早上用户肉眼报的三条之一）：网线推流与 SD 回放同时跑时，
  屏幕上两路画面互相盖、闪。而 `arb_handover_test.mjs` 的七条判据在同一个 elf 上连跑两遍全绿。
- 根因是**地址重叠**，不是时序竞态：
  - ETH 入包落在 DDR 乒乓双 bank `0x1000_0000 / 0x1008_0000`（`frame_commit_lock` 给 `row_base`）；
  - PS 侧 SD 的 DMA 目的地址 `FRAME_ADDR` **也是 `0x1000_0000`**（`sd_play.c:35`、`main.c:24`）
    ⇒ SD 每 33 ms 往 ETH 正在填/正在读的那块内存上刷 300 KB。
  - `src_arb` 互锁的是"谁用 DDR→帧缓存这台搬运机"（AXI 读口 + FB 写口）。
    而 SD 的 DMA 是 **PS 自己的 HP0 主设备，根本不经过 PL** ⇒ 仲裁在结构上看不见它。
    #49 里我自己写过一句"仲裁不管 DDR 带宽"，当时理解成了"并发只是抢速度"，
    **真正的后果是抢同一块内存**，这句要改口。
- 我自己在这条上的错误口径（必须留在文档里）：06:0x 给 #50 结案时我顺手把
  "演示口径：一幕只按一个片源"的技术理由划掉了，凭据只是"并发 165 s 里 SD 读取路径零失败"。
  **那测的是读，不是显示。** 用户眼睛一试就知道两路在打架。
  ⇒ 撤销该结论：SD 读路径确实修好了（#50 那笔不变），但"并发可看"要等本条修完 + 上板确认。

  - RTL：`pl_video_top` 新参数 `PS_BASE_ADDR`，只给 `u_aw`（PS 那条搬运机）；`system_top` 的

    而且 FILL 与 SD 混用、以及"谁先写"的根都没解决 —— 地址分开是结构性修法，节流只是遮。

### 54. 窗口级效果链一直"数据与 Valid 错位"，而顶层的总延迟写的还是错数（r45 加形态学时量出来的；本条只修了一半，V8-4 之前必须修完。2026-09-24 晚：错位量已量成数字，见本条末尾）

给效果链加第 5、第 6 个模块（腐蚀/膨胀、锐化）时，第一件事是搞清"总延迟到底几拍"，因为顶层要用它
把左窗（原图）对齐到右窗（处理图）。量下来是三件事叠在一起：

1. **窗口级是三拍，不是两拍。** `de_in → de_d1 → de_d2 → de_out` 是三级寄存器（`proc_box_blur.v:65-68`、
   `proc_sobel.v:60-62` 都是这个写法）。点运算级（灰度/二值化/反色）是一拍。
2. **窗口级的数据取的是"中心抽头 p11"，而 p11 来自上一行的行缓存。** 也就是说 dout 与 de_out 是同一拍
   出来的，但它俩说的不是同一个像素：数据比标签**旧约一行**。
3. **顶层的 `localparam PROC_LAT = 7` 是个字面量。** 按 1 的规则，V7 那条链
   （灰1 + 二值1 + 模糊3 + Sobel3 + 反色1）真实是 **9 拍**，写成 7 ⇒ 左右窗长期错 **2 个像素**。
   （9 这个数不是手推的：r45 的新链按同一条规则是 1+1+3+3+3+1+3 = 15，而 `tb_v86` 的 T2 **实测**
   就是 15 —— 实测与算法对得上，才敢说旧链是 9。）

为什么这么久没人看见：**整幅平移在单幅画面上不可辨**；左右分界线是竖直的，行错位不会在缝上留痕；
2 个像素在 1024 宽的面板上约 0.2 %，除非缝两侧有连续的网格或跨缝的图案，肉眼分不出来。
所以这不是"测试漏了"，是**没有一条判据在量它** —— 现在有了（`tb_v86` 的 T2/T3/T5）。

### 55. 长按"没反应"、切模式顺带转 1°、ETH 画面偶然变成彗星图 —— 三条同根：**模式没有可见反馈**（用户报的，r45 已定位，修在 r46）

- 机器侧先排除了两个嫌疑人（这两条都是**实测**，不是推断）：
  - 采 lane30 共 333 次 / 40 s，`eth_live`、`owner_eth`、两个 busy **一次都没跳** ⇒ 不是仲裁在抖；

- 真因（三条共用一个根）：
  1. **模式四态里有两态在画面上不可分。** 有流时 `AUTO` 与 `锁 ETH` 长得一模一样
     （OSD 那行只有 `SRC:0/1`，说的是 fb 还是图卡，**不是模式**）。于是"长按生效了"= 没有反馈 =
     用户再按一次 ⇒ 走到 `锁 PS`/`锁图卡` ⇒ 看到彗星图。①与③是同一条：不是不灵，是**灵了看不出来**。
  2. **短按在按下沿就发火**：`key_debounce` 的 `pulse` 是 `key_prev && !key_stable`（press edge），

     写明并接受的"已知代价"，用户报上来才知它有多碍事。
  3. 1.2 s 的阈值没有任何进度指示，靠手掐 ⇒ 有时差一点没到（`fired` 不置位、松手也没有短按之外的反馈）。

  1. 短按改到**松手时**发：`key_long` 出第二个事件 `short_pulse`（按住时长 < 阈值才算），

     （它的语义就是"连续反向转"，早发更好用）。

     OSD 的片源行改成显示四态 `SRC:AUTO|ETH|PS |CARD`，`led[1]` 从 `src_use` 改成显示 mode 低位
     （OSD 与 lane30 都能读到同一件事，三处一致是硬要求）。
  3. `have_src` 现在写的是 `eth_link_pix | ps_src_seen` —— 推流偶发 >200 ms 空档、且本次上电 PS 的发布

     这才是"有没有东西可看"的正确判据；"谁活着"归 `link_monitor`，两件事不要混。
  4. 长按事件加一个计数器进健康 lane（读一次就知道"板子一共收到过几次长按"），
     以后这类"到底生效没有"不必再靠眼睛，也不需要再靠我猜。

| 症状 | 优先检查 |
|------|----------|
| 无 HDMI | bit、线、1024×600 |
| ping 不通 | 是否 **PL 口**、ARP 表 |
| ping 通无视频 | 端口 5001、offset 协议、src 绑定 |
| 4 幅/窄条 | CDC 切片、AXI 拆包 |
| 右屏不缩放 | `zoom_en`、`zoom_ctrl` 参数、inv 范围 |
| 缩放坐标乱 | inv 位宽是否 10-bit 有符号 |
| 效果只在错误窗 | 效果是否挂在右窗 de |
| 时序 WNS 为负 | 时钟组是否含 clkout*；FIFO 是否 BRAM |
| 串口无效 | PS app 有没有真在跑：`xsdb build/tcl/ps_app_reload.tcl` 看 `pc`/`cpsr`（模式 0x1b=Undefined ⇒ #44 那类没修上；pc 停在 0x4/0x0 ⇒ 异常落进向量区） |
| 串口发多条只有第一条应 | 是夹具不是板子：`powershell -File` 不绑数组、循环会在两条命令之间提前收工（`board/uart_cap_once.ps1` 已修并自检 `SENT n/n`） |
| 第二次 `SD` 必 mount failed | `XSdPs_CfgInitialize` 每个上电周期只成功一次（#45）；已用 `mounted` 短路规避，真机换卡要重下 app |
| 报"卡少了文件 / Σ 帧数对不上" | **先怀疑读进来的字节数**（缓冲区多大、读几个扇区），再怀疑卡 —— #48 就是这个顺序反了：清单 712 B 而固件只读 512 B，尾行数字被切一半，卡其实 md5 全对 |
| 板子"像自己重启了一遍" | 没人设 VBAR ⇒ 异常去执行 0x0 那里恰好摆着的代码（#44）；读 `DataAbortAddr`/`PrefetchAbortAddr`/`UndefinedExceptionAddr` 三个全局看是谁 |
| PS 写了 DDR 却全红 / `FILL` 看不见 | 显示前最后一级 mux `bram_or_hold`（#47）；DDR 侧先自证：`board/rdddr.tcl` 读 `0x10000000` 两次，内容在变就说明卡在 PL |
| 停流之后画面**不**交回 SD，`STALL` 钉 9999 | 不是仲裁的换手规则坏了，是**喂它的位在说谎**（#49）：`stall_ms` 的"ms"从 `eth_rxc` 分频，断链时 RTL8211 把 RXC 拉到 ≈2.5 MHz 而不是停掉 ⇒ `stall_ms<200` 可以连着十几秒为真。查 lane31 的 `hb_slow`（它就是为这个工况加的），确认 `eth_tb_ok` 有没有落到 `src_arb` |
| 推流停了但 `owner_eth` 一直是 1，而 `eth_live` 已经在 0 | **先看 lane30 的模式位**：不是 AUTO（锁 ETH/锁 PS）说明手动锁占着，与自动判据无关（#52：上电白送一次长按就是这个表现）；模式是 AUTO 才轮到看 `eth_tb_ok`（#49）和 `row_busy` 占空比 |
| 两路片源抢画面 / 交接时闪一下 | 同一个 AXI 读口 + 同一个帧缓存写口，选择位**只能**在两个引擎都空闲时翻（#49 的 `both_idle` 互锁）；反复抢说明滞回 `T_OFF_CYC` 短于对端的帧间隔 |
| 字符串比对的 RTL 总是"差一位/短一字节" | Verilog 字面量三条规则（#51）：拼接位宽不足会在**高端**补零；`\r` 不是转义；`[base -: w]` 的 base 是最高位下标 |
| 单个台架跑绿、全量回归报 `ELAB_FAIL` | 红的是**清单**不是 RTL：`sim/run_one.sh` 与 `sim/run_sim.tcl` 各有一份 KU5P 文件列表，新模块要两处加（#51 第 4 条） |
| git push 失败 | 网络/代理；git 是否在 PATH |
| 动画拖影 / 每隔一个 16bit 黑纹 | `node src/host/ddr_stale.mjs` 看**包内相位**：台阶=排空速率（在途深度、往返延迟）；长带=端口被占死；整包带=前端丢包 |
| 静止图也撕裂 | 覆盖门限是否生效（`stat_frames`/`stat_bad` 比例）；bank 内帧号跨度应为 1 |
| 回读命中率像随机数 | 是否**边推边读**（回读要几秒）；`mrd` 是否读到 D-Cache（先 `rst -processor`，别 `con`） |
| Vivado 批处理 `Failed to load feature 'core'` | 内存吃紧，不是 RTL 问题；关掉占内存的进程后重跑同一脚本 |
