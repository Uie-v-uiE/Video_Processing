# S28 WNS 是负的：先看 `logic/route` 的分配再决定动哪一手，否则会在错误的杠杆上花掉一轮构建

## 触发
有一条（或一族）setup 违例，你想修它。直觉动作是"把那段算术改短"或"把高扇出复制几份"——
这两个动作分别针对**逻辑深度**与**扇出**，而违例可能是第三种原因：**布线距离/那片区域的绕线**。
猜错杠杆的代价是一次 12–15 分钟的构建加一轮归因。

## 不适用
- 违例在 CDC 路径上且报告把它列为 async 组 ⇒ 那是跨域约束问题，不是这一段。
- 只差几 ps 且分布随每次布局大幅摆动 ⇒ 那需要的是策略扫描/余量，不是本条。

## 动作
1. **读出三个数**（`report_timing` 一条路径的块里就有）：
   `Data Path Delay: 7.694ns (logic 2.229ns (28.970%) route 5.465ns (71.030%))` 与 `Logic Levels: 6 (CARRY4=3 …)`。
   仓库里的现成口子是 `build/tcl/crit_path.tcl`：它只读已布线的 dcp，
   每条最差路径出一行 `slack | 时钟组 | 数据路径延迟 | 级数 | 起点 -> 终点`。
2. 按分配选杠杆：
   - `logic` 占大头、级数多 ⇒ 动算术/流水（把一段组合搬到前一拍寄存）。
   - `route` 占大头（本例 71 %）⇒ 动**物理**：邻接约束（Pblock）、减少该终点族的端点数
     （28 位计数器每 bit 一个 `CE` ⇒ 8 条最差路径全是它的兄弟 bit，改成"一个使能 + 并行数据"能把端点族压成 1 个）、
     或疏解那片绕线（先看利用率**形状**：BRAM 67.86 % 而 LUT 逻辑只用 19.12 % ⇒ 缺的不是面积，是线长）。
   - 扇出高 ⇒ 才轮到 `max_fanout`；**但先做第 1 步**，因为扇出与布线经常混在一起。
3. 无论动哪一手，改完跑同一个脚本比**同一族的 route 占比**，而不是只看全局 WNS 有没有转正。

## 完成判据
一条被数字支持的选择，加一次"猜错也来得及止损"的记录。本仓库的实例是反面的两层：
① 我看到一族 `wbin_reg → drop_words_reg[*]/CE` 违例后先猜扇出，加 `max_fanout=12`，
   WNS 从 −0.062 拖到 −0.192 ⇒ **回滚**（`report/OPTIMIZATION_LOG.md` r83/r84 两节）；
② 回滚后我在日志里写"瓶颈不是扇出，是锥体本身（14 位加法→格雷→比较）"，
   第二天把 `crit_path.tcl` 修到能跑，实测 **6 级逻辑 / route 71 %** ⇒
   **这句结论也被推翻**（`report/log/ISSUES.md` #121 记的就是这次自我更正）。
**失效边界**：`report_timing` 的 `logic/route` 是按最坏角算的，换速度等级/温度角分配会变；
另外布线占比高不一定能靠 Pblock 解决——如果那片区域本来就绕不开（BRAM 与 DSP 的固定位置），
物理杠杆也会失效，那时剩下的是流水或降频。

## 出处

`report/log/ISSUES.md` #121（我原先写的"瓶颈是这个锥体本身"被 `crit_path.tcl` 修好后的实测推翻：
7 级逻辑、route 占 71 %）与 #124 及其「#124 补充」（切断目标那一族之后，失败端点 16 → 2，
但全设计 WNS 反而变成 −0.135——最差路径换成了邻域里的兄弟路）。
