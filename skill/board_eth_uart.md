# S7 · 双网口 + 板载 USB-UART/JTAG 桥：先把"板子活着"定义成一条能读的增量

## 触发
- 当你看到 ping 不通，或者 ping 通却没有画面、没有回包
- 当你敲进串口的命令没反应，或"一条命令要发好几遍才灵"
- 当 JTAG 服务器里找不到器件，或两块板同时插着时只有一块可见
- 当你刚下过一次位流，之前一切正常的通路忽然全断
- 当你正准备拿 `ping` 或板上的 `DONE` 灯当"活着 / 位流还在"的判据
- 当你换了电脑（多网卡）或换了组网方式之后，同一套结论开始漂

## 不适用
- 经交换机/多主机的网段：本页只在"点对点直连 + 静态地址 + 数据面走 PL 侧网口"这一种拓扑上量过
- PS 侧跑协议栈收流的工程：速率与自协商那一格要重新量，别把这里的清单当依据
- 要人眼看屏才能判的画质与内容对不对：那一半在 [S23](eye_acceptance_loop.md)
- 接收链自己的协议假设（前导码计数、ARP 只缓存一个对端、接受广播目的地址）：唯一住处是 [S1](udp_offset_reasm.md)

## 动作
1. 先核三件物理事实再谈软件：数据面网线插到**承担数据面的那个网口**（本工程是 PL 侧 PHY 口，不是 PS 口）、
   PC 侧配成与板同网段的静态地址、供电与显示模式按板卡手册（本仓库 `board/README.md` §Hardware）
2. 多网卡必须**绑源地址**再发，否则默认路由从另一张卡出去、`ping` 通的是别的面（`socket.bind(("192.168.1.100", 0))`；
   本仓库把这一参数统一收在脚本的 `--src` 上）
3. 把"存在性"分两层写：`ping` 只验到链路/ARP 由谁应答这一层；**板子活着 = 器件自己维护的计数器在涨**，
   所以推流前后各读一次包计数做差（`node src/host/health_read.mjs`）。位流没加载时 PL 口 ping 不通是正常，**不许反推网口坏**
4. 串口只留一条真源：帧格式抄上位机指南（115200 8N1），**命令语法不许在技能里另抄一份**
   （抄了就漂；本仓库的权威表是 `report/COMMANDS.md`）；批量发并留档 / 只捕获不发 / 成套复验各用一支脚本，
   并且先确认那个 COM 口没被另一个终端占着
5. 怀疑串口线之前先把"要发好几遍"拆成三层量：① 固件完全没有本地回显 ⇒ 你看不见自己敲了什么，只能重发
   （错觉，占比最大）；② 某条命令一次写几百项、期间不轮询串口，占用的时间比接收 FIFO 的容量换算还长
   （例：写 256 项 ≈2.6 ms，而 115200 下 16 字节缓冲 ≈1.4 ms）；③ 大块 I/O 期间几十毫秒不轮询 ⇒ 粘贴一行必丢字。
   三层的修法分别是"补回显 / 收与派发分离并在长循环里插保活 / 缩小每段 + 缓冲超长明确报错"，都不是换线；
   顺带记住：缓冲区超长被**静默截断**后照样派发，是最难查的一种"没反应"
6. JTAG 固定成一个顺序并在每次下位流后重跑：先扫链确认器件在（`vivado -mode batch -source build/tcl/scan_jtag.tcl`），
   再"起 PS → 下 PL → 载应用"三件套（`ps_jtag_boot` → `program_pl` → `ps_app_reload`）；
   **下位流会复位处理器，不重跑应用就一定没反应**；换位流时若应用正在猛敲总线，先做一次系统级复位再走三件套
7. 两块板只有一块可见时先查枚举而不是驱动：列出现场的 USB 实例名与序列号（`Get-PnpDevice -PresentOnly` 过滤桥片 VID/PID）
   ⇒ 两颗桥片被写成同一个序列号时，系统只给其中一个保留该实例名、另一个退回总线位置名，
   而 JTAG 服务是按序列号拼 cable 地址的 ⇒ 第二根线**根本不产生第二个 target**；换板要重启服务，这不是线材问题

## 完成判据
- 一条数字关系：`每秒包增量` 必须等于上位机标称帧率 × 每帧包数（本工程 15 fps × 221 包 = 3315/s；
  个别秒偏高是 1 秒采样的边界效应）——对上才算链路通，`ping` 通不算
- 断链自愈实验可复现：拔线期间计数冻结、插回后立即恢复且停等计数归零，**全程不重启板子、不重下位流**
- 串口验收不看感觉：每条命令要有一行可 `grep` 的回显，跑完一轮之后状态读回必须回到初态
  （行尾 CR 与 LF 都认——收进缓冲时统一成换行，所以"必须 CRLF"只是第三方助手不带结尾符时的稳妥发法，不是协议要求）

## 失效边界
- 断电重上电后 `DONE` 常暗，在"只做下载、板上没有自启动镜像"的设计里是预期 ⇒ 不许用它判"位流丢了"
- 回读过大块内存之后，处理器可能被校验流程停在原地 ⇒ "串口没反应"其实是软件停跑，重跑三件套再判，别先改固件
- 本设计**完全不配置 PHY**（管理接口悬空、复位由上电计数驱动）⇒ 收包依赖芯片上电默认的自协商结果；
  在板级支持包里写死速率那类开关只属于 PS 侧 GEM/协议栈那条通路，换板或换通路则整段作废
- 换成交换机后，接收侧的隐性假设会让结论漂移（那几条只在 S1 有住处）；防火墙、异网段、线材与变压器仍是第一嫌疑
- 本页只管到"命令进去了、链路有增量"这一格；屏上算不算过不由本页负责
