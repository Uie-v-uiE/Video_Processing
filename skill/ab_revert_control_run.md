# S25 新红了先别怪硬件：把改动存补丁、退回未改状态、用**同一版台架**再跑一遍

## 触发
一版改动之后台架红了一批，而这些判据在上一份冻结报告里是绿的。现在**分不清**是
"我改坏了"、"尺子今天也改过"、还是"它本来就红了没人说"。

## 不适用
红项与改动明显同域（改了模糊算法、模糊判据红）——直接查代码即可。

## 动作
1. `git diff -- src/rtl > /tmp/x.patch`，然后 `git checkout -- <那几个文件>` 退回未改状态；
   **记下退回后的合指纹**（`find src/rtl -name '*.v' | sort | xargs md5sum | md5sum`）。
2. 用**完全同一版台架文件**（台架的 md5 也要一致）再跑一遍，得到"基线红名单"。
3. 比红名单：逐条相同 ⇒ 与本次改动无关；不同 ⇒ 差异项就是你的改动造成的，回去重推修法。
4. 恢复补丁，核对合指纹回到第 1 步记录的值。
5. 顺手查那份"绿"的冻结报告是不是**同一把尺子**：把历史报告的 `tb_md5` 与当前台架文件比一下——
   本项目就是这么发现 12 条红其实来自"台架自己把某个准静态激励留在了上一段的状态"。

## 完成判据
两份报告的头部指纹（top/tb/rtl）都写下来并对照过，结论里**指名**哪几条是既存、哪几条是新增。
只说"应该不是我改的"不算。

## 失效边界
- 跑基线期间不许再动源码（报告的出处就废了）；台架文件也要冻结。
- 若改动本身跨域共享状态（同一版台架在不同顺序下结果不同），基线跑一次不够。
- 台架跑一次很久时，先跑**单元级**的 A/B（本项目 `tb_v103` 一分钟，`tb_v98` 85 分钟）。
