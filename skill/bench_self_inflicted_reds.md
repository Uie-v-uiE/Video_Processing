# 台架自己造的红：八种"看起来是硬件错"的假红签名（以及各自怎么一眼认出来）

## 适用场景

新写或改动一个台架，第一跑就红 —— 而且红得"有道理"（数值看起来很像 bug 的症状）。
2026-09-25 写 `tb_v94_zoom_sel`（V8-8 八档手动缩放）时，**一次跑出了三种**假红，
硬件其实全对；如果按"红了就是硬件错"去改 RTL，就会把一个正确的实现改坏。
本仓库的规矩是"红了 = 没做完"，所以**必须先证明红不是判据自己造的**，再谈修 RTL。

签名一到四按"最容易被误当成 bug"排序；五以后是同一族的扩展（探针版、起点版、宿主版）。

## 签名一：期望值的算式写错（症状：数值差得很"整"，而且每一档都差）

```
DBG T3 档 0: inv=1023 期望=10 code=0
DBG T3 档 1: inv=776  期望=8  code=1
DBG T3 档 2: inv=512  期望=5  code=2
```

DUT 报的是 1023/776/512/341/…，期望报的是 10/8/5/3/… —— **全部差同一个因子**（这里是 100 倍量级）。
这就是"我的算式错了"，不是"硬件错了"：真实缺陷一般是**一格**不对或差 1，不会整整齐齐差一个常数倍。

根因：`inv = 256 / 倍率`，倍率用万分比 `x` 表示时应是 `inv = 256*10000 / x`；
我写成了 `25600*10000 / x`（把 Q8 的 256 当成 25600 用）。修法：分子用 `256*10000`，
四舍五入写成 `(2*256*10000 + x) / (2x)`（Verilog 台架里可以放心用 `/`，硬件那条不许，见 #58）。

**可复用的判据写法**：期望值要**从定义算**，不要从被测代码抄。
本仓库那条规矩（"判据要有自己的独立来源"）在这里的落地就是：
台架从"0.75 倍 ⇒ 倒数尺度 341"算，RTL 从"中点比较 ⇒ 档号 3"算，两条路交汇才是真凭据。

## 签名二：采样相位与被测节拍混叠（症状：值明明变了，判据却说一次都没变）

```
DBG T2 steps_ok=0 bad=0 min=256 max=298
```

`min/max` 在动 ⇒ `inv_scale` 确实在走；`steps_ok=0` ⇒ 我的比较一次都没抓到变化。
原因：帧节拍是 **40 拍**，而我"隔 2 拍比一次" ⇒ 采样相位固定在同一个残差类上（40 是 2 的整数倍），
变化永远落在两次采样的**中间**。这类假红最阴，因为"多采样几次"并不能修好它 —— 得改**步长与周期的互质关系**，
或者干脆**逐拍跟踪**（本仓库采纳：`prev` 存上一拍的值，每拍比一次）。

认出来的口诀：**同一份数据里，"极值在变"与"变化计数为 0"同时出现 ⇒ 一定是采样问题，不是被测问题。**
（同类前科：`#60` 里 `integer` 没清零 ⇒ 判据什么都没判却报绿；那条是"空跑"，这条是"空采样"。）

## 签名三：等待窗口比被测节拍短（症状：断言"停在 X"红，而 X 其实还没生效）

第一版里每换一档只 `repeat (8) @(negedge clk)`，而一档要**等一个 40 拍的帧节拍**才落进 `inv_scale`
（手动档故意做成"只在帧首换"，避免一帧内半屏新一档半屏旧一档）。
于是 T5a "先停在 0.25x" 读到的是**上一档**的值 341，接着 T5b 拿 341 当起点去验"1023→1021"，
一路红下去，而且每一层的"现象"都像真 bug。

修法：把"等固定拍数"换成**等事件**，并且等不到必须判红（不许静默通过）：

```verilog
task wait_change;            // 结果放模块级 wc_ok，不用 output 参数
    ... for (k=0; k<60 && !wc_ok; k=k+1) @(negedge clk) if (inv_scale !== v0) wc_ok = 1;
endtask
...
wait_change;
if (!wc_ok) chk("切回自动后确实动了（没等到变化=判据空跑）", 0);   // 等不到 ⇒ 红，不给绿
```

⚠ 两个附带教训：
- **别用同一个整数既当"本轮结果"又当"累计器"**。第一版写成 `if (!wait_change(t3_bad))`，
  任务内部把 `t3_bad` 覆盖了，累计器每轮被重置 ⇒ 判据恒绿（假绿比假红更糟）。改成模块级 `wc_ok` + 独立累计器。
- 判"跑没跑起来"的**下界要按物理算**：呼吸一趟是 128 步上行 + 128 步下行 = 256 个帧节拍 = 10240 拍，
  我却把窗口开成 900 拍 ⇒ T2b/T2c 一起红。窗口不够长不是判据太严，是**判据没跑到被测的那一步**。

## 签名四：激励自己的位序写反（症状：只有一半组合红，红的还是"最不该错"的那几位）

`tb_v796` 的 G1 第一次跑：`gi=0..3` 全对、`gi=4..7` 全错，期望与实际的差**永远只在最高那一位**。
"半数对、半数错，而且错在同一个位" 是**位序**的指纹，不是硬件的错 ——
激励写成 `sel = {1'b0, gi[2]}`，于是 `gi[2]=1` 落到了 `sel=01`（锁 ETH）而不是 `sel=10`（锁 PS），
硬件于是**正确地**报出 `force_ps=0`。

- 修法不是"把期望改成 `{~gi[1], ~gi[0], gi[2]}`"（那是拿硬件当规格）。是**把激励摆正**，
  再顺手把 8 组扩成 16 组，让 `sel` 的四种编码（`00/01/10/11`，含保留值 `11`）全被走一遍 ——
  红的时候判据要变**强**，不能变松。
- 多比特字段的期望值要**按编码手抄成表**（`case (sel) 2'd10: ... default: ...`），
  而不是写成 `(sel == 2'd10)` 这种与被测式子同形的式子：同形就等于把 RTL 抄进台架。

## 判据的判别力：为什么"末态检查"必须配一条"按时间量的检查"

`tb_v95`（lane23 的准静态总线 + 发沿时机）第一跑就 16/16 全绿 —— 这种绿必须先自证能红。
两次变异（凭据 `build/mutation_zoom_snap_r54.txt`）：

| 变异 | 结果 | 结论 |
|---|---|---|
| 同拍发沿 **+** 延迟发沿（沿翻倍） | Z3 / Z4 / Z7 三条红 | 计数类判据抓得住"沿多了" |
| **只**同拍发沿（把 8 拍延迟删掉） | **只有 Z4 红**，Z3/Z5/Z6 全绿 | 末态类判据（Z6"停在最后发出去的那一档"）**永远抓不到时序错** |

第二行才是重点：机制里"沿必须晚于数据稳定"这一条，如果台架只判"最后读到的值对不对"，
就是**一条永远不会红的判据** —— 它会放走一个真 bug（目的域采在总线翻转的当口），
还让人以为这一半已经验过。凡机制含"先后"，就要有一条以拍/ ns 为单位的断言，
并且**变异一次证明它有效**（上限也要卡：`lag_min == lag_max == 8 拍`，
只卡下限时"根本没发过沿"会顶着初值假绿）。

## 自查清单（新台架第一跑之前，30 秒）

1. 期望值是从**定义**算的还是从被测代码抄的？抄的要换掉。
2. 采样步长与被测节拍**互质**吗？不确定就逐拍跟。
3. 每个"等一等"是不是**等事件**而不是等固定拍数？等不到会不会判红？
4. 累计器/标志位有没有**初始化**？（`integer` 默认 X，X 参与 `if` 会两个分支都不走）
5. 观测窗口是否覆盖**一整趟**被测行为（含反向/回程）？
6. 拼多比特激励时，位序按**端口的文档**写死（`{a,b}` 的顺序抄端口注释），别靠下标推算。
7. 第一跑就全绿 ⇒ 做一次**变异**（改坏 RTL 一处，跑，改回来），记下哪几条红了；
   没有一条红 = 这条判据是装饰。全绿还写"某条判据已验证"就是撒谎。
8. 上面七条都过了还是红：那才是硬件的。

## 第五个签名（探针版，2026-09-25 r57）：**"查不到"被当成"不存在"**

同一族的**非台架**版本，发生在一次性探针脚本上（`OVERNIGHT_LOG` §41）：想回答"这颗 7020 有没有 UltraRAM 站点"，
三条问法都返回 0，看起来就是"没有"。但只有把**明知存在的东西**放进同一条命令里，才知道那个 0 是谁都不给：

| 问法 | 目标（返回） | 阳性对照（返回） | 结论 |
|---|---|---|---|
| `get_lib_cells -regexp {.*URAM288.*}` | 0 | `RAMB36E1` = **0**、`FDRE` = **0** | ❌ 问法坏（对照都查不到），0 不作数 |
| `get_sites -filter {TYPE == "URAM288"}` | 0 | `RAMB36` = **0**、`IOB` = **0** | ❌ 同上（这条命令在没有物理数据库时什么都不返回） |
| 直接例化原语 | `URAM288` 通过、`URAM1240` 被拒 | `RAMB36E1` 通过、`URAM288E` 被拒 | ⚠ 有对照、方向正确，但只回答"库里有这个原语"，**不等于器件有站点** |

三条规矩：
1. **任何"查不到 ⇒ 不存在"的推理，都要先在同一次运行里查一个明知存在的东西**（这里是 `RAMB36E1`/`IOB`）。
   对照没过，那个 0 就是命令语法问题，不是事实。
2. **同一个问题问不通就停手**（这里三次都不通 ⇒ 按"3 次就回退"的规矩收工），
   并把"未答上来"写进对外清单，改去查手册 —— 而不是换第四种命令猜法继续烧时间。
3. 探针**也要留日志**：三份 console（`build/uram_presence_console*.txt`、`build/uram_sites_console.txt`）
   里那些"0"以后会被别人当成证据引用，所以文件头必须写明"这两道问法已被自己的对照证伪"。

## 第六个签名（2026-09-25 上午，r58）：**判据没检查"起点是谁定的"**

八条仲裁判据连续多版全绿，某天上午一次跑红四条 —— 硬件没变，**变的是板子被人按过几下**：
片源模式环当时只有按键一个入口，脚本无法把它放回已知态，于是"锁 PS"状态下
`owner_eth` 本来就不该动，V3/V6 当然红。**这不是被测对象坏，是判据在赌一个它从没检查的前提。**

- 症状识别：红的判据都是"某个信号应当变化"型，而另一批"不该变化"型（V1/V5）全绿 ⇒ 先怀疑起点，不是先怀疑硬件。
- 修法是两步，**缺一不可**：① 给状态机一个**机器可写的复位入口**（这里是 GPIO 里的 mode 覆盖位）；
  ② 复位之后**读回来验**（`stat` 里 `mode=0`）。只发命令不验，等于把前提从"运气好"换成"我希望"。
- 通用检查：**每一条"应当变化"的判据旁边，写清楚它假设的初始态是什么、谁负责把它摆回去、摆没摆成功怎么知道。**

## 第七个签名（同一天）：**给模块加输入端口，四份台架的浮空 X 会伪装成功能坏了**

`src_mode` 加了 `ov_tog`/`ov_code`。例化 `pl_video_top` 的台架（tb_v6 / tb_v81 / tb_v82 / tb_v89）
没人接它 ⇒ 输入浮空成 `z` ⇒ 边沿检测 `osync[2] !== oprev` **恒真** ⇒ 每一拍都"收到一条命令"、
模式变 X、整条片源通路在台架里瞎掉。硅片上没有 X，所以这条**只会在仿真里出现**，
而它出现的形状与"新功能把老功能弄坏了"一模一样。

- 模块侧的防法（已采用，比"记得改台架"可靠）：**把"必须是实 0/1 才算一次事件"写进 RTL** ——
  `if ((osync[2] === 1'b1 || osync[2] === 1'b0) && osync[2] !== oprev)`。一个 LUT 都不多花。
- 流程侧的防法：**新加输入端口的同一轮必跑全量 L1**（不是只跑"相关的那两份"），
  因为浮空的是顶层往下传的端口，受害的往往是你没想到的那一份台架。



## 第八个签名（2026-09-25 上午，r58，宿主侧）：**解析器"半个接受"**，症状却长成"硬件没反应"

前七个都在说"判据把对的判成红"；这一条是它的**反面**：**输入被静默改意之后接受了**，
于是没有任何一处报红，只有操作者觉得"是我打错了"。用户原话就是它的指纹：

> "为什么要发 8 位或者十位 `pipe 00001100` 类似这种才能读到，五位读不到"

`parse_bits()` 只挡"第 10 个字符"，所以 6/7/8 位被当成 9 位**前面补零**收下。三种最常见的形状：
**静默补零 / 静默截断 / 静默取模**。认出来的办法只有一条：拿"操作者以为自己在说什么"去对
"程序实际听成了什么"，两边一致才算接受 —— 所以修法必须自带一句回显（这里是 `pipe show`
按名字念出九位控制字，而不是再让人去猜屏上那五位）。

规则：**要么明确接受、要么明确拒绝并且不产生副作用**。"拒了还写寄存器"与"收了但不改"同罪，
所以判据里除了"这条要红"，还要一条 `!` 反例（板级电池里那条 `!sel=`）证明**没写**。

判据本身的写法也记一笔（`src/host/pipe_len_check.mjs`）：行为类判据**把被测函数原文抠出来用宿主
gcc 现编**，不要在测试里重写一份 —— 重写一份就把"两处各说一遍"这个病搬进了判据；
位号则从 **RTL** 抠（`proc_pipeline.v` 的位定义表、`effect_ctrl.v` 的老五位翻译），
这样固件抄件、名字表、help 文案三份都有人对。两条变异对照（删长度口径 ⇒ 红 5/6；
删位序契约 ⇒ 红 3/5）是这条判据"真的在看"的证据。
