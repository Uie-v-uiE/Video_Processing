# 台架自己造的红：三种"看起来是硬件错"的假红签名（以及各自怎么一眼认出来）

## 适用场景

新写或改动一个台架，第一跑就红 —— 而且红得"有道理"（数值看起来很像 bug 的症状）。
2026-09-25 写 `tb_v94_zoom_sel`（V8-8 八档手动缩放）时，**一次跑出了三种**假红，
硬件其实全对；如果按"红了就是硬件错"去改 RTL，就会把一个正确的实现改坏。
本仓库的规矩是"红了 = 没做完"，所以**必须先证明红不是判据自己造的**，再谈修 RTL。

三种签名，按"最容易被误当成 bug"排序。

## 签名一：期望值的算式写错（症状：数值差得很"整"，而且每一档都差）

```
DBG T3 档 0: inv=1023 期望=10 code=0
DBG T3 档 1: inv=776  期望=8  code=1
DBG T3 档 2: inv=512  期望=5  code=2
```

DUT 报的是 1023/776/512/341/…，期望报的是 10/8/5/3/… —— **全部差同一个因子**（这里是 100 倍量级）。
这就是"我的算式错了"，不是"硬件错了"：真实缺陷一般是**一格**不对或差 1，不会整整齐齐差一个常数倍。

根因：`inv = 256 / 倍率`，倍率用万分比 `x` 表示时应是 `inv = 256*10000 / x`；
我写成了 `25600*10000 / x`（把 Q8 的 256 当成 25600 用）。修法：分子用 `256*10000`，
四舍五入写成 `(2*256*10000 + x) / (2x)`（Verilog 台架里可以放心用 `/`，硬件那条不许，见 #58）。

**可复用的判据写法**：期望值要**从定义算**，不要从被测代码抄。
本仓库那条规矩（"判据要有自己的独立来源"）在这里的落地就是：
台架从"0.75 倍 ⇒ 倒数尺度 341"算，RTL 从"中点比较 ⇒ 档号 3"算，两条路交汇才是真凭据。

## 签名二：采样相位与被测节拍混叠（症状：值明明变了，判据却说一次都没变）

```
DBG T2 steps_ok=0 bad=0 min=256 max=298
```

`min/max` 在动 ⇒ `inv_scale` 确实在走；`steps_ok=0` ⇒ 我的比较一次都没抓到变化。
原因：帧节拍是 **40 拍**，而我"隔 2 拍比一次" ⇒ 采样相位固定在同一个残差类上（40 是 2 的整数倍），
变化永远落在两次采样的**中间**。这类假红最阴，因为"多采样几次"并不能修好它 —— 得改**步长与周期的互质关系**，
或者干脆**逐拍跟踪**（本仓库采纳：`prev` 存上一拍的值，每拍比一次）。

认出来的口诀：**同一份数据里，"极值在变"与"变化计数为 0"同时出现 ⇒ 一定是采样问题，不是被测问题。**
（同类前科：`#60` 里 `integer` 没清零 ⇒ 判据什么都没判却报绿；那条是"空跑"，这条是"空采样"。）

## 签名三：等待窗口比被测节拍短（症状：断言"停在 X"红，而 X 其实还没生效）

第一版里每换一档只 `repeat (8) @(negedge clk)`，而一档要**等一个 40 拍的帧节拍**才落进 `inv_scale`
（手动档故意做成"只在帧首换"，避免一帧内半屏新一档半屏旧一档）。
于是 T5a "先停在 0.25x" 读到的是**上一档**的值 341，接着 T5b 拿 341 当起点去验"1023→1021"，
一路红下去，而且每一层的"现象"都像真 bug。

修法：把"等固定拍数"换成**等事件**，并且等不到必须判红（不许静默通过）：

```verilog
task wait_change;            // 结果放模块级 wc_ok，不用 output 参数
    ... for (k=0; k<60 && !wc_ok; k=k+1) @(negedge clk) if (inv_scale !== v0) wc_ok = 1;
endtask
...
wait_change;
if (!wc_ok) chk("切回自动后确实动了（没等到变化=判据空跑）", 0);   // 等不到 ⇒ 红，不给绿
```

⚠ 两个附带教训：
- **别用同一个整数既当"本轮结果"又当"累计器"**。第一版写成 `if (!wait_change(t3_bad))`，
  任务内部把 `t3_bad` 覆盖了，累计器每轮被重置 ⇒ 判据恒绿（假绿比假红更糟）。改成模块级 `wc_ok` + 独立累计器。
- 判"跑没跑起来"的**下界要按物理算**：呼吸一趟是 128 步上行 + 128 步下行 = 256 个帧节拍 = 10240 拍，
  我却把窗口开成 900 拍 ⇒ T2b/T2c 一起红。窗口不够长不是判据太严，是**判据没跑到被测的那一步**。

## 自查清单（新台架第一跑之前，30 秒）

1. 期望值是从**定义**算的还是从被测代码抄的？抄的要换掉。
2. 采样步长与被测节拍**互质**吗？不确定就逐拍跟。
3. 每个"等一等"是不是**等事件**而不是等固定拍数？等不到会不会判红？
4. 累计器/标志位有没有**初始化**？（`integer` 默认 X，X 参与 `if` 会两个分支都不走）
5. 观测窗口是否覆盖**一整趟**被测行为（含反向/回程）？
6. 全部改完再判红：如果这时还是红，才是硬件的。
