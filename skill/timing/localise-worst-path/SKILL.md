# 读时序报告定位瓶颈类型

## 适用场景

- 报告里 slack 是负的（或余量薄），但下一步该动哪一类东西判不下来。
- 解析脚本抓不到字段、抓出空值，却把空当 0 用——判读错的基本都是形状靠猜。
- 只看到 hold 违例"要加延迟"，没拆过差额在到达侧还是需求侧。
- 想"换个钟／挪个沿"，把它当成一次便宜的试验。

## 使用方法

**低自由度第一步：先把报告的形状实测，再写解析。** 顺序固定，不许凭记忆：

1. 打开**已布线**检查点（读不到就 REFUSE，不许拿综合后的顶替，后者的延迟是估计值），对同一个 `-delay_type` 出一份 `report_timing`，原文整段落进证据件。
2. 用一次只读探针把关键行的**原文**打出来核对：摘要行 `Slack (MET|VIOLATED) : <值>ns (required time - arrival time)`——hold 报告里减数被互换，是 `(arrival time - required time)`；`Requirement: … (…rise@… - …rise@…)`；`Data Path Delay: <x>ns (logic <a>ns (<p>%)  route <b>ns (<q>%))`——**百分比在括号里**，不在 `…ns` 尾巴上；`Logic Levels: <n> (<原语>=<计数>)`；`Clock Path Skew: …(DCD - SCD + CPR)`——hold 侧是 `(DCD - SCD - CPR)`；`Clock Uncertainty` 是否出现（内部 hold 常没有这一行）；逐级表头与 `Incr`／`Path` 两列的相对位置。
3. 解析只允许按核对过的形状匹配；任何一列抓不到 ⇒ `NA`／`NOT_MEASURED`，不许留空、不许当 0。命令名与选项名也问工具（`help <命令>`），不要凭记忆——猜一个不存在的选项会静默产出空件，红的是你的尺子。

**先跟用户确认**：能不能动约束、能不能动时钟结构（挪沿属于后者）、哪些路径允许被豁免覆盖（不许为了好看乱挂豁免）。

四类瓶颈的判别与各自第一手方向（先用两个数分开它们：`Logic Levels` 与 `route %`）：

- ① **逻辑级数深**：levels 大、`route %` 不占多数、逐级延迟集中在最深那几级 ⇒ 走 `fix-logic-depth`，先算收益上限再动手。
- ② **布线主导**：levels 很小（1～3）而 `route %` 过半、单段 net 延迟就是差额主体 ⇒ 先看拥塞读数与这根网的扇出计数，**别改逻辑**；改逻辑只会让终点族换人。
- ③ **高扇出广播网**：net 行的 `fo=` 很大、一个驱动散布到很多片、同一驱动名下多族同时紧 ⇒ 走 `reduce-fanout-and-congestion`；机制证据（复制是否真发生）与结果证据（名册差分）分开写。
- ④ **时钟树分量**：差额出现在 `Clock Path Skew`／`Clock Uncertainty`／`Requirement` 与源侧网络延迟里，而数据路径本身很短 ⇒ **先确认这些分量的口径**（这条钟从哪个源脚出来、不确定度怎么建模、偏移是显式约束还是自动布局引入），再谈挪沿。**换钟／挪沿属结构改动，必须走正式一轮**（完整构建＋台架＋名册差分），不许用只重跑局部布局布线的捷径构建出结论。
- 附一条 I/O 判别：出现 `Input Delay`／`Output Delay` 行、或 `Path Group: (none)`、或 `Slack: inf` ⇒ 这是"没被约束"不是"违例"，先补窗再谈修法。

hold 的算术怎么拆（同沿 hold 的 `Requirement` 常是 0.000，所以差额全在两侧分量上）：

```
到达侧 = 起点时钟网络延迟（源侧）+ 单元延迟 + 布线延迟   （取最小路径、快角）
需求侧 = 最小需求时刻 + 终点时钟网络延迟 + 时钟路径偏移（hold 用 -CPR）+ 目的寄存器的 hold 时间
slack_hold = 到达侧 - 需求侧
```

差额落在哪侧决定方向：落在**到达侧**（数据路径太短）⇒ 加长路径／避免过短锥／别把复制点放在这条路的前段；落在**需求侧**（两端时钟树不对称、偏移、不确定度建模）⇒ 这是时钟口径问题，先按 `clock-tree-changes-checklist` 确认，不要拿逻辑改动去凑一个 skew 数。还要核对角分配：I/O 路的 setup／hold 所取的工艺角可能与片内路相反，拿片内的直觉读它是错的。

## 失效条件

- 手上只有一份全局最差报告：你判出的"瓶颈类型"是整个设计最差那一族，不是你要改的锥。
- 形状靠记忆：换工具版本／换 corner 后摘要行措辞、单位后缀或百分比位置变了，解析静默返回空 ⇒ 整列 NA 还照写结论。征兆是某列全空，或 `route_pct` 全等于同一个数。
- 把综合后报告与已布线报告混着看 ⇒ "布线主导"这一类判读不成立。
- 改后终点族换了名字还沿用上一轮的判读（不可比，必须退回逐域名册）。
- 把 `Logic Levels` 当成整个设计的最深层级：它只数这一条路径上的单元级数。

## 已验证效果

以下读数来自某一次具体设计，量级只用于说明形状，随设计而变，不可当普适结论引用。

- 某次实测：一条 1 级逻辑的路，`route %` 93.6%，单段广播网独占 5.690 ns ⇒ 判为②／③类，刀落在复制与放置，逻辑侧无可拆。
- 某次实测：一条 22 级（其中 9 级在进位链）的锥，`route %` 59.2% ⇒ 主导项是级数，判为①类，但收益上限要先算。
- 某次实测：某条姊妹路 `route %` 70.5%，据此判"逻辑修法收益上限低"，没有开构建。
- 形状三条真值（百分比在括号内、hold 的 skew 符号为 `- CPR`、hold 摘要行减数互换）都来自一次只读探针的原文核对；此前凭记忆写的两版解析各产出过整列空值，都是把空当 0 才没被发现。
