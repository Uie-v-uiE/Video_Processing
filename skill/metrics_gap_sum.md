# S14 · 性能指标采集：把"推流 N 秒 → 读计数器 → 算成表"做成一条可复跑的命令

类别：**校验脚本 + 案例模板**（对应指南 §3.3.5.2 里点名的"性能与资源数据自动采集并生成报告的工具"）

## 适用场景

任何"硬件自己数了数，PC 要把它读回来变成指标"的场合：链路吞吐、丢包、帧间隔抖动、
时钟漂移。本仓库的实现是 `src/host/metrics.mjs`（约 150 行，Node，无第三方依赖）。

**不适用**：
- 需要"眼睛"的指标（glass-to-glass 延迟、画质主观评价）——本方法只能给**链路内**的数；
- 计数器不是单调累计的场合（比如本仓库 `rows_miss_max` 是终身保持的峰值，只能取 max 不能算差值）；
- 采样期间 CPU 被 JTAG 停住的系统（Zynq 上 `mrd` 会halt A9，此时"墙钟时间"包含停机时间）。

## 三条会算错的式子（这就是本件存在的理由）

1. **`gap_sum` 的分母是"段数 N−1"，不是帧数 N。**
   硬件里第一帧只建立基准、量不出间隔（`link_monitor` 的 `have_base` 就是这个意思），
   所以 N 帧只产生 N−1 段。写成分母 N ⇒ 平均间隔被低估、fps 被高估，误差 1/N：
   30 帧时约 3 %，短测（`--count 5`）时 20 %。
   判据写法（`--selftest` 里）：
   ```js
   const segs = Math.max(0, Math.round(frames_recv) - 1);
   const avg_gap_ms = segs > 0 ? d('gap_sum') / segs : NaN;
   // 反面对照：错用 N 作分母必须给出**不同的** fps，否则这条判据是恒真的
   ```
   只有一帧时段数为 0 ⇒ 必须是 `NaN` 而不是 `0 ms ⇒ Infinity fps`。
2. **累计计数器一律取差值，"终身保持"的量取 max。**
   差值：`drop_words / frames_bad / pkt_err / cdc_episodes / pkts / bytes / gap_sum`；
   取 max：`rows_miss_max`、`gap_min`（min 只在**归零之后**才是本次测量的最小值 ⇒
   测量开始前必须先跑一次 `--gapclr`）。把峰值当差值算会得到负数或假 0。
3. **"没丢字"的判据要两条一起。**
   `drop_words` 增量为 0 **且** `cdc_episodes` 增量为 0。只看前者会漏掉
   "FIFO 满过但刚好没溢出"这种即将出事的状态。

## 使用方法（照抄可用）

```bash
# 1) 正常测量：基线（含帧间隔归零）→ 推流 → 读回 → 出表 + 存档
node src/host/metrics.mjs --fps 30 --seconds 20 --tag r32 --out board/evidence_r32
# 2) 制造丢包，看验收门（每 40 个包确定性丢 1 个）
node src/host/metrics.mjs --fps 30 --seconds 15 --drop-every 40 --tag r32_drop
# 3) 先跑算式自检（不打板子；换题目时改这里，不改采集）
node src/host/metrics.mjs --selftest
```
产出：`metrics_<tag>.md`（人读的表）+ `metrics_<tag>.json`（**前后两次原始读数**）。
表里每个结论都必须能在同一份 JSON 里找到那几个数——这是"评委能回查"的最低要求。

依赖：读计数器需要一个**机器可读**出口。本仓库给 `health_read.mjs` 加了 `--json`
（只吐一行 JSON 就退出），因为去解析中文判读行会把两个工具焊死：改一句文案就崩。

## 已验证效果

- `--selftest` **14 条**全绿。其中一条是**反面对照**：故意用错分母算一遍，必须与正确值差 >0.3 fps
  ⇒ 证明"分母 N−1"那条判据不是恒真（这是本仓库对检查器的一贯要求）。
- 板级：本工具在 Zynq7020 上采集的 15 fps 基线与 OSD/串口两条独立读数一致
  （原始件见 `board/evidence_r32/`，若当次未跑成则标注"未验证"，不假装有）。

## 第二课（2026-09-24 补）：分母的**总体**也要对，不只是 N 与 N−1

第一次用 `--drop-every 200` 做受控丢包时，表里打出 `平均帧间隔 22.39 ms`，
而同一行的 `gap_min = 6667 ms` —— **平均值小于最小值，算术上不可能**。
根因不是 N/N−1，而是**分子分母来自两个不同的总体**：

| 量 | 谁 produced | 包不包括"被验收门作废的帧" |
|---|---|---|
| 交付帧数（旧分母） | `bytes / 帧长` | **包括**（作废的帧照样交付字节） |
| `gap_sum`（分子） | 硬件只给**被接收**的帧记间隔 | **不包括** |

于是丢包越重，分母虚高越多，平均间隔被摊薄、`fps_from_gap` 虚高（那一版报 44.7 fps，
真实是"整轮没有一段可算"）。正确写法：`接收帧数 = 交付 − 作废(frames_bad)`，段数再减 1。

**两条可以照抄的规矩：**
1. 任何"总量 ÷ 计数"的指标，先问一句**分子是谁累加的、分母是谁数的**，两者必须是同一批事件。
   本项目里作废/丢弃这类"到了但没算"的事件总存在，所以默认就要怀疑。
2. 给指标加一条**自相矛盾检查**：平均值必须落在 `[min, max]` 里，越界就当场把这句话印出来，
   而不是等人去看。`metrics.mjs` 现在会打
   `[M][自相矛盾] 平均间隔 X ms 不在 [min, max] 之内 ⇒ 分母与 gap_sum 不是同一总体，这张表不能用`，
   并在 JSON 里留 `gap_avg_impossible: true`。

判据也要跟着升级：`--selftest` 从 8 条到 **14 条**，新增的三条是
"有作废时分母用 接收−1"、"整轮都作废 ⇒ 必须是 NaN 而不是一个像样的 fps"、
"avg 出界必须自曝 + 正常输入不许误报"。**第二条尤其重要**：一个报错的判据如果错得安静，
比不判更糟 —— 它会让人以为表是对的。

## 失效条件 / 什么时候别信这张表

- **推流期间不要用 JTAG**：`mrd` 会停住 A9，墙钟 fps 立刻失真（本工具只在推流前后各读一次，
  就是为了避开这点）。
- `hb_slow=1` 或 `hb_gone=1` 时，**所有 ms 类数字都是周期数不是毫秒**（PHY 断链时 RXC 会被
  拉到约 1/48），此时表里的 `avg_gap_ms / fps_from_gap` 只能当序指标看——工具会把这两个标志
  一起印出来，就是为了让读的人当场知道该不该信。
- 帧长写死 `FRAME_BYTES=307200`（512×300 RGB565）。换分辨率必须同步改，否则帧数按字节折算就错了。
- 载荷字节增量不是帧长的整数倍时，`frames_recv` 是小数：那是"有半帧没凑齐"的信号，
  不要四舍五入掉，它本身就是要报的东西。
