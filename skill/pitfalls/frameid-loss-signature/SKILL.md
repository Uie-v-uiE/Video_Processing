## 1. 一句话用途

用自描述图案 + 相位分带定位丢字在哪一级。

## 2. 适用场景

- 当数据流写进内存/DDR，肉眼只看到花屏 / 拖影 / 黑纹，而你还不知道**是不是在丢数据、丢在哪一级**时。
- 当任何"PC → 板卡 → 内存 → 显示/计算"链路要对**数据完整性**取证时（视频、点云、ADC 流、DMA 采集）。
- 当有人要用"加深缓冲"来修丢数据，而你还没证明瓶颈是深度还是排空速率时。
- 当你已经回读了一堆数，但每个数说不清它来自第几帧时（图案不携带帧身份 ⇒ 统计无法归帧）。

## 3. 不适用 / 失效条件

- 不适用：画质类问题（缩放走样、色彩、抖动）——本判据只判数据完整性，不判画质。
- 不适用：无法回读内存的平台（无 JTAG、无调试端口）：判据失效，只能退化为板内自检 + 计数寄存器。
- 失效：载荷不是字宽整数倍时，"包内相位"会与打包器的部分字状态混在一起 ⇒ 先解决对齐再用本判据。
- 失效（测量工具自己会造假）：用**恒定图案**得到的"100% 命中"是假的——恒定图案只能验地址映射，
  结构上发现不了逐帧丢字。
- 结构性盲区：这套判据"看不见自己不覆盖的工况"——只出现在帧尾/边缘的残留，基线回读一次都不会出现。
  遇到这种工况时本条没能给出板级区分力，相关修复的证据等级只到"机理 + 仿真双向判据"，不许写"板上已排除"。
- 前置的失效面：回读会把处理器停住 ⇒ 之后任何复测前必须重跑"引导→刷 PL→设源"三件套，
  否则量的是"PS 不跑"的工况（判读分叉见第 6 节末条）。

## 4. 前置条件

- 一条能回读被写内存的通道（JTAG / xsdb / 自研回读脚本），并且你接受它会停住处理器。
- 图案生成端可写：每个字的每个 lane 能写成"字序号 + 帧号"，反解只需一次减法。
- 采集脚本能改成"发完再读"（一次回读要几秒，边推边读会让每个地址段读到不同时刻的帧）。
- 回读前能关/绕开 D-Cache，否则同一块内存三次读出三组数。
- 已知两个常数：每帧字数、每包载荷字节数（换题目只改这两个，见第 8 节）。
- 本条目在 Vivado/Vitis 2025.2.1 的裸机 + DDR 回读流程下写成（版本真相源见 `skill/_meta/naming-and-format.md`）。

## 5. 使用方法

1. **图案必须逐帧变化**。让回读能对每个字反解出"它来自第几帧"：本仓做法是把第 `w` 个字的每个 lane 写成
   `value = (w + n) & 0xffff`（`n` = 帧号），反解 `n_implied = (value − w) & 0xffff`。
   完成后应看到：每个字都能解出一个帧号，且不同帧给出不同值。
2. **先停流再回读**。把采集脚本按"发完再读"写死，而不是靠人记。
   完成后应看到：这次回读的帧号跨度只覆盖你预期的那一两帧。
3. **把丢字按三个维度展开**（三个维度对应三种不同机理，缺一不可）：
   - 包内相位：丢字率 vs 字节偏移分带；
   - 空间连续性：连续丢字带的长度分布、最长带；
   - 粒度：同一宽字内的两个窄字是否属于不同帧。
   完成后应看到：一张带**数字**的分带表（最新帧占比、各相位带丢字率、最长连续丢字带、半字错帧比例），修复前后各一组。
4. **判"换帧是否原子"**：看每个 bank 的帧号跨度。
   完成后应看到：健康 = 每个乒乓 buffer 恰好一帧。
5. **控制缓存这个变量**：从调试端口回读前先关/绕开 D-Cache。
   完成后应看到：同一地址段重复读三次的数一致。
6. 换题目时只改两个常数（每帧字数、每包载荷），其余不动——这本身就是"方法可迁移"的检验。
   完成后应看到：表结构一个字节没变，只有那两个常数变了。

## 6. 判读与失败分叉

- 步骤 1：
  通过 = 每字可反解帧号，且帧号随帧递增。
  失败 = 图案恒定 ⇒ 本条不成立，此时任何"100% 命中"都要判 `FAIL`（测量工具自己造了假）。
  读不到输入 = 回读全 0 或读不出有效图案 ⇒ `NOT_MEASURED`，先确认 PL 已加载、推流真的在发、通道没被缓存挡住；
  不要改成"跳过这一段"。
- 步骤 2：
  通过 = 帧号跨度 ≤ 预期。
  失败 = 跨度达几十帧 ⇒ 边推边读，**这次统计全废**（不是"取平均"），停流后重跑。
  读不到输入 = 脚本只打了收尾文案没有表 ⇒ 先看分带表有没有数（见本节末"判读位置"）。
- 步骤 3：
  通过 = 三个维度各自成表且有数，修复前后各一组，差得出来的才叫结论。
  失败 = 只有总丢字率、没有分带 ⇒ 无法区分机理，判 `FAIL`，补分带而不是加缓冲。
  典型分叉：相位呈**固定台阶** ⇒ 下游**平均排空速率**跟不上，加深缓冲无用；
  一条几百字长带 ⇒ 某窗口端口被完全占死；整包那么长 ⇒ 前端整包丢失；
  半字跨帧比例高 ⇒ 丢在窄粒度（写侧门控 / CDC），不是整字丢弃。
- 步骤 4：
  失败 = 一个 bank 混进十几帧 ⇒ 提交/切换逻辑有问题（不是带宽问题）。
  读不到输入 = bank 边界未知 ⇒ `NOT_MEASURED`，先把乒乓基址读清楚再算跨度。
- 步骤 5：
  失败 = 三组数不同 ⇒ 缓存还在挡，本轮所有分带数不可用，关掉重读。
- 步骤 6：
  失败 = 除了两个常数还要改判据文字 ⇒ 表形里混进了本题目专用的东西，回到步骤 3 重写维度。
- 判读位置：脚本结尾固定打的那行"没读到有效图案"可能与同一轮的 100% **不矛盾**，只是文案位置错的假警报
  ⇒ 判读看判据表，不看最后一行。
- 复测前置：一旦做过回读，处理器被停住过 ⇒ 先重跑"引导→刷 PL→设源"三件套，再念任何新数。

## 7. 已验证的效果

- 本轮（2026-10-04）**未重跑**：这套取证要板卡 + DDR 回读 + 停流，本轮禁止上板与串口，所以本条**没有**本轮实测数字；
  "本轮复现下面那组数"记 `【待验证】`。
- 仓库里留下的历史读数（台账 `report/log/ISSUES.md` #34，并见 #30 / #31；属更早轮次的件，本文只引用不重跑）：
  修复前最新帧占比仅约 42~52%、包尾相位带丢 54~64%、半字错帧约 18.6%；
  根因是"每写一字就等 B 响应"把在途深度钉成 1；流水化后三档帧率全部 100.0%、各相位带 0.0%、半字错帧 0。
  这组数是"分带表"这一交付物的**形状样本**，不是本轮可复现的凭据。
- 仿真侧同一签名的形状（历史记录，本轮未起仿真 ⇒ `【未实测】`）：
  判据能在仿真里复现同一签名——端口被独占 N 拍 ⇒ 丢字起始位置恰好等于打包器 FIFO 深度。

- 不再适用的条件：图案已保证逐帧唯一、分带表已成惯例、瓶颈已由 S4 那笔账定量 ⇒ 本条退化为回归检查。
- 迁移到新题目/新板卡要改的地方：
  1. 两个常数：每帧字数、每包载荷字节数；
  2. 字宽与 lane 数（`& 0xffff` 那个位宽要跟着改，宽字拆窄字那一半同理）；
  3. 乒乓 bank 的个数与基址来源；
  4. 回读通道（JTAG / xsdb / 自研脚本）以及它是否会停住处理器；
  5. D-Cache 的关闭方式（本仓做法与其 MMU 设置绑定，示例取值，需按自身工程替换）。
- 平台相关：判据本身与器件家族无关，只依赖"能回读被写内存 + 图案能反解帧号"这两件事。
