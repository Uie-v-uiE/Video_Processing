# 检查器自带自测与变异对照

## 适用场景

- 交付一个检查器/门禁脚本之前，需要证明它"能红"而不只是"能跑"。
- 收紧一条已有判据（阈值调严、解析加约束、把提示升级为拒绝）。
- 出现：`--self` 全绿而真实运行红；一条根因把 N 条判据一起染红；某条判据从项目开始就没红过。
- 报告文件被自己的遍历扫进射程，出现"上一轮的输出触发下一轮"的自指现象。

## 使用方法

1. 每个检查器自带 `--self` 入口，内置正/负样例各至少一条，并打印每层计数。命令形状（低自由度）：

   ```text
   node tools/<checker>.mjs --self              # 只跑夹具
   node tools/<checker>.mjs --self --mutation   # 再逐条注入缺陷
   ```

   跑完应看到：每条判据各有"正样例绿、负样例红"的配对；`判 N 项` 里 N 是比较次数；
   退出码 0=全绿、1=有红、2=有未测（见 `three-state-verdicts`）。缺依赖、缺夹具时
   必须走 2，不许跳过并返回 0。

2. **夹具必须复制真实件的形状**：列数、表头、单位、分隔符、字段顺序、行尾、编码。
   否则 `--self` 全绿而真实运行红——因为夹具**绕过了提取层**，负样例的红是断言硬编码出来的，
   不是从数据里解析出来的。征兆：真实运行报"读不到/列数不符/字段改名"，而这类报错在自测里从没出现。
   做法：夹具从真实件裁一段再脱去专有内容，而不是手写一份"我以为的形状"。

3. 判据被**收紧之后必须重跑真件**：只跑 `--self` 买通的只是测试。
   收紧后至少跑一次未修改的干净树（见 `bench-expectations-first`）与一次已知有缺陷的件，
   确认新增的红都可解释，且没有把无关判据一起带下来。

4. **一条变异只该红一条判据**。若一个根因合理连带红 N 条（例如共用同一个提取层），
   要把连带列出来写成一句"注入此处，预期 X/Y/Z 同时红，因为它们共用提取层"，
   而不是削弱判据让它少红——削弱判据换来"归因干净"是拿尺子换叙事。

5. **正对照必须能动**：一条永远不可能红的判据等于没有判据。
   每条判据登记"它最近因什么红过"（哪次注入、哪个已知缺陷）；登记不出来的标注"未配对照"，
   在门禁里降级为提示、不参与放行结论，并在下一轮补上注入。

6. **检查器自己的输出不要放进交付树**：报告会把自己扫进射程——
   报告里出现的字符串触发下一条判据，形成自指红；或报告被当成输入解析，形成自指绿。
   输出写暂存目录或包外，遍历里显式排除，并打印排除了哪些路径。

7. **条数本身就是被引数字**：文档与索引里会有"这个检查器有 N 条判据"这类句子。
   改判据条数（增、删、合并）要在**同一次提交**里改掉所有引用它的句子：
   先全文检索所有出现处，再改，再复跑门禁与索引一致性检查。漏一处就得到
   "文档 N 条 / 实跑 N+1 项"这种对不上（见 `mutation-controlled-coverage`）。

**先查什么**：检查器读的提取层在哪、字段来自真实件的哪个位置，以一手文件形状为准，
不按记忆里的表头写解析；协议/工具的字段定义查厂商用户指南或格式说明 ＞ 应用笔记 ＞ 教程 ＞ 记忆。
**先跟用户确认什么**：把判据从门禁摘出或降级、扩充豁免、调阈值——这些改的是"什么叫通过"；
以及是否允许为变异在真件里临时插桩（会动源码，须能一键复原）。

## 失效条件

- 夹具与真实件同源生成（都出自同一个函数）：自测永远只测实现层，提取层的形状变化扫不到。
- 变异靠"改期望值"而不是"改被检数据"：只证明比较在跑，不证明提取在跑。
- 判据之间共享状态（前一条写临时文件、后一条读它）：单条自测绿、跑批红，归因彻底乱掉。
- 报告落进被扫描目录后，红来自上一轮自己的输出——你会开始"修读数"而不是修设计。
- `--self` 依赖外部命令而环境里没有，脚本 `try/catch` 后静默返回成功：全绿假象。
- 连带红没记录，下一轮为了让归因干净而放宽判据，尺子在无人注意时退化。

## 已验证效果

未量过，属建议。采用本条的最低交付物：每条判据的红/绿配对表（注入点 → 变红的判据 → 复原后变绿）、
夹具与真实件的形状对照说明（列数/表头/单位逐项）、以及一次收紧判据后重跑真件的读数。

## 来源

长自三类观察：`--self` 全绿而真实运行红（夹具绕过了提取层）；收紧判据后只跑了自测没跑真件；
检查器把自身输出扫进射程导致自指读数。对应坑清单 `ruler-fake-greens`、`package-integrity`、
`build-artifact-races`。配套见 `bench-expectations-first`、`three-state-verdicts`、`golden-reference-compare`。
