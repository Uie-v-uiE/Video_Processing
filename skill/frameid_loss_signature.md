# S9 · 用「逐字反解帧号 + 包内相位」定位丢字机理

## 适用场景
数据流写进内存/DDR，肉眼只看到「花屏/拖影/黑纹」，但**不知道是不是在丢数据、丢在哪一级**。
任何「PC → 板卡 → 内存 → 显示/计算」的链路都适用（视频、点云、ADC 流、DMA 采集）。

## 使用方法

1. **图案必须逐帧变化**。本项目用 `frameid`：第 `w` 个 64bit 字的每个 16bit lane
   写 `value = (w + n) & 0xffff`（`w`=字序号，`n`=帧序号）。
   回读时反解 `n_implied = (value - w) & 0xffff` ⇒ 每个字「来自第几帧」直接可读。
   恒定图案（值=字号、纯色、棋盘）只能验地址映射，**结构上发现不了逐帧丢字**。
2. **先停流再回读**。回读耗时远大于一个帧周期时，边推边读会让每个地址段读到不同时刻
   的帧，统计全废（症状：反解出的帧号跨度达几十帧）。
3. 把丢字按**三个维度**展开（`src/host/ddr_stale.mjs` 直接输出）：

   | 维度 | 指标 | 指向的机理 |
   |------|------|-----------|
   | 包内相位 | 丢字率 vs 字节偏移分带（0–48 B / 48–96 B / …） | 呈**固定台阶** ⇒ 下游**平均排空速率**跟不上（深度无用） |
   | 空间连续性 | 连续丢字带的长度分布、最长带 | 一条几百字长带 ⇒ 某窗口端口被完全占死；≈整包长度 ⇒ 前端整包丢失 |
   | 粒度 | 同一 32bit 内两个 16bit 是否属于不同帧 | 高比例 ⇒ 丢在 16bit 粒度（写侧门控/CDC），不是整字丢弃 |
4. 判「换帧是否原子」：看每个 bank 的**帧号跨度**。健康 = 每个 bank 恰好一帧
   （乒乓下相邻两帧分属两 bank）；混十几帧 = 提交/切换逻辑有问题。

## 已验证效果
- 本项目据此把「红块撕裂 + 拖影 + 黑横纹」从「显示侧问题」改判为入包链丢字：
  修复前最新帧只占 42~52%、包内 0–48 B 丢 6.7% / 之后丢 54~64%、18.6% 的 u32 半字错帧。
- 定位到根因 = `axi_frame_saver64` 逐字等 B 响应（在途深度 1 ⇒ 20 MB/s 上限），
  流水化后 15/30/60 fps 全部 100.0%、各带 0.0%、半字错帧 0/76800。
- 同一套判据在仿真里复现：`sim/tb_v6_pingpong.v`（端口被独占 N 拍 ⇒ 丢字起始位置
  恰好等于打包器 FIFO 深度 512）与 `sim/tb_v6_ingress_integrity.v +FULL`（221 包整帧）。

## 失效条件
- 无法回读内存的平台（无 JTAG、无调试端口）：判据失效，只能退化为
  板内自检 + 计数寄存器（需另外构造可观测出口）。
- 开启 D-Cache 的 CPU 侧读回会读到缓存 ⇒ 必须先停核/关缓存再读（本项目用
  `rst -processor`，且读完不 `con`）。
- 载荷不是 8 字节整数倍时，「包内相位」会与打包器的部分字状态混在一起，
  先把对齐解决掉再用本判据。
- 只能判**数据完整性**；画质类问题（缩放走样、色彩、抖动）不适用。
