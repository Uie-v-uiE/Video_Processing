name: wns-logic-vs-route-lever
description: 查"负 WNS 该动哪一手"的杠杆对照表：当有一条（或一族）setup 违例，直觉动作是把那段算术改短或把高扇出复制几份，而 `report_timing` 里的 `Data Path Delay` 分配（logic 与 route 各占多少）与 `Logic Levels` 指向第三种原因——布线距离/那片区域的绕线；猜错杠杆的代价是一次 12–15 分钟的构建加一轮归因。需要按占比选算术/物理/扇出，或需要确认"route 占比高"该不该上 Pblock 时使用。
---

## 1. 一句话用途

logic/route 占比 → 杠杆，一行一个读数。

## 2. 适用场景

- 当有一条（或一族）setup 违例、你要决定动算术、动扇出还是动物理时。
- 当你准备花一次构建去试 `max_fanout` 时（先按本页读一次分配，再决定要不要花这一轮）。
- 当你手上只有全局 WNS、没有一族路径的 `logic`/`route` 分配与级数时。
- 当利用率数字显示面积不缺、而你仍想加 Pblock 时（要先看利用率的**形状**）。
- 当改完一手要判断有没有收益时（比同一族的 route 占比，而不是只看全局 WNS 有没有转正）。

## 3. 不适用 / 失效条件

- **本层不是判据**：任何结论都不能靠本页自称成立，只能靠 `evals/` 的记录或实测输出；本页只回答"这个占比该动哪一手、去哪确认"。
- 不适用：违例在 CDC 路径上且报告把它列为 async 组 ⇒ 那是跨域约束问题，不是这一段。
- 不适用：只差几 ps 且分布随每次布局大幅摆动 ⇒ 那需要的是策略扫描/余量，不是本条。
- 失效（版本与角绑定）：`report_timing` 的 `logic/route` 是按最坏角算的，换速度等级/温度角分配会变；
  本页全部读数出自 Vivado/Vitis 2025.2.1（build 6403652）那颗器件的一次已布线实现（版本口径见 `skill/references/tool-version-drift/SKILL.md`）。
  换到你没量过的角/版本时，那一格对你就是 `NOT_MEASURED`，不许套用。
- 失效：布线占比高**不一定**能靠 Pblock 解决——如果那片区域本来就绕不开（BRAM 与 DSP 的固定位置），物理杠杆也会失效，
  那时剩下的是流水或降频。
- 不许越界：本页不给出"该加哪条约束、阈值改成多少"，也不替你判断这一轮该不该采纳。

## 4. 前置条件

- 一份**已布线**的 dcp（本仓形状：实现 runs 目录里的那两份 routed dcp 候选，由脚本自己按顺序找；示例取值，需按自身工程替换）。
- 仓库里的现成口子：`build/tcl/crit_path.tcl`——它只读已布线的 dcp、出报告，不动任何产物（本轮直读到它的第 13 行那句声明与第 26 行的"找不到 routed dcp 就退出"分支）。
- 能读 `report_timing` 一条路径块里的两行：`Data Path Delay: …` 与 `Logic Levels: …`。
- 一轮构建的代价要先认（12–15 分钟 + 一轮归因），否则不值得试第 3 步那一格。

## 5. 使用方法

1. **读出三个数**（`report_timing` 一条路径的块里就有）：
   `Data Path Delay: 7.694ns (logic 2.229ns (28.970%) route 5.465ns (71.030%))` 与 `Logic Levels: 6 (CARRY4=3 …)`。
   完成后应看到：logic 与 route 两个百分比加起来对得上那个延迟，且能报出级数。
2. **用仓库里的现成口子** `build/tcl/crit_path.tcl`：它只读已布线的 dcp，每条最差路径出一行
   `slack | 时钟组 | 数据路径延迟 | 级数 | 起点 -> 终点`。
   完成后应看到：一族路径的级数与占比一致（本例最差 8 条全是同一族、级数一律 6、route 占比 71 %）。
3. **按分配选杠杆**（下表是主表；"出处"列本轮都打开过）。

| 分配长什么样 | 该动的杠杆 | 具体动作 | 出处（本轮直读） |
|---|---|---|---|
| `logic` 占大头、级数多 | 动算术/流水 | 把一段组合搬到前一拍寄存 | 旧卡 S28 动作 2；形状例见 `report/log/ISSUES.md` #121 的"量到的"块（本轮第 5202–5211 行；该例 logic 只占 28.970 %，所以**不是**这一行） |
| `route` 占大头（本例 71 %） | 动**物理** | 邻接约束（Pblock）、减少该终点族的端点数、或疏解那片绕线 | `report/log/ISSUES.md` 第 5208–5211 行与第 5230 行（#121 内）；`report/OPTIMIZATION_LOG.md` r83/r84 两节（本轮第 333 行、第 366 行两个小节标题） |
| 终点族是"每 bit 一个 `CE`" | 压端点族 | 28 位计数器每 bit 一个 `CE` ⇒ 8 条最差路径全是它的兄弟 bit；改成"一个使能 + 并行数据"能把端点族压成 1 个 | 旧卡 S28 动作 2；台账 #121 那句"最差 8 条全是同一族（`drop_words_reg[20..27]/CE`）" |
| 利用率看着很高、想加面积 | 先看形状再动手 | BRAM 67.86 % 而 LUT 逻辑只用 19.12 % ⇒ 缺的不是面积，是线长 | `report/log/ISSUES.md` 第 5230 行（#121 内同句）；`report/OPTIMIZATION_LOG.md` 第 374 行的 LUT 10173 / 19.12 % 一格 |
| 扇出高 | 才轮到 `max_fanout` | **但先做第 1 步**，因为扇出与布线经常混在一起 | `report/OPTIMIZATION_LOG.md` 第 349–350 行记的那一刀失败 |
| 改完任何一手 | 换判读方式 | 跑同一个脚本比**同一族的 route 占比**，而不是只看全局 WNS 有没有转正 | 旧卡 S28 动作 3 |

4. 无论动哪一手，改完跑同一个脚本比同一族的 route 占比。
   完成后应看到：占比这一维度的前后两个数，来自同一支脚本、同一棵树。

## 6. 判读与失败分叉

- 步骤 1：
  通过 = logic % 与 route % 加起来对得上 `Data Path Delay`，且 `Logic Levels` 报得出级数。
  失败 = 只有 WNS 一个数 ⇒ `FAIL`，杠杆选不出来，此时动手就是猜。
  读不到输入 = 那份报告里没有这条路径块（或报告是 0 字节）⇒ `NOT_MEASURED`，先确认件的来历与时间戳。
- 步骤 2：
  通过 = 脚本自己报出它开的 dcp，并每条最差路径出一行摘要。
  失败 = 脚本打出找不到 routed dcp 那一行 ⇒ `FAIL`，构建还在跑或还没布线，先等件。
  读不到输入 = 脚本从来没在这台机器上跑通过 ⇒ `NOT_MEASURED`（本仓旧版就是因为指向另一台机器的另一个工程而从来没跑起来过，见 §7）。
- 步骤 3：
  通过 = 你选中的杠杆与占比同向（route 大 ⇒ 物理；logic 大 ⇒ 算术；只有扇出证据才动 `max_fanout`）。
  失败 = 猜了扇出而实测 route 占大头 ⇒ `FAIL`，代价是一次 12–15 分钟的构建加一轮归因（本仓实例：WNS 从 −0.062 拖到 −0.192 ⇒ 回滚）。
  读不到输入 = 没有一族的级数/占比 ⇒ `NOT_MEASURED`，不许直接下"动物理"的结论。
- 步骤 4：
  通过 = 同一族 route 占比真的降了，且失败端点数同向。
  失败 = 占比没降、WNS 却"看起来转正" ⇒ `FAIL`，那是邻域里的兄弟路接棒（本仓记录：切断目标那一族之后失败端点 16 → 2，但全设计 WNS 反而变成 −0.135）。
  读不到输入 = 换了另一把尺子（不是同一个脚本/同一份报告口径）⇒ `NOT_MEASURED`，两次的占比不可比。

## 7. 已验证的效果

- 旧卡记的实例是**反面的两层**（本卡的"完成判据"就是它）：
  ① 看到一族 `wbin_reg → drop_words_reg[*]/CE` 违例后先猜扇出，加 `max_fanout=12`，WNS 从 −0.062 拖到 −0.192 ⇒ **回滚**
  （`report/OPTIMIZATION_LOG.md` r83/r84 两节；本轮直读到第 333 行与第 366 行那两个小节，第 349–350 行记的正是这一刀失败与失败端点 28→34）。
  ② 回滚后我在日志里写"瓶颈不是扇出，是锥体本身（14 位加法→格雷→比较）"，第二天把 `crit_path.tcl` 修到能跑，
  实测 **6 级逻辑 / route 71 %** ⇒ **这句结论也被推翻**（`report/log/ISSUES.md` #121 记的就是这次自我更正；本轮直读到该小节起于第 5202 行，
  同一条路径块里 `Data Path Delay` 那行与 `Logic Levels: 6 = CARRY4=3 LUT4=2 LUT5=1` 都在，最差 8 条同级数同占比）。
- 另一条同轮记录：#124 及其「#124 补充」（切断目标那一族之后，失败端点 16 → 2，但全设计 WNS 反而变成 −0.135——最差路径换成了邻域里的兄弟路）；
  本轮直读到 #124 小节在第 5333 行、「#124 补充」在第 5452 行，那张对照表里 `−0.135 / 2` 与"兄弟路 7 级"两格都在。
- 两处"级数"旧卡本就不同（动作/完成判据写 **6 级**，出处段写 **7 级**）：本轮直读台账确认它们分属两个轮次
  （#121 量的是 `drop_words` 那一族 = 6 级；#124 补充里 r86 正式那一跑的新的最差族 = 7 级）⇒ 本页两处各按原文保留，不合并、不改写。
- 本轮没有跑 Vivado、没有开 dcp、没有跑 `build/tcl/crit_path.tcl` ⇒ §5 主表里的百分比与级数都是**转录**，
  本轮执行结果记 `【未实测】`；`build/tcl/crit_path.tcl` 只直读了代码（本轮打开：第 13 行"只读：开已布线的 dcp、出报告，不动任何产物"）。
- 利用率那一格的两个数：67.86 % 本轮在交付侧的 r84/r86/r88 三行都见到（同一个数）；19.12 % 本轮在 `report/OPTIMIZATION_LOG.md` 第 374 行
  与台账第 5230 行两处核对到（LUT as Logic 10173 = 19.12 %）⇒ 两个数都是**历史轮的读数**，不是本轮复算。
