# 位流加载后的身份确认与最小可用闭环

覆盖"加载命令返回"到"可以开始用"之间那段路。这一段最容易写成叙事、最难被自证，
所以每一步都要求**读数进日志**，不认返回码、不认记忆、不认文件名。

## 适用场景

- 刚跑完整片或分区加载，想知道"现在能不能开始联调"。
- 现场/评审前怀疑板上产物与仓库里那份不是同一个东西。
- 换版本或重载之后行为漂移，或者访问口（调试链/内存映射读口）突然失联。
- 处理器侧程序"消失"、串口无回显，需要判断该重试还是该断电。
- 出现"加载器报了 0 但板子不对"这类矛盾读数。

## 使用方法

### 动手前先查、先确认

- 一手资料优先级：器件/板卡的**用户指南与重配章节** ＞ 加载工具手册 ＞ 应用笔记 ＞ 模型记忆。
  要查的具体项：本次加载是否要求处理器侧保持在复位、外扩存储的初始化序列在重配后是否要重跑、
  分区加载是否允许与其它分区并发、访问口的地址窗口在重配期间是否仍在。
- 先跟用户确认（不可逆或影响演示的）：能否断电重上、能否覆盖板上当前版本、
  演示窗口是否允许中断、这块板是否有别的进程正在占用访问口。

### 第一步：加载前先读"现在板上是什么"

1. 读回身份：版本字段、构建摘要、只读标识寄存器——三者任一存在就都要读，全不存在走最后的退路。
2. 与版本库里那份产物的摘要逐条比对（哈希或版本字段），一致才继续；不一致先弄清哪个是真的旧。
3. 禁止的推定：靠文件名、靠"我刚才加载过"、靠加载器返回码来断定板上状态。
4. 读不到、读出全 0 或全 1、读出错响应 ⇒ 一律记 `NOT_MEASURED`（不是"一致"）。
   退路是外接探针（看引脚级自洽信号）或换一个访问路径，仍然要留读数。

### 第二步：加载顺序与前置（低自由度清单，逐项打勾）

- 处理器侧状态：需要停机/复位就先停；**不要在处理器还在跑循环或还在中断里搬运时重配**。
- 存储/外设初始化：外扩存储控制器、初始化序列、时钟合成器的配置是否在重配后需要重跑一遍。
- 访问口占用：确认只有一个持有者；有别的会话连着，先让它释放，否则报错误判成加载失败。
- 供电与时钟：各电源域状态、参考时钟是否存在、时钟合成器是否已锁定。
- 这一层的通用前置与禁区由 `before-touching-hardware` 负责，本节只列与"加载"直接相关的四项。

### 第三步：加载后必做三件事（缺任何一件都不算"可用"）

1. **链路可达**：读一个只读标识（复位后恒定值）。期望 = 寄存器表里的常量；
   读到全 0/全 1/总线错 ⇒ 判链路不可达，后面两件不用做，直接进第四步分类。
2. **时钟/复位到位**：读状态寄存器的锁定位、就绪位、释放位。期望全部置位；
   只要有一个没置位，就不要往下测数据通路（那只会测出一个假坏点）。
3. **数据通路通**：跑一段自洽激励（已知输入 → 可算输出，例如自检图案或计数回路）。
   期望硬件计数推进且结果自洽：至少两次读数、差值非 0，且落在激励预期的界内。

### 第四步：失败恢复——先分类再动作

- **加载器报错**（工具非 0，但访问口仍可读到身份）：产物、权限、电缆、会话占用这一类。
  可原地重试；重试前**重读一次身份**，别假设"这次失败等于板上没变过"。
- **板子卡死**（访问口不可达，或读什么都是同一个错响应）：重试加载器、重启上位机进程、
  换命令流通常都解不了；这类只有**断电重上**（保持掉电若干秒）能解。
  分不清就先做一次"只读身份"的探测：读得到 ⇒ 按报错处理；读不到 ⇒ 按卡死处理。
- **顺序陷阱（最常见的一类楔死）**：重载逻辑 while 处理器侧仍在猛访问共享总线
  （在循环里读写、或中断里发起搬运），处理器会在一次事务里等不到响应而楔死，
  现场表现就是"程序不见了、串口无回显"，看起来像板子坏了。
  正确顺序：停处理器（复位/停机/关中断）→ 重配 → 跑第三步三件事 → 再放处理器跑。
  恢复后必须把第三步重跑一遍，"重新上电了"不等于"可用了"。

### 第五步：每次加载都落一份身份件

内容 = 时间戳 + 所用产物的摘要/版本字段 + 读回的身份值 + 三件事各自的读数 + 最终判定。
台账形式交给 `evidence-ledger` 那类工具；**没有这份件，本轮就判 `NOT_MEASURED`**，
不许用"上一轮的件"顶替（同名覆盖这类事故见 `build-artifact-races`）。

## 失效条件

- **只读一次就宣称稳定**：身份口可能读到别名、缓存的上一次结果或桥接层的重试残值。
  征兆：两次加载读出同一个值就以为安全——要连读多次、换一次激励再看，值仍自洽才算。
- **把"工具返回 0"当板上状态已变**：返回 0 只说明命令流跑完了，与板上是否真的换成本版无关。
  征兆：加载后立即跑测试全绿，但身份读回仍是旧版本字段。
- **没有可读回的标识**（或标识口本身在被重配的区域内）：这条只能判 `NOT_MEASURED`，
  必须改用外接探针或别的访问路径，不许因此改成"靠加载器输出判断"。
- **把只读标识口当可写口去设置**：写不进去会被误判成"链路不可达"，实际是属性搞错。
  以 `register-map-and-readback` 的读写属性列为准。
- **把两类失败混成一类**：会对不可达的板子重试十次加载，或在真报错的场合直接断电丢证据。
- **分区加载时连带别的分区**：整片复位会同时打断其它通路的数据，别把"别的通路也停了"
  当成新加载的这块坏了；先确认受控区域范围。
- 状态位没置位却继续测数据通路：测出来的"坏点"是假象，会把人引去查数据通路本身。

## 已验证效果

未量过，属建议。可复跑的形式（谁做都行，要有数）：台架脚本对同一份产物连做 3 轮
"读身份 → 加载 → 读身份 → 读状态位 → 跑自洽激励取两次计数"，判 3 × 4 = 12 项，
期望 3 轮身份一致且等于库中摘要、状态位全部置位、计数差值非 0 且在界内；
任一轮读不到值 ⇒ 那一项记 `NOT_MEASURED` 而不是通过。三态与计数规则按 `three-state-verdicts`，
期望值先按未改动的树推出（`bench-expectations-first`）。

## 来源

长自两类观察：一是"只 program 不读身份 ⇒ 板上产物与版本库对不上，后面所有读数都归错因"；
二是"重载逻辑时处理器侧仍在访问共享总线，把处理器楔死，现场找不到恢复路径而反复断电"。
相关的探针自骗与构建竞态清单见 `tcl-and-probe-traps`、`build-artifact-races`；
在线判活与替代读数见 `board-liveness-readback`。
