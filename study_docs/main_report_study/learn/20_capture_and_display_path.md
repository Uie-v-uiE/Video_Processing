## 0. 地图与术语

**是什么。** 一条链，十段，每段一个模块：

```
 上位机 UDP:5001（Node，见 §2）
   | RGMII 4bit DDR @ PHY 恢复出来的 125 MHz
   v
 rgmii_rx / gmii_to_rgmii ............ 双沿拼回 8 bit GMII（rgmii_rx.v:31 的 dv）
   -> gmii_rx_mac ..................... 剥前导码、自己算 FCS-32，出 m_sof/m_eof/m_good/m_bad
   -> udp_rx_parser ................... 按字节下标解 IPv4/UDP + 目的端口过滤，出 p_data/p_valid
   -> frame_reasm ..................... 4 字节 offset 头 → 16bit 字写口 + 三道验收门 → frame_done
   -> dc_fifo ......................... 36bit x 8192 的 BRAM 异步 FIFO（125 MHz → 100 MHz）
   -> axi_frame_saver64 ............... 两个字拼一个 64bit beat，AW/W 流水化写进 DDR
   -> ddr_bank_commit ................. 换页 + 交出 completed_base（TAIL_GUARD）
  DDR 乒乓双 bank 0x1000_0000 / 0x1008_0000（PS 的第三个 bank 0x1010_0000）
   -> frame_commit_lock ................ 只在消隐窗口放行，并把"请求"与"基址"锁在一起
   -> axi_frame_writer_gated ........... AXI 读 16 beat x 8B，整帧搬进显示帧缓存
  显示帧缓存 frame_buffer_w64（在 fb_bilin 里面，512x300 的 64bit 字阵列）
   -> fb_bilin ......................... 唯一的读口，双线性，每源像素用满 4 个像素拍
   -> 两条抽头：raw_line_delay(4 行环) / proc_pipeline(15 拍)
   -> split_display .................... 逐像素二选一 + 那条 2 列蓝线 + 画面外给黑
   -> osd_overlay（五行字）-> rgb2dvi -> HDMI 1024x600 @50 MHz
```

例化位置（`src/rtl/top/pl_video_top.v`）：`u_arb:376`、`u_cmt:385`、`u_row:409`、`u_life:538`、
`u_aw:639`、`u_bilin:679`、`u_bar:704`、`u_raw:733`、`u_pipe:745`、`u_seam_src:849`、
`u_split:856`、`u_osd:944`、`u_dvi:970`。收侧那一半在 `src/rtl/eth/eth_udp_video_top.v`：
`u_rgmii:73`、`u_rx_mac:186`、`u_rx_par:197`、`u_reasm:231`、`u_lm:280`、`u_cdc:294`、
`u_commit:326`、`u_saver:350`。

**为什么要先背它。** 本仓库里"屏上多一条带 / 偏了几列 / 闪一下 / 画面冻住"的案子，最后都落在四类
原因之一：**写侧与读侧没对齐**（§7、§9），**标签与内容不同级**（§9），**跨域只搬了一位却把整条总线
当电平读**（§5），或者**"曾经有"与"现在有"被写成了同一个位**（§10）。这四类都不是编译错误，也不是
综合错误，只有把判据摆到正确位置才看得见。

## 1. 收侧为什么是"自研那一对"

**是什么。** `src/rtl/eth/gmii_rx_mac.v`（剥前导码 + 自己算 FCS）与 `src/rtl/eth/udp_rx_parser.v`
（按下标解 IPv4/UDP + 目的端口过滤），串起来接在 `frame_reasm` 前面（
`src/rtl/eth/eth_udp_video_top.v:186-204`）。厂商的 `udp_rx.v` 仍在仓库里，但**只有台架在例化它**
（`sim/tb_eth_video.v:37`，`docs/MODULES.md:130` 明写"未例化"）；厂商那层 `udp.v` 套壳已经删掉，
`src/rtl/eth/` 下现在只剩 `udp_rx.v` / `udp_rx_parser.v` / `udp_tx.v` 三个 UDP 文件。

**为什么要换。** 三个理由，一条比一条硬（`src/rtl/eth/eth_udp_video_top.v:154-158` 把这笔账写全了，
完整过程在 `report/log/ISSUES.md:295` 的第 38 条）：

1. **RGMII 交不出错误标志。** 4 根数据 + 1 根控制，`RX_CTL` 在 `rgmii_rx.v` 里只当 `gmii_rx_dv`
   用（`src/rtl/eth/rgmii_rx.v:4`），板上**没有 RX_ER 这根线**。于是厂商 `udp_rx` 的"没有 ER"恒真，
   收侧没有任何错误源，`frame_reasm` 的 `p_good` 只能硬接 `1'b1` —— 遥测与 OSD 里那个"坏包"计数
   就成了一只构造性为 0 的死数字。
2. **厂商模块不给包边界。** 收侧只有 `rec_en/rec_data/rec_byte_num`，包与包的边界要靠下游自己凑
   （`src/rtl/eth/eth_udp_video_top.v:225-226` 记的就是这段被删掉的推导）。
3. **端口过滤没人做。** 目的端口 5001 只是一个参数（`src/rtl/top/system_top.v` 里把 `UDP_PORT` 灌进 ETH
   顶层的那一行），而过滤必须落在字节流上，位置在 `src/rtl/eth/udp_rx_parser.v` 里 `udp_off + 3`
   那一拍比 `{dport[15:8], s_data}` 的那一段。

   **为什么这一格非补不可。** 会 C 的人第一反应通常是"端口不对就让操作系统丢掉它"，但这里是裸链路：
   板子的 IP 只有一个（192.168.1.10），**打到这个 IP 的 UDP 包并不只有视频**。局域网里任何一台机器的
   广播、探测包、或者上位机敲错端口的那第一条包，都会原样落进拼帧器。而拼帧器把载荷的**头 4 个字节当作
   帧内字节偏移**用（§3），所以对它来说"一个随机 UDP 包"就是"一次地址随机的 1392 字节写"：偏移会被截成
   19 位半字下标（`fb_wr_addr`），能指的落点是**当前 bank 基址往上约 1 MB** 之内任意位置。于是三类后果
   都可能出现：落在本帧范围内 = 若干像素被随机内容覆盖（屏上一闪，下一帧才恢复）；落在另一块 bank =
   把"显示侧正在搬的那一帧"改掉（这一帧的其余部分还是好的，所以症状像撕裂又不像）；落在 PS 那第三块
   bank 的地址范围 = 与 SD 回放的 DMA 互相覆盖（bank 划分见 `src/rtl/top/system_top.v` 里
   `0x1000_0000 / 0x1008_0000 / 0x1010_0000` 那三个常数；最后这一类是我按 19 位下标 × 2 字节的量程
   推出来的，留档里没有实测记录，按**推断**看待）。**端口过滤是唯一一条"数据还没变成地址之前"就把它
   挡掉的关口**，所以它必须在解析器里，不能靠上位机守规矩 —— 这条与 §2 末尾"判据挂在硬件那一条"是同
   一个道理的两个方向。

**原理（为什么"整帧过一遍 CRC 会剩下一个常数"）。** 标准以太网 CRC-32 是反射多项式 0xEDB88320、
初值全 1、末异或全 1。发送端把 CRC 取反后附在帧尾，于是接收端"把消息和 FCS 一起再喂进同一个
寄存器"这件事，在代数上等于把余数减掉自己 —— 结果与消息内容无关，只剩一个由约定决定的常数
（不末异或那一版是 `0xDEBB20E3`，末异或版互为取反 = `0x2144DF1C`，见
`sim/tb_v795_rx_fcs.v:5`）。所以判"这帧有没有比特错"不需要单独算一遍余数再比较，只需要看
**残值**对不对。本仓库用的是发送侧同一个 `crc32_d8` 核（`src/rtl/eth/crc32_d8.v:2-4`：复位全 1、
每字节异或前先位反转），它留下的残值由台架量出来并钉在 RTL 里：`FCS_RESIDUE = 32'hC7_04_DD_7B`
（`src/rtl/eth/gmii_rx_mac.v:23`，注释明写"实测值、不是推算值"，判据是
`sim/tb_v795_rx_fcs.v:158` 那条 `RTL 常数 == 实测残值`）。这里的方法论值得记：判据用**另一套实现**
造帧（T0），否则拿 `crc32_d8` 验 `crc32_d8` 是同义反复，两边一起错也照样过。

**代码怎么落。**

- 状态机只有三格：`S_WAIT` 等 `0x55`、`S_PRE` 等 `0xD5`（SFD）、`S_DATA` 逐字节输出
  （`src/rtl/eth/gmii_rx_mac.v:88-112`）。CRC 的 `crc_clr` 打在 **SFD 那一拍**而不是第一个数据字节
  那一拍，因为该模块里 `clr` 的优先级会吞掉同拍的数据（`:42-45`）。
- 帧尾约定：`m_eof` 与 `m_good/m_bad` 同拍，表示"上一个 `m_valid` 的字节就是最后一个字节"
  （`:71-80`）。这一句看起来像文字游戏，但它是一个真 bug 的修法：`m_eof` 曾经声明了、复位清了、
  **却没有任何一处写 1**，于是例化它的下游永远等不到包边界（`:72-74`，由
  `sim/tb_v795_rx_chain.v` 的 C1 抓到）。
- 判决四条件：没有 ER、长度 `>= 64`、残值对、帧由 SFD 起（`:76-80`）。长度那一半挡住了 runt 帧，
  残值那一半挡住比特错，两者都不是"看着像"。
- 解析器的判定点在 `bcnt == 14 + ihl*4`（UDP 头第一个字节）：验 `0x0800`、IPv4 版本 nibble、
  协议号 17、不分片（`src/rtl/eth/udp_rx_parser.v:137-148`），再在 `udp_off+3` 那一拍比目的端口
  （`:147-153`）。这两个点各有一次真事故：前者曾经因为 `ihl` 在同拍才存进去而**每帧误报一次
  "被过滤掉"**（`:130-133`）；后者是 P0-C 欠到那轮的端口过滤债，例化那一行旁边的注释就是它的记账
  （`src/rtl/eth/eth_udp_video_top.v:197`）。
- 载荷**按 UDP 长度字段收尾**，不是一路发到帧尾（`:166-180`）：原来的写法会把帧尾 4 个 FCS 字节
  也当载荷吐出去 —— 32 字节的载荷吐出 36 个，接上 `frame_reasm` 就是每包固定多 4 字节的确定性
  错位。最后一个载荷字节只**记账**（`eof_pend`/`pay_len_q`，`:176-179`），不当场发 `p_eof`，因为
  FCS 的判定要等帧结束那一拍才知道；早发就得猜，猜错就是"把坏包当好包提交"。
- 坏帧也必须把包闭合（`:89-104`）。判据是"只要往外吐过字节，就必须给一个 `p_eof`"（`in_pay` 也进
  条件）：载荷只发了一半就被判死的帧，如果下游的 `pkt_active` 一直挂着，下一包的字节会接到这一包
  后面 —— 那比丢一帧更坏。
- 帧尾收尾放在字节处理**之后**，而且要认两种 `s_eof` 时序（`:185-207`）：厂商风格是 eof 与最后一个
  字节同拍，本仓库的 `gmii_rx_mac` 是最后一个字节早在上一拍已随 `m_valid` 出去。少认一种就少一个字节。

**顺带两条"注释旧于代码"，读源码时别照抄。** `src/rtl/eth/link_monitor.v:4-5` 与 `:23` 还说
"p_good 在顶层硬接 1、上板时坏包恒 0"，`sim/tb_v795_rx_chain.v:5` 还说 `udp_rx_parser` 从未被任何
顶层例化过 —— 这两句都是 V7.9.6 之前的账，今天 `p_good` 是真值
（`src/rtl/eth/eth_udp_video_top.v:234` 那句"这一位从此是真值"就是这次改动）。

**怎么验证。** `bash sim/run_one.sh tb_v795_rx_fcs`（T1..T5：好帧判好、坏帧判坏、短帧判坏、
残值常数对得上）、`bash sim/run_one.sh tb_v795_rx_chain`（C1 载荷字节数 / sof / eof / udp_ok /
不误报丢弃；C2 坏帧仍闭合且 `p_good=0`；C3 端口不对就整包丢）、`tb_udp_parser`、`tb_crc32`。
一次只跑一条：`sim/run_one.sh:18-23` 有全局守卫，看到活的 xsim 就拒绝启动并说清该杀谁。

## 2. 分包长度为什么钉在 8 的倍数（1392）

**是什么。** 上位机把一帧 307200 字节切成约 221 个 UDP 包，每包 `[u32 小端 byte_offset][RGB565 载荷]`，
载荷 1392 字节（`src/host/video_sender.mjs:6`、`report/HOST_GUIDE.md:68-71`）。

**为什么要 8 的倍数。** DDR 打包器一个字是 64 bit = 4 个 RGB565。若包边界落在字中间（载荷取
1396 就是这样），同一个 64 bit 字会被相邻两包分两次写：第一次写低两 lane、第二次写高两 lane。
当年的写选通恒为 `8'hFF`，第二次就把第一次刚写好的半字**覆盖成 0** ⇒ 每帧约每两个包留一个
4 字节黑洞（实测每帧 111 处），屏上是均匀散布的黑点。这条账写在
`src/rtl/eth/axi_frame_saver64.v:80-82`，协议侧的对偶写在 `src/host/video_sender.mjs:23-26`。

**为什么今天仍然用 1392。** 因为硬件已经把这个坑堵掉了：v6.4 起写选通**按 16 bit lane 生成**
（`src/rtl/eth/axi_frame_saver64.v:83-84` 的 `{2{keep_r[3]}}, ...`，lane 掩码在 `:126-138` 的
打包器里逐字节攒）。同一块板、同一版 bit 用 1396 复测：命中率 100.0%、空洞 0
（`report/HOST_GUIDE.md:76-83`）。默认仍取 1392 是两条工程账，不是两条物理约束：少发约 0.3% 的
重复 beat；"一个包不跨两个 64 bit 字"这个性质让"按包内偏移做相位分析"的判据仍然成立
（`src/host/ddr_stale.mjs:6-12` 那套签名就靠它）。`--mtu-payload` 只为做这个对照实验而存在。

**这里值得推一遍的一件事。** 同一个洞有两种堵法：**让边界不落在字中间**（上位机侧）或
**让每个 beat 只写自己那几个字节**（硬件侧）。前者依赖发送端守规矩，后者把不变量收进自己的边界里。
本项目两个都做了，但**判据挂在硬件那一条**上 —— 因为发送端是别人的脚本，而 `WSTRB` 是自己写的线。

**怎么验证（读盘，不碰板子）。**

```bash
grep -n "1392\|8 的倍数" src/host/video_sender.mjs report/HOST_GUIDE.md
grep -n "m_axi_wstrb\|cur_keep" src/rtl/eth/axi_frame_saver64.v
```
第一条应看到 `video_sender.mjs:6`、`:24-26` 与 `HOST_GUIDE.md:76-83`；第二条应看到端口声明 `:33`、
按 lane 生成 `:83-84`、打包器里 `cur_keep` 的四个 lane 分支 `:126-138`。若哪天 `:83` 变回
`8'hFF`，上面那两条 grep 就是提醒。

## 3. 拼帧与三道验收门（`frame_reasm`）

**是什么。** 拿载荷头 4 字节当**帧内字节偏移**，把 16 bit 像素写进当前 bank；一帧收完时给出
`frame_done`（`src/rtl/eth/frame_reasm.v:86-185`）。一帧 307200 字节是参数
（`:11`），几何只有一处定义（`src/rtl/top/system_top.v:132-135` 的四个 localparam）。

**为什么要"门"，而且要三道。** 因为"屏上出现半张新图 + 半张旧图"比"停在上一帧"糟得多，而 UDP
不会告诉你缺了什么。三道门各自抓一种缺法（`:149-153`）：

```
 ① rows_hit >= IMG_H —— 每一源行都至少被一个像素写过      （行覆盖位图 :75、:127-130）
 ② bytes_ok —— 307200 个字节一个不少（饱和计数器正好到界）  （:63-70）
 ③ !bad_frame —— 这一帧里没有任何一个包被判坏               （:46-48、:177-181）
```
**只用①会放过去什么**：丢一整包会让某行缺一段，但下一帧的同一行可能被别的包补上 ⇒ 位图"行行都
有",洞却留在行中间（一个从没写过的字 = DDR 里的旧值或 0，停在流断时就是屏上的黑纹）。
**只用②会放过去什么**：字节数够但被写到错的偏移（重复包、乱序包互相盖）。行位图与字节计数问的是
两个不同的问题，所以两个都要。

**原理（为什么算术要改写）。** 旧写法每个字节都算一次 `cover + pkt_pay + 1 >= FRAME_BYTES`，这是一条
32 位三操作数加法链，独占了 125 MHz 那组的全部十条最差路径（WNS +0.499，文件头 `:5-7`）。现在换成
**两个饱和的运行值**：`cov`（本帧已到的载荷字节，含在飞那一包）与 `pend`（在飞那一包自己的偏移），
两者都封顶在 `FRAME_BYTES`（`:56-72`）。关键一句是注释里的：对一个**单调**计数而言，"`+1 >= 界`"
与"`== 界`"是同一个问题 —— 于是把加法换成一次等值比较，代价为零，且一个像素都没少写。

**两个不显然的细节。**

- **行号必须按 `off / (IMG_W*2)` 算**（`:80-81`）。曾经试过切 `off[16:1]`（当成 16 位像素下标），
  那会把约一半的行折进同几个数 ⇒ `frame_done` 永远不来 ⇒ SRC1 全黑（`:78-79` 写得很直白）。
  今天综合器会把除以 1024 折成右移（`IMG_W*2` 是 2 的幂），所以这条不是硬件账，是可读性账。
- **包最后一个字节与 `p_eof` 同拍**，此时计数器还没看见它，所以在两处都要补记一次
  （`:68-70`、`:163-166`）。这类 off-by-one 在同一文件里出现过两次（`udp_rx_parser.v:47-50` 的
  `last_pay_now` 是同一件事的另一半），所以两边都要有判据。
- `frame_abort` 只在"字节预算已用完但验收没过"那一拍脉冲一次；**连 307200 都没凑够的短帧不脉冲**
  （`:26-29`），那种情况由 §5 的 `stall_ms` 抓到。缺行数以 `rows_missed` 与 `frame_abort` 同拍给出，
  而"行数够、字节不够"时它是 0 —— 注释明写这不是 bug，是在说"缺的不是行，是最后一包的字节"
  （`:170-173`）。

**乱序为什么能拼对。** 偏移来自包自己，不来自到达顺序（`:105-109` 攒出 32 位 `off`），所以先到后到
都行；但**同一字的两半由两个包提供时，谁先到都一样**，因为每个 lane 各自带 `keep` 位（§2）。
`report/HOST_GUIDE.md:71-73` 那三行"乱序可以拼对 / 坏包不重传 / 下一帧自动恢复"就是这个设计的用户
可见说法。

**怎么验证。** `bash sim/run_one.sh tb_v6_cover_gate`（三道门各自的反例）、`tb_udp_reasm`、
`tb_v50_rows` 与 `tb_v50_rows_prod`（行覆盖的算术，两份分别是缩小版与生产参数版）、
`tb_v6_ingress_integrity`（整条入包链的字节完整性）。

## 4. CDC 与反压：被挡住那一拍的字为什么永远消失

**是什么。** 36 bit x 8192 的异步 FIFO（`{flush_flag, addr[18:0], data[15:0]}`），BRAM 实现：
`src/rtl/eth/eth_udp_video_top.v:259-301` + `src/rtl/eth/dc_fifo.v`。写侧在 125 MHz（PHY 恢复的
`gmii_rx_clk`），读侧在 100 MHz（`fclk0`，HP0 那一域）。

**原理（为什么不能"叫上游等一等"）。** 上游是网线上的线速字节流：PHY 不会停，UDP 没有流控。
于是写侧只有两种结局 —— **写进去**，或者**这一拍的数据消失**。`dc_fifo` 的实现把这件事写得很干净：
`wr_en && !wr_full` 才动指针、才写阵列（`src/rtl/eth/dc_fifo.v:41-51`），`full` 由对端格雷码读指针
算出（`:33-35`）。所以"丢掉"不是异常路径，是**同一句 `if` 的 else 分支**；它没有任何补救。

再推一层：为什么这不会自愈？因为 `frame_reasm` 的地址来自包里的 `off`，它已经推进了
（`src/rtl/eth/frame_reasm.v:134`），FIFO 之外没有任何人记得"那个字没写进去"。DDR 里那一格保持
旧值 ⇒ 显示侧读到旧帧的那一格 ⇒ **一块会随画面变的旧像素**。这就是为什么必须把它变成可读数
（§5 的 `drop_words`）而不是靠眼睛。

**为什么"把缓冲做深一点"治不了。** 深度只解决**突发**，吞吐 deficit 是速率问题。这两条账都写在
源码里：v6.1 之前读侧限成"每 3 个 axi 周期取 1 条"= 66 MB/s < 线速 125 MB/s，于是**稳定丢约 46%
的字**，与上位机速率无关，屏上是"每隔一个 16bit 空洞"的黑纹（
`src/rtl/eth/eth_udp_video_top.v:254-258`）；改成 1 条/周期（200 MB/s）之后，v6.2 把 CDC 做到 8192
条上板**毫无改善**，因为瓶颈是打包器的**平均排空速率**（`src/rtl/eth/axi_frame_saver64.v:5-7`，
ISSUES #31/#32，两份账都在 `report/log/ISSUES.md`）。同一条教训在读侧也出现过（`src/rtl/eth/eth_udp_video_top.v:252` 的 `sv_full`
反压：取出来就丢 = 白读，于是满时不取）。

**读流水为什么必须三段。** `fifo_rd → cdc_d1 → sav_*`（`src/rtl/eth/eth_udp_video_top.v:303-318`）
是为了让**同一份实现**被 `ddr_bank_commit` 拿去判"本帧的字是否已全部穿过 CDC"（§6）。这段 glue
原来写在顶层、台架只能抄一份副本 —— 抽成模块的唯一理由就写在
`src/rtl/eth/ddr_bank_commit.v:4-5`：抄的那一份永远不会因真代码改错而变红。

**`flush_pend` 那一格。** 打包器需要一个"这个字到此为止，可以推了"的标记，它由 `reasm_flush` 生成，
但如果同一拍正好有一个数据写，两者不能同时进 FIFO，于是把 flush 记下来延后（
`src/rtl/eth/eth_udp_video_top.v:259-267`），并且 flush 标记永远让路给真实数据写
（`:256-258` 那句）。

**顺带：跨域的只有一位。** `gapclr_sel` 从 PS 的 fclk0 域进来，先 3 级同步再当**电平**用
（`src/rtl/eth/eth_udp_video_top.v:273-277`，带 `ASYNC_REG`）。它是准静态控制位、不是脉冲，所以
不需要握手 —— 与 §5 的快照、§7 的翻转位合起来，就是本仓库用到的三种跨域形状。

**怎么验证。** `bash sim/run_one.sh tb_v6_pingpong`（乒乓 + CDC 交付）、
`tb_v6_ingress_integrity`（写侧丢字必须能被读出）、`tb_sync_fifo`、`tb_link_monitor` 的 **A 段**
（故意挡住 CDC 写口 ⇒ `drop_words` 必须非 0；没挡住时必须恒 0，否则这个数字是噪声）。

## 5. 链路健康统计为什么在硬件里，以及那个 1/48 的坑

**是什么。** `src/rtl/eth/link_monitor.v`：四个量 —— 丢了多少字、作废过几帧（含最大缺行数）、
帧间隔（last/min/max/Σ）、多久没收到完整帧（`stall_ms`）。全部在 125 MHz 源域计数，经一条 320 bit
快照总线 + 一个跳变位跨出去（`:32-34`、`:178-196`）。

**为什么要它。** PS 完全不参与像素通路，只能问 PL。如果计数器不写在 PL 里，"板子上到底丢没丢字"
这个问题就只能靠眼睛回答，而眼睛能看见的症状（黑点、黑纹、停顿）比原因少得多 —— 这条链上有三处
不同的丢数据位置（§4 的两处 + 上游坏包），症状却可以完全相同。

**原理（丢字为什么只可能在那一处）。** 全链路里唯一会吃掉数据而**不留痕迹**的地方，是 CDC 写口被
`fifo_full` 挡住那一拍（§4）。所以计数器直接打在那两个信号的与上：
`if (cdc_wr_req && cdc_full) drop_words <= drop_words + 1'b1`（`:113`）。同一段还数 `cdc_ep`
= **进入满状态的次数**而不是拍数（`:72`、`:81`、`:114`）：一次灌满可能吃掉几百个字，"满过几次"
回答的是"这是偶发还是常态"，"满了几拍"回答不了任何事。

**原理（ms 其实是周期数）。** 时基是把 125 MHz 除以 125000 得到 `ms_tick`（`:36`、`:58-64`）。
这个除法在 125 MHz 下是纯计数器，**但它的物理含义依赖那颗钟真的是 125 MHz**。板级实测（2026-09-23）：
**RTL8211 断链时并不停供 RXC，而是把它拉到约 2.5 MHz（≈1/48）**（`:6-7`；同一件事的另一份记录在
`src/rtl/util/src_arb.v:11-13` 与 `sim/tb_link_monitor.v:357-358`）。于是断链之后 `ms_tick` 每
48 ms 真时间才来一次，`stall_ms` 以约 1/48 的速度往上爬 —— `stall_ms < 200` 这一位能连着十几秒
为真。**"没有帧"这件事不会把自己报告出来**，因为报告它的那张钟正是被拖慢的那张。

**所以下游必须与"源时钟健康"相与。** 健康位怎么造出来：`link_monitor` 每毫秒翻一次 `lm_hb`
（`:61`），目的域用 `snap_cross` 量**心跳间隔**——间隔超过 `SLOW_MS` 判 `hb_slow`，一个沿都等不到
判 `hb_gone`（`src/rtl/eth/snap_cross.v:25`、`:49-56`）。方向要想清楚：**源时钟变慢，在目的域看到的
是间隔变长**，而不是心跳消失，所以只测"有没有停"是不够的，`hb_slow` 就是专门为这一格加的
（`snap_cross.v:6-7`）。落到线上：`src/rtl/top/system_top.v:198-202` 跨到 fclk0，`:222` 把
`{hb_slow, hb_gone}` 摆进 lane31，`:239-240` 给出 `eth_live = lane7.bit3`、
`eth_tb_ok = !(slow || gone)`。

**为什么相与放在 `src_arb` 而不是顶层的裸与门。** `src/rtl/util/src_arb.v:11-14` 写了原话：这一条
判据原来在 `system_top` 里是一个裸与门，**没有任何台架能验到它**。搬进 `src_arb` 之后
`tb_v796_src_arb` 的 E 段能专门造"位仍是 1、但时基被拉到 1/48"的工况，判 E1/E3/E6
（`sim/tb_v796_src_arb.v:130-146`：坏时基必须让出屏幕、时钟恢复必须立刻抢回）。这一格是"判据要放在
**能被例化的那个边界**上"的教科书例子。

**原理（为什么跨域总线要用跳变沿捕获，不能直接读）。** 320 bit 的 `lm_bus` 在源域是一拍写进去的
（`src/rtl/eth/link_monitor.v:192-196`），但对目的域而言它是一个**异步更新的组合体**：目的域的
采样沿可以落在源域那一拍的任意位置附近。直接打两拍会怎样？每一位各自决定自己的新旧 —— 于是可能
读到"lane0 是这一轮的、lane1 是上一轮的"的中间态，而中间态在数字上完全合法（没有 X、没有越界），
只有拿恒等式去卡才露馅。正确形状：源域**整拍写好总线 + 同拍翻 toggle**，目的域把 toggle 过 3 级
同步、**只在沿上那一次采样**（`src/rtl/eth/snap_cross.v:27-37`、`:60-63`）。沿要三级才到，而总线
至少保持到下一次写入（本项目 ≥1 ms），所以采到的必是完整值。这套形状在本仓库里出现了三次：
`ddr_bank_commit` 的 `frame_done`（翻转位）、`zoom_snap` / `snap_cross`（总线 + 心跳）、
`frame_commit_lock` 的 `blank_tog`（§7）。

**发布节流与那个 `pend_ev`。** 每来一个事件就翻一次 toggle 会让目的域来不及（`SETTLE=32` 个源周期
= 256 ns，覆盖到 31 MHz 以下的目的时钟，`:156-158`）。但节流窗口里到的 `frame_done` **不能丢**：
少了 `pend_ev` 那一位（`:159-172`），正好落在窗口里的那一次会被整个丢掉，而 `stall_ms` 要等
200 ms 才会再刷一次快照 —— 仪表会"少报一帧"，而计数其实是对的。

**饱和而不是回卷。** 所有 16 bit 字段越过 65535 就钉在 0xFFFF（`:84-88`、`:103`、`:142-143`）：
健康数字回卷到 0 会被读成"没问题"，那是比少报更坏的错（`gap_max` 曾被 16 位回卷永久污染，之后更大
的间隔读起来反而更小，`:50-51`）。帧间隔也改成"直接数"而不是两个毫秒计相减 —— 后者是全设计最差
setup（`:46-47`，那条账在 `docs/log/ISSUES.md` 里编号 #95）。这里还留了一条代价说明：拆成两拍的版本记账与 min/max 全对，但快照在记账前就被
采走 ⇒ 台架红两条，于是**放弃那次时序改善**（`:48-49`：仪表的读数节拍是对外契约，不许为了时序挪它）。

**`gapclr` 为什么需要。** `gap_max` 是终身保持的，一次长空闲就永久污染它（还会因回卷读小），所以
测量前要有归零入口（`src/rtl/eth/eth_udp_video_top.v:63-65`）；归零只清 `gap_*`，其余 lane 保持
"自启动以来"的语义（`link_monitor.v:24-25`、`:107-110`），并且撤销 `have_base` 基准，于是下一个
`frame_done` 只重建基准、不把"空闲到现在"折进间隔。

**怎么验证。** `bash sim/run_one.sh tb_link_monitor`（文件头 `:3` 那张索引就是判据清单：A 丢字、
B/B2/B3 提交与发布分家、C 断流后快照必须继续刷新、D 第一个 `frame_done` 只建基准、E 长间隔饱和不
回卷、F `gapclr` 只清帧间隔、以及 snap_cross 段的不撕裂 + `hb_slow` + `hb_gone`）；
`bash sim/run_one.sh tb_v796_src_arb`（E 段）。不碰硬件的一条：
`grep -n "RTL8211\|1/48\|2.5 MHz" src/rtl/eth/link_monitor.v src/rtl/util/src_arb.v
src/rtl/top/system_top.v sim/tb_link_monitor.v` —— 同一个事实必须在四处都说得一样。

## 6. DDR 乒乓、提交与帧尾那 4 个字节

**是什么。** 采集侧写两块同样大的区域（bank0/bank1 = `BASE_ADDR` 与 `+0x0008_0000`，
`src/rtl/eth/eth_udp_video_top.v:67-68`），`ddr_bank_commit` 负责换页并把"刚写完那块"的基址交给
显示侧（`src/rtl/eth/ddr_bank_commit.v:53-79`）。

**为什么要乒乓。** 让采集直接写显示帧缓存做不到，因为两侧的节奏是别人的：显示每一刻都在读，采集
陆续到达、会丢、会重排。所以必须 ① 先在 DDR 攒完整帧 ② 只在没人看屏幕时搬进帧缓存 ③ 保证"搬的那块
内存"就是"刚攒好的那块"。① 是本节，② 是 §7 的窗口，③ 是 §7 的锁。一帧 307200 字节，两块 bank
隔 512 KB，**结构上不重叠**（`src/rtl/top/system_top.v:136-140`）。

**为什么提交要带基址而不是"翻个位"。** 显示侧要回答的问题不是"现在该读哪块"，而是"我该从哪个地址
开始搬这一整帧"。所以 `ddr_bank_commit` 交出去的是 `completed_base` + 一个 `commit_pulse`
（`eth_udp_video_top.v:342-343`），而 `bank` 只在提交那一拍翻（
`ddr_bank_commit.v:67-73`）。写侧的基址由 `sav_base = bank ? BANK1 : BANK0` 组合给
（`:79`），并且打包器只在**一个字的开头**锁存它（`axi_frame_saver64.v:91-95` 的 `pack_base` 只在
`!cur_dirty` 时更新）—— 这一句是换页不撕裂的前提：翻 bank 之后开始的那个字，一定整字落在新 bank。

**"乒乓"与"提交锁"为什么必须成对。** 初学者容易把它们当成同一件事的两种说法，其实它们管的是四个不同
的问题，少答任何一个都会得到一种独特症状：

- **写哪。** 写侧基址由当前 `bank` 选（`ddr_bank_commit` 里 `sav_base = bank ? BANK1 : BANK0` 那一行），
  而 `bank` 只在提交那一拍翻。
- **读哪。** 读侧**从不看 `bank`**，它只看交出去的 `completed_base`。于是"正在被写的那块"与"正在被搬的
  那块"是同一个寄存器的两个互补值，结构上不可能相同 —— 这条不需要时序、不需要握手，只依赖
  "读侧不许自己猜 bank"。**读侧一旦直接去读 `bank`（第一版几乎都这么写），乒乓立刻退化成撕裂**，因为
  翻位那一拍恰好是"新帧刚开始写、旧帧还没搬完"的那一刻。这是"为什么要成对"最硬的一句：
  乒乓本身不保证读侧看到的那块是完整的，它只保证两块不撞。
- **什么时候允许切。** `frame_done` 只说"验收门过了"，不说"数据已经躺在 DDR 里了"。中间还隔着异步
  FIFO、三段读流水和打包器自己的 FIFO，所以切换条件是 `saver_idle && tail_drained`（本节的
  TAIL_GUARD），而不是 `frame_done` 本身。把这两件事合成一件的板上症状，是右下角固定少 2 像素。
- **什么时候准搬。** 切完也不能马上搬，要等消隐窗口开门（§7）。**"切"与"搬"是两个时刻**：前者由数据
  落地决定，后者由扫描位置决定，两者相差最多一整帧。

四个答案分别落在 `ddr_bank_commit`（前三条）与 `frame_commit_lock`（第四条）。读代码时可以把它们当成
一条链检查：**bank → completed_base → commit_pulse → pending_base → copy_base**，五个名字各管一段，
少一段就少一层保护。

**跨域用翻转位而不是脉冲。** `frame_done` 是 125 MHz 域的单拍脉冲，先翻成 `frame_done_tog`
（`:37-41`），在 axi 域过 3 级再异拍出沿（`:42-47`）。理由与 §5 同源：脉冲跨域会被吃掉。

**TAIL_GUARD：换页必须等本帧数据真的全部穿过 CDC。** 只看打包器空不够 —— 最后几个 16 bit 还排在
异步 FIFO 与三段读流水里（`:24-29` 把五个输入都摆出来正是为此），它们会被写进**下一帧**的 bank，
刚提交那块内存的帧尾停在旧值，板上症状是 HDMI 右下角少 2 像素（`:6-7`，v6.4）。交付判据是
`tail_drained = cdc_empty && !cdc_rd && !cdc_d1_v && !sav_en && !sav_flush`（`:50`），提交条件
`commit_ok = TAIL_GUARD ? (saver_idle && tail_drained) : saver_idle`（`:51`；`=0` 那一支保留旧判据，
只供 A/B 对照复现）。

**PS 那条路：第三个 bank，不是仲裁的事。** PS 片源（SD 回放 / `fill`）落 `0x1010_0000`
（`src/rtl/top/system_top.v:140`、`src/ps/main.c:45`、`src/ps/sd_play.c:35` —— 三处必须相等，
`src/ps/main.c:40-44` 说得很清楚）。以前它也是 `0x1000_0000`，于是两路同时跑时 SD 的 DMA 会刷掉 ETH
正在读的那块，屏上"两个片源打架、闪"（板级实测 2026-09-24）。**关键一句：仲裁只管谁用那台搬运机，
管不到谁写 DDR** —— SD 的 DMA 走 PS 自己的 HP0 主端口，根本不经过 PL（
`src/rtl/top/pl_video_top.v:10-13`），所以只能靠地址分开。这是"两个模块看起来在抢同一个资源，其实
抢的是不同层的资源"的典型。

**写入器（`axi_frame_saver64`）的三条要点。**

- **AWLEN=0 的单元写 + 通道流水化**（`:40-44`）。v6.2 之前每字走完 `S_AW→S_W→S_B`，在途深度恒 1，
  HP0 的写延迟（约 40 拍，被显示拷贝抢端口时上百拍）直接成为吞吐上限 ≈20 MB/s，板上是"每包固定从
  第 48 字节起丢字"（`:5-6`）。现在 AW 与 W 并行挂出、各自握手，在途上限 `OST=8`（`:66`），
  B 通道**永不反压**（`:156`），发完立刻取下一个字 ⇒ ≤2 拍/字 = 400 MB/s。
- **`outst` 只减不回绕**（`:157-160`）：万一上游偶尔多回一个 B，回绕成 15 会让 `have` 永远不成立
  ⇒ 整条入包链卡死（板上"冻结"类症状）。宁可少计，不要锁死。
- **打包 FIFO 必须是分布式 RAM 且存储写独占一个不带异步复位的 always**（`:46-50`、`:104-114`）。
  写成 task + 和指针同在异步复位块里时，Vivado 报 `Synth 8-7186` 拒绝推断 RAM，512x64 bit 退化成
  3.29 万个 FDRE（实测对比 `FF=32904/LUTRAM=0` vs `FF=85/LUTRAM=864`）。

**一处留在树上的死线，值得当反面教材。** `copy_hold` 在 `eth_udp_video_top.v:21` 声明为输入，但
该模块里没有任何一处读它，而驱动它的是 `pl_video_top.v:488` 的 `assign copy_hold = 1'b0`。本项目为
这类"没人读的线"付过两次学费（`#57` 的位宽、`#61` 的多驱动，都写在
`src/rtl/top/pl_video_top.v:115-117`）。读端口表时先看有没有 `assign` 在驱动，再看有没有 `if` 在读。

**怎么验证。** `bash sim/run_one.sh tb_v6_tail_bank`（帧尾 / TAIL_GUARD，判的就是上板那份实现）、
`tb_v6_pingpong`、`tb_v5_bank`、`tb_v5_saver`（例化的是 `axi_frame_saver_burst`，属于退役候选，
见 `report/MODULES.md:8-10`）。

## 7. 消隐窗口与提交锁：什么时候准搬，搬不完怎么办

**是什么。** `src/rtl/video/frame_commit_lock.v` + `src/rtl/axi/axi_frame_writer_gated.v`，
例化在 `src/rtl/top/pl_video_top.v:385-395`、`:409-424`。

**先背时序发生器，因为本节和 §9 的账都压在它身上。** `video_timing` 是个纯计数器，数出
`x`/`y`/`hs`/`vs`/`de`/`frame_start`/`frame_done`（`src/rtl/video/video_timing.v:16-25`），
`video_timing_1024x600` 只是把参数填好的壳（`src/rtl/video/video_timing_1024x600.v:17-26`；板上用的
就是它，`video_timing_720p.v:4` 那颗钟是 75 MHz，而且它在当前树上不被例化）。三件事必须记住：

1. **判据全是区间比较**：`de_act = (h_cnt < H_ACTIVE) && (v_cnt < V_ACTIVE)`，`hs_act` 是半开区间
   `[H_ACTIVE+H_FP, +H_SYNC)`（`src/rtl/video/video_timing.v:49-51`）。内部没有任何运行时判断，
   所以它是整条链里最可预测的一块 —— 参数错一个数，症状会分散到五个模块上。
2. **次序**：`h_cnt` 回绕那一拍才 `v_cnt + 1`（`:37-45`），并且所有输出再打一拍（`x <= h_cnt`，
   `:63-67`）⇒ **引脚上的 `x` 是上一拍的计数**。§9 那条"下一行的行槽就是 `rslot+1`"整个推断压在这个
   次序上。
3. **极性**：`H_POL=1'b1`、`V_POL=1'b0`（`src/rtl/video/video_timing_1024x600.v:21`），于是
   `vs <= ~vs_act`（`src/rtl/video/video_timing.v:66`）—— `vs` 是**负脉冲**，它的上升沿落在场同步
   结束那一拍，而不是帧首。本节下面的"为什么不等 vs"就是被这件事坑过才改的。

一行 1344 拍里只有 1024 拍有效（`H_TOTAL = 1024+44+88+188`），一帧 625 行 = 600 有效 + 3 + 6 + 16，
刷新率 50 MHz / (1344 x 625) ≈ 59.5 Hz（`src/rtl/video/video_timing_1024x600.v:3-4`、
`src/rtl/video/video_timing.v:26-27`）。

**原理（先把预算的账算清）。**

```
 一行 1344 拍、一帧 625 行、有效 1024x600（src/rtl/video/video_timing_1024x600.v:3-4）
 竖消隐 25 行 x 1344 拍 = 33600 个像素拍 @50 MHz = 67200 个 axi 拍 @100 MHz
 一帧 = 512*300/4 = 38400 个 64bit 字 ⇒ 1 拍 1 字也够，但窗口形状不是矩形
 窗口：y = 600..623 整行可搬；y = 624 只有 x <= 1279 可搬
 disp_quiet = (y >= 600) && ((y < 624) || (x <= 1279))
```
（`src/rtl/top/pl_video_top.v:352-356`、`:401`）。**提前 64 个黑像素关门**是因为
`allow` 要过一层同步（3 级 + 异拍），到 axi 域已经晚约 5 个像素拍。

**为什么不能等 `vs` 上升沿再搬。** `video_timing` 的 `vs` 是负脉冲
（`V_POL=1'b0`，`src/rtl/video/video_timing_1024x600.v:21` ⇒ `vs <= ~vs_act`，
`src/rtl/video/video_timing.v:66`），于是它的**上升沿落在场同步结束那一拍**，也就是消隐已经过去了
`V_FP + V_SYNC = 3 + 6 = 9` 行（`src/rtl/video/video_timing.v:50`）。窗口只剩 16 行，白扔三分之一
预算。所以 v6 起搬运在 allow **开门那一拍**启动（`allow_rise`，
`src/rtl/video/frame_commit_lock.v:78-86`，理由就写在 `:78-80`）。这里有个值得背下来的因果：
`h_cnt` 回绕那一拍才 `v_cnt + 1`（`src/rtl/video/video_timing.v:37-45`），且所有输出再打一拍
（`:63-67`）—— §9 那条"下一行的槽就是 `rslot+1`"整个推断压在这个次序上。

**提交锁解决三件事。**

1. **撕帧。** 没锁时搬运可能从一帧中途开始，屏上半新半旧。锁把"请求"与"基址"分开：`pending` 只记
   请求、`pending_base` 只更新（`src/rtl/video/frame_commit_lock.v:30-43`），真正的 `copy_base`
   只在 `start_copy` 那一拍从 `pending_base` 取（`:111-124`）⇒ 搬运期间到达的新帧只改 pending，
   下一轮才生效。**这一句是本章最值钱的一条**：同一个变量在两个地方各读一次，就是两条真相。
2. **撞窗口。** 搬运超出一个消隐期 = 换帧跨两个消隐期 = 运动物体被一条水平缝切开还带拖影。两级
   防护：模块内看门狗 `wd_cnt >= WD_CYC`（默认 2_000_000 拍 = 20 ms，`:8`、`:88-98`）触发
   `copy_abort`，搬运机随即复位（`src/rtl/axi/axi_frame_writer_gated.v:118-121`）；板级另有
   `copy_overrun` 粘滞位（比较 `row_copy_cycles > VBLANK_AXI_CYC`，
   `src/rtl/top/pl_video_top.v:400-407`），用 led[0] 的闪速区分：**慢 1.5 Hz 正常、快 6 Hz 超窗**
   （`:982-983`）。
3. **跨域丢沿。** `copy_abort` 在 axi 域只有一拍（10 ns），两钟又同源同相（MMCM 出来的 100/50 MHz），
   于是翻转沿**正好压在**像素域的采样沿上 —— 收不收得到取决于建立/保持窗口里的亚稳。这里必须推一遍：
   **电平型 3 级同步器修不好它**（`src/rtl/video/frame_commit_lock.v:100-105` 明写"实测与裸采逐相位
   一模一样"），因为慢域的采样沿可能整拍错过那个 10 ns 电平。正确形状是**翻转式脉冲同步器**
   （`abort_tgl`：每次 abort 翻一位，目的域过 3 级再异拍，`:26`、`:106-109`），与本文件像素域→axi
   那一侧的 `blank_tog`（`:59-63`）完全对称。两次 abort 至少隔 `WD_CYC`，所以两个翻转沿不会落进同一
   个像素周期被并成 0 次（`:26-28`）。`report_cdc` 抓不到这类错 —— 那份报告只有"时钟对 + 端点数"
   的粒度、不点名信号；凭据只能是台架 `sim/tb_v79_abort_toggle.v`（错开 4 ns 时裸采 0/3、翻转式 3/3，
   见 `:105`）。顶层那一路同步器就摆在那儿：`src/rtl/top/pl_video_top.v:437-444`。

**搬运机（gated 版）的三个关键。** 在途 burst 上限 `MAX_OUT = 4`（4 x 16 拍 ≈ 64 beat，够盖 HP0
读延迟又维持 1 beat/拍，`src/rtl/axi/axi_frame_writer_gated.v:39-46`、`:71-74`）；
`allow && skid 空` 时 AXI 数据**直通**写帧缓存（`do_direct`，`:77`、`:143-149`），不允许写时先塞
64 深 skid（`:78`、`:84-89`）；`done` 要等最后一个字真写完（`:157-161`，不是"最后一个 beat 收到"）。
skid 那两片数组同样必须写成**分布式 RAM 且不带复位**，否则 `Synth 8-4767`，64x83 bit 全掉进触发器
（约占当时剩余寄存器的一半，`:49-53`）。

**`frame_latency` 量的是三段时间。** `c1 = commit→copy_start`（等窗口）、`c2 = copy_start→copy_done`
（搬运）、`c3 = tot−c1−c2`（等扫描轮到它）；三段成因不同，合起来报等于没报
（`src/rtl/video/frame_latency.v:2-3`、`:16-19`）。两条硬规矩：① **PL 里不做除法** —— 第一版把拍数
除以 100，除数不是 2 的幂，综合架出组合除法器，100 MHz 域 WNS −5.014 / 96 个失败端点（`:42-45`），
现在只报拍数、换算在 `src/host/health_read.mjs` 的一个常量里做；给 OSD 的 ms 改成"一轮一次的 32 拍
逐次除法"（`:135-138`）。② **读回口必须读一组快照**而不是五个各读各的 —— 五个数来自不同轮是完全
正常的（r50 实测 11 组里 4 组破坏 `tot >= c1+c2`），而 RTL 里 `t_start <= t_done <= cyc` 是构造性
成立 ⇒ **错的是读法不是硬件**（`:21-25`、`:83-92`）。武装信号就是"lane 选择指到 25"那一拍
（`src/rtl/top/system_top.v:220`）。

**怎么验证。** `bash sim/run_one.sh` 逐个跑：`tb_v5_lock`（窗口/pending/abort）、`tb_v5_gated`
（只在消隐写帧缓存）、`tb_v57_first_ar`（第一个 AR 的发起时机）、`tb_v58_full_done`（done 必须等
最后一个字）、`tb_v571_allow_lead`、`tb_v5_vblank_copy`、`tb_v6_vblank_copy`、`tb_v90_latency`
（三段恒等式与快照）、`tb_v79_abort_toggle`（相位扫描）。板级症状对照见 §12。

## 8. 显示帧缓存与唯一的读口

**是什么。** 现在真用的是 `frame_buffer_w64`（64 bit 写口 + 16 bit 随机读 + 原始字出口），
它被包在 `fb_bilin` 里面（`src/rtl/process/bilin/fb_bilin.v:65-69`）。`frame_buffer`、
`frame_buffer_db`、`line_cache`、`axi_frame_writer`（16 bit 时代的搬运机）在当前树上**都不被例化**，
`report/MODULES.md:8-10`、`:35`、`:45`、`:60` 已经把这件事写清；它们仍在仓库里只为台架与对照。
`src/rtl/video/fb_pack.v` 这个文件**不存在**（旧学习稿里那段关于它的话，随第二块板一起没了）。

**为什么要 64 bit 写口。** 搬运机一次 burst beat 拿回 8 字节 = 4 个 RGB565。写口若只有 16 bit 就得
用状态机分四拍拆开喂（`src/rtl/axi/axi_frame_writer.v:113-127` 正是这个老写法，现已不被例化）。而
消隐窗口只有 67200 个 axi 拍，一帧 38400 个字拆成 153600 次 16 bit 写根本来不及 ⇒ 一拍写完一个字
（`src/rtl/axi/axi_frame_writer64.v:83-87` 一类的 `waddr_pix[18:2]` 折地址）。

**原理（地址怎么折 + 为什么必须拆成两块 2 的幂）。**

```
 64bit 字：[ 63:48 | 47:32 | 31:16 | 15:0 ]
 车道：      p3      p2      p1      p0    ← 小端：字节 0-1 是第一个像素
 读像素 px： 物理字地址 = px[18:2]，4 选 1 的车道 = px[1:0]
```
BRAM 推断会把**非 2 的幂**的深度向上补到 2^16：38400 深的单阵列实测吃 128 块 RAMB36，而 xc7z020
只有 140 块（全设计 BRAM 占用就卡在这里）；补成 32768 + 8192 两块后实测 80 块，省下的 48 块给了
插值行缓存。这是对照实验的数（`sim/probes/fbtest.v:5` 那份 V0/V5 对比），不是推算
（`src/rtl/video/frame_buffer_w64.v:4-7`）。切分本身：`WORDS=(W*H+3)/4`、`D_LO` = 不超过 WORDS 的
最大 2 的幂、`D_HI` = 余量的上界，`bitsof` 在 elaboration 期算完、不留硬件（`:23-35`）。

**读侧为什么"两块每拍都读一次"。** 若先选块再读，读出就多一级 mux ⇒ 读延迟变 2 拍。现在的写法是
两块各读一次、由打过一拍的 `sel_hi` 选（`:51-54`、`:62-70`），越界一侧用掩码 `& (D_HI-1)` 夹住地址
所以不会读出 X（`:63-64`），越界读回黑另由 `blank <= (rd_addr >= W*H)` 管（`:67`、`:80`）。
**读延迟是契约**：顶层 `MIX_D = 3 + 1 + 1 + u_pipe.LATENCY` 里那两个 `1` 就是"地址寄存 + BRAM 读出"
（`src/rtl/top/pl_video_top.v:307-309`、`src/rtl/process/bilin/fb_bilin.v:39-41`）。把它改成组合读出
会让混色级、skid、`SEAM_TAPS` 一起错位；守它的是 `sim/tb_fb_roundtrip.v`（加地址后的下一拍必须出数）。

**`fb_bilin`：一个读口怎么同时服务双线性。** 每个源像素在屏上占 2 列 x 2 行，也就是**天然有 4 个
50 MHz 拍**在问同一个源像素 —— 一个每拍一读的口正好被用满，不需要第二个口
（`src/rtl/process/bilin/fb_bilin.v:4`）。四个抽头按 `(row0,col0)` 的四种组合分时发出
（`:37-40`、`:58`），末列/末行的 +1 抽头**折回图内**并把小数钉 0（`:51-57`：只做"钉 0"不够，
`w_b = w_a + ROW_WORDS` 会读到帧缓存的填充区，硬件里是上电 0、xsim 里是 X，而 `X x 0 = X` ⇒ 整行被
污染）。⚠ 这一处"钉 0"是 `fb_bilin` 自己**主动**的两道钉子（`bilin off` 与末列/末行折回），不是
#104 那条：#104 说的是**上游 `zoom_mapper` 的旋转支把小数写成 0**，r94 已修，现在旋转态也带非零小数
（取 `>>> 16` 之后的 `[15:8]`，纵向连着 floor 一起退一格），所以旋转态的 `bilin off ↔ on` 真的会换一张画。
索引一律用**显示列对号** `jd = x[9:1]` 而不是源列 `sx`：旋转时 `sx` 沿一行会停滞/倒退，用
`sx` 当地址会让同一个格子被别的源行重写 ⇒ 满屏噪点（`src/rtl/top/pl_video_top.v:690-692`）。

**两台搬运机共用一个读口与一个写口。** `eth_mode ? row_* : fill_*` 那束 mux 在
`src/rtl/top/pl_video_top.v:654-663`，主人由 `src_arb` 定（§10）。ETH 那台受消隐门控与看门狗；PS 那台
（`axi_frame_writer64`）由"发布"触发、从帧首开始逐行搬、端口表里**没有** allow
（`src/rtl/axi/axi_frame_writer64.v:9-31`、`:63-72`）。这一处差别值得注意：PS 路径的原子性靠的是
"发布发生在帧起始 + 搬运快过扫描"，不是靠窗口门控（这条是我从端口表与两处赋值推的，源码没有把它
写成结论 —— 按本套规矩标为**推断**）。

**怎么验证。** `bash sim/run_one.sh tb_fb_roundtrip`（全帧写完 + 逐像素回读、分块边界、越界读回黑、
越界写不污染）、`tb_v101_fb_bilin`（插值读口的相位与折回）、`tb_zoom_frac`（上游送进来的小数与 floor
是否自洽，#104 那一刀的判据，旋转态也要有非零小数）、`tb_tap_sched`、`tb_fb_rd5x`
（后两个测的是被换掉的另一条方案，`report/MODULES.md:8-10`）。读盘的一条：
`grep -n "ram_style\|D_LO\|D_HI" src/rtl/video/frame_buffer_w64.v`。

## 9. 坐标、两条抽头与逐像素混合

**是什么。** 片源 512x300（`src/rtl/top/pl_video_top.v:6-7`）、面板 1024x600，整屏**只有一个视口**：
源列 `cx = x>>1`、源行 `cy = (y>>1)` 夹到 `IMG_H-1`（`:242-243`）。原图抽头与处理抽头从此吃**同一份
源坐标**，缝只是逐像素二选一。

**为什么要"一份坐标"。** 硬件预算里养不起真 scaler，最便宜的铺满方式就是"每个源像素画 2 列 x 2 行"
= 坐标右移。同时，把两份坐标合成一份是"分割线 0~100 % 可调"与"整体旋转缩放"在数学上第一次相容的
前提（旧几何左右各画一整幅，缝只能钉死在 512）。

**原理（这份假设破了会怎样，三层都推一遍）。** "同一份源坐标"的含义是：**同一个显示列 `x`，链子的
输入与输出指向同一个源像素**。破了：① 缝两侧同一行画面被错开 ⇒ 一条内容对不上的竖接缝；
② `oob`（画面外）对两个抽头不再是同一件事，同一格里一边黑一边有内容 —— 顶层今天正是靠这一点才敢
把一个 `oob_out` 同时喂两口（`src/rtl/top/pl_video_top.v:869`、
`src/rtl/video/split_display.v:45-47`）；③ "缝位 = 图像列"这类判据失去意义：它问的是"这一格属于画面
哪一侧"，两抽头各有坐标时这问题没有唯一答案。

**为什么要提前 `OFF_LINES` 行、还要再补 `BILIN_ROWS` 行。** 行缓存式 3x3 滤波收到第 y 行才算得出第
y−1 行的窗口 ⇒ 内容必然滞后一行；**数据不能提前，只有地址能提前**（帧缓存是随机地址的），于是喂
mapper 的行号加 4（`:244-250`，滞后量的唯一出处是
`src/rtl/process/proc_pipeline.v:20-24`、`:45`）。双线性读口又带来"一对显示行的结果要在这对的第二行
才算得出" ⇒ 再补 2，而且**必须是偶数**：成对奇偶由 `row0 = ~y[0]` 决定，加奇数会让一对的两行分属两个
源行（`:250`、`:263`）。代价是帧末尾几行的请求必然越界，而它们要输出的行已不在本帧 —— 它们喂的是
**下一帧的头几行**，所以越界要绕回而不是钳到末行（`:265-271`）。第一版钳到 `IMG_H-1`，屏顶那几行画的是
"这张图自己的最后一行"：内容逐帧随画面变、位置永远贴顶边，而**列位置一格都不变** ⇒ 普通逐列判据看不见
它（凭据是 `tb_v98` 专门加的 C5/C5b/C5c）。

**`raw_line_delay`：一块 1W1R 的行环形 RAM。** 把一路像素流整体延后 N 个显示行，N = `u_pipe.OFF_LINES`
（`:726`，例化 `:733-737`，`W = 2*IMG_W = 1024`、`DW = 17`）。

```
 LINES=4 ⇒ RLOG = clog2(LINES+1) = 3 ⇒ 环 8 个行槽
 写槽 = y 的低 3 位；读槽 = (y − 4) 的同一几位 ⇒ 恒差 4，同一拍读写不撞
 同一拍：写 mem{wslot,x}、读 mem{rslot,x} ⇒ 延迟 = 4 行 + 1 拍，列一格不偏
```
（`src/rtl/video/raw_line_delay.v:41-43`、`:55-56`、`:80-83`）。**为什么环深取 `2^clog2(LINES+1)`
而不是 `LINES`**：若环深正好等于 LINES，写槽与读槽算出来是同一个数，那一拍读到的是"自己正在覆盖的那格"
的旧内容 ⇒ 延迟 0 行，环白搭；取 `>= LINES+1` 才保证两者不同（`:41`、`:56`）。再向上取 2 的幂，是让
`mod` 退化成**切位**，不留运行时除法/取模（`:37-40`）。**为什么不是几级 `line_cache` 串起来**：第一版
就是那么写的，被台架当场打掉 —— 串 N 个行缓存 = 延后 N 行**又**多花 N 拍 ⇒ 列方向偏 N 格；而这种错在
**模块级**台架里看不见（每台架只喂自己那一级），又一次"只有顶层才看得见"（`:6-7`、`:10-14`）。

**#102：行首那一格读的是消隐期的地址。** "列不偏"只在**一行之内**成立。多出来的那 1 拍在行首会越过
消隐：一行 1344 拍而有效列只有 1024，尾部那 320 拍里 `x[CWID-1:0]` 从 0 数到 319，而 RAM 读出的是
**上一拍发出去的那个地址** ⇒ 下一行第 0 列摆出的恰好是消隐期最后那个格子（台架读数：源列 160，定义
要源列 0）。一帧 600 行、行行都有一格，这就是用户念的"从视频里切出来贴在屏幕左边缘的一条线"
（`:58-62`，由 r80 的 P100 探针量出来，不是推的）。**两种"看着更简单"的修法都不行**（`:77-79`）：把
读出再打一拍 = **每一列**都推后一格，正是 #92 那一族整列错位（C1c/C2b 立刻红）；把消隐期读地址一律
钳到 0 = 帧头那一行仍错一行，因为 `V_TOTAL = 625` 不是环深 8 的整数倍，25 行竖消隐会把槽位相位挪走。
**现在的做法**：在"`de` 刚掉下去"那一拍（`bl_head = !de && v`，每行只有一次、竖消隐里没有）做一次
预读 —— 那一拍的 `y` 还是刚结束的那一行，所以下一行的槽是 `rslot+1`（`y` 在 `h_cnt` 回绕时才加一，
`src/rtl/video/video_timing.v:37-45` 那个次序在这里兑现）；发 `{rslot+1, 0}`，晚一拍回到 `q`，再锁
一拍进 `head_q`；输出只在 `de && x==0` 那一格选 `head_q`（`:73-76`、`:95`）。其余消隐拍照常读（值落在
`de_out=0` 的位置上，谁都看不见），所以行末最后一列原本那次读一点没动。还有一个必须留的细节：
`look/head_q` 只许在**一个** always 里写 —— RAM 与其读出不带异步复位，同一根寄存器分给两个进程综合
会直接报多驱动（`:84-94`）。
⚠ 读这里时留意：文件头把 `W` 说成"源列数"、环宽写成 `8x512x16`（`:10`、`:38`），而顶层递进去的是
`2*IMG_W = 1024` 个**显示列**（`:733`，`:60` 自己那句"有效列 1024 / 消隐 320 拍"也是按 1024 走的）——
那两行注释旧于代码。

**`DW=17` 那一位不是装饰。** 顶层把越界标签与像素**打包过同一条环**（`:733`）。以前 `pix_raw` 过环
（4 行 + 1 拍）而 `oob` 绕开环只走等长 skid ⇒ 到混色级两者差 (4 行, 1 列)：画面右沿最后一列被"别的
格子"的越界位按黑、上下边界的越界位来自别的行（屏上表现是"上边缘有东西闪"，
`src/rtl/video/raw_line_delay.v:11-16`）。16→17 位仍在 RAMB36 的 18 位宽度模式里 ⇒ 一块 BRAM 都不多
要，但这句必须在构建后的 `utilization.rpt` 上核对、不许停在注释（`src/rtl/top/pl_video_top.v:730`）。

**`split_display`：标签必须与内容同一拍。** 混色级手里三样东西：`orig_pix`、`proc_pix`、以及"这一格
选谁"的坐标标签。前两个是**内容**、第三个是**标签**，必须站在同一拍。历史上不是：

```
 内容站的那一级 = 3(mapper/打拍) + 1(读地址寄存) + 1(BRAM 读出) + 15(链 LATENCY) = 20 = MIX_D
 旧代码的标签用第 11 级 ⇒ 判定比内容**旧 9 列**
```
旧几何里"缝以外那一路被强制清 0"，于是在缝左边约 9 列里标签说"这是原图侧"、同一拍真正到达的内容却
是另一路（已被清 0）⇒ 选出来的是 0 ⇒ 一条**近黑的竖带**（`src/rtl/video/split_display.v:10-15`）。
讲成原理是三层：① 标签与内容必须是**同一份流上的同一个位**，不是"差不多对齐"；② 错开的量 = 两条链
的拍数差，所以它是**固定列数**、不随倍率/角度变 —— 这解释了"1.00x 时画面铺满整屏、偏一列看不出来；
一缩小就露出来"；③ **改级数不能只改一半** —— r59b 修 #68 时只把 `x_sel` 提到 `MIX_D`，而 `x/y/de/
hs/vs` 留在第 11 级 ⇒ 送到面板的 `de` 比同一拍的像素早 9 列：屏上最左 9 列画的是**上一行末尾那 9 格**、
最右 9 列的像素落进消隐丢掉（对着黑底看不见），而 OSD 一格都不动（它的 `x/y` 与 `de` 同源、跟着一起
错）。三条观察说的是同一件事（`src/rtl/top/pl_video_top.v:858-863`）。

**两条抽头各走几拍，一处定义。** 原图那一路 = 行环的 1 拍 RAM 读出 + `orig_skid` 的 `PROC_LAT` 拍 =
16 拍（`:765-794`）；链子那一路 = `LATENCY` 拍 + `pipe_dout_q` 1 拍 = 同样 16 拍（`:770-774`）。
`PROC_LAT`/`LEFT_TAIL` 直接取 `u_pipe.LATENCY`（`:761-762`），顶层不另写数字 —— 以前那里写字面量 7，
链上加一级就得记得改这里，忘了不是编译错而是两窗错开 N 个像素。`SEAM_TAPS = MIX_D + 1 - 3` 同样由
深度推出（`:847`）：图像域那一路的"哪一侧给原图 / 画不画蓝线"在**源头那一拍**判完，只让 1 个位跟着
内容走 18 拍（`src/rtl/video/seam_src.v:24-25`、`:34-47`），比把 12 位 `sx` 打 18 级再比较少 200 多个
触发器。`TAPS` 差几拍在这里只是把整条线**刚体平移**几列，不会再制造暗带 —— 暗带的根因是"标签与内容
不是同一份流"，而这里两者是同一份流上的同一个位（`src/rtl/top/pl_video_top.v:844-846`）。

**混色级的输出形状。** `left = seam_in_src ? ~src_orig : (x_sel < seam)`（缝位是**输入**，不再是参数
`PANE_W`，`src/rtl/video/split_display.v:44`）；`sel = oob ? 16'h0000 : (take_orig ? orig_pix :
proc_pix)`（`:49`）—— 画面外给黑是因为"本来就没有源像素"，给黑底才读得出"这是一幅被摆放的画面"而不是
"画面被切掉一块"。RGB565→8 bit 是**位复制** `{r5, r5[4:2]}` / `{g6, g6[5:4]}`（`:67-69`），不是左移
补 0，所以灰阶不会多出台阶。蓝线画在 `x_sel == seam-1 || == seam` 两列（`:53-54`），颜色 `40/40/FF`
（`:65`）：判据是 `x < seam`，所以这两格正好压住边界，而判据本身一个比特都不用改；`seam = 0` 时
`seam-1` 是 12 位无符号的 4095，极端缝位有专门踩点（`sim/tb_v97_seam_scan.v`）。链子现在的"一行"是
**显示列 1024**（`H_ACTIVE = 2*IMG_W`，`:745`），代价写在原处：行缓存宽度翻倍（约 +8 块 BRAM），且
3x3 的空间尺度从"源像素"变成"显示像素"（横向覆盖 1.5 个源列）。

**这一族为什么特别容易读错（#92 / #97 / #98 / #102 合起来看）。** 上面几段讲的是一件事的四个侧面：
**显示侧的地址是"数出来的"，而消隐期也在数，只有 `de` 决定这些数有没有人看。** 把四个案子摆在一起，
能数出五条共同成因，每条都是可以带去下一个工程的话：

1. **两套编号叠在一起，而切换点不写在名字上。** 面板坐标 `x` 一行里从 0 数到 1343，其中只有 1024 个是
   列；源行 `cy` 由 `y>>1` 再夹到 `IMG_H-1`；帧缓存的读地址是"像素下标折成字下标 + 4 选 1 的车道"（§8）。
   这三套都叫"坐标/地址"，但**周期、位宽、以及"越界了怎么办"各不相同**。案子里没有一条是"算术算错了"，
   全都是"用了另一套编号的规矩"：切 `off[16:1]` 当行号，是拿半字下标当位段用（§3）；把消隐期的读地址
   一律钳到 0，是拿"行内列范围"去管"帧内槽位相位"（下面第 3 条）。
2. **消隐期不是"暂停"，是"照跑但没人看"。** 拍子继续、地址继续发、RAM 继续按**上一拍发出去的那个地址**
   出数，只是 `de_out=0` 让结果无处显示。于是"行末最后一拍"与"下一行第 0 格"之间只隔一个寄存器：#102
   那一格错位正是这么从消隐期走私进显示区的。硬推论：**任何只看一行之内的判据，都看不见跨行边界的错**。
   这解释了为什么同一条 bug 在模块台架全绿、上板却是一条贴着左缘的细线。
3. **"钳位"与"绕回"只差一个词，语义相反。** 钳到 `IMG_H-1` 的动机是"别让地址越界"，代价是把越界请求折成
   "这张图自己的最后一行" —— 一个真实存在、内容随画面变、位置永远贴顶边的错误。绕回则是"让第
   `y+IMG_H` 行的请求落到第 0 行"，因为它喂的本来就是下一帧的头几行。挑这一对的时候，
   `V_TOTAL = 625` 与环深的整除关系也要一起看：竖消隐那 25 行会把槽位相位挪走，所以"钳到 0"这种看起来
   更保守的修法仍然错一行。
4. **标签与内容分开走，就一定会在某一天不同级。** #92 的第三笔是 `oob` 标签绕开了环而像素过环 ⇒ 到混色级
   差 (4 行, 1 列)；#68 是列标签停在第 11 级而像素在第 20 级 ⇒ 差 9 列。两次的修法都是同一个动作：**把
   标签塞进内容正在走的那条流水**（`DW=17`、`x_sel` 提到 `MIX_D`），而不是给标签再补几条延迟线 —— 后者
   只能对齐"平均值"，永远对不齐"同一拍"。
5. **尺子自己会错，而且错得很安静。** #92 那一轮的"三档各 484"先被台架的心跳节拍污染过一次，把节拍从
   "跟着 `frame_start`"改回"按时间翻"之后，八档才给出干净的直方图；#102 更直接 —— 模块台架的消隐只有
   2 拍且 `x` 停在 `W-1`，而顶层一行 1344 拍、320 个无效列，**洞在激励里根本不存在**。这一族最贵的教训
   不是 RTL 写错，而是"用一份不匹配真实栅格的激励所证明的事情"。

`#98` 记的是这一族**还没结束**的那一半，值得单独念一遍：绕回改完之后屏顶不再画末行，但**源行 0 在整帧里
一个像素都没出现过**（帧头那一对显示行吃的是源行 1）。缝左、缝右、中缝三列读数同一个值，说明它跟"原图抽头
还是处理抽头"无关。r80 那一轮量到的两条数把范围收进了 `u_pipe` 内部（链子**入口**在帧头 0..5 行摆的是
源行 2,2,3,3,4,4，链子**出口**摆的是 2,2,2,2,2,2，而原图抽头的帧头逐格等于定义 ⇒ 重复发生在链子里，不在
地址侧也不在行环侧）。于是下一个嫌疑是 `src/rtl/process/proc_box_blur.v` 里 `stale_row` 那一族补偿 ——
它是"地址还不绕回"的时代把陈旧中心抽头换成邻居行的补丁，绕回之后它等于把正确数据扔掉。留档明写这一刀
**r80 没有动、判据继续红、不冻结**，理由是同一个 `stale_row` 被另一份台架的激励判着，而那份激励没有绕回
⇒ 必须连着改激励，"改一处红一处是必然的"。**学习点**：一个还没结的案子会把"已证"与"嫌疑"分层写清楚，
而不是先把修法写进 RTL 再回头找理由。

完整账目在 `report/log/ISSUES.md`，本章只讲形状：#38（第 295 行起，换掉厂商收侧的整条决策）、#92 的三笔
与"收尾"（第三笔在 `:3446`、收尾在 `:3852`）、#97 的八条追加（第二~四条就是"绕回"那一刀）、#98
（`:4508`）与"#98 的状态"（`:4771`）。**具体读数、凭据文件名、哪一轮动过什么一律以那份留档为准**，
不要在第二处抄一遍数字 —— 抄了就会有一个过期（§13 第 1 条教的正是怎么查两份凭据是不是同一轮的）。

**怎么验证。** `bash sim/run_one.sh tb_v100_raw_delay`（T1 稳态逐格、T3 `de` 链与数据链等长、T4
`LINES=0` 必须组合直通、T5 跨槽位回绕仍对齐；**#102 之后新增的 T7/T7k/T8 才是关键**：原来那几条的
"消隐"只有 2 拍且 `x` 停在 `W-1`，而顶层 `x` 一路数到 1343 —— 洞在激励里不存在，于是模块台架全绿、
板上却有一条左缘细线）。`tb_v89_align`（整链是不是一个干净的平移）、`tb_v97_seam_scan`、
`tb_v92_seam_bleed`，以及唯一例化顶层的那份 `tb_v98_top_seam`（约 75 分钟；它的 C1c 钉"原图抽头与
`x_d[MIX_D]` 同级"，C3 只用输出引脚建立面板坐标、不引用任何内部标签）。这里改错对齐**不会**让综合或
仿真报错，只有顶层台架会红。

## 10. 谁拥有搬运机、此刻到底有没有片源

**是什么。** 三件分开的事：`src_arb`（谁能用 AXI 读口与帧缓存写口）、`src_life`（这一路此刻到底还有
没有货）、`src_mode`（ AUTO / 锁 ETH / 锁 SD / 锁 TEST 四态环，按键与串口命令谁优先）。

**为什么仲裁要单独成模块。** 因为正确答案**不是**"哪边有数据"，而是"哪边活着 + 现在能不能安全换手"
（`src/rtl/util/src_arb.v:2-16`）。老写法是 `eth_mode = 3FF(|s_pkts)`：① `|s_pkts` 是"自配置以来收过
任何一个包"，PC 的 ARP 就够触发，而且**拔网线也不回 0** ⇒ PS 片源被永久锁死（#47 的根）；② 就算换成
"最近有包"，两个引擎共用同一个读口 + 同一个写口，选择位在一次拷贝**中途**翻转会留下半开的 AXI 读
突发。于是这里把两件事拆开：**活着**由 `link_monitor` 用 `stall_ms` 判（并且必须与 `eth_tb_ok` 相与，
§5，`:51`）；**换手**只在两个引擎都空闲时发生（`both_idle`，`:48`、`:69-72`），往 PS 方向再多等
`T_OFF_CYC = 2_000_000`（= 20 ms @100 MHz，`:20`，这是**第二级**迟滞，第一级是 `stall_ms > 200 ms`）。
手动锁**只改"谁想要总线"，不改"什么时候能换手"**（`:41-45`）—— 直接在输出上加 mux 是最容易想到的
写法，也是错的。仲裁还把"判决那一拍看到的三个输入"寄存成 `why_ps`
（`:32-39`、`:62`）：屏上/上位机看到的"原因"必须与主人出自同一份输入，否则就是 #55 那一类"两个地方
各说一套"。

**为什么"有片源"必须是活判据（#94 的修法）。** 原来顶层是
`have_src = eth_link_pix | ps_src_seen`，**两个位都只置位、从不清零** ⇒ "曾经有"与"现在有"同形。
后果：拔网线落 SD 一直对（ETH 那路有 200 ms + 20 ms 两级迟滞），但再拔 SD 卡 ⇒ 画面**永久冻在最后一
帧**、插回也不恢复，而 `Src:` 那一格还写着 `SD`、`FPS:` 还在 30 —— 画面静止而两处读数都说正常。
现在的判据吃的是**已有的发布握手**给出的 `ps_pub` 脉冲（`src/rtl/util/src_life.v:20-23`、`:36-49`：
零新增异步配对，`cdc.rpt` 不该因此多出一行），超时 500 ms（`:15`、`:31-32`），顶层参数
`PS_SRC_TIMEOUT_MS = 500`（`src/rtl/top/pl_video_top.v:536-542`）。于是：

- 500 ms 收不到发布 ⇒ 认为 PS 这一路没片源 ⇒ 画面交回仲裁（有网络回网络，没有回图卡）。
- 固件必须替"我还要屏"说话：`stop` / `play 0` / `frame N` / `fill` 之后 PS 不再每帧发布，而屏上那张
  画**是要留住的**，没人替 PS 说话就会落图卡（`src/ps/main.c:232-248` 的 `ps_keepalive()` 每 100 ms
  把**同一帧**重发一次，DDR 里那张画没动、PL 重新搬一遍、屏上无感）。100 ms 对 500 ms = 5 拍余量，
  这个比例由 `sim/tb_v102_src_life.v` 的 S12 钉住。
- **只有真的读卡失败才停心跳**：`card_gone()`（`src/ps/sd_play.c:583-590`）→ `ps_source_lost()`
  （`src/ps/main.c:252-257`）。被拒的命令（帧号越界、没挂载）**不停**心跳，因为屏上那张仍是 PS 主动

  （`src_life.v:52-54`、`report/COMMANDS.md:106`）。

**最后"该画什么"落在三行上。** `pub_consume = frame_start && src_use && !owner_eth_pix`

## 11. 最后两级：OSD 与 TMDS

**是什么。** `osd_overlay` 是像素通路的最后一级功能块，把五行状态字叠在画面上，输出比输入晚 **2 拍**
（`src/rtl/video/osd_overlay.v:2-4`），后面只接 `rgb2dvi`（`src/rtl/top/pl_video_top.v:970-976`）。
版式行数写在参数里（`N_LINES = 5`，`:19`）：

```
 L0 1024X600  FPS:59  SRC:ETH   :256-   ← 画**面板**尺寸（OUT_W/OUT_H = 2*IMG_W/2*IMG_H）；`FPS:` 数的是**显示场同步**（`pl_video_top.v:893-910` 累加 `vs_tick`，1344×625 @ 50 MHz ⇒ 59.5 场/秒），**不是片源帧率**（片源帧率的可信出处是板上 100 帧滑窗，`data/metrics.csv`；把它改成"写进屏的新帧"是任务 #128 的 B 方案）
 L1 PIPE:11000 TH:80 GAMMA:1.8  :268-
 L2 ROT:45°  ZOOM:0.75X(Fit)     :282-   ← r94 起这一格的后缀是 `zoom_fit_en | rot_forced` 决定的（顶层
                                          `pl_video_top.v`）：旋转真的在生效时，生效倍率被钳进 fit，
                                          即使 `zoom fit 0` 也标 `(Fit)`；`(Auto)` 只在不钳的时候出现
 L3 SPLIT:50%(AUTO) LATENCY:16MS :294-
 L4 TEMP:47C  ETH IS NO SIGNAL   :305-   ← 第 5 行放片上温度与"没有 ETH 信号"
```
前四行的字段、顺序、空格是定好的格式，所以新话只能另起一行（`:16-18`）—— 第 5 行就是为这件事开的。

**为什么要拆一拍寄存（#96）。** `ly / LINE_H`、`lx / CHAR_W`、`lx % CHAR_W` 三个除/模（`LINE_H=31`、
`CHAR_W=18` 都不是 2 的幂）原本和"取字符 → 查字形 → 选位图行 → 上色"串在同一拍里，最差那条 29 级 +
9 个 CARRY4。拆法：把除/模那一半单独寄存一拍，背景像素与 `de/hs/vs` **跟着同样晚一拍** ⇒ 内容与坐标
仍同一拍（`:71-104`）。另一条同族的账：**行号位宽必须跟着 `N_LINES` 走**，写死 `[1:0]` 时加到第 5/6 行
屏幕上永远取不到，而综合与时序报告全绿 —— 这种错只有屏能看见（`:88-90`）。

**哪两格的数据来自 PS。** 只有两格，而且都挤在 gamma 那个寄存器（`CFG_DATA1 = 0x4122_0000+0x08`）的低
14 位里：`gamma_disp`（γx10，`src/rtl/process/effect_ctrl.v:60-67` 解出来）与 `temp_disp`（两位十进制
BCD，`:61`）。PL 那条链的复位值是 `0x…FF`（`:45-48`）⇒ app 起来之前屏上是 `--` 而不是 `00C`；
OSD 侧任一半字节 >9 就画 `--`（`osd_overlay.v:314-320`）。**为什么十进制在 PS 算**：OSD 那五行字符是
一整块组合逻辑，而 `u_pipe/xd_reg → u_osd/g_reg` 正是那一组的 WNS 最差路径，在屏上再加一次 `/100` 与
`/10` 就是往全设计最差的链上加深度（`src/ps/main.c:79-83`、
`src/rtl/process/effect_ctrl.v:63-65`；同一手法先例是 Latency 那一格"换算在 axi 域做完再跨域"，§7）。
`Latency:` 那一格的跨法是"心跳与发沿是同一件事"：没有新测量就等于心跳停了 ⇒ `hb_gone` 亮 ⇒ OSD 画
`--`，于是"ETH 停了、屏上还挂着上一轮那个 12 ms"不可能出现
（`src/rtl/top/pl_video_top.v:908-932`）。

**OSD 用的坐标取自哪一级。** `x_d[MIX_D]` / `y_d[MIX_D]`（`:950`）—— 与混色级同一束标签。它相对
`de_o` 的"早一拍"关系一个字都没变（`:946-949`），所以 OSD 在屏上的位置一个像素都不动。

**怎么验证。** `bash sim/run_one.sh tb_osd_lines`（五行版式与"画不出可信读数就画 `--`"）、
`tb_v794_osd_glyph`（256 个码点全比字形）。读盘的一条：
`grep -n "L0:\|L1:\|L2:\|L3:\|L4:\|N_LINES" src/rtl/video/osd_overlay.v`。
