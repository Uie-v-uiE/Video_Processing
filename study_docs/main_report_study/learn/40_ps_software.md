## 0. 先把名词说清楚

后面每一节都建立在这张表上，所以它长，但值得先读完。

| 词 | 说人话 |
|---|---|
| **PS / PL** | Zynq-7020 一颗芯片里有两半。PS（Processing System）是两颗 Arm Cortex-A9 加上它们的 DDR 控制器、SD 控制器、UART、以太网 MAC 等固定电路；PL（Programmable Logic）是"可编程的那半"，你写 Verilog 它就是什么。本项目里像素流水线全在 PL，PS 只发号施令。 |
| **裸机（bare-metal）** | 没有操作系统，没有线程调度，没有文件系统，`main()` 就是全世界。上电后 CPU 从复位向量开始一条一条执行，堆栈多大由链接脚本定，越界没人救你。本项目的"操作系统"就是 `main.c` 里 `main()` 末尾那个 `while (1)`（`main.c:1516-1523`）：一圈六件事，轮流做，谁都不抢占谁。 |
| **BSP** | Board Support Package，厂商预先编好的驱动库 + 一份把硬件地址写成 C 宏的头（`xparameters.h`）。本项目用的是 `vitis/platform/ps7_cortexa9_0/.../bsp/` 里的 `include/` 与 `lib/libxil.a`。**关键性质：它是手工链接用的，不会因为你的 RTL 改了而自动更新。** |
| **elf / 位流（bit）** | elf 是 CPU 跑的程序镜像，bit 是 PL 里"长成什么样"。二者在 Zynq 上是**一套**：elf 里硬编码了"我往 `0x41220000` 写"，bit 里必须真有一个从设备住在那儿。见 §2.6。 |
| **OCM** | On-Chip Memory，PS 内部那 192 KB 真 RAM。本项目的链接脚本 `src/ps/lscript_ocm.ld`（文件名里的 `ocm` 就是这个）把程序摆在 OCM 而不是 DDR —— 这件事一次性解释了三四个现象，§9.4 单独算这笔账。 |
| **MMIO（内存映射外设）** | PL 里的一个 AXI 从设备被摆在某个物理地址上，CPU 对它做一次 `Xil_Out32` 就等于"把外面那 32 根线拧成这个位型"。这是 PS 与 PL 之间**唯一**的控制通道，地址表在 §3。 |
| **AXI-Lite / GP / HP** | AXI-Lite 是小带宽寄存器总线（一次搬一个 32 位字，适合控制字）。GP 是 PS 通往 PL 的通用主端口（慢、量小、控制用）；HP 是高带宽端口（PL 或 PS 的 DMA 搬像素用）。本项目控制走 GP0，像素走 HP0。 |
| **轮询 vs 中断** | 轮询 = 每圈主循环去问一句"有数据吗"。中断 = 硬件事件强行打断 CPU 去跑 handler。本项目 PS 侧**不注册任何串口中断服务程序**，命令最快也要等主循环转到下一圈才被派发。这条选择带来一个真实后果：长流程（写 256 项 γ 表、读一帧 SD）不回主循环，串口会饿住，所以那两个地方各自留了"收字节"的水口（§4.2）。 |
| **`xil_printf`** | BSP 自带的最小 printf，往 UART0 阻塞式打字。它**不是** libc 的 printf（不认 `%f` 之类的浮点转换），而且是轮询等 TX 空：115200 波特只有约 11.5 KB/s。这一句是 §5.5 那笔"回显刷屏"账的根。 |
| **数据缓存一致性** | Cortex-A9 有 D-cache。CPU 写内存时数据可能只停在缓存行里，没落到 DDR；而 DMA（SD 控制器）和 PL 的 HP0 读写的是真 DDR。两边看到的"同一块内存"可以不一致。解法是显式 `Xil_DCacheFlushRange`（把脏行写出去）与 `Xil_DCacheInvalidateRange`（丢弃缓存行、下次强制从内存读）。§8 讲本项目到底谁做哪一半。 |
| **XSA** | Vivado 导出的一个压缩包（本质是 zip）：位流 + 硬件描述（谁挂在哪个地址）+ `ps7_init.*`。Vitis 从它生成平台与 BSP；本项目的 `build/ps7_init.tcl` 就是从 `build/system.xsa` 里解出来的（`ps_jtag_boot.tcl:6-9` 写了这个回退顺序）。 |
| **FSBL** | First Stage Boot Loader。Zynq 固化在片内的 BootROM 先跑，它加载 FSBL，FSBL 初始化 DDR/时钟、配置 PL，再把应用搬进去跳过去。**本项目板上不走这条路**（§2.1）。 |
| **JTAG 三件套** | 本项目的上板方式，三条命令按序（§2.2）。它代替了 FSBL 的角色：DDR/时钟由 `ps7_init` 脚本初始化，位流由 Vivado 直烧，elf 由 xsdb 下载。 |
| **QSPI** | 板上那串 SPI Flash。走它就得写 BOOT.BIN（FSBL + bit + elf 打包），开机自动加载。**本项目从不写 QSPI** —— 这不是遗漏，是选择，理由在 §2.1。 |

讲不清的、建议再查：**MMU 的域与缓存策略**、**AXI-Lite 与 AXI-Full 的握手差别**、
**Zynq 启动模式引脚与 BOOT.BIN 镜像头**、**`asm_vectors.S` 的异常向量布局**。

## 1. 本章要回答的六个问题

如果只允许你从这一章带走六句话，是这六句：

1. **裸机里"轮到 `main()`"这件事不是理所当然的**，它前面排着 BootROM、FSBL（本项目换成 `ps7_init` 脚本）、
   `boot.S`、链接脚本四个环节，少配一个都表现为"板子没反应"而不是"编译报错"。（§2）
2. **PS 与 PL 之间只有三只 GPIO、四个 32 位字**，那就是全部的合同。合同有三处读者，改一处必须同次改完。（§3）
3. **命令层的全部难度不在"能收"，在"该拒的必须拒"**：`pipe` 只收九位，五位不写一个 bit 只回一句等价串，
   6/7/8 位一律拒 —— 因为"猜"曾经让用户以为设好的和屏上显示的是两件事。（§4）
4. **`[STAT]` 那一行不是日志，是协议**：上位机脚本按前缀逐字段解析，并且要求跑完整串命令后回到初态。
   加字段只能往后加。（§5）
5. **"PS 不参与数据面"是这个项目的卖点，而温度和 γ 曲线确实放在 PS**，这两句不矛盾：判据是
   "每秒几十万次"还是"一次上电算一遍"。（§6）
6. **片源存活这件事必须两边都有话**：PL 用 500 ms 活判据，PS 用 `ps_hold` + 100 ms 心跳，比例 1:5
   被台架钉住 —— 只改一边就一定红。（§7）

## 2. 启动：从上电到 `while (1)`，没有 FSBL 意味着什么

### 2.1 三条路线，本项目只走 JTAG，而且从不写 QSPI

**是什么**：Zynq 让程序跑起来有三条常见路线。

| 路线 | 谁初始化 DDR/时钟 | 谁配置 PL | 谁搬 elf | 本项目 |
|---|---|---|---|---|
| QSPI Flash 启动 | FSBL | FSBL（PCAP） | FSBL | **不用，也从不写** |
| SD 卡启动 | FSBL | FSBL | FSBL | 不用（SD 卡在本项目里是**素材盘**，不是启动盘） |
| JTAG 直下 | `ps7_init.tcl` 脚本 | Vivado `program_hw_devices` | xsdb `download` | **就是这条** |

**为什么选 JTAG 并且坚持不写 QSPI**（四条，都是这个项目的真实约束）：

- 迭代节奏：这个项目一天要换十几版 bit，每次走"重出 bit → 重下 elf → 立刻看屏"，
  写 Flash 一次要几秒到几十秒，而且会把上一版盖掉。
- 证据链：交付口径要的是"这块板上跑的 bit/elf 是哪一份"，JTAG 路线让板上状态**不落非易失介质**，
  断电即回空；写 QSPI 会留下一个"上电偷偷跑旧版"的暗路径。
- 风险：QSPI 里躺着一版旧固件的最坏后果，是在你以为在测新版的时候演示成功 —— 这类事故
  在 `report/log/ISSUES.md` 里有同族记录（板上只认 md5，不认文件名）。
- 第二块板（KU5P）与随之而来的那套 Python 上位机都已经从仓库删掉了，
  现网只剩一块 Zynq-7020 加一套 Node/PowerShell 工具，路线选择更不需要靠 Flash 固化。

**没有 FSBL 具体意味着三件事**，这是"会 C 但没碰过裸机"的人最容易忽略的部分：

1. **没人替你初始化 DDR 控制器**。所以 `ps_jtag_boot.tcl` 里要跑 `ps7_init` + `ps7_post_config`，
   它还自带一次 DDR 自检（往里写个魔术字再读回来打印）。
2. **有些寄存器只有 FSBL 会写**。`build/tcl/ps_jtag_boot.tcl:13-14` 那两行注释就是权威出处：
   *"正常交付流程仍然应该用 FSBL/ELF 启动：只有 FSBL 会写 SLCR 里 FPGA_FCM* 一类的寄存器
   （HP 通道缓冲），ps7_init 的 tcl 版本不含这些写入。"*
   ⇒ 直接后果：**性能类数字（带宽、丢包）在 JTAG 路线上测出来偏保守，交付口径要写清这一点**，
   而不是拿它当硬件上限。这一条是本知识库里少见的"启动方式会影响测量结论"的例子。
3. **elf 的加载地址、异常向量表、栈、MMU 开关全都归你的链接脚本与 BSP 启动文件管**，
   没有"操作系统帮你摆好"这回事。所以 §9 里那三个必须额外链接的启动文件（`asm_vectors.S`、
   `boot.S`、`translation_table.S`）不是可选装饰，漏一个的症状分别是：跑到第一条 VFP 指令陷进
   Undefined、异常表落在 0x0 一中断就飞、MMU 一直关着（进而非对齐访问一定 fault）。

### 2.2 上板三件套：顺序不可换

```
xsdb build/tcl/ps_jtag_boot.tcl        # PS 侧：复位系统 + ps7_init + DDR 自检 + con
vivado -mode batch -source build/tcl/program_pl.tcl   # PL 侧：把 bit 烧进配置链
xsdb build/tcl/ps_app_reload.tcl       # 只换 elf：dow 新镜像 + 重新 con
```

- 第一步里能读到三件重要的事：`ps7_init.tcl` 路径**三级回退**（显式传参 → 已解出的
  `build/ps7_init.tcl` → 从 `build/system.xsa` 里自动解，`ps_jtag_boot.tcl:23-26、31、42`），
  找不到就明说并退出（`:47`）；`rst -system`（`:58`）是**整机复位**，不是只复位核。
- 第二步烧 bit 选的是**芯片**而不是 `arm_dap`，所以它之后 PL 里的寄存器全回到复位值，
  而 PS 那只核刚被 `con` 起来的程序写的控制字也就作废了 —— 这就是为什么换 bit 必须重出/重下 elf。
- 第三步 `ps_app_reload.tcl` 的注释值得抄下来贴在显示器边上：它先 `targets -set -filter
  {name =~ "*Cortex-A9 MPCore #0"}`（`:21`），`catch {dow $elf}`（`:24`），再 `catch {con}`（`:27`）；
  文件末尾 `:36` 还有一句 *"上面那次 stop 只是采寄存器；不 re-con 核就停在断点上，
  串口命令发进去没人应"*。⇒ 这条脚本存在的意义就是把"重下 elf 之后忘了 con"这个真实踩过的坑
  变成不可能：它自己负责收尾。

### 2.3 `main()` 前十一行：从复位向量到我们的第一句打印

顺序是这样（每一层都是"上一层不管就没人管"）：

```
上电 → BootROM（JTAG 模式下只等命令）
     → ps7_init.tcl 把 DDR/时钟/GP0 通路配好（外部代劳）
     → xsdb download 把 elf 按程序头表搬到 OCM/DDR 上它的段地址
     → con 放行核 → BSP 的 boot.S：设各模式栈、清 BSS、搬异常向量、开需要的东西
     → 调 libc 初始化 → 调你的 main()
```

`main()` 自己开头四行（`main.c:1452-1455`）就是裸机的"标准库前置"：

1. `Xil_ExceptionInit()` —— 把异常表指针装好。**装了不等于有 handler**；本项目不注册串口/定时器中断，
   所以这张表基本是"备而不用"。
2. `Xil_DCacheEnable()` / `Xil_ICacheEnable()` —— 缓存**是开着的**。这一句直接把 §8 那笔一致性账变成
   强制义务：只要 CPU 往 DDR 写了 PL 或 DMA 要读的东西，就必须自己 flush。
3. `Xil_ExceptionEnable()` —— 打开中断总闸。
4. 然后才轮到"我们的事"：`xil_printf("\r\n[BOOT] video_pipeline PL-UDP control plane\r\n");`
   （`main.c:1457`）。这一行是整个 PS 侧**唯一的"我还活着"锚点**，串口看到它才知道前面四层都通了。

**给读 C 的人的三个提醒**（这些在裸机上第一次见都会愣一下）：

- 没有 `int main(void)` 之外的第二个入口；`return 0` 是装饰（`main.c:1524`），因为永远不会返回。
- 栈就是链接脚本划的那点。`main.c` 里所有缓冲都是 `static`（命令行的 `static char cmd_buf[CMD_BUF]`、
  γ/温度影子字、SD 那三个对齐数组），不是在调用链上摆大数组 —— 摆了就死，且**症状是 data abort 而不是"栈溢出提示"**。
- 没有 `printf`。`main.c` 里有 `#include <stdio.h>`（`:20`）但输出全走 `xil_printf`；
  它不认浮点格式，所以 γ 值要拆成整数两部分打印（`[STAT]` 那行里的 `gm=%d.%02d` 就是这么来的，
  见 `main.c` 里 `STAT` 那条 `xil_printf`）。

### 2.4 `main()` 剩下的部分干了什么（八步，全在 `main.c:1457-1523`）

| # | 干了什么 | 为什么排在这个位置 |
|---|---|---|
| 1 | `Xil_Out32(GPIO_TRI, 0)`（`main.c:1458`） | 名义上"把那只 GPIO 设成纯输出"。**它其实是空操作**：BD 里那几个 GPIO 是全输出配置，方向寄存器不可编程。留着是因为删它要确认没有任何工具依赖它，收益是零。第一次读到这行的人都会以为它在干活 —— 记下来。 |
| 2 | `ctrl_apply()`（`main.c:1459`） | 把编译期的默认影子值一次性写进 PL：阈值 80、src=0、呼吸开、双线性开、缩放档 4（=1.00x）、缝在正中、γ 关、mode=auto。这些默认值就是 `main.c:139-181` 那一排 `static` 初值，**它们是行为定义，不是装饰**。 |
| 3 | 配套自检第一条（`main.c:1461-1479`） | 往 `0x41220000` 写 `0x1FF` 读回比对，再写 `0x00780000` 读回比对，两处都过才打 `[CFG] axi_gpio_2 @41220000 ok`。为什么值得开机做，注释（`main.c:1461-1464`）写得很白：地址是硬编码的，位流里没这个从设备时**不会编译失败**，现象只是"效果命令全都没反应"，最容易让人误查一晚上 RTL。 |
| 4 | 配套自检第二条（`main.c:1481-1494`） | γ 窗口是**另一个寄存器**（`+0x08`），ch1 活着不代表 ch2 在。图案故意让 `en=0、wr=0`：**自检不许顺手把功能打开**（同一处注释）。收尾写回的是影子值 `gm_w` 而不是 0，否则屏上 `Gamma:` 那一格会被抹成 0.0 —— 这个细节在 `main.c:1487-1488` 的注释里，是"顺序挪一动就出新 bug"的现成例子。 |
| 5 | `xadc_init()`（`main.c:1498`） | 拉起 PS 侧 XADC 读片上温度。放在自动播片**之前**，因为失败一定要在开机就看得见，而不是等谁敲 `temp` 才发现"读不到"。 |
| 6 | 两条横幅（`main.c:1500-1501`） | `[BOOT] UDP RX is in PL (RGMII PHY2). PS is control + SD playback.` 与 `[BOOT] uart115200，命令表敲 help；效果控制字是 9 位（pipe 010000000）`。这两句是**开机就把分工口径说出来**，防的是"新来的人以为 PS 在收包"。 |
| 7 | 上电自动挂载 + 起播（`main.c:1506-1514`） | `autoplay` 默认 1（`main.c:606`），所以不用任何人敲命令屏幕就有画面。注释（`main.c:1503-1505`）把与仲裁的分工说清了：**自动播放只让 PS 这一路"有货"，屏幕归谁由 PL 的 `src_arb` 决定**，插着网线推流不会被打扰。 |
| 8 | `while (1)`（`main.c:1516-1523`） | 六件事轮流：`uart_poll()` 收命令 → `sd_tick()` 到点喂一帧 → `sd_recover_tick()` 卡插回自动重挂 → `ps_keepalive()` 片源心跳 → `gamma_tick()` γ 自动扫描推进 → `temp_poll()` 一秒一次温度。 |

**为什么主循环长这样而不是"中断 + 线程"**：这个系统对 PS 的全部要求是
"人在的时候答应命令、人不在的时候把卡上的帧按节拍交出去、并且永远替自己说一句话（心跳）"。
三件都是低频事，轮询就够，而线程会把 §8 的缓存一致性变成需要锁的问题。
**六件事轮流做**这个结构本身就是设计说明：任何一件里放长阻塞，其余五件全部迟到 ——
所以那三段"长流程里给自己留串口水口"的代码（§4.2）是必需的，不是洁癖。

### 2.5 为什么"elf 必须和位流一起重出"

把 `main.c` 与 BD 的关系想清楚，这句话就是定理而不是口号：

- elf 里写的是**字面量地址**（`main.c:47、71、90` 那三个宏：`0x41200000`、`0x41220000`、`+0x08`）。
- 这些地址来自 `build/tcl/build_system_axigpio.tcl:188-190` 的显式指派
  （`axi_gpio_0/S_AXI/Reg 0x41200000`、`axi_gpio_1/S_AXI/Reg 0x41210000`、
  `axi_gpio_2/S_AXI/Reg 0x41220000`），并且该脚本在 `:202` 附近把它们**逐一回读校验**过
  （`:89` 那句注释就写着"固件里的 `AXI_GPIO_CFG_BASE` 必须等于它"）。
- 于是：RTL 里加/删一个从设备、或者位序改了，**elf 侧没有任何编译期信息**。它不会报错，
  它只是写到一个没人读、或者读的人理解成别的地址上。

所以三件套的第二步之后必须重跑第三步；所以 §2.4 第 3、4 步那两条自检值得开机就做；
所以下面这句话建议直接背：**"改了 RTL 的 PS 可见接口而没重下 elf" 与 "下错 elf" 是同一个现象。**

### 2.6 怎么验证这一节（不碰硬件）

1. 读 `build/tcl/build_system_axigpio.tcl:184-209`：你会看到地址不是"由工具分配的"，
   而是"钉死 + 回读断言"。再读 `ps_jtag_boot.tcl:13-14` 那句 FSBL 的账。这两处对得上，
   §2.5 的结论就不是我编的。
2. `grep -n "Xil_ExceptionRegisterHandler\|XScuGic" src/ps/*.c` —— 数不出来，就说明"PS 侧无中断"
   这句是真的（本项目连 GPIO 的中断输出都没接，三只 GPIO 的 `C_INTERRUPT_PRESENT` 都没启用）。
3. `grep -c "xil_printf" src/ps/main.c` —— 拿这个数与 §5.5 那张"协议应答 vs 调试回显"表对，
   知道全部输出点有多少、其中被判据写着的是少数。

## 3. PS 与 PL 的三条 GPIO：各自写什么

### 3.1 地址表（本轮实测确认，可以放心记）

先纠一个旧学习稿的错误：**`0x1000_0000` 不是 GPIO，那是 DDR 里的乒乓帧 bank**。
真正的三只 AXI GPIO 是：

| 基址 | BD 里的实例 | 方向 | 固件里的宏 | 管什么 |
|---|---|---|---|---|
| `0x41200000` | `axi_gpio_0` | PS→PL（32 位全输出） | `AXI_GPIO_BASE` / `GPIO_DATA`（`main.c:47-48`） | **控制字**：阈值、片源、呼吸、发布脉冲、双线性、模式覆盖、健康 lane 选择 |
| `0x41210000` | `axi_gpio_1` | PL→PS（只读） | 固件里不定义（只在 `health_read.mjs:35` 以 `--gpio1 41210000` 出现） | **回读窗口**：链路健康 lane 的 32 位数据。RTL 侧 `system_top.v:45` 的注释就叫它"PL→PS 的健康 lane 窗口"，端口是 `system_top.v:84` 的 `.GPIO_1_tri_i(gpio1_i)` |
| `0x41220000` | `axi_gpio_2`，**双通道 × 32 bit** | PS→PL | `AXI_GPIO_CFG_BASE` / `CFG_DATA0`（`main.c:71-72`） | **+0x00 = 九位效果字 + 几何字**；RTL 侧 `system_top.v:85` 的 `.GPIO_2_tri_o(gpio_cfg1_o)` |
| `0x41220008` | 同上，第二个通道 | PS→PL | `CFG_DATA1`（`main.c:90`） | **+0x08 = γ 表写入窗口 + OSD 那两格**；RTL 侧 `system_top.v:86` 的 `.GPIO_3_tri_o(gpio_cfg2_o)`，端口注释见 `system_top.v:260` |

四行里有两个"看起来奇怪"的点，都不是错：

- **只读那只为什么算"GPIO"**：AXI GPIO IP 配成输入时 `GPIO_x_tri_i` 就是纯数据入口，
  PL 用 `assign` 把一条多路选择的结果打上去即可。于是"PS 想读 PL 的 20 多条内部快照"
  这件事**没有新增任何协议**：只要 `axi_gpio_0` 的高 5 位当通道号、这只当数据口（§3.5）。
- **`0x41220000` 与 `0x41220008` 是同一个 IP 的两个通道**，不是一个 IP 加了一个从设备。
  这也是 §2.4 里两条自检必须分开做的原因：写通了 ch1 不代表 ch2 在位流上。

⚠ 一个**真实会误判**的坑，固件里自己就标了（`main.c:199-201` 的注释）：
`CFG_DATA0` 与 `CFG_DATA1` 两个宏名只差最后一个字符，而它们的**效果完全不同**：
写错字的症状恰恰是"设了没反应"，最容易误判成"PL 坏了"。手工 `mwr` 调试时先确认自己写的偏移。

### 3.2 控制字（`0x41200000`）位表

出处是 `main.c:4-14` 的文件头（人读表）与 `ctrl_write()` 里那条拼装式（机器真相，`main.c:194-197`）。
两处一致，我把它合成一张：

| 位 | 含义 | 影子变量（`main.c` 里的 `static`） | 备注 |
|---|---|---|---|
| `[4:0]` | **保留、恒写 0** | — | V7 那五位 `effect_en` 已随 #66 从 RTL 删净。为什么还占位：整字 32 位，重排位序会把 `set_src.tcl`、`health_read.mjs` 这些按位写的工具全打乱；**空位比"重排一遍再逐个改工具"诚实**（`main.c:191-193` 原话）。 |
| `[15:8]` | 二值化阈值 | `cur_thr`（默认 80） | 钳到 0..255 |
| `[16]` | 片源选择 | `cur_src`（默认 0） | 与 `[24:23]` 的模式码是两件事，别混（§3.2 末） |
| `[17]` | 缩放"要不要呼吸" | `cur_zoom`（默认 1） | V7 时代它曾是空命令；V8-8 之后右窗缩放真的由 `[28:26]` 的档号驱动 |
| `[18]` | **发布脉冲（翻转位）** | `pub_lvl` | 翻一次 = "DDR 里这一帧写完了，请在下一个 `frame_start` 搬走" |
| `[19]` | 双线性 / 最近邻 | `cur_bilin`（默认 1） | 演示时现场 A/B 对照用 |
| `[21:20]` | 保留 | — | 定表时与 25 一起留给以后 |
| `[22]` | 模式码"翻转位" | `mode_tog_lvl` | 翻一拍 = 告诉 PL"下面那两位是新写的" |
| `[24:23]` | 片源模式覆盖 | `cur_mode_ovr` | `00` 自动 / `01` ETH / `11` SD / `10` TEST —— **屏上那三个词就是这张表**；编码不许在 PS 侧"顺手改"（`main.c:52-59`） |
| `[26]` | `gapclr` | — | 归零帧间隔统计（健康 lane 的配套） |
| `[31:27]` | 健康 lane 号 | — | 选哪条快照进 `0x41210000` |

**`[16]` 与 `[24:23]` 的关系是答辩会问的那种细节**：一个是"这一帧从哪来"的旧口，
一个是"这一路要不要钉住"的新口（四态环：自动 / ETH / SD / TEST）。
现在真正决定屏幕归属的是 PL 的 `src_arb`，PS 只能通过模式覆盖去"钉"或"放"；
`[16]` 保留是因为老工具与 LED/status 逻辑还在用它。

**一次改一个字段 = 重写整字**。四个 setter（`ctrl_set_thr`、`ctrl_set_src`、`ctrl_set_zoom`、
`ctrl_set_bilin`，都在 `main.c` 里 `ctrl_write()` 下面一段）全都写成"改影子 + 调 `ctrl_apply()`"，
不存在按位读改写。好处：PL 不会看到半更新状态。代价：**只要有一个字段被外部工具（`mwr`）改过，
下一条串口命令就会把它冲回 PS 的影子值**。排障时"我用 tcl 设的怎么没了"就是这个。

### 3.3 九位效果字与几何字：同一个 32 位字（`0x41220000`）

`ctrl_write()` 的第二笔写（`main.c:202-204`）把三样东西塞进同一个字：

| 位段 | 内容 | 影子变量 |
|---|---|---|
| `[8:0]` | **`stage_sel` 九位，一位一级**（效果链的真相） | `cur_sel`（默认 0，`main.c:164`） |
| `[28:26]` | 缩放档号（8 档，默认 4 = 1.00x） | `cur_zsel`（`main.c:171`） |
| `[29]` | 手动旗标（1 = 不呼吸、用上面那档） | `cur_zman`（`main.c:172`） |
| 其余低位 | 分割线/旋转/拟合那 19 位几何量（`GEOM_MASK` 掩着写） | `cur_split`（`main.c:139`，默认缝在正中） |

位定义（那九位各是哪一级）的**唯一出处是 `src/rtl/process/proc_pipeline.v` 的文件头**；
PS 侧只有 `SEL_NAME[9]` 这一份"用于串口回显"的名字表（`main.c:563-566`，注释就地声明了它不是定义处）。
这个"单一出处 + 旁路镜像"的处理是本章值得学的一招：**名字表可以有副本，位序表不能有第二份权威。**

RTL 侧的接线在 `system_top.v:249` 的注释里点名了"同一个字"：高位那几位（缩放档、手动旗标）
与低九位共享同一条 `snap_cross` 同步/打拍路径 —— 也就是**它们原子生效**，
不会出现"缩放换档了但效果位还是上一刻"的中间态。

⚠ 我在本轮读到一处**文件头注释已经过期**：`main.c:17` 还写着
"ch1[31:9] 与 ch2 留给 V8-3/Gamma、V8-4/分割线（现在一个字节都不写）"，
而 `ctrl_write()`（`main.c:202-204`）已经在写 `[28:26]`、`[29]` 与几何那 19 位，
ch2（`CFG_DATA1`）更是 γ 与温度在用。**行为以 `ctrl_write()` 为准**，注释是化石（§11a）。

### 3.4 γ 窗口（`0x41220008`）：为什么寄存器要设计成"边沿 + 索引 + 数据"

PL 侧那是一张 256 项 × 8 bit 的表；PS 侧只有一个 32 位字可写。于是窗口协议长这样
（`main.c` 里 `gamma_put()` / `gamma_set()` 两个函数，自检用的 `GM_DATA()` / `GM_IDX()` 宏在
`main.c:1484` 被使用）：

- 一个位放**数据**、一个位段放**索引**、一个位放使能、一个位是**写使能的边沿标志**。
- 于是"写一项"要两笔：先摆好 idx/data 与 `wr=0`，再翻 `wr`。
  **`wr` 是边沿不是电平**（γ 表在另一个钟域，靠电平会写进去一串），
  后果很实际：手工 `mwr` 一次写不进一项，必须写两次。这是 §6.4 讲 γ 曲线时唯一需要记住的硬件细节。
- 同一个字的低段还捎带两格 OSD 数据（γ 的显示值 ×10、温度的两位 BCD）——
  这就是"γ 寄存器顺便管显示"这件事的由来，也是为什么 ch2 的自检图案必须 `en=0、wr=0`。

**为什么不用 256 次 AXI 写**（也就是"每项一个寄存器"那种最直觉的做法）：
AXI-Lite 上没有地址空间预算给 256 个从寄存器，而且一次全表刷新会变成 256 次总线事务；
窗口 + 边沿只占一个字，代价是"手工调试要写两次"。**这是典型的"给人方便 vs 给硬件方便"的取舍，
本项目选了后者，并且把坑写进注释。**

### 3.5 那只只读 GPIO：读 PL 内部状态的正确姿势

需求：PL 里有链路/丢帧/延迟等十几条计数器与快照，PS 完全不参与数据面，只能"问"。
做法（不新增 AXI 从设备）：

1. 用 `axi_gpio_0[31:27]` 当**通道选择**（lane 号），RTL 侧 `system_top.v:192` 附近的注释
   就是在说"再从新加的 `GPIO_1`（输入）读那一条 32 bit"；
2. lane 号 → 具体某条快照，在 `src/rtl/top/pl_video_top.v` 里 `assign gpio1_i = ...`（本轮不引行号）；
3. PS（或脚本）读 `0x41210000` 拿那一条。

脚本 `src/host/health_read.mjs` 把这套纪律实现得很干净，三件事值得抄进自己的习惯里：

- **读回原值、只改那 5 位、读完写回去**（它的文件头注释就写了这三步）—— 因为控制字是共享的，
  乱写一位就把别人的功能拧动了。
- **非法 lane 号硬件直接回 `0xDEADBEEF`** —— 一眼看得出是"号写错了"而不是"读不到"。
- **每条单调计数器读两遍，第二遍变小就重读** —— 因为快照是别处打的拍，
  你可能正好采在刷新那一瞬。**读数要自带"我读到的是不是一次完整快照"的证据。**

### 3.6 双侧对照：PS 写哪一段 ↔ PL 谁在读

**这一段的右边一列我故意只给端口名与文件名**，因为 `system_top.v` 的行号本轮只读到 45/84/85/86/192/249/260
那几处，其它行不引。方法不变：从 `ctrl_write()` 里每一项出发，在 `src/rtl/top/system_top.v` 搜
`gpio_o[` / `gpio_cfg1_o[` / `gpio_cfg2_o[`，就能找到那个端口连去了哪。

| PS 侧（`ctrl_write()` 的项） | PL 侧端口 | 干什么的模块 |
|---|---|---|
| `cur_thr << 8` | `pl_video_top` 的 `.threshold(gpio_o[15:8])` | 效果链里的二值化级 |
| `cur_src << 16` | `.src_sel(gpio_o[16])` | 片源 mux（旧口） |
| `cur_zoom << 17` | `.zoom_en(gpio_o[17])` | 右窗缩放呼吸使能 |
| `pub_lvl << 18` | `.ps_publish(gpio_o[18])` | 一次翻转 = 请求把 DDR 那帧搬上屏一次；也是 §7 活判据的"饲料" |
| `cur_bilin << 19` | `.bilin_en_axi(gpio_o[19])` | 插值方式 A/B |
| `mode_tog<<22`、`mode_ovr<<23` | `.mode_ovr_tog` / `.mode_ovr` | 钉/放片源（四态环） |
| `gapclr<<26`、`lane<<27` | 帧间隔统计归零、lane mux | 与 `0x41210000` 配套 |
| `cur_sel & 0x1FF` | `gpio_cfg1_o[8:0]` → `proc_pipeline` 的 `stage_sel` | **九位一位一级**（唯一真相） |
| `cur_zsel<<26`、`cur_zman<<29`、`cur_split & GEOM_MASK` | `gpio_cfg1_o` 高位 | 缩放档/手动、分割线、旋转、拟合，同一字同一拍生效 |
| `gm_w`（γ 窗口整字） | `gpio_cfg2_o` | γ 表 idx/data/wr/en + OSD 的 `Gamma:`、`Temp:` 两格 |

## 4. 命令层：V8 的"动词 + 空格 + 参数"，怎么做到"该拒的必须拒"

### 4.1 一条命令的完整旅程

`th 120`（阈值改 120）从键盘到 PL 里某个模块，八步；每一步都有自己的失败方式。
**"命令没反应"这句笼统话在八步上指的是八件不同的事** —— 这就是为什么要拆开讲。

| 步 | 代码在哪 | 干了什么 | 这一步坏了长什么样 |
|---|---|---|---|
| ① 收字节 | `main.c` 的 `uart_poll()`（函数起于 `:1376`） | `XUartPs_IsReceiveData` + `RecvByte` 轮询取一个字节 | 一个字节都没有 = COM 口/波特率/线；这是唯一"不是固件的锅"的一步 |
| ② 本地回显 | 同上，收一个字节的循环体里 | `XUartPs_SendByte` 把你敲的字原样发回去 | **看不见自己敲的字 ≠ 没收到**，只是没回显。注释就地说明了这条，因为每个人都会先误判它 |
| ③ 行长守卫 | `CMD_BUF`（缓冲大小）+ `cmd_toolong` | 超长只报**一条** `[CMD!]`，不刷屏 | 缓冲区小的时候是"尾巴被啃掉还当正常行派发" —— 这就是 `CMD_BUF` 从旧值 48 涨到 128 的原因：要装得下 `gamma auto 1.0 3.0 0.2 2000` 这种多参数命令 |
| ④ 残包丢弃 | `main.c` 的 `rx_fill()`（`:1417` 起） | 半行搁置超过 `RX_IDLE_MS` 就丢掉并**明说** | 不丢的话，你下一条命令会和那半行拼成一句谁都没敲过的话（这是最容易让人以为"板子中邪"的现象） |
| ⑤ 逐字节 → 整行 | `uart_poll()` | 一次攒下多行（粘贴/脚本连发），逐条切出来派发 | 只处理一行的实现会在脚本连发时丢命令 |
| ⑥ 切 token | `main.c` 的 `tokenize()`（`:645`）+ `ci_eq`（`:608`）/ `ci_pre`（`:618`） | 按空白切，最多 `T_MAX` 个；大小写不敏感 | 老实现用前缀匹配，连 `THE` 都被当成 `TH`；现在靠 `strict_int` 兜（`:629`） |
| ⑦ 派发 | `dispatch()`（`main.c:864-1347`） | 一条按优先级排列的 `if` 链；**全不中时 `return -1`**（`:1346`） | 由调用方打成 `[CMD] 不认: …` + 整段 help。返回 -1 而不是"默认分支什么都不做"是刻意的 |
| ⑧ 写寄存器 | `ctrl_write()`（`main.c:188-206`） | 两笔 `Xil_Out32`：`GPIO_DATA` 与 `CFG_DATA0`（`main.c:198、202-204`） | "设了没反应"最容易误判成 PL 坏了，实际常是写错字（§3.1）或地址不配套（§2.5） |
| ⑨ PL 侧有人读 | `system_top.v:84-86` 那三路端口 + `pl_video_top` 的端口连接 | 32 位逐位接到各模块 | **写了没人读 = 命令答应了但硬件没动**，比报"待接"更糟（§4.6） |

`th 120` 的具体轨迹：`dispatch()` 命中 `ci_pre(tk[0], "TH")`（`main.c:885`）→
取参数那句 `(nt >= 2) ? tk[1] : tk[0] + 2`（`main.c:888`，新写法取下一个 token，老写法 `TH80` 从第 3 个字符起）→
`strict_int` 不通过就 `[TH] 要跟十进制 0..255`（`:889`）→ 钳位（`:890-891`）→
`ctrl_set_thr()` 改影子 + `ctrl_apply()`（`:470` 起）→ `ctrl_write()` 把 `cur_thr << 8` 拼进整字 →
写 `0x41200000` → PL 的 `gpio_o[15:8]` → 二值化判决。

### 4.2 为什么解析要拆成"只收"与"派发"两半（本项目一个真实的设计决定）

`gamma_set()` 一次要把 256 项逐个写进窗口，每项两笔写、中间还有一点点延时，**整段时间不回主循环**。
而 115200 波特下 Zynq 的 UART RX FIFO 只有 16 字节 —— 约 1.4 ms 的量。
SD 那条路同理：一帧 300 KB 要分几段读，每段之间不回头转主循环。

于是：

- `rx_fill()`（`main.c:1417`）**只搬字节进缓冲，绝不派发**；
- `uart_keepalive()`（`main.c:1443`）是给 `sd_play.c` 用的同名出口（`extern` 声明在 `sd_play.c` 里），
  SD 的分段读之间调它；
- 派发只留在主循环的 `uart_poll()`。

**为什么不直接在长流程里调 `uart_poll()`**：那会重入 `dispatch()`。
重入的裸机函数会改同一批影子变量、会在打印中间再打一段，
症状是"回显串行 + 状态错乱"，比丢几个字符难得多。**宁可分两半，也不要重入。**
这是"没有 OS 就没有递归保护"的具体体现。

### 4.3 长度判据：`pipe` 只收九位，五位一个 bit 都不写

这是"该拒的必须拒"最好的教材，因为它有三种长度三种处置。

`parse_bits()`（`main.c:544-558`）逐字符只接受 `'0'/'1'`，遇 `CR/LF/空格` 停，
**最左字符 = bit0**；数到第 10 个直接 `return -1`；末尾判
`if (n != 5 && n != 9) return -1;`（`:555`）。⇒ 它**故意**还数得出 5，理由写在 `:551` 的注释里：
"五位仍然数得出来，好把等价串报给他"。

`apply_pipe_bits()`（`main.c:457-468`）分三种：

| 输入 | 处置 | 为什么 |
|---|---|---|
| **9 位** | `ctrl_set_sel()` 真写，返回"已生效" | 九位是唯一口径 |
| **5 位** | **一个位都不写**，只把等价的九位算出来印给他看，返回 0 | 五位是 V7 老位序（`invert` 在 bit4、`binary` 在 bit1，与新表不同）。老代码"两种都收"，代价是**同一个串有两种答案** |
| **6/7/8 位** | 一律拒，并说明"过去被当 9 位补零，屏上对不上"（`:877-879` 的 `[PIPE]` 消息） | 补零 = 猜。猜错时用户以为设好的与屏上显示的是两件事 |

**"不猜"的三条纪律**（可以照抄到自己项目里）：

1. 猜出来的意思**只在一种情况下对**，拒掉的意思**永远清楚**。
2. 拒绝的同时给出**可照抄的正确写法**：`legacy_to_sel()`（`main.c:441-448`）把五位翻译成九位，
   然后 `for (i = 0; i <= 8; ++i)` **从 bit0 往后**打出来（`:465`）。
   打印方向是硬约束：反向打给的是一串镜像，照着敲会开出完全不同的几级 ——
   `main.c:453-455` 就地记了这条，并说 `src/host/pipe_len_check.mjs` 的 B 段就是拿它当 FAIL 判的。
3. 判据脚本与固件**互为反例源**（同一条约定，`uart_cmd_check.mjs` 里另写一份五→九映射）。

裸五位串还有第二条入口：`dispatch()` 的第一件事就是
`nb = parse_bits(tk[0], &en); if (nt == 1 && nb > 0) { … }`（`main.c:870-871`）——
即使你不写 `pipe`，光秃秃一串也走同一个 `apply_pipe_bits()`，**行为一致**。

### 4.4 `pipe show` 与"屏上那一格不是这串 0/1"（答辩必问点）

`print_sel_names()`（`main.c:568-578`）打两行：

- 第一行 `[PIPE] sel=%03x 生效: gray sharpen …` —— 把人话给你；
- 第二行直接解释那五格：**"屏上那五是每一级选了第几个算法（0=无，1/2=该级的两个算法，
  3=两位都设了）⇒ 与命令串不是同一个写法，看这一行的名字。"**

两张表的差别一句话说清：

| | 命令/寄存器的九位 | 屏上 `Pipe:` 那一格 |
|---|---|---|
| 长度 | 9 | 5（每一级一位） |
| 每位的值域 | 0/1 | **0..3** |
| 含义 | 这一级开不开 | 这一级**选了第几个算法** |
| 谁生成 | PS（`cur_sel`） | PL（OSD 自己按每级的选择信号排出来） |

⇒ **拿命令串去对屏上那五位，必然对不上**，而且对不上的方式让人怀疑人生
（`pipe 000100000` 屏上第一位不是 0）。这不是 bug，是两个不同抽象层：
九位是"使能"，屏上五位是"每级的算法序号"。固件每次都用第二行主动说明，
`cmd_help()` 里也印了同一句（`main.c:1356-1357`）。**同一个知识点在两处冗余出现，
因为这是被问次数最多的一个。**

### 4.5 老写法兼容的实现纪律：偏移取尾串，不按下标取字符

新语法（`th 80`）与老写法（`TH80`）共用一条出口，取参数那一句的写法是
`(nt >= 2) ? tk[1] : tk[0] + <动词长度>`。本轮读到四条：`TH` 用 `+2`（`main.c:888`）、
`SRC` 用 `+3`（`:900`）、`ZOOM` 用 `+4`（`:911`）、`AUTOPLAY` 用 `+8`（`:1317`，注释就写着"AUTOPLAY 是 8 个字母"）。

**为什么按偏移而不是"取最后一个字符"**：`main.c:896-899` 那段注释给了答案 ——
老代码本来是"两个 `strncmp` 分支"，重构成取尾字符时**数错过一位**（`BILIN1` 那次），
于是改成"整串交给 `strict_int`"。教训值得抄下来：
**兼容层的正确性不靠细心，靠把易错操作收进一个函数。**

### 4.6 "语法已收、硬件待接"也要出声：`not_wired()`

`not_wired()`（`main.c:661`）打印的是三件事：语法我收了、硬件现在没接、缺哪一步。
现存的例子是 `osd on|off`，`cmd_help()` 末尾那半行"语法已收/硬件待接"就是它的目录（`main.c:1358`）。

**这里有一处特别值钱的删除记录**：`main.c` 里 `dispatch()` 的 `bilin` 分支之后、
`rot` 分支之前，注释说明过"这里原本也放了一条 bilin 的待接分支，撤掉了"，理由有两条 ——
①它永远不会被执行（上面 `ci_pre(tk[0], "BILIN")` 前缀匹配先到先赢），
②它说的是错的活。结论就是本节标题那句：
**"命令答应了但硬件没动" 比 "报待接" 更糟。**
把这一条当成本章对"接口诚实性"的第一原则，§4.7 会看到它如何影响 `zoom` 的设计。

### 4.7 有一处**故意保留**的语义重叠：`zoom 1`

`zoom` 有三种意思：开关呼吸（`on|off`）、指定倍率（`<数>`）、拟合模式（`fit 0|1`）。
而 `zoom 1` / `zoom 0` **沿用 V7 的开关语义**（`ZOOM1`=开呼吸），所以"回到 1.00 倍"必须写
`zoom 1.0`（带小数点才走倍率那条路）。这条在 `main.c:907-910` 的注释里明写，
并且**打印在拒绝消息里**，因为 r53 第一次跑串口电池就是拿 `zoom 1` 当"回到 1.0x"用，
结果把呼吸又打开了 —— 现场表现是画面在缓缓缩放，而命令表的作者以为自己写错了脚本。

取舍说明：干净的做法是让 `zoom 1` 表示 1.0 倍、`zoom on` 表示呼吸，
但那会让所有老脚本静默改变意思。**与其静默改变，不如把这个坑摆在明面上并每次提醒。**

### 4.8 现在真实存在的动词（以 `cmd_help()` 为准，不是以本文档为准）

`cmd_help()` 在 `main.c:1349-1370`，它自己打印的口径是：

### 4.9 怎么验证解析器（半条命令都不用硬件）

1. 读 `dispatch()`（`main.c:864-1347`）本身，回答三个问题：哪几条分支会在**参数不合法时直接 return**
   而不写寄存器？裸五位那条（`:870-871`）走的是不是同一个 `apply_pipe_bits()`？
   `return -1` 有几处？（`main.c` 的 `dispatch()` 里就一处，在末尾 `:1346`。）
2. 跑 `node src/host/pipe_len_check.mjs`：钉的是"只收九位"这条判据与**打印方向**（§4.3）。
3. 上板时（本轮不做）：`pipe 00111` 之后 `stat` 的 `sel=` **不许变**，
   而 `pipe` 回声里那串九个字符照抄下去再敲一次，`sel=` 才会动。

## 5. `[STAT]` 那一行是契约，不是日志

### 5.1 它长什么样，谁在逐字段读它

固件里 `STAT` 那条分支（`main.c:1324-1344`）打一行：

```
[STAT] ctrl thr=80 src=0 zoom=1 bilin=1 zsel=4 zman=0 pub=0 sd=1 frames=1180 playing=1
       sel=008 gm=1.80 (PL owns UDP datapath) mode=0 geom=00020000
```

（字段名与顺序是上面代码里那条 `xil_printf` 的格式串；`gm=` 用 `%d.%02d` 拆整数与两位小数，
因为 `xil_printf` 不认浮点转换。）

读它的是 `src/host/uart_cmd_check.mjs`（396 行）：它按 **前缀**解析
（`[STAT] ctrl`、`thr=`、`src=`…），并且整串命令跑完后要求 **`STAT` 回到跑之前的值**。
⇒ 这行文本的性质和一份 API 的 JSON schema 一样。改它 = 改协议。

### 5.2 为什么"只能往后加"

`main.c:1325-1328` 的注释就地声明：*"字段顺序不许动：串口电池与 `uart_cmd_check.mjs` 都按
`[STAT] ctrl thr=…` 的前缀解析，后加的 `sel` / `mode` / `geom` 只能往后放。"*

按前缀解析的实现只要"字段名 + 值"就能工作，看起来对**顺序**不该敏感。它仍然敏感，原因很朴素：
判据里写的是**整行正则**（为了同时断言"这行只有这些字段、没有多出来的野值"），
于是插入一个字段就等于让后面所有捕获组错位。
**这是判据实现反过来塑造被测代码形状的典型例子**，值得在答辩时主动说：
我们不是"想到哪写到哪地加字段"，加字段的姿势被尺子的形状规定了。

### 5.3 `geom=` 为什么必须存在（一次"元组看不见某些位"的补账）

`main.c:1329-1333` 的注释是这一节最该读的东西，我把它的意思复述成三条：

1. 串口电池的核心判据是"跑完一串命令必须回到初态"。
2. 以前那个元组里**看不见**几何这 19 位 ⇒ 电池可以把板子留在"自动旋转还开着、缩放还在 fit、
   缝贴着右边缘"而**判绿**。
3. 于是补一个整字回显 `geom=`。V8-8 当时给 `zsel`/`zman` 补过同一课，这是第二遍。

⇒ 判据的强度不取决于你发了多少命令，取决于**回显里看得见多少状态**。
看不见的那部分，就是你迟早会在演示现场撞上的那部分。

顺带一处**注释与代码不一致**（本轮实测）：那段注释说"末尾再挂一个 `geom=%05x`"，
而代码里的格式串是 `geom=%08x`（`main.c:1336`）。值本身没问题（`GEOM_MASK` 是 19 位，
八位十六进制装得下且判据按前缀取），**过期的是注释**。这正好是本章开头那条写法纪律的理由。

### 5.4 改一行回声要同次改完哪些地方

这是一份"改协议的影响清单"，比上一小节更实用：

| 你要动的东西 | 必须同次改完 |
|---|---|
| `[STAT]` 的任何字段 | `src/host/uart_cmd_check.mjs` 的解析与"初态=末态"比较；`report/COMMANDS.md` 里抄着这行的那一处；`src/host/demo_cmds.mjs` 若把 `stat` 当基线用 |
| 任何命令的回声文本 | `uart_cmd_check.mjs` 里对应那条 `EXPECT` 正则；若它出现在 `report/DEMO_SCRIPT.md` 的代码块里，还要过 `demo_cmds.mjs --check` |
| 五→九位映射 | 固件 `legacy_to_sel()` + 判据器里那份**独立写的**映射（互为反例源）+ `pipe_len_check.mjs` |
| 温度显示编码 | 固件 `temp_code_of()` + `src/host/temp_formula_check.mjs` 里另写的编码器 |
| 心跳节拍/超时 | `main.c` 的 `PS_HB_MS` + PL 侧 `PS_SRC_TIMEOUT_MS` + 台架 `sim/tb_v102_src_life.v`（§7） |

`uart_cmd_check.mjs` 还有两个机制值得单独学：

- **`--align` 对位哨兵**：`EXPECT[]` 数组与电池文件 `board/cmd_battery_v81.txt` 必须**同序同数**，
  它专门防"中途插一条命令，让后面每条都错一位"。这条**不碰串口**，几秒跑完。
- **反例（`!` 前缀）**：判"该拒的必须真拒，**而且不许写寄存器**"。
  ⇒ 所以反例走的是字面量包含而非正则，这一点脚本自己的注释里承认过（有几条一直在空跑）。
  对读者的启示：**判据脚本本身也是会被判的对象**，它同样有化石与已知不足。

### 5.5 调试性回显 vs 协议应答：一个可执行的判别方法

`main.c` 里含 `xil_printf` 的行有上百，但绝大多数**是协议的一部分**。
判别方法不需要读判据脚本的注释，只要一条命令：

```
grep -o "\[CTRL\]\|\[PIPE\]\|\[STAT\]\|\[GAMMA\]\|\[TEMP\]" src/host/uart_cmd_check.mjs | sort | uniq -c
```

某条前缀在 `uart_cmd_check.mjs` 里出现次数 = 0，它才**可能**是可裁的调试回声。

两类输出的定义：

- **协议应答**：`[CMD]`、`[PIPE]`、`[CTRL]`、`[STAT]`、`[TEMP]`、`[GAMMA]`、`[SD]`、`[SRC]`、
  `[SPLIT]`、`[ZOOM]`、`[ROT]`、`[BILIN]` 的正常应答，加上告警族 `[CMD!]`、`[CFG!]`、`[GAMMA!]`、
  `[TEMP!]`、`[SDRD!]` —— **删了就判红**。
- **调试性回显**：当年为了"看得见它动了没有"加的，今天信息已被协议应答覆盖。
  典型是"每条改状态的命令都重打一遍整字"，与 `stat` 一行覆盖同一批数；
  以及"不认某词之后又把整段 help 重打一遍"（拒绝是协议，附送 help 是便利）。

**为什么这一节的存在本身有价值**：裸机固件的串口输出是**有限资源**。
`ctrl_write()` 上面那段注释（`main.c:184-187`）算过这笔账：如果每帧一次的发布脉冲走"写 + 打印"，
30 fps 回放每秒要往串口推约 2 KB，而 115200 只有 11.5 KB/s，`xil_printf` 还是阻塞实现 ——
板上实测"播放 10 秒收回 28549 字节全是 `[CTRL]` 行"。
于是有了这一章反复出现的一个函数拆分：**`ctrl_write()` 只写不打字（每帧调用），
`ctrl_apply()` = 写 + 打字（人在改状态时调用）**。
`ps_publish()`（`main.c:221-230`）走的是前者，注释就写着"每帧都调，所以不出声"。

⇒ 这不是风格洁癖：**输出走错了函数，回放就会卡。**

## 6. 为什么"PS 不参与数据面"是卖点，而温度与 γ 又确实在 PS

### 6.1 判据表（先给尺子）

| 判据 | 交给 PS（Arm） | 留给 PL |
|---|---|---|
| 每秒要做几十万次的事 | 不能 | **必须** |
| 每像素一次的算术（乘、加、比较、查表） | 不能 | 必须 |
| 与像素时钟同拍的时序（消隐窗口、行首） | 追不上 | 必须 |
| 一次上电只算一遍的表/常数 | 能 | 不必 |
| 要文件系统 / 随机访问 / 人话错误 | **能** | 不能 |
| 一秒钟一次的采样与显示 | 能 | 浪费 |

### 6.2 这条切分是**三代演化的结论**，不是嘴上说的

`report/PS_VS_PL.md` 里那张对照表是本仓库最该被读第二遍的文件之一：
v1 用的是 **PS 侧 GEM0 + lwIP**（软件中断 + memcpy 收包），v2/v3 换成 **PL 硬件解析 RGMII**，
PS 的角色从"收包 + 控制"缩到"仅控制"。为什么换，那篇列了七行账，最硬的两条是：

- **延迟**：中断 + 协议栈是毫秒级抖动，流水线是确定的几拍；
- **CPU 占用**：约 220 包/帧 × 30 fps 的软件收包 vs 接近 0。

而"PS 不参与数据面"这件事在代码里是**硬证据级**的可查，不必信任何人（包括我）：

1. `main.c` 的 include 列表（`:20-35`）里没有任何网络协议栈 —— 只有
   `xparameters / xil_printf / xil_io / xil_cache / xil_exception / xuartps / xadcps / sleep / xiltimer / sd_play.h`
   加上标准库的 `stdio / string / stdlib / math`。
   **没有 socket、没有 lwIP、没有 XEmac，一次网络调用都没有。**
2. 开机横幅自己声明：`[BOOT] UDP RX is in PL (RGMII PHY2). PS is control + SD playback.`（`main.c:1500`）。
3. `ps_publish()` 只是翻一个位（`main.c:221-230`），**它连一字节像素都不搬**。
4. SD 回放那一路的边界写在 `sd_play.h` 的文件头：**PS 全程不做 memcpy**，
   SD 控制器的 DMA 直接把卡上的帧写进 PL 要读的那块 DDR，PS 只发一次"发布"脉冲。
   ⇒ 省掉一帧 300 KB 的拷贝，也不需要第二块 DDR 做双缓冲。

### 6.3 那低频的事为什么给 PS：三行算式

- **γ 表**：`gamma_curve()`（`main.c:355`）对 256 个索引各算一次 `pow(i/255, 1/γ)`。
  换一次 γ 值才重算一遍。PL 要干同等的事，得加一条除法器链 + 一个 256 拍的状态机 +
  一张只读表；而 PS 这边**已经有的 `pow` 只值几行 C**。
  这正是判据表第三行"一次上电只算一遍"。
- **温度**：`temp_poll()`（`main.c:782`）一秒一次；`temp_mc_of()`（`main.c:730`）
  把 XADC 原始字换成毫摄氏度，用的是**乘加移位**而不是除法
  （`(raw * 503975) >> 16` 再减 273150，`main.c:731` 那条电压式子同理）。
  一秒一次的换算在 Arm 上是零成本。
- **文件系统**：SD 卡的 FAT32 只读解析（`sd_play.c`）根本不可能在 PL 做 ——
  簇链跳转是**数据依赖的控制流**，硬件实现它等于写一台 CPU。

**同一件事的反面也要看**：γ 曲线的**扫描**（`gamma auto lo hi step ms`）也放在 PS，
理由不是"PS 算得快"，而是 `gamma_tick()`（`main.c:326`）本来就是主循环里
"到点改一下影子值、再刷一次表"的那段代码。
`main.c` 里 γ 那一段的两条注释给了完整理由：
①**算错的凭据与接错的凭据要分开**（PS 算错 vs PL 接线错，混在一处就没法定位）；
②PL 那边只有一张表和一个写口，没有第二条曲线发生器，在 PS 扫 = **零新增硬件、零时序风险**。
⇒ 判据的完整表述是：**在 100/50 MHz 域里塞算术之前，先问一句值不值。**

### 6.4 γ 表怎么从 C 落到 PL 的 256 项里

流程（`gamma_set()`，`main.c:374` 起；单项写是 `gamma_put()`，`main.c:345`）：

1. 关掉使能（避免半新半旧的表被采样）→ 2. 循环 256 次：算 `gamma_curve()`、
   摆 idx/data、翻 `wr` 边沿、`usleep` 一点 → 3. 打开使能 →
   4. 把 γ×10 放进显示位段（屏上 `Gamma:` 那一格）。

三条硬约束来自 §3.4：`wr` 是**边沿**、整个窗口在 `0x41220008`、
中途不回主循环所以要 `rx_fill()`（§4.2）。
还有一个"顺序"细节值得记：**扫描过程中每一步都会重刷整表**，所以
`gamma_tick()` 与 `gamma_set()` 共用同一个 `gm_w` 影子值 —— 任何一处直接 `Xil_Out32(CFG_DATA1, …)`
绕过影子，下一次刷新就会把你刚设的东西抹掉。（§2.4 第 4 步那个自检收尾为什么写回 `gm_w`
而不是 0，是同一课的第二个例子：**PS 与硬件之间不许有两套真相，包括自检代码。**）

### 6.5 温度：XADC → BCD → OSD 第五行，为什么除法在 PS

链路：`xadc_init()`（`main.c:733`）解锁并使能 PS 侧 XADC →
`temp_poll()` 每圈问时间、到一秒取两路（片上温度 + VCCINT）→
`temp_mc_of()` 换毫摄氏度 → `temp_code_of()`（`main.c:762`）编成**两位十进制 BCD** →
`temp_disp_write()`（`main.c:774`）把那个字节塞进 γ 窗口的最低 8 位 →
PL 的 OSD 逐半字节画字。

**为什么不在 OSD 里做除法**（这是本项目最好讲的"时序换代码"案例）：
OSD 那五行字符是一整块组合逻辑，而 `u_pipe/xd_reg → u_osd/g_reg` 这一组**正是全设计 WNS 最差的路径之一**。
在屏上再加一次 `/100` 与 `/10`，就是往最差的链上再加几级。
于是换算在 100 MHz 的 PS 侧做完，PL 只查表画字（同一件事的先例是 OSD 的 Latency 那一格：
换算在 axi 域做完再跨域）。**代价也说清楚**：量程只剩 0..99 °C，
装不下（或半字节 >9 这种非法码）PL 就画 `--`。这不是缺陷，是**约定的空值**。

两个"诚实读数"细节：

- VCCINT 一起读，是"这一次转换像不像真的"的旁证（温度在合理区间但电压离谱 = 采样不可信）。
- 阈值告警：`temp_th_deg` 默认 85 °C（`main.c:724`），`temp th <°C>` 可改；
  这是**唯一**由温度驱动的 PS 行为 —— 它不联动任何 PL 的降速/关屏。
  别在文档里承诺"超温保护"，那事没做。

### 6.6 PS 也碰帧内存，但那不叫数据面

两条路会让 PS 写 DDR：`fill` 命令（`cmd_fill()`，`main.c:668`）画一张诊断图；
SD 回放的**地址**归 PS 配（DMA 搬，CPU 不搬）。要点三条：

1. PS 片源的帧落在 DDR 的**第三个 bank** `0x1010_0000`（`main.c:45`）。
   以前是 `0x1000_0000`，与 ETH 乒乓双 bank 的第 0 块重叠 ⇒ 屏幕上"两个片源打架、闪"
   （板级实测 2026-09-24，账记在 `main.c:40-44`）。
   关键洞察：**仲裁只管谁用那台搬运机，管不到谁写 DDR**（SD 的 DMA 走 PS 自己的 HP0，不经过 PL），
   所以只能靠地址分开。
2. 这个数必须**同时**等于 `pl_video_top.v` 的 `PS_BASE_ADDR` 与 `system_top.v` 的 `PS_DDR_BASE`。
   三个数各说一次就是等着错 —— 这是"同一个常量在三个语言里存在"的经典风险，
   没有共享头文件机制可用时，只能靠注释点名 + 上板现象。
3. 屏上是否看得见 PS 片源，取决于 PL 的仲裁；PS 能做的只有"钉/放"（`ctrl_publish_mode()`，
   `main.c:487`）。⇒ 所以 `src 1`（钉 ETH）而当下没推流时，屏幕**冻在最后一帧**并写 `SRC:ETH*`。
   这不是故障，是"锁"的定义 —— 想知道此刻为什么归某一路，读 `stat` 的 `mode=`。

## 7. 心跳与片源存活判据：为什么要两边都有

### 7.1 问题原型：粘滞位让"曾经有"与"现在有"同形

早期 PL 侧判断"这一路有没有片源"用的是两个**只置位、从不清零**的粘滞位
（"自配置以来收过任何一个包"、"挂上过一次卡"）。后果是 #94 那组症状：
播放中拔 SD 卡，屏幕**永久卡在最后一帧**，卡插回也不恢复；
最阴的一条是 **`Src:` 那一格还写着 SD、`FPS:` 还在 30 —— 画面静止而两处读数都说正常**。
（`report/log/ISSUES.md` 的 #94 条目里那三条症状按顺序读，是"粘滞位"这个反模式最好的教材。）

### 7.2 现在的方案：PL 用活判据，PS 用心跳

- **PL 侧**：`src/rtl/util/src_life.v` 的看门狗超时 500 ms（顶层 `pl_video_top.v` 里的
  `PS_SRC_TIMEOUT_MS = 500` 例化它），500 ms 内没见到发布脉冲就当 PS 这一路没片源，
  画面交回仲裁（有网线回网络，没有回测试图卡）。
  它吃的是**已有的发布握手**给出的 `ps_pub` 脉冲 —— 零新增异步配对，这是它能被塞进去的原因。
- **PS 侧**：`ps_hold`（`main.c:181`）+ `PS_HB_MS = 100`（`main.c:239`）+ `ps_keepalive()`
  （`main.c:240-248`）：**每 100 ms 把同一帧重发一次**。
  DDR 里那张画没动，PL 重新搬一遍，屏幕上看不出差别，也不需要任何新的 DDR 读量。

**为什么 PS 必须"说话"**（这一句是这一节的要点）：
`stop` / `play 0` / `frame N` / `fill` 之后 PS 不再每帧发布，而**屏上那张画是要留住的**。
PL 现在按"最近有没有收到发布"判片源存在 ⇒ 没人替 PS 说话就会落图卡 ——
那是拿掉一个红（拔卡冻帧）换来一个新红（一切暂停就丢画面），不划算。

`main.c:232-238` 那段注释还钉了另一半：**100 ms 与 500 ms 是同一件事的两半，比例 1:5
由台架 `sim/tb_v102_src_life.v` 的 S12 用例钉住**
（"改这里就要改那里，两边各自成立不等于合起来成立"）。
⇒ 这是本章最该被复述的一条工程纪律：**跨模块的时间常数要有第三个地方（测试）把它绑在一起。**
判据器 `src/host/ps_hb_check.mjs` 是第四处：它不编译、不上板，
钉的就是"节拍 / 超时 / 调用点 / 恢复键这几处源码之间的约定还成立"，并带变异对照。

### 7.3 谁有权停心跳

只有**真的读卡失败**才停：`sd_play.c` 里读帧失败的统一收口 `card_gone()` → 调 `ps_source_lost()`
（`main.c:252-257`），它清 `ps_hold` 并打一句
`[SRC] PS 停心跳：片源不可信（拔卡 / 读错），画面交回仲裁`。

被**拒绝**的命令（帧号越界、还没挂载、`src 1` 而当下没流）**不停**心跳。
这条区分不是洁癖，是两种语义：**用户主动要的静止 = 还在持有画面；硬件报错 = 不再持有。**
"冻在最后一帧"在前者是**语义**，在后者是**故障**，PL 与 PS 都必须用同一个标准，
否则就会出现"屏幕看起来对但 `stat` 说不持有"这种无法排障的组合。

### 7.4 拔线 / 拔卡 / 插回分别看见什么

| 动作 | 走哪条路 | 串口 | 屏 |
|---|---|---|---|
| 拔网线 | PL 侧 ETH 链路监控（毫秒级 `LIVE_MS`）+ 仲裁第二级迟滞 | `[LINK]` 一类 | 立刻从 ETH 落到 SD/PS，OSD 的 `Src:` 跟着变 |
| 播放中拔 SD 卡 | 下一次读帧重试两次都失败 → `card_gone()` → `ps_source_lost()` | `[SDRD!] lba=… clus=…`、`[SD] playback stopped at frame N: …`、`[SRC] PS 停心跳…` | ≤500 ms 落到该落的那一路 |
| 卡插回 | 主循环 `sd_recover_tick()`：**曾经挂载过、且丢卡那一刻正在播** ⇒ 每 2 s 试一次重挂，最多 30 次 | 成功/失败/到限三种播报各不相同（能数出试了几次） | 重挂成功后自己接回回放，`ps_publish()` 每帧把 `ps_hold` 拉回 1 |
| 手工重挂 | `sd remount` | `[SD] remount ok` + 摘要，或失败原因 | —— |

两条"为什么不那样"的账：

- **为什么恢复限 2 s、每拍最多试一次**：`sd_recover_tick()` 跑在主循环里，而主循环**同时是串口的服务循环**；
  卡不在位时一次初始化要等 CMD 超时，连着跑几十次等于把控制台闷死。
  ⇒ 裸机的资源不是 RAM，是**主循环那一圈的时间配额**。
- **为什么要记一个"丢卡那一刻正在播"的旗标**：`want_play` 是在还挂着的那一拍按 `playing` 记下的，
  所以"用户先按了 `stop`、后来再插卡"不会被偷偷开播 —— 自动恢复不能覆盖人的显式意图。

### 7.5 不碰硬件能验的部分

行为级凭据分三层，缺一层就是没验（这个分层本身就是这套工程的规矩）：

1. **台架**：`sim/tb_v102_src_life.v`（PL 侧十几条，含 1:5 那条 S12）—— 要跑仿真，本轮不做。
2. **固件静态判据**：`node src/host/ps_hb_check.mjs --self`（不编译、不上板，几秒）。
3. **眼睛**：`board/README.md` 板级验收项里那一条（拔卡落图卡、暂停不丢画面、
   `sd remount` 说不说实话说）—— 要板子，本轮不做。

⇒ 第 2 层是**你现在就能自己跑的那一层**，也是本章结尾验证动作的主力。

## 8. 缓存与 DMA：谁负责 clean / invalidate

**结论先说**：**没人替你负责，写侧与读侧各自负责自己那一头。**

三个词的权威定义以 BSP 的函数名为准（不同书叫法不一样，别背术语，背函数）：

| 名字 | 做什么 | 什么时候用 |
|---|---|---|
| **Flush / clean**（`Xil_DCacheFlushRange`） | 把脏行**写回**内存，行还留着 | CPU 写完、别人（DMA / PL）要读 ⇒ "把我改过的推出去" |
| **Invalidate**（`Xil_DCacheInvalidateRange`） | **丢弃**缓存行，不写回，下次读强制走内存 | DMA 刚往这块地址灌完、CPU 要读 ⇒ "别再用你那份旧的" |
| **对齐** | 两者都按 cache line（A9 是 32 B）取整 | 所以本项目那几个缓冲显式 `__attribute__((aligned(64)))` |

⚠ **最反直觉的一条**：Flush 与 Invalidate 的区别**不是"哪个更狠"**。
数据是脏的时候只 Invalidate，那些脏行并不会消失 —— 它们**迟早**被替换算法写回内存，
把 DMA 刚写进来的内容**盖掉**。`sd_play.c` 里 `read_secs()` 那一段注释讲的就是这个真实踩过的现象，
所以它在**读之前**先 `Xil_DCacheFlushRange`（比如刚跑过 `fill`，目标区里可能正躺着脏行）。

**分工的另一半在驱动里**：XSdPs 的读实现自己会 `Xil_DCacheInvalidateRange` 目标缓冲
（`vitis/platform/.../bsp/libsrc/sdps/src/xsdps.c` 里那两句，本轮之前就已核实过，不再靠推断）。
⇒ 我们的代码只做一半，**是分工不是遗漏**。读 SDK 源码的价值就在这里：
"该做的那半有没有人做"必须有出处。

顺序也要对：`cmd_fill()` 是先 `Xil_DCacheFlushRange(FRAME_ADDR, FRAME_BYTES)`、
**然后**才 `ps_publish()`。反过来的话等于"告诉 PL 可以搬了，但数据还在缓存里"，
屏上拿到的是上一帧或半新半旧。

**还有一类"看着像一致性问题"其实不是的**：data abort。
`build/ps_app.mjs` 的文件头注释记了两处非对齐访问（`-O2` 会把逐字节读合并成一条 `ldr`；
newlib 的 memcpy 有半字快路径），而 **MMU 关掉时非对齐访问一定 fault** ——
所以构建里必须同时链上 `boot.S`（它才开 MMU）并加 `-mno-unaligned-access`。
**症状一模一样（data abort），根因不同**：一个是缓存/DMA，一个是编译器的合法假设。
这类"同症状不同根因"的清单，是裸机调试最有价值的私有知识，值得每个项目自己攒一份。

## 9. 构建：手写链接的裸机 elf，不是 Vitis 工程导出的那种

### 9.1 入口是 `build/ps_app.mjs`

一句 `node build/ps_app.mjs` 重编，产出 `build/ps_app.elf`（脚本 181 行）。
为什么不用 Vitis IDE 导出：脚本文件头写得很直白 —— 交付要求"从零复现"，
而"在 IDE 里手工点 New Platform / New Application"不属于能复现的步骤。

它做的事情按顺序是：

1. **前置检查**：编译器在不在、BSP 的 `xparameters.h` 与 `lib/libxil.a` 在不在，缺一就 FATAL。
2. **编译 `src/ps/` 下所有 `.c` 与 `.S`**：CFLAGS 里有 `-mcpu=cortex-a9 -mfpu=vfpv3
   -mfloat-abi=hard -mno-unaligned-access -O2`（那一条 `-mno-unaligned-access` 的账见 §8）。
3. **额外链上 BSP 的三个启动文件**：`asm_vectors.S`、`boot.S`、`translation_table.S`。
   漏掉三个的后果分别写在脚本注释里（§2.1 已复述）。**这一段是整个脚本最值钱的注释**，
   因为它解释了"手工链接"到底比 IDE 多管了哪三件事。
4. **链接**：`--gc-sections` + 链接脚本 `src/ps/lscript_ocm.ld` +
   `--start-group -lxil -lxilstandalone -lxiltimer -lgcc -lc -lm --end-group`。
   `-lm` 是 γ 曲线的 `pow` 要的（`main.c` 有 `#include <math.h>`）；三个归档都得给的理由在脚本注释里。
5. **成品自检**：链接"成功"不等于可执行。脚本用 `nm` 查关键符号在不在
   （`_boot`、`_vector_table`、`main`、`XSdPs_CardInitialize` 等）、`.text` 体积是否在合理区间、
   **ELF 入口是否等于 `_boot`**、**`_vector_table` 是否落在 0x0**。
   历史上曾经因为 ENTRY 指到一个绝对调试符号，`--gc-sections` 把 `main` 和整个 XSdPs 裁光，
   产出一个 `.text = 80 B` 的**空 elf 而毫无报错** —— 于是有了这一步。

**"链接成功但镜像是空的"** 是这一节要留给你的一句话。任何用 `--gc-sections` 的项目都可能中，
裸机上它不会抛异常，它只会在板子上表现为"什么都没发生"。

### 9.2 链接脚本文件名里的 `ocm` 解释了三件事

`src/ps/lscript_ocm.ld` 把程序放在 PS 内部的 OCM（不是 DDR）。这一个决定同时解释了：

- 为什么成品自检硬要求 `_vector_table` 落在 `0x0` —— 代码就在那附近；
- 为什么脚本要卡 `.text` 体积下限 —— OCM 只有 192 KB，装不下就没有回退；
- 为什么 JTAG 换 elf **不必先初始化 DDR 也能跑** —— 它是从 OCM 起来的。

栈也在脚本里按七个 CPU 模式各划一块（用户模式那块是 KB 级，不是 MB 级）。
⇒ 回看 §2.3 那条提醒：**裸机里别在调用链上摆大数组**，所有缓冲都写成 `static`。

### 9.3 换机器会撞的三件事

1. `PS_CC` / `PS_BSP` 两个环境变量是唯一的逃生口；默认 BSP 路径**在仓库内**
   （`vitis/platform/...`），以前默认指仓库外一个"曾经存在过"的目录，那目录一被删，
   PS 侧就悄悄变成"只能沿用旧 elf、不敢重编" —— 脚本注释里记了这笔账。
2. BSP 的 `bsp.yaml` 里驱动 `path` 是**绝对路径**（指向某个盘符下的 Vitis 安装），换工具版本或换盘符要重生成平台。
3. **一次性准备时少勾驱动不会编译失败**：`main.c` 里 XADC 那段包在
   `#ifdef XPAR_XXADCPS_0_BASEADDR` 里，BSP 少这个驱动就把温度分支整个编没，
   开机只多打一句"没有 PS-XADC"的说明。**功能静默缩水比编译错误难发现得多**，
   所以 `build/ps_app.mjs` 要求 BSP 里必须有 `libxiltimer.a`（γ 自动扫描与 SD 节拍都靠 `XTime`）。

### 9.4 elf 与 bit 的"一套"关系（收尾）

交付口径不认文件名，只认 md5：`build/ps_app.elf` 的 md5 要对得上冻结目录里
`MANIFEST.md5` 登的那一份，才算"这块板子跑的就是我刚编的"。
换 bit 必须重下 elf（§2.5），三件套顺序不可换（§2.2）。
这两条合起来就是本章关于"配套"的全部可执行内容。

| `report/` 目录下的各种报告 | **该目录不存在**。交付文档在 `report/`，过程记录在 `report/log/`（`ISSUES.md`、`VERSION_LINEAGE.md`、`CHANGELOG_V6/V7.md`、`PLAN_V8_SPEC.md`、`CONTEST_CHECKLIST.md` 等） |
| 串口靠 Python 的 `serial_ctrl.py` | 只有 **PowerShell**：`board/uart_cmd_script.ps1`（连发脚本）与 `board/uart_cap_once.ps1`（一次捕获），用 PowerShell 自带的 `SerialPort` |
| 推流靠 `.py` | 只有 `src/host/video_sender.mjs`（Node） |

于是"和板子说话"只剩三种通道，各自对应一类工具：

| 通道 | 工具 | 用途 |
|---|---|---|
| 串口（115200 8N1） | `board/uart_cmd_script.ps1` + `src/host/uart_cmd_check.mjs` + `board/cmd_battery_v81.txt` | 命令层验收（§5.4 那套契约） |
| 串口（捕获） | `board/uart_cap_once.ps1` | 留一份原始回声，供 `uart_cmd_check.mjs --replay` 离线复验 |
| UDP | `src/host/video_sender.mjs` | 推流与八种测试图案（讲数据面那一章的事，见 §6.2） |
| JTAG/xsdb 子进程 | `src/host/ddr_verify.mjs`、`health_read.mjs`、`build/tcl/set_src.tcl` | 回读与直控；**注意 `set_src.tcl:20` 是 `mwr -force 0x41200000 $SRC_VAL`**，它写的正是 §3.2 那张表 |

**为什么全部工具用 Node 而不是 Python**：判据要能在"验收 PC"上跑，
那台机器不保证有 python 与 pyserial，而 Node 与 PowerShell 是这台 Windows 一定有的。
这条选择不是偏好，是**可交付性约束**——值得在答辩里当作一句工程判断来讲。

⚠ 还有一条 JTAG 通道的隐含规矩（`ddr_verify.mjs` 生成的 tcl 里）：回读 DDR 前会
`catch {rst -processor}` 把核**暂停**（因为 app 开了 D-cache，`mrd` 走 A9 端口会读到缓存旧数据），
回读后**故意不 `con`**（A9 一跑回 boot ROM 就可能把 Flash/SD 里的旧 bitstream 刷回 PL）。
⇒ 这既解释了 §2.1"从不写 QSPI"为什么安全，也提醒：**每轮回读之后必须重跑三件套**。
它和本章"JTAG 路线不落非易失介质"是同一枚硬币的两面。

## 11. 已知过期与冲突点（读代码前先看这一节）

本轮**不改代码**，只登记。四条都是"文案/口径"级，不影响行为，但会让人判断错方向。

### 11a. `main.c` 文件头 ch1/ch2 那行已经不成立

`main.c:17` 写"ch1[31:9] 与 ch2 留给 V8-3/Gamma、V8-4/分割线（现在一个字节都不写）"，
而 `ctrl_write()`（`main.c:202-204`）已经在写 `[28:26]`、`[29]` 与几何 19 位，
ch2 更是 γ/温度在用。**行为以 `ctrl_write()` 为准**；文件头是 V8-2 时代的化石。
（同一文件头里 `[4:0] 保留` 那半句仍然正确 —— 化石只有一半，这种注释最容易骗人。）

### 11b. 开机横幅那句"旧写法仍可用"要读对

`cmd_help()` 末尾（`main.c:1368-1369`）印的是：
`旧写法仍可用: SRC0 SRC1 TH80 ZOOM0 ZOOM1 BILIN0 BILIN1 FRAME12（裸五位已随五位控制退役，给了会回一句等价的九位）`
括号这半句是后来补的、**它救回了整句话** —— 但如果只读前半句，
你会以为 `00111` 还能设效果，而它一个 bit 都不写（§4.3）。
⇒ 记法：**动词 + 数字的老写法全部仍收；裸位串只剩"翻译成九位"这一种作用。**

### 11c. `STAT` 分支的注释说 `geom=%05x`，代码是 `geom=%08x`

见 §5.3。这条本身不重要，重要的是它给本章的写法纪律提供了证据：
**引用函数名比引用行号耐久，引用代码比引用注释耐久。**

### 11d. 旧稿/旧文档里仍能找到 `report/…` 与 `serial_ctrl.py` 式的路径

包括 `report/HOST_GUIDE.md` 与若干章的交叉引用。判定方法很机械：

```
grep -rn "report/\|serial_ctrl.py\|video_sender.py\|requirements.txt" report/
```

命中不等于错，但**每一处都要按 §10 那张表核对**，因为目录结构与工具链都变过。
这类检查已经有工具：`src/host/doc_currency_check.mjs`（文档时效判据）与
`src/host/doc_enc_check.mjs`（编码门禁）。**文档也要有 CI**，否则它会以代码看不见的速度腐烂。
