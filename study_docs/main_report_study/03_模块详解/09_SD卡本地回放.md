## 1. 为什么这条通路值得单独写一篇

这是全工程里**唯一一处 PS 参与视频数据本身**的地方（其余时间 PS 只做控制面）。
它也是最容易"想当然"的一类改动：涉及 SD 控制器 DMA、D-Cache 一致性、
跨时钟握手、裸机 FAT32 四套知识，而每一套的错法都不会编译报错。

```
VIDEO*.BIN(卡) ─SD0 DMA→ DDR@0x10000000 ─(PS 翻转 bit18)→ PL 在 frame_start 搬一次 → 显示帧缓存
                        ↑ 唯一一次 memcpy 发生在硬件里
```

## 2. 零拷贝是设计目标，不是巧合

PL 的 `axi_frame_writer64` 通过 HP0 从 `BASE_ADDR` 读整帧。所以 SD 的 DMA **目标就是它**：

| 方案 | PS 侧代价 | 结论 |
|------|-----------|------|
| SD → 暂存缓冲 → memcpy 300 KB → BASE_ADDR | 每帧一次 300 KB CPU 拷贝 + 一次整段 flush | 多此一举，还多一个脏行窗口 |
| SD DMA **直接写** BASE_ADDR | 一次 `Xil_DCacheFlushRange` 预防脏行 | ✅ 采用 |

`read_secs()` 里那句 `Xil_DCacheFlushRange` **在读之前**，不是在写之后 ——
驱动读完会自己 invalidate 目标区间，但如果那里已经有**脏行**（比如刚跑过 `FILL`），
invalidate 之后脏行仍会在稍后被写回，把刚 DMA 进来的帧盖掉。顺序反了就是一次
"看起来随机花屏"。〔这条是四套知识里最容易写错的一套〕

## 3. 为什么必须"发布制"而不是"每帧自动搬"

`pl_video_top` 原来的触发是 `frame_start && src_sel && !eth_link`：**每个帧起始都搬一次**。
放 FILL 诊断图没问题（DDR 内容不变），但 SD 回放时 PS 要 30~60 ms 才写完一帧，
PL 每 16.8 ms 搬一次 ⇒ 一定会搬到"上半是新帧、下半是旧帧"的中间态 = 撕裂。

改法只有一行判断，但语义变了：

```verilog
wire pub_consume = frame_start && src_use && !eth_link;   // 条件不变
else if (pub_consume && pub_pend) fs_tog <= ~fs_tog;      // 多了"有请求才搬"
```

PS 侧对应：写完一帧 → `ps_publish()` 翻一位 GPIO → 至少等一个帧周期再写下一帧。

### 3.1 这个握手为什么单独成模块

`ps_publish.v` 里是"翻转位跨域"的标准三件套：3FF（前两级打异步，第三级专供异拍出沿）+
`new_tog = m1 ^ m2` + 挂起位 `pend`。它之所以值得拆出来，是因为**塞在顶层就只能靠上板看**，
而这段逻辑错了的表现（偶尔多刷/少刷一帧）和 SD 本身的速度抖动在屏幕上分不开。

台架 `sim/tb_ps_publish.v` 的做法值得记：把两个时钟做成 **7 ns / 20 ns 非整数比**，
再给每次发布加 0~5.9 ns 的伪随机相位（LFSR，可复现），扫 60 次。
判据不是"看着对"，而是**三次计数必须相等**：`rises=falls=consumes=60`。

### 3.2 电平语义的取舍（写清楚，别让别人当 bug）

`pend` 是电平不是计数器 ⇒ 两次快速发布会合并成一次挂起。
本项目里 PS 两帧之间至少隔 30 ms，不可能撞上；真撞上也只是"少刷一帧"，**不会撕裂**。
换成 2 bit 计数器要多一套溢出/复位约定，收益为零。这条在模块头部和 TB 判据 5 里都写了。

### 3.3 顺手修掉的一个真实亚稳态

`fs_tog` 原来采的是 `src_sel` —— 那是 `axi_clk`(100 MHz) 域的 GPIO 电平，
而这段 always 在 `clk_pix`(50 MHz) 域，**同一个文件里 `src_sel_pix` 早就存在**。
改成 `src_use` 之后 CDC 报告里那条 `clk_fpga_0 → clkout0_1` 的 Critical 行才有依据可查。
教训：一个信号有两种域版本时，**每一处引用都要问一句"我用的是哪个域的"**。

### 3.4 两个片源抢同一块屏幕：仲裁为什么不能只看"有没有包"

上面 `pub_consume` 里那个 `!eth_link`（现在是 `!owner_eth_pix`）背后是一件更大的事：
**ETH 引擎和 PS 引擎共用同一条 AXI 读口和同一个帧缓存写口**，谁在用时另一个必须等着。
老写法 `eth_mode = 3FF(eth_link)` 之所以能用，是因为那时只有 ETH 一路真的在搬。

判据换过一次，教训有两条值得留：

1. **"曾经收过包"不等于"现在活着"**。`eth_link` 来自 `link_active = |s_pkts[15:0]`，
   含义是自配置以来收到过**任何一个**包 —— PC 上一个 ARP 就够触发，拔网线也不会回 0，
   只有重配 PL 才清。所以"推完流再演 SD"以前必须重配一次板子（约 1 分钟）。
   新判据用链路健康引擎的 `stall_ms < 200 ms`（快照 lane7.bit3），它在断流后会自己落回去。
2. **用别人的计数器之前，先问那个计数器的时基还准不准**。这一条是板上撞出来的：
   RTL8211 断链时**不停 RXC，而是把它拉到 ≈2.5 MHz（≈1/48）**，而 `stall_ms` 的"ms"
   正是从这个时钟分出来的 ⇒ 那一位会连着十几秒一直说"活着"，仲裁死占 ETH，
   SD 接不回画面（屏幕上 `STALL` 钉在 9999，那是 OSD 的钉住值，不是时长）。
   所以仲裁要多一个输入 `eth_tb_ok`：**量 eth_live 的那个源时基没被拉慢也没停**
   （来自既有的 `snap_cross`：`hb_slow` 专门看"心跳还在但变慢"，`hb_gone` 看不见这个工况）。

还有一条工程上的：换手**只能在两个引擎都空闲时**发生（`~row_busy && ~fill_busy`）。
选择位在一次拷贝中途翻转会留下半开的 AXI 读突发 —— 老代码靠"ETH 优先"侥幸避开，
换了判据之后这件事不能再靠运气。往 PS 方向再多等 20 ms（滞回），
免得帧间隔卡在 200 ms 阈值附近时两路来回抢总线。台架 `sim/tb_v796_src_arb.v` 里
每一条断言都配了一个"反面对照"（包括把 `T_OFF_CYC` 设成 0 的第二个实例，
它必须真的会来回翻，否则"不抖"这条判据毫无价值）。

## 4. 裸机 FAT32：只需要读，所以只需要 200 行
| 步骤 | 偏移 | 说明 |
|------|------|------|
| MBR | LBA0 `0x1BE` | 取分区 1 的类型(必须 0x0B/0x0C) 与起始 LBA(`+8`) |
| BPB | 分区首扇区 | 11=字节/扇区(须 512)、13=扇区/簇、14=保留扇区、16=FAT 份数、36=FATSz32、44=根目录首簇 |
| FAT | `part+rsvd` | 簇 c 的表项在 `c*4` 字节处，只用低 28 bit；`≥0x0FFFFFF8` 是链尾 |
| 数据区 | `fat_lba+nfat*fatsz` | 簇 2 从这里开始：`lba = data + (c-2)*spc` |
| 目录项 | 32 B/项 | 名字 11 B（8.3、大写、空格填充）、attr=0x0F 是 LFN 要跳过；首簇 = **偏移 20 起那个 16 位小端字** `ld16(&d[20]) << 16` 再或上 `ld16(&d[26])` |

关键前提是**卡是我们自己做的**（`src/host/make_sd_video.mjs`）：全 8.3 名、无子目录、
无 LFN、`META.TXT` 里写清 `FRAMES/FPS/FILEi=名字 FRAMES=n`。
所以不需要 FatFs，也不需要 LFN 处理。BSP 的 `libsrc` 里本来也没有 `xilffs`。

一个容易忽略的解析陷阱：`META.TXT` 里 `FRAMES=` 出现两次语义（全局帧数、以及每个
`FILEi=` 行内的该文件帧数）⇒ 全局键必须**按行首匹配**，文件内键才允许在行内找。

## 5. 构建：为什么不用 Vitis IDE 点出来的工程

`build/ps_app.mjs` 直接调 `arm-none-eabi-gcc` + 现成 BSP。理由：**交付要求"从零复现"，
而"在 IDE 里 New Platform / New Application"不是可复现的脚本步骤。**

三个真实踩坑（都已变成脚本里的自检，不是一次性修好就走）：

1. **抄来的 FSBL `lscript.ld` 用 `ENTRY(_vector_table)`**，而 `_vector_table` 在 standalone 库里
   是个 `N` 类（绝对/调试）符号、不绑定任何输入段 ⇒ 配 `--gc-sections` 后链接器认为
   "没有任何东西可达"，把 `main` 和整个 `XSdPs` 全裁掉，产出 `.text = 80 B` 的**空镜像却报成功**。
   当时改成 `ENTRY(_start)` 并强制检查 `_start`/`main`/`XSdPs_CardInitialize` 与 `.text ≥ 20 KB`
   —— **"链接退出码 0"不等于"能跑的镜像"。**
   但那次修法本身有代价（2026-09-23 才还清，ISSUES #44）：`_start` 不引用
   `boot.S`/`asm_vectors.S`/`translation_table.S` ⇒ 标准启动整条链被 `--gc-sections` 裁走，
   于是一次冒出四个只在这条路径上才有的怪现象：没人写 CPACR（第一条 VFP 指令就陷 Undefined）、
   没人设 VBAR（异常去执行 0x0 那里恰好摆着的代码，症状长得像"板子自己重启了一遍"）、
   六个模式的栈从没初始化、**MMU 一直关着**（于是 newlib `memcpy` 的半字快路径必发对齐异常）。
   现在把三个 `.S` 显式编进来、入口写回 `ENTRY(_boot)`（命令行 `-Wl,-e,_boot` 会被脚本里的
   `ENTRY` 顶掉，`readelf` 悄悄给 0x0，一声不响），并把哨兵从"符号在不在"升级成**等值校验**：
   ELF 入口 == `_boot`、`_vector_table` == 0x0。
2. 2025.2 的 BSP 把 `_start` 放在 `libxilstandalone.a`、`XTime_GetTime` 放在 `libxiltimer.a`，
   都不在 `libxil.a` ⇒ 归档要三个都给。
3. 编译告警走 stderr，`execFileSync` 成功时只回 stdout ⇒ 不显式转发的话 `-Wall -Wextra` 等于没开。

## 6. 命令与状态

```
SD              挂载 + 打印（FAT32 参数、总帧数、fps、每个文件的帧数）
PLAY / STOP     循环回放 / 停止
FRAME<n>        显示第 n 帧（单帧跳转）
STAT            现在会把 sd / frames / playing / pub 一起报出来
SRC1 / FILL     原有：切到 DDR 源 / 画诊断图（FILL 也改成走发布协议）
```

`ps_jtag_boot.tcl` 起 PS → `program_pl.tcl` 下 bit → `xsdb build/tcl/ps_app_reload.tcl`
（只 `rst -processor` + `dow` + `con`，位流与控制字不受影响）→ 串口 115200 敲 `SD`。

## 7. 板上结论（2026-09-23 R29/R30，build#23/#24）

| 原来"还没证明的" | 现在 |
|---|---|
| ① SD 座是不是 BSP 里那个 SDIO0 | **是**：`XPAR_XSDPS_0_BASEADDR=0xE0100000` 那份 BSP 直接挂上（`FAT32 part_lba=2048 spc=32 rootclus=2 data_lba=34816`、`files=9 frames=4398`） |
| ② 实测吞吐 | **30.0 fps 稳定**，两条独立判据：`PLAY` 每 100 帧报的**窗口**速率（19/46 个窗口全 29.999，最低 29.18）；`STOP` 回报帧数 ÷ 时长（360 帧 / 12 s）。300 KB/帧 ⇒ 卡读带宽 ≈ 9.0 MB/s。注意别把"自首次 PLAY 起的累计平均"当帧率读（ISSUES #46） |
| ③ 撕裂 | 眼睛没看到；机理性判据在 `sim/tb_ps_publish.v`（逐相位扫，"一次发布=一次消费"）+ 只在 V-blank 提交的 `frame_commit_lock` |
| ④ META 不符必须挂载失败 | 反被用上了：真实卡上 `META.TXT` 有 712 B 而固件只读一个扇区 ⇒ 清单尾行被切成 `FRAMES=51`，`Σ≠FRAMES` 那条判据**如实报了不一致**（ISSUES #48）—— 判据没错，错在先怀疑卡而不是怀疑读进来的字节数 |

三关是连着翻的，讲 SD 这一幕时值得按顺序说：
`#47` 显示前最后一级 mux 用粘性的 `eth_link` 当"有没有片源" ⇒ 网线拔掉反而全红、PS 片源在屏幕上
从来没机会出现；`#48` 清单只读一个扇区 ⇒ 假缺口；`#49` 仲裁（谁拥有搬运机改由"最近有帧 **且**
量它的时基还准"+"两边都空闲才换手"决定）⇒ **插着线也能看到 PS 片源**，这一半 build#24 板级已确认。
还欠的眼睛判据：**停流之后画面自己交回 SD**（#24 红在这里 —— 那位"活着"被退化时钟骗住了，
见 §3.4 第 2 条；修好的是 #25，`build/frozen_r25_arbfix/`），以及推流与回放同时存在时不抢画面。
所以现场口径要按还没确认的那一半留余地：**一幕一个片源**，换源先停另一路。

## 9. 2026-09-24 06:3x 补：上面那行"首簇"曾经拼错，代价是一整晚

旧版这一格写的是 `首簇 = [20:21]<<16 拼 [26:27]` —— 读起来无害，但代码照它实现时把
** `[20:21]` 当成大端** 拼了（`(d[20]<<24) | (d[21]<<16)`）。正确的只有 `ld16(&d[20])<<16` 一种写法。
两个字节换不换，**只在高字非 0 时才有区别**，而高字非 0 等价于"首簇 ≥ 65536"，也就是
"这个文件的数据起点在数据区 1 GiB 之后"（本卡 `spc=32` ⇒ 簇 = 16 KiB，65536 × 16 KiB = 1 GiB 整）。

于是现场长成这样：

| 观察 | 当时的解释（错） | 真实解释 |
|---|---|---|
| 播到第 3584 帧必报 `SD read failed`（= 第 8 个文件第一帧） | 并发推流把 SD 挤到超时 | 第 8 个文件是第一个首簇 ≥65536 的文件，簇号被翻成 `0x01000686` |
| 之后连 `PLAY` 都报 `frame file not found` | 卡/目录坏了 | 一次半途夭折的多块读把控制器留在未完成传输里，**后续每次读都失败**（含目录扫描）⇒ 尸体不是病因 |
| 前 7 个文件（含 3583 帧）完全正常 | "所以不是数据问题" | **正好相反**：低簇号文件高字为 0，拼错也看不出来 ⇒ 选择性本身就是空间缺陷的签名 |

数值链条（这三个数对上，就再没有第二种解释）：

- 目录项错误解析给 `16778886 = 0x01000686`；把高字两字节换回来是 `0x00010686 = 67206`。
- 由 `sd_stage_r29` 的文件长度算"连续布局"预测：`META(712) + MANIFEST(466) + 7×9600 簇` ⇒ **67205**（差 1 簇）。
- `clus_lba()` 用错误簇号反算：`34816 + (16778886−2)×32 = 536959104` —— 与板上打印的 LBA 逐位相同。
- 分区末尾 `part_lba + part_sect = 62332928`（32 GB 卡，`part_lba=2048`）⇒ 该 LBA 不存在，卡拒绝是对的。

**排查它靠的不是更聪明的假设，是一行打印**：`read_secs` 的失败分支现在报
`lba / n / clus / part_end / IN-RANGE 还是 OUT-OF-RANGE / data_lba / spc`
（后两个是让人能复核那个分类的）。第一次定点跳帧就打出 `OUT-OF-RANGE`，十分钟结案。

现在这份固件里另外有两道自证，都是这段教训的产物：

| 名字 | 位置 | 判什么 | 反例 |
|---|---|---|---|
| `dir_selftest()` | `sd_mount()` 之前，不过就不挂载 | 三个合成目录项的解码，外加一条"旧写法必须给出 16778886 且与新写法不同" | 把字节序改回去 ⇒ 板子打印 `mount failed: cluster decode SELF-TEST failed (firmware bug, not the card)`，实测过 |
| 挂载时逐文件核对首簇 | `parse_meta()` 之后 | 每个 `VIDEOxxx.BIN` 的首簇必须 `< (part_lba+part_sect-data_lba)/spc + 2` | 正常打印 `[SD] dir map ok: 9 files, first clusters within 1946818` |

**留给自己的一句话**：这套文档里凡是"某字段 = 若干字节拼接"的写法，都必须显式写清**哪个字节是低位**；
不写，就会被下一个人（或下一个我）按直觉实现成反的，而且**只在数据量长到跨过 2^16 个簇之后**才发作。
