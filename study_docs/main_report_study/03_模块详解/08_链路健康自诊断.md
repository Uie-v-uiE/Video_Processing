## 1. 一句话职责

**把"屏上有黑纹"这种事后判断，变成运行期可读数：丢了多少字、作废过几帧、
帧间隔多少、多久没收到完整帧、以及 eth_rxc 到底还在不在。**

## 2. 为什么非做不可：现有统计在上板时是"死的"

入包链原本有四条统计（`frame_reasm` 的 `stat_frames/pkts/bytes/bad`），但：

| 统计 | 上板时的真实状态 | 原因 |
|------|------------------|------|
| `stat_bad` | **恒 0**（死路） | `eth_udp_video_top.v` 把 `p_good` 硬接成 `1'b1` —— 本设计不做 UDP 校验和检查 |
| `stat_frames` | 只会告诉你"成功了几帧" | 失败的帧**没有任何事件**，只能靠"没涨"倒推 |
| `stat_bytes/pkts` | 有效 | 但只反映"收到了"，不反映"落位了" |

而真正会吃掉数据的只有一处：

```verilog
// eth_udp_video_top.v
wire cdc_wr = (fb_wr_en || reasm_flush || flush_pend) && !fifo_full;
```

`fifo_full` 那一拍上的 16 bit 永远消失了。之前唯一的证据是**屏幕上出现黑纹**，
而且还得靠人眼、事后、并且无法区分"丢在 CDC"和"丢在 HP0 拷贝"。

## 3. `link_monitor`：探针放哪里

全部在 **eth_rxc（125 MHz）** 域，输入一律是**已经打过一拍的信号**：

| 输入 | 来自 | 含义 |
|------|------|------|
| `cdc_wr_req` | `fb_wr_en \| reasm_flush \| flush_pend` | 这一拍想往 CDC 写 |
| `cdc_full` | `dc_fifo.wr_full` | CDC 满了 |
| `frame_done` | `frame_reasm` | 有一帧过了验收门 |
| `frame_abort` | `frame_reasm`（v7.6 新增，只增口不改行为） | 有一帧字节数凑够了但验收没过 |
| `rows_missed` | 同上，与 `frame_abort` 同拍 | 本帧缺多少源行 |
| `frame_err` | `frame_reasm` | 坏包（上板恒 0，仿真里能测到） |

产出的十个 32 bit lane 见 `link_monitor.v` 尾部注释，其中三个是"判据级"的：

* `lane0 drop_words` —— 板上唯一真实丢数据通道的**累计字数**；
* `lane2 stall_ms` —— 距上一个完整帧过了多少 ms，流一断就从 0 开始涨，
  这是"链路死了"和"链路很慢"的分水岭；
* `lane2 rows_miss_max` —— 作废帧最多缺几行，直接对应黑纹的宽度。

三条语义约定，写在这里免得读代码时猜：

* lane0/1/2/6/8/9 是**自启动以来**的累计量，只有 `rst_n` 能清；
* lane3/4/5（帧间隔）可以用 `gapclr` **单独归零**，因为终身保持的 `gap_max`
  会被一次长空闲永久污染（详见 §7.5）；
* 所有 16bit 显示字段一律**饱和**，`0xFFFF` 读作"至少 65.5 s / 超过量程"。

## 4. 快照而不是活计数器：`snap_cross`

OSD 在 50 MHz 像素域、PS 在 100 MHz `fclk0` 域，而数字生在 125 MHz eth 域。
320 bit 的总线**不能直接跨**（会撕烈）。做法是本工程已经在用的一招：

1. 源域把 `lm_bus` **整拍**写好，同一拍翻转 `lm_bus_tog`；
2. 目的域用 3 级 `ASYNC_REG` 同跳变，看到沿之后再采一次总线；
3. 因为沿要 3 个目的周期才到，那时源总线早就稳定了 ⇒ 取到的必是完整快照。

两个细节是踩过才知道要做的：

* **发布节流 `SETTLE=32`**：目的域捕获的总线必须至少稳定 3 个目的周期
  （50 MHz 下 60 ns）。两次事件如果贴得太近，`tog` 会翻两次（等于没翻），
  而总线可能正被改写。节流窗口 256 ns 把这件事挡住了。
* **节流不能丢事件**：第一版直接 `pub = upd_w && settle==0`，结果 TB 立刻抓到
  "新帧到了但屏上 stall 还停在 531" —— 那个 frame_done 正好落在窗口里被**丢掉**了，
  要等 200 ms 后下一次强制刷新才回来。修法是 `pend_ev`：窗口期内到的事件记下来，
  窗口一过立刻补发。

## 5. 心跳：为什么"数字不动"本身要能被看见（以及本板给出的意外）

原设计动机：拔网线之后如果 PHY 停供 RXC，整个 eth 域冻住，`lm_bus` 停在最后一帧的值，
OSD 上的 STALL 会停在一个好看的数字上 —— 这是最坏的一种谎。所以源域每 ms 翻一个
`lm_hb`，目的域超时未见到沿就置 `hb_gone`，OSD 于是强制 `STALL=9999`。

**2026-09-22 的板级实验把这个假设推翻了**（数据在 `data/measured/board_measure_r08.md`）：
拔线之后 `hb_gone` 一次都没有触发。原因不是心跳逻辑坏了，而是
**RTL8211F-CG 在链路断开时并不停掉 RXC，而是把它拉慢到约 1/48**。
证据不是"lane31 一直是 0"这一条（那只能说明有时钟），而是一条更硬的定量观测：
断流那 13 秒里 `stall_ms` 只从 831 走到 1117，即 **+20.5 计数/秒**，而不是 1000/秒；
而 `stall_ms` 的唯一时基就是 `ms_tick = (ms_div == 124999)` ⇒
**当时 eth_rxc 实际只有约 125 MHz / 48.6 ≈ 2.5 MHz**。

⇒ 时钟"在，但慢了 48 倍"，所以"有没有沿"检不出来，要检的是**沿来得够不够快**。

于是加了 `hb_slow`：目的域量到心跳间隔大于 `SLOW_MS`（默认 5 ms）就置位。
正常 1 ms、退化 ~50 ms，门限两侧各有 5× 与 10× 余量。注意方向不要搞反 ——
**源时钟变慢 ⇒ 目的域量到的间隔变长**（第一版我把比较写成 `<` 的反面，用具体数字
重推一遍才发现：`LIM=10_000_000`、1 ms 心跳时 `to_cnt=9_950_000`，
必须 `to_cnt < LIM − SLOW_MS×DST_HZ/1000` 才是"间隔超标"）。

`osd_stall = (hb_gone | hb_slow) ? 9999 : stall_ms` —— 断链时 `stall_ms` 已经没有
"毫秒"的含义，屏上就不要再假装它是；宁可显示一个明确的 9999。
lane31 对 PS 侧变成 `{30'd0, hb_slow, hb_gone}`，两件事分开可读。

**这一节留下的通用教训**：涉及"外部时钟会不会消失"的判据，不能靠 PHY 数据手册的
一句话或直觉，必须真拔一次线。这条实测同时说明 `stall_ms` 在断链期间只是
**序指标**（越来越久），不是秒表 —— 对外表述时要用 `flags.bit3 流活着` 和
`pkts` 停止增长来说"没流了"，而不是引用那个爬得很慢的毫秒数。

## 6. PS 侧读回：不加 AXI 从设备，只用一个 lane 窗口

BD 里原本只有一条输出方向的 AXI GPIO。为了读到 320 bit，只加**一条 32 bit 只读 GPIO**：

* lane 号写在**已有**的 `gpio_o[31:27]`（这 5 位原本没人用）；
* 数据从 `GPIO_1_tri_i[31:0]` 读；
* `system_top` 里一个 10 选 1 的组合 mux + `lane 31 = 心跳状态`，越界返回 `0xDEADBEEF`。

上位机 `src/host/health_read.mjs` 会先读回 GPIO_0 原值、只改这 5 位、
读完再原样写回 —— 否则会顺手把特效开关和阈值踩掉。

## 7. 两个只有**综合**才暴露、仿真全绿的 bug

这一节是本模块真正的学习价值所在。

### 7.1 `ms_last16` 被两个 always 块驱动

时基块只在复位里写 `ms_last16`，计数块在 `frame_done` 时写它 ——
两个 always 驱动同一个 reg。仿真里看不出问题，综合报：

```
CRITICAL WARNING: [Synth 8-6859] multi-driven net on pin Q with 2nd driver pin 'GND'
CRITICAL WARNING: [Synth 8-6858] multi-driven net Q is connected to at least one constant
                  driver which has been preserved, other driver is ignored
```

"other driver is ignored" 意味着板上 `ms_last16` 只剩一个 GND 常量驱动 ⇒
间隔测量和 stall 基准全是死的。**修法是让一个信号只属于一个 always 块**，
不是"把 warning 关掉"。

### 7.2 分频器位宽写死，`ms_tick` 在板上永远不来

```verilog
reg [15:0] ms_div;
if (ms_div == TC-1) ...     // TC = 125_000_000/1000 = 125000 > 65535
```

16 bit 永远够不到 125000 ⇒ 比较恒假 ⇒ `ms_tick`、`ms16`、`stall_ms`、`gap_*`、
心跳在**真实参数**下全部不工作。综合的取证是一句不起眼的 WARNING：

```
WARNING: [Synth 8-6014] Unused sequential element ms_div_reg was removed.
```

**为什么 26 条断言全绿却漏了它**：TB 为了让"等 200 ms 断流"跑得动，
把 `CLK_HZ` 改成了 1000（TC=1，一拍一 ms）—— 恰好把这个问题改没了。
教训写成一条规则：**为了跑得动而改参数的 TB，必须再用生产参数跑一遍守门。**
现在 `tb_link_monitor` 里多了一个用 `CLK_HZ=125_000_000` 例化的 `u_lm_prod`，
它只回答一个问题：这段仿真结束时 `ms_tick` 到底响过没有。实测
`PASS production timebase: 62 ms_ticks in 7832805 cycles (125000/ms)`。

修法是把宽度算出来，而不是猜：

```verilog
localparam integer DW = $clog2(TC + 1);   // TC=1 时也至少 1 bit
reg [DW-1:0] ms_div;
```

### 7.3 第三个：一次综合才暴露的 45 级组合链（OSD 十进制）

第一次全流程 L3 直接**门禁失败**：`WNS −6.765 ns、19 个违例端点`，最差路径是

```
Source      u_pl/u_lm_x/bus_q_reg[31]/C      （clkout0_1，50 MHz 像素域）
Destination u_pl/u_osd/g_reg[3]/D
Data Path   26.647 ns（logic 7.945 / route 18.702）   Logic Levels 45（CARRY4=16 LUT6=16 …）
```

根因是我把 32 bit 的 `drop_words` 直接在像素域做十进制：`/10000、/1000、/100、/10`
四个常系数除法合成一条链。修法分两步，都不涉及"放宽约束"：

1. **DROP 改成十六进制** —— 取 nibble 只要一层 mux，且"00000 = 没丢"在任何进制下一样成立；
2. **STALL 保留十进制，但先饱和到 14 bit、再分两拍算** —— 第一拍只算 `/1000` 和余数，
   第二拍算余下的百十个位。数字每帧才变一次，晚两拍对人眼没有任何影响。

改完 OOC 复测：OSD 最差路径回到 27 级，而且那 27 级是 `x → 行/列除法 → 字模` 的
**既有形状**（V7.6 之前就一直在 +0.9 左右 met），除法头部已经从这条链上摘掉了。

顺带把 `build/tcl/ooc_newmods.tcl` 升级成"带时钟和 I/O 延迟的 OOC 时序预检"：
三个新模块单独跑 1~2 分钟，而全流程要 15 分钟。**这个脚本存在的唯一理由就是上面这一条。**
（它自己也踩了两个坑：本流程里没有 `remove_from_collection`，也没有 `get_object_name`，
只能用对象名串比较；不给 `set_input_delay` 的话 OOC 里全是 IN2REG、slack 恒为 `inf`，等于没测。）

### 7.5 第三个层次：数字**能算对**但**装不下**（gap_ms 回卷）

前两个缺陷是"逻辑死了"，这个是"逻辑活着但说谎"，性质不同、也更难发现 ——
因为它不产生错误行为，只产生**看起来合理的错误数值**。

`gap = ms_now − ms_last`，而 `ms_now` 当时是 16bit。任何超过 **65.535 s** 的帧间隔都会
`mod 65536` 绕回去。板级实测到 `gap_max = 34066 ms`：那不是任何一次断链的时长，
是回卷后的余数。而 `gap_max` 是终身保持的，所以危害有两层：

1. 一次长空闲（例如两次实验之间忘了推流）留下的假数会**永远挂着**；
2. 之后**真正更大**的间隔会因为绕回而**读出更小的数** —— 排序都不可信。

修法三层，缺一层都会以别的形式复发：

* `ms32` 加宽到 32bit（49 天不回卷）；
* `gap` 一律**饱和**在 `0xFFFF`，语义写成"至少 65.5 s"（仪表宁可说"超出量程"，
  也不给一个假精确值 —— 与 §不变量 I-2 是同一条原则）；
* 加 `gapclr`：`gpio_o[26]` 经 3FF 同步进来的电平，只清 `gap_*` 并**撤销 have_base 基准**
  （于是清零后的第一个 `frame_done` 只重建基准、不把"空闲到现在"折进间隔，
  与 §8 判据 D 是同一个道理），其余 lane 保持"自启动以来"的语义不变。
  上位机侧就是 `node health_read.mjs --gapclr`。

**这次真正的教训**：我原本为拔线实验写了一条预测（"`gap_max` 应该跳到约 270 ms
而不是 10066 ms"），方向是对的，但**仪表根本没有量程表达这个数**，而且它还被实验
前的空闲期污染了。所以：**设计预测性判据之前，先检查计数器的位宽，以及这个量是
终身保持、可清零，还是会被别的事件污染。** 判据写得再好，也救不了一个会绕回的寄存器。

### 7.4 顺带：TB 自己也会错

* 在**正沿**用阻塞赋值拉 `cdc_full`，会和 DUT 的 `always @(posedge)` 抢同一时刻，
  导致 `full_d` 和 `cdc_full` 同拍变 1 ⇒ 上升沿检测不到 ⇒ `cdc_episodes` 恒 0。
  测试台里凡是喂给 DUT 的激励都该在负沿变。
* 给 16 bit 的 `net_stall` 传 `70000` 想测饱和，结果先被截成 `4464`。
  饱和测试要挑**装得下但超过阈值**的值（60000）。

## 9. 不变量

* **I-1** `lm_bus` 只在事件拍被整拍写入，其余周期纹丝不动 ⇒ 任何目的域都能安全捕获。
* **I-2** 16 bit 显示字段一律**饱和**而非回卷：健康数字回到 0 会被读成"没问题"。
* **I-3** 每个 reg 只属于一个 always 块（7.1 的直接产物；`ooc_newmods.tcl` 是它的机器检查）。
* **I-4** 屏上任何"看起来正常"的数字都必须能在源时钟停止时翻转成"明显不正常"
  （靠 `lm_hb` + `hb_gone`），否则它就不算诊断。
