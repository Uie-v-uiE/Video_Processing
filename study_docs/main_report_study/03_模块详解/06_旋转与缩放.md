## 0. 两条几何通路的位置

> **V7.7（2026-09-22 夜）改了拓扑：左半窗不再旋转。**
> 原来 `pl_video_top` 给左窗例化了 `rotate_mapper`（`u_rmap`），右窗再通过
> `zoom_mapper.rotate_en` 叠一次旋转 —— 两个窗一起转。现在按需求只留右窗转，
> `u_rmap` 已删除，左窗固定走 `cx_q3/cy_q3`（就是过去 `angle=0` 时板上实际在跑的那条路径）。
> 结果：**省掉 4 个 DSP48**（13→9）、182 个 LUT，WNS 反而从 +0.408 提到 +0.540。
> `rotate_mapper.v` 仍留在树里当参考实现和本页的讲解对象，但它**不再被任何顶层例化**。

```
光栅 (x,y) ─► 画布坐标 ┬─ 左半窗 ─► 直连（cx_q3/cy_q3，不旋转）──┐
   cx = x<512 ? x : x-512 (:111-112)                             ├─► 共用 BRAM 读口（分时）
   cy = (y>>1)<300 ? y>>1 : 299   (:113)  ─ 右半窗 ─► zoom_mapper（3 级）─┘
                        （zoom_mapper 内部的 rotate_en 分支 = 现在唯一的旋转）
```

**两窗共用同一个 16 bit 读口**：`fb_sel_right = ~left_d[2]`（`pl_video_top.v:351-354`），
没有第二个读口。这是单口 BRAM 决策的直接后果
（见 [模块详解 03](../03_模块详解/03_显示帧缓存与光栅几何.md) §1）。
⇒ 任何插值（每像素要多读几个抽头）都必须先解决这个口，见 §3.3 末尾与
`report/OVERNIGHT_LOG.md` 的 R11 追加 2。

## 1. 旋转：逆映射的 RTL 原文

> 下面这些行号描述的是 `rotate_mapper.v` 本身。它今天只有一个"读者"：
> `zoom_mapper` 的旋转分支用的是**同一套数学**（只是多乘一个 `inv`、末尾 `>>>16`）。
> 学一份等于学两份，这也是它没被删掉的原因。

### 1.1 三级流水

```verilog
// s0：中心化 + Y 翻转（无复位块，rotate_mapper.v:24-28）
xp <= x_in - IMAGE_W/2;            // x − 256
yp <= IMAGE_H/2 - y_in;            // 150 − y  ← 把屏幕坐标系翻成数学坐标系

// s1：Q8 乘加（:33-36），xp 由 13 bit 符号扩展到 24 bit
xr_m <= xp*cos_v + yp*sin_v;
yr_m <= -(xp*sin_v) + yp*cos_v;

// s2：>>>8 反 Q8、反中心化、越界判定（:40-43,45-65）
xr = xr_m >>> 8;   yr = yr_m >>> 8;
xs = xr + IMAGE_W/2;   ys = IMAGE_H/2 - yr;
```

写成数学式（完整推导，不含糊）：

```
sx = ( (x−256)·cosθ + (150−y)·sinθ ) / 256  + 256
sy = 150 − ( (−(x−256)·sinθ + (150−y)·cosθ) / 256 )
```

- 这是**逆向映射**：对每个目标像素求它的源坐标，而不是把源像素推到目标位置。
  为什么必须逆向，见 [图像原理 03](../01_图像原理/03_几何变换_旋转缩放与定点数.md) §2 ——
  正向映射会在旋转时留下空洞，而且无法逐拍流式输出。
- 旋转角实际是 **−angle**（注释 `:3` "rotate by -angle (matches reference matlab)"）。
  也就是按键增大角度时屏幕上是**顺时针**转。这个符号约定值得记住，
  因为「为什么反了」是很容易被问到的问题。
- `>>>8` 是**算术右移 = 向 −∞ 取整（floor）**，不是四舍五入 ⇒
  负坐标会额外 −1 偏置（`−3/256 = −1`）。〔推断，由 `>>>8`〕
  这就是旋转图看起来「往左上偏一点点」的来源，量级 1 像素。

### 1.2 越界：填黑，不是 clamp

```verilog
if (xs<0 || xs>=IMAGE_W || ys<0 || ys>=IMAGE_H) begin x_out<=0; y_out<=0; oob<=1; end  // :55-58
else                                            begin x_out<=xs[11:0]; y_out<=ys[11:0]; oob<=0; end
```

`oob` 一路传到 `pix_left/pix_right = oob_fb_d1 ? 16'h0000 : ...`
（`pl_video_top.v:398-401`）与 `split_display.v:28` 的 `sel = oob ? 黑 : ...`。
注意 `x_out/y_out` 仍被强制成 0，所以被遮罩那一拍其实**读的是源 (0,0) 像素**，
只是结果被 `oob` 挡掉（无害，但不是「不读」）。

### 1.3 三角表：手写的组合 ROM

| 事实 | 值 | 证据 |
|------|----|------|
| 形式 | `always @(*) case` **组合查表**，不是 BRAM、无输出寄存器 ⇒ 0 拍延迟 | `sin_rom.v:7-370`、`cos_rom.v:7-370` |
| 条目数 | 每个恰好 **360 条** case 项 + default | `grep -c "^            9'd"` = 360 |
| 语义 | `round(fn(deg)*256)`，10 bit **有符号** Q8 | `sin_rom.v:2`、`cos_rom.v:2` |
| 精度 | 0°/90°/180°/270° 处为 **±256 而不是 ±255** ⇒ 1.0 精确 | 对照表 |
| default | **`10'sd0`（两个表都是）** | `sin_rom.v:369`、`cos_rom.v:369` |
| 例化次数 | `rotate_mapper.v:20-21` + `zoom_mapper.v:22-23` ⇒ **各 2 份，共 4 个查表实例** | |
| 综合落点 | 全部 **512×10 → LUT**，不占 BRAM（条目按 9 bit 地址全展开成 512，不是 360） | `build/build_r05_skid.log:1034-1039` |

抽查对照（从文件里逐条读出）：

| angle | sin | cos | 期望 ×256 |
|-------|-----|-----|-----------|
| 0 | 0 | 256 | 0 / 256 |
| 45 | 181 | 181 | 181.02 |
| 90 | 256 | 0 | 256 / 0 |
| 180 | 0 | −256 | 0 / −256 |
| 269 | −256 | −4 | −255.95 / −3.54 |
| 270 | −256 | 0 | −256 / 0 |
| 359 | −4 | 256 | −4.45 / 255.96 |

45° 处 181/256 = 0.70703 vs 真值 0.70711 ⇒ 相对误差 1.1e−4。

⚠️ **`cos_rom` 的 default = 0（不是 256）是一个潜在隐患**：
若 `angle ≥ 360`（正常由 `angle_ctrl` 回绕保证不会出现），
sin=cos=0 ⇒ 映射把**所有点塌到源图中心 (256,150)**，屏幕上会变成一个点，
而不是「未旋转」。0° 恒等性只由 case 项 `9'd0: 10'sd256` 保证。〔推断，仅越界可达〕

### 1.4 DSP 落点（综合实证）

```
rotate_mapper:  A2*B 13x10 → P23、(PCIN±A2*B)' → P24、AREG=1   （s1 被吸进 DSP 输入寄存器）
zoom_mapper:    A*B 24x11 → P 35，AREG/BREG/CREG/DREG 全 0（纯组合）
                       — build/build_r05_skid.log:1081-1084, 1088, 1092
```

`rot_xs = xr_m * inv` 声明为 32 bit，而 24×11 乘积自定宽度是 35 bit ⇒ **高 3 bit 被丢**。
按 IMG_W=512/IMG_H=300、inv ≤ 512 估算最大 |值| ≈ (255+150)×256×512 ≈ 5.3e7 ≪ 2³¹
⇒ 在本几何下无害。〔推断，由最大值估算〕
但如果分辨率改大（例如 1280×720 + inv=1024）这个截断就会咬人 —— 属于「参数化不可信」的清单。

## 2. 角度从哪里来

```
key1_n / key2_n（低有效，W18 / V14）
  → 2 个独立 key_debounce #(.CNT_MAX(1_000_000))，clk = sys_clk   pl_video_top.v:68-73
      · 2 级同步 + 计数器 + 边沿检测                              key_debounce.v:12-41
      · CNT_MAX=1e6 @50 MHz = 20 ms                              （由 xdc:6 算）
      · 需要「连续 20 ms 稳定电平」，抖动/短按不产生事件           :28-35
      · pulse 只在 释放→按下 的边沿出，宽 1 拍                    :27,37-40
      ⇒ 长按只出一次脉冲，无连发（angle_ctrl.v:2 注释里的
         "Optional hold-to-accel" 在 RTL 中未实现）
      ⇒ key_stable 输出悬空（:69,:72）
  → angle_ctrl：key_inc=p1、key_dec=p2，angle[8:0]，rotate_active=(angle!=0)
      · 0↔359 双向回绕，单位 1 度，无小数度                       angle_ctrl.v:11-19
      · 两键同时脉冲：if(inc) ... else if(dec) ⇒ +1° 优先          :16-19
  → angle[8:0] 被 clk_pix 域的 rotate_mapper / zoom_mapper /
    split_display(angle[1:0]) / osd_overlay 整总线直接使用        :127,:156,:455,:494
```

**关于 `angle` 跨域的正确说法**（这点很容易被说错）：
`sys_clk` 与 `clk_pix` **同源同频**（同一 MMCM，`clk_gen.v:17,21`），
XDC 把它们放进**同一个** group（`rk_zynq7020.xdc:53-56`），组内路径**照做时序分析**
⇒ 这不是「未检查的异步 CDC」（`build/cdc.rpt` 把它列为 `sys_clk→clkout0_1` "Safely Timed"、
347 端点全 safe、WNS +8.401）。
但 9 bit 总线同时翻转，仍可能在同一个像素周期里读到「旧的 xp/yp × 新的 sin/cos」
⇒ **每按一次键，一帧内有若干像素的过渡撕裂**。〔推断〕
要彻底消除就把 `angle` 在像素域打两拍并锁存成 `angle_q`，让 s0/s1 用同一个值。

`led[0]` = 心跳（正常 `hb[24]` ≈ 1.5 Hz；发生过 V-blank 拷贝超时则 `hb[22]` ≈ 6 Hz 快闪），
`led[1]` = `src_use`（`pl_video_top.v:512-518`、`:249-254`）—— 这是**不看屏幕**判断
「有没有撕裂风险」的板级判据，见
[验证与上板 02](../05_验证与上板/02_不看屏幕的判据.md)。

## 3. 无级缩放

### 3.1 Q8 的 `inv_scale` 语义

```
INV_LO = 256 → 1.0×（原始尺寸，最大）
INV_HI = 512 → 0.5×（画面上四周留黑边）
"inv 越大 → 采样越散 → 画面越小"        zoom_ctrl.v:2-4,6-7
顶层覆盖：#(.INV_LO(10'd256), .INV_HI(10'd512), .STEP(10'd2))   pl_video_top.v:117
```

11 bit 有符号扩展才放得下 512：`wire signed [10:0] inv = $signed({1'b0, inv_scale});`
（`zoom_mapper.v:26`）。

**无旋转分支**：
```verilog
raw_xs = xp_s1 * inv;   xs_pix = raw_xs >>> 8;   sx_c = xs_pix + IMAGE_W/2     // :60-71
yp_disp = y_in − IMAGE_H/2      ← 显示域，不做 Y 翻转
⇒ sy_c = ys_pix + IMAGE_H/2
```
即 `sx = W/2 + ((x−W/2)*inv)>>8`，与 `report/ROTATION_AND_EFFECTS.md:48-51` 一致。
`inv=256` 时是**严格恒等映射**（`xp*256 >>> 8 == xp`，无舍入损失）—— 由 `:60,65` 推导。

**有旋转分支**：先 Q8 旋转（`xr_m/yr_m`，用 `yp_math` 做 Y 翻转）、再乘 inv、最后 `>>>16`
（`:46-51,58-64,68-70`）。
⇒ RTL 实际顺序是**先旋转后缩放**；`report/ROTATION_AND_EFFECTS.md:53` 的文字写的是
"先缩放偏移再套旋转"。对「同一中心的等比缩放 + 旋转」两者可交换 ⇒ 结果等价。〔推断〕

0.5× 时的可见范围（推断自 `:65-71`）：列 128..383（256 列显示 512 源列）、
画布行 75..224（即显示行 150..449），四周各留 128 列 / 150 显示行黑边。

### 3.2 呼吸循环

```verilog
// zoom_ctrl.v:27-47  只在 frame_start 单拍上更新（每帧一次）
dir=0: inv_scale + STEP >= INV_HI → 顶到 512、dir<=1
dir=1: inv_scale <= INV_LO + STEP → 回 256、dir<=0
```

- 256→512 用 128 帧、512→256 用 128 帧 ⇒ **256 帧一个完整呼吸**。
- 帧周期 1344×625 = 840000 拍 @50 MHz = 16.8 ms ⇒ **一个循环 ≈ 4.30 s**〔推断〕。
- 每帧线性变化 2/256 = **0.78%** ⇒ 视觉上连续，看不到台阶。
- `frame_start` 是 `(0,0)` 处 1 拍脉冲（`video_timing.v:68`）⇒ 缩放参数**逐帧一致**，
  不会在一帧内部变化（否则一帧里上下部分的缩放率不同，会出现「果冻」效果）。
  这是这条链最重要的一个设计细节。
- `zoom_active` 只是状态位（`:45,:47`），**不参与 `zoom_mapper` 的使能**
  （`zoom_mapper` 根本没有 enable 端口）⇒ 缩放恒生效，`inv=256` 时数学恒等等效「关」。
- `enable` 通路：`zoom_en` → 3FF `ze0/ze1/ze2`（`ASYNC_REG`，复位值取
  `ZOOM_DEFAULT_ON[0]`）→ `zoom_run`（`pl_video_top.v:91-101,10,119`）；
  `!enable` 时 `inv_scale/dir/zoom_active` 全部回 1.0×。
- ✅ **`zoom_en` 已经在 V7.7 接回可控**（`system_top.v` 用 `gpio_o[17]`，不再硬绑 `1'b1`）
  ⇒ 串口 `ZOOM0/ZOOM1` 真正生效。代价是一条**解绑常数时必须查谁在依赖它**的教训：
  `set_src.tcl` 原来只写 `0x00010000`（bit16 src_sel），解绑后那样会让"上电即呼吸缩放"
  直接消失 ⇒ 改成写 `0x00030000`。`main.c` 的 `cur_zoom` 默认 1 也是同一原因。
  旧版这里写的是"`ZOOM0/ZOOM1` 与 GPIO bit17 全部无效"，那是 V7.6 及之前的状态。

### 3.3 `frac_x/frac_y`：算了，但没人用

```verilog
// zoom_mapper.v:73-74
fx = rot_s1 ? 8'h00 : raw_xs[7:0];    // Q8 的小数低 8 bit
fy = rot_s1 ? 8'h00 : raw_ys[7:0];
// 寄存输出 :81-94（越界时清 0）
// 顶层：wire [7:0] zfrac_x, zfrac_y; .frac_x(zfrac_x), .frac_y(zfrac_y)   pl_video_top.v:153,159
```

**全仓检索 `zfrac_x/zfrac_y` 只有这两处命中，没有任何读方**
（`frac_x/frac_y` 的其余命中全在 `zoom_mapper.v` 自身与 `sim/tb_zoom_mapper.v:31`）。

⇒ 结论：**缩放是最近邻采样，没有双线性插值**。
而且一旦与旋转叠加（`rot_s1=1`）小数位被强制清 0 ⇒ 即使将来接上，旋转态也拿不到插值信息。

〔这条值得记〕**接口留好了 ≠ 功能存在**。想加双线性：需要 4 次读
（当前 1 个 BRAM 读口做不到）、把 `>>>8` 改成加权混合、并且在旋转态也要输出小数 ——
是一个「先解决读口」的问题，不是「先解决乘法器」的问题。

**V7.7 把这句话从"推测"变成了"量出来的三件事"**（`src/host/interp_study.mjs`，
表在 `data/measured/interp_gain_attribution.txt`）：

| 结论 | 数字 | 对架构的意义 |
|------|------|--------------|
| 缩放端的增益**全在横向** | inv=384 各图样 +3.6~+6.2 dB，纵向占 0% | 只需要 `fx` ⇒ 少读一行源数据 |
| 旋转端的增益**必须两维都有** | 各向同性纹理 +14.2~+17.0 dB，其中横向仅 ~20%、纵向 ~20%，其余是 2D 组合才有 | "只做横向"拿不到旋转的肉 ⇒ 必须读两行 |
| 硬边缘/2px 棋盘上双线性**更差** | −3.7 dB / −1.5 dB | 对外只能承诺"对纹理与细线 +14 dB"，不能说全面优于最近邻 |

还有一条更容易搞错的：**"横向免费"是错的**。`pl_video_top.v:357-379` 的读口每个像素周期
恰好一次读（两窗共用），**零余量** ⇒ 哪怕只补横向抽头也要提速。
好消息是 `clk_pix5x`（250 MHz，同一 MMCM，已经在用）每像素给 5 个槽，双线性要 4 个 ⇒ 够，
而且同源整数比不是异步 CDC、不用 FIFO；对照实验（`sim/probes/`）证明**再加一个逻辑读口**
会把帧缓存从 80 个 RAMB36 顶到 160 个，所以"同一个口跑快 5 倍"是唯一可行的路子。

## 4. 彩条源（几何对照用）

```verilog
color_bar #(.H_ACTIVE(512), .V_ACTIVE(300))   ×2 实例
  左路 .x(cx), .y(cy), .de(de)                    pl_video_top.v:377-380
  右路 .x(sx_r), .y(sy_r), .de(de_d[2])           :381-384
⇒ 右半窗的彩条是按「缩放/旋转之后的坐标」生成的（几何域彩条）
```

- 8 条色带用 `th_k = k*H_ACTIVE/8` 的**精确阈值比较**划分（不是除法近似）
  （`color_bar.v:20-26,29-38`），H=512 ⇒ 每带 64 列。
- 颜色序：白/黄/青/绿/品红/红/蓝/深灰(0x10)（`:42-51`）。
- 对角暗条：`((x+y) & 13'h001F) < 2` → `(0x30,0x30,0x30)`（`:52-54`）——
  用来在屏幕上暴露「行/列错位」，因为它是斜的。
- 输出 1 级寄存，`de` 无效时强制 `16'h0000`（`:57-64`）。
- ⚠️ 两条延迟链不同深：左路 `bar_l_d4`（D=5）、右路 `bar_r_d2`（D=6）
  ⇒ SRC0（彩条）与 SRC1（视频）下右窗水平配准差 1 列
  （见 [效果链 §4.2](../03_模块详解/05_效果链.md)）。
- ⚠️ `V_ACTIVE` 参数被传值但模块体内 0 次引用（`color_bar.v:5`）。

## 5. 一句话结论索引

1. 旋转是**逆映射 + Q8 三角表 + `>>>8` floor 取整**，角速度量 = 1°，0↔359 回绕。
2. 旋转角实际是 **−angle**（与 MATLAB 参考对齐）。
3. 越界**填黑**（不是 clamp/复制边缘），旋转图的四个角就是黑边。
4. 缩放是 `inv/256` 的 Q8 最近邻，256↔512 三角波、256 帧一循环 ≈ 4.3 s。
5. 缩放参数只在 `frame_start` 更新 ⇒ 帧内恒定，这是「看起来平滑」的必要条件。
6. `frac_x/frac_y` 仍是死输出 ⇒ 还没有双线性插值；但旋转分支的小数**已经在数据里**
   （`rot_xs` 的低 16 位），接上只是"别再把 `fx` 强制清 0"，不是定点不够。
7. `zoom_en` 自 V7.7 起接 `gpio_o[17]` ⇒ 串口 `ZOOM0/1` 有效（`set_src.tcl` 相应改写
   `0x00030000`，否则上电默认就不呼吸了）。
8. 两键同按时 **+1° 优先**；长按无连发。
9. 三角表 default 都是 0 ⇒ `cos` 的 default 与 0° 恒等不一致，是潜在隐患。
10. **V7.7：旋转只属于右半窗**，左半窗是未旋转原画面；`rotate_mapper` 因此不再被例化，
    换回 4 个 DSP48 + 182 LUT，WNS 还更好（+0.408 → +0.540）。
11. 右半窗的"缩放 + 旋转"是**先转再缩**（`zoom_mapper` 里 `xr_m*inv` 再 `>>>16`），
    两者同中心可交换，所以 RTL 顺序和报告文字谁先谁后不影响结果。
