## 1. PS 固件的边界：它到底做了什么

`src/ps/main.c` 只有 162 行，头 7 行就写明职责边界：
**PS 只做 UART 命令 + AXI GPIO，UDP 视频数据面全部在 PL 的 `rtl/eth/*`**（`main.c:1-7`）。

一个可以拿来当证据的细节：全文 include 的头文件是
`xparameters.h / xil_printf / xil_io / xil_cache / xil_exception / xuartps / sleep`
（`main.c:8-17`）—— **没有任何 XEmac、lwIP、socket 头，也没有一次网络调用**。
所以「这块板子里的软件跟网络有关吗」这个问题的答案是硬证据级的：**无关**。

`main()` 流程（`main.c:144-159`）：

```
Xil_ExceptionInit → Xil_DCacheEnable → Xil_ICacheEnable → Xil_ExceptionEnable
→ 打印 [BOOT] → Xil_Out32(GPIO_TRI, 0) → ctrl_apply() → 三条 BOOT 提示
→ while(1) uart_poll()
```

没有中断、没有定时器、没有 OS、**没有复位任何硬件**。
PL 侧复位完全由硬件自己解决（上电计数器 → `eth_rst_n`，`system_top.v:98-102`，约 168 ms）。

⚠️ 那次 `Xil_Out32(GPIO_TRI, 0)`（`main.c:150`）是**空操作**：
GPIO IP 配的是 `C_ALL_OUTPUTS=1`（`build_system_axigpio.tcl:47-52`）⇒ 方向寄存器不可编程。

开机第一次 `ctrl_apply()` 写出的字是 **`0x00025000`**
（由 `cur_en=0 / cur_thr=80 / cur_src=0 / cur_zoom=1` + 拼装式 `main.c:28-36` 得）——
**与 JTAG 流程写的 `0x00010000` 不同**：前者阈值 80、源=彩条；后者阈值 **0**、源=视频。
这个差异会带来真实的困惑（见 §3.4）。

## 2. AXI GPIO：地址、通道、位分配

| 项 | 值 | 证据 |
|----|----|------|
| IP | `axi_gpio:2.0`，`C_GPIO_WIDTH=32`、`C_ALL_OUTPUTS=1`、`C_INTERRUPT_PRESENT=0`，**单通道** | `build_system_axigpio.tcl:47-52` |
| 地址 | `0x41200000`（range 64K），由 `assign_bd_address` 给的默认段 | `main.c:24`、`set_src.tcl:8,13` |
| 寄存器 | `+0x00` = DATA（唯一有效）；`+0x04` = GPIO_TRI0（全输出 IP 下无效） | `main.c:25-26` |
| 物理路径 | PS `M_AXI_GP0` → `axi_gp0_ic` → `axi_gpio_0/S_AXI`，都在 `FCLK_CLK0` 100 MHz | `build_system_axigpio.tcl:79-82,28,59-68` |
| 到 RTL | `gpio_io_o` → 外部化改名 `GPIO_0_tri_o` → `design_1_wrapper` → `wire [31:0] gpio_o` → `pl_video_top` | `build_system_axigpio.tcl:97-102`、`system_top.v:77,44,161-165` |

位分配（`system_top.v:164` 是权威）：

| 位 | 含义 | 消费者 |
|----|------|--------|
| `[4:0]` | `effect_en`：bit0=gray、1=binary、2=blur、3=sobel、4=invert | `effect_ctrl` 3 级 → `proc_pipeline` 按位旁路 |
| `[15:8]` | `threshold`（二值化阈值，默认 80） | `effect_ctrl` → `proc_binary` |
| `[16]` | `src_sel`（0=彩条 1=视频） | 3FF 同步 → 源 mux、LED1、status |
| `[17]` | `zoom_en` —— **未连接**，`system_top.v:165` 绑 `1'b1` | ⇒ **`ZOOM0/ZOOM1` 是空命令** |
| `[31:18]` | 无人使用 | |

跨钟性质：GPIO 在 `clk_fpga_0`(100M) 域、被 `clkout0_1`(50M 像素) 域采样。
`effect_ctrl` 的 `en_meta/en_sync` **没有 `ASYNC_REG`**（`effect_ctrl.v:12-13`）
⇒ 方法学报告点名一处 TIMING-10「Missing property on synchronizer」
（`build/methodology.rpt:35,938-941`）。对比：`pl_video_top.v:91,225,273,294,314,468`、
`frame_commit_lock.v:61,68,117`、`ddr_bank_commit.v:50` 全都打了属性 —— 就这一处漏了。

## 3. UART 行协议（115200 8N1）

### 3.1 接收与解析优先级

轮询 `XUartPs_IsReceiveData` + `RecvByte`（`main.c:86-87`），行缓冲 `static char buf[32]`，
遇 `\n`/`\r` 结束（`:84-88`）。解析是**自上而下的 else-if 链**（`:92-133`）：

| 优先级 | 形式 | 规则 | 陷阱 |
|--------|------|------|------|
| 1 | **位串** `00111` | 逐字符只接受 `'0'/'1'`，遇 `\r\n空格` 停止，**最左 = bit0**，最多 5 位 | `000000`（6 位）**不是命令**；空串也不是 |
| 2 | `SRC0`/`SRC1` | `strncmp(...,4)` **前缀匹配** | `SRC1xyz` 也会被接受 |
| 3 | `ZOOM0`/`ZOOM1` | `strncmp(...,5)` | 硬件里无效（§2） |
| 4 | `TH<十进制>` | `strncmp(buf,"TH",2) && idx>2` + `atoi(buf+2)`，钳 0..255 | `TH80abc` 解析成 80（atoi 行为） |
| 5 | `FILL` | PS 直写 DDR 诊断图 | 只在**网线拔掉**时才可能上屏（§3.5） |
| 6 | `STAT` | **只回显软件影子值**，不读硬件 | 名字容易让人以为在读 PL |
| 7 | 其他 | 回显 `[CMD] <行>` + 帮助列表 | |

⚠️ `main.c:136`：第 32 个字符之后的字符被**静默丢弃且不 flush 缓冲**
⇒ 一条超长垃圾行的前 31 个字符仍会被当命令解析。〔推断〕

上位机侧：115200 8N1、命令后自动补 CR+LF（`HOST_GUIDE.md:128-131`）；
`serial_ctrl.py:100,102` 的 `q/quit/exit/help/?` 是 **PC 侧解释**，板端会落「未知命令」。

### 3.2 效果位序（三处独立确认，值得背）

`gray / binary / blur / sobel / invert`，**bit0 = 最左字符**：
- `proc_pipeline.v:3-4`（且 `:24-28` 证明 `bypass = ~effect_en[i]` ⇒ 位=1 开启）
- `HOST_GUIDE.md:149`、`report/ARCHITECTURE.md:149`
- OSD 的 `EN=` 第一个字符打 `effect_en[0]`（`osd_overlay.v:102-106`）
- 软件模型：`sim/tb_uart_decode_bits.v` 就是 `parse_bits` 的 Verilog 复刻

所以串口 `00111` = 开 blur+sobel+invert、关 gray/binary。

### 3.3 四个 setter 都是「改影子 + 全字重写」

`ctrl_set_en`（`:42-46`，掩 0x1F）、`ctrl_set_thr`（`:48-52`）、`ctrl_set_src`（`:54-58`）、
`ctrl_set_zoom`（`:60-64`）⇒ **任何命令都重写整个 32 位控制字**，不存在按位更新。
好处：不会读到半更新状态；坏处：只要有一个字段被脚本改过，就会被下一次串口命令冲掉。

### 3.4 一个真实会踩的坑：`set_src.tcl` 把阈值清 0

`build/tcl/set_src.tcl:8` 写 `0x00010000` ⇒ `src_sel=1`、`effect_en=0`、**`threshold=0`**。
此时若用串口发 `01000` 开二值化，会得到**阈值 0 = 全白**，
而 RTL 复位默认是 80（`effect_ctrl.v:16-22`）。
〔结论〕JTAG 直控路径与 PS 固件默认值不一致，排障时先确认 GPIO 现值（`puts [mrd ...]`）。

### 3.5 `FILL`：PS 唯一一次直接改帧内存

`main.c:107-127`：以 `FRAME_W=512/FRAME_H=300/FRAME_ADDR=0x10000000`（`:19-22`）
循环写 `512*300` 个 u16，图案是「上 8 行绿、左上红、右上黄、左下蓝、其余白」
（`:113-122`），然后 `Xil_DCacheFlushRange(0x10000000, 307200)`（`:125`）并 `ctrl_set_src(1)`（`:126`）。

**它写的正是 PL 的乒乓 bank0**（`BANK0=0x1000_0000`，`eth_udp_video_top.v:55-56`）
⇒ FILL 与入包写入抢同一块内存。

它能不能上屏，取决于**片源仲裁当前把搬运机判给谁**：PS-FILL 的消费路径是
`axi_frame_writer64`，其 `enable = eth_mode ? 1'b0 : src_sel`、
`frame_start = eth_mode ? 1'b0 : ps_frame_start`（`pl_video_top.v:406-407`），
而 `eth_mode` 现在就是 `src_arb` 输出的 `owner_eth`（V7.9#25 之前它是 3FF 后的粘性命
`eth_link` = "自配置以来收过任何一个包" ⇒ 只要跑过一次推流，PS 片源就永久被排除，
`FILL` 只能在拔了网线时验证，这正是 ISSUES #47/#49 的那笔账）。

⇒ 现在 `FILL` 的正确用法仍是「验证 PS→DDR→HP0→BRAM→HDMI 这条回读链是否活着」，
但**不需要再拔网线**：没有推流时仲裁会自己归 PS（`owner_eth` 复位为 0；线插着但不流时
`stall_ms` 在 200 ms 内越过阈值、再等 20 ms 滞回；线拔着时 `eth_tb_ok` 直接判"这句话不可信"，
不必等那个慢下来的计数器）⇒ 量级是**几百毫秒**，build#24 板级已看到"插着线 FILL 上色块"。

## 4. 上位机工具链（Node，不是 Python）

**为什么是 Node**：`HOST_GUIDE.md:213-214` 写得很清楚 ——
判据类工具用 Node 写，是因为验收 PC 上不一定有 python。这台机器上确实如此
（Node v24、无可用 python）。

三种与板子通话的方式：
- **UDP**：`video_sender.mjs`、`udp_sink_check.mjs`、`ingress_probe.mjs`（发包半边）
- **JTAG/xsdb 子进程**：`ddr_verify.mjs`、`ingress_probe.mjs`；GPIO 写由 `set_src.tcl` 承担
- **串口**：只有 Python 的 `serial_ctrl.py`（.mjs 里没有任何串口代码）

### 4.1 `video_sender.mjs`（225 行）—— 推流 + 图案生成器

| 开关 | 默认 | 备注 |
|------|------|------|
| `--ip/--port/--src` | `192.168.1.10 / 5001 / 192.168.1.100` | bind 失败退回默认路由（`:155-158`） |
| `--fps` | 15 | |
| `--no-pace` / `--pace-mpbps` | 限速 **15 MB/s** | 帧内逐包匀速：`performance.now()` + `Atomics.wait` + 尾部忙等（`:160-175`），**因为 15 MB/s 下每包只有 ~93 µs 预算，`Date.now()` 的 1 ms 精度不够** |
| `--count` | — | 发完**等 2000 ms 才关 socket**（`:208-216`），否则 `--count 1~2` 的短测会把大部分包丢在内核 tx 队列里 |
| `--test` | `bars` | 8 种图案，见 §5 |
| `--dump` | — | 落盘**最后两帧**（`<file>` 与 `<file>.prev`，`:200-203`）—— 正好对应乒乓的两个 bank |
| `--mtu-payload` | 1392 | **只为复现 bug 而存在**（`:22`）；非 8 倍数会打印警告 |

协议：每包 `[u32 LE byte_offset][RGB565 载荷]`，`HDR=4`，一帧 307200 B ⇒ 221 包（`:199`）。

### 4.2 `measure_v63.mjs`（43 行）—— 一条命令完成复验

`node src/host/measure_v63.mjs --fps 15 --count 200`
= 推 `frameid` → **发完** → JTAG 回读两个 bank → 包内相位丢字签名。

**「先停流再回读」这条规则值得单独记**（`:5-6`）：回读要几秒，
边推边读会让每个地址段读到不同时刻的帧 ⇒ 命中率统计全部作废
（注释里举的证据：「bank0 帧号跨度 130..152 就是这么来的」）。
`--live` 是唯一例外：边推边读、6 秒后 kill 自己起的 PID，
**明确只用于看 16bit 粒度探针，不看命中率**（`:8-9,28-33`）。

`--count` 默认 `ceil(fps*4)+20`（`:20-23`）；推流退出后 `Atomics.wait` 500 ms「让最后一帧落位」，
再跑 `ddr_verify.mjs --frameid`，最后无条件跑 `ddr_stale.mjs`（`:35-42`）。

### 4.3 `ddr_verify.mjs`（261 行）—— 回读与三种分析

常量：`WORDS=38400`、`BANK0=0x10000000`、`BANK1=0x10080000`、`CHUNK=1000`
⇒ 每 bank 76800 个 u32，分 77 次 `mrd -force`（`:17-20,34`）。

生成的 tcl 里有**三条硬规则**（`:36-56`）：

1. `targets -set -filter {name =~ "*#0"}` 选 A9#0；
2. **`catch {rst -processor}` + `after 200`** —— 因为 Vitis 应用开了 D-Cache，
   `mrd` 走 A9 端口会读到缓存里的旧数据；复位并**暂停**核心可以连 MMU/Cache 一起关掉，
   而 DDR 控制器保持已初始化（`:40-44`）；
3. **故意不 `con`** —— A9 一跑回 boot ROM 就会把 SD/QSPI 里的**旧 bitstream 刷回 PL**（`:53`）。

三种分析模式：

| 模式 | 判什么 | 关键输出 |
|------|--------|----------|
| 默认 `wordid`（`:69-116`） | 期望 `u32 = v\|(v<<16)`，`v=((w>>1)+ADD)&0xffff`；不匹配分成 `never`(值=0，从未写) / `stale`(上一轮残留) / `other` | 空洞按 16 行一组归档；末尾「入包链无空洞 / 有空洞」 |
| `--frameid`（`:167-219`） | 反解帧号 `n = (lane − w64) & 0xffff` | 帧号跨度、**同一字内两 lane 帧号不同的字数**、按字位置分 10 段的「新帧占比」、`mixedBands/seamBands` |
| `--ref <file>`（`:136-164`） | 与 `--dump` 的最后两帧逐 32bit 比对 | 某 bank 与「最后一帧」mismatch=0 ⇒ 撕裂在**显示侧**；两 bank 都不匹配 ⇒ DDR 里就是两帧逐字混合，去查乒乓切换 |

**`--frameid` 模式有一个必然的假警报**：`hit` 永远为 null、`refs` 为空
⇒ 结尾必然打印「两个 bank 都没读到有效 wordid 图案：帧没有写进 DDR」
（`:249-261`；实证 `data/measured/board_measure_15fps.txt:23`，
而同一次测量上面两行却是 100.0%）。判据不受影响，但读日志的人会被误导。

### 4.4 其它三个工具的用途与现状

| 工具 | 用途 | 现状 |
|------|------|------|
| `ddr_stale.mjs` | **判据核心**：输入上次 `ddr_verify` 落盘文件，产出三维丢字签名 | 可用；文件头注释仍写老路径 `build_v6/_ddr_dump.out` |
| `ddr_holemap.mjs` | 早期定位用：逐 lane 打 0/1 位图 + 坏游程直方图 | ⚠️ 不带参数时因 `MEASURED` 未 import 而 `ReferenceError`（`:11-23`） |
| `ingress_probe.mjs` | **定点注入**：只发 K 个包、等 1.5 s、读回前 K×174 个 64bit 字，统计「从第几个字开始丢」 | ⚠️ **一加载就崩**（`:13-20` 同样漏 import）⇒ 目前只能当文档读 |
| `udp_sink_check.mjs` | 本机环回自检（`127.0.0.1:5001`），按 `offset==0` 切帧，判每帧字节数**恰好 307200** | 可用；但声称的「按 offset 查缺洞」是假的：`cur.offs` 这个 Set 只写不读（`:35`），实际只有字节总数判据 |

`ingress_probe` 的价值在被崩之前说明过一次：仿真里 `tb_v6_pingpong` 得到过
「端口被独占 N 拍 ⇒ 丢字起始位置恰好等于打包器 FIFO 深度 512」这个对应关系
（`skill/frameid_loss_signature.md:30-31`）—— 这是「用注入长度反推缓冲深度」的思路，
比看命中率更能定位问题。

## 5. 八种测试图案各判什么（这是本工程的精华之一）

| `--test` | 图案 | 判据 | 证据 |
|----------|------|------|------|
| `bars`(默认) | 8px 横纹滚动 + 每帧右移黄块 + 左边缘 8 列奇偶行洋红/黑 | 黑横纹=丢行；方块拖影=换帧不原子；左边缘标记=行序错乱 | `:11-13,134-151` |
| `grad` | `(x+2n, 2y, 128)` 缓变渐变 | 量化/色带 | `:14,141-142` |
| `edge` | 整屏逐帧**黑白交替** | 换帧原子性：非原子会看到灰行/残影 | `:15,135,139-140` |
| `blocks` | 四象限大色块 + 1~2px 参考线 + 每帧左移 6px 黄块 | 纯色场不该有噪点 ⇒ 屏上椒盐点必为真实数据问题 | `:104-121` |
| `hold` | **与帧号无关**的图案 + 方块固定居中 + 蓝象限 1px/32 白网格 | 两帧相同却仍撕裂 ⇒ **问题在显示通路**；干净 ⇒ 之前的撕裂来自图案运动 | `:84-103` |
| `move` | 白象限内往返的**红块**(270..410 永不触边) + 蓝象限 4px 粗网格 | 重影/拖尾=换帧不原子；4px 粗网格不再闪 ⇒ 之前 1px 细线闪烁是最近邻走样而非数据问题 | `:52-71`；板上验收项 `board/README.md:58` |
| `wordid` | 第 w 个 64bit 字填 `w+add` | 只能验地址映射；`--wordid-add` 用来区分「真丢了」和「上一帧碰巧写过同样值」 | `:122-132` |
| `frameid` | 第 w 个字填 `w+帧号` | **唯一能发现「逐帧丢字」的图案**；定量测换帧滞后与逐字混合程度 | `:73-82` |

**核心设计思想一句话**：像素值同时编码了**地址**与**时间**。
`w` 由回读地址可推知，所以 `value − w` 就是帧号。
反过来说：**任何恒定图案（纯色、棋盘、固定渐变）在结构上就发现不了逐帧丢字**
（`skill/frameid_loss_signature.md:12`）—— 这是我在这个工程里学到的最值钱的一条测试设计原则。

注意 `wordid/frameid` 每个 64bit 字内 4 个 lane 写同一个值 ⇒ 分辨率是 64 bit；
16bit 粒度的丢字靠比较同一 u32 的两个半字来暴露（`ddr_verify.mjs:176-183`）。

## 6. 构建与烧写流程

### 6.1 规范入口只有一个：`build/tcl/build_system_axigpio.tcl`

149 行、13 步（详见 `report/`，这里只挑关键）：

- 器件 `xc7z020clg484-2`、RTL 按目录全量 glob + 单独追加 `pl_video_top.v`/`system_top.v`
  ⇒ **`pl_demo_top.v` 有意不进系统工程**（`:12-18`）。
- PS 预设逐项手配、`apply_board_preset "0"`（`:21-25`）：
  `FPGA0=100 MHz`、`USE_M_AXI_GP0=1`、`USE_S_AXI_HP0=1` 且 **HP0 位宽 64**、
  UART0 MIO10..11、ENET0 MIO16..27、**`EMIO_GPIO_ENABLE=0`**、
  **DDR 颗粒 `MT41K256M16 RE-125`（32 Bit 总线 / 16 Bits DRAM 宽度）**（`:27-45`）。
- `axi_mem_intercon/S00_AXI` 外部化并改名 **`M_AXI_HP0`** —— 这就是 PL 写 DDR 的端口（`:86-89`）。
- **不设任何实现策略**（全文无 `set_property strategy` / `STEPS.*`）⇒ 走 Vivado 默认 `impl_1`。
- 产物：`build/system.bit`、`build/system.xsa`，报告
  `timing_summary.rpt`、`utilization.rpt`，以及 `catch` 包住的
  `cdc.rpt / methodology.rpt / power.rpt / route_status.rpt / clock_util.rpt`（`:138-143`）。
  ⚠️ `catch` ⇒ **报告失败不会让构建失败**，所以 CI 式门禁必须另判报告文件是否存在。

### 6.2 上板三件套（顺序不可换）

```
ps_jtag_boot.tcl  →  program_pl.tcl  →  set_src.tcl  →  推流  →  回读
```

- `ps_jtag_boot.tcl`：`ps7_init.tcl` 路径三级回退（`$PS7_INIT` → `argv[0]` → glob）；
  `targets -set 1` + `rst -system` + `after 3000`；`ps7_init` + `ps7_post_config`；
  **自检** `mwr 0x10000000 0x5A5AA5A5` 再 `mrd` 打印 `DDR_ECHO:`；最后 `con`（`:12-46`）。
  注释 `:6-8` 说明一件重要的事：**只有 FSBL 会写 SLCR 里的 `FPGA_FCM*`（HP 通道缓冲）**，
  ps7_init 的 tcl 版不含 ⇒ 所以 `board/README.md:27-29` 补「交付态请用 Vitis Run ELF 启动；
  **性能类结论应以 FSBL 启动为准**」。
- `program_pl.tcl`：`connect_hw_server -allow_non_jtag` → 先打印链上器件 →
  按 `PART =~ "xc7z020*"` 选器件（**选 xc7z020 而不是 arm_dap**）→ `PROGRAM.FILE` → `program_hw_devices`。
- `set_src.tcl`：`stop → mwr -force 0x41200000 0x00010000 → puts [mrd ...] → con`。
- 回读脚本**不 con** ⇒ 每轮回读后 A9 停在复位态，**下一轮必须重跑三件套**。

### 6.3 构建脚本里埋的雷（读代码前必须知道）

| 雷 | 后果 |
|----|------|
| `build_system.tcl:113-114,193,209` 与 `fix_bd_and_top.tcl:57,156,159` 会 **`puts` 重新生成 `src/rtl/top/system_top.v`**，而且是 **640×360 老几何 + EMIO GPIO** | 与规范入口混用会**静默毁掉现网 RTL** |
| `apply_cdc_report.tcl:2`、`rebuild_opt.tcl:2`、`rebuild_cdc_fix.tcl:2`、`rebuild_zoom_out.tcl:2`、`sim/run_zoom_only.tcl:1` 硬编码另一台机器的工作区路径 | 不可直接用 |
| `crit_path.tcl` **文件本身已损坏**（首行是别机绝对路径，3-5 行残留字面量 `\]`） | 无法解析 |
| `board/README.md:19` 让用户跑 `build_v6.tcl`，而该脚本**有意不入库** | 文档指向不存在的文件 |
| `build/tcl/README.md:5-8` 速查表还在推荐已废弃的 PL-only 链与 `output/` 目录 | 陈旧文档 |
| 若干脚本首字节带 UTF-8 BOM；`create_project.tcl:38,98` 有 mojibake（`鈥?`） | Windows 下 Vivado 能eat，但属隐患 |

**这条清单本身就是「可复现构建」的价值**：仓库里能一键重建的入口只有一个，
其余同名脚本是历史化石，必须能在 5 秒内分辨出来。
