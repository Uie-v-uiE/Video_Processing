# 模块详解 03 · 显示帧缓存与光栅几何

> 概念铺垫：[前置知识 09 BRAM/LUTRAM 与综合推断](../00_前置知识/09_BRAM_LUTRAM与综合推断.md)、

## 1. 为什么需要一块「显示 BRAM」而不是直接从 DDR 显示

三个理由，都是量出来的：

1. **延迟确定性**。逆映射（旋转/缩放）每拍要一个像素，DDR 访问有几百 ns 的抖动，
   而且 HP0 还要同时服务入包写。BRAM 是**同步 1 拍读**，正好接得住 50 MHz 的像素流。
2. **端口冲突**。入包写和显示读要抢同一份 DDR 带宽。把「当前显示帧」搬到 BRAM 之后，
   读侧完全不占 DDR，写侧只剩每秒一次的整帧搬运（在消隐期做）。
3. **撕裂可控**。显示侧只读 BRAM，而 BRAM 只在消隐期被写 ⇒
   「屏幕上永远是某一整帧」由结构保证，不依赖调度。见
   [模块详解 02](../03_模块详解/02_DDR乒乓与提交锁.md) 的不变量 I1。

## 2. `frame_buffer_w64`：两块 2 的幂换 48 个 BRAM tile

### 2.1 问题：非 2 的幂深度的代价

512×300 需要 38400 个 64 bit 字。直接声明 `reg [63:0] mem[0:38399]` 时，
综合器推断 BRAM 会把地址空间**向上填满到 2 的幂**：38400 → 2^16 = 65536 个字 ⇒
65536 × 64 bit = 4 Mb = **128 个 RAMB36**（全片只有 140）。数据本身只需 67 个 tile，
多出一倍。

### 2.2 做法

```verilog
// frame_buffer_w64.v:25-37
WORDS = (W*H+3)/4 = 38400;  D_LO = 32768;  REM = 5632;  D_HI = 8192;
(* ram_style="block" *) reg [63:0] lo [0:32767];
(* ram_style="block" *) reg [63:0] hi [0: 8191];
```

拆成两块 2 的幂阵列：32768 + 8192 = 40960 字 = 2.62 Mb = **80 个 RAMB36**（对比 128）。
总容量富余 6.7%。

这不是「猜出来的」，是**探针实验**测出来的：`sim/probes/fbtest.v` 里放了 6 个变体
（v0 单阵列 / v1 深度写成 65536 / v2 写成两个 2 的幂 / v3 加 `ram_style` / v4 改 32bit 宽 / v5 分块+32bit），
每个单独综合、只读 `report_utilization` 的 RAMB36 数：

| 变体 | RAMB36 | 结论 |
|------|--------|------|
| v0 单阵列 38400 | **128** | 基线 |
| v1~v3（写法/属性变体） | 128 | **与深度声明写法无关**，是「地址空间被取到 2^16 个字」决定的 |
| v4 32bit 宽单阵列 | 64 | 位宽减半 ⇒ tile 数减半（但需要 2 个阵列或读拼接） |
| v5 **分块 32768+8192** | **80** | 采纳 |

完整表见 [版本演进 03](../04_版本演进/03_优化的方法论.md) §探针实验。
教训：**「加个 `ram_style` 属性就好了」这类直觉在这里是错的**，必须逐个变体综合去看报告。

### 2.3 地址映射与延迟

| 口 | 时钟 | 地址单位 | 映射 |
|----|------|----------|------|
| 写 | `axi_clk` 100M | **64bit 字索引** `widx[18:0]` | `wr_hi = widx>=32768`、`w_off = widx-32768`（`:43-44`） |
| 读 | `clk_pix` 50M | **像素号** `rd_addr[18:0]` | `ridx = rd_addr[18:2]`、`lane = rd_addr[1:0]`（`:55,68`） |

一个 64bit 字里装 4 个 RGB565，`{p3,p2,p1,p0}`（`:18`）。

**读延迟 = 模块内 1 拍**（`:64-70`）：一个**无复位**的 `always @(posedge rd_clk)` 里
两块阵列**每拍都读**（越界一侧地址被夹住，不会产生 X，注释 `:53-54`），
同时打拍 `sel_hi / sel_lane / blank`；组合的 2:1 + 4:1 mux 在 `:72-81`。
加上 `pl_video_top.v:359-367` 的 `rd_addr_q` 一级 ⇒ **从逆映射输出到 `fb_rd` 共 2 拍**。

> 为什么「两块都读 + 寄存选择位」而不是「用 mux 选一块读」：
> 后者会让选择位进入 BRAM 地址通路，读延迟变成 2 拍或者根本推不出 BRAM。
> 这个「双读 + 寄存 mux」的写法保住了 1 拍契约，代价是多 8192 字的动态功耗。〔推断〕

### 2.4 越界保护是两道

1. **写侧**：`if (wr_en && widx < WORDS)`（`:47`）⇒ **越界写被忽略**（不会回卷到地址 0 污染开头）；
   `hi` 侧索引还额外 `& (D_HI-1)` 掩码（`:48`）。
   `sim/tb_fb_roundtrip.v` 专门验「越界写不污染」。
2. **读侧**：`blank <= (rd_addr >= W*H)`（`:69`）+ `assign rd_data = blank ? 16'd0 : lane`（`:82`）
   ⇒ **越界读回黑**。顶层还有第二道：`oob_fb → oob_fb_d1 → pix_left/right` 里
   `oob_fb_d1 ? 16'h0000 : ...`（`pl_video_top.v:398-401`）。

### 2.5 没有任何读写仲裁

写口 `wr_clk=axi_clk`、读口 `rd_clk=clk_pix`，同一套阵列两套时钟、**无握手无仲裁**。
正确性 100% 外包给消隐门控（`pl_video_top.v:3-4` 头注释就是这个契约）。
这是一个**有意的架构赌注**：如果哪天窗口逻辑被改坏，就会直接看到撕裂，
而不是「数据偶尔错一像素」。所以 `copy_overrun`→LED 那条粘滞告警必须保留。

顶层还有一条补偿：

```verilog
// pl_video_top.v:294-305
ac0/ac1 = allow_copy 的 2FF（ASYNC_REG）
if (!ac1) fb_pix_hold <= fb_rd;                 // 窗口打开前最后一拍锁住
fb_out = (ac1 && !de_d[11]) ? fb_pix_hold : fb_rd;  // 只在拷贝机可能碰 BRAM 的消隐期保持
bram_or_hold = eth_link ? fb_out : 16'hF800;    // 只有无链路才红屏
```

⇒ **有效期内永远显示活的 BRAM**，只有消隐期才用锁存的最后一个像素。

## 3. 光栅与几何

### 3.1 时序发生器

`video_timing_1024x600.v:17-26`：H 1024+44+88+188 = **1344**，V 600+3+6+16 = **625**，
`H_POL=1`、`V_POL=0`。帧率 = 50e6/(1344×625) = **59.52 Hz**〔推断，由参数算〕。
`video_timing.v:63-67` 把 x/y/de/hs/vs **全部寄存一拍**输出（所以它们与 de 同槽），
`frame_start = de_act && h_cnt==0 && v_cnt==0`（`:68`，1 拍宽），
`frame_done` 在最后一行最后一列（`:69`，顶层未接）。

### 3.2 双窗几何

```verilog
// pl_video_top.v:111-113
PANE_W = 512;                                  // system_top.v:161 传入
left_pane = (x < 512);                         // 左窗 x=0..511，右窗 x=512..1023
cx = left_pane ? x : x - 512;                  // 两窗各自源 x = 0..511
cy = ((y>>1) < 300) ? (y>>1) : 299;            // 丢掉 y 最低位 = 垂直 2× 最近邻放大
```

**源图 512×300 显示成 512×600**：垂直方向每个源像素扫两行、无插值；
消隐期（y≥600）被夹到最后一行 299 ⇒ 不产生越界读。
〔后果值得知道：模糊/Sobel 的**垂直方向邻居在交替的两拍里是同一个源行**，
详见 [效果链](../03_模块详解/05_效果链.md) §5。〕

### 3.3 三岔的像素选择

| 窗 | 路径 | 流水级数 |
|----|------|----------|
| 左（不旋转） | `cx_q3/cy_q3` 纯延迟 | 3 拍（与 mapper 对齐） |
| 左（旋转） | `rotate_mapper` | 3 级（`rotate_mapper.v:25-28/32-37/45-64`） |
| 右（恒走） | `zoom_mapper` | 3 级（`zoom_mapper.v:31-36/42-55/76-96`） |

选择器 `fb_sel_right = ~left_d[2]`（`:351`，2 = 与两个 mapper 同槽），
`sx_fb/sy_fb/oob_fb` 三选一（`:352-354`）。

**行距被硬编码**：

```verilog
// pl_video_top.v:363
rd_addr_q <= {sy_fb[8:0], 9'b0} + {7'b0, sx_fb};   // = sy*512 + sx
```

⇒ 只有 `IMG_W=512` 时地址图才对；`sy_fb[8:0]` 也只能表达到 y=511。
这是「改分辨率」时最容易漏的一处（见 [文件地图](../02_架构/03_模块与文件地图.md) §4）。

### 3.4 `split_display` 的优先级

```verilog
// split_display.v:28,32,42-47
sep = (x == 511) || (x == 512);                 // 中缝 2 列
if (sep && de)  {r,g,b} = {8'h40,8'h40,8'hFF};  // 蓝：优先级最高
else if (oob)   黑
else            选中的像素
// RGB565 → RGB888 扩展：r={r5,r5[4:2]}、g={g6,g6[5:4]}、b={b5,b5[4:2]}
```

中缝那两列**永远是蓝**，不受源、不受越界影响 —— 文档里没写这条优先级，
但代码里 `sep` 的判断在 `sel` 之后覆盖它。`y` 与 `angle_idx` 两个输入在体内未使用。

### 3.5 延迟对齐（**这块是全文最容易读错的地方**）

从 `clk_pix` 到 TMDS 编码前的总深度：

```
逆映射(3) → rd_addr_q(1) → BRAM(1)          = 5 拍到 pix_left/pix_right
        → proc_pipeline(PROC_LAT=7 手写) ‖ 左路 7 级 skid
        → de_d[11]/x_d[11]/y_d[11]           = 11 拍到 split_display 输入
        → split_display 输出寄存(1)
        → osd_overlay(1)
                                            = 共 13 拍到 rgb2dvi
```

三处不一致（都在代码里，都不致命，但都会让你以为「对齐了」的时候错开几个像素）：

1. **`PROC_LAT = 7` 与真实列延迟不符**。逐拍数五个效果是 **9 拍**
   （1+1+3+3+1），⇒ 右窗效果像素与它的越界黑边在列方向差 2 个像素。
   详见 [效果链](../03_模块详解/05_效果链.md) §4。
2. **`de_in/x_in` 与 `din` 差 1 拍**：进 `proc_pipeline` 的是 `de_d[3]/cx_d[3]/cy_d[3]`
   （4 拍前），而 `din=pix_right` 是 5 拍前（`pl_video_top.v:410-419`）。
   `pipe_de` 接出来了但**没人读**。
3. **彩条两条链不同深**：左路 `bar_l_d4`（4 拍，合计 5 拍，正好等于 BRAM 读路），
   右路只取 `bar_r_d2`（2 拍）⇒ 右窗彩条比右窗视频晚 1 拍。
   8 条 64px 竖条 + 32px 对角暗纹（`color_bar.v:20-37,52-54`）下肉眼看不出。

〔推断〕`PROC_LAT=7` 是在板上标定出来的经验值 —— 因为效果链内部
（`proc_box_blur.v:65-72`、`proc_sobel.v:53-66`）的 de 与数据通道各有不同的安排，
净延迟不等于各模块标称值之和。**这也解释了为什么它「看起来不对」但板子上成立**。
