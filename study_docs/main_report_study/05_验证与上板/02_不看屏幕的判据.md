# 验证与上板 02 · 不看屏幕的判据（frameid 签名法）

> `board/README.md:31` 把「不看屏幕的复验」写成本项目的**主要验收手段**。
> 这篇讲它为什么必要、怎么成立、什么时候会失效。
> 通用技能版在 `skill/frameid_loss_signature.md`。

---

## 1. 为什么必须放弃屏幕

屏幕判据有三个不可克服的问题：

1. **不可复现**。「有一点拖影」不能进回归表；同一个人两次看也会给出不同结论。
2. **不可归因**。屏幕上的一条黑线，可能是入包丢了字、可能是换帧不原子、
   可能是显示拷贝越窗、可能是最近邻缩放的走样。**它们看起来很像。**
3. **不可量化**。修一版之后「好多了」不是证据。

而且第 2 条在这个工程里真实发生过：一开始所有排查都在往显示侧走
（`frame_commit_lock`、消隐窗、`split_display` 都改了个遍），
根因却在**入包写 DDR 的吞吐**上。如果只有屏幕，就不会有那次方向纠正。

## 2. 核心技巧：让像素值同时携带**地址**和**时间**

```js
// src/host/video_sender.mjs:73-82   --test frameid
第 w 个 64bit 字的 4 个 16bit lane 全写 (w + n) & 0xffff     // n = 帧号
```

于是板端 DDR 里任意一个 16bit 位置都满足：

```
n_implied = (lane_value − w64) & 0xffff        // ddr_verify.mjs:176-177
w64 = (addr − bank_base) / 8                   // 回读时地址已知
```

**这一个式子同时给出三个维度**：

| 维度 | 问的问题 | 能区分什么 |
|------|----------|-----------|
| 时间 | 这个字是第几帧写的？ | 换帧是否原子（每 bank 帧号跨度 = 1 = 原子） |
| 空间 | 哪些字没写/写错了？ | 是整行缺、还是零散洞、还是尾部缺 |
| 相位 | 洞在**包内**的哪个字节区间？ | 是「一开始就不够快」还是「缓冲区满了才开始丢」 |

对照实验：`wordid` 图案（值 = 字号，不含帧号）**只能验地址映射**。
它验不出「这一帧真丢了」还是「上一帧碰巧写过同样的值」——
所以 `--wordid-add` 存在，专门用来打散这种巧合。

**推论（值得背）**：任何恒定图案（纯色、棋盘、静止渐变）在结构上就发现不了逐帧丢字。
我一开始用彩条和渐变找黑点，找了很久，因为图案本身没有携带时间信息。

## 3. 三条 JTAG 硬规则（违反任何一条，数字就是假的）

| 规则 | 为什么 | 证据 |
|------|--------|------|
| **先停流，再回读** | 回读要几秒；边推边读会让每个地址段读到**不同时刻的帧**，命中率统计全部作废 | `measure_v63.mjs:5-6`（并自证「bank0 帧号跨度 130..152 就是这么来的」） |
| 必须 `rst -processor` | Vitis 应用开了 D-Cache，`mrd` 走 A9 端口会**读到缓存里的旧数据**；复位并暂停核心连 MMU/Cache 一起关掉，DDR 控制器保持已初始化 | `ddr_verify.mjs:40-44` |
| **绝不能 `con`** | A9 一跑回 boot ROM 就把 SD/QSPI 里的**旧 bitstream 刷回 PL** ⇒ 你测的已经不是这一版 | `ddr_verify.mjs:53` |

副作用要记住：回读脚本不 `con` ⇒ 每轮之后 A9 停在复位态，**下一轮必须重跑三件套**
（`ps_jtag_boot → program_pl → set_src`）。

## 5. 三维丢字签名（把症状映射到机理）

`ddr_stale.mjs:5-11` 的文件头就是一张机理对照表：

### 5.1 包内相位分带

```
BANDS = [[0,48],[48,96],[96,192],[192,384],[384,768],[768,1392]]
off = (k*2) % PAYLOAD,   PAYLOAD = 1392（硬编码）
```
**呈固定台阶** ⇒ 下游平均排空速率跟不上（不是随机丢）。
这正是当初定位 V6.3 的那一刀：板上「从第 48 字节起按 16bit 粒度被丢」，
说明**打包器每拍能吞的字节数**是瓶颈，而不是网络丢包（网络丢包不会在包内整齐分带）。

⚠️ 已知局限：`PAYLOAD` 固定 1392 ⇒ 若上一轮用 `--mtu-payload 1396` 发包，分带会整体错位。

### 5.2 连续丢字游程

游程分布 + 最长带 + 「≥696（整包一半）」的段数。
**长游程** ⇒ 端口被长时间独占；**短而均匀** ⇒ 逐字覆盖问题（例如 `WSTRB` 恒 0xFF 时
分包非 8 倍数造成的半截字互相覆盖，表现为**均匀散布的黑点**，1396 B 实测每帧 111 处）。

### 5.3 粒度：同一 u32 内两个 16bit 是否同帧

不同 ⇒ 丢在 **16bit 粒度**（CDC/写侧门控），不是整 64bit 字（打包器）。
这一条把「谁在丢」的候选集合直接砍掉一半。

### 5.0b 第五件量具：让失败行自己报出**几何量**（2026-09-24 #50 的教训）

前面四把刀都是"主动去量"，这一条是"失败的时候必须开口"。写法固定四类量：

| 类别 | 例子（`sd_play.c` 的 `[SDRD!]`） | 为什么必须有 |
|---|---|---|
| 想去的位置 | `lba=536959104`、`n=32` | 没有它，只能猜"是不是被挤到" |
| 这个位置怎么来的 | `clus=16778886`、`data_lba=34816`、`spc=32` | 有它才能把**上游解析**接上，反算核对 |
| 合法边界 | `part_end=62332928` | 不写边界，"越界"这个判断不可复核 |
| 当场分类 | `OUT-OF-RANGE` / `IN-RANGE` | 一句话把"数据位置错"与"时机错"分开 |

判定规则：**同一位置必失败 ⇒ 先怀疑空间（地址/索引/字段解析），后怀疑时间（并发/时序）**。
"只在某个位置之后才发作"这种选择性，时间类解释原理上就给不出 —— 它解释不了边界为什么是那个位置。
#50 就是活例：两晚的时间类假设（并发挤超时、控制器被留在半途、RXC 被拉慢）都不算错到离谱，
但它们**都解释不了"为什么恰好是第 3584 帧"**；一行打印十分钟内就结案了。

配套纪律（不然判据是空的）：**新加的判据必须能红**。做法是把缺陷改回去重下一版，
看它是不是真的报警（这次是 `cluster decode SELF-TEST failed`）。见 `02_不看屏幕的判据.md` §8 的失效条件。

### 5.4 定点注入（`ingress_probe.mjs` 的思路）

只发 K 个包、等 1.5 s 排空、读回前 `K×174` 个 64bit 字（1392/8=174），
统计**从第几个字开始丢**与丢失间距 ⇒ **直接暴露缓冲深度**。
仿真侧的对应结论：`tb_v6_pingpong` 里「端口被独占 N 拍 ⇒ 丢字起始位置恰好等于
打包器 FIFO 深度 512」。
⚠️ 该脚本目前**一加载就崩**（`ingress_probe.mjs:13-20` 用了 `MEASURED` 但没 import），
所以这套方法现在只能手工复现，不能一键跑。这是记在案的技术债。

## 6. 实测金样怎么读（`data/measured/board_measure_15fps.txt`）

条件：`--test frameid` 200 帧 @15 fps、pace 15 MB/s、一帧 221 包、实测 ~15.1 fps。

| 读数 | 含义 |
|------|------|
| bank0 主导帧号 **f198 = 153598/153600 lane** | 这个 bank 基本是**一整帧** ⇒ 换帧原子 ✅ |
| `同一字内两 lane 帧号不同的字数 = 0` | 没有 16bit 粒度混写 ✅ |
| 含多个帧号的 16 行组 = 1/19，次要帧号占比 >12% 的组 = 0 | 唯一的"多帧"组是残留，不是逐字混合 |
| **最新帧 16bit 命中率 100.0%** | 入包链无损 |
| **包内六带丢字率全 0.0%** | 没有相位性丢字 |
| 连续丢字带 1 段 / 共 2 个 16bit 字 / 最长 2 / ≥696 段数 0 | 就是那个已知残留 |
| bank1 主导 f199 | 乒乓：上一帧在另一个 bank ✅ |
| 帧号跨度里出现 **f27137** | **不是噪声**：`27137 = (0 − 38399) & 0xffff`，即最后一个 64bit 字读到 0x0000 |

那条「2 个 lane 读到 0」= 帧的最后 4 字节偶发未落位，**下一帧同地址即被覆盖**，
肉眼不可见，`tb_v6_ingress_integrity +FULL` 也不复现（`board/README.md:49-51`）。
把它写进文档而不是删掉，是为了将来判据变化时能对上账。

**同时注意 `--frameid` 模式下有一行必然的假警报**：
「两个 bank 都没读到有效 wordid 图案：帧没有写进 DDR」（`ddr_verify.mjs:249-261`，
实证 `board_measure_15fps.txt:23`，而上面两行却是 100.0%）。
**读日志要按判据表读，不要按最后一行读。**

## 8. 判据的失效条件（必须一起背）

`skill/frameid_loss_signature.md:34-40`：

1. 平台**无法回读内存**（没有 JTAG/没有 debug module）⇒ 整套方法不可用；
2. 从 CPU 侧读而 **D-Cache 开着** ⇒ 读到旧数据，全部结论反了；
3. 载荷长度不是 8 的倍数 ⇒ 包内相位与打包器半截字状态**混叠**，分带解释失效；
4. **只能判数据完整性，不能判画质**：颜色映射错、缩放取整偏差、效果算错，这些方法看不见；
5. 图案必须逐帧变化；静止图案结构上发现不了逐帧丢字。

## 9. 仍需肉眼的 6 项

判据法不能替代全部：SRC0 彩条无横纹、`--test move` 红块无拖影、
`--test blocks` 网格不被逐字空洞打断、OSD 的 `eth=`/`net_bad=` 递增、
停流后冻结帧干净、拔线 30 s 再插自动恢复（`board/README.md:53-62`）。

其中 `hold` 图案是专门设计的**二分工具**：它两帧完全相同，
所以「仍然撕裂」⇒ 问题在**显示通路**；「干净」⇒ 之前的撕裂来自图案运动
（`video_sender.mjs:84-103`）。**一次实验把两个候选机理分开**，这类图案值得专门设计。
