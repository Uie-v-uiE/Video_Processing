# 验证与上板 03 · 上板流程与踩坑清单

> 按「一次完整复验」的时间顺序写，每一步都注明**为什么这个顺序不能换**、
> 以及出错时先看哪里。环境事实（本机）附在最后。

---

## 1. 全流程（顺序不可换）

```
① 构建：build_system_axigpio.tcl   → build/system.bit + system.xsa + 7 份报告
② 起 PS：ps_jtag_boot.tcl <ps7_init.tcl>   （DDR + FCLK0=100 MHz）
③ 配 PL：program_pl.tcl                     （选 xc7z020 器件，不是 arm_dap）
④ 写控制字：set_src.tcl                      （GPIO 0x41200000 = 0x00010000）
⑤ ping -n 2 192.168.1.10                     （0% 丢包 = PL 网络栈活着）
⑥ node src/host/measure_v63.mjs --fps 15 --count 200     （推流→停→回读→签名）
⑦ 需要串口时：Vitis 里 Run ELF（main.c）
```

### 为什么 ② 必须在 ③ 前

HP0 通路要 PS 的 DDR 控制器**已经初始化**才可能写进去；
`ps7_init` 做的就是 MIO/PLL/DDRC 的配置。先配 PL 会让入包链一开始就往未初始化的地址写。

### 为什么 ③ 选器件要 `PART =~ "xc7z020*"`

JTAG 链上有两个目标：`arm_dap`（PS 的调试端口）和 PL 的 FPGA。
program 必须落在 **PL** 上；`program_pl.tcl:13-22` 先把链上器件全打印一遍再按 PART 选，
就是为了不在选错目标时静默失败。

### 为什么 ④ 之后不能直接测出「交付态」性能

`ps_jtag_boot.tcl:6-8` 的注释指出关键差异：
**只有 FSBL 会写 SLCR 里的 `FPGA_FCM*`（HP 通道缓冲）**，ps7_init 的 Tcl 版不含这些寄存器。
所以 `board/README.md:27-29` 补了一句：
**交付态请用 Vitis Run ELF 启动；性能类结论应以 FSBL 启动为准。**

> 2026-09-23 更正（ISSUES #42/#44）：这句里"**必须**用 Vitis 才能跑 PS 应用"那半句不成立 ——
> 当时跑不起来是因为手工链接的镜像缺了标准启动（没人开 CPACR/VBAR/MMU），不是 JTAG 路径的固有限制。
> 现在 `xsdb build/tcl/ps_app_reload.tcl` 纯 JTAG 就能起 app（`[BOOT]` 横幅、SD 挂载、30 fps 回放都验过）。
> 但**性能口径**那半句仍然有效：`FPGA_FCM*` 只有 FSBL 会写，所以要报"交付态性能"仍然该固定启动路径。

这条很重要：JTAG 直灌 bit 的工况下 HP0 缓冲配置可能与 SD/QSPI 启动不同，
「在 JTAG 工况下量到的余量」不一定等于交付工况的余量。

### ③ 之后 PS 会复位

`README.md` 的「下载 bit 后 PS 会复位，需再次 Run ELF，串口才有效」——
现象是「bit 下去了、屏亮了、串口不回话」，属正常，重跑 ELF 即可。

## 2. 三条回读硬规则（重复一遍，因为它最重要）

| 规则 | 违反后的**错误结论**长什么样 |
|------|------------------------------|
| 先停流再回读 | 「命中率 42%」——其实是你读的时候帧还在变 |
| 必须 `rst -processor` | 「bank1 是空的」——其实是 A9 的 D-Cache 在骗你 |
| 绝不能 `con` | 「这版 bit 有问题，还是丢字」——其实 boot ROM 已经把旧 bit 刷回去了 |

配套事实：`set_src.tcl` 写 `0x00010000` 会**顺带把 threshold 清成 0**（RTL 复位默认是 80）
⇒ 这时开二值化会得到全白。想改回 `SRC0` 就写 `0x00000000`（`set_src.tcl:6-7`）。

## 3. `ps_jtag_boot.tcl` 里的一个自检，值得单独表扬

```tcl
mwr -force 0x10000000 0x5A5AA5A5
puts "DDR_ECHO: [mrd -force 0x10000000]"     # :42-45
```

**在配 PL 之前先证明「PS 能读写 DDR 的那个 300 KB 区域」**。
如果 `DDR_ECHO` 不对，后面所有的「丢字」都不必查 PL。
另外 `targets -set 1` + `rst -system` + `after 3000`（`:29-32`）是为 DAP 卡住
（APB AP transaction error）准备的：**先系统复位再配**。
`ps7_init.tcl` 路径三级回退（`$PS7_INIT` → `argv[0]` → glob `*/platform/*/hw/ps7_init.tcl`），
找不到就报错退出，不静默继续。

## 4. 屏幕之外的可观测出口（按可信度排序）

| 出口 | 内容 | 可信度 |
|------|------|--------|
| JTAG 回读 DDR | 逐字命中率、帧号跨度、相位签名 | ★★★★★（可量化） |
| `ping` | ARP + ICMP 活着 | ★★★★★ |
| **`led[0]` 心跳频率** | 正常 `hb[24]` ≈ **1.5 Hz**；发生过 V-blank 拷贝越窗则 `hb[22]` ≈ **6 Hz 快闪**（粘滞，只有 `axi_rst_n` 能清） | ★★★★（把「撕裂风险」变成可观察事件） |
| `led[1]` | `src_use`（当前显示的是彩条还是视频） | ★★★ |
| OSD 三行 | `FPS=` / `ANG=` / `EN=` | ★★（要拍照/采集才有证据） |
| 肉眼看画面 | 8 项肉眼清单 | ★（但不可替代） |

**`led[0]` 那条是这套流程里性价比最高的设计**：
一个粘滞位 + 一个 LED，就把「拷贝有没有越过消隐窗」变成不需要上位机、
不需要回读、随时可查的事件。做 FPGA 板级调试时值得模仿。

`pl_video_top.v:249-254,516-517` 是它的实现；
50 MHz 下 `hb[24]`/`hb[22]` 的半周期分别约 0.336 s / 0.084 s。

## 5. 踩过的坑（按症状查）

| 症状 | 真因 | 对策 |
|------|------|------|
| TB 超时、什么都没打印 | `#20_000_000_000` 被当 32 bit 截断成 2.82 ms | 写 `#(64'd...)` |
| 「8 个字里恰好 1 个对」 | AXI 从机用了寄存后的 AW 地址，同拍 W 写到上一个突发 | 从机 `cur_addr = (awvalid&&awready) ? awaddr : awaddr_r` |
| 「8 个字里恰好 1/8 对」 | TB 喂的是字节地址，端口单位是半字索引 | 看端口注释，别猜 |
| `xelab` 报找不到 design unit | `xvlog` 那步已经失败但被忽略 | 先看 xvlog 输出；或 `SIM_ONLY=1` 单独编 |
| xsim 打印 usage 就退出 | `+key=value` 直接传给 xsim | 用 `--testplusarg key=value` |
| 构建中途 `ERROR: [Common 17-217] Failed to load feature 'core'` | **内存压力**（本机只有 ~2.7 GB 空闲），不是 RTL 问题 | 等负载降下来重跑同一脚本；别去查设计 |
| `connect` 成功但 `targets`/`mrd` 报 `Invalid target` | `hw_server` 没起来（xsdb 的裸 `connect` 不总会自动拉） | 手动起 `Vivado/bin/hw_server`（这个名字**没有 .exe**），等几秒 |
| xsdb 脚本里 `mrd addr N` 什么都没有 | 脚本模式只回显 `puts` 的内容 | `puts [mrd ...]` |
| 屏上出现**均匀散布的黑点** | 分包长度不是 8 的倍数 + 旧的 `WSTRB=8'hFF` | 用 1392；v6.4 起硬件已免疫（按 16bit lane 生成 WSTRB） |
| 屏上出现**移动的黑条** | 缺行（丢包）+ 缩放动画把洞带着走 | 看 OSD `net_bad` 是否递增，再回读判据 |
| 帧号跨度 130..152 | **边推边读** | 先停流 |
| 串口不回话但屏是亮的 | 刚下过 bit，PS 复位了 | 重新 Run ELF |
| `git push` 报 `Everything up-to-date` 但其实没上去 | 代理请求实际失败 | 用 `ls-remote` 复核 |

## 6. 本机环境事实（省得每次重新发现）

- **器件/板**：RK-ZYNQ7020-F `xc7z020clg484-2`，12 V 供电，HDMI 1024×600。
- **线缆**：FTDI FT4232（JTAG + 一个 VCP = **COM6** @115200），USB-C 到板。
- **网络**：网线接**板卡 PL 网口（PHY2）**，PC `192.168.1.100/24` @1 Gbps，板 `192.168.1.10:5001`。
- **工具链**：`D:/Software/Vivado/2025.2.1/` ——
  `Vivado/bin/vivado.bat`、`Vitis/bin/xsdb.bat`、`Vivado/bin/hw_server`（无 `.exe`）。
- **Python**：这台机器上 `python`/`py` 曾经只有商店 stub；
  现在 `D:\DevEnv\...\python.exe` 实测可用（2026-09-22 验证 `python -c` 正常）。
  **但判据工具仍统一用 Node（v24）**，因为
  `HOST_GUIDE.md:213-214` 的理由依然成立：验收 PC 上不一定有 python。

  `sed -i` 的分隔符里带 `&` 会静默改错 —— 用编辑工具。

## 7. 「复现性」本身是一项要测的性质

2026-09-21 在一份**干净克隆**上直接跑规范入口（连 `vivado_system/` 工程目录都是它现建的），
得到的资源与时序和开发工作位一致：
Slice Registers 54588（51.30%，那是 R02 之前的数）、Block RAM 138.5/140（98.93%）、
WNS +0.708 / WHS +0.064 / WPWS +0.264、115065 端点 0 违例、`All user specified
timing constraints are met.`、0 Critical Warning。
完整记录在 `report/CHANGELOG_V6.md` §3。

**bit 文件不会逐字节相同**（布线种子与时间戳不同）——
所以「复现」的判据是**报告里的数字**，不是文件的 hash。
