# 04 时序与资源的读法：怎么从 Vivado 的报告里问出"该动哪一手"

> 这一篇不讲概念史，只讲**手上的动作**：给你一份 Vivado 报告，怎么读出下一步该改什么、
> 以及怎么避免读出三个最常见的假结论。所有数字都是从本仓库真跑出来的，路径都能自己点开对。
> 前置：`00_前置知识/` 里"一个时钟周期里发生什么"那篇就够了。

## 一、一条 setup 路径的块里，每行是什么

拿本设计真出现过的一条（r87，`build/r87_timing_summary.rpt` 第 366 行起）：

```
Slack (MET) :             0.152ns  (required time - arrival time)
  Source:      u_eth/u_cdc/wbin_reg[0]/C        ... clocked by eth_rxc {period=8.000ns}
  Destination: u_eth/u_cdc/mem_reg_0/ENARDEN    ... clocked by eth_rxc
  Data Path Delay: 7.236ns  (logic 2.467ns (34.091%)  route 4.769ns (65.909%))
  Logic Levels:    8  (CARRY4=5 LUT4=2 LUT5=1)
```

- **Slack**：还差多少 / 还剩多少。`MET` 是正的，`VIOLATED` 是负的。**只有这一行不能告诉你该干什么。**
- **Source / Destination**：起点是哪一个触发器的哪个脚，终点是哪一个单元（这里是 BRAM 的
  `ENARDEN` = "使能"脚，不是数据脚）。**终点是什么，决定这件事的性质**：
  终点是 `D`/`CE` ⇒ 你在改逻辑；终点是 `ENARDEN`/`ADDRARDADDR` ⇒ 你在改"存储器的控制"，
  而存储器摆哪儿是布局器决定的。
- **Requirement 8 ns**：`eth_rxc` 是 125 MHz（RGMII 的接收时钟），一拍就 8 ns，很紧。
- **logic vs route 的分配**：**这一项才是选杠杆的依据**。
  `logic 34 % / route 66 %` 意思是大头在"绕线走路"，不在"算得慢"。
  把算术改短最多买到那 34 %，把两个模块挪近才买得到 66 %。
- **Logic Levels: 8 (CARRY4=5 …)**：穿过几个单元层。`CARRY4` 是加法器的形状 —— 看到 5 个 CARRY4
  就该想到"这里有一串进位链"。本例那 3 级就是 `wbin + 1'b1` 与二进制转格雷的移位/异或。

下半段那一大列（`Delay type / Incr / Path(ns) / Netlist Resource`）是**逐拍足迹**：
`Path(ns)` 是累计时刻，`Incr` 是这一步花掉多少。读法是从上往下找**最贵的两三步**：

```
wbin_reg[0]/Q      →  net routed 1.396   → CARRY4 ...  → b1_in__0[10] net routed 0.845
→ full_d_reg_i_1/CO[0] → net u_eth/u_reasm/wr_full 0.603
→ u_reasm/mem_reg_0_i_1/O → net u_cdc/wr_en routed 1.557 (fo=9) → RAMB36 的 ENARDEN
```

三个信号在这里：**出了 `u_cdc` 走到 `u_reasm`，再折回来当 BRAM 的使能**（一来一回各 0.6 + 1.6 ns）；
`fo=9` 是扇出 9（8192×36bit 要用 9 块 BRAM，使能得同时喂给它们）。
所以这一条的毛病有两个来源：算术挂在了使能上，以及这个使能要横跨一片区域跑一个来回。

## 二、本仓库在这一条上真的走过两次弯路（比方法论有用）

| 我当时的假设 | 做了什么 | 结果 | 学到什么 |
|---|---|---|---|
| "终点扇出 9 太高，复制一下缓冲就近了" | 给 `wr_full` 加 `max_fanout=12` | WNS −0.062 → **−0.192**，失败端点 28 → 34 ⇒ **回滚**（#105 第一刀） | **没读 logic/route 分配就动手，会把设计改差**。扇出高 ≠ 扇出是瓶颈 |
| "瓶颈不是扇出，是那条 14 位加法→格雷→比较的锥体" | 写下结论，去修工具 | 把 `build/tcl/crit_path.tcl` 修到能跑之后实测：**6 级逻辑、route 占 71 %** ⇒ 后半句错（#121） | **结论也要有测试**。我修的是"读结论的那把尺子"，结果它推翻了我自己 |
| 第三刀（r88）：把满判据从 `wgray_n`（下一个写指针）换成 `wgray`（当前写指针），使能锥里不再有加法 | 先造一条会红的判据（新台架对**旧树**跑）再改源 | 同一把尺子的族计数：r85 的 8 条最差里 6 条是这一族，r88 是 **0 条**，级数 7 → 4 | **能报的是"归属变了"，不是"WNS 涨了 0.364 ns"** —— 0.4 ns 是本设计实测过的摆放抖动 |

一句话总结：**每次动手前先问"我这一步会改变上面哪一格"**。改不了任何一格的动作就是抽奖。

## 三、"资源被谁吃了"——四行 Tcl 就能问出来

`report_utilization` 只给总数（本设计：Slice LUT 14358 / 26.99 %，其中 `LUT as Distributed RAM` 4044；
Block RAM Tile 95 / 67.86 %）。总数不告诉你该省哪儿。把**叶子单元按名字前缀分组数一遍**：

```tcl
# 只对**已经布线完的 dcp** 问；只读，不写任何产物
open_checkpoint <你的 impl_1/system_top_routed.dcp>
foreach grp {RAMB36E1 RAMD64E MUXF7 FDRE} {
  set d {}
  foreach c [get_cells -hier -filter "REF_NAME == $grp"] {
    set a [join [lrange [split [get_property NAME $c] /] 0 1] /]   ;# 取到二级层次
    set i [lsearch -exact $d $a]
    if {$i < 0} { lappend d $a; lappend d 1 } else { lset d [expr {$i+1}] [expr {[lindex $d [expr {$i+1}]]+1}] }
  }
  foreach {k v} $d { if {$v >= 100} { puts [format "  %-9s %6d  %s" $grp $v $k] } }
}
```

本仓库跑出来的真数（`build/r88_resource_owners.txt`）：

```
RAMB36E1      80  u_pl/u_bilin        ← 93 块里 80 块就是那一帧 512×300×RGB565 显示缓存
RAMD64E      928  u_eth/u_saver       ← 打包器 FIFO：100bit × 512 格
RAMD64E      864  u_pl/u_blur         ← 3×3 效果链的四个窗口级合占 2912 个 = LUTRAM 的 72 %
RAMD64E      864  u_pl/u_sharp
RAMD64E      768  u_pl/u_sobel
RAMD64E      416  u_pl/u_morph
```

读到这张表之后，"还能省什么"就变成**两个可以验证的问题**，而不是"再挤挤看"：

1. **这些存储器是承重的还是余量？** 用台架量过载时的峰值占用：
   线速连灌下打包器 FIFO **512/512 填满**、CDC **8192/8192 填满**（`build/r88_packer_peak_gap0.txt`）
   ⇒ 两者都是**填满的**，削深度等于砍掉过载吸收 ⇒ 不做。
   （这一步的判据是"探针必须见过非空"：如果一条探针永远是 0，它要么接错名，要么这个模型里根本没压力，
   那"没问题"这句就没有意义 —— 见 `05_验证与上板/02_不看屏幕的判据.md`。）
2. **有没有一份数据被存了两遍？** `u_saver` 每格存 `{地址32, 数据64, 有效4}`。
   地址看着能从序号算出来，但读代码判掉了（`src/rtl/eth/axi_frame_saver64.v:91-94`）：
   存的是**绝对**地址，而 `pack_base` 会在一帧中途换基址 ⇒ 队列里还有旧条目时序号对不上。
   所以真正的大杠杆只剩一个：把效果链从"×2 展开之后"挪到"之前"（行宽从 1024 变 512，四个窗口级一起减半）——
   **但那是换效果**（3×3 核的半径、梯度、连通域尺寸都跟着变），不是换参数，本仓库选择不做并写明原因。

## 四、三个最常踩的误读（每一个我本人都踩过）

1. **把 WNS 的绝对差当收益**。同一条路径两次构建差 0.4 ns 是常态。
   要报就报"归属/形状/计数"这类噪声做不到的事：哪个族从几条降到几条、级数从几到几。
2. **把 `n/a` 当通过**。聚合判据（`build/gates.sh`）里"今天没法判"的分支不判红是对的，
   但如果结论行只数红绿，"两项主台架压根没跑"也会念成 `ALL PASS`。
   现在这一行必须带范围：`判定 18 项全过，但有 2 项因缺凭据未判 ⇒ GATES: PARTIAL`。
3. **把 `PROBE` 当判据**。`PROBE cdc peak_occupancy=…` 只是打印，改坏设计它也不会红。
   每一个你想相信的数，旁边要有一条会红的判据（`PASS/FAIL` 行），并且那条判据要有"改前必须红"的记录。

# 2) 想知道某一版构建的门禁读数（可以直接指到隔离构建的目录）

## 六、附：怎么判断"跑了十几分钟没输出"的台架是死是活

台架**只在每条判据结束时打一行**，中间那些"多跑几帧再统计"的阶段可以十几分钟一声不响。
区分"在算"与"挂住"的办法不是等，也不是猜，是量 CPU 时间有没有在涨：

```powershell
# 两次之间睡 6 秒：delta 接近 6 s ⇒ 一整个核在满算，就是在跑
powershell -NoProfile -Command "$a=(Get-Process xsimk).CPU; Start-Sleep 6; $b=(Get-Process xsimk).CPU; $b-$a"
```

本仓库今天实测到的一个真实例子：顶层台架跑到"帧头/缝旁黑列"那一段时 14 分钟没有新行，
但 CPU delta 是 5.9 s / 6 s ⇒ 在算。同一次跑里另一条线索是**判据计数**：
`grep -c '^PASS' run.log` 从 31 → 45，说明它确实在推进，只是不快。

⚠ 别做的事：看到没输出就 `taskkill`。`run_one.sh` 的头部注释写了为什么 ——
`xsim.exe` 只是外壳，真正在写 `run.log` 的是 `xsimk.exe`，杀掉外壳会留下一个继续往同一份日志里
写行的孤儿内核，下一跑就会把两跑的行混在一起（这份报告就是这么废过一次，而它头部 md5 全对）。
