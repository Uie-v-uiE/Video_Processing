# 03 · 几何变换：逆映射、旋转、缩放与定点数

> 本工程"任意角旋转 + 连续缩放 + 窗滤"能同时成立，靠的就是这一篇的三个想法：
> **逆映射**、**Q 格式定点数**、**目标域窗口**。

---

## 1. 为什么用逆映射而不是正映射

| | 正映射（源→屏） | **逆映射（屏→源）** |
|---|---|---|
| 做法 | 遍历源像素，算它落到屏幕哪里 | 遍历屏幕像素，反算它来自源哪里 |
| 问题 | 目标点会**留空洞**（旋转后不是每个屏幕格都被打到），还要处理写冲突 | 每个屏幕格**必然**有一个源值 |
| 硬件 | 需要随机**写**帧缓存（多端口/仲裁） | 只需随机**读**帧缓存（单口即可） |
| 缩放 | 放大时留洞 | 放大时自然插值 |

**结论：显示侧是"逐格光栅扫描 + 反查源图"，所以帧缓存只需要一个读口。**
本工程的 `rotate_mapper` / `zoom_mapper` 都是这个模式：
输入是屏幕坐标 `(cx, cy)`，输出是从 `frame_buffer_w64` 读到的那个像素。

## 2. 旋转的数学

以图像中心 `(cx, cy)` 为轴心，把屏幕点 `(x, y)` 反旋转 θ 回到源图：

```
sx = cx + ( (x−cx)·cosθ − (y−cy)·sinθ )        （正向旋转的逆变换是 −θ）
sy = cy + ( (x−cx)·sinθ + (y−cy)·cosθ )
```

硬件形态（Q8 定点，见下一节）：

```
dx = x − cx            // 有符号，约 ±512
dy = y − cy            // 约 ±300
sx = cx + (dx·cos_q − dy·sin_q) >> 8
sy = cy + (dx·sin_q + dy·cos_q) >> 8
```

需要 **4 次乘法 / 像素**。用 DSP48 就是 4 个（或时分复用 2 个）；
本工程 `utilization.rpt` 里 `DSPs = 13/220`，左右两窗 + 缩放合计 13 个，
说明它没有把乘法省到极限，而是**用 DSP 换时序余量**（这是合理取舍：DSP 极空闲）。

### sin/cos 怎么来：查表

```
angle ∈ [0, 359]（整数度） → ROM 查 sin(angle)、cos(angle)，Q8（−128..127）
```
- `rotate/sin_rom.v`、`rotate/cos_rom.v`：360 项 × 8 bit ⇒ 2880 bit，一个 BRAM 都装不满；
- 因为 `cos(θ) = sin(90°−θ)`，其实一张表就够，本工程存了两张 ⇒ **用 1 个 tile 换掉一级减法与地址翻转逻辑**（**推断**：这是典型取舍，具体以代码为准）；
- 角度步进 1° ⇒ 不是"任意实数角"，但 360 档在视觉上连续，
  按键 `+1°/−1°` 环绕（`rotate/angle_ctrl.v`）。

### 中心与宽高不是 2 的幂时

1024×600 的中心是 (512, 300)，源图 512×300 的中心是 (256, 150)。
**中心取整会带来半像素偏移**，旋转 180° 时如果中心算错，整幅图会平移 1 像素——
这类"旋转后画面偏一格"的 bug 全部出在这里。本工程有专门的 TB
（`sim/tb_rotate_window.v`、`tb_rotate_mapper.v`）来钉这个对齐。

## 3. 缩放：Q8 倒数刻度

本工程缩放用**倒数**表示，很聪明：

```verilog
// src/rtl/process/zoom/zoom_mapper.v:3（文件头注释）
// inv_scale Q8: 256=1.0x（原始，最大），512=0.5x（缩小）。3 级流水，可与旋转叠加。
// :10
input wire [9:0] inv_scale,   // Q8, 256=1.0, up to 512=0.5x
```

为什么用倒数？因为**逆映射需要"每前进 1 个屏幕像素，源坐标前进多少"**：

```
源坐标增量 = 1 / scale = inv_scale / 256
```
用 `inv_scale` 时，屏幕坐标累加就是 `src += inv_scale`（整数加法 + 移位），
不需要除法。若用 `scale` 本身，每拍都要做一次除法 ⇒ 硬件上不可行。

- `inv_scale = 256` ⇒ 1.0×（原始尺寸，最大）
- `inv_scale = 512` ⇒ 0.5×（缩小一半，四周留黑边）
- 中间 256 档连续 ⇒ 所谓"无级/连续缩放"
- `>256` 时源坐标会超出原图范围 ⇒ 边缘 OOB 填黑（`:57` 注释）

**累加器 vs 乘法**：本工程用 `坐标 × inv_scale >> 8`（`:57` 注释「s2: * inv_scale」），
即每轴一次乘法而不是逐拍累加。差别在于：
- 累加器：省一个乘法器，但**误差会随 x 累积**（定点截断误差线性增长）；
- 每点乘法：多一个乘法器，误差**不累积**（每点独立量化）。
在 512 宽、Q8 下，累加器误差最大约 `512 × (1/256) ≈ 2` 像素 ⇒ 不可接受，
所以选乘法是**正确的**（**推断**：代码没有写明这个理由）。

## 4. 定点数与 Q 格式：一页讲清

### 4.1 什么是 Qm.n

把二进制点固定在某位之后：`Q8` 表示低 8 位是小数。

```
0x0100 (256) = 1.0        0x0080 (128) = 0.5        0x0200 (512) = 2.0
```

乘一个 Q8 数：`结果 = (整数 × Q8值) >> 8`。
所以"乘 0.5"= `×128 >>8`，"除 3"= `×85 >>8`（85≈256/3）。

### 4.2 三个必踩的坑

1. **位宽增长**：`a[15:0] × b[7:0]` 结果 24 bit。右移 8 位后仍有 16 bit，
   若再相加就会溢出 ⇒ **必须先算总位宽再决定在哪里截断**。
   本工程 `zoom_mapper` 里 `wire signed [10:0] inv = $signed({1'b0, inv_scale});`（`:26`）
   就是在做符号扩展，避免有符号乘法把 10 bit 的 512 当负数。
2. **有符号**：sin/cos 有负值 ⇒ 必须 `signed`，且 `$signed()` 要作用在**已经扩好位宽**的向量上。
   一个常见的错是 `$signed(a) * $signed(b)` 其中 a 是 unsigned wire —— 符号位就丢了。
3. **截断 vs 舍入**：`>>8` 是**向下截断**（对有符号数是向 −∞ 取整），
   会让整体偏暗/偏移半像素。要四舍五入就加 `(1<<7)` 再移位：
   ```verilog
   y = (acc + 32'sd128) >>> 8;     //  round-half-up
   ```
   **注意算术右移 `>>>` 与逻辑右移 `>>` 对有符号数的区别** —— 这是图像硬件里最经典的单字符 bug。

### 4.3 本工程哪里能看到这些

| 位置 | 内容 |
|------|------|
| `zoom_mapper.v:3,:10,:26,:57` | Q8 `inv_scale`、符号扩展、`* inv_scale` 的那一级流水 |
| `rotate_mapper.v` + `sin_rom/cos_rom` | Q8 三角、`dx·cos − dy·sin` 的四乘两加 |
| `proc_gray.v` | 加权和的定点系数（见 01 篇） |
| `proc_box_blur.v` | ÷9 的定点实现（见 02 篇） |

具体算式逐行核对见 [模块详解 · 旋转与缩放](../03_模块详解/02_DDR乒乓与提交锁.md)（同目录下）。

## 5. 最近邻 → 双线性：下一步该付多少代价

本工程目前是**最近邻**（取整坐标直接读一个像素），所以缩放时能看到 1 px 栅格闪烁
（`V6_ROOT_CAUSE.md` 里明确记着"这不是丢数据，是走样"）。

双线性需要 4 个 taps：`(x0,y0) (x0+1,y0) (x0,y0+1) (x0+1,y0+1)`：

```
O = (1−fx)(1−fy)P00 + fx(1−fy)P10 + (1−fx)fy·P01 + fx·fy·P11
```

**硬件代价分析（本工程的实际条件）**：

| 项 | 代价 | 说明 |
|----|------|------|
| 水平邻点 `P10` | **几乎免费** | 帧缓存一次读出是 **64 bit = 4 个像素**，现在只用了其中 1 个 lane；`x0` 与 `x0+1` 有 3/4 概率在同一个字里 |
| 垂直邻点 `P01/P11` | 需要 **1 行行缓存** | 512×16bit = **1 个 BRAM tile**（当前剩余 ~49 个） |
| 4 个乘法 + 3 个加法 | 2~4 个 DSP48（当前用 13/220） | 或者用移位近似 `(1−fx)` |
| `fx/fy` | **已经算出来了但没用** | 这是本工程留好的接口（`CHANGELOG_V6.md` 记着这条待办） |

⇒ 双线性在本工程是"资源已经备好、只差实现"的改动，
而且它有一个**能不看屏幕验证**的判据：TB 里用 Node 写一个黄金模型算 PSNR/最大误差，
逐像素比对 RTL 输出。这也是把它列为下一轮主线的原因。
