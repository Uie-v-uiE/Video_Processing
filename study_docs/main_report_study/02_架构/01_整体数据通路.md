# 架构 01 · 整体数据通路（主入口）

> 这篇是全套文档的**枢纽**：一张端到端图 + 每一段的展开链接 + 一张关键常量表。
> 只想了解全貌的话，读完这篇就够；要动手改某个模块，再点进对应的 `03_模块详解/*`。

## 0. 一句话概括

上位机用 **UDP** 把 512×300 的 RGB565 画面按「字节偏移 + 载荷」的分包格式推给板卡；
**PL 里自己写的 RGMII/ARP/ICMP/UDP 协议栈**收包、按 offset 拼帧，经跨钟 FIFO 用 **AXI HP0**
写进 DDR 的两个乒乓 bank；显示侧在 **HDMI 消隐窗口**里把整帧从 DDR 原子拷进一块 BRAM 帧缓存，
再用两个 50 MHz 的逆映射通路（左窗原图、右窗缩放）读出、过效果链、叠加 OSD，
最后经 TMDS 编码送到 HDMI 口输出 1024×600。**PS 完全不碰视频数据**，只通过 AXI GPIO
接收串口来的控制字（效果使能、阈值、源选择）。

## 2. 为什么是这个形状（三个设计决定）

### 决定一：网络在 PL 而不是 PS

第一版（分支 `v1-ps-ethernet`）用 PS 的 GEM + lwIP：UDP 收包由 ARM 上的协议栈完成，
再 DMA 到 DDR，PL 用 HP0 把数据读出来显示。这条路**能用**，但视频吞吐被 ARM 的
中断/协议处理绑住，而且「网络—DDR—显示」三者的时序关系由软件调度决定，很难说清。
第二版起改成 PL 自己写协议栈（`src/rtl/eth/` 里 20 个文件、约 2700 行），
PS 退回纯控制面。代价是必须自己实现 ARP/ICMP/UDP 和 RGMII 的采样问题
（见 [前置知识 07](../00_前置知识/07_用硬件写协议栈.md)），
收益是**视频通路的延迟与吞吐完全由 RTL 决定**，也才能做后面那些逐字判据。

### 决定二：DDR 做主存储，BRAM 只做「当前显示帧」

XC7Z020 只有 **140 个 BRAM tile（36 Kb）**。一帧 512×300×16bit = 2.4576 Mb = 66.8 个 tile，
双缓冲 + 行缓存 + 各种协议 FIFO 会直接把片上 RAM 用光（第三版确实试过 `frame_buffer_db`，
记录在 `report/VERSION_LINEAGE.md:56`：资源爆掉、实现失败）。
所以数据落在 DDR（乒乓两个 512 KiB bank），BRAM 只留一份「电子枪正在扫的这一帧」。

但这样一来，「什么时候把 DDR 里的新帧搬到 BRAM」就变成了一个**必须精确回答的问题**：
搬的过程本身要几百 µs，如果搬的时候电子枪正在有效期扫描，屏幕上就会一半新一半旧 ——
这就是最早就出现过的「撕裂/固定位置黑线」。答案是只在消隐期搬，并且用一把「提交锁」
把「新帧就绪」这个事件对齐到消隐窗上升沿。整条设计里最精巧的状态机就是这个：
[模块详解 02](../03_模块详解/02_DDR乒乓与提交锁.md)。

### 决定三：入包用「offset 协议」而不是「按序流」

包里没有帧号、没有包号，只有**这包数据应该落在帧内的第几个字节**。好处：
- 上位机可以乱序发、可以重发，板端不需要维护接收窗口；
- 一个包丢了只影响那一帧，下一帧的 offset=0 包自然把状态清零；
- 拼帧逻辑只是「写地址 = offset」，非常薄。
代价是板端必须自己判断「这一帧到底齐没齐」，于是有了 `frame_reasm` 的
**行覆盖位图 + 字节总量**双门限（`frame_reasm.v:122` 的 `rows_hit>=IMG_H && bytes_ok`）。
为什么一个门限不够，见 [入包链 §5.6](../03_模块详解/01_以太网入包链.md)。

## 4. 数据通路上的四次「形态变换」

看懂这四次变换，就看懂了整条链为什么这么长：

1. **字节 → 半字**：网线上是 8bit/拍的字节流；`frame_reasm` 把两个字节攒成一个 RGB565 像素
   （`pix_lo/have_lo`），因为帧缓存与 DDR 都以 16bit 为最小写单位。
   于是产生了一个永远存在的边界问题：**载荷长度为奇数时最后半个字是「半个像素」**，
   靠 `flush` 标记把这一「半截字」也推给下游（`eth_udp_video_top.v:212-220`）。
   帧尾 4 字节丢失那个 bug 就长在这里 ⇒ [版本演进 02 的问题条目](../04_版本演进/02_问题与修复全记录.md)。
2. **半字 → 64bit 字**：`axi_frame_saver64` 把 4 个 16bit 像素拼成一个 AXI 64bit beat，
   并生成**按 16bit lane 的 WSTRB**（V6.4 之前的 `WSTRB=8'hFF` 会在分包长度不是 8 的倍数时
   把相邻两包的同一个字互相覆盖 ⇒ 屏上均匀散布的黑点）。
3. **DDR → BRAM**：`axi_frame_writer_gated` 在消隐窗内以 16 拍突发把整帧读回，
   经 63 深 skid 缓冲对齐 HP0 的 2 拍读出延迟与 BRAM 的 1 拍写口。
   这里发生的是「地址空间不变、时钟域不变、只改存储介质」，所以关键是**窗口**而不是协议。
4. **BRAM → 屏幕**：像素号 → 字号（`ridx=addr[18:2]`）+ lane（`addr[1:0]`），
   再经效果链、OSD、TMDS 编码、5:1 串化。
   注意这一级里「行的对应关系」被硬编码成 `{sy[8:0],9'b0}`（`pl_video_top.v:363`），
   也就是说 **IMG_W=512 是写死在地址算术里的**，不是靠参数联动。

## 5. 三处「看起来对、其实有分歧」的地方

这套文档之所以存在，很主要是因为下面三条。它们都不是 bug（板子跑得起来），
但如果按文档字面理解就会得出错误结论。

1. **消隐窗到底多宽**：注释与报告都用 67200 个 axi 拍（25 行 × 1344 × 2），
   但 RTL 里的 `VB_X_GUARD=1279`（`pl_video_top.v:209-211`）让最后一行只放行 1280 个像素，
   真实窗口是 **67072** 拍；而判越窗的 `VBLANK_AXI_CYC` 又是 67200
   ⇒ 报警比它监控的窗口**松 128 拍**。〔推断〕这不是错误，是「宁可少报一次」的取值，
   但报告里应当把两个数分开写。
2. **效果链延迟 `PROC_LAT=7`**：`pl_video_top.v:405` 的注释与实现是「7 拍 skid 对齐」，
   但逐拍数五个效果的真实列延迟是 **9 拍**（详见
   [效果链 §4 延迟实测](../03_模块详解/05_效果链.md)）⇒ 右窗的效果像素与它的越界黑边
   在列方向上差 2 个像素。板上不易发现（效果本身是"糊"的、黑边只在缩放空角处出现）。
3. **「ETH 收到完整帧后自动切到视频源」**（`README.md` 串口命令一节、`HOST_GUIDE.md:120`）：
   代码里画面选择只看 `src_use = src_sel_pix`（`pl_video_top.v:289,398-401`），
   `frame_ready_pix → eth_ready` 那条链最终只进了 `status[31:0]`（`:520`），
   而 `status` 在 `system_top` 顶层**没有对应输出端口**（`system_top.v:44`）⇒ 被裁掉。
   也就是说：**自动切换没有实现**，只是「ETH 模式 + 无链路时显示彩条」这一条规则在起作用。
   这条被列在 [版本演进 02 · 文档与代码不一致](../04_版本演进/02_问题与修复全记录.md)。
