# 04 · 存储：BRAM、DDR 与"这份画面到底要多少资源、多少带宽"

> 本工程两次最大的优化（BRAM 从 98.93% 降到 64.64%；拖影根因）都是算术题。
> 这一篇把那些数字一次算清楚，后面所有"够不够"的判断都回到这里。

---

## 1. 先算数据量：一帧到底多大

```
源画面   512 × 300 像素，RGB565 = 2 字节/像素
        = 512 × 300 × 2 = 307,200 字节 = 2,457,600 bit ≈ 2.46 Mb
        = 38,400 个 64bit 字（AXI 一次写一个字）
显示输出 1024 × 600 @ 50 MHz 像素钟
```

**为什么显示 1024×600 但帧缓存只有 512×300？**
因为显示是"左窗原图 + 右窗处理"，且垂直方向做 2 倍复制（`cy = y >> 1`）：
1024 宽被劈成两个 512 窗，600 高每两行取同一行 ⇒ 真正需要存的独立像素是 512×300。
**这是一次很划算的设计取舍：用 1/4 的存储换 1024×600 的输出。**

## 2. 三种存储，三种代价

| 存储 | 在哪 | 容量 | 访问方式 | 适合 |
|------|------|------|----------|------|
| **触发器阵列** | PL 逻辑区 | 每 SLICE 8 bit | 任意读写、异步 | 极小、需要组合读 |
| **BRAM** | PL 块存储 | 140 tile × 36 Kb = **5.04 Mb** | 同步读（地址给出后**下一拍**出数），1~2 端口 | 行缓存、帧缓存 |
| **LUTRAM（分布式）** | PL 逻辑区 | 17,400 个可用 LUT × 64 bit ≈ **1.1 Mb** | **异步读**，1 写 + 1 读 | 中小深度 FIFO、需要当拍读 |
| **DDR** | PS 外挂 | 板载 256 MB（MT41K256M16） | 经 HP 端口，延迟几十~上百拍，带宽共享 | 整帧、乒乓 |

### 本工程实际怎么分

| 用途 | 选择 | 数量 |
|------|------|------|
| 显示帧缓存（2.46 Mb） | BRAM | 分块后 80 tile |
| 入包 CDC（36 bit × 8192） | BRAM | 9 tile |
| 模糊/Sobel 的行缓存 | BRAM/LUTRAM 混合 | 2×RAMB18 + 192 LUTRAM |
| 入包打包 FIFO（100 bit × 512） | **LUTRAM**（第五版起） | ~1100 LUT-RAM 单元 |
| 显示拷贝 skid 缓冲（83 bit × 64） | **LUTRAM**（第五版起） | ~110 单元 |
| 整帧乒乓 | DDR | 2 × 300 KB |

**为什么帧缓存不能放 DDR？** 可以放，但显示每拍都要随机读一个像素（旋转/缩放是乱序读），
DDR 延迟几十拍 ⇒ 必须堆很深的预取，且会把 HP 端口带宽吃光。
所以本工程的结构是：**DDR 存"完整帧"（乒乓），BRAM 存"当前正在显示的那一帧"**，
中间用消隐窗口做整帧搬运。这是所有"视频 + 小 FPGA"设计的标准结构。

## 3. BRAM 用量的算法（以及本工程那个 1.9 倍的坑）

一个 RAMB36 在 36 bit 宽模式下是 `1024 × 36`。所以：

```
需要 tile 数 = ⌈深度 / 1024⌉ × ⌈位宽 / 36⌉      （还要考虑级联的地址译码）
```

显示帧缓存：`38400 深 × 64 bit`
- 理论下限（只看容量）：`2,457,600 bit ÷ 36,864 bit = 66.7` → **67 tile**
- 按上面的式子：`⌈38400/1024⌉ = 38`，`⌈64/36⌉ = 2` → **76 tile**
- **实测：128 tile** ❗

128 这个数怎么来的？`128 = 64 列 × 2`，而 `64 × 1024 = 65536 = 2^16`。
⇒ **综合器把 38400 深的地址空间向上填充到了 2^16**，填充率 `38400/65536 = 58.6%`，
`67 / 0.586 ≈ 114`，再算上端口浪费就是 128。

**这个填充不是"数组声明得不好"能救的。** 第五版做了 6 个变体的 out-of-context 综合实测：

| 写法 | RAMB36 |
|------|--------|
| `[0:38400-1]`（原样） | 128 |
| `[0:65535]`（本来就是 2 的幂） | 128 |
| `[0:38911]`（1024 的整数倍） | 128 |
| 4 个 16 bit 宽 bank 交织（每块仍 38400 深） | 128 |
| 32 bit 宽、38400 深 | 64 |
| **地址空间拆成两个 2 的幂块：32768 + 8192** | **80** ✅ |

结论：**只要单个数组的地址空间不是 2 的幂，就会被填到下一个 2 的幂；
要省，就得让每块数组自己的地址空间正好是 2 的幂。**
38400 = 32768 + 5632，第二块填到 8192，总利用率 `38400/40960 = 93.75%`。

代价是多一级 bank 选择 mux（在读出寄存器之后），换来 **48 个 tile**（34% 的整片容量）。

> 通用教训：算 BRAM 时**先算容量下限，再和报告对比**。
> 报告明显高于下限 ⇒ 一定是写法/结构问题，不是"数据太多"。
> 怎么定位到具体哪个模块吃的：`build/tcl/report_mem_hier.tcl` → `build/util_hier.rpt`（层次化资源报告）。

## 4. 带宽：三个必须会算的数

### (1) 入包侧需要多少
```
RGMII 125 MHz × 4 bit × 双沿(DDR) = 1 Gbps 链路
有效载荷约 15 MB/s（本工程上位机默认限速）
一帧 307200 字节 ÷ 15 MB/s ≈ 20.5 ms/帧 ⇒ 约 48 fps 上限
```

### (2) 入包写 DDR 需要多少
```
打包后每拍最多 8 字节 @100 MHz = 800 MB/s（HP0 64bit 理论上限）
但真正决定吞吐的是"在途深度 ÷ 往返延迟"：
  在途 1 拍 → 8B/40拍 × 100MHz = 20 MB/s   ← 第四版之前的真实上限（拖影根因）
  在途 8 拍 → 64B/40拍 × 100MHz ≈ 160 MB/s ← V6.3 之后，实测约 400 MB/s 量级
```

### (3) 显示读回需要多少
```
每帧 38400 个 64bit 字要在一个消隐窗口内搬完
窗口 ≈ 67200 个 axi 周期（100 MHz）= 672 µs
需要平均 38400/67200 = 0.571 拍/周期 ≈ 457 MB/s（读+写两侧都占 HP0）
```

**把三个数放在一起就理解了本工程的整个矛盾**：
入包平均只要 15 MB/s，但显示读回会在 672 µs 里吃掉几百 MB/s ⇒
**入包侧必须能在这 672 µs 里既不被挤死、又能在挤过去之后把账补回来**。
补回来的能力 = 在途深度（决定补得多快）× 缓冲深度（决定能撑多久）。
第四版之前的失败是"补得太慢"（在途=1），不是"撑不住"（缓冲已经 8192 深）。
所以加深缓冲无效、流水化写通道有效——这就是那篇 `CHANGELOG_V6.md` 里 V6.2 被标注
"方向错误，保留记录"的完整逻辑。

## 5. 乒乓：为什么必须两份、以及为什么放 DDR

如果只有一份帧缓存，UDP 边写、显示边读 ⇒ 读到的永远是"新旧混合"，
屏幕表现为**撕裂 + 拖影**。要消除就必须"整帧原子换"：

- 两份缓冲，一份写、一份读，写完交换角色；
- 交换只能发生在**消隐窗口**（屏幕不采样的时刻）。

放 BRAM 做两份？`2 × 2.46 Mb = 4.9 Mb`，而全片 BRAM 只有 5.04 Mb ⇒
**装得下两份帧缓存，就装不下协议栈、行缓存、CDC 的任何东西**。
这正是第二版 `ISSUES.md #13` 写的"BRAM 双缓冲爆资源，实现失败"。
所以答案是 **DDR 乒乓 + BRAM 显示缓存**：DDR 出两份，BRAM 只留一份。

代价就是第 4 节那笔账：整帧搬运要占 HP0，从而挤压入包 ⇒ 于是有了第四版的全部故事。
