# 10 · Vivado 报告怎么读，以及"门禁"这套做法本身

> 前面几篇讲"怎么造"，这一篇讲"怎么知道自己造对了"。
> 本工程所有结论都必须落到某份报告的某一行上 —— 这套习惯本身就是最值得学的部分。

## 1. 一次实现之后应该看哪几份报告

| 报告 | 命令 | 回答的问题 | 本项目里的路径 |
|------|------|-----------|----------------|

| `power.rpt` | `report_power` | 功耗与结温 | `build/power.rpt` |

## 2. 时序报告的读法：从汇总到那一条路径

### 第一层：Design Timing Summary

```
WNS(ns)  TNS(ns)  TNS Failing Endpoints  TNS Total Endpoints  WHS(ns) ...
  0.499    0.000                       0               30846   0.060 ...

All user specified timing constraints are met.
```

要读的四个数：
- **WNS**（最差建立裕量）：≥0 才叫满足。正数越大越安全。
- **TNS**（累计负裕量）：0 表示没有任何端点违例。
- **失败端点数**：这才是"有没有问题"的真数；WNS 只说"最坏的那个多坏"。
- **最后一行那句话**：`All user specified timing constraints are met.` —— 只有它出现才叫干净。

### 第二层：定位到路径

```
Slack (MET) : 0.499ns
  Path Group: eth_rxc            ← 哪个时钟组（先看是不是自己关心的域）
  Requirement: 8.000ns           ← 周期；100 MHz 域是 10 ns，50 MHz 是 20 ns
  Logic Levels: 11 (CARRY4=6 LUT2=1 LUT3=2 LUT6=2)
  Source: u_eth/u_udp/u_udp_rx/rec_en_reg/C
  Destination: u_eth/u_reasm/rows_hit_reg[0]/CE
  Source Clock Delay: 4.851ns    ← 时钟插入延迟
```

### 第三层：判断"该改 RTL 还是改实现"

把逐行 `net (fo=…) 延迟` 加起来看**线**占多少、把 cell 延迟加起来看**逻辑**占多少。
本工程这条：总数据延迟 7.16 ns 里约 6.4 ns 是线，逻辑只 0.8 ns ⇒
**改 RTL 收益小，应该给布局器更多自由**（换策略、降占用）。
反过来，如果 Logic Levels 高、net 很短，那就是逻辑链太长 ⇒ 该加流水级。

### 别忘了 hold

`WHS` 是保持裕量。**保持违例比建立违例更阴险**：建立违例通常表现为"跑不到那个频率"，
而保持违例表现为"在这个频率上偶尔采错"——换板子、换温度才会复现，最难查。
所以门禁要求 `WHS ≥ 0`，而且**改完 RTL 一定要重看 WHS**
（本工程第五版从 +0.064 → +0.048 → +0.060，就是每次都在盯它）。

## 3. 资源报告的三个陷阱

1. **看 "Slice LUTs" 而不是 "System Gates"**；看 `CLB Memory Tiles / Block RAM Tile`
   而不是 `RAMB36` 个数（一个 tile 能放 2 个 RAMB18）。
2. **`Slice` 这一行是空间约束**，它到 99% 时即使 LUT/FF 都不满，
   布局器也放不开了 —— 本工程第四版正是 `Slice 99.92%` 而 `LUT 只有 37%`。
   为什么？因为**一个 SLICE 里 8 个 FF 配 4 个 LUT**，FF 用得极多时
   slice 会先被 FF 塞满，LUT 却空着。
   （这就是"5.1 万个 FF 的 FIFO"同时撑爆 Slice 与寄存器的机制。）
3. **`LUT as Memory` 很低不代表好事**，它可能意味着"该用 LUTRAM 的地方全用了 FF"。
   本工程第四版它是 1.75%，同时寄存器 51.3% —— 这两个数放在一起就是诊断结论。

层次化报告（`util_hier.rpt`）用来回答"谁吃的"：本工程一眼看到
`u_fb`（显示帧缓存）独占 **128.03** 个 RAMB36，而全片只有 140 个。

## 4. 功耗报告：先问可信度，再问绝对值

```
| Dynamic (W)  | 2.188 |
| Static (W)   | 0.174 |
| Junction (C) | 52.1  |
```

- 没有输入开关活动（SAIF/FSDB）时，`report_power` 用**估计的翻转率**，
  报告里置信度会写 **Low**。所以**绝对值不可信，相对比较可信**。
- 本工程的用法：固定同一套流程与同一份网表来源，只比"改前/改后"的差值
  （2.525 → 2.412 → 2.362 → 2.350 W）。
- 要拿绝对值就得喂 SAIF：仿真导出的活动文件 + 后仿网表，代价是多一轮全流程，
  本工程把它列为低优先级待办（`OVERNIGHT_LOG` 的 U4）。
- **启动方式会影响功耗与 HP 行为**：JTAG `ps7_init` 不写 SLCR 的 `FPGA_FCM*`（HP 缓冲配置），
  只有 FSBL 会写 ⇒ 严格对比要固定启动路径。

## 5. 方法学与 CDC 报告：目标是"不新增"，不是"清零"

`methodology.rpt` 本工程第五版：

```
Checks found: 186
DPIR-1 36 | LUTAR-1 1 | SYNTH-5 48 | SYNTH-6 92 | TIMING-9 1 | TIMING-10 1 | TIMING-18 7
```

- 全是 **Warning**，没有 Critical ⇒ 门禁项"无新增 Critical"成立。
- 第四版是 170 条，第五版 186 条 ⇒ **必须解释这 +16 是什么**。
  逐条看实例名，新增全部是 `u_pl/u_fb/hi_reg_*`，即帧缓存新第二块的 16 个 tile
  被逐个报告 `SYNTH-6`（"BRAM 没合并输出寄存器，时序可能非最优"）。
  **这就是"记录并论证"和"忽略"的区别。**
- `cdc.rpt` 有 4 行 Critical，但那是**基线就有**的（异步时钟组工具无法自动判定）。
  门禁写的是"无新增 Critical"，同时要求把基线记下来 —— 见下一节。

## 6. 把"报告门禁"变成流程（本工程的做法）

```
L0 静态：diff / 位宽 / 复位 / 约束 / 资源粗估            → 不出 bit
L1 仿真：sim/run_sim.tcl 全量回归（30 个 TB）            → 不出 bit
L2 实现：synth + impl + 读报告                           → 不出 bit
L3 全量：完整构建 + bit + xsa + 全套报告 + 门禁判定       → 出 bit
L4 上板：ping / UART / JTAG 回读（需要硬件证据时才做）
```

**门禁判据（写死，不临时改）**：

| 项 | 门槛 |
|----|------|
| WNS / WHS | ≥0，且 `All user specified timing constraints are met.`，失败端点 0 |
| BRAM | ≤97%（目标 ≤95%） |
| Slice | ≤98% |
| 功耗 | 相对基线不明显恶化，恶化要解释 |
| methodology / cdc | 无新增 Critical；新增 Warning 要逐条论证 |
| route | Failed Nets = 0 |

配套纪律（这三条比门槛本身更有价值）：
1. **每轮数字都写进同一份记录**（本工程是 `report/OVERNIGHT_LOG.md`），
   形成"基线 → 每轮 → 当前"的可比表；
2. **门禁不过不算完成**，也不允许在失败状态上另起新主题；
3. **同一问题最多试 3 轮**，第 3 轮还不过就换策略或回滚 ——
   本工程真的用过这条：V6.2"加深缓冲"被自己的数据证伪后明确标注"方向错误"，
   第五版对 `--no-pace` 复现失败后**主动撤销**了自己写下的"P04 消失"结论。

## 6.5 两次构建的 WNS 不一样，怎么知道是"我改坏了"还是"布局布线轮次差异"

R24 撞上的一次真实判断：build#18 的 WNS 是 +1.002，我只改了 `eth_ctrl`（125 MHz 域、多一级寄存），
build#19 出来 WNS +0.598 —— 掉了 0.4 ns。**先别认错，也别先说"这是噪声"**，去看那 0.4 ns 长在哪：

```bash
# 两次的"最差路径"是不是同一条结构路径？（端点名字，不是 slack 数字）
grep -A3 "Slack (MET) :" build/timing_summary.rpt | grep -E "Source:|Destination:"
grep -A3 "Slack (MET) :" build/frozen_r18_abort/timing_summary.rpt | grep -E "Source:|Destination:"
```

两次分别是 `x_d_reg[11][4] → u_osd/b_reg[6]` 与 `x_d_reg[11][3] → u_osd/b_reg[3]/D`
—— **同一类端点、同一条逻辑链**（OSD 取字符行），而 `eth_ctrl` 根本不在这条链上。
⇒ 结论：这 0.4 ns 是布局/布线轮次差异，不是我这笔改动的代价。

**后来有了一个更干净的样本（R27）**：#21 → #22 之间**逻辑完全等价** ——
只是把顶层里写了两遍的 `512/300/基址/端口` 收成一组 `localparam`，一个值都没改。
结果 LUT 7452→7396（−56）、Reg −3、WNS +0.770→+0.566（−0.204 ns）、bit 哈希完全不同。
⇒ 两个教训叠在一起：
  ① **别把"bit 逐字节相同"当中性判据**。我当时就把它写成了"若相同即证明是中性重构"，
     结果不同 —— 如果不是先想好"不同该说明什么"，这句话就会让我误以为自己改坏了什么。
     中性的证据是：源码 diff 只有别名替换、L1 全量绿、门禁七项绿。
  ② 反过来这也是**噪声的直接测量**：等价逻辑都能差 0.2 ns，
     那么"我这笔优化让 WNS 涨了 0.2 ns"这种说法在单一样本上根本不成立。
     要谈时序收益，得谈**结构量**（逻辑级数、CARRY4 数、资源数、端点数）或者多样本统计。

顺手得到三个可复用的判据：
1. **比较构建要看路径的"名字"，不是只看 WNS 数字**。数字相同不代表同一条链，数字不同也不代表
   改动有害；端点名 + `Logic Levels` + `logic/route` 比例才是身份。
2. **`route 占 66%、logic 27 级`这种形状直接告诉你该动什么**：这种路径改约束、改布局策略都只是
   绕，只有把那一拍里的组合逻辑拆开或减级数才有真收益（本工程最差那条链一拍里做了
   `line*MAX_CHARS+cidx` → 40 项 `chars[]` 选择 → 字形译码 → `font[gi][fy]` 查表 → 变位选，
   所以第一步把"串行区间比较"的字形译码换成并行 `case`。**换掉的只是"译码方式"，等价性由
   `sim/tb_v794_osd_glyph.v` 的 256 码点差分证明；级数到底降了几级、WNS 涨没涨，要看 build#20 的
   timing 报告** —— 这两件事分开声明，别把"结构上应当更好"写成"已经量到更好"。
3. 说这句话要有出处：*"WNS 掉了但不是这笔改动造成的"* ⇒ 出处就是上面那两行 `grep` 的输出，
   写进 `build/frozen_r19_arb/MANIFEST.txt`。**没有这一条，别人只能选择信或不信你。**

## 7. 一个具体例子：本夜唯一没被"修好"的问题是怎么记录的

第五版修了帧尾 4 字节丢失，但**板级 A/B 拿不到证据**：
把第四版基线 bit 烧回板上，用 15/30 MB/s、60/120 fps 不限速、1396 载荷共 8 轮测量，
当年那个"8 次见 4 次"的现象一次都没复现。

记录里怎么写的（摘要）：

> 板上 A/B **没有区分力** ⇒ 该修复的证据等级只到"机理三段论 + 仿真双向判据"，
> 不宣称板级证实；同时撤销中途"P04 洪水丢包消失"的推论，因为基线同样洪水下也是 100%，
> 说明该现象在手头激励下根本没被触发。要拿到板级判据，需先造出 `sv_full`
> 落在帧尾的条件（非 8 倍数载荷 / 拉长 HP0 占用窗口），列为待办。

这就是"报告门禁"文化的核心：**结论的强度不能超过证据的强度。**

## 8. 自测

1. 一份报告里 WNS=+0.5、失败端点=0、`All ... met`，但 `Slice 99.9%`。你现在能改什么、不能做什么？
2. 为什么 hold 违例比 setup 违例更难查？给出一个典型板级症状描述。
3. `LUT as Memory` 只用了 2%、寄存器用了 51%，这个组合提示什么？
4. 功耗报告的置信度是 Low，那它还有用吗？怎么用才对？
5. 你的改动让方法学报告从 170 条涨到 186 条，你要做什么才算过关？
