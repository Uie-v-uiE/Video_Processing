# 07 · 用硬件写一个协议栈：ARP / ICMP / UDP / CRC32

> 这是本工程含金量最高、也最适合讲清楚"状态机 + 移位 + 比较"的部分。
> 每一段都对应 `src/rtl/eth/` 里一个真实文件。

---

## 1. 硬件协议栈与软件协议栈的根本差别

| | 软件（lwIP） | 硬件（本工程） |
|---|---|---|
| 处理粒度 | 一个包一次函数调用 | **一个字节一拍**，流水线 |
| 决策方式 | if/else 读结构体字段 | 状态机 + 并行比较器 |
| 内存 | pbuf 链 + 堆 | FIFO + 少量寄存器（**不存整包**） |
| 延迟 | 不确定（中断、调度） | 固定（可数拍） |
| 校验和 | CPU 算 | 组合逻辑/移位累加，边收边算 |
| 难点 | 内存管理、并发 | **成帧边界、字段对齐、跨域** |

核心设计原则：**流式处理，绝不缓存整包再解析。**
包是一个字节一个字节来的，硬件必须"边收边判断"，判断出来不匹配就当场丢弃。

---

## 2. 帧的解析顺序与"每层要判断什么"

```
前导码(7B) + SFD(1B)  → 目的MAC(6) → 源MAC(6) → EtherType(2) → IP头(20) → UDP头(8) → 载荷 → CRC(4)
                         ①                                    ②          ③         ④
```

| 层 | 必须做的事 | 不匹配怎么办 | 本工程模块 |
|----|-----------|--------------|-----------|
| ① 目的 MAC | 等于本机 MAC **或** 广播 `ff:ff:ff:ff:ff:ff` | 整帧丢弃（继续等下一帧） | `arp_rx.v` / `udp_rx.v` 各自的 MAC 比较 |
| EtherType | `0x0806`=ARP、`0x0800`=IPv4，其它丢 | — | 同上 |
| ② IPv4 | 版本=4、协议号=17(UDP)、**头部校验和**、目的 IP=192.168.1.10 | 丢；若是 ICMP 且类型=8 → 回 echo reply | `icmp_rx.v` |
| ③ UDP | 目的端口=5001、长度字段合法 | 丢 | `udp_rx.v` |
| ④ 载荷 | 前 4 字节 = u32 小端**字节偏移** | 偏移越界计入 `stat_oob_off` | `frame_reasm.v` |

**广播为什么要收？** ARP 请求本身是广播发的（"谁是 192.168.1.10？"），
如果只认单播 MAC，板子永远收不到 ARP 请求，也就永远无法被 ping 通。
这是硬件栈最常见的第一个 bug。

---

## 3. ARP：一个只有三种动作的小状态机

ARP 的作用：**IP ↔ MAC 的翻译**。

```
请求（广播）：谁有 192.168.1.10？请告诉 00:11:22:33:44:55
应答（单播）：192.168.1.10 是 aa:bb:cc:dd:ee:ff
```

硬件要做三件事：
1. **认出 ARP 请求**（EtherType=0x0806，opcode=1，目标 IP == 本机 IP）；
2. **把请求方的 IP/MAC 存下来**（否则不知道该回给谁）——这就是"ARP 表"的最小形态；
3. **构造一个 ARP reply 发回去**：把 opcode 改成 2，源/目标字段互换，
   以太网头里目的 MAC = 刚存下的对方 MAC。

本工程对应 `arp_rx.v`（判断 + 存对方信息）、`arp_tx.v`（组包发出）、`arp.v`（仲裁两者）。
组 reply 时的字段顺序必须严格按 ARP 报文格式：
`HTYPE|PROTYPE|HLEN|PLEN|OPER|SHA|SPA|THA|TPA`，
其中 `OPER=2` 是 reply。**顺序错一个字段，PC 上看到的就是一条奇怪的 ARP，ping 不通。**

> 硬件实现 ARP 的实用简化：不做老化、不做免费 ARP、不缓存多条。
> 本工程就是一条"来一个请求答一个"的无状态机 + 一个对方地址寄存器。
> 这在"PC 直连板子"的场景完全够用，也是把复杂度控制住的正确取舍。

## 4. ICMP：让 `ping` 成为"上电自检"判据

ICMP echo request（ping）的硬件应答只需：
1. 认出 `协议号=1`、`类型=8`（echo request）；
2. 把 `标识符` 和 `序列号` **原样搬**到 reply；
3. 类型改成 `0`（echo reply），code=0；
4. **重算 IP 与 ICMP 校验和**；
5. 目的 MAC/IP 换成对方。

实现技巧：**校验和不用从头算**。
echo request → reply 的差别只有"类型 8→0"和"校验和字段本身"，
所以可以按 RFC 1071 的增量更新：`new_sum = ~(~old_sum + ~0x0800 + 0x0000)` 一类，
省一个完整的 16 位累加树。本工程 `icmp_rx.v` / `icmp_tx.v` 走的是
"边收边累加、发时回填"的路线（具体见模块详解）。

有了 ICMP，就有了这条极有用的调试判据：

```
program bit 完成 → ping 192.168.1.10 通 ⇒ RGMII 收、MAC 比较、ARP、ICMP、发送通路全对
```

**不需要 PS 参与、不需要看屏幕。** 本工程的板级复验第一步就是它。

## 5. UDP：本工程真正的入口

UDP 头 8 字节：`源端口(2) | 目的端口(2) | 长度(2) | 校验和(2)`。
硬件里要做的判断很少：目的端口 == 5001。

但**"包边界"是硬件栈最难的部分**，因为字节是连续来的，没有"包结束"这个信号。
本工程的处理：

- 从 IP 头的 `总长度` 与 UDP 头的 `长度` 推出本包还剩多少字节 ⇒
  产生 `rec_en`（每字节一拍）与 `rec_pkt_done`（包尾单拍）；
- 包起始时产生 `sof`（本工程用"不在包内 + 收到第一个字节"来推断）；
- 载荷交给 `frame_reasm`：**前 4 字节当作 u32 小端偏移**，之后的字节按偏移写进帧缓冲。

```
[u32 LE byte_offset][RGB565 载荷 ...]
```

这个"带偏移的裸管道"协议是刻意的选择，它换来三件事：
1. **乱序可拼帧**（每个包自带落点，不依赖顺序）；
2. **丢包不毁整帧**（丢的那块留洞，下一帧补上）；
3. 上位机零依赖（一个 socket 就能发）。

代价是**没有重传、没有校验应用层完整性** ⇒ 必须自己在 PL 里判断"这一帧收全了没有"，
这就是 `frame_reasm` 里的覆盖率门限（`rows_hit` / `cover`）存在的原因，
也正是第五版那个帧尾 bug 的发生地。

## 6. CRC32：以太网帧校验的硬件形态

以太网 FCS 是 CRC-32（IEEE 802.3，多项式 `0x04C11DB7`，位反转输入/输出，初值 `0xFFFFFFFF`，末值异或 `0xFFFFFFFF`）。

硬件实现是**组合逻辑异或树 + 寄存器**，每拍吃 1 字节（本工程 `crc32_d8.v`，
名字里的 `d8` = data 8 bit）：

```
crc_next[31:0] = (crc[23:0] << 8) ^ f(crc[31:24], data[7:0])
```
`f(...)` 是一个 16 输入的 XOR 网络（查表化简而来），所以每拍只需 1 级 LUT + 1 级 XOR ⇒
125 MHz 轻松。

工程上的两个注意点：
1. **CRC 由 PHY 还是 MAC 算？** 板级可配置（RTL8211 有 CRC 剥离/添加模式）。
   若 PHY 已剥离，硬件就不要把最后 4 字节当载荷 ⇒ 会把 CRC 当成 4 个像素写进帧里。
2. **本工程对视频载荷是"信任"态度**：CRC 主要用在**发送方向**（ARP/ICMP reply 要带合法 FCS，
   否则 PC 网卡直接丢）。收包侧对坏包的处理依赖"偏移越界丢弃 + 覆盖率门限"，
   而不是逐包 CRC 判定 —— 这是一个明确的取舍，值得在文档里写清楚而不是假装做了。

## 7. 把这几块拼起来：一个包在 PL 里的完整旅程

```
1 字节进 IDELAYE2 → rgmii_rx DDR 解串 → 8bit + DV
2 跳过前导码/SFD，抓目的 MAC（比较：本机 / 广播）
3 抓 EtherType → 分诊：0x0806 → arp_rx；0x0800 → IP 解析
4 IP：验版本/协议号/校验和/目的 IP → 17 且端口 5001 → udp_rx
5 udp_rx 逐拍吐 rec_en/rec_data，并给出包尾 rec_pkt_done
6 frame_reasm 状态机：S_OFF0..3 收 4 字节偏移 → S_DATA 收载荷
     每 2 字节拼一个 RGB565 像素，按偏移写 fb_wr_en/fb_wr_addr/fb_wr_data
7 包尾 → flush；帧收全（覆盖率门限）→ frame_done
8 之后就是 CDC 与 DDR 的事（见 02/04 篇）
```

对应代码：`src/rtl/eth/` 下同名文件；逐模块状态机与信号定义见
[03_模块详解/01_以太网入包链](../03_模块详解/01_以太网入包链.md)。
