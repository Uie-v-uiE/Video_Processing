## 实验 1 第一条命令：读一份冻结门禁

**目的**：不碰任何工具链，看清"这个工程怎么判自己能不能交付"。

**操作命令**（仓库根执行）：

```bash
bash build/gates.sh build/evidence_r75
```

为什么传目录而不是裸跑：裸跑（`bash build/gates.sh`）会**当场执行**
`python build/check_ports.py --dup > build/ports_check.txt`（`build/gates.sh:253`），
也就是往 `build/` 写一个文件；传一个冻结目录时这一项被跳过、改为读该目录里已有的凭据
（同文件 `:262-269`），所以这条命令是只读的。

**预期观察**（"看到什么算理解了"）：

- 末行是 `GATES: PARTIAL —— 判定 22 项全过，但有 2 项因缺凭据未判（见上面 n/a 行），这一版不作"过门禁"`。
  ⇒ 理解点是：**"全过"不等于"全判"**。这一版有两条 `n/a`，脚本因此拒绝给出 `ALL PASS`
  （判定逻辑在 `build/gates.sh:581-587`）。
- 中间有一行 `分组最差（记录用…）` 列出 `eth_rxc`、`clk_fpga_0`、`clkout0_1`、`sys_clk` 各自 setup/hold，
  并有一行 `← 门禁 WNS 就是这一组`。⇒ 理解点是：全局 WNS 只说"最紧那一条属于谁"，
  四域要一起念（口径见 `report/timing_global.md` 第 1 节第 1 条）。
- 末段有一行 `端点总数 39915`（这是这份**冻结件**的读数，与当前位流的读数不同，见 `data/metrics.csv` 第 5 行的 51135）。

**看到别的说明什么**：

- 看到 `FATAL 缺报告：…` ⇒ 你传的目录里没有成套件；`build/gates.sh:31-33` 就是这条判据，
  缺任何一份它就停，不会给你半套结论。
- 看到 `GATES: 有红项` ⇒ 这套冻结件本身判红（那是历史事实，不是你环境的问题）。
- 完全跑不起来（`bash: command not found`） ⇒ 你不在仓库根，或没有 bash（不是 Vivado 的问题）。

小结 1：这一条命令 30 秒内给你全部 22 项判据的**形状**，是本目录推荐给所有人的第一站。
小结 2：它同时证明了"门禁只读报告、不重跑构建"（`build/gates.sh:22` 那句就是这条设计）。下一步：实验 2。

## 实验 2 只读探针：从代码里把层次图重新长出来

**目的**：验证 `subsystem-map.md` 第 5 节的图不是编的。

**操作命令**：

```bash
grep -n "proc_pipeline" src/rtl/top/pl_video_top.v
grep -n "u_pipe.LATENCY\|u_pipe.OFF_LINES" src/rtl/top/pl_video_top.v
grep -c "u_" src/rtl/top/pl_video_top.v
```

**预期观察**：

- 第一条命中例化那一行（本目录记的行号是 `src/rtl/top/pl_video_top.v:800`）与几处注释。
- 第二条命中两个"由模块自己声明、顶层只取用"的量：混色深度 `MIX_D`（`:354`）与 skid 长度 `PROC_LAT`（`:816`）、
  行延迟环 `RAW_LINES`（`:781`）。⇒ 理解点是：**这三个数在顶层没有第二份字面量**，
  链条加一级时它们会自己跟着走（这条纪律的理由写在 `src/rtl/process/proc_pipeline.v:19-21`）。
- 第三条数出的 `u_` 出现次数**包含注释里的**，所以它只用来做前后对比（改完代码再数一次看有没有丢实例），
  不能用来当实例数。实例数请用 `build/check_ports.py` 那把尺子的读数（`build/ports_check.txt:1`）。

**看到别的说明什么**：第一条完全没有命中 ⇒ 你不在仓库根，或你的树不是本仓库这一版（`git status` 先看一眼）。

小结 1：这个实验教你一件通用技能：**用 grep 把"只有一个出处"这件事验出来**，而不是相信注释。
小结 2：第三条那种"数出来的数不能当结论"是本仓库反复登记的那类判据坑（判据要能红才算有牙）。下一步：实验 3。

## 实验 3 只读尺子：文档里的 `文件:行` 到底对不对

**目的**：体会"行号会漂"这件事怎么被机器管住。

**操作命令**：

```bash
node src/host/line_cite_check.mjs
node src/host/line_cite_check.mjs --self
```

**预期观察**：

- 第一条末行以 `D5: CLEAN` 结尾（= 硬错 0 条）。它判的三类硬错写在自己的文件头
  （`src/host/line_cite_check.mjs:21-22`）：引的文件不在树里、行号越过文件末尾、
  "例化者"列与逐字抄的固件回声对不上。
- 第一条的**计数**（扫了多少份文档、命中多少条锚点）会随文档增删变化 —— 本目录引用它时
  **不写死这些数**，只写判据形状；要数就自己跑。
- 第二条全部 `PASS`，末行退出码 0。⇒ 理解点是：**尺子自己也带反例**，
  它把一条故意错的行号与一条正确的行号同时喂给自己（写法见 `src/host/line_cite_check.mjs:316-320`）。

**看到别的说明什么**：出现"硬错"清单 ⇒ 某处引用真的坏了（文件改名、行号越过 EOF），
按清单里的 `文档:行` 去修文档；`--self` 不过 ⇒ 这把尺子本身不可信，此时**不要**去改文档迎合它。

小结 1：这条命令是本目录所有 `文件:行` 的自动质检口，也是写文档的人必须跑的一条。
小结 2：它管不到 `.md` 之间的行号引用（设计取舍写在 `src/host/line_cite_check.mjs:24-26`）。下一步：实验 4。

## 实验 4 需要工具链：跑一支单台架

**操作命令**：

```bash
VP_VIVADO_BIN=<Vivado>/bin bash build/sim/run_one.sh tb_sync_fifo
```

**判据形状**（脚本自己定义的，`build/sim/run_one.sh:112-124`）：退出码
`0 绿 / 1 编译或例化失败 / 2 REFUSE / 3 台架判红 / 4 认不出判定行`，
末行是一条 `VERDICT <tb>: … || FAIL 行数=N || PASS 行数=M`。

**预期观察**：先是 xvlog/xelab 的过滤输出，然后那行 `VERDICT`。
"看到什么算理解了"= 你能指出 `FAIL 行数` 与判定行**同源**（同一次跑的同一份 `run.log`），
而不是从两处拼出来的。

⚠ 三条风险先说：

- 同一时刻只能有一个 `xsim` 在跑，否则脚本会**拒绝启动**（判据与提示原文：`build/sim/run_one.sh:57-61`）。
- 编译产物落在 `/tmp/kx/<tb>.run`（`build/sim/run_one.sh:49`），不在仓库里 ⇒ 想看全文要去那个目录读 `run.log`。
- 本目录**没有在本机跑过这支台架**（我没有跑 Vivado 的许可），所以这一节给的是命令与判据形状，
  实际读数标 `【未实测】`；`tb_v98_top_seam` 那支更要约 108 分钟（`data/metrics.csv` 第 15 行的测量条件栏）。

**看到别的说明什么**：`REFUSE: 找不到 xvlog` ⇒ `VP_VIVADO_BIN` 没设或指错（这条报错原文在
`build/sim/run_one.sh:47`）；`XVLOG FAILED` ⇒ 树里的 RTL 与台架清单编译不过，先 `git status` 看有没有本地改动。

小结 1：**先认退出码，再认打印的行** —— 这台工具把"红"与"没数"分成了 3 与 4 两个码。
小结 2：任何"跑过了"的说法都必须带上命令、输入与看到的输出，否则按 `【待验证】` 处理。下一步：实验 5。

## 实验 5 需要板卡：读回一条 lane

标 `【需板上验证】`。本目录没有任何一次本机板级实测，下面全部是**照仓库脚本复述**的操作，
读数一律 `【未实测】`。

前置连接（原文口径在 `board/README.md:36-45`）：板子上电、JTAG 链可见
（先 `vivado -mode batch -source build/tcl/scan_jtag.tcl`）、`hw_server` 在听 3121
（`src/host/health_read.mjs:15` 那句前置说明）。风险：这一支会**写** GPIO_0 的 `[31:27]`，
脚本按"读原值 → 改 5 位 → 读完写回"的顺序做（`src/host/health_read.mjs:6-8`），
中途打断会把 lane 选择位留错值 ⇒ 下一次读数看起来像"越界"。

```bash
VP_XSDB=<Vitis>/bin/xsdb.bat node src/host/health_read.mjs --once
```

**预期观察**：`lane7` 那一条的 `bit3`（流活着）与 `lane2` 的 `stall_ms` 互相自洽；
`lane31` 低两位说明源时基有没有被拉慢（定义在 `src/rtl/top/system_top.v:209-211`）。
"看到什么算理解了"= 你能说出**为什么 `stall_ms` 单独不可信**（答案的物理事实在
`src/rtl/util/src_arb.v:11-14`）。**看到别的说明什么**：读出 `0xDEADBEEF` ⇒ 你写的 lane 号越界（第 4 节第 3 段）。

小结 1：这一支实验的全部价值是"把屏幕上的说法换成机器读数"，它不证明任何新东西。
小结 2：没有板卡就跳过实验 5，但**不要**因此怀疑实验 1~3 的结论 —— 那三条与板卡无关。下一步：实验 6。

## 实验 6 改一处会看到什么（独立副本法）

**目的**：理解"帧缓存只有 4 个像素一拍"这条设计后果（`src/rtl/top/pl_video_top.v:242`、
`src/rtl/axi/axi_frame_writer_gated.v:40`）。

**做法（三行，全在仓库外）**：

```bash
mkdir -p ../vp_copy && cp -r src sim ../vp_copy/
cd ../vp_copy && sed -i 's/wire \[11:0\] cx = x >> 1;/wire [11:0] cx = x;/' src/rtl/top/pl_video_top.v
```

**预期观察**：改动之后**不重新构建就不会有任何现象变化** —— 这个实验的全部意义在于
"你能一眼还原它"，还原命令是 `cd .. && rm -rf vp_copy`（副本整棵删掉，仓库一个字节没动）。
被改的那一行现在长什么样，可以先用 `grep -n "cx = x" src/rtl/top/pl_video_top.v` 在**改之前**核对一次
（本目录记的原文位置是 `src/rtl/top/pl_video_top.v:242`）。
屏上会出现什么，本目录标 `【未实测】`：**我没有跑过这次改动**，而且跑它需要一次完整构建
（`build/tcl/build_system_axigpio.tcl:269-317`）+ 一次上板，代价远超这一条实验的价值。

⚠ 两条硬规矩：**不要**在 `src/rtl` 里就地改（构建脚本会重新综合当前树）；
**不要**把实验用的改动留在树上再跑门禁（门禁第 15/15b 项会认"报告与当前树不是同一次跑"，
判据在 `build/gates.sh:347-351`）。

小结 1：任何"改一处看现象"的实验都必须自带还原路径，且默认在副本里做。
小结 2：这条实验给了你判据形状，**没给**读数；把它引用给别人时要带着这个 `【未实测】` 一起给。下一步：第 8 节。

## 第 8 节 还原清单与红项处理

| 实验 | 改动了什么 | 还原 |
|---|---|---|
| 1、3 | 无（只读） | 不需要 |
| 2 | 无（只读 grep） | 不需要 |
| 4 | 只写 `/tmp/kx/<tb>.run`（`build/sim/run_one.sh:49`、`:63`） | `rm -rf /tmp/kx/<tb>.run` |
| 5 | 板上 GPIO_0 的 `[31:27]`（脚本自己写回） | 重新下一版固件位流即回默认；或让固件再 `ctrl_write()` 一次 |
| 6 | 仓库外副本 | 删掉 `../vp_copy` |

跑出任一实验判红时的分叉：先分清"红 = 结论"与"没数 = 不是结论"（这条区分在 `build/sim/run_one.sh:40-41`
里被做成了两个不同的退出码），再去 `report/known_issues.md` 看它是不是**已登记**的红
（例：`data/metrics.csv` 第 15 行明写了当前唯一那条被登记的台架红项 `C5c`）。

小结 1：这张表让"做实验"与"把仓库弄脏"这两件事解耦 —— 每个实验都有还原动作。
小结 2：红项先对已登记清单，再决定要不要报新问题。下一步：`glossary.md` 或回到 `one-pass-walk.md`。
