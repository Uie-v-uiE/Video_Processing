# 09 OSD 与同屏分割：字模译码的四级刀、五行版式、缝发生器与逐像素 A/B

`src/rtl/video/seam_src.v`（图像域判据）、`src/rtl/video/split_display.v`（逐像素混合）、

## 1 前置知识

### 1.1 字符发生器（OSD/scaler）这一类硬件在做什么

电视/显示器上的"字幕"从来不是渲染出来的，而是**逐格替换**：把一个字符网格叠在扫描栅格上，
当某个像素落在"第 `line` 行、第 `cidx` 格、格内第 `pix_x` 列、第 `pix_y` 行"时，去字模表里取一个 bit，
为 1 就把该像素涂成前景色，否则透出背景。本设计就是这个形状，只是网格尺寸与前景色定了就不改
（`src/rtl/video/osd_overlay.v:8-19` 的参数、`:519` 的前景 `8'hFF,8'h00,8'h90`）。

这条结构有两个必然后果，本章反复用到：

1. **一整块组合逻辑要在一拍里解出"这一格画不画"**：于是"坐标 → 格号 → 字符 → 字模行 → bit"是一条串联链，
   它的深度就是全设计最差路径的深度（1.2 与第 3 节）；
2. **文本内容必须提前准备好**：屏上要显示一个十进制数，就得先把它拆成 ASCII 码放进一个字符缓冲，
   拆位的算术因此也挂在那条链上（1.6）。

### 1.2 为什么"显示一个数"会烧掉一级流水线

`LINE_H = CHAR_H + LINE_GAP = 21 + 10 = 31`，`CHAR_W = 18`（`src/rtl/video/osd_overlay.v:11-14, 71`）。
31 与 18 都**不是 2 的幂**，所以

```
line   = ly / 31      pix_y = ly − line*31      cidx = lx / 18      pix_x = lx % 18
```

（`src/rtl/video/osd_overlay.v:94-97`）这四个除/模**每个是一串减法**，合起来就是那条链上的 9 个 `CARRY4`。
这一点被量得很死：`开发台账` 把同一拍里挤着的四件事列成 ①乘+比较链 ②字形译码
③字模查表 ④变位选；`开发台账`（#96）补上第五、第六件（除法与模），
并给出当时的读数 `Logic Levels 29（CARRY4=9 LUT6=10 MUXF7=2）`。

设计上的对应态度有两种，本设计两种都用：**把算术挪走**（分拍、挪到 PS、挪到源头寄存），
**而不是把算术做快**。这条纪律在文件里被重复声明了至少四次（`src/rtl/video/osd_overlay.v:164-167, 219-221`、
`src/rtl/video/split_ctrl.v:108`、`src/rtl/process/effect_ctrl.v:63-65`）。

### 1.3 为什么"不画到屏上的量不许当输入进来"

`src/rtl/video/osd_overlay.v:31` 把这条写成端口规矩。它的物理理由不是整洁：多一根进线就多一个扇出负载、
多一条要过时序的路径，而这条链是全设计相对余量最紧的一条（3.6 的读数）。
反面例子也记着：`src/rtl/top/pl_video_top.v:956-958` 那一段写的是 V8-5 撤下两格之后，
一条 320 bit 的健康快照跨域**没有读者**了，于是那条 `snap_cross` 连同三个端口一起删掉——
"留着它就是一根没人读的线"。

### 1.4 百分比不要除：乘常数 + 固定移位

`shown_pct = eff*100/W`，而 `W` 是 2 的幂（1024 或 512），所以把 100 与 1/2 的幂合成一个 elaboration 常数：

```
localparam [13:0] PCT_DISP = (100 * 16384) / DISP_W;   // = 1600，1024 ⇒ 精确
localparam [13:0] PCT_SRC  = (100 * 16384) / SRC_W;    // = 3200，512  ⇒ 精确
pct = (eff * pct_c) >> 14;                             // src/rtl/video/split_ctrl.v:112-117
```

`src/rtl/video/split_ctrl.v:107-111` 写明另一条不许：不许有运行时的非 2 幂除法，也不许有 `% 扫描周期`——
先例是 100 MHz 域里一个组合除法器把 WNS 打到 −5.014。代价也说清：这条只因为两个宽度都是 2 的幂才成立，
换成非 2 幂宽度必须改成"每帧一次逐次除法"，而台架 T5 会先一步变红（它独立按整数除法算期望值）。

### 1.5 静态文本与运行时文本的区别

`src/rtl/video/osd_overlay.v:161-162`：`putnum4(OUT_W)` / `putnum4(OUT_H)` 的参数是 elaboration 常数，
综合直接把十进制位折成接线——所以第一行那格"1024X600"**没有硬件**。同一段下面紧跟着一条不许：
不许拿 `putnum4` 打运行时数值，因为 16 位除以 1000 就是二十几级链，而 OSD 的读侧正是全设计最差那条路径
（`src/rtl/video/osd_overlay.v:218-221`）。要显示新的运行时数值就照 `lat_v` 那一招分拍算（1.6）。

### 1.6 跨域与控制：缝位是怎么从 PS 落到这一拍的

缝的 19 位几何字与第 08 章的九位控制字**不是同一条链**：几何字走 `snap_cross`（整字 + 翻转位 + 3 级同步 +
沿到再采），九位效果字走 `effect_ctrl` 的 2 级 `ASYNC_REG`。分开的理由写在
`src/rtl/process/effect_ctrl.v:62` 与 `src/rtl/top/pl_video_top.v:52-53`：加宽现成那条链会让
`cdc.rpt` 的 unsafe 端点按位长涨，而再开一条 `snap_cross` 就是"一个发射触发器扇出两组目的域同步器"——
CDC-11 Critical 的签名（#65 与 r54 构建 #34 各为它红过一次门禁）。

顶层的发布节拍也值得看一眼：`axi` 域里一个 17 位计数器数满 `17'h1FFFF` 就把 `split_ctl` 整字抄进 `sp_bus`
并翻一次 `sp_tog`（`src/rtl/top/pl_video_top.v:865-875`）⇒ 约 1.3 ms 一次心跳，
`DST_HZ=50_000_000 / HB_TO_MS=200` 的快照同步器据此判"心跳有没有停"（`:876-880`）。

## 2 五行版式：几何账与每一格到底画什么

### 2.1 尺寸是怎么加出来的

| 量 | 值 | 来源 |
|---|---|---|
| 起点 | `(X0, Y0) = (16, 12)` | `src/rtl/video/osd_overlay.v:9-10` |
| 字模 | 5 列 × 7 行点阵 | `src/rtl/video/osd_overlay.v:333`（`reg [4:0] font [0:63][0:6]`） |
| 放大 | `SCALE = 3` | `:11` |
| 字符格 | `CHAR_W = 18`（`5*3 + 3` 横向空隙）、`CHAR_H = 21`（`7*3`） | `:12-13` |
| 行距 | `LINE_GAP = 10` ⇒ `LINE_H = 31` | `:14, :71` |
| 每行格数 | `MAX_CHARS = 32` | `:15` |
| 行数 | `N_LINES = 5` | `:19` |
| 文本框 | `BOX_W = 32*18 = 576`、`BOX_H = 5*31 = 155` | `:72-73`（算式在此，乘积由这两行代出来） |

`N_LINES = 5` 而不是 4，理由写在 `src/rtl/video/osd_overlay.v:16-18`：前四行的字段、顺序、空格是定好的格式，
"动不得，所以新话只能另起一行"，于是第五行专职装"没有 ETH 信号时印 `ETH IS NO SIGNAL`，其余时间整行空格"。
高度账也在那里核过：`5×(21+10) = 155 px < 600`，字格尺寸一个都没动。

一个容易被忽略的位宽账：`src/rtl/video/osd_overlay.v:92-94` 注明"行号位宽必须跟着 `N_LINES` 走"，
写死 `[1:0]` 时加到第 5/6 行屏幕上永远取不到，而综合与时序报告全绿——这类错只有屏能看见。

### 2.2 为什么文本框 576 px 比半屏宽还宽，却不算越界

`BOX_W = 576` 而左半窗只有 512 px。设计上的实际约束是**打出来的字符串**不许压到分割线：
`src/rtl/video/osd_overlay.v:260-262`（最宽一格 `TEST*` 27 字符 ⇒ 右沿 `16 + 27*18 = 502 ≤ 511`）与
`:309-311`（最宽激励 26 格 ⇒ `16 + 26*18 = 484 < 511`）。判据不是"目测不出格"而是尺子：
`sim/tb_osd_lines.v` 的 T13 要求每行右沿 `X0 + k*CW <= 511`，同时比整串也逐像素比对（见 6.1）。
第一行那句"画**面板**尺寸并放在行首"（`src/rtl/video/osd_overlay.v:260`）也是为了不被读成 `SRC:` 的定语，
所以分隔符换成了大写 `X`（字模 56，`:431`）。

### 2.3 五行逐格内容

装配段是 `src/rtl/video/osd_overlay.v:256-329` 的 `always @(*)`，一行一段、按列往 `chars[]` 里打：

**L0：`1024X600  FPS:30  SRC:ETH`**（`:263-270`）。尺寸递进来的是**面板**那一份（`OUT_W = 2*IMG_W`、
`OUT_H = 2*IMG_H`，`src/rtl/top/pl_video_top.v:996-999`，#67 把这一格从片源尺寸换成面板尺寸的动机写在同一处：
屏上画的数与真实扫描的列/行数同源）。`FPS` 见 2.4。`SRC` 由 `put_src(src_eff, mode)` 打
（`:243-254`）：`src_eff == 2'b11` 打 `ETH`、`2'b10` 打 `SD`、其余打 `TEST`，`mode != 00` 时补一个 `*`。
`src_eff` 的构造是 `{fb_vis, owner_eth_pix}`（`src/rtl/top/pl_video_top.v:1014`）——**画的是屏幕上真的这一路，
不是意愿**（`:5` 的文件头同句）。用词只有 ETH / SD / TEST 的理由写在 `src/rtl/video/osd_overlay.v:238-240`：
`CARD` 在板上同时被念作"SD 卡"和"测试图卡"，PS 既指处理器也指片内自绘。

**L1：`Pipe:11000 Th:80 Gamma:1.8`**（`:276-284`）。五位 `Pipe` 码来自**实际生效**的九位
（`stage_sel = sel_sync`，`src/rtl/top/pl_video_top.v:1007`），每格是"这一级开了哪个算法"：

```
pc1 = lvl([0], [1])                       // 颜色：灰度/反色 → 0/1/2/3
pc2 = lvl([2], [3])                       // 滤波：模糊/锐化
pc3 = lvl([4], 1'b0)                      // 边缘：只有 Sobel
pc4 = ![5] ? "0" : ([6] ? "2" : "1")      // 阈值：只有两种，没有"同时开两种"
pc5 = lvl([7]&~[8], [8]&~[7])             // 形态学：两位同时 1 必须给 0
```

`src/rtl/video/osd_overlay.v:131-142`。`pc4` 与 `pc5` 这两条特殊处理不是修辞：
`lvl([5], [5]&[6])` 会把两位都设了画成 3，而屏上仍是**一张**二值图（`:136-138`）；
`pc5` 给 3 就是"屏上写着两个都开、画面上什么都没发生"（`:139-141`，对应第 08 章那条互斥旁路）。
这一行的两个分隔是**单空格**，理由写在 `:272-275`：格距 18 px 而左半窗只有 512 px ⇒ 一行最多 28 格就贴到
分割线，收成 26 格 ≈ 468 px，留 44 px 余量。

**L2：`Rot:45°  ZOOM:0.75X(AUTO)`**（`:286-296`）。角度直接是 `angle_ctrl` 里的十进制度数 0..359，
不换算（`:289`）；度数符号是 `8'hDF`（Latin-1 的 `°`，`:290`，字模 49 在 `:419`）。
缩放那一格画的是 `zoom_code`——**最近一档**的号，八档表在 `zoom_ctrl` 里查、不除
（`src/rtl/video/osd_overlay.v:144-159`；号→字符串的 case，`default` 也走 `1.00x`，
因为号只有 3 bit、没点出来的那一支就是 4）。后缀 `(Fit)` 与 `(Auto)` **互斥**
（`:293-296`）：同时叠两个后缀那一格 32 格会溢到下一行去（`put` 会直接写进 L3 的格子里），
而且"呼吸"与"按角度定"本来就不可能同时成立。顶层给的两个使能是
`.zoom_auto(zoom_run && !zman_pix && !zoom_fit_en)` 与 `.zoom_fit(zoom_fit_en | rot_forced)`
（`src/rtl/top/pl_video_top.v:1010-1011`）——手动档不许再标 `(Auto)`，被旋转钳住时标 `(Fit)`，屏上才讲真话。

**L3：`Split:50%  Latency:16ms`**（`:298-307`）。缝位百分比见第 4 节。Latency 那一格的规矩是
**没有可信测量就画 `--`**（`:305`），两个条件位来自 `lat_ok_pix = lat_bus_q[17] & lat_bus_q[16] & ~lat_gone`
（`src/rtl/top/pl_video_top.v:986-987`）：`lat_valid`（这一次测量算完了）与"这一次配对干净"两个都要，
少一位就会把一个假 ms 画上屏。换算不在这里做——它在 axi 域逐次除法做完，再按翻转位跨域
（`src/rtl/video/osd_overlay.v:42`，先例是 #59）。

**L4：`Temp:47C  ETH IS NO SIGNAL`**（`:309-328`）。温度是 PS 侧 XADC 编成的**两位十进制 BCD**
（`[7:4]` 十位、`[3:0]` 个位，`:318-321`），任一半字节 > 9 就画 `--`（`:322-324`）。
"为什么由 PS 先算成 BCD 再跨、不在这里除"的理由在 `src/rtl/video/osd_overlay.v:49-52` 与
`src/rtl/process/effect_ctrl.v:63-66`：下面是一整块组合逻辑，而 `u_pipe/xd_reg → u_osd/g_reg/D` 正是
`clkout0_1` 那一组的 WNS 路径，多一次 /100 与 /10 就是往全设计最差的链上加深度。
PL 那条链的复位值就是 `32'h0000_00FF`（`src/rtl/process/effect_ctrl.v:44-48`），所以 app 起来之前屏上是
`TEMP:--` 而不是 `TEMP:00C`。`no_sig` 由顶层从 `eth_live` 推：
`wire no_sig = (mode_eth | owner_eth_pix) & ~eth_live_pix;`（`src/rtl/top/pl_video_top.v:510`）——
拔线时画面会冻在最后一帧，没有这一句就会被当成"板子卡死"。

### 2.4 `FPS:` 那一格数的是什么（一次口径变更）

这一格是**改过口径**的，而且改的是"数什么"，不是"数错了"。

改前：顶层数显示场的 `vs` 下降沿，窗口又是 `sys_clk` 的 1.000 s，而面板是 1344×625@50 MHz ⇒
读数恒在 59/60，与片源是 30 fps、15 fps 还是**根本没有片源**都无关
（`src/rtl/util/shown_rate.v:4-7`；`src/rtl/top/pl_video_top.v:930-933` 记的是同一次改口，
并明确写"这是改口径，不是抓到的新 bug"，因为旧的口径早就写在模块表里）。

改后：判据变成"这一场真的取走了一帧新内容"，三个片源各有各的凭据，全部复用顶层**已有**的线
（`src/rtl/util/shown_rate.v:9-14`）：

```
new_shown = frame_start && (owner_eth_pix ? eth_pend : (fb_vis ? (pub_consume && pub_pend) : 1'b1));
```

`src/rtl/util/shown_rate.v:42`。三个细节都是量出来的：

- ETH 的 `frame_ready` 落在哪一拍不重要，重要的是**下一次 `frame_start` 才真的被扫到** ⇒ 内部存一个
  `eth_pend` 在 `frame_start` 用掉（`:11-12`）；原来顶层缺这一位，所以"帧到了"与"帧上屏"混成一根线；
- `frame_start` 与 `eth_new` **同拍**时按"仍然欠着一帧"算：新内容是在这一场开始之后才进缓存的，
  这一场扫的是上一场的内容。优先级写反会让读数在 ETH 满速时偏高（`:16-17`，台架 S2 钉的就是这件事）；
- 窗口常数一字未改，只是从 `sys_clk` 搬进 `clk_pix`（`WIN_LAST = 49_999_999` ⇒ 50 MHz 下正好 1.000 s，
  `:19-21`）⇒ 顺带少了一对跨域（原来 `fps_q` 在 sys_clk 里寄存、像素域直读）。

屏上那一格还有一道夹：`fps_v = (fps > 99) ? 99 : fps`（`src/rtl/video/osd_overlay.v:129`），
`putnum` 按实际位数打、不打前导零（`:213-217`）。台架 `sim/tb_shown_rate.v` 用缩小的窗口（`WIN_LAST=999`）
逐秒判四种片源态与同拍到达那一支（文件头 S1..S7），顶层接线在
`src/rtl/top/pl_video_top.v:940-950`。

## 3 字模 ROM 与译码：为什么它是 WNS 瓶颈，四刀分别买到什么

### 3.1 ROM 的形状与号位的历史负担

```
reg [4:0] font [0:63][0:6];     // 64 个字形 × 7 行 × 5 bit
```

`src/rtl/video/osd_overlay.v:333`，装载全在 `initial` 块里（`:335-435`）。
索引 0..27 是**历史插入序，不是字母序**（`:331-332`）：0..9 是数字、10..15 是 A..F，然后
G=16、R=17、O=18、T=19、N=20、L=21、P=22、U=23、S=24、H=25、*=26、==27，
44..52 是后补的符号与大写 Z、53 之后是 I M X Y，63 是空格。新字一律往后接、不回头改已经在用的号——
因为金表钉的就是那一段号（`sim/tb_v794_osd_glyph.v` 自带一份**独立手写**的码点→字形表，
文件头第 1-2 行写明它比的是 0..255 全部码点各自落到哪个字形号，含反向断言）。

两个"没有字模"的代价被记过账：`U` 与 `H` 从来没画过，缺字模的表现是"字母静默变成空格"，
`SRC=A?TO` 看着像渲染坏了（`src/rtl/video/osd_overlay.v:341-345` 补的就是这两个）；
小写 `c` 的右列多点、`p` 的左列断开，形状按字母重画并且金表在 TB 里独立手写
（`开发台账` 的 #97 之后那一段）。

### 3.2 小写为什么整批删掉（不是为了美观）

`src/rtl/video/osd_overlay.v:405-407`：28..43 是小写让出来的空洞，理由是
"5×7 字模做不出真正的降部（p/q/y 尤其明显），不是画得不好，而是**这个字号画不出** ⇒ 屏上只有大写"。
工程上的落点在**写侧**而不是读侧：`put` 里 `if (u >= 0x61 && u <= 0x7A) u = u - 0x20`
（`:190-198`），因为读侧 `ch → gi → font → b_reg` 是全设计最差路径的主体，
"在这里折一次只多一句比较 + 一次减法，换来译码表少 17 个分支"（`:187-189`）。
`glyph_idx` 里因此**不认** 0x61~0x7A（`:474-475`）。

### 3.3 四刀的时间线与读数

| 刀 | 改的是什么 | 实测读数 | 采纳 |
|---|---|---|---|

### 3.4 今天这条链上还剩什么

读侧只剩"取字符 + 并行译码 + 选行"（`src/rtl/video/osd_overlay.v:485-486`）：

```
wire [15:0] ch_addr    = s_line * MAX_CHARS + s_cidx;         // :489  移位+或（MAX_CHARS=32）
wire [15:0] ch_addr_pre= line * MAX_CHARS + cidx;             // :500  与被寄存的 s_* 同源同拍的那一对
reg  [7:0]  ch_r;  always @(posedge clk) ch_r <= chars[ch_addr_pre];   // :501-502
wire [5:0] gi = glyph_idx(ch_r);      wire [2:0] fx = s_pix_x / SCALE;   // :504-505
wire [2:0] fy = (s_pix_y < 7*SCALE) ? (s_pix_y / SCALE) : 3'd6;         // :506
wire [4:0] font_row = font[gi][fy];    wire pixel_on = s_in_char && (fx < 5) && (font_row[4-fx]);  // :507-508
```

`/SCALE` 只有 5 个取值，本来就不深。**当前**这一组最差路径的身份已经不再是"字模链"而是"字格地址链"：
`src/rtl/top/pl_video_top.v` 的 `x_d[20]` 那一拍坐标 → `u_pl/u_osd/ch_r_reg/ADDRARDADDR[6]`，
3.630 ns、22 级（`CARRY4=9`）、route 59.15 %（`build/timing_summary.rpt:739-748`）。
终点是 `RAMB18E1` 的地址脚——160 格 × 8 bit 的字符缓冲在硅上是一块 **Block RAM 带寄存读出**，
所以 `ch_r` 那一拍不是 8 个触发器，而是一次 BRAM 读（同一份件 `:743`、`:830` 与
`:742-743` 的地址脚说明；全设计 RAMB18 共 5 只，`build/utilization.rpt:109`）。

`ch_addr` 与 `ch_addr_pre` 是**两根线**，这不是冗余：`src/rtl/video/osd_overlay.v:487-488` 说明读地址要
"起一根线"给台架的越界判据吃真信号，而不是让台架按同样的式子重算一遍——重算式看不见"将来有人改了地址算术"
（`sim/mut_control.sh` 的 `osd_addr` 分支实测过这个盲区（这个台架工具现在的位置是 `build/sim/mut_control.sh`，RTL 注释里的 `sim/` 前缀已经漂了））。

### 3.5 那一拍切下去的可见性风险

流水线切错一拍，屏上的字会整体挪一格，而原来的判据只数**亮像素总数** ⇒ 总数一个都不变，会绿着错。
对策记在 `开发台账`（#96 的判据段）：`sim/tb_osd_lines.v` 的 `scan_glyph` 改成
逐像素比对（每格 35 个像素全比）+ 样本数必须 35（不许空集）；并且**牙验过了**——
把探针里那个采样沿去掉（模拟"读早一拍"）⇒ `RESULT tb_osd_lines FAIL (39 errors)`，
报"格(3,17) 逐像素 16/35 不对（形状平移/错行）"，加回来 ⇒ PASS。
最终裁判是 `sim/tb_v98_top_seam.v`：它的 C3 三把尺子用**面板自己的** `de_osd/vs_osd` 建坐标系，
所以延迟变了也必须仍然对上。

### 3.6 越界索引：一条"机会计数"判据

`chars[]` 只有 160 格，而地址是 `s_line*32 + s_cidx`。`s_line` 是 3 bit、`s_cidx` 是 5 bit ⇒
最大索引 255 > 159，整屏扫一遍必然有越界的读。这一件事被做成了**可数**的：
`sim/tb_osd_lines.v` 的 T18 判"越界的那些拍里没有一次 `s_in_char=1`"（读到什么都不画），
读数是 **190464 拍**（`build/evidence/r86_osd_t18_teeth_addr.txt:12`，同一数登记在
`data/metrics.csv` 第 17 行与 `结果页`）。

这条判据的来历与强度都在那份件里：`build/evidence/r86_osd_t18_teeth_addr.txt:2-4` 是一段注错差分
（把 `ch` 的地址加 `6*MAX_CHARS`，恰好 1 行改动），而 `:14` 留了一句老实话——
**修复前的写法上 T18 仍然不红 ⇒ 判据当时测不到那一族，别把它当凭据**。
"屏上没现象"与"真的被门住了"这两种说法因此第一次可以区分（`data/metrics.csv` 第 17 行的测量条件列）。

## 4 分割线：一条缝 + 两个抽头 = 同屏 A/B

### 4.1 几何前提：为什么必须先改成"一条地址流覆盖全屏"

`src/rtl/video/split_ctrl.v:2-6` 的文件头记了这件事：V8-4 写这个模块时屏上是"左右各 512、每半屏各画一整幅"
的双屏几何，于是"缝 0~100 % 可调"在数学上与它**不相容**——缝只能钉死在 512。
统一成"一条地址流覆盖全屏 + 逐像素选原图/处理图"之后（`src/rtl/top/pl_video_top.v:237-241`，r59b-1 / #73），
"分割线 0~100 % 可调"与"整体旋转缩放"第一次相容，代价是原图抽头必须过一条行环（4.3）。

同一次改动删掉了旧的 `cx_q*/cy_q*` 三拍打拍与 `sx_l/sy_l`（`src/rtl/top/pl_video_top.v:336-338`），
也删掉了那对 `pix_left/pix_right` mux（`:769-772`）——那对 mux 是 #68 暗带的另一半：
"标签与内容不同级时被清零的一路会在缝旁留一条带"。现在只有一个流，那一族结构上消失。

### 4.2 缝发生器：三角波、端点、速度、夹紧

`src/rtl/video/split_ctrl.v` 是纯像素域时序，只吃 `de`（有效像素旗标），不数空拍
（`:6`、`:15`）。四个要点：

**① 坐标空间由 `follow` 选，两个分支都是 elaboration 常数**
（`wire [16:0] W = follow ? SRC_W17 : DISP_W17;`，`:33`）⇒ 综合出来是 2:1 选线，
既不是除法器也不是桶形移位器。顶层递的是 `#(.DISP_W(2*PANE_W), .SRC_W(IMG_W), .TICK_BITS(16))`
（`src/rtl/top/pl_video_top.v:885`）⇒ 不跟随时装 0..1024 显示列，跟随时装 0..512 画面列。

**② 端点用 1/16 宽度作单位**（`lo16/hi16`，0..16）⇒ 换算成像素就是一位移位 `(u*W)>>4`，
不给"端点落在哪一像素"留二义性（`src/rtl/video/split_ctrl.v:35-42`）。
`hi < lo` 是**合法输入**（`split range 80 20` 就会这样），不许它把三角波甩出界 ⇒
先折成 `[min,max]`（`:43-47`，台架 T3 单独判这一条）。

**③ 计数按有效像素走，不按"第几拍"**（`src/rtl/video/split_ctrl.v:64-66`）：这是 #54/#56 那一课——
任何拿每拍计数器与"0/末列"比的判据，换一种消隐宽度或占空比就会挡住不同的列 ⇒ 台架与板子给出两个不一样的答案
（`tb_rotate_window` 的 `SLOT_LAG` 假红、"分割线旁边的颜色条"都源于此）。
手工模式下把扫描值**跟住**手工位置（`:73-76`），于是打开 auto 的那一瞬间不跳位——
演示里"扫起来先跳一下"会被当成 bug。到端点那一拍同时换向，波形在 lo/hi 各停一拍，绝不越界（`:80-84`）。
减法判界要防下溢：`hi` 很小而 `speed` 很大时 `hi13-step` 会回绕成巨大数 ⇒ "永远没到端点" ⇒ `swp` 一路涨出去，
所以先夹一次（`:58-62`）。

**④ 位置夹紧到 `[0, W]` 而不是 `[0, W-1]`**：手工位置允许合法地等于 W（"缝推到最右"= 整屏都是缝左侧那一半），
`src/rtl/video/split_ctrl.v:92-99`。中途改 range 时旧 `swp` 可能暂时在新端点之外，`eff` 那一级再夹一次
（`:100-103`）。

扫描一格的物理时间：`tcnt` 数满 `2^TICK_BITS = 65536` 个**有效像素**才走 `speed` 格
（`:77-85`），顶层 `SPEED=4'd1`（`src/rtl/top/pl_video_top.v:19`）、一行 1024 个有效像素
（`src/rtl/top/pl_video_top.v:800` 的 `H_ACTIVE = 2*IMG_W`）⇒ 一步 = 64 个显示行；
端点 `SPLIT_LO16=2 / SPLIT_HI16=14`（`src/rtl/top/pl_video_top.v:20-21`）在 1024 宽下是 128..896，
单程 768 步 ⇒ 49152 行 ≈ 82 个显示场 ≈ 1.38 s（600 行/场、面板场频 1344×625@50 MHz ⇒ 59.52 Hz）。
**这一组是代出来的推算，未量**（量的话要在台架数 `split_eff` 的变化沿，本文没有那份件）。

百分比那一格单独寄存了一拍，而且**不许删**（`src/rtl/video/split_ctrl.v:118-129`）：
这一级寄存器是给 r60 那条 −0.482 ns 准备的——当时全设计最差是
`u_split_ctrl/swp_reg[7] → u_osd/r_reg[1]`，28 级、里面有一个 DSP48，起点就是这里的 `eff × PCT`
（端点/扫描值 → 百分比乘法 → OSD 的十进制拆位 → 字模 → 像素）。
乘法本身在 50 MHz 下没问题，**串到 OSD 的字符装配后面**才有问题；而这个数只是屏上给人读的一格，
晚一拍完全不可见。这正是 1.2 那条纪律的第三次应用。

一处**文档与事实不符**必须点名：`src/rtl/video/split_ctrl.v:3` 的文件头还写着"本模块目前没有被任何顶层例化
（连同 `sim/tb_v93_split_ctrl.v` 先单独做完、单独判住）"，而顶层的例化就在
`src/rtl/top/pl_video_top.v:885-891`，且 `split_display` 的 `seam` 输入由它驱动。
这句注释属于 #51 接上去**之前**的状态，随第 08 章 6.4 第 2 条一起留在清单里。

### 4.3 同屏 A/B 的硬件：两个抽头 + 逐像素二选一

真正的"切"发生在 `src/rtl/video/split_display.v:43-53`，四行组合逻辑：

```
left      = seam_in_src ? ~src_orig : (x_sel < seam);
oob       = left ? oob_l : oob_r;
take_orig = seam_in_src ? src_orig : (raw_left ? left : ~left);
sel       = oob ? 16'h0000 : (take_orig ? orig_pix : proc_pix);
sep       = marker && (seam_in_src ? src_mark : ((x_sel == seam-1) || (x_sel == seam)));
```

- `x_sel` 必须是**与两个像素抽头同一级**的列坐标（`:9-15`）。以前直接用 `x` 判左/右、也用它画那条 2 px
  标记线，而顶层的 `x` 是第 11 级标签、`orig_pix/proc_pix` 是第 20 级的内容（3 拍打地址 + 1 拍读地址寄存 +
  1 拍 BRAM + `u_pipe.LATENCY`=15）⇒ 判定比内容旧 9 列 ⇒ 缝左边约 9 列里"标签说左窗、内容其实是右窗那一路
  （被强制清 0）"⇒ 一条近黑的竖带。这就是用户念的"缩放碰到分割线时周围出现颜色条"的第二个成分
  （第一个是故意画的蓝线，4.5）。修好之后 `x/y/de/hs/vs` 仍按原级数穿过输出寄存器 ⇒
  OSD 位置一个像素都不动，只有"选哪一路"与"标记线画在哪一列"跟着内容走。
- `oob` 对两个抽头是**同一件事**（同一份源坐标）⇒ 一位喂两口
  （`src/rtl/top/pl_video_top.v:924`，`:926` 那对 `.oob_l/.oob_r` 都接 `oob_out`）。
- 两个抽头必须**同深**：链子 `PROC_LAT` 拍，原图那一路是行环 + skid，行环本身多 1 拍 ⇒
  给处理抽头补一级 `pipe_dout_q`（`src/rtl/top/pl_video_top.v:819-829`，第 08 章 4.2 记了同一笔）。
- 原图抽头为什么要过一条行环，写在 `src/rtl/top/pl_video_top.v:775-781`：地址只有一份，而它的行号带着
  效果链的提前量 `cy_r`——那个提前量是给链子准备的（链子内容天生滞后 4 行），原图抽头不需要它。
  补偿不是再开一个读口（第二个逻辑读口实测把 80 块 BRAM 顶到 160 块，全片才 140），
  而是把原图抽头整体延后 `OFF_LINES` 个显示行，且 `LINES` 的唯一合法出处是 `u_pipe.OFF_LINES`（`:781`）。
  **越界标签与像素必须过同一条环**（`src/rtl/video/raw_line_delay.v:11-16`，打包成 17 bit）：
  以前标签绕开环只走等长 skid ⇒ 到混色级两者差 (4 行, 1 列)，画面右沿最后一列被"别的格子"的越界位按黑。
  17 位仍在 RAMB36 的 18 位宽度模式里 ⇒ BRAM 一块不多要（这句话自己要求"要在 utilization.rpt 上核"）。

### 4.4 follow：把判据从显示列搬到图像列

`src/rtl/video/seam_src.v:2-6` 讲清了它补的是哪半件事：`follow` 位当时只改了**扫描坐标系**，
线本身还是屏幕空间 ⇒ "follow"名不副实。用户要的是"蓝线放在视频中间、在视频的两端去转，而不是在整个屏幕上扫"。
改法是**分类在源头做**：

```
in_band = (sx == seam) || (sx == seam - 1);     // 蓝线宽 = 2 个图像列
mark_n  = marker_on && in_band && !oob;         // 画面外不画
orig_n  = (sx < seam) ? raw_left : ~raw_left;   // 只由 swap 那一个位决定
```

`src/rtl/video/seam_src.v:26-30`。`sx` 站在 `zoom_mapper` 输出那一拍（= 显示坐标之后第 3 拍），
而混色级看的内容站在 `x_d[MIX_D]` ⇒ 要打 `TAPS = MIX_D + 1 − 3` 拍（`:21-23`、
顶层 `src/rtl/top/pl_video_top.v:899-902`）——**由流水线深度推出来，不许再抄字面量**（#68 那一课）。
这一路的省法也值得注意：晚/早几拍在这里只是把整条线刚体平移几列，**不会**再制造暗带，
因为暗带的根因是"标签与内容不是同一份流"，而这里两者是同一份流上的同一个位。
于是只需要两个位跟着内容走 18 拍，而不是把 12 位的 `sx` 打 18 级再比较——少 200 多个触发器，
也少一条 12 位布线（`src/rtl/video/seam_src.v:24-25`）。复位值 `sh <= 2'b01`（"原图、不画线"）
与旧代码 oob 时的观感一致（`:35`）。

### 4.5 那条 2 像素蓝线

`split_display.v:63-64`：`sep && de` 时输出 `{8'h40, 8'h40, 8'hFF}`。它的开关位是**反着写的**——
`gp[13] = 1` 才是"关"，所以复位与 PS 从没写过时屏上仍有那条线
（`src/rtl/top/pl_video_top.v:892-894`，与 r59a 的观感口径一致，"故意画的"那条说明在板上操作卡里）。
PS 侧的语义换算在 `src/ps/main.c:1136-1137`：`marker` 这个词的语义是"画不画"，位是 `marker_off`，
所以命令里 `marker 1` 写的是 0。

接上它们要再挤 5 位控制字并重开一条跨域账。

### 4.7 100 % 念成 99 %：一道夹与它的来源

字段只有 10 bit（`cfg1[22:13]`）而屏幕宽 1024 ⇒ `SPLIT_POS_MAX = 1023`（`src/ps/main.c:125`）。
`split 100` 算出 `px = 100*1024/100 = 1024`（`src/ps/main.c:1186`，那句除法注释写明"除法只在 PS 做一次，
PL 无除法器"），`1024 << 13 = 0x800000` 恰好落到 bit23 = `SPLIT_AUTO_BIT` 上。
**不夹的历史症状在板上复现过两次**，两份记录都在盘上：

- `build/probe_split100_old.txt:6-11`：`>> split 100` 的回显是
  `[SPLIT] 100% -> pos=1024/1024（显示列；manual；屏上 Split 格应显示 100%）`，
  而紧接着 `>> split show` 念出 `[SPLIT] pos=0/1024（显示列） = 0% manual marker=on`——
  缝位是 0，回显却说 1024/100 %；
- `build/probe_split100b_old.txt:10-16`：`split video` + `split px 512` 再 `split screen` 这一条写口
  **不清 auto**，于是缝跳到第 0 列 + 自动扫描**悄悄开起来**，回显还说"auto 仍开着"
  （`src/ps/main.c:130-132` 记的就是这一支）。

现在的处理是三处写口都在**存进寄存器之前**夹一道，并且**明说夹了**：
`split_pos_clamp()`（`src/ps/main.c:162-169`，返回 1 = 夹过，调用方必须在回显里说出来）被
`:1161`、`:1177`、`:1187` 三处用；回显与屏上那一格的百分比都由**存进去的值**反算
（`src/ps/main.c:1190-1195`），所以 100 % 念成 99 %、30 % 念成 29 %
（`report/commands.md:203`、`report/commands.md:286-288`）。为什么由调用方打印而不是函数里打印：
三处写口的文案各自不同，而"夹了"必须与那一处报出的百分比**同源**——回声与执行值不同源是这一族病的签名。

三个"为什么这样夹更好"的账也写在 `src/ps/main.c:133-136`：`cfg1` 三十二位已经排满
（`[8:0]` 效果、`[12:9]` 旋转、`[22:13]` 缝位、`[25:23]` 三个旗标、`[28:26]` 缩放档、`[29]` 手动、
`[30]` 蓝线、`[31]` 拟合），塞不进第 11 位；差的这一列是 1/1024，比"用户没要求却开了扫描"轻得多。
PL 那一侧其实允许 1024（`src/rtl/video/split_ctrl.v:93-98` 把 eff 夹到 `W` 而不是 `W-1`），
所以这一列是被 PS 侧的**字段宽度**丢掉的，不是被硬件丢掉的。

板侧的期望写在 `board/HANDS_ON.md:90`：`split 0` / `split 100` 让整屏只剩一路抽头，而
`split 100` 会被夹到 1023 并在回显里说出来、屏上念 99 %；
`board/HANDS_ON.md:126-127` 进一步用它做"最左那一列不该是与画面内容无关的一条亮线"的对照。

**一处方向上的文案分歧要说清**（不是行为分歧）：`split_display.v:43,47` 与 `seam_src.v:30` 三处给出的式子
在 `swap=0` 时都是"缝**左侧**给原图"，于是 `split 100`（=1023）是"1023 列原图 + 最右 1 列处理图"，
`split 0` 是整屏处理图——`board/HANDS_ON.md:90` 与 `命令优先级记录` 就是这个读法。
但 `report/commands.md:288` 那句"左边永远留一列原图"与 `src/ps/main.c:128-129`
"要'整屏处理图'得到'整屏原图'"把两侧说反了。**行为侧没有争议**（三处 RTL 式子 + 两份板上件同向），
这两句是文案；本文按式子写，并把它们留作待改的文档账。

## 5 叠层的总开关与"关掉必须逐位等于背景"

`osd_en` 走的是它自己的一条 3 级 `ASYNC_REG`（`src/rtl/top/pl_video_top.v:263-275`），
源头是 `gpio_o[20]` 的**反相**位（1 = 关掉叠层，`src/ps/main.c:53-57`）。两个决定都有理由：

- **每一位各走一条链而不共用**：#65 那一次 CDC-11 就是"把两个翻转位挂同一级扇出"打出来的（`:264-265`）；
- **复位取 0（= OSD 开着）**：与固件默认一致 ⇒ 上电/PS 没写过时的屏上与加这个口子之前逐位相同，
  "开了口子但观感不变"是可查的（`:265-266`，同一手法也用在 `bilin_en` 上，`src/ps/main.c:217` 那一位
  复位取 1）。

开关落在**字形还是背景**那一级选择上，不另加一级寄存器（`src/rtl/video/osd_overlay.v:55-58`）⇒
关与开的内容延迟一模一样，顶层的 `MIX_D`/`PROC_LAT` 账一个字都不动。
判据成对：`sim/tb_osd_lines.v` 的 T13/T16 既判"关掉叠层后逐位等于背景"，也判"开着时必须 differ"
（文件头覆盖点那条"总开关正反成对"）。用途很实在：叠字会盖住画面最左上角那一块，
逐像素比对与拍摄时它是脏的（`src/ps/main.c:191-192`）。

## 6 排版与字符缓冲：一个 160 格的组合数组

### 6.1 为什么按实际位数打，而不是固定格

`src/rtl/video/osd_overlay.v:183-185`：格式定的是 `Th:80`、`Split:50%`，
固定三位右对齐会打出 `Th:080` / `Split: 50%`。代价是"某一格在第几列"不再是常数 ⇒
判据按**整串比对**，更不容易被"挪一格"糊过去。实现是三个 task：`at(ln)` 定位行首、
`put(c)` 打一个字符（顺带折大小写、并做越界保护 `if (col < N_LINES*MAX_CHARS)`，`:190-198`）、
`puts(s,n)` 打 n 个字符（`:199-204`），数字有 `putd3`（百位十位按前导零省略，全零时打一个 "0"，
因为 0 也是一个要看的数，`:205-212`）、`putnum`（10 bit 的 /100、/10、%10，`:213-217`）、
`putnum4`（只给面板宽高，1.5）。

`put_src` 的两个入参 `se/md` 必须是**任务入参**而不是任务里直接读全局信号
（`src/rtl/video/osd_overlay.v:241-242`）：否则切片源时那一整块不会被重新叫醒，屏上永远留着旧名字。
这是本章唯一一处"结构即判据"的写法问题，实际后果是一条会撒谎的格子。

### 6.2 拆位在 OSD 里也要分拍

Latency 那一格的十进制是**两拍算完**的（`src/rtl/video/osd_overlay.v:164-177`）：
第一拍 `lt_h <= lat_v / 100`、`lt_rem <= lat_v % 100`，第二拍再从余数取十位个位。
一次算三位在 50 MHz 像素域是二十几级组合链——**这么做时 WNS 到过 −6.765**（`:165-166`）。
这个数一帧才变一次（甚至几帧一次），晚一拍对人眼没有任何影响，而 OSD 一像素都不该抖。
同一招在第 08 章出现过（温度的十进制换算挪到 PS 侧），在缝百分比那一格也出现过（单独一级寄存器）。

### 6.3 与第 08 章链子的接缝

OSD 用的坐标是 `x_d[MIX_D] / y_d[MIX_D]`、`de` 用的却是 `de_o`（`de_d[MIX_D]` 再打一拍，
`src/rtl/top/pl_video_top.v:1001-1005`，#92 第二笔）。注释把关系钉死了：它与 `de_o` 的相对关系一格都不变
（"仍是早一拍"，与改前 `x_d11` vs `de_d11+1` 完全同形）⇒ OSD 在屏上的位置一个像素都不动，
动的只有"画面 vs 面板有效窗口"那一笔。这一句之所以重要，是因为 `MIX_D` 的定义里就有 `u_pipe.LATENCY`——
链子改一拍，OSD 的位置、缝的位置、标记线的位置会一起漂。
