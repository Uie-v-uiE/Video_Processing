## 1 前置知识（只收这一章要用的，并且全部换成仓库自己的数字）

### 1.1 这条曲线在这里长什么样

`docs/course/02-gamma-principle-to-rtl.md:5-13` 把"为什么需要 gamma"讲完了（人眼对暗部更敏感、
显示器件本身走 `V^2.2`、工程上不做浮点），本章不重复论证，直接把这一版实现用的那一条式子抄下来。
式子只有一份，在 PS 侧，`src/ps/main.c:376-383`：

```c
static u8 gamma_curve(u32 g100, u32 i)
{
    float e = 100.0f / (float)g100;                       /* :378 */
    float y = pow((float)i / 255.0f, e) * 255.0f + 0.5f;   /* :379 */
    if (y < 0.0f)   y = 0.0f;                              /* :380 */
    if (y > 255.0f) y = 255.0f;                            /* :381 */
    return (u8)y;                                          /* :382 */
}
```

三个必须钉住的读法：

1. **它是 `x^(1/γ)`，不是 `x^γ`**。形如 `y = 255·(i/255)^e`，而 `e = 100/g100 = 1/γ`（`:378`）。
   串口里那个数（`gamma 1.8`）是 γ，代码算的是它的倒数幂。所以 **γ>1 ⇒ e<1 ⇒ 曲线整体上提、暗部拉开**，
   这一点很容易被念反，`main.c:375` 的那行注释 `out = 255·(in/255)^(1/γ)` 就是防这个的。
2. **定义域/值域都是 0..255 的整数**（`:380-382` 两侧夹位），所以"表项"天然就是 8 bit，
   与 `gamma_lut.v:27-29` 声明的 `reg [7:0]` 对得上，没有任何一处需要再解释"表宽为什么是 8"。
3. **`+0.5f` 然后截断 = 四舍五入**（`:379` + `:382`）。这是本条曲线唯一一次取整，
   它给的是 `±0.5`（8 bit 单位）的误差；后面 §4 会算它在整条通路里占多大比重。

量程：`main.c:400` 只认 `100..300`（即 γ=1.00..3.00），越界就拒绝并且**不改任何状态**
（`:401-403` 打完就 `return`）。`report/commands.md:194` 那行表写的就是这个范围。
γ×100 是 PS 侧的量纲（`main.c:291` 的 `cur_gamma`），跨到 PL 的只有 γ×10、6 bit（`:101-102`、
`effect_ctrl.v:24`），而且这一份**只给 OSD 看，不参与任何运算**（`effect_ctrl.v:24`、`60-61`）。

### 1.2 为什么是查表，不是算术

`gamma_lut.v:4` 那一行就是本仓库给的理由，原文：
"用表不用幂函数：PL 里做 `in^(1/γ)` 要堆 DSP 或做对数/指数近似"。这条选择有两个可以直接核读数：

- **实现结果里 gamma 一支的 DSP 是 0**。逐实例账：`build/util_hier_probe.rpt:70`
  那一行是 `u_gamma | gamma_lut | 191 | 95 | 96 | 0 | 1 | 0 | 0 | 0`，
  列头在 `build/util_hier_probe.rpt:23`（`Total LUTs | Logic LUTs | LUTRAMs | SRLs | FFs | RAMB36 | RAMB18 | DSP Blocks`）
  ⇒ DSP Blocks 那一列是 **0**，RAMB36/RAMB18 也是 **0**。
  ⚠ 这一条把指标表的一处失实顶了出来，并且**已经改口**：`data/metrics.csv:11` 原先写 DSP"用在缩放/旋转的
  坐标乘法与 **gamma 计算**"，而 `gamma_lut.v` 全文一个乘号都没有（整个文件读过，只有拼接与位选），
  逐实例报告 `build/util_hier_probe.rpt:70` 那行 `u_gamma` 的 `DSP Blocks` 是 **0**。
  现在那张表念的是 19 的逐实例分解（`u_lerp` 6 ＋ `u_blur` 1 ＋ `u_split_ctrl` 1 ＋ `u_zfit` 3 ＋ `u_zmap` 8 ＝ 19，
  与 `build/utilization.rpt:121` 的总数闭合），改动同时落进 `资源章`、`结果页`、
  `report/measurements.md`（台账 #389）。
  **这里留下的真正教训是：数对上了不等于归属对上了**——`metric_recheck` 能把 19/220 对回报告总数，
  却判不出"这 19 只算在谁头上"，所以"资源归属句"目前没有尺子（这条债记在 #389，不在本章解决）。
- **代价从 DSP 转到了 LUTRAM**：同一行给出 96 只 LUTRAM、95 只逻辑 LUT、1 只触发器（这 1 只就是
  `gamma_lut.v:34` 的 `prev`，见 §2.4）。器件总量纲在 `build/utilization.rpt:35-39`
  （Slice LUTs 14154 / LUT as Logic 9969 / LUT as Memory 4185 / LUT as Distributed RAM 4044），
  原语名册 `build/utilization.rpt:195` 那行是 `RAMD64E | 4044 | Distributed Memory`。

另一个理由不是资源，而是**可变性**：表在 PL、曲线在 PS ⇒ 换一条 γ 不需要重新综合。
`main.c:281-283` 把这条分工写成了验收口径："算错曲线"由 `gamma_curve()` 自带的端点+单调自检负责，
"接错线"由 `sim/tb_v88_gamma.v` 的八条判据负责。两件事各有凭据，这一点在 §6 会展开。

### 1.3 量纲地图：这条通路到底有几 bit

这是本章所有结论的地基，先把"名字相似但量纲不同"的四段宽度摆出来：

| 段 | 宽度 | 出处 |
|---|---|---|
| 链上流动的一只像素 | **16 bit RGB565**（R5/G6/B5） | `gamma_lut.v:15-16`、拆分在 `:20-22` |
| 单通道扩展后 = 表的**索引** | **8 bit** | `gamma_lut.v:23-25` |
| 表本身 | **256 项 × 8 bit**，三张 | `gamma_lut.v:27-29` |
| 查表后回到链上的宽度 | **5/6/5 bit**（取表值的 `[7:3]`/`[7:2]`/`[7:3]`） | `gamma_lut.v:51` |
| 面板真正拿到的 | 8 bit（在这里才被展开回去） | `src/rtl/video/split_display.v:66-68` |

⇒ 关键结论（后面全部量化都挂在它上面）：**表算到 8 bit，但出这支模块的只有 5/6/5 bit，
而且这 5 bit 一直到显示端才被重新展成 8 bit**。所以表值低 3 位（R/B）/ 低 2 位（G）
在硬件里根本没有出口 —— 它们不是"精度损失"，是**从来没有被用过的 3 行位**。

节拍与位宽无关，但和"能不能随机读"有关：这一支在 `clk_pix` 单域（`proc_pipeline.v:7`），
周期 20 ns 的量级在台架里写成 `always #10 clk = ~clk`（`sim/tb_v86_pipe_sel.v:30`），
`effect_ctrl.v:2` 的文件头把两个域点名了：AXI GPIO 100 MHz → 像素域 50 MHz。

### 1.4 索引可达集：256 项里每拍只有 88 格可能被读到

`gamma_lut.v:23-25` 的扩展是**位复制**，不是补零：

```
r8 = {r5, r5[4:2]}   （5 位复制高 3 位到低 3 位）
g8 = {g6, g6[5:4]}   （6 位复制高 2 位）
b8 = {b5, b5[4:2]}
```

于是 R/B 的索引集合只有 32 个值、G 只有 64 个。按上面这两条式子（`gamma_lut.v:23`、`:24`）
我自己算了一遍（**不是板子读数，是把式子代进 0..31 / 0..63**）：

- R/B 可达索引的头六个是 `0, 8, 16, 24, 33, 41`，尾三个是 `239, 247, 255`；
- G 可达索引是 `0, 4, 8, 12, 16, 20, 24, 28, …`（4 的倍数加上高位进位）；
- 两个集合不是包含关系：`33` 在 R 集合里但不在 G 集合里 ⇒ **三张表合起来的可达索引是 88 个**，
  256 项里有 **168 项永远不会被任何一读命中**（R/B 各 224 项不可达、G 192 项不可达）。

台架在写这条判据的时候就知道这件事，`sim/tb_v88_gamma.v:157` 的原文是：
"槽 0x11 不可达（`r5=17 ⇒ r8=0b10001_100=0x8C`，不是 0x11）"，
`:23` 的文件头更直接："R/B 只有 32 个可达索引（`r8={r5,r5[4:2]}`）、G 64 个 ⇒ 每张表先写满 256 槽再比"。
所以台架必须先 `fill()` 写满 256 槽（`tb_v88_gamma.v:79-91`），否则它拿一个不可达索引去比，
读到的是没写过的格子，判据就没有牙。

这条可达集直接给出三个工程结论：

1. **`gamma_set()` 那 256 次写里只有 88 次的值会被用到**（`main.c:405-413` 逐项写满）。
   为什么还要写满：`gamma_lut.v` 的读端口宽度是 8 bit，索引可达集将来会变（谁把 565 换成 888 立刻全可达），
   而且"写满"的代价已经算进 2.6 ms（`main.c:286-287`），不省这笔。
2. **曲线的实际分辨率 = 表可达索引的分辨率**，不是 256。给 γ 加小数位（`gamma 1.85`，`main.c:445` 只留两位）
   并不提高屏上能区分的级数，级数由 32/64 卡着（见 §4.2 的并级表）。
3. **三张表内容永远相同**：`gamma_lut.v:43-45` 把同一个 `data` 同时写进 `tr/tg/tb`。
   ⇒ 这套接口**不可能**做"每通道不同曲线"（红蓝分离的白平衡之类），
   三份复制只是为了"每通道各一个异步读口"，理由写在 `gamma_lut.v:3-4`：
   "三通道共用一张表 ⇒ 复制三份 RAM 各 1W1R：一份三读要额外读口，复制三份则内容永远由同一个写口保证一致"。

### 1.5 翻转位（toggle）而不是脉冲：为什么这一位必须"变"

PS 与像素域不是一个钟（`effect_ctrl.v:2`）。`gamma_lut.v:12` 那句端口注释是这一章最硬的一条协议：
"`wr`：**翻转位**，不是脉冲（脉冲跨不到本域）"。机理在 `docs/course/02-gamma-principle-to-rtl.md:53-55`
也写了：脉冲宽度只有一两个 PS 侧周期，像素域两拍同步器**可能整拍都采不到**。
翻转位只需要"电平在同步之后至少变过一次"，事件就丢不了。

配套的另一半在 `effect_ctrl.v:36-39`：`en/wr/data/idx` 四个字段**过同一对** 32 位 ASYNC_REG
（`reg [31:0] gm_meta, gm_sync`），文件头给出的前提是
"`wr` 是边沿标志，协议要求 idx/data 在 wr 翻转之前已经稳定至少一次 AXI 写 ⇒ 必须与 wr 同源同深度 ——
分两组同步就会出现在本域里'边沿到了、数据还是上一次的'那种错拍"。
PS 侧严格照这个协议走两笔写（`main.c:366-373`，见 §5.2）。

## 2 `src/rtl/video/gamma_lut.v` 逐行

全文 53 行，我一次读到底；下面按语义块拆，每一块都指回行号。

### 2.1 文件头（`:2-7`）已经把这一支的五个决策说完了

`:2` 定位：级 0，256 项 8-bit 表，PS 通过第二个控制字的通道 2 逐项写入。
`:3` 时钟域：像素域，读写都在这里（控制位由 effect_ctrl 同步）。
`:4` 为什么用表（见 §1.2）。
`:5-6` 写入协议：先写 `idx`+`data`、**下一次写把 `wr` 翻转** ⇒ PL 看边沿才写一项，
"地址与数据不必同时对齐（#36 那笔账的正面用法）"。
`:6` 为什么挂在**第 0 级**："是左窗原图/右窗处理图的一贯半屏对比语义"（这条在 §3 展开）。
`:7` 两件事一起讲：挂在第 0 级 ⇒ 不加拍数（分布式 RAM 非同步读出）⇒ LATENCY 常数不动。

### 2.2 端口（`:8-17`）

```
clk / rst_n / en / wr / idx[7:0] / data[7:0] / din[15:0] / dout[15:0]
```

`:9` `clk` 注释：像素域，读写都在这里；`:11` `en`：0 = 旁路，**逐位**等于输入（"台架第 1 条判据"）；
`:12` `wr`：翻转位；`:15-16` 一进一出都是 RGB565。
注意端口上**没有 `de`**：这支模块是纯点运算，不看有效信号，消隐期的 16 bit 也会被同样地查表
（下游按 `de` 取舍，链上 `de` 的走法见 `proc_pipeline.v:109-116`）。这也意味着 `en=1` 时
`dout` 在消隐期是"表对消隐值的查表结果"，但它不会进帧缓存，因为 `de_out` 一路没被它影响。

### 2.3 通道拆分与 5→8 扩展（`:20-25`）

`:20-22` 拆 R5/G6/B5；`:23-25` 位复制扩展。**为什么不抽一个公共函数**，`:18-19` 给了理由：
"与 proc_binary / proc_morph 各写一遍同一套 5→8 / 6→8 扩展：不共用是故意的，
三处公式必须能被独立核对，谁改了另一处会在'灰度图与 gamma 图对不上'时暴露"。
盘上这条式子实际出现**六次**（我逐处看过行号）：
`gamma_lut.v:23-25`、`proc_gray.v:18-20`、`proc_binary.v:19-21`、`proc_morph.v:30-32`、
`proc_sobel.v:33`（同一形）、`split_display.v:66-68`（输出端展回 8 bit）。
⇒ 这套"冗余"是**核对用的**，不是复制粘贴事故；改一处就是要造一次分歧。

位复制而不是补零，性质是 `r8 = 8·r5 + (r5>>2)`：单调、0→0、31→255。
`r5=17 ⇒ 17·8+4 = 140 = 0x8C` —— 这条与台架 `tb_v88_gamma.v:157` 的 `0x8C` 对得上，
两边是从不同方向算同一件事（台架把展开**又独立写了一遍**：`tb_v88_gamma.v:59-61` 的
`r = {p[15:11], p[13:11]}`，与 RTL 的 `:23` 互为对照）。

### 2.4 存储与写口（`:27-47`）

```verilog
(* ram_style = "distributed" *) reg [7:0] tr [0:255];   // :27
(* ram_style = "distributed" *) reg [7:0] tg [0:255];   // :28
(* ram_style = "distributed" *) reg [7:0] tb [0:255];   // :29

reg prev;                                                // :34
always @(posedge clk or negedge rst_n)                   // :35-38
    if (!rst_n) prev <= 1'b0; else prev <= wr;
wire do_wr = rst_n && (wr !== prev);                     // :39
always @(posedge clk) if (do_wr) begin                   // :41-47
    tr[idx] <= data; tg[idx] <= data; tb[idx] <= data;
end
```

**(a) 载体是 LUTRAM，三条独立凭据**

1. 代码显式指令：`ram_style = "distributed"`（`:27-29`）—— 不是"推断出来的"。
2. 综合警告口径：`资源章` 那一行 `SYNTH-5 | Mapped onto distributed RAM
   because of timing constraints | 336`，`:58-59` 把 336 条与"4044 项映射成分布式 RAM"讲成一回事的两面。
3. 布局后的**实例名**：`build/evidence/1006_csumconst_timing_summary.rpt:771-773` 里
   `u_pl/u_pipe/u_gamma/tr_reg_128_191_6_7/ADDRA1` → `SLICE_X66Y88 RAMD64E (Prop_ramd64e_RADR1_O) … /RAMA/O`。
   `tr_reg_128_191_6_7` 这个命名自己就把结构念出来了：`tr` 这张表里覆盖**地址 128..191、数据位 6..7**
   的那一只 RAMD64E。同一条证据链也说明它**不是** BRAM（BRAM 的实例会是 `RAMB18E1/RAMB36E1`，
   对照 `build/timing_summary.rpt:742-743` 那个 OSD 字符缓存的终点就是 `RAMB18E1`）。

数量对得上（**这一句是我做的除法，报告给的是读数**）：3 张 256×8 = 6144 bit，
`util_hier_probe.rpt:70` 报 `u_gamma` 的 LUTRAMs = 96 ⇒ 每只原语 64 bit（6144/96 = 64），
与地址段 `128_191`（64 格深）自洽。
`FFs = 1` 也是同一条证据：整支模块只有一只真触发器（`prev`，`:34`），
读写都不占寄存器 ⇒ 见 §2.5 的"零拍"。

**(b) 表不是编译期常量数组**

这一点必须说死，因为它决定很多行为。`gamma_lut.v` 全文**没有 `initial` 块、没有 case 常量表**
（整文件读过）：上电后三张表的内容就是 LUTRAM 的初值，也就是"没人写过"。
仓库里"编译期常量数组"长什么样有现成对照：`src/rtl/video/osd_overlay.v:333-345`
的 `reg [4:0] font [0:63][0:6]` + `initial begin … font[23][0]=5'b10001; …`。
所以 gamma 的 256 项**没有一项在盘上可以 dump**：要核对内容只有两条路 ——
要么看 PS 侧算曲线的那段（`main.c:376-383`）加它自带的自检，要么看台架里那份独立表（`tb_v88_gamma.v:39`）。
⇒ 所以"逐项 dump 表的端点与单调性"这条核对手法在这里**前提不成立**（没有可 dump 的盘上表）；
我改成核对**式子**与**自检**（见 §2.6 与 §6）。

**(c) 边沿检测与复位**

`:39` 的 `do_wr = rst_n && (wr !== prev)` 有两个作用：上电本身不算一次写（`:31-32` 的注释点名 ISSUES #52），
以及 `rst_n=0` 期间压住写。`:33` 还专门交代 `prev` 为什么走复位而不是 `reg prev = 1'b0;`：
"后者是 SystemVerilog 写法，本工程按 Verilog-2001 编"。
台架对这两件事各有一条判据：`T6b 复位本身不产生一次写`（`tb_v88_gamma.v:172`），
而它的前置条件 `T6a 此刻 wr=0`（`:166`）也写成了判据，`:165` 的注释很老实："前提不成立时这条判据就没牙"。

由这两行可以**推出**一个台架故意没覆盖的相位关系（我的推论，标明未量）：
如果 PS 的 `gm_w` 里 bit30 停在 1，而 PL 侧发生一次复位（重烧位流 / `rst_pix_n` 落下），
`prev` 复位成 0、`wr` 同步后是 1 ⇒ `do_wr` 在复位释放后的第一个允许拍成立一次，
`tr/tg/tb[idx]` 会被**用当前那一对 idx/data** 多写一笔。
这一笔不会丢任何项（后续每次翻转仍各写一项），而且写的就是同一张曲线里的某个合法格；
真正的后果在下一段。

**(d) 表是易失的，而 `en` 不是**

LUTRAM 无初值 ⇒ 位流一重烧，整张表清零。而 `gamma_en` 的值来自 PS 侧那个寄存器字，
PL 复位之后 PS 并不重新灌表（`main.c` 里只有 `gamma_set()`/`gamma_auto_start()` 会写表，
`:395-428`、`:327-344`；开机那段自检只验"窗口在不在位流上"，`:1552-1565`，明确"不许顺手把 gamma 打开"）。
于是"app 不重启 + PL 重烧"这个组合下，如果当时 γ 是开着的，`en=1` 而表全 0 ⇒ 查表结果全 0 ⇒ 处理那一路全黑。
仓库里对此的实际缓解是**流程约定**（先烧 PL 再跑 elf，开机自检 `main.c:1552-1565` + 位流/elf 配对由
`build/frozen_*` 的 md5 清单管，见 `main.c:75-76` 那句 ⚠），不是硬件保护。
这一条我**没有**板级凭据，属危险分析；要量它：烧位流时保持 app 运行并 `gamma 2.2`，
看屏是否右半全黑，再敲一次 `gamma 2.2` 看是否恢复。

### 2.5 读口与旁路（`:49-52`）

```verilog
wire [15:0] y16 = {tr[r8][7:3], tg[g8][7:2], tb[b8][7:3]};   // :51
assign dout = en ? y16 : din;                               // :52
```

`:49-50` 是一行命名警告：`packed` 是 SystemVerilog 关键字，xvlog 会当声明读。

**零拍**：`y16` 是组合线网，三张表是异步读（分布式 RAM 的本质），所以 gamma **不占拍数**。
这条在链上有两处对账：`proc_pipeline.v:21`（"级 0 的 gamma 是分布式 RAM 组合读出 ⇒ **不占拍**；
谁改成寄存读出（BRAM 风格）LATENCY 必须同时改成 16"）与 `proc_pipeline.v:18` 的逐拍账
（灰度1+反色1+模糊3+锐化3+Sobel3+阈值1+形态学3=15，`LATENCY=15` 在 `:22`）。
`tb_v86_pipe_sel.v:27` 把 15 定成台架常数 `LAT_EXPECT`，`:8` 的 T2/T3 判据是
"**实测** de_in→de_out == 模块声明的 LATENCY"，`:15` 的通过形状写得很清楚。
⇒ 所以 gamma 一旦改寄存读出，红的不是猜测，是 T3 那条实测。

**时序代价**：因为它不占拍，读出路径就必须**在别人的那一拍里**走完。
两份报告的读数正好给了两个答案：
- `build/evidence/1006_csumconst_timing_summary.rpt:730-739`：
  最差 `clkout0_1` 路径 Source 是 `u_pl/u_mode/mode_q_reg[1]/C`、Destination 是
  `u_pl/u_pipe/u_gray/dout_reg[8]/D`，Slack **3.723 ns**、Data Path Delay **15.983 ns**、
  Logic Levels 18，其中**明确列着 `RAMD64E=1`**，而那一行就是 `:772-773` 的 `u_gamma/tr_reg_128_191_6_7`。
  ⇒ 在那一次实现里，gamma 的表读出**在关键路径上**，而且终点是下一级（灰度）的 D 端。
- `build/timing_summary.rpt:739-748`：r118 那一份的最差 `clkout0_1` 路径是

所以逐实例账要跟着**当次**报告念，不能跨构建引用。

**旁路的性质**：`en=0 ⇒ dout===din` 是逐位，不是"表全黑"也不是"表恒等"。

### 2.6 索引边界与端点

`:51` 的位选取没有饱和、没有夹位：`tr[r8][7:3]` 恒 5 bit，因为 `tr[*]` 本身就是 8 bit。
地址边界：`idx` 是 8 bit，`[0:255]` 全可写，没有越界可能（`:43-45` 的地址就是 `idx` 原值）。
两端槽各写各读是判据 T7（`tb_v88_gamma.v:174-183`）：
`put(8'h00,8'h00)` 与 `put(8'hFF,8'hFF)`（`:175-176`），然后核 `r5=0 ⇒ ir===8'h00` 且输出 0、
`r5=31 ⇒ ir===8'hFF` 且输出 31（`:180-182`）。
`:177` 那句是关键说明：**0xFF 确实在 r8 可达集合里**（`r5=31` 且 `r5[4:2]=111`）——
我按式子代了一遍，31·8+7 = 255 ✓，所以这条判据同时是"最深一格能写能读"的凭据。

**表内容的端点与单调性怎么核对**（因为表不在盘上）：能核的是 PS 那三条自检
（`main.c:405-427`）——
- 单调：`if (v < prev) bad++`，逐 i 累计（`:407`，注释"幂曲线对 in 单调不降，反过来就是算错了"）；

- 判定：`bad != 0 || first != 0 || last != 255` ⇒ 额外打一行 `[GAMMA!] 曲线自检没过（表已写入但**不要**用它演示）`
  （`:426-427`）。注意语气：**表已经写进去了**，自检只是警告，不回滚、不关使能。
- 我按 `main.c:376-383` 的式子代了 γ=1.80/2.20/3.00 三档的端点，结果都是 `first=0, last=255`，
  且对 R 可达索引的序列逐档不降 —— **这是我自己算的**，与固件自检的口径一致，
  主机侧还有一条外部对照：`src/host/uart_cmd_check.mjs:90`
  `/\[GAMMA\] g=1\.80 mono_bad=0 first=0 last=255/`。
- 我**没有**逐项核对 256 项（没有可核对的盘上表，见 §2.4(b)）；这条要写明白，不冒充"全查过"。

## 3 这一级为什么排在最前面（只讲排队的理由，链本身见第 08 章）

### 3.1 位置：级 0，且是链上唯一不占拍的级

`proc_pipeline.v:100-106` 是整支例化，注释第一行就是"级 0 明暗：gamma。**组合读出，不占拍数**，
所以它不在上面那串逐拍账里"。接线是把链的输入 `din` 直接喂给它（`:105`），输出 `d0` 喂级 1（`:111`）。
`proc_pipeline.v:51` 给出级序的一句话定义："级序：gamma → 颜色 → 滤波 → 边缘 → 阈值 → 形态学
（阈值在滤波**之后**，形态学是对面具图的操作）"。

**控制位不在 `stage_sel` 里**，这是这一级与其余各级最大的不同：
九位控制字的位定义是 `[0]灰度 [1]反色 [2]模糊 [3]锐化 [4]Sobel [5]二值化 [6]判决反相 [7]腐蚀 [8]膨胀`
（`proc_pipeline.v:6`，端口 `:31`），gamma 用的是**另一个字的另一个位** ——
`gamma_en` 是独立端口（`proc_pipeline.v:33`，来自 `effect_ctrl` 的 `:20`）。
⇒ 后果：`pipe 000000000`（六级全旁路）**不等于**"画面逐位不动"，
只有 `gamma_en=0` 才保证这一点。这正是 `[GAMMA]` 回声（`main.c:1211-1216`）与 `[STAT]` 里的 `gm=`
字段（`main.c:1381-1389`，`sel=%03x` 与 `gm=%d.%02d` 是两个字段）要独立于 `sel=` 各报一处的原因。

### 3.2 排在颜色之前的算术理由

级 1 的灰度是**线性加权求和**：`y16 = r8*77 + g8*150 + b8*29`、`y8 = y16[15:8]`
（`proc_gray.v:22-23`），二值化与形态学的亮度走同一条式子（`proc_binary.v:22`、`proc_morph.v:33`）。
γ 是**非线性**的，非线性与线性求和不可交换：先求和再上 γ，得到的是"亮度的 γ"；
先按通道上 γ 再求和，得到的是"三个通道各自 γ 之后的加权和"。两条曲线在屏上是两回事。
这一版选了后者，而语义在 `gamma_lut.v:6` 就写完了 —— 挂在第 0 级是为了"左窗原图 / 右窗处理图"
的半屏对比：观众看见的是"同一张传感器码值，明暗被换过一次"，不是"亮度算法的差别"。

### 3.3 只作用于处理那一路

链的入口与"原图抽头"取的是**同一份** `pix_raw`，但只有链里的那一路过了 gamma：

- 处理路：`pl_video_top.v:800-810` 例化 `u_pipe`，`.din(pix_raw)`（`:808`），输出 `pipe_dout`（`:809`）；
- 原图路：`pl_video_top.v:790-792` 的 `raw_line_delay` 抽头，`.d_in({oob_raw, pix_raw})`，**不进链**；
- 混合：`split_display.v:47-48` 用 `take_orig` 在 `orig_pix` 与 `proc_pix` 之间逐像素选，
  顶层两个抽头接在 `pl_video_top.v:911` 与 `:923`（`.orig_pix(orig_disp), .proc_pix(pipe_dout_q)`）。

⇒ 所以 `gamma 1.8` 一开就是**缝两侧明暗直接对比**，这句话不是我推的，是仓库的口径
（`report/commands.md:232-236`："整屏一个视口，语义是'缝的左边给原图、右边给处理图'……
不需要额外做整屏 A/B 键"）。纯 PL 演示顶层干脆把这一级钉死关掉：
`pl_demo_top.v:84` 写 `.gamma_ctl(32'd0)`，`:79` 的注释把后果说明白了
"gamma_ctl = 0 ⇒ 级 0 的 en=0、逐位旁路，OSD 的 Gamma 那一格因此画 0.0（=没开）"。

### 3.4 与第 08 章的分工

九级的旁路语义、四个窗口级的行缓存与边界旗标、`OFF_LINES = 4` 的内容偏移（`proc_pipeline.v:23-27`）、
坐标延迟线 `xd[1:12]` 那两笔硬件后果（`proc_pipeline.v:71-82`）都在第 08 章。
本章只保留一句与 gamma 有关的对账：**gamma 不进那份拍数账**，
所以任何"链总延迟"的讨论里它都应当是 0；如果谁给它加了一拍，红的不是推测，
是 `tb_v86_pipe_sel.v:8` 那两条实测（T2/T3）与 `tb_v88_gamma.v:126`/`:133` 那两条逐位判据。

## 4 取值量化：把能算的都算出来

### 4.1 误差预算表

| 环节 | 动作 | 引入的量 | 出处 |
|---|---|---|---|
| PS 算曲线 | `pow(...)·255 + 0.5` 再截断 = 四舍五入 | ±0.5（8 bit 单位） | **[码]** `main.c:379-382` |
| PS 端点夹位 | `y<0→0`、`y>255→255` | 对 `i∈[0,255]`、`e∈(0,1]` 不触发 | **[码]** `main.c:380-381`；**[算]** 端点恒 0/255 |
| 写入 | 8 bit 原样进表 | 0（无损） | **[码]** `gamma_lut.v:43-45` |
| 索引 | 位复制扩展 5/6 → 8 | 0（可逆，见 §4.4） | **[码]** `gamma_lut.v:23-25` |

**[算] 那一格怎么来的**：对 `v = 0..255` 全体，`v − (v>>3)·8` 取值 0..7 循环 ⇒ 最大 7、平均 3.5
（8 bit 单位）。换成"565 的 R 一个 LSB"的量纲（R 的 LSB = 255/31 ≈ 8.23）就是
**最坏 0.85 个 R-LSB、平均 0.43 个** ⇒ 截断永远不足以让输出跨过一级。
再把三条曲线代进**可达**索引（`out5 = curve(γ, r8) >> 3`，γ=1.80/2.20/3.00）：
损失最小 0、最大 7、均值 3.75 / 3.81 / 3.25。
**[未量]**：屏上看不看得见这一档。要量它：同一张灰阶斜坡在 `gamma off` 与 `gamma 1.80`
下各存一帧（斜坡由 `fill` 命令造，`main.c:629` 声明 `cmd_fill`），逐格比对 5 bit 码值。

### 4.2 并级：这条曲线在 32 级里到底合并掉多少

**[算]**（两条式子：`main.c:376-383` 与 `gamma_lut.v:51`；遍历 R 的 32 个可达码。
这些数字是我自己算的，不是板子读数）：

| γ | R 输出序列（k=0..31 的 `out5`） | distinct | 合并掉的级 |
|---|---|---|---|
| 1.00 | `0,1,2,3,…,31`（不降且不重） | 32 | 0 |
| 1.80 | `0,4,6,8,10,11,12,13,15,16,17,17,18,19,20,21,22,22,23,24,25,25,26,27,27,28,28,29,30,30,31,31` | 25 | 7（k=11,17,21,24,26,29,31） |
| 2.20 | 首三格 `0,6,9`，末三格 `30,31,31` | 23 | 9 |
| 3.00 | 首三格 `0,10,12`，末三格 `30,31,31` | 20 | 12 |

同一算法跑 G 通道（64 个可达码，`out6 = curve(γ, g8) >> 2`）：
**distinct = 51 / 46 / 40**（γ=1.80 / 2.20 / 3.00），合并 13 / 18 / 24 级。

读法：γ>1 的提亮是**暗端拉伸、亮端压缩**，所以合并发生在亮端
（γ=1.80 那行末尾的 `30,30,31,31` 就是最后四级挤成两级的现场）。
**这才是这条通路真正的可见代价，比 §4.1 的截断误差大一个量级**：
截断最多 0.85 个 R-LSB（不跨级），并级是**整级消失**。
屏上多大范围看得出来 = **[未量]**（要一张灰阶斜坡照片 + 一帧 `gamma off` 对照）。

再补一条与 §1.4 的连账：写满 256 项**不减少并级**。
`main.c:405-413` 把 88 格之外的 168 格也写了，那 168 格的值永不参与查表；
限制级数的是索引可达集（32/64）与 `gamma_lut.v:51` 的截断，两者是同一个 565 瓶颈的两面。

### 4.3 gamma 的"取值量化"与 OSD 那一格的"取值量化"是两回事

屏上 `Gamma:1.8` 那个数是**声明值**，不是回读值。路径：PS 把 γ×10 塞进同一个字的 `[13:8]`
（`main.c:415-418`：`gm_w = (gm_w & ~GM_DISP_MASK) | GM_DISP((g100 + 5u) / 10u)`，
注释："OSD 那一格与表**同一次提交**……分开两处写会出现'表已经换成 2.2、屏上还写着 1.8'"），
PL 只让它过同一条同步链（`effect_ctrl.v:39`、`:54-55`、`:67`），OSD 再拆成两个字符
（`osd_overlay.v:281-284`：`putnum(gamma_disp / 6'd10)`、`put(".")`、`put(dig(gamma_disp % 6'd10))`）。

量化点：γ×100 → γ×10 是**四舍五入**（`(g100+5)/10`，`main.c:417`），
`gamma_disp` 只有 6 bit（`effect_ctrl.v:24`、`osd_overlay.v:36`）⇒ 量程 0..63，
而 γ×10 最大 30，位宽有余量；`gamma 1.85` 会上屏成 `1.9`（**[算]** 按 `(185+5)/10 = 19`）。
⇒ 这一格证明不了"表里写进去的是什么"，它只证明"PS 当时想写什么"。
仓库对"不许把不成立的数画到屏上"是有硬规矩的（`osd_overlay.v:43` 的 `lat_ok`、
`:316-324` 的温度半字节判 ≤9），但 gamma 这一格天生不在那条规矩的覆盖范围内 ——
它与第 05 章讨论 `Zoom:` 那一格"报的是不是真正在用的那个数"是同族问题，
差别是缩放那一格有 `zoom_code` 反推（`deep_course/05-…md` §1.5），这一格没有反推。

共用同一个字的温度那两位值得对照一句，因为它是**同一条链上做对了的量化**：
PS 先算成两位 BCD 再跨（`main.c:83-93`；为什么不在 PL 除，`effect_ctrl.v:63-65` 给了时序理由），
PL 侧"任一半字节 >9 = 没有可信读数 ⇒ 画 `--`"（`osd_overlay.v:318-324`），
同步链复位值故意给 `32'h0000_00FF`（`effect_ctrl.v:45-48`）。
⇒ 顺带一条 **[算]** 的推论：`pl_demo_top.v:84` 把整个字钉成 `32'd0`，
低字节 0x00 的两个半字节**都是合法十进制数字** ⇒ 演示顶层的屏上第 4 行会画 `Temp:00C`
而不是 `--`，与 `effect_ctrl.v:45-48` 那段"复位成 0 就是一条没人测过的数"的意图相反。
这是演示顶层（不是产品路径），**[未量]**：量法=跑一版 `pl_demo_top` 的位流看第 4 行。

### 4.4 为什么这里是截断而不是四舍五入：一条可以被证伪的选择

直觉会说"低 3 位扔掉太浪费，为什么不 `(v+4)>>3`"。答案是**会坏 identity**。
**[算]**（式子：`gamma_lut.v:23` 与 `:51`）：`r8 = 8·r5 + (r5>>2)`，
当 `r5 ≥ 16` 时 `r5>>2 ≥ 4` ⇒ 低 3 位 ≥ 4 ⇒ `+4` 会**进位**，`(r8+4)>>3 = r5+1`。
我把 k=0..31 全代了一遍：加 4 舍入会让 **16 个码**（k=16..31）各偏 +1；
G 通道同理，`(g8+2)>>2` 会让 **32 个码**（k=32..63）各偏 +1。
⇒ 现在这个"纯截断"是**唯一能让 γ=1.00 的恒等表逐位不动**的取整方向，
而"γ=1.00 时开了也逐位不动"是被判据钉住的性质（`main.c:375` 的注释 +
`tb_v88_gamma.v:128-133` 的 T2；期望式在 `:104` 的 `dout[15:11] !== ref[ir][7:3]`）。
⇒ 换句话说：**改这里之前先想清楚 T2 会红**。这不是风格选择，是判据锁住的方向。

### 4.5 同一条链上的三种取整/夹位口径（对照，都在 `src/rtl/process/`）

| 级 | 式子（行号） | 取整 | 越界处理 | 位宽账 |
|---|---|---|---|---|
| 级 0 gamma | `{tr[r8][7:3], tg[g8][7:2], tb[b8][7:3]}`（`gamma_lut.v:51`） | **截断**，无加法 | 不需要：8 bit 进、5/6 bit 出，恒不溢 | 8 → 5/6/5 |
| 级 1 灰度 | `y16=r8*77+g8*150+b8*29`、`y8=y16[15:8]`、`gray={y8[7:3],y8[7:2],y8[7:3]}`（`proc_gray.v:22-24`） | **两次截断**（高字节、再高 5/6 位） | 靠"系数和=256"不溢 | 8×常数 → 16 → 8 → 5/6/5 |
| 级 2 模糊 | 九个 5/6 bit 相加 → `×57`、取 `[13:9]`/`[14:9]`（`proc_box_blur.v:104-120`） | **截断** | **不夹位**，靠位宽证明（下段） | 和 10/11 bit，积 17/18 bit |
| 级 2 锐化 | `5×中心 − 四邻和`，**先比大小再减**（`proc_sharpen.v:92-104`） | 截断 | **显式饱和**：`>31→31`、`>63→63`（`:105-107`），负差夹 0（`:102-104`） | 中间量 9/10 bit |
| 级 4 阈值 | `y16[15:8] >= threshold`（`proc_binary.v:22-23`） | **不量化**，只比较 | 输出二值 `16'hFFFF/16'h0000`（`:25`） | 8 bit 比较 |

模糊那一行的"靠位宽证明"值得写全（**[算]**，代 `proc_box_blur.v:104-112`、`:115-120` 的字面量）：
R 九个 5 bit 之和最大 `9×31 = 279`，声明 10 bit（`:104`）有余；
`279×57 = 15903`，`>>9` 得 **31** ⇒ 满量程白**不夹位也不会溢**；
G 那一路 `9×63 = 567`、`567×57 = 32319`、`>>9` 得 **63**，同样正好。
`57/512 = 0.111328` 与 `1/9 = 0.111111` 的差（`:114` 的注释 `*57 >> 9 ≈ /9`）我穷举验过：
`S = 0..279` 上 `floor(57S/512)` 与 `floor(S/9)` **逐点相同**；`S = 0..567`（G）最大差 **1**，
发生在亮端 ⇒ 模糊在 G 上最多偏亮 1 个 G-LSB。

灰度那一行也验一次（**[算]**，穷举全部 65536 个 565 码，把 `r8/g8` 按 `proc_gray.v:18-20` 展开）：
`max|y8 − (0.299R+0.587G+0.114B)| = 1.411`（8 bit 单位），出现在 `(R,G,B) = (8,255,231)`，
`y8 = 177` 而浮点是 `178.411`；系数和 `77+150+29 = 256` ⇒ `255×256 = 65280 < 65536` 正好装进 16 bit。
⇒ 与 gamma 对比：**灰度这一级把量化做在"1/256 的系数近似 + 高字节截断 + 再截到 5 bit"三处**，
总误差比 gamma 那一级的截断（≤7）还小一档，但它没有表可以背锅。

**这一节最有价值的一条结论**：gamma 是这条链上**唯一**"值域由外部决定、模块内部完全不设防"的级。
`gamma_lut.v:43-45` 不检查单调、不检查端点、不做平均，任何 8 bit 数都收。
所以"曲线对不对"在 PL 侧**不可判定**，只能由写它的人自证
（`main.c:405-427` 的三条自检），而台架反过来故意**不用真曲线**去验接线
（`tb_v88_gamma.v:22`："曲线的算术不在这里验（PS 算、PL 只'写进去什么就查什么'），
所以表是故意挑的怪表（identity / 0xFF−i / i^0x5A）用来暴露接错线"）。
责任切分是这套设计的核心决策之一，不是偷懒。

## 5 控制通路：一条 `gamma 1.8` 的十站全程

### 5.1 串口侧（收字节 → 切词 → 派发）

1. **收字节**：`rx_fill()` 把 UART 字节搬进 `cmd_buf`，**只搬运不派发**（`main.c:1478-1500`）。
   为什么要拆：`main.c:303-310` 那段注释直接点名 gamma ——
   "`gamma_set` 一次要写 256 项、每项两次 `usleep(5)` ⇒ 约 2.6 ms **不回主循环**，
   而 115200 波特下 Zynq 的 RX FIFO 只有 16 字节（≈1.4 ms 的量）"。
   于是派发段里要反复 `rx_fill()`（`main.c:412`，就在那 256 次写的循环体内）。
2. **派发**：主循环 `while(1)` 第一句就是 `uart_poll()`（`main.c:1587-1588`），
   `uart_poll()` 按 `\n` 逐行切词、`tokenize()`（`main.c:1465`，函数体 `:677`）后交给
   `dispatch(tk, nt)`（`main.c:1466`，函数定义 `:890-891`）。
3. **认命令**：`dispatch()` 里那一支是 `if (ci_pre(tk[0], "GAMMA"))`（`main.c:1204`）——
   **前缀**匹配，所以 `gam`、`gamma2` 之类都会走进这一支；参数取法
   `const char *arg = (nt >= 2) ? tk[1] : tk[0] + 5;`（`main.c:1206`）——粘着写也吃（`GAMMA1.8`）。
4. **解析数值**：`parse_gamma()`（`main.c:431-452`）："1.8"→180、"180"→180，
   小数第 3 位**只舍不进**（`:445` 的注释），带非法尾字符一律拒（`:439`、`:448`）。
   拒绝路径明确回声且**不改状态**（`main.c:1244-1247`）。

### 5.2 PS 侧：算曲线 + 两项一提交的写协议

5. **开关与量程**：`gamma off` → `gamma_off()`（`main.c:385-393`）：
   先停 Auto（`:387`，"手动出口永远先把 Auto 停掉：不许'关了还在扫'"）、
   `cur_gamma = 0`、**只清 `GM_EN` 与 `[13:8]` 那 6 位**（`:389-390`），然后整字写一次（`:391`）。
   ⇒ 表**保留**（`:392` 的回声就说"表保留"），所以来回切不用重灌 2.6 ms。
   `gamma on` → `gamma_set(cur_gamma ? cur_gamma : 220u)`（`main.c:1209`）：
   没有当前值就落 **γ=2.20**（`report/commands.md:196` 念的也是这个数）。
   `gamma <数>` → `gm_auto = 0` 再 `gamma_set(g)`（`main.c:1249-1250`）。
6. **算与写**（`gamma_set()`，`main.c:395-428`）：
   量程先拒（`:400-404`），然后 `for (i = 0; i < 256u; i++)`（`:405`）逐项
   `v = gamma_curve(g100, i)`（`:406`）→ 记 `bad`/`first`/`last`（`:407-410`）→
   `gamma_put(i, v)`（`:411`）→ `rx_fill()`（`:412`）。
   两项写完才 `gm_w |= GM_EN`（`:414`）并同字带 γ×10（`:417-418`）——
   ⇒ **使能是在 256 项灌完之后才抬起的**，这是这条协议里最要紧的顺序：
   不会出现"半张表 + 开着"的中间态。
7. **一项两笔写**（`gamma_put()`，`main.c:366-373`）：

   ```c
   Xil_Out32(CFG_DATA1, gm_w | GM_DATA(v) | GM_IDX(i));   /* :368 先摆地址与数据，wr 不动 */
   usleep(5);                                             /* :369 */
   gm_w ^= GM_WR;                                         /* :370 翻 wr = 写这一项 */
   Xil_Out32(CFG_DATA1, gm_w | GM_DATA(v) | GM_IDX(i));   /* :371 同一对 idx/data 再写一次 */
   usleep(5);                                             /* :372 */
   ```

   `gm_w` 是通道 2 的**影子**、`wr` 位的唯一真相（`main.c:288-290`），
   所有写这一寄存器的地方都必须从它出发整字写回（`main.c:94-95` 那条 ⚠：
   读-改-写会踩 #55 那个"每帧重写把别的位抹掉"的坑 —— 温度与 γ×10 都在同一个字里）。
   两次 `usleep(5)` 不是节流：`main.c:285-287` 写的是
   "PL 看的是 `wr` 的**边沿**，而 AXI 连发的间隔可以短到一个像素拍都不到 ⇒ 这条约束是真实的，别删"。
   5 µs×2 × 256 项 = **约 2.6 ms** **[码]**（同一行注释给的数），一帧是 16.8 ms 量级
   （625 行 × 1344 拍 × 20 ns，账在 `deep_course/05-zoom-fixed-point-and-row-ring.md:107` 那张表），
   所以整表重灌跨不到一帧，人眼看不出来。

### 5.3 AXI → PL：寄存器、位段、同步链

8. **落到哪根线**：`CFG_DATA1 = 0x41220000 + 0x08`（`main.c:96`，基址 `:77`），
   基址由 BD 钉死并回读校验（`build/tcl/build_system_axigpio.tcl:243-251` 赋址、
   `:258-264` 数值比对；`:145-146` 那两行注释讲的正是"地址错了不是编译失败而是写了没反应"）。
   设备是 `axi_gpio_2`，双通道、两路都 32 位纯输出（`:147-155`：`C_IS_DUAL {1}`、
   `C_GPIO_WIDTH {32}`、`C_GPIO2_WIDTH {32}`、`C_ALL_OUTPUTS {1}`、`C_ALL_OUTPUTS_2 {1}`），
   通道 2 的输出口 `gpio2_io_o` 被改名成 `GPIO_3_tri_o`（`:222-226`）。
9. **PL 侧接线**：`system_top.v:87` `.GPIO_3_tri_o(gpio_cfg2_o)` →
   `system_top.v:276` `.gamma_ctl(gpio_cfg2_o)` → `pl_video_top.v:34` 端口 →
   `pl_video_top.v:204` `.gamma_async(gamma_ctl)` 交给 `effect_ctrl u_eff`。
   ⚠ `system_top.v:49` 那行注释还写着"ch2 全留给 V8-3/Gamma……现在**故意不接**"，
   而同文件 `:276` 已经接上了 —— 这是同一份文件里的过期口径，以 `:276` 为准。
   ⚠ 另一条命名坑写在 `system_top.v:267`："别写成 `gpio_cfg2_o`：那是 PS 侧 +0x08 的 gamma 窗口"，
   `main.c:221-222` 从 PS 侧同一句提醒（"`CFG_DATA0` 就是 RTL 的 `gpio_cfg1_o`；
   gamma 那个窗口是 `CFG_DATA1(+0x08)`，两个名字差一位，写错字的症状恰恰是'设了没反应'"）。
10. **同步与拆位**：`effect_ctrl.v:39` 那对 `gm_meta/gm_sync`（`ASYNC_REG = "TRUE"`）
    在 `:54-56` 按位段重排（`[31]→en`、`[30]→wr`、`[29:22]→data`、`[21:14]→idx`、`[13:8]→disp`、`[7:0]→temp`），
    `:66-68` 用一个 `always @(*)` 把 32 位**解构成六个出口**
    （`{gamma_en, gamma_wr, gamma_data, gamma_idx, gamma_disp, temp_disp} = gm_sync;`）。
    复位值 `32'h0000_00FF`（`:48`）⇒ 上电时 `en=0`、`wr=0`、`idx=0`、`data=0`、`disp=0`、`temp=0xFF`，
    正好同时满足"旁路"、"边沿检测不许把上电当一次写"、"屏上画 `--`"三件事。
    位序的**唯一口径**在三处一致：`main.c:79-84`、`effect_ctrl.v:60-61`、`pl_video_top.v:32-33`。
11. **进链**：`pl_video_top.v:208-209` 把四个已同步信号 + `gm_disp`/`tmp_disp` 收下来，
    `pl_video_top.v:803` 把四个喂给 `u_pipe`，`proc_pipeline.v:104` 喂给 `u_gamma`，
    最后落回 `gamma_lut.v:39` 的 `do_wr` 与 `:41-47` 那一笔三表同写。
    OSD 走另一岔：`pl_video_top.v:1009` `.gamma_disp(gm_disp)` → `osd_overlay.v:36` → `:281-284` 画字符。

**这条路上唯一被"实测"过的位段判据**是 `tb_v86_pipe_sel.v:239-248` 的 T15/T16：
激励 `gm_a = {1'b1, 1'b1, 8'hA5, 8'h3C, 14'd0}`（`:239`），四个字段互不相同
—— `:238` 的理由："任何一处对调（idx/data、en/wr）都会红"。
T16（`:245-248`）钉的是另一半：`en` 落到 0 时 `idx/data` 仍照实同步，
"旁路与表内容互不牵连"（否则 `en` 会被误当"整字关断"）。

### 5.4 没有的那条路：状态回读

`gamma` 在健康快照的 lane 名册里**没有位置**。顶层的 lane 注释列的是
`lane30`（仲裁）、`lane29/28/27/26/25/24`（时延六个字）、`lane23`（像素域真正在用的缩放状态）
（`pl_video_top.v:62-79`、`:636-648`），没有一个 lane 携带 gamma 表状态或 `gm_en` 的 PL 侧读数。
`main.c:881-883` 的 `temp` 命令确实会 `Xil_In32(CFG_DATA1) & GM_TEMP_MASK` 打一个 `gpio=` 字段，
但那读的是**AXI 从设备自己**（证明寄存器存住了），不证明 PL 采样到了。
⇒ 想机器化验证"PL 真的收下了这张表"，目前只有两条：仿真台架（§6）与肉眼屏上对比。
**[未量]**：若要把回读做实，代价最小的一条是给 `gamma` 加一条与 `zoom` 同一手法的
准静态快照 lane（`pl_video_top.v:644-656` 那段就是现成模板），但那要重新过 CDC 门禁

   T8（`:185-198`）只比 DUT 自己的输出序列是否不降，`:187` 的理由是
   "把 R 与 B 接反的 DUT 在逐点比对里可能碰巧对，在单调序列上一定露"。

- **判据器**：`src/host/uart_cmd_check.mjs` 对每段命令切片比回声，gamma 相关三条：

### 6.3 缺的部分（照实说）

1. **没有一条判据比对过"真曲线"**。台架用怪表，固件自检用端点+单调，
   中间那 256 项的实际值没有任何一处被逐点核对过（**没有可核对的盘上表**，见 §2.4(b)）。
   要补：一支 C/脚本台架把 `gamma_curve()` 单独跑成一份 256 项文件，
   再与 `tb_v88_gamma.v` 的 `ref[]` 机制对拍（同一张表两边各写一遍的老手法）。
2. **没有 PL 侧"表内容"的可观测量**（§5.4）：既没有 lane，也没有把 `gm_en` 回读的命令。
3. **PL 重烧 + app 不重启**那一格（§2.4(d)）没有台架也没有板级凭据，只有推论。
4. **`wr` 影子位与 PL 复位的相位**（§2.4(c)）故意没被判据覆盖：
   `tb_v88_gamma.v:165` 那句"前提不成立时这条判据就没牙"就是承认了这个洞；
   补法很便宜——再加一段"`wr` 停在 1 时复位，然后要求**恰好一次**额外写"的判据（现在没有）。
