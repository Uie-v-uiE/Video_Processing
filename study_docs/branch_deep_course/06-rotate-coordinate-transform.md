# 06 旋转：角度→三角表→逆映射，以及角度这件事的可观测债

被测对象：`src/rtl/process/rotate/angle_ctrl.v`、`src/rtl/process/rotate/sin_rom.v`、
`src/rtl/process/rotate/cos_rom.v`、旋转在屏上的执行体是 `src/rtl/process/zoom/zoom_mapper.v` 的
旋转支（不是 `rotate_mapper.v`，见 §6），加上顶层 `src/rtl/top/pl_video_top.v` 的角度节拍与跨域接线。

读完这一章要能回答：一个 9 bit 的"度"是怎么变成两个 10 bit 有符号数的；
为什么这条链上**没有**象限折叠、**没有**小数角、**没有**累加器；
帧尾那一次翻转位是在哪一拍翻的、为什么不能是帧首；
哪些信号是"准静态/影子值"、它们各自走哪条同步路；
以及为什么"现在屏上转了几度"这件事到今天只能靠眼睛读。

## 1 前置知识

### 1.1 旋转的逆映射形式

第 05 章定了方向：屏上每个像素解出它该取源图哪一格。旋转同一条式子，只是多乘一个 2×2 矩阵：

```
X_src =  cosθ·(x − cx) + sinθ·(y_math − cy)
Y_src = −sinθ·(x − cx) + cosθ·(y_math − cy)
```

带 `+sin` 在前这一路对应的是**把画面旋转 +θ**（等价于坐标系旋转 −θ），
`src/rtl/process/rotate/rotate_mapper.v:2-3` 的文件头写的是 "rotate by -angle (matches reference matlab)"。
`y_math` 是数学系（Y 朝上）的量，而扫描栅格是显示系（Y 朝下），所以进矩阵之前要翻一次号，
出来之后再翻回去——这两次翻号是本模块一半的坑（§3.2）。

### 1.2 定点形式：Q8 × Q8 = Q16

表值是 Q8（`round(sin·256)`，10 bit 有符号），中心偏移是整数像素。
`偏移 × 表值` 得到的是"值 × 256"，再乘缩放步长 `inv`（又一个 Q8）就得到 **Q16**，
所以取整右移 16 位、取小数要看 `[15:8]`：

```
xr_m  = xp·cos_v + yp_math·sin_v           // 值 × 256      （zoom_mapper.v:47-48）
rot_xs = xr_m · inv                        // 值 × 65536     （:58）
xr_pix = rot_xs >>> 16                     // 整数源坐标      （:63）
rot_fx = rot_xs[15:8]                      // Q8 小数         （:75）
```

缩放支单独走 `>>> 8` 与 `[7:0]`（`:65`、`:92`）。**两支的 Q 格式不同**，
这是本章最容易看错的一处，也是 #104/#189 两刀的病根（第 05 章 §3.3）。

### 1.3 角度的表示：整数十进制度，9 bit，0..359

`src/rtl/process/rotate/angle_ctrl.v:15` 的 `output reg [8:0] angle` 存的就是**十进制度**，
不是弧度、不是 Q 格式、不是 CORDIC 的迭代角。OSD 那一格因此不需要换算
（`src/rtl/video/osd_overlay.v:289` 直接 `putnum(angle)`，文件头 `:32` 写明"0..359，不用换算"）。

分辨率 1°，一圈 360 格。9 bit 装得下 0..511，所以多出来的 360..511 是空档，
表里的 `default` 分支负责兜住（§4.4）。

### 1.4 "象限 + 小数角"：**本设计一个都没有**

教学上常被假设存在的两件事，先说清楚这里的真实形状，再讲通用做法，免得照着通用做法去找代码。

**(a) 象限折叠。** 三角函数在四个象限里只差符号与 sin/cos 互换：
`cos(θ) = cos(360−θ)`、`cos(180−θ) = −cos(θ)`、`cos(90−θ) = sin(θ)`。
表里看得见这个对称（自己算就能验）：`cos 30° = 222`（`src/rtl/process/rotate/cos_rom.v:39`）、
`cos 330° = 222`、`cos 150° = −222`；`sin 30° = 128`（`src/rtl/process/rotate/sin_rom.v:39`）。
**但落盘的两份文件就是完整的 360 格 `case`**：
`src/rtl/process/rotate/sin_rom.v:2` 的文件头是
"Auto-generated sin_rom: round(fn(angle_deg)*256), signed 10-bit"，
`:8` 起是 `9'd0` 到 `:368` 的 `9'd359`，`:369` 是 `default: value = 10'sd0;`；
`cos_rom.v` 同构、同长（两个文件各 372 行）。
折叠是"生成脚本层面可以压但没压"的余地：满表 360×10 bit ≈ 3.6 Kb，LUTRAM 或 BRAM 都装得下。
换来的是查表**组合 0 拍**、且不需要"象限判断 + 取反 + sin/cos 交换"那三级组合逻辑——
在 20 ns 的 `clk_pix` 上那三级不难，但这条链的输出还要再乘 `inv`（§2.1），少三级就是少一段余量。

真正在本树里用了"取绝对值 + 象限"这半套技巧的只有 `zoom_fit`：
`src/rtl/process/zoom/zoom_fit.v:23-24` 把 `cos_v/sin_v` 取成 `C/S`（两个 10 bit 无符号绝对值），
因为"装得下"只跟外框尺寸有关、跟旋向无关。

**(b) 小数角。** 通用做法有两种：把表压到 0..90° 之后用 `θ = q·90° + φ` 分解，
`φ` 再用一次小表或线性插值；或者 CORDIC——把角度写成
`θ = Σ atan(2^-i)`，用一个**角度累加器**和 12~16 级迭代换掉整张表。
本设计**两种都不用**：角度是整数度，直接当 `case` 的索引（`src/rtl/process/rotate/sin_rom.v:7-8`
的 `always @(*) case (angle)`）。精度代价因此是固定的：Q8 表的每一项最多差 0.5 LSB，
`src/rtl/process/zoom/zoom_fit.v:48` 把这条量化成"`inv` 最大差 `(W+H)/2/H ≈ 1.35`"，
并据此加了余量。

**(c) 累加器。** 正映射/扫描式生成才会用"每拍 `x += step`"的相位累加器。
本设计**没有**：`zoom_mapper` 每个显示像素独立解一次
（`xp <= x_in − W/2` 在 `src/rtl/process/zoom/zoom_mapper.v:32`，`x_in` 就是当拍的视口列），
不做跨像素的累加。原因有三条，全部可指到代码：

1. mapper 是一条**三级流水**（`:31`、`:42`、`:96`），累加器会把相邻像素的算术串成一条依赖链，
   流水就没了；
2. 每一行的行首要能直接落位（`x_in` 由 `video_timing` 的计数器给，不从上一列推）；
3. 旋转态下源列沿一条显示行**不单调**——`src/rtl/process/bilin/fb_bilin.v:136-138` 写的正是
   "旋转时一条源图线在 x 方向会停滞甚至倒退"，这条事实本身就否掉了"步进累加"能当地址用。

⚠ 名字里带 `acc` 的那个东西在 `src/rtl/process/bilin/tap_sched.v:56`（`reg acc1, acc2`），
它是"这一拍的请求有没有被采纳"的跟随链，与坐标累加无关，第 07 章讲。

### 1.5 准静态与影子值：什么叫"能跨进像素域"

一个 bit 可以打两拍同步。一条**总线**不行：每一位各自新/旧，会读到半新一半旧的中间态。
本树只有两种合法的跨域形态，都要求在源域"整字一次写完、并且至少稳定到目的域采完"：

* **准静态总线 + 跳变沿**：`src/rtl/eth/snap_cross.v:3-6` 的契约——
  源域整拍写好总线、同拍翻 `bus_tog`；目的域等 3 级同步之后再采一次，
  而源总线至少保持到下一次写入（本项目 ≥ 1 ms）⇒ 采到的必是完整值。
* **一条链上打包**：`src/rtl/process/effect_ctrl.v:34` 声明
  `reg [12:0] sel_meta, sel_sync;   // {manual, zsel[2:0], stage[8:0]}`，
  13 bit 载荷过**同一个**两级链（`:50-51`），出口在 `:74-75` 的 `zoom_sel`/`zoom_manual`。
  理由在 `:30-33`：PS 是一次整字写、而 `zoom_ctrl` 把这两个位当**一对**用
  （`manual = 1` 时必须看见对应档号），分两组同步就会出现"旗标到了、档号还是上一次的"。

"影子值"指的是**目的域里那一份寄存副本**：像素域永远读影子（`bilin_en_pix`、`osd_en`、`zoom_run`、
`gp[18]`），从不直接摸 axi 侧的输入脚。§5 给全表。

## 2 原理拆解（把数带进去）

### 2.1 一条像素的全链算例（45°、1.00×）

取 `angle = 45`、`inv_used = 256`、`rotate_en = 1`、`cx = 456`、`cy_r = 50`：

| 步 | 量 | 值 | 出处 |
|---|---|---|---|
| 1 | `xp = cx − 256` | 200 | `zoom_mapper.v:32` |
| 2 | `yp_math = 150 − cy` | 100 | `:33` |
| 3 | `C = cos_v[45]` | 181 | `cos_rom.v:54` |
| 4 | `S = sin_v[45]` | 181 | `sin_rom.v:54` |
| 5 | `xr_m = 200·181 + 100·181` | 54300 | `:47-48` |
| 6 | `yr_m = −200·181 + 100·181` | −18100 | `:49-50` |
| 7 | `rot_xs = 54300·256` | 13,900,800 | `:58` |
| 8 | `rot_ys = −18100·256` | −4,633,600 | `:59` |
| 9 | `xr_pix = rot_xs >>> 16` | 212 | `:63` |
| 10 | `rot_fx = rot_xs[15:8]` | 28 | `:75` |
| 11 | `yr_pix = rot_ys >>> 16` | −71 | `:64` |
| 12 | `rot_ys[15:0]` | 19456（高字节 76、低字节 0） | `:81-82` |
| 13 | `rot_fy_ceil = 76 + 0` | 76 | `:83` |
| 14 | `rot_fy = (256 − 76) & 0xFF` | 180 | `:84-85` |
| 15 | `rot_y_has_frac = (19456 ≠ 0)` | 1 ⇒ 减那一格 | `:86-87` |
| 16 | `sx_c = 212 + 256` | 468 | `:68` |
| 17 | `sy_c = 150 − (−71) − 1` | 220 | `:87` |

自检（对着**表值**而不是对着真 cos45）：
`X = 54300/256 = 212.109` ⇒ floor 212、frac 0.109·256 = 28 ✓
`Y_math = −18100/256 = −70.703125` ⇒ `Y_disp = 150 + 70.703125 = 220.703125` ⇒ floor 220、
frac 0.703125·256 = 180 ✓
**floor 与 frac 逐位自洽。** 而与"真 cos 45° = 0.7071068"给的理想值差 0.008 px，
那 0.008 是 Q8 表量化（181/256 = 0.707031），不是取整错——`src/rtl/process/rotate/sin_rom.v:2`
声明的就是 `round(fn(angle_deg)*256)`。台架因此**不**在外面重算三角函数，
而是直接读 DUT 自己的表项当参考（`sim/tb_zoom_frac.v` 文件头的激励段）。

### 2.2 #189 那一格的算例（构造，命中条件是 `(yr_m·inv) mod 65536 ∈ [1,255]`）

取 `yr_m = 1`、`inv = 128`（2.00×）：

| 量 | 值 |
|---|---|
| `rot_ys` | 128 |
| `yr_pix = 128 >>> 16` | 0 |
| `rot_fy16` | 128（高字节 **0**、低字节 128 ≠ 0） |
| `rot_fy_ceil` | 0 + 1 = 1 |
| `rot_fy` | 256 − 1 = **255** |
| `rot_y_has_frac` | **1** ⇒ `sy_c = 150 − 0 − 1 = 149` |

真值 `Y_math = 128/65536 = 1/512 = 0.001953` ⇒ `Y_disp = 149.998` ⇒ floor 149、权重 255 ✓。
**旧写法两半都错**：`has_frac` 只看高字节 ⇒ 判成"没有小数" ⇒ 不减那一格；
权重也按高字节取 ⇒ 给成 0。于是这一格被表示成 150.0 而不是 149.998 ⇒ 沿角度方向整行错一格。
发生率实测 ≈ 0.27 %（扫 3726 个旋转态像素命中 10 个、10 个全错，首个反例 `x=337 y=195`），
口径在 `src/rtl/process/zoom/zoom_mapper.v:76-80`。
`f = 0` 时 `rot_fy_9` 算出 256，取低 8 位正好回绕成 0，与旧行为一致（`:84` 的注释就写这件事）。

### 2.3 角度的推进节拍（为什么不能在帧首）

三个数拼出结论：`IMG_H = 300`、`OFF_LINES = 4`、`BILIN_ROWS = 2`。

```
y_right_adv = y + pipe_off_rows + BILIN_ROWS         // pl_video_top.v:276
y_req_row   = y_right_adv >> 1                       // :277
wrap_row_now = (y_req_row >= IMG_H)                  // :299
```

`y_req_row ≥ 300` ⇔ `y + 6 ≥ 600` ⇔ `y ≥ 594` ⇒ **屏上从显示行 594 起，请求行已经绕回**。
而屏上最上面 6 行（`OFF_LINES + BILIN_ROWS`）的内容恰恰是在**上一帧**的绕回请求行取回来的。
所以如果挂在 `frame_start` 换角，帧头 6 行吃上一帧的角度、其余吃这一帧的 ⇒ 每帧换角时
这几行整体错开一档。`src/rtl/top/pl_video_top.v:286-292` 记的就是这件事与它的板侧症状
（眼睛那一半对上了：动起来才有顶部分散细线、角度停住就干净）。

修法是把**翻转拍点**挪到"最后一个不绕回的行（今天 = 593）的行尾消隐"：

```
if (fs_de_d && !de && wrap_row_next && !wrap_row_now) rot_fs_tog <= ~rot_fs_tog;   // pl_video_top.v:312
```

`wrap_row_next` 是按"下一行的请求行"算的（`:300-302`），所以行 594..624 那些绕回行与场消隐
全部被 `!wrap_row_now` 挡住 ⇒ **每帧恰好一次，不多翻**（`:310-311`）。
那一刻本帧要显示的行全部请求完了、而下一帧帧头的请求还没开始 ⇒ 帧头与主体吃到同一个角度。

节拍余量：`de` 掉下去之后是整段行消隐，`H_TOTAL − H_ACTIVE = 1344 − 1024 = 320` 拍
（`src/rtl/video/video_timing_1024x600.v:19`，注释 `:3` 的加法）= 6.4 µs；
而 `angle_ctrl` 里那三级同步只要 3 × 20 ns = 60 ns。这条口径写在
`src/rtl/top/pl_video_top.v:294-295`。

### 2.4 一步几度与取模

`speed[2:0]` = 每帧走几个度（`src/rtl/top/pl_video_top.v:177`），0 = 自动开着但不走。
一帧 16.8 ms ⇒ 7°/帧 ≈ 417°/s，一圈不到 1 s。

取模这一条有具体的坏形状：

```
up      = {1'b0, angle} + {7'd0, speed};              // angle_ctrl.v:33
wrap_up = (up >= 10'd360) ? (up - 10'd360) : up[8:0]; // :34
```

写成"到 359 就回 0"会在回绕处丢几度——因为一帧最多走 7°，
`360 = 7·51 + 3`，只用一个上限比较就会有一档跨过 360 时的残量被吃掉，
转速快的时候肉眼看得见那一顿（`:31-32`）。减法一次就够：`angle ≤ 359`、`speed ≤ 7` ⇒
`up ≤ 366` ⇒ 减完 ≤ 6 ✓ 这正是 10 bit 那一支的合法性前提。

### 2.5 角点出屏：三件事，不是一件事

`#93` 的用户报告是"168° 时右下角戳出屏幕，右上方出现一道宽彩条"。
档案（`开发台账` 3481 行起）把它拆成三条，并逐条给了候选与判据缺口：

* **(A) 宽彩条**：候选三条，其中第 ③ 条与用户"内容和右下角一样"字面最合——
  越界那一拍的 `(sx,sy)` 被折回图内 ⇒ 读到图内另一角的格子。
  本设计**确实**有折回，但只给了末列/末行那一道门（`src/rtl/process/bilin/fb_bilin.v:53-54` 的
  `kx_use/ky_use`），而且越界那一拍同时有 `oob` 回黑，所以折回与回黑是同一次、同一个像素
  （`:46-47`）。#93 的宽彩条**不是**这一条，档案里也没把它归到这里。
* **(B) 左边的细线**：与 #102 那一格同族，第 05 章已修并有 C8a/C8b 判据。
* **(C) 判据缺口**：这一条是真正还差的东西——顶层按定义逐像素比对源坐标的那几条
  （C1g/C1h/C1c/C2b/C7）**全部跑在不旋转的世界**，旋转只出现在 C4 那一圈，
  而 C4 判的是**形状**（每行至多一段非黑），不比对源行号。
  档案把这句话写成了结论："旋转 + 缩放的几何一致性今天没有任何机器判据，只有用户眼睛"。
  这条缺口在 #189 的复查里被再次确认（`开发台账` 9273 行起）。

### 2.6 `rows_hit`：这个名字不在几何链上

`rows_hit` 在本树里只有一个定义处：`src/rtl/eth/frame_reasm.v:82`（16 bit），
它是收包侧重装配的**行计数**——每有一拍把某个 64 bit 字写进 DDR 就 +1（`:159`），
提交那一拍拿它跟 `IMG_H` 比（`:182`），不够就把缺的行数报进 `rows_missed`（`:201-202`）。
它与旋转的角点出屏**没有关系**。教学材料里把这个名字挂到几何上会指向错的模块，
所以这一章按实际代码把名字纠正过来，并在第 12 章（网络收包）里讲它。

## 3 代码逐段分析

### 3.1 `angle_ctrl`：一个 9 bit 计数器与它的三个入口

模块本体只有 46 行，逐块看：

* **复位与输出**：`angle` 复位写 0（`src/rtl/process/rotate/angle_ctrl.v:37-38`），
  `rotate_active = (angle != 9'd0)`（`:18`）。
  这一位就是顶层递给 `zoom_ctrl` 的 `rotate_en`
  （`src/rtl/top/pl_video_top.v:329`）与递给 `zoom_mapper` 的 `rotate_en`（`:345`）。
  **0° 时旋转钳整个不参与**这件事的根据就在这里：`zoom_ctrl.v:72` 的 `rot_clamp` 第一项是 `rotate_en`。
* **`frame_tgl` 是翻转位而不是脉冲**：`:20-21` 的理由是"1 拍的脉冲跨时钟域会被整个吃掉"。
  本模块吃 `sys_clk`（`src/rtl/top/pl_video_top.v:184` 的 `.clk(sys_clk)`），
  而脉冲来的是 `clk_pix` ⇒ 真跨域，**同步器放在谁拥有时基谁那里**，顶层不许再自己采一遍（`:21-23`）。
* **同步器与边沿**：`(* ASYNC_REG = "TRUE" *) reg [2:0] fs_s`（`:24`），
  `fs_s <= {fs_s[1:0], frame_tgl}`（`:27`），`fs_edge = fs_s[1] ^ fs_s[2]`（`:29`）
  ⇒ 每次帧沿恰好一拍、在 sys_clk 域。
* **三个入口的优先级**（`:36-45` 的 `else if` 链）：
  `key_inc` > `key_dec` > `auto_en && fs_edge && speed != 0`。
  按键走的是"到 359 就回 0 / 到 0 就回 359"的单步回绕（`:40`、`:42`），
  与自动那支的"减 360"是两套式子——因为单步永远不会跨过上限，只有多步累加才会。
  按键接的是短按松手沿：`pl_video_top.v:185` 的 `.key_inc(k1_short), .key_dec(p2)`。

**发射触发器必须独占**：`:22-23` 写明顶层为它单起一个翻转触发器（不共用 `sof_tgl`/`z_hb_tog`），
"发射触发器扇出到两组目的域同步器会被 cdc.rpt 判 CDC-11 Critical"，
同一个工程里为这件事红过两次（`#65`、r54 构建 `#34`）。顶层那一段的同一份警告在
`src/rtl/top/pl_video_top.v:232-234`。

### 3.2 三角表：组合 `case`，0 拍延迟，`default` 是保险

```
module sin_rom (input wire [8:0] angle, output reg signed [9:0] value);   // sin_rom.v:3-6
    always @(*) case (angle) …                                            // :7-8
```

* **组合读** ⇒ 流水上不占拍：mapper 的 s1 那一拍**同拍**就能吃到表值参与乘加
  （`src/rtl/process/zoom/zoom_mapper.v:42-55`）。改成 BRAM 就要多一拍，
  而且 `angle` 一帧只变一次、根本不需要 BRAM 的容量。
  代价是它综合进 LUT/分布式 RAM 而不是 BRAM（表本体 360×10 bit）。
* **`default: value = 10'sd0`**（`sin_rom.v:369`、`cos_rom.v:369`）。
  `angle` 是 9 bit、全 512 个取值里只列了 360 个 ⇒ 360..511 这一族会拿到 `sin = cos = 0`，
  代入 §2.1 的式子：`xr_m = yr_m = 0` ⇒ `rot_xs = rot_ys = 0` ⇒
  `sx_c = 256`、`sy_c = 150` ⇒ **所有点塌到源图中心那一格**。
  今天不会出现，因为 `angle_ctrl` 的三个入口都把值夹在 0..359（`:34`、`:40`、`:42`）。
  这是一条**依赖上游的保险**，不是自证的性质：`cos` 的 `default = 0` 与"0° 应该是 256"不一致，
  所以恒等性只由 `case (9'd0)` 那一行（`cos_rom.v:9`）保证。
* **精度**：`round(fn(angle_deg)*256)`（`sin_rom.v:2`）。
  45° 给 181 而真值 181.019 ⇒ 表值略小于真值，`181/256 = 0.707031`。
  90°/270°/180°/0° 这几格是精确的（`sin_rom.v:99` 给 256、`:189` 给 0、`:279` 给 −256），
  这就是 `zoom_fit.v:49` 能说"在 0°/90° 表是精确的"的依据。

### 3.3 `zoom_mapper` 的旋转支：一条 `rot_s*` 位跟着数据走

旋转与缩放共用同一条三级流水，靠一个随流水推进的**模式位**选路：

| 级 | 位 | 在做什么 | 行 |
|---|---|---|---|
| s0 | `rot_s0 <= rotate_en` | 与 `xp/yp_math/yp_disp` 同拍寄存 | `zoom_mapper.v:29`、`:35` |
| s1 | `rot_s1 <= rot_s0` | 乘加 `xr_m/yr_m`，非旋转态清 0 | `:41`、`:46-54` |
| s2 | `rot_s1` 选 `xr_pix` 还是 `xs_pix` | 加回中心、算 `frac` | `:68-69`、`:87-88`、`:92-93` |

`yp_math` 与 `yp_disp` **两份并存**（`:33-34`）：`yp_s1 <= rot_s0 ? yp_math : yp_disp`（`:44`）
在 s1 选路。为什么缩放支不用 math：缩放没有翻号需求，直接用显示系，
翻号只出现在旋转的 Y 那一支（`:87`）。

`s1` 里非旋转态把 `xr_m/yr_m` 写成 `24'sd0`（`:52-53`）而不是"不算"，
是为了让两个乘加**每拍都执行**，工具就能把它们稳定映射进 DSP48 而不需要额外的流水使能。
这一条是拿资源换时序的取舍，与 `:42-55` 的注释"Multiplies registered in 2 stages for timing"同源。

### 3.4 顶层：角度与拟合值的消费者

```
zoom_fit #(.IMAGE_W(IMG_W), .IMAGE_H(IMG_H)) u_zfit (.clk(clk_pix), .angle(angle), .inv_fit(inv_fit));   // pl_video_top.v:322-324
zoom_ctrl … .rotate_en(rotate_active), .fit_en(zoom_fit_en), .inv_fit(inv_fit)                            // :325-334
zoom_mapper … .inv_scale(inv_used), .angle(angle), .rotate_en(rot_on), .x_in(cx), .y_in(cy_r)             // :343-349
```

三条**同名字段但语义不同**的接线要分清：

* `angle` 直连到 mapper 与 `zoom_fit`。两个消费者吃的是**同一个** `angle` 寄存器输出，
  但 `zoom_fit` 的输出要晚两拍（`src/rtl/process/zoom/zoom_fit.v:38`、`:52-55`），
  所以 `inv_fit` 与 `angle` 之间天然错开 2 个像素周期，而不是错开一整帧。
  这两拍落在消隐里（自动旋转时角度本来就在消隐换）。
* `rotate_en` 递的是 `rotate_active` 原样（`:329`），顶层不加工。
* `clocks`：`u_zfit`/`u_zctrl`/`u_zmap` 全在 `clk_pix`，而 `angle_ctrl` 在 `sys_clk`。
  ⇒ `angle` 这一条**总线**其实也在跨域，只是它跨的方式是"源域就是慢域、目的域直接吃寄存输出"，
  而 `angle` 只在 `fs_edge` 那一拍变，而那一拍落在行尾消隐 ⇒
  目的域采到的值整帧不变。这是"准静态"用法而不是"打两拍"用法；
  实测这一对跨域方向（`sys_clk → clkout0_1`）在本轮路由报告里 WNS 3.695 ns、231 端点
  （`build/timing_summary.rpt:199`）。

`zoom_fit` 里 `IMAGE_W/IMAGE_H` 用顶层的 512/300（`:322`），而 `zoom_mapper` 用同一对（`:343`）——
`src/rtl/process/zoom/zoom_fit.v:18` 特意写明"与 zoom_mapper 用的是**同一张**三角表"，
所以拟合判的"装得下"就是那条链真正画出来的框。参数不一致是这一族唯一可能的错法。

### 3.5 状态字里有没有角度：有口，没有读者

`src/rtl/top/pl_video_top.v:1046-1049` 的 `assign status` 里确实有 9 位 `angle`：

## 4 旋转状态机的"状态"到底是什么

旋转没有 FSM。它的"状态"是**一组随帧推进的量**，列出来比画图有用：

| 量 | 位宽 | 变化时刻 | 读者 |
|---|---|---|---|
| `angle` | 9 | `fs_edge`（行尾消隐）或按键 | `zoom_mapper`、`zoom_fit`、OSD、`status` |
| `rotate_active` | 1 | 与 `angle` 同拍组合出 | `zoom_ctrl`、`zoom_mapper`、`proc_pipeline` |
| `inv_fit` | 10 | `angle` 之后**两拍** | `zoom_ctrl` |
| `inv_used` | 10 | 帧首（呼吸/手动）或组合跟随（fit/钳） | `zoom_mapper`、`zoom_snap`、`status` |
| `rot_forced` | 1 | 组合，跟随 `inv_used` | OSD `(Fit)`、`zoom_snap` bit19 |
| `rot_fs_tog` | 1 | 每帧恰好一次（`:312`） | `angle_ctrl` 的同步器 |
| `gp[14] rot_auto` / `gp[17:15] rot_speed` / `gp[18] zoom_fit_en` | 各若干 | axi 域整字快照，目的域 3 级同步后采 | `angle_ctrl`、`zoom_ctrl` |

`rot_forced` 与 `zoom_fit_en` 在 OSD 那一格是**或**起来用的
（`src/rtl/top/pl_video_top.v:1011`：`zoom_fit(zoom_fit_en | rot_forced)`），
理由写在 `:1010` 与 `src/rtl/process/zoom/zoom_ctrl.v:31-32`：
被旋转钳住的时候屏上也要讲真话。`zoom_code` 报的仍然是"用户那一档"的分区结果，
但分区用的 `inv_used` 已经是钳后的数（`zoom_ctrl.v:64-84`），
所以 T8c 能判"钳生效时 `code(341) = 3 = 0.75x`"（`sim/tb_v94_zoom_sel.v:261`）。

## 6 `rotate_mapper.v`：它不在链上

`src/rtl/process/rotate/rotate_mapper.v` 与 `zoom_mapper` 的旋转支是**同一份式子**
（`:33-36` 对 `zoom_mapper.v:47-50`），但有四处实质差别：

| 项 | `rotate_mapper` | `zoom_mapper` 旋转支 |
|---|---|---|
| 缩放 | 无 `inv_scale` | `:58-61` 乘 `inv` |
| 小数 | 无 `frac_x/frac_y` 输出 | `:92-93` 交 8 bit |
| Y 翻号 | 一次（`:43`） | 两次（`:33` 进、`:87` 出，且连着 floor） |
| 关闭态 | `!enable` 时直通 `x_in/y_in`（`:50-53`） | 由 `rot_s*` 位选另一支 |
| 默认画幅 | `IMAGE_W=640`、`IMAGE_H=360`（`:6-7`） | 顶层递 512/300 |

**全树没有一处例化它**（`grep` 只命中 `module rotate_mapper` 那一行），
唯一驱动者是 `sim/tb_rotate_mapper.v`——它判的是三件事：0° 在左上角/中心/右下角三点逐位恒等、
90° 中心不被判越界、输出不出现 X 态（台架头 1-13 行的覆盖点段，`.IMAGE_W(64)/.IMAGE_H(36)` 小画幅）。
这个台架在 `sim/baseline_regression.log:119-124` 里是基线的一员。

结论要说得不含糊：**读现行旋转设计不要照 `rotate_mapper.v` 读**（它没有小数、没有缩放、
画幅参数还是 640×360，跟屏上的东西不是一个东西）；它留着是给"式子本身对不对"保一条最短的回归。
`src/rtl/process/bilin/fb_rd5x.v` 与 `tap_sched.v` 也是同一类"只剩台架在钉"的模块，
而且它们自己在文件头声明了这件事（`tap_sched.v:5`：本模块与 `fb_rd5x` 现在只由两个台架驱动，
"不是死代码"）。

## 7 为什么这样选（含被否决的方向）

**查满表，不折叠、不 CORDIC。** 折叠省 3/4 的表，但表本来就不大（3.6 Kb 量级），
省下来的容量要拿"象限判断 + 取反 + 交换"三级组合逻辑换；
CORDIC 省整张表，但把一次乘加换成 12~16 级迭代，且每级的符号判断都要真数据 ⇒
在逐像素流水里是 12~16 拍延迟，而 mapper 只有 3 级（`zoom_mapper.v:31/42/96`）。
本设计的角度分辨率是 1°，表就是最便宜的解。

**`angle` 每帧只在消隐变一次。** 这是**必须**的而不是优化：
`angle` 是两张表的**索引**，而 mapper 逐像素组合地吃它 ⇒
帧中间换角度 = 这一帧上半与下半用两个不同的角，画面在换的那一行错开一下。
以前只有按键会改角度（人手一次几毫秒、没人拿它做逐帧动作），所以这件事从来没暴露过；
今天它每帧都要换，就必须钉在消隐里（`angle_ctrl.v:4-6`）。

**翻转点从帧首挪到行尾消隐。** 这就是 §2.3。否决"帧首"的凭据不是推理：
板侧 E4r（动起来才有顶部分散细线、角度停住就干净）与台架 C5c/C12
（`sim/tb_v98_top_seam.v:1563`、`:1885`），
而"错开的大小"由 `sim/tb_head_rot_displace.v` 单独量（k = 1..7 度/帧的位移表）。

**帧头的越界请求行走"绕回"而不是"钳到 `IMG_H-1`"。** `pl_video_top.v:278-284` 给的取舍是：
钳到 `IMG_H-1` 也能画（屏顶画这张图自己的末行），而且**列位置与段数一点都不变** ⇒
#92/#93 那一族的可见症状会被它藏起来，C5 那把尺子就量不到东西了。
真正写的代码是绕回一次（`cy_r = (y_req_row >= IMG_H) ? (y_req_row - IMG_H) : y_req_row`，`:284`），
绕回之后仍走一遍逆缩放 ⇒ 小于 1.00× 时不多出一条顶带。
`y_req_row` 最大 302 ⇒ "减一次就够"，不需要除法器/取模（`:281-283`）。
⚠ 另一处 `cy` 用的才是真钳位（`(y >> 1) < IMG_H ? (y >> 1) : IMG_H - 1`，`:243`），
两个式子服务两个消费者，不要混。

**取模用减法而不是比较上限。** §2.4，档案口径写在 `angle_ctrl.v:31-32`。

**0° 不参与旋转钳。** 这条被记为**改口**：档案里一度写"0° 因为 ±0.5 LSB 的表余量给 259 ⇒ 也在钳"，
那是把 `zoom_fit` 的**输出**当成了生效条件；真实形状是"任何非 0 角度都在钳"
（`src/rtl/process/zoom/zoom_ctrl.v:68-71`，档案 #162 的"追加更正"）。
连带两条代价写在同一处：旋转态**不提供放大**（1.33×/1.5×/2.0× 三档被拉回 fit），
且 `zoom fit 0` **解不开**这一钳（钳的是"旋转在不在生效"，不是 fit 开关）。

**`zoom_fit` 分两拍。** 一拍做完 15 级、含两个 DSP48、slack +1.843 ns（当时全设计第三差），
输入一帧才变一次 ⇒ 多一拍屏上看不见（`src/rtl/process/zoom/zoom_fit.v:34-38`）。

**没做的：正映射 + 空洞填充。** 见第 05 章 §1.2；旋转叠上去之后前向映射还要处理
"一条源线在显示栅格上停滞/倒退"（`fb_bilin.v:136-138` 实测到的那条），
前向映射会把这件事变成写冲突。

## 8 可观测债：角度读不回来

这是本章要点名的**已知债**，不是新发现，也已经有立案号。事实清单：

1. `angle` 在 PL 里有三个入口、一个出口。出口是屏上那一格 `Rot:<n>°`
   （`src/rtl/video/osd_overlay.v:286-290`，`putnum(angle)` 加一个 Latin-1 的 `°`）。
2. 状态字里那 9 位没有读者：`pl_video_top.v:1046-1049` 把 `angle` 拼进 `status`，
   而 `system_top.v:45`/`:319` 只声明与连接、没有任何消费 ⇒ 综合删掉，**板上今天没有机读的角度**。
3. 固件侧同一件事：串口 `ROT SHOW` 只念 `auto / speed / deg/frame`，
   `STAT` 末尾的 `geom=` 里也只有 `rot_auto | rot_speed | zoom_fit | 缝的 19 位`
   ⇒ **串口没有任何"当前角度"读数**（`开发台账` #100 追加段，4694 行起）。
4. 后果具体发生过一次：整轮测量都以为在"无旋转"下做，而角度是否真为 0 无从核对。
5. 这条债还牵出一个解释不了的现象：上电为什么是 1 度而不是 0 度。
   `angle` 复位写 0（`angle_ctrl.v:37-38`），所以"1 度"必是复位之后进来的一个事件；
   板侧只读回读把软件那条路排除掉了
   （`rot_auto`/`rot_speed` 都是 0；凭据 `build/evidence/r111_angle_readback.txt`），
   机理由 `sim/tb_v111_key_boot.v` 用真三份链（`key_debounce`→`key_long`→`angle_ctrl`）钉住：
   上电那一根线读低约 1.5×去抖窗再回高 ⇒ `short_pulse` 恰好一枚 ⇒ `angle = 1`、
   `rotate_active = 1`、而 `ltog` 不动——与用户看到的"只多 1°、模式没变"一字不差
   （立案记录 `开发台账` 的 #247，11133 行起）。
6. 电气侧前提也记在同一处：`src/constraints/rk_zynq7020.xdc:8-9` 给 `key1_n`(W18)/`key2_n`(V14)
   只写了 `PACKAGE_PIN + IOSTANDARD LVCMOS33`，**没有 `PULLUP`**
   ⇒ 松开时这根脚靠什么保持高取决于板上有没有外部上拉。
   这一条在档案里明确写着"结论出来之前不把 PULLUP 写成修法"，所以本章也不写。

修法形状档案已经给好，且明确"单独成一轮"：lane 口 `gpio_o[31:27]` 的 20/21/22 是空号
（`src/rtl/top/system_top.v:244` 现在给越界号回 `32'hDEAD_BEEF`），
把 `angle` 搭一条 `snap_cross`（照 #175 的"搭同一条准静态快照、心跳单独一个 FF"手法）挂到一个空 lane。
要动的东西：一条跨域 + `cdc.rpt` 配对 + 门禁第 6 项 + **一条能红的台架（先红后修）**。

当下能立刻用的两条（不改代码）：回 0 度按一次 **KEY2**（−1°）；
若"上电 1 度"只出现在某一块板/某种接法，先怀疑按键那根脚的电气状态，而不是固件。

## 10 已量 / 未量

已量（本轮盘上原件）：路由后 `sys_clk → clkout0_1` 跨域 WNS 3.695 ns / 231 端点、
`clkout0_1 → sys_clk` 14.757 ns / 19 端点（`build/timing_summary.rpt:198-199`）；
`clk_pix`（`clkout0_1`）自身 intra-clock WNS 3.630 ns、WHS 0.059 ns、30179 端点（`:186`）；
全设计 WNS 0.739 ns（`:151`，终点在 `eth_rxc` 组，与本章无关）。
表值的精度口径（`round(fn(angle_deg)*256)`、45° = 181、90° = 256）是**数出来的**，
来自 `sin_rom.v:54/99` 与 `cos_rom.v:54/99`。
#189 的 0.27 %（3726 里 10 个）是台架扫出来的。

未量 / 明确不写：
旋转 + 缩放的**逐像素**几何一致性今天没有机器判据（§2.5 的 C 条，档案原话），

按键脚的电气状态（有无外部上拉）未查到手册/原理图证据，本章不下结论。
`sin_rom`/`cos_rom` 生成脚本没找到，所以"当初为什么没折叠"停在推测。
