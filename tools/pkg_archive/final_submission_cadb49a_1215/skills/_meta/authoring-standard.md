# 技能包写作规范（v2）

## 这个包是什么

技能包不是文档堆，是**给下一个 agent 或下一支队伍装上"这类活该怎么干"的肌肉记忆**：
一个自包含的、可被按症状检索到的工作包。它的核心评价指标只有一个——**可复用性**：
一支从没做过这个题目的队伍，拿到目录能不能直接用在自己的工程上。

## 这套约定的出处（不是拍脑袋）

- **技能不是叙事**：Agent Skills 的公开规范与 superpowers 的 `writing-skills` 都写着同一句——
  技能是"被证明有效的技巧/模式/工具的参考页"，**不是"我某次怎么解决问题的故事"**。
  所以本包的 `来源` 一节只写"长自哪一类失败/观察"，不写轮次、不写工程名。
- **description 只写"什么时候用"，绝不写做法**（同上两处）：描述是唯一的检索入口，
  agent 有时会**照着描述行动而不读正文**，描述里塞做法会把人引到正文之外。
- **三级渐进加载**：启动只读元数据 → 触发才读正文 → 请求才取 `references/`/`scripts/`。
  这就是"正文要短"的真正理由，不是排版偏好。
- **长度维度按字符数**（中文没有空格，按"词"数等于没判）：正文 ≤ 500 行且 ≤ 6000 字符；
  超出就把速查表/长表挪进 `references/`。
- **没有失败测试就不许写技能**（superpowers 的 RED-GREEN-REFACTOR）：
  新条目要先有"不带它时走过弯路"的观察，或至少一次基线复跑；量不了就在 `已验证效果`
  明写「未量过，属建议」——**空话视为没写**。
- **反面清单**（两处文档都点名的写法）：叙事式举例、同一条做多语言翻译、流程图里塞代码、
  通用化的标签（`misc`/`tips`/`other`）。宁要一个精准例子，不要五个平庸例子。

外部参照（下一支队伍想自查可以去这些位置，本包不依赖它们）：
Agent Skills 规范（SKILL.md + YAML 头、`scripts`/`references`/`assets` 三种子目录、正文 500 行上限、
`skills-ref` 校验）、superpowers 的 `writing-skills` 技能、公开仓库里按"架构→位宽→同步→时序"
组织的 FPGA 设计评审类技能。

## 结构约定（借 Agent Skills / superpowers 的形状，再按赛题 §3.3.5.2 补齐四问）

```
skills/
├── README.md              # 索引：一行一条，写"什么时候用"，不写做法
├── _meta/                 # 规范、接入指南、验证方法、机器判据（这一份就在这里）
├── <类别>/<条目名>/SKILL.md
├── <类别>/<条目名>/references/*.md   # 超过 ~100 行的速查表拆出去
└── <类别>/<条目名>/scripts/*           # 可执行工具，用解释器调用，不写绝对路径
```

- 类别 = 赛题四类再加两个工程实践中长出来的：`workflow`（提示词工作流与顺序纪律）、
  `prompts`、`templates`（案例模板）、`scripts`（校验脚本）、`pitfalls`（踩坑清单）、
  `references`（速查表）、`runtime`（片上运行时范式）、`timing`/`rtl`/`verify`（按活分的专业条目）。
- 目录名 = frontmatter 的 `name`，只用小写字母、数字、连字符。**不许出现具体工程/板子的名字**
  （工程专有的事实属于 `report/` 与 `docs/`，不属于技能包）。

## 一条 SKILL.md 必须有六块

1. `frontmatter`：`name` + `description`（单行、≥40 字、**以「用于…」开头**，写症状与触发条件，
   不写实现步骤——描述是被检索到的唯一入口）。
2. **适用场景**：什么现象/哪一步会用到它（症状级描述，越具体越好）。
3. **使用方法**：能照做的最小序列；有脚本就给命令与"跑完应看到什么"；
   并写**先查什么、先跟用户确认什么**（这是通用纪律，不是本项目细节）。
4. **失效条件（边界）**：什么情况下这条会失效或误导，失效前有什么征兆。这条最容易被写成空话——
   空话就等于没写。
5. **已验证效果**：在什么场景下量到什么结果（数、件名、复跑命令）。没有就写"未量过，属建议"。
6. **来源**：它是从哪一次失败或观察里长出来的（指向 `pitfalls/*`、`references/*` 的条目名，
   不指向具体轮次号或仓库日记）。

## 精简纪律（上下文是公共财产）

- 正文 ≤ 500 行、≤ 1400 词；超了拆 `references/`，正文只留"去哪查、什么时候查"。
- 模型已经会的常识不写（"什么是 FIFO"这种一句都不要）。每段自问："它值这些 token 吗？"
- 自由度匹配脆弱度：不可逆/易错的动作给**低自由度**（精确命令 + 前置条件 + 应看到的读数）；
  判断类给**高自由度**（原则 + 对照问题），不要假装能写成流程。
- 不许写绝对路径、不许写"本工程的 rNN/某文件第几行"、不许把工程专属数字当普适结论。
- 每条都要能单独被用：不许"必须先加载某几条"，也不许在正文里贴别的条目的文件路径
  （要用条目名引用，并说明依赖关系）。

## 怎么验证一条新技能有效（不是"写完就算沉淀"）

1. **格式**：`node <本包根>/_meta/check-skill-package.mjs <本包根>` 全绿（判条目数、索引双向一致、
   四问齐不齐、词数与行数、有无绝对路径）。
2. **可检索性**：用一句"只有症状、没有解法"的话去问，能否命中这条（命中不了就是 description 写坏了）。
3. **增益**：拿一个干净的小工程 A/B——不带这条 vs 带这条，看是否少走弯路（谁做都行，但要有数）；
   量不了就写"未量过"。
4. **陌生人演练**：让没参与过的人照条目做一遍，卡住的地方就是条目的缺陷，改条目而不是改人。
