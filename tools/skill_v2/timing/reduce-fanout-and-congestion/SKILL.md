# 高扇出与布线拥塞的识别与修法

## 适用场景

- `report_timing` 的路径块里 `Data Path Delay` 的 route 占大头（历史读到过 66 %／71 %／74 %），而 `Logic Levels` 只有个位数 ⇒ 不是锥深问题，继续砍逻辑是白费一次构建。
- 一族违例的终点是同一个驱动的多根扇出脚（广播使能、满/空标志、控制字、地址），或起终点横跨大片坐标。
- 单个网段就能吃掉大块预算（量过 fo=9 的一段单段布线 1.557 ns 这一类）。
- 利用率看着不缺面积（逻辑单元只用两三成）而你仍想加面积约束 ⇒ 缺的是线长，不是面积。
- 已经决定"让工具复制驱动" ⇒ 那么第 5～6 步的判据顺序必须先定下来再开构建。

## 使用方法

1. **先确认工具里真有这条命令**（一手资料优先级：本机 `help`／官方命令参考 ＞ 应用笔记 ＞ 文章博客 ＞ 模型记忆）。不开设计只跑 `help`，几十秒一次；下表是"要用的东西 → 查法 → 已量到的形状"，形状对不上就在你的版本上重新量，别套用。
   | 想要的东西 | 怎么查（不开设计） | 实测过的形状 |
   |---|---|---|
   | 按扇出排序的网名册 | `help report_high_fanout_nets` ＋ 跑一次落件 | 这条存在（阈值／条数／落件参数以 help 为准）；而 `report_design_analysis` 没有按扇出的模式，它唯一带 fanout 字样的选项是分析阈值，不是网名册 |
   | 扇出上限约束 | `help <你记忆里的命令名>` | 某版本没有这条通用约束，`help` 直接回 "No topics matched"——那名字属于旧工具族 |
   | 让工具复制驱动 | `help phys_opt_design` | 按扇出复制／对指定网强制复制／关键单元优化三处可选；副本对象名带 `_replica` |
   | 拥塞分区表 | `report_design_analysis -congestion` 跑一次看形状 | 某颗器件上只回到时钟区域汇总 ⇒ 那一格不能当依据 |

2. **命令不存在又被 `catch` 吞掉 ⇒ 假的"没差别"**：两滚都"跑完但变量没加上"，差分出来是一张全绿表。任何名册/差分脚本都要有"取不到对象就非 0 退出"的分支，空集写 `NOT_MEASURED`，不许当 0 行通过。
3. **出名册**：`report_high_fanout_nets`（阈值、条数、落件参数以本机 help 为准）按扇出排序留一份改前快照；再用对象查询把目标网的负载数一遍（`get_nets`／`get_pins` + 集合计数；集合命令名各工具不同，先 help）。两边对得上才开始动。
4. **判主导方**（每条违例各读一次，别拿全局 WNS 代替）：route 大且级数少 ⇒ 物理/扇出；logic 大且含进位链 ⇒ 深度问题，走拆锥那一族；两边都不明显 ⇒ 先怀疑那片绕不开，按上表最后一行确认拥塞读数能不能当依据。
5. **修法①（设计侧，高自由度）**：把广播信号按用途分组或独热化，让每根网的负载只覆盖真正消费它的那批终点。判据是名册里那根网的引脚数下降。收益上限先算：这条最多能抬多少，值不值一次构建。
6. **修法②（让工具复制，低自由度）**：用第 1 步确认过的那几个复制选项（原文口径是"对时序关键的高扇出网做基于单元复制的优化"，**选项名一律以本机 help 为准**）；help 明说副本对象名带 `_replica` ⇒ 机制是可数的。前置条件：一份已布局的 DCP 或正式流程里的物理优化钩子，且这一刀按第 8 步与用户确认过。
7. **机制判据与结果判据分开打印，顺序不许反**：
   - 机制行：副本对象计数、目标网引脚数前后，且与代价互相咬合（闭合等式：新增端点数 == replica 数 == 寄存器增量）。机制不绿 ⇒ 判 `MECHANISM_INERT`（"这一刀没打到东西"），**不许**写成"时序收益不成立"。
   - 结果行：逐时钟域名册差分（每域 setup/hold 的相对余量），任何一格不许变小；头条 WNS 的绝对差不作采纳依据。
   - 代价行：触发器/寄存器增量、LUT/BRAM/DSP、被挤紧的别的域。
   - 每条判据自带正对照（点名某根网必须测到下降）与负对照（恒等表必须为 0），否则它是装饰。
   - 机制证据的出水口有两个（实现 run 自己的日志与顶层控制台），只读顶层会把"动了"读成没动。
8. **先跟用户确认**：允许加多少寄存器（面积/功耗/别域余量）、是否允许在正式流程里挂物理优化钩子、这一刀按"同 DCP 快车道"还是"正式构建"归因。

## 失效条件

- **零违例（或目标检查已全正）的设计上，物理优化是结构性空转**：工具自己会打印 slack ≥ 0 ⇒ 跳过全部 setup 优化、跳过 hold 修复、网表未修改。征兆=两滚数字与基线逐位相同而位流不同；这不是"打平"，只许念"没达门槛"。
- 拥塞不是扇出造成时复制无效：违例源于固定布局（存储块/乘法器的硬位置）绕不开 ⇒ 只多花寄存器。征兆=机制行绿、目标网引脚数降了，但同一族 route 占比一格不降。
- 目标名单要复核：量到"扇出确实下降"的那根网名字像钟（带 mmcm 字样）时，先把它剔出目标名单再重开这一刀，否则归因错。
- 买到的收益与被拿走的东西落在**同一个域**，而那个域的 hold 本来就没有可信余量 ⇒ 再削几成等于把"每次重建掷 ±1 ps 硬币"请回来，判负。
- 跨构建的放置噪声盖过真实变化：0.000 ns 的噪声底**只对同一份 DCP 的重复滚**成立；换构建时 0.4 ns 量级摆幅里的差值不可主张。
- 走综合侧扇出属性那条路：属性名与可用性先用对象属性查询实测；没验过就不许写成"已按官方属性做"。

## 已验证效果

- 名册与归因：`report_high_fanout_nets` 量到某广播网约 240 引脚、一族 39 根 fo≥200；把某域最差族的根因从"两端离得远"改判成 FANOUT，靠的就是这个读数加单段布线延迟。
- 判负（机制绿、结果红）：强制复制那一族，`REPLICA_CELLS` 0→310，但 32 次名册比较里 4 格变差 ⇒ 拒绝。另一例目标族 setup +0.456 ns、副本 296 颗、LUT +31，而同域 hold 相对余量 −29.0 % ⇒ `DECLINE`。
- 判正（可复跑形式）：同一份 `opt.dcp` 单变量滚，机制 `239→1 引脚`、`_replica` 10 颗、端点 15,721→15,731，代价 Slice 寄存器 +10 而 LUT/BRAM/DSP 不变；三域 setup +0.033／+0.187／+0.298 ns，第四域 setup/hold 逐格不动 ⇒ 采纳（闭合等式两边都在）。
- 反面（早于工具侧杠杆）：给某满标志广播网加扇出上限那一刀，WNS 从 −0.062 拖到 −0.192、失败端点 28→34 ⇒ 回滚；它就是"先读占比再选杠杆"的理由。
- 空转证据：布线后物理优化在零违例版上的数字与基线逐位相同，判定记 `DECLINED（结构性空转，凭工具自己那三行）`。
- **未量过，属建议**：按用途分组/独热化这类改动在同一设计里的收益上限（没单独滚过正式构建）。

## 来源

- 长自三类观察：① 凭旧工具族记忆写下不存在的命令，被 `catch` 吞成一张假的"没差别"；② 复制驱动"机制动了但时序没赢"，一度被误写成"瓶颈不是扇出"；③ 在零违例设计上让工具做物理优化，两滚数字一格不差。
