
## 25. 2026-10-20 夜：UDP 遥测上板（r144→r146）、发送仲裁排队与 PS 的 JTAG 启动

- **r144 上板第一版遥测整包右移一字节**：监听器收到 `00 'V' 'D' 'E' 'O'…`，首字节 0、末字节被截。
  根因在 `udp_telemetry` 数据路径插了两级寄存器（`q <= pay[idx]` 再 `tx_data <= q`），
  而 `udp_tx` 在 IP 头最后一个字节提前一拍拉 `tx_req`、下一拍就要数据。删掉 `q` 后线上
  `VDEO...` 顺序正确（r145 板上 1 Hz 连续读到 magic 正确、tick 每秒 +1）。
- **单测为什么没抓到**：旧台架直接读 DUT 内部 `pay[]`，不经过 `udp_tx` 握手——正是
  "参考模型与 RTL 同一套算式"的变体。新的 `tb_udp_telemetry` 例化真 `udp_tx + crc32_d8`，
  从 GMII 口按帧偏移抓 86 字节，逐字节比对 DA/SA/type/IP-dst/UDP 端口/长度/32 B 载荷；
  对修前 RTL 红（`payload byte 0 got 00 exp 56`），修后两包 PASS（`PKT ok frame_bytes=86`）。
- **tick 字段曾是常数**：载荷 20..23 直接采样分频计数器，而 take 恰好发生在分频归零那一拍
  ⇒ 每包都相同。改为独立的 32 位秒计数（`sec_cnt`），台架新增"两包 tick 必须前进"判据。
- **rows_missed 是 sticky 的"上一次作废"**，不是当前帧缺行。r145 板上同时看到
  frames 每秒 +30 而 rows_missed 恒 300，就是这个语义。r146 在载荷 24..25 增加累计作废
  帧数（`reasm_fabort` 计数），监听器把旧字段改名为 `last_abort_rows`，一次给"发生几次 +
  最后一次缺多少"。
- **发送仲裁原来会在帧中间换源**：`protocol_sw` 在 `*_tx_start_en` 那一拍无条件切换。
  1 Hz 遥测若落在 ARP/ICMP 帧中间，会把该帧剩余字节换掉。r145 改成"请求先记账，
  udp/icmp/arp 三路都不忙才发一拍 granted 脉冲"，top 的 `udp_tx/icmp.tx_start_en` 改接
  granted。新增 `tb_eth_ctrl_arb`：ICMP 帧中请求 UDP、UDP 帧中请求 ARP，判据是每帧字节
  恒定且长度 13 拍、三帧顺序 ICMP→UDP→ARP、三个 granted 各一次。把 idle 条件人为改成
  恒真后台架红（`frame truncated: 4 bytes`），恢复后 PASS。
- **PS 启动恢复**：读回 boot mode = 0（JTAG 启动），CPU 原停在 BootROM。按文档顺序先
  `ps7_init` + `ps_app.elf`（xsdb）再装 PL，Cortex-A9 #0 的 PC 进入 DDR 应用区且持续前进，
  串口 COM6 115200 能应答 `help/stat/temp`：`TEMP degC=64.41 ... osd=64C gpio=0x64`
  （温度链从 PS 到 PL 的 gpio 读回一致）。注意 ELF 的 mtime 是 08:36、`src/ps/main.c` 是
  19:38，板上跑的是旧固件（命令表里没有旋转角度设定/归零）；重建 BSP 目录不在本机仓库。
- **r145 板上证据**：`system.bit md5=a064e7ee84ab`，ping 10/10；PC 推 512×300@30fps 时
  遥测连续读到 `link=1 frames≈+30/s pkts≈6600/s bad=1 tick+1/s sport=1234`；

- **r145 时序/资源**（impl_1 routed）：WNS 1.262 / WHS 0.059，TNS=THS=0，55,399 端点全过；

  BRAM 是最紧的一项，主要是 512×300 帧缓存与几何行缓存。
