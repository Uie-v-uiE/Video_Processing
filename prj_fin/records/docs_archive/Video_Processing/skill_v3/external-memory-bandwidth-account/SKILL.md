# 外存带宽账：先把竞争者列全，再算上限

## 适用场景

- 设计评审要回答"这条通路够不够"，而目前只有"应该没问题"。
- 症状与负载相关：加一路就好、减一路就坏；偶发；换个分辨率/帧率才复现。
- 有多主设备共用同一片内存（显示读出、相机写入、编码读出、DMA 中转…）。
- 不适用：纯片内流水的吞吐问题（那是逻辑深度与扇出，见 `depth-vs-routing-cut`）。

## 使用方法

**先查**：内存的实际位宽与时钟、每个主设备的突发/占用规则、互联的仲裁与读写切换代价——
**以器件手册与互联配置为准，不用"DDR 大概几 GB/s"这类常识**。取不到原文的数值只引公开转述并标"未核"。
**先跟用户确认**：能不能改缓冲策略（双缓冲要翻倍内存）、能不能降一路的刷新率、
以及"带宽不够"结论会导致的方案变更（换器件、改架构）是否在本轮授权范围内。

1. **列全竞争者**，一个都不许漏。做法：从地址映射/互联配置**反查**所有挂在同一端口上的主设备，
   而不是从记忆里点名。漏一路是这条账最常见的失效。
2. **逐路算需求**：`每帧字节 × 帧率`，再乘上**实际搬运量与净数据的比值**
   （stride 取整、格式对齐、色度子采样都会让实搬 > 净数据）。写清每一项的出处。
3. **算供给上限**：峰值 = 位宽 × 频率 × 每周期传输数；**有效带宽要再乘一个折扣**
   （读写切换、刷新、页命中/行冲突）。不要直接拿峰值当可用值——那正是"账算得通、板上坏"的来源。
4. **给结论加余量口径**：Σ需求 / 有效上限 = 占用率。写清这一版用的折扣是多少、
   为什么，以及占用率超过多少就要动方案。**阈值是自己定的处方，不是器件规格**，要标明。
5. **账与症状必须对得上**。如果占用率明显不够却从没坏过，或者占用率低却坏了，
   说明模型漏了一路或多算了一路 ⇒ 先修模型，再谈结论。
6. **能测就别只算**：跑一个只搬数据不做处理的通路，量出实测吞吐与"多路并发时各路的跌幅"，
   用它校准第 3 步的折扣。测不了就明写"未测，纸面账"，不许把纸面账写成实测结论。

## 失效条件

- **漏一路竞争者**：账看起来宽裕。征兆：改任何一路的速率，症状都不变（因为它本来就不在账里）。
- **拿峰值当可用**：永远"够用"。征兆：实测吞吐明显低于纸面值。
- **折扣拍脑袋**：换成一个看不见的自由参数，谁都能凑出想要的结论。折扣要么有出处，要么有实测。
- **忽略突发粒度与行边界**：跨页访问的真实代价远大于字节数账。症状是"尺寸非对齐倍数时才坏"。
- **把"整帧慢一拍"全归因带宽**：也可能是仲裁公平性或缓冲策略；只算带宽会把设计带偏。
- 纸面账不能证明板上够：结论必须标明来源是"手册计算"还是"实测"。

## 已验证效果

未量过，属建议：带宽折扣与页命中代价这两项没有在本队工程里做过实测校准，
所以本条只给"账怎么列"的形状，不给任何具体占用率数字（给了也是随设计变的）。
可复跑的形式：任选一条真实通路，输出三行——Σ需求、峰值供给、实测吞吐——
并检查 `实测吞吐 / 峰值供给` 这个折扣是否落在你假设的区间内；
若测量值明显低于假设，折扣必须重写，纸面账才算成立。

## 来源

长自一类反复出现的观察：撕裂/慢一帧/偶发丢样最后都落在"多条通路抢同一块内存"，
而纸面账当时都算得通；失效原因集中在**漏竞争者**与**用峰值当可用**两处。
配套：`pynq-dma-buffer-coherency`（一致性与对齐）、`depth-vs-routing-cut`（片内吞吐）。
