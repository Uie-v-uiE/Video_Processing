# 从题目到第一份位流：最短可验证路径

原则：**每一步都要留下一个能红的读数**，否则"能综合"这件事要等到架构全铺开后才发现不成立。

## 适用场景

- 新题目开工；或已经写了大量 RTL 但从未完整跑通一次实现。
- 症状：顶层与约束反复返工；第一次综合失败时无法定位是哪一类原因。

## 使用方法

**先查**：题目给的器件/板卡与引脚（板卡原理图或官方板卡资料，不靠记忆）、目标工具版本
（赛事通常限定版本区间，超出的要声明并保证脚本可复现）、构建脚本的落点约定。
**先跟用户确认**：第一版允许牺牲什么（功能面、时钟档位）、要不要先只做"点亮+回环"这一条通路。

七步，每步一个产出物：

| 步 | 做什么 | 产出物（能红的读数） |
| --- | --- | --- |
| 1 | 把题目压成一句话 + 一张最粗的框图（模块与边界，不画实现） | 框图文件；评审能指出一处"这里说不通" |
| 2 | 建目录骨架与**一条命令能跑完的构建脚本**（见 `project-skeleton`） | 跑通空壳工程综合：日志落盘 |
| 3 | 顶层先只接最少的端口（时钟、复位、一个 LED/一个回环口） | 综合成功 + 未约束端口清单（此时非空是**预期**） |
| 4 | 写第一版约束：时钟必须有，I/O 窗可以先欠，但**欠的要列成名单** | `check_timing -verbose` 名单落盘 |
| 5 | 跑一次完整实现出位流，不管时序 | 位流 + 资源占用 + 最差路径读数（三件同轮） |
| 6 | 上板点灯（或最小回环），拿到第一个**硬件**读数 | 上板件 + 回读值（见 `board-liveness-readback`） |
| 7 | 才把功能一块块加进来，每块按 `round-work-loop` 走一轮 | 每轮一个提交、一份改前红 |

第 2、5 步不许跳：跳过骨架直接铺架构，第一次失败会同时来自三类原因，定位成本是前面的数倍。

## 失效条件

- **"架构先做完再综合"**：第一份报告出来时，约束、时钟、端口命名全都要返工。
- **把第一版约束当终稿**：第 4 步的欠账名单必须在交付文档里书面挂着，否则"报告好看"是假象
  （见 `io-clock-constraints`）。
- **第一份位流就追时序收敛**：没有基线的收敛是猜的；先量到基线再谈优化（`global-timing-roster`）。
- 板卡与题目不符（封装/引脚数不同）时，第 0 步就要声明差异，别到上板才发现。

## 已验证效果

未量过，属建议：这条路径是按"每步留一个能红的读数"重构出来的，没做过带/不带的对照。
可自查的形式：任取一个卡在第一版位流的工程，数第 2 步与第 5 步的产出物在不在——
两个都不在 ⇒ 瓶颈就是它们，不是逻辑本身。

## 来源

长自两次"铺完架构才第一次综合"的返工，与一次"报告好看而约束树里一条 I/O 窗都没有"的读数。
配套：`project-skeleton`、`round-work-loop`、`io-clock-constraints`。
