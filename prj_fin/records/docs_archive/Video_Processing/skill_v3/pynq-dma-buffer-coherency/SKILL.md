# 搬运与缓存一致性：封装的最小形状与按症状定位

**两个方向不对称是一切坏点的根**：数据从缓存走向内存要做清理（clean），从内存走向缓存要做失效（invalidate）。
方向搞反症状相似、修法不同。Zynq 的 DMA 天生非一致（官方 AR 记录：`dma_alloc_coherent` 不保证一致），
"不报错但数据是旧的"就是它的签名。

## 适用场景

- 处理器写完一块内存让搬运引擎读 ⇒ 引擎读到旧内容或前半新后半旧。
- 搬运引擎写完一块内存处理器读 ⇒ 读到自己缓存里的旧行（残影）。
- 只在长度/地址不是对齐倍数时坏：坏在开头几字节、结尾几字节，或撞到邻居。
- 偶发、与负载相关，换个缓冲大小就好或就坏。
- 要给新设计定"搬运 + 缓存维护"的最小封装，而不是一处一份拷贝。

## 使用方法

**先查**（一手资料优先）：本平台缓存维护的方向与对齐要求、搬运引擎完成状态的语义（"已发出"还是"已落到内存"）、
**哪些端口天生一致**（AXI-Lite 控制路径不做维护）。逐条出处登记在 `references/locate-by-symptom.md`。
**先跟用户确认**：这块缓冲能否改成对齐分配（动内存布局）、是否允许为一致性多拷一份（空间换确定性）、
是否允许临时关某段缓存（影响别处性能）、维护操作是否要在中断/线程安全上下文里做。

封装的最小形状（缺任一项就不要复用这段代码）：

1. **缓冲描述**：起始地址、长度、对齐要求、方向（读入/读出/双向）、归属（此刻谁可以写）。归属要能打印出来。
2. **缓存标志的默认值在两代之间翻转过**——这是本条最容易写反的一处。
   新栈（3.x/4.0）的缓冲对象带 `coherent` 标志，`coherent=False` 时**可缓存**；
   旧栈 `Xlnk.cma_alloc(length, cacheable=0)` 的默认值却是**非缓存**。
   同一句"默认是缓存的"在两代里答案相反 ⇒ 移植代码时必须在本版本里现读一次默认值，
   并把读到的结果打印进证据件（别照旧文档、也别照新文档，照自己这台上的）。
   维护动作也成对：写出前 `flush`（同步到设备）、读入后 `invalidate`（从设备取回），
   而这两个调用**只在非一致（coherent=False）时才做事**——一致缓冲上调它们是空转，
   反过来指望一致缓冲自动同步则要看互联与端口是否真的 coherent（这一条要查器件手册，见失效条件）。
3. **搬运前一次维护 + 搬运后一次维护**，按方向选；两次都写进同一层，调用者不许自己拼"这次要不要清"。
   失效会丢弃未写回的数据——**处理器正在往同一块里写时做失效 = 数据丢失**，症状是"随机少一小块"，
   比读到旧值更难归因。这就是归属规则存在的原因。
4. **完成判定用硬件读数**，禁止固定延时/循环次数（它在空载时通过、负载高时偶然通过，是最坏的假绿）。
   两条静默形状要防：下发只写描述符、不等待；等待的超时**可能返回假值而不抛异常**
   （本包在部分版本里未能核到它是返回还是抛出 ⇒ 一律**接住返回值并打印**，别假设一定会炸）。
   新栈另有明确的通道状态错误（"通道未启动"/"通道不空闲"/"超过最大搬运长度"），
   以及"旧驱动已迁到 `pynq.lib.deprecated`"的显式报错——按旧驱动名写的代码会直接撞它。
   计数读数为 0 或读不到 ⇒ `NOT_MEASURED`。
5. **对齐按 IP 类型分族**：多数块搬运与流搬运的地址/长度有 8 或 16 字节的硬性要求，
   **但这些数字随 IP 配置（如 DRE 是否使能）与本包未能核到的旧 C 层实现而变** ⇒
   写法是"从本工程的 IP 配置与本版本源码/PG021·PG025 现查"，把查到的值写进表并在代码里断言，
   违反时**要么报错要么由判据红**，不许静默把坏数据搬过去。
   通用规则不依赖具体数字：**起址向下对齐、止址向上对齐，但绝不越过本缓冲的真实边界**；
   做不到就换行对齐的专用缓冲。
6. **并发归属**：同一块被两条通路写 ⇒ 慢一帧或撕裂（两个半帧拼一帧）。按代价从低到高：
   双缓冲轮转 ＞ 加锁串行化 ＞ 由硬件写、处理器只读。定好后写进表的责任方列（见 `pynq-register-map-readback`）。

## 失效条件

- **裸核/无缓存目标**：维护操作是空转甚至指令不存在。接口形状要保留（该层退化成空函数），
  否则换到有缓存的目标上方向全乱。征兆：为"能编过"到处插维护调用。
- **把一致性端口当非一致性处理**：多做维护只浪费带宽，少做就是数据坏；搞不清以器件文档端口描述为准，做一次实测。
- **靠异常类名判错**：`TCircularity`/`Alignment` 这类只存在于旧栈的 `pynq-dmadma`，新版本没有——
  照旧教程 `except` 会一条都不捕，异常直接冒到顶层。征兆：文档里的异常名在板上 `ImportError`。
- **拿 `xlnk.stat()` 的配额当可扩上限**：reserved 区是固定配额（读不到就判 `NOT_MEASURED`，不许按"应该够"放行）。
- **视频/流式通路**：帧尾缺结束标记 ⇒ 接收端不出最后一拍 ⇒ 读帧**永不返回**（症状是卡住，不是数据错）；
  按行宽算的字节数与 stride 不是 4 的倍数会立刻报错，但输出侧对齐官方明写"不保证"。
- **不许在没有对应硬件时宣称板上已修**：没板/没该外设时结论只能写"未在板上验证"或 `NOT_MEASURED`。

## 已验证效果

未量过，属建议：本条按官方文档/FAQ/源码（含 C 层对齐与等待逻辑）逐条核对，**未在本队板卡实跑 PYNQ**。
可复跑的形式（有对应硬件时才允许跑）：1 个已知图案缓冲 + 1 个紧邻其后的邻居结构，
跑 3 种长度（对齐倍数、倍数+若干字节、若干字节）× 2 个方向 = 6 项内容比对，
再加 2 项邻居存活检查（首行、尾行未被波及），共 `判 8 项`；
每项比"处理器侧参考结果 vs 硬件通路读回"，期望完全一致；
另跑 1 项变异对照：故意抽掉维护操作，6 项应稳定变红——抽掉后仍全绿说明这条判据是永绿的假判据。

## 来源

长自一类反复出现的观察：搬出来的数据"半新半旧"、首块坏或尾块坏，定位到最后全落在
**维护方向搞反**与**对齐取整**两点上；以及"用固定延时等搬运完成"在负载变化时复发、
"等待返回假值没人接"表现为随机丢帧。接口事实出处见 `references/locate-by-symptom.md`；
