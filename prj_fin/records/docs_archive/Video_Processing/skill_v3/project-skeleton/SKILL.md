# 工程骨架：让没参与过的人找得到入口

## 适用场景

- 新题开工；或已有工程但报告散落、复现步骤写不出来。
- 症状：别人问"这个数从哪来"你答不上路径；构建要手工点三下才开始。

## 使用方法

**先查**：赛事/接收方对目录与命名的硬性要求（名称纯 ASCII 小写、中文只进正文；
推荐结构里 `skill/` 与 `report/` 各是什么用途），以及板卡资料里引脚与器件型号的声明要求。
**先跟用户确认**：目录要不要与既有工程不同（改名会牵动所有引用者，见 `doc-rotation-damage`）、
哪些大件不入库（要同行声明词，见 `delivery-package-integrity`）。

照 `assets/skeleton.md` 落七件事，每件都对应一个"别人能不能复现"的问题：

1. `src/` 源码分层（rtl / ip / ps 或 python），顶层端口与命名一次定死。
2. `sim/` 台架 + **一条命令跑一个台架**的入口脚本（带改前红落点，见 `anchor-bench-before-edit`）。
3. `build/` 构建脚本（非交互、日志与报告落点固定）+ 综合实现报告目录。
4. `board/` 上板工程、运行脚本与实测输出。
5. `data/` 测试数据与黄金参考（只读位置，别和产物同名轮换）。
6. `skill/` 技能包（本包放这里；README 要写每项的适用范围/使用方法/失效条件）。
7. `report/` 设计报告 + 大模型协作记录（提示词、回答、自我纠错轨迹）。

骨架成立的判据不是"目录齐"，而是这三条能红：
`bash build/run.sh` 从零跑通并落出报告；`node`/`bash` 的一条比对命令能对 `data/` 里的参考给出判定；
新克隆（clean checkout）里文档点名的件**都在**（见 `delivery-package-integrity`）。

## 失效条件

- **骨架先于功能铺满**：目录空壳会被当成进度。每一层都要有至少一个能被引用的产出物。
- **构建脚本要人手工点**：第一次失败时无法定位是哪一类原因（见 `start-to-first-bitstream` 第 2 步）。
- **报告只落在二进制日志里**：下一轮拿不到同口径输入（见 `round-work-loop` 第 5 步）。
- 把工程专有读数写进骨架文档：那些属于 `report/`，写进来这个模板就只在原工程成立。

## 已验证效果

未量过，属建议：模板来自一轮真实工程的目录收敛，没做过带/不带对照。
可自查的形式：任选一项要求（一条命令跑通 / 比对有判定 / 克隆后引用都在），
在陌生机器上按 README 走一遍，卡住的地方就是模板缺陷——改模板，别改人。

## 来源

长自两类观察：报告只活在一次终端输出里；接手散乱工程时"这个数从哪来"没人答得出。
配套：`start-to-first-bitstream`、`round-work-loop`、`delivery-package-integrity`。
