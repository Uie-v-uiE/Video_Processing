# 症状路由表（先分派，再动手）

## 适用场景

拿到一句话现象（"画面上方几行慢一帧""hold 余量像掷硬币""检查器全绿但现场还是坏"），
需要在 30 秒内决定：读哪条、动手前先搜什么、哪一步必须先问人。也用于派工——
给队员或 agent 分派任务时，条目名比口头描述可靠。

## 使用方法

按症状查表；**"先搜/先确认"那一列是动手前的检索动作，不是可选项**。
**先跟用户确认**：症状还原到哪一层（有的描述本身已是结论）、以及分派结果要不要改变本轮边界（一次只修一件事？见 `ask-before-irreversible` 与 `round-work-loop`）。
一手资料的优先级统一为：厂商用户指南/数据手册/接口规范 ＞ 应用笔记 ＞ 工具自身回读 ＞ 教程 ＞ 模型记忆；
文档站是 JS 单页应用，直接 HTTP 抓到的"请启用 JavaScript"**不是**"查不到"的证据。

| 症状 | 先读这条 | 动手前先搜 / 先确认 |
| --- | --- | --- |
| 只有现象、不知道该从哪一条读起 | `symptom-router` | 就是本表；先还原成可观测现象 |
| 只盯最差路径，改完别处变差 | `global-timing-roster` | 本工具按时钟域出摘要的命令；"别的域不许变差"的阈值 |
| 报告读不出瓶颈类型 | `prompt-report-to-bottleneck` | 先用只读探针打印报告**原文形状**再写解析 |
| 关键路径是深逻辑锥 / 插了拍不不动 | `depth-vs-routing-cut` | 该命令的选项到底存不存在（`help` 探针）；收益上限先算 |
| 改了钟之后"时序突然变好" | `clock-change-constraint-reach` | 逐条按名回查点该钟的约束是否还生效 |

| 跨域警告成串 / 偶发单拍错值 | `cdc-and-async-reg` | 同步器级数与属性的工具语义；加了属性时序会不会动 |
| 截断、回绕、只在边缘几行错 | `width-and-overflow-audit` | 每一步的舍入方向；口头报出的数有没有出处 |
| 板子加载后行为对不上仓库 | `pynq-overlay-load-verify` | 本版本有没有身份回读口；允许刷写吗 |
| 寄存器读不回来 / 默认档不符 | `pynq-register-map-readback` | 该格的读写属性与复位值出处；谁能写这一格 |
| 数据半新半旧、首块尾块坏 | `pynq-dma-buffer-coherency` | 本平台维护操作的方向与对齐要求；能否改对齐分配 |
| 画面停住 / 读帧不返回 / 换分辨率错位 | `pynq-video-frame-pipeline` | 本版本帧通路类名；`parked` 与结束标记怎么读 |
| 上位机常量与寄存器表不一致 | `contract-to-host-bindings` | 表是不是唯一真源；`readback=no` 的格谁挂着 |
| 撕裂 / 整帧慢一拍，与负载相关 | `external-memory-bandwidth-account` | 把所有竞争者列全再算账；折扣有没有出处 |
| 串口无回显 / 日志 0 字节 / 读数永远不变 | `board-liveness-readback` | 这个字段凭什么会动；能不能读这些口 |
| 改前没红、不知赢在哪 | `anchor-bench-before-edit` | 在**未改**的树上跑同一把尺子 |
| 某判据从来没红过 / 检查器全绿但真实运行红 | `ruler-teeth-and-empty-sets` | 夹具是否绕过提取层；重跑真实件 |
| 0 条比较却报通过 / 判定词读不出 / 把没测到写成通过 | `three-state-verdicts` | 三态与计数地板的口径；空集判未测 |
| 比对全绿却查不出差异 | `golden-frame-compare` | 豁免必须按期望值作键 |
| 命令返回 0 却什么都没发生 | `vivado-tcl-probe-traps` | 打印集合大小与 rc；配正对照 |
| 报告被自己的遍历扫进射程、自指读数 | `ruler-teeth-and-empty-sets` | 检查器输出落包外并显式排除 |
| 构建结果与源不符 / 在飞被改 | `artifact-provenance-binding` | 指纹工具是哪个；跑前打还是跑后打 |
| 文档改口后出现怪句 / 两处各一个数 | `doc-rotation-damage` | 谁在机器读这段文本（读尺子源码） |
| 交付包"点名的件不在盘上" | `delivery-package-integrity` | 在干净检出上跑同一把尺子 |
| 新工程目录怎么摆、别人找不到入口 | `project-skeleton` | 赛事推荐的目录与命名要求；哪些大件不入库 |
| 不知这一轮该产出什么 | `round-work-loop` | 本轮边界（只做一件事？） |
| 接手新题不知从哪下手 | `start-to-first-bitstream` | 骨架与"一条命令跑完"的构建脚本 |
| 要从算法描述定软硬件划分 | `prompt-algo-to-hw-partition` | 每步数据量与访问模式；实时约束的出处 |
| 要让别人复核我的产出 | `prompt-adversarial-review` | 它只报不改；范围由遍历现算 |
| 下一步不可逆 / 要动演示画面 / 要发布 | `ask-before-irreversible` | 题目与用户已表态的边界 |

**用法约定**：这张表只做分派，不做结论。落到具体条目后以该条目的 `使用方法`/`失效条件` 为准。
表里没列出的症状说明本包还缺一条；新增条目时**同时**给它配一条路由用例（否则 `V1` 会红）。

## 失效条件

- **症状本身就是结论**（"这就是约束问题"）⇒ 先还原成可观测现象再查表，否则你会顺着预设找证据。
- **多条同时命中**：按"能伤硬件/不可逆"优先，其次"会让读数不可信"（尺子类），最后才是效率类。
- **表与条目正文冲突**：以条目为准；冲突意味着改过一条而没改表，属于"改口没改完"。
- 本表不覆盖架构级取舍（选什么器件、买什么板卡、要不要换方案）——那是人定的部分。

## 已验证效果

本表的每一行同时是一条评测用例：跑 `node evals/route-eval.mjs .` 会打印"症状→条目"的词面 top-1 命中情况，实跑读数记在 `README.md` 的"已验证的复用结果"一节。未量过的是另一件事：带模型的触发率没测过（测法见 evals 目录那份增益口径）。本表是那份评测的用例来源：表里的每一行都是一条"症状 → 期望条目"。

## 来源

长自两类观察：报告点名的问题与真实根因不同层（约束缺失 / 尺子假绿 / 设计缺陷），需要先分派；
以及口头派工导致同一症状被分到不同条目。结构借自"按症状索引技能"的公开做法。
