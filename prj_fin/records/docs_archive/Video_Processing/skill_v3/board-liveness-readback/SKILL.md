# 判活与回读：先证明"能动的字段真的在动"

## 适用场景

- 现场演示或夜间长跑中，需要在几十秒内回答"这块板还活着吗"，而不是重跑 20 分钟的台架。
- 出现：串口无回显；日志存在但 0 字节；某个遥测字段跨几次刷写完全相同；计数器读到 0。
- 需要为新设计定"最小可判活回读口"。
- 不适用：纯静态检查（编译期、约束覆盖率），那些有报告就读报告。

## 使用方法

**先查**：本平台有哪些口天生可读（JTAG 硬件目标、寄存器回读、串口、网络）、
读这些口会不会带动被测对象（读 FIFO/握手类寄存器有副作用，读前先确认它是"只观测"还是"会推进"）。
一手资料优先级：器件/工具的调试章节 ＞ 应用笔记 ＞ 教程 ＞ 记忆。
**先跟用户确认**：是否允许读这些口（有些读操作会清空状态）、是否允许为了判活单独加一个计数器（那是 RTL/固件改动，要单独一轮）。

1. **区分三种"没读数"**：路径死了、读数冻了、我没读到。判据不同：
   路径死了＝连接建立失败；读数冻了＝连得上但某个本该变的字段不动；没读到＝解析器读空却打 0。
2. **判活看三样，三样都读不到就判 `NOT_MEASURED`，不许猜"还在跑"**：
   进程/任务是否在册、日志是否随时间增长、产物 mtime 是否推进。
   0 字节日志通常意味着"刚起"或"已成孤儿"，**不是进度证据**。
3. **每个遥测字段先问"它凭什么会动"**。跨刷写完全相同的字段是**冻住的通路**，不是坏板：
   用刷写前后的两份快照对比来定它属于哪一类；要证活就找一个**构造上必然会变**的字段
   （温度、包计数、运行秒数）。反例来自真实教训：一个"帧计数"其实是**当前文件的总帧数**，
   按定义就是静态值——差点据此立一条不存在的缺陷。
4. **计数器读到 0 必须与存活标志同读**。"丢包 0"在"没有流"时是空集判定，不是通过。
   每条 `== 0` 的判据都要点名它依据的 liveness 字段。
5. **可疑读数用一次 A/B 归因，不靠推理**：把上一轮已知好的产物重新刷一遍、给同一刺激、
   再刷回来。四个读数逐字节相同 ⇒ 该现象早于本轮改动。这比任何解释都便宜。
6. **探针自身的形状要先证**：查询硬件对象的接口在"打开目标"之前返回空集合；
   批处理脚本可能**退出码 0 而日志写着 FAILED**。判据要从文本读判定词，别从 shell 的 `$?` 读。
7. **现场最快的一轮循环**：一方控制串口/终端、读出数值、只问不超过三个单事实问题
   （"现在看到几个""它是整数还是带单位"）。比让模型猜画面可靠得多。

## 失效条件

- **用"跑一次没坏"当判据**：负载变了症状就回来，回来时看起来像新问题。
- **把读口的副作用当成被测行为**：读一个会自清的状态寄存器，然后说"状态已复位"。
- **遥测字段由静态量喂**：字段永远等于一个常量或文件属性，跨版本同值被误读成冻死。
- **只用一个数判活**：单一计数器可能因为该通路本来就静止而是 0。至少两样独立证据。
- **探针脚本自己骗自己**：`cmd | tail` 之后读 `$?` 拿到的是 `tail` 的状态；
  空日志分不清"没输出"与"回显被吞"。判活脚本必须打印每一步的 rc 与非空断言。
- 没有可回读口的工程：本条只能当"该建什么口"的清单用，别把 checklist 当读数。

## 已验证效果

形状已在一类真实调试中反复生效（读数不来自 PYNQ，而来自裸机+串口+寄存器回读的工程）：
"跨刷写同值的字段"被证明是**静态定义**而非冻死通路——判据是同值 + 定义核对；
"计数器 0"配 liveness 标志后，空载与无流两类被分开。
可复跑的形式：任选两个字段，做"刷写前快照 / 刷写后快照"两份，
逐字段判"能动 / 冻住 / 不可比"三种读数并打印各自的依据；判据在字段实际未变时必须能红。

## 来源

长自三类观察：串口无回显被判成板子死了（其实是握手字段是静态量）；0 字节日志被当成"还在跑"；
以及"丢包 0"在空闲链路上被记成通过。配套见 `artifact-provenance-binding`（件与树绑定）、
`ruler-teeth-and-empty-sets`（空集与比较数地板）。
