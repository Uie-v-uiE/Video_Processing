# 由契约表生成主机侧绑定：一处真源

## 适用场景

- 软硬件接口定稿后，主机侧要写常量、读写封装与测试骨架。
- 症状：文档写一档、板上另一档；主机代码里的地址常量与表不同步；新增一格没人补测试。
- 不适用：只有两三个寄存器、且从不变更的小工程（手抄更快，但要写清"手抄"这个事实）。

## 使用方法

**先查**：位段与复位值的**出处**（IP 地址映射与数据手册那一张表；取不到就留空并接受被判红，
别把记忆里的数写进表）。**先跟用户确认**：哪些格允许 `readback=no`（那是不可回读，要书面挂着）、
`owner=both` 的格由谁负责仲裁（这是取舍不是技术判断）。

1. 把 `assets/contract.csv` 当模板，列固定为
   `name,offset,bits,access,reset,unit,owner,readback`。表头缺列 ⇒ 生成器直接红。
2. 跑校验 + 生成：

   ```bash
   node scripts/gen.mjs assets/contract.csv --out-dir build/generated
   node scripts/gen.mjs --self     # 8 项对照，含 4 条"故意写坏该红"
   ```

   跑完应看到：`判 N 项 条目=M 红=0 未测=0 PASS`，其中 **N 是做了多少次比较**（重叠检查是两两比较，
   所以 N ≥ 行数）；表里没有条目 ⇒ `NOT_MEASURED` 并退出码 2，**空表不算通过**。
3. 生成物写进构建目录而不是手工维护的源文件里，并加一条判据：
   主机代码里出现的地址若不在生成物中 ⇒ 红。这一条才是"两边漂移"真正的止疼药。
4. 单位/换算只允许在表里出现一次（例：`dB_over_8`）；主机侧再手写一次换算就是第二份真相。
5. 每次改表要同轮跑：生成 → 判据 → 与上一轮生成物 diff（逐字一致才叫确定性生成）。

## 失效条件

- **表不是唯一真源**：有人继续改生成的头文件 ⇒ 下一次重跑覆盖掉那处修改，症状是"我明明改过"。
- **把 `reset` 当运行时读数**：它是抄来的黄金值；要证明它得回读（见 `pynq-register-map-readback`）。
- **位段重叠检查覆盖不了跨 offset 的语义重叠**（同一功能两个别名地址）：那是接口缺陷，表看不出来。
- **`owner=both` 却没有归属规则**：生成的常量没错，硬件行为仍会慢一帧或撕裂。
- **生成器与判据用不同词表**（例如判据认 `rw/ro/wo` 而表里写 `R/W`）：豁免会静默吞掉整片。
  ⇒ 两边共用同一份闭合词表，读不到就全部判红（fail-closed）。

## 已验证效果

`node scripts/gen.mjs --self` 实跑读数：

```text
T1 正对照全绿 比较=4 问题=0 PASS
T2 位段重叠 / T3 缺复位值 / T4 读写词表外 / T5 bits 形状错 —— 各自命中 PASS
T6 空表判未测 比较=0 PASS
T7 两次生成逐字一致 h一致=true js一致=true PASS
T8 产物含表里每一行 行数=3 出现数=3 PASS
判 8 项 红=0 未测=0 PASS
```

这 8 项是**这条脚本自己的**对照，证明它能红、能确定性生成、不漏条目；
它不证明"表内容正确"——那是 `pynq-register-map-readback` 里回读三元组的事。

## 来源

长自一类反复出现的观察：手工维护的两边漂移、新增条目漏测试、地址与复位值靠抄、
以及"两次生成结果不一样"被当成小问题（其实是生成器读了本轮状态）。
配套：`pynq-register-map-readback`、`three-state-verdicts`、`doc-rotation-damage`。
