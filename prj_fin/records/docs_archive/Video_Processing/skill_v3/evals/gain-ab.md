# 增益怎么量：baseline vs 带技能

本包没有做过"带这些条目 vs 不带"的对照，所以 README 与条目的 `已验证效果` 里
凡是没数字的都写成了「未量过，属建议」。这份文件给**想补这一步**的队伍一个可执行口径，
形状借自赛事 §3.1.5.2 对基线入口的定义（同一模型、同一上下文，绕过技能包，单次生成，不重试、不给工具）。

## 最小实验设计

```text
任务：从一份真实报告出发，产出"下一步做什么"的判读 + 一条能红的判据设计。
条件 A（基线）：只给任务描述 + 报告原文，不给本包任何条目。
条件 B（带技能）：额外允许检索本包（先按症状选条目，再按条目正文执行）。
每个条件跑 3 次（同模型、同温度、同上下文预算），共 6 次运行。
```

## 打分表（机械可判的部分先自动，剩下的才交人）

| 维度 | 判据（能机械判） | 为什么算增益 |
| --- | --- | --- |
| 有没有先要"改前红" | 输出里是否出现"在未改动的树上跑同一把尺子"这一动作 | 缺它就是断链的第一来源 |
| 读数有没有落件 | 是否给出**相对路径**的文本件 + 复跑命令 | 只在终端里存在过的读数下一轮无法继承 |
| 差分是否成对 | 是否同时列"预期变好"与"可能变差"两列 | 只列赢面=没做差分 |
| 有没有被射程骗 | 是否把"约束不再覆盖"当作需要排除的解释 | 本包最贵的一类误判 |
| 判定是否三态 | 结论是否用 `PASS/FAIL/NOT_MEASURED`，且空集不判通过 | "没扫到当通过"是假绿的根 |
| 不可逆动作前有没有问 | 是否出现"要先确认"的具体项 | 授权边界是协作质量的一部分 |

**计分**：每条 0/1，六次运行各自打分；增益 = B 的均分 − A 的均分。
报告时**必须一起写**：模型与版本、上下文预算、每条运行耗时与 token、以及"评分者是谁"（机械项与主观项分开报）。

## 三个门槛（不满足就别写"已验证有效"）

1. **同上下文预算**：B 组多花的 token 要如实计入成本——技能不是免费的。
2. **正对照 + 能红对照**：判分脚本自己要能构造一个"B 并不比 A 好"的用例并读出这个结果。
3. **不循环引用**：不要用本包的条目给自己出题（会挑到条目能答对的题）；题目来自真实工程失败。
