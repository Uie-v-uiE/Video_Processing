# 构建与证据件的竞态

## 适用场景

- 综合/实现/批处理在跑，同时有人改源、改约束、改脚本。
- 上一轮被中止，下一轮的读数要沿用同一个输出目录。
- 日志、报告、快照要进版本库或当某一轮的证据。
- 不适用：无并行、无覆盖的纯手工单件流程。

## 使用方法

**先查什么**：先确认盘上现在是谁的件——工具自己的工作目录、报告文件头的生成参数与修改时间、在飞的进程清单；一手顺序=件本身＞工具日志＞记忆。**先跟用户确认**：杀进程、移动或覆盖历史快照、改输出目录结构、把二进制件排除出版本库——这些会影响别人正在用的件或回滚能力。

竞态排查总则：**任何"对不上"先问三件事**——这份件是哪一轮生成的（件头/时间戳）、有没有别的进程正在写它（活体探测）、我读的是不是它（路径与 glob）。三件没核完之前，不下"构建变好了/变坏了"的结论。

### 坑一：构建在飞时改同一批源 ⇒ 工具静默重新综合

- 触发条件：批任务运行中编辑它已读入或将再读的源文件。
- 现象：没有报错，但那一格读数的归属不纯——分不清改前还是改后。
- 排查步骤：1) 看日志是否出现重新分析/重新综合同一模块的迹象（同一文件出现两次处理）；有⇒静默重跑坐实；2) 对质时间：源文件修改时间落在构建起止之间⇒被吸收进本轮；3) 核该模块是否同时出现在新旧两份网表/报告里；4) 都干净而读数仍怪⇒我的解析错，去核对取的哪份件。
- 根因分类：竞态（构建生命周期不冻结输入）。
- 修法：该轮读数标 NOT_MEASURED 并重跑；改动记入下一轮。
- 预防：构建在飞时源树只读；要改先停干净再改；改前检查有无活体（见坑三）。

### 坑二：正在运行的脚本被自己编辑

- 触发条件：脚本跑着的时候编辑同一个文件。
- 现象：语法检查（如 `bash -n`）通过，跑到中途报语法错，位置前后不着。
- 排查步骤：1) 比对脚本修改时间与进程启动时间：改在跑之后⇒竞态坐实；2) 原文件不动、同一输入重跑一次：不再复现即确认；3) 复现且报错位置固定⇒不是竞态，是真错或解析错；4) 查该脚本是否在运行中自己再读自身（循环里 source/eval 同一文件最易犯）。
- 根因分类：解释器按字节偏移边读边执行，改文件移动了偏移。
- 修法：停干净后从副本跑（先复制再执行，不原地执行）。
- 预防：运行中禁编辑正在执行的脚本；改动写入新副本、下轮生效。

### 坑三：中止批任务留下孤儿进程继续写同一份运行目录

- 触发条件：中断批任务后立刻起下一轮，而工具子进程没被一起终止。
- 现象：下一轮读到脏件——半新半旧的报告、写一半的文件；读数诡异。
- 排查步骤：1) 活体探测：列相关进程是否仍在、输出目录内文件修改时间是否还在推进；2) 有活体⇒这份件不可信，等它结束或干净终止全部相关进程；3) 无活体而件仍不完整⇒上一轮遗留的截断件；4) 确认目录里没有两个来源的同名件。
- 根因分类：中止只杀了父进程，子进程仍在写。
- 修法：清孤儿后重跑该轮；地板检查不通过就以非 0 退出，不继续读。
- 预防：中止用能终止整个进程组的方式；起新轮前先跑"活体探测+非 0 退出"的地板检查。

### 坑四：0 字节日志被当成"还在跑"

- 触发条件：以日志大小判断任务是否活着；子进程输出块缓冲未刷出。
- 现象：日志空着以为在跑（实际卡住），或以为失败了（实际在写别的件）。
- 排查步骤：1) 别只看日志，轮询工具自己的工作目录有无新增/更新的中间件；2) 核进程清单：在⇒在跑，只是输出未刷；3) 进程不在且日志 0 字节⇒启动即失败，读退出码与错误流；4) 件在推进而日志不动⇒缓冲问题，可继续等。
- 根因分类：块缓冲使日志不是进度实时指标。
- 修法：改判活依据为"输出目录 mtime 推进+进程在册"。
- 预防：需要实时进度时设行缓冲或周期刷盘；判活一律双看。

### 坑五：探针脚本硬编码输出路径，覆盖上一轮唯一的快照

- 触发条件：探针/提取脚本写死固定输出文件名，每轮都往同一处写。
- 现象：差分没有基线——上一轮唯一的件被覆盖，改口无法核对。
- 排查步骤：1) 先看盘上现在是谁的件：读件头标识与修改时间；2) 核输出路径是否含轮次标识（没有⇒每轮互相覆盖）；3) 查版本库里该路径的历史，确认是否还能找回基线。
- 根因分类：固定路径+无轮次标识。
- 修法：按修改时间归档既有件再写，或输出名带轮次/时间戳。
- 预防：探针输出目录规则化（每轮一目录），唯一快照先入库再生成新的。

### 坑六：同一报告目录两份版本混读

- 触发条件：目录里同时存在两次运行、两个工具版本的同名报告，glob 一网打尽。
- 现象：字段对不上、数值口径不一致，报告"看起来有两套"。
- 排查步骤：1) 列目录内同名件的所有变体（扩展名、后缀、时间戳差异）；2) 读每份件头确认生成器版本与参数；3) 一次只认一份：按生成时间取最新，其余显式排除；4) 核对提取脚本取的是哪一份（路径打印出来）。
- 根因分类：目录不做隔离，解析层按模式匹配取件。
- 修法：固定"一次运行只认一份生成器产物"，并在结论行写明件头信息。
- 预防：一轮一目录；旧件归档不留在解析路径里。

### 坑七：证据件用二进制/压缩格式，进不了版本库

- 触发条件：把 GUI 会话文件、压缩数据库当机器证据。
- 现象：版本库不收或无法 diff，别人取包后无法核对读数。
- 排查步骤：1) 查版本库对件的状态（未跟踪/被忽略/过大）；2) 确认能否用文本导出命令产出同一读数；3) 对比文本导出与原件的字段是否等价；4) 确认交付包规则要求哪些件必须随包。
- 根因分类：证据格式与"可核对的文本"要求错配。
- 修法：机器证据统一落文本（.txt 一类），或交给版本库自身跟踪；原二进制只作附件不作判据。
- 预防：写探针时就规定输出为纯文本。

### 坑八：重跑同一轮时 md5 指纹把行尾算进去

- 触发条件：重跑后对比证据件的哈希指纹，而件只有行尾（CRLF/LF）或编码差异。
- 现象：读数明明一样而指纹不同，被判成"本轮变了"，死磕无关差异。
- 排查步骤：1) 先看两份件的实质内容差异（逐行比对并忽略行尾）；2) 只有行尾/空白差异⇒无关差异，改按内容哈希；3) 内容真不同⇒不是指纹算法问题，回坑一/坑六查件的归属；4) 确认归一化规则写进指纹脚本并一致沿用。
- 根因分类：指纹算法作用在字节序列而非内容。
- 修法：指纹按归一化内容（按行、去行尾差异）计算。
- 预防：定指纹规则时先声明"归一化什么、为什么"。

## 失效条件

- 工具串行执行、且每轮用全新隔离目录时，坑一/坑三/坑五基本不会触发；不要为了套本条而虚构竞态。
- 活体探测依赖能列出进程清单的手段；在被严格隔离、看不到宿主进程的环境里，这一招退化为"看输出文件是否还在长"，结论强度下降，要标明。
- "件头能证明归属"只在件自带生成时间/参数时成立；被裁剪过的报告没有件头，只能靠路径与 mtime，而 mtime 会被拷贝改写——征兆是 mtime 比内容里的时间戳新。
- 归档策略一改，历史判据里依赖旧路径的部分会静默失效；改目录结构要与按名点人的检查同步核。
- 本条只治"件从哪来、能不能信"，不治"读数该怎么解读"；后者属于时序/验证类条目。

## 已验证效果

未量过，属建议。可自查读数：一轮内报告文件数是否唯一、中止后活体探测的通过与否、指纹比对在"行尾归一/未归一"两种规则下的差异数。

## 来源

长自一类观察：构建在飞时改源致工具静默重综合、那一格读数归属不纯；正在运行的脚本被自己编辑，出现语法检查过、跑到中途报语法错的假怪；中止批任务后孤儿进程继续写同一份运行目录；0 字节日志被当成还在跑；探针硬编码路径覆盖上一轮唯一快照；同一报告目录两份版本混读；二进制件进不了版本库；重跑时行尾被算进指纹判死无关差异。相邻条目：workflow/before-an-rtl-change、pitfalls/ruler-fake-greens、verify/three-state-verdicts。
