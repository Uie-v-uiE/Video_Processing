# 01 · 颜色、灰度、二值化与反色：点运算为什么"和旋转天然兼容"

> 本工程效果链有五级：灰度 / 二值 / 模糊 / Sobel / 反色。
> 它们分成两类，这个分类**直接解释了第一版那个"旋转时有些效果保不住"的问题**。

---

## 1. RGB565：为什么是 16 bit 而不是 24 bit

| 格式 | 每像素 | 512×300 一帧 | 说明 |
|------|--------|--------------|------|
| RGB888 | 24 bit | 3.69 Mb | 标准，但带宽/存储贵 |
| **RGB565** | **16 bit** | **2.46 Mb** | 红 5 bit、绿 6 bit、蓝 5 bit |
| YCbCr422 | 16 bit | 2.46 Mb | 视频常用，需色度抽样 |

选 565 的理由很实际：**人眼对绿色的分辨率最高**，所以绿色给 6 bit；
而 16 bit 正好是 2 的幂次分之一，地址计算简单（像素号 = 字节偏移 >> 1）。

**位域排布（本工程的约定）**：

```
像素 16 bit = { R[4:0], G[5:0], B[4:0] }     // 高位在左
一个 64bit AXI 字 = { p3, p2, p1, p0 }        // 4 个像素，p0 在最低 16 bit
```

展开到 8 bit：`R8 = {R5, R5[4:2]}`（高位复制补齐）或 `R8 = {R5,3'b0}`（简单左移）。
本工程各模块取哪种，见 [模块详解 · 效果链](../03_模块详解/05_效果链.md)。

## 2. 点运算 vs 邻域运算：一个决定架构的分类

| 类别 | 定义 | 例子 | 与旋转的关系 |
|------|------|------|--------------|
| **点运算** | `out(x,y) = f(in(x,y))`，只看当前像素 | 灰度、二值、反色、亮度/对比度、查表 | **任意坐标变换都成立** |
| **邻域（窗口）运算** | `out(x,y) = f(以 (x,y) 为中心的 3×3/5×5 邻域)` | 均值模糊、Sobel、中值、形态学 | **要求邻域在"扫描序"上连续** ⇒ 旋转时会出问题 |

**这就是第一版那个问题的全部本质。** 下面说清为什么会出问题、以及正确的解法。

---

## 3. 灰度：把三个通道压成一个

### 3.1 为什么不是简单平均

人眼对三种颜色的敏感度不同（亮度感知），标准加权（ITU-R BT.601）：

```
Y = 0.299 R + 0.587 G + 0.114 B          // R,G,B ∈ [0,255]
```

用平均 `(R+G+B)/3` 会把蓝色提得太亮、红色压得太暗，视觉上"发灰发蓝"。

### 3.2 硬件怎么不做浮点乘法

定点化：把系数乘 256（Q8）再右移。

```
0.299 × 256 = 76.5 → 77      0.587 × 256 = 150.3 → 150      0.114 × 256 = 29.2 → 29
Y ≈ (77·R + 150·G + 29·B) >> 8
```

校验：R=G=B=255 ⇒ `(77+150+29)·255 = 256·255` ⇒ `>>8` 得 255 ✔ 不溢出、白仍为白。

再省一点：系数取 2 的幂组合，把乘法变成移位相加：

```
Y ≈ (R·64 + R·16 + R) + (G·128 + G·16 + G + G/2…) + (B·32 − B)  一类近似
常用极简式： Y = (R·77 + G·150 + B·29) >> 8   // 一个 DSP48 就够
或更省：     Y = (R·80 + G·150 + B·26) >> 8   // 80=2^6+2^4，可用移位
```

**一个关键工程事实：本工程只有 220 个 DSP48，而效果链每拍要处理一个像素。**
灰度/Sobel 都要乘常数 ⇒ 若每个乘法都占一个 DSP 就紧张。
所以要么把系数拆成移位相加（用 LUT），要么复用同一个 DSP（时分）。
具体用了几个 DSP，看 `build/utilization.rpt` 里 `DSPs = 13 / 220` —— 很宽裕，
说明这个设计选择了"少量乘法 + 移位"的路线（旋转的 sin/cos 乘法也在这里）。

### 3.3 灰度之后怎么变回 RGB 显示

`{R,G,B} = {Y,Y,Y}`（本工程的做法），或者写回 565 时 `Y` 截成 5/6/5 bit。
**截断会带来量化误差**：8 bit 灰度压回 6 bit 绿会丢 2 bit ⇒ 缓变背景上可能出现色带，
这就是 `ROTATION_AND_EFFECTS` 里"grad 渐变图案用来查量化/色带"的判据意义。

## 4. 二值化：一个比较器 + 一个可调阈值

```
out = (Y >= TH) ? 白 : 黑
```

要点：

1. **阈值从哪来**：本工程由上位机串口命令 `TH80` 写进 AXI GPIO 的 `[15:8]` 位，
   PL 侧 `effect_ctrl.v` 同步后送给 `proc_binary.v` ⇒ **阈值是运行时可调的**，
   不是编译期常数（这决定了它必须做跨域同步，见 02 篇）。
2. **在哪个空间比**：必须先转灰度再比（在 RGB565 上直接比"和"会得到奇怪的结果）。
3. **滞回（hysteresis）**：工业做法会用 `TH_hi/TH_lo` 双阈值防止边缘抖动。
   本工程没做（单阈值），因为源是压缩视频、噪声不像摄像头那么大 —— 这是一个可以指出的改进点。
4. **它属于点运算** ⇒ 与旋转/缩放任意叠加都成立。

---

## 5. 反色：`~x` 也需要一个模块

```
out = {~R, ~G, ~B}   // 或灰度下 out = 255 − Y
```

看起来最没技术含量，但它在工程上有两个真实用途：
1. **验证数据通路是否逐位正确**（反色是最强的"位翻转探测器"，接错线一定看得见）；
2. 深色背景内容在 HDMI 上更省显示功耗（对 OLED 明显，对 LCD 不明显）。

## 6. 为什么"点运算与旋转兼容、窗滤不兼容"——画出来

旋转用**逆映射**：对屏幕上每个点 `(x,y)`，反算它在源图里的位置 `(sx,sy)`：

```
sx =  cx + ( (x−cx)·cosθ + (y−cy)·sinθ ) / scale
sy =  cy − ( −(x−cx)·sinθ + (y−cy)·cosθ ) / scale
```

现在考虑屏幕上一行连续取的 3 个点 `A=(x,y) B=(x+1,y) C=(x+2,y)`：

- **点运算**：只需要 `A`、`B`、`C` 各自的像素值 ⇒ 完全无关它们来自源图哪里 ✔
- **3×3 窗滤**：需要"以 A 为中心的 3×3 邻域"。
  如果这个邻域是在**源图坐标**里取的（θ≠0 时源图的上下左右 ≠ 屏幕的上下左右），
  那么"源图 3×3"投到屏幕上是一个**旋转过的斜方块**，
  而且相邻屏幕点的邻域互相不再重叠 ⇒ 行缓存复用关系被破坏，
  结果就是**滤波方向错、甚至花屏**。

第一版的处置是：`θ≠0` 时**强制关掉** blur/sobel（保功能正确性，牺牲组合能力）。
第二版的解法是：**把 3×3 窗口建在屏幕（目标域）扫描序上** ——
即"先逆映射拿到屏幕这一行这一列的像素值，再在屏幕数据流上做 3×3"。
这样邻域天然就是屏幕上的 3×3，与旋转角无关。

```
源像素(逆映射得到) → 点运算 → 目标域 3×3 → 右窗输出
```

代价是要在**屏幕坐标**上维护 2 行行缓存（512 像素 × 16 bit = 1 个 BRAM tile/行）。
被否掉的方案是"多路 BRAM 口同时取 9 个源像素"—— 7020 资源放不下（`PS_VS_PL.md` 里有这段对比）。

> 详见 [02_卷积与3x3窗口](02_卷积与行缓存_模糊与Sobel.md) 与
> [版本演进 · 第二版](../04_版本演进/02_问题与修复全记录.md)。
