# 02 · 卷积、3×3 窗口与行缓存：均值模糊和 Sobel 是怎么在硬件里成立的

> 这一篇讲"邻域运算"的硬件代价。理解了行缓存，就理解了本工程
> 为什么必须把窗口建在目标域，也理解了 BRAM 是怎么被一行一行吃掉的。

---

## 1. 卷积是什么

对图像 `I` 用一个 3×3 核 `K` 做卷积：

```
O(x,y) = Σ_{i=-1..1} Σ_{j=-1..1} K[i,j] · I(x+i, y+j)
```

两个最常用的例子：

| 用途 | 核 | 归一化 |
|------|----|--------|
| 均值模糊 | 全 1 的 3×3 | ÷9 |
| Sobel 水平梯度 Gx | `[[-1,0,1],[-2,0,2],[-1,0,1]]` | 无（取幅值） |
| Sobel 垂直梯度 Gy | `[[-1,-2,-1],[0,0,0],[1,2,1]]` | 无 |

**关键观察**：算 `O(x,y)` 需要 `I` 的 9 个点：`(x-1..x+1, y-1..y+1)`。
在硬件里，像素是**一行一行、从左到右**流过来的，所以当你拿到 `(x,y)` 时，
`(x, y-1)` 那一行的数据**早就流过去了**——你必须把它**存下来**。这就是行缓存。

## 2. 行缓存（line buffer）：3×3 窗口的标准结构

```
             ┌────────────── lb0（上一行，1 行宽）──────────────┐
 像素流 ──►  │                                                │──► 上一行像素
             └────────────────────────────────────────────────┘
             ┌────────────── lb1（再上一行，1 行宽）────────────┐
             │                                                │──► 再上一行像素
             └────────────────────────────────────────────────┘
   当前行像素（直接来自上游）                                      │
                                                                  ▼
                             p00 p01 p02   ← 第 y-2 行的 x-1,x,x+1
                             p10 p11 p12   ← 第 y-1 行
                             p20 p21 p22   ← 第 y   行   → 送进 9 个乘法/加法
```

实现细节：
- 每行 512 像素 × 16 bit = **8192 bit = 1 个 BRAM tile 用不完**（一个 RAMB36 是 36864 bit）；
  两行 `lb0/lb1` 合起来 16384 bit，可以塞进 1 个 tile 的两个 18 bit 口，或用 2 个 RAMB18。
- 还要**再存 2 个像素的横向移位寄存器**（`x-1`、`x-2`），才能同时拿到 `x-1,x,x+1`。
- 写地址 = 当前列号；读地址 = 同一个列号（因为上一行同一列正是我要的 `y-1` 位置）。
  ⇒ 一个"每拍读+每拍写"的简单 BRAM 就够。
- **行首行尾**（x=0 与 x=511）没有左/右邻域 ⇒ 要么复制边界、要么填 0、要么输出无效。
  本工程在缩放/旋转的 OOB 区填黑，窗滤边界按"复制/无效"处理（具体见模块详解）。

**这就是"目标域窗滤"为什么便宜**：窗口建在**屏幕扫描序**上，
每拍推进一个屏幕像素，行缓存天然连续 ⇒ 只需 2 个行缓存。
反之若窗口建在**源图坐标**上（旋转时），源图坐标不是单调推进的 ⇒
需要随机访问 9 个点，等价于要 9 个 BRAM 读口或者把整帧存下来 ⇒ 7020 放不下。

## 3. 均值模糊：除以 9 怎么算

```
O = (p00+p01+p02 + p10+p11+p12 + p20+p21+p22) / 9
```

9 不是 2 的幂，所以不能移位。三种硬件做法：

| 方法 | 式子 | 代价 | 误差 |
|------|------|------|------|
| 真除法器 | `/9` | 巨大（多拍、占 DSP） | 0 |
| **乘倒数** | `S·(512/9)/512 ≈ S·57 >> 9`（57=⌊512/9⌋） | 1 个乘法 + 移位 | 最大约 0.06·S/512，8 bit 下 ≤1 |
| 移位近似 | `S/8 = S>>3`（把 ÷9 当 ÷8） | 只移位，零成本 | 整体偏亮约 11% |

工程上常用 `>>3` 的"近似模糊"，因为**模糊本来就是一种视觉平滑，偏亮 11% 看不出来**，
而省掉一个乘法器很值。本工程用哪种、误差多大，见
[模块详解 · 效果链](../03_模块详解/05_效果链.md)（含 `proc_box_blur.v` 的确切算式）。

**另一个技巧：可分离滤波。** 3×3 均值 = 先横向 3 点平均、再纵向 3 点平均 ⇒
乘法次数从 9 降到 3+3。对高斯核收益更大。代价是要两级流水与额外缓存。

## 4. Sobel：边缘检测的完整硬件算式

```
Gx = (p02 + 2·p12 + p22) − (p00 + 2·p10 + p20)
Gy = (p20 + 2·p21 + 2·p22) − (p00 + 2·p01 + 2·p02)
```

注意 `2·p` 是**移位**，不是乘法 ⇒ **Sobel 全程不需要一个乘法器**，只要加/减与移位。
这是它能在小 FPGA 上跑的根本原因。

幅值：

| 定义 | 代价 | 特点 |
|------|------|------|
| `sqrt(Gx²+Gy²)` | 要开方，硬件不划算 | 精确 |
| **`|Gx| + |Gy|`** | 2 个加法 | 偏大约 10~40%，但**单调性一致**，做阈值判断完全够用 |
| `max + min/2` | 1 比较 + 1 移位 + 1 加 | 精度介于两者之间 |

本工程用哪种、以及有没有再套阈值（把幅值二值化成"边缘线"），见模块详解。
`|Gx|+|Gy|` 的范围是 0~4·255·… ⇒ **必须饱和到 8 bit 或 5 bit（RGB565）**，
不饱和就会"绕回"成黑色条纹，这是 Sobel 硬件实现最经典的花屏原因。

## 5. 流水与延迟：窗滤一定会引入几拍延迟

从"当前像素进来"到"它的 3×3 邻域齐了"，至少要等：
- 下一行第一个像素到来 ⇒ **一整行**（512 拍）之后才能算上一行的输出。

所以行缓存结构的固有性质是：**输出比输入滞后约 1 行**。
这带来两个必须处理的问题：

1. **帧首/帧尾**：第 0 行没有"上一行" ⇒ 用无效标志或复制边界；
2. **与旋转/缩放的对齐**：左右窗的数据流延迟不同 ⇒
   `split_display` 拼接时两路的 `de`（数据有效）必须对齐，
   否则右窗整体偏移一行。本工程 `pl_video_top` 里那一串
   `bar_l_d1/d2/d3/d4`、`de_d[2]` 之类的打拍就是在做这件事。

> 学习提示：读任何图像处理 RTL，第一件事是**数清每一级流水的延迟**，
> 第二件事是确认 `valid/de` 信号被打了同样多的拍。
> 图像错位、偏色带、边缘残影，九成是这里对不齐。

## 6. 为什么这些和"本工程的资源"直接相关

| 结构 | 资源 |
|------|------|
| 2 个行缓存（512×16bit） | 约 1 个 BRAM tile（本工程 `proc_box_blur` 的 `lb0/lb1` 显式写了 `ram_style="block"`） |
| 横向移位寄存器（2 像素） | 32 个 FF |
| 9 个加/减 + 移位 | 约 200~400 LUT |
| 若改成 5×5 | 行缓存 4 个、加法 24 个 ⇒ 资源翻倍 |

而本工程 `util_hier.rpt` 里 `u_pipe`（效果链）总共才 724 LUT（532 逻辑 + 192 作存储器）+ 2 个 RAMB18 ——
说明它用的是最省的 3×3 结构。**"效果链很轻"这个事实，是后面敢把资源腾给别的模块的前提。**
