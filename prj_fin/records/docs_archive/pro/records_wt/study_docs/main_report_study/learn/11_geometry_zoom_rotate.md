## 0. 先看整条通路长什么形状

一块板子上，几何只做四件事：**把画面缩小/放大、把画面转一个角度、取像素时做插值、
在原图与处理图之间画一条分界**。它们在 RTL 里的先后顺序是：

```
显示坐标 (x,y)  ──视口换算──▶  (cx, cy_r)     ← 每 1 个源像素画 2×2 个显示像素
     │                        pl_video_top.v:242-243（cx/cy）、:263-271（行号提前量）
     ▼
 zoom_mapper（逆映射：显示 → 源），内部例化 sin_rom / cos_rom
     │   输出 sx, sy, oob, frac_x, frac_y
     ▼                pl_video_top.v:298-304
 fb_bilin（一个读口 + 双线性 + 乒乓结果缓冲）──▶ 一个 16bit 像素 + 同级的 oob
     │                              pl_video_top.v:677-695
     ▼
 效果链 u_pipe（gamma/灰度/反色/模糊/锐化/边缘/二值化/形态学，见 10_effect_pipeline.md）
     │                              pl_video_top.v:745-755
     ▼
 split_display（原图 vs 处理图 + 那条蓝线 + oob 涂黑）  pl_video_top.v:856-873
        ▲
        ├ 原图那一抽头：pix_raw → 行环 raw_line_delay → orig_skid   :717、:733-737、:776-792
        └ seam_src（把"这条线在画面第几列"在源头算好，跟着内容推 18 拍） :847-854
```

旁支的控制逻辑：`zoom_ctrl`（八档倍率、呼吸、以及"此刻真的在用哪个 inv"的唯一出口）、

（`video_timing.v:68`）——下面好几个"只在帧首变"的规矩都钉在这根线上。

## 1. 逆映射：为什么是"倒着问"而不是"正着撒"

**是什么。** 逆映射 = 对**每一个显示像素**去问"你该涂哪一处的源图"，
而不是对每一个源像素去算"你该画到屏上哪里"。
代码里就是 `zoom_mapper.v:2` 那行注释："右屏无极缩放逆映射：屏幕 (x,y) → 源图 (sx,sy)"。

**为什么要。** 反过来做（正向散布，forward mapping）有两个致命问题，都是从硬件角度：

1. **空洞与重叠**。缩放与旋转都是"任意"映射：源像素 (3,7) 变换到屏上可能是 (2.4, 8.9)，
   取整之后有的屏格被两个源像素砸到（要仲裁谁赢），有的屏格一个源像素都没落到（要填空）。
   放大时是重叠，缩小时是空洞——0.25x 就是四个源像素挤进一个屏格。仲裁和填空都得要
   一片"这一格填了没有"的位图，在逐像素流水的视频通路里放不下，而且每帧得清一次。
2. **输出不连续**。显示扫描是**刚性**的：`video_timing` 每拍给出一个 (x,y)，
   你必须**当拍**给出一个像素，晚一拍就是花屏。逆映射天生满足这个契约：输入是扫描坐标，
   输出还是扫描坐标，一进一出、每拍一个。正向散布的输入是源像素顺序，输出要按屏顺序，
   两边对不上，只能中间放一个整帧的缓冲——而整帧缓冲在 512×300×2B 这一级就是又一枚帧缓存。

代价是逆映射会问出"画面外面"的源坐标——放大时采样窗收进画面内部不会越界，
但旋转（图角转出外框）和缩小（画面四周空出来）必然越界。于是多出一条纪律：
**越界的像素显示成黑色**。`oob` 在几何上是"这一格的源坐标不在 [0,IMG_W)×[0,IMG_H) 内"，
在时序上与像素同拍有效（这正是 §7 里 `fb_bilin` 把 `oob` 与像素写进同一个字的原因）。

**原理怎么推。** 记显示像素相对画面中心的偏移 `(xp, yp)`，缩放倍率 `s`，转角 `θ`：

```
逆旋转： sx' =  xp·cosθ + yp·sinθ
        sy' = -xp·sinθ + yp·cosθ
逆缩放： sx = sx'·(1/s) ， sy = sy'·(1/s)
```

`1/s` 在项目里叫 `inv_scale`，用 Q8 定点表示（§2）。RTL 里没有浮点也没有除法，
全部是"整数乘 + 定长右移"。注意这是**把显示格映回源格**的矩阵，也就是 R(−θ)：
`rotate_mapper.v:3` 把这条约定写成英文 "rotate by -angle (matches reference matlab)"，
于是按键增大角度时屏幕上是顺时针转。`zoom_mapper` 沿用了同一套式子（推断：两处乘法逐字相同），
但它自己没有这句注释。

**代码在哪几行。** `zoom_mapper` 的 s0 级就是"中心化 + 翻 Y"（`zoom_mapper.v:31-36`）：

```verilog
xp      <= $signed({1'b0, x_in}) - $signed(IMAGE_W / 2);
yp_math <= $signed(IMAGE_H / 2) - $signed({1'b0, y_in});
yp_disp <= $signed({1'b0, y_in}) - $signed(IMAGE_H / 2);
```

两个 yp 都要，因为屏幕坐标 y 向下、数学坐标 y 向上：纯缩放走 `yp_disp`（不翻，直接加回来），
带旋转走 `yp_math`（最后再翻回去，`src/rtl/process/zoom/zoom_mapper.v` 里那句
`sy_c = (IMAGE_H/2) - yr_pix - (rot_y_has_frac ? 1 : 0)`，多减的那一格与 §2 的小数是一对，
r94 之前没有这一项）。`rotate_en` 本身也被寄存成 `rot_s0`（`:35`）、再寄存成
`rot_s1`（`:45`），**跟着数据走**——它必须与像素同流水级，否则会出现"半帧按旋转算、半帧按不旋转算"。

**越界为什么必须是黑，而不是绕回、拉伸或不管。** 三处涂黑，都写着同一个字面量：

- `src/rtl/process/zoom/zoom_mapper.v` 末尾那个 `always`：`sx_c < 0 || sx_c >= IMAGE_W || sy_c < 0 || sy_c >= IMAGE_H`
  ⇒ 把 `x_out/y_out` 钉 0、`oob` 置 1、`frac` 清 0。**"钉 0"不是"不读"**：这一拍下游读的是
  源 (0,0) 那个真实地址，只是结果被 `oob` 挡掉（`rotate_mapper.v:55-58` 是同一段写法）。
  为什么要钉 0：地址必须永远合法，否则越界坐标直接进 BRAM 地址线，行为取决于地址位宽截断——
  那才是真正的不可控。
  ⚠ 两个"钉 0"不是一件事，别混：**这里钉的是越界那一拍的地址**（现行行为，是对的）；
  #104 那条"把小数钉成 0"钉的是**旋转支的分数位**，那是缺陷，r94 已修（见 §2 与 §7.9）。
- `split_display.v:49`：`wire [15:0] sel = oob ? 16'h0000 : (take_orig ? orig_pix : proc_pix);`
  ⇒ **`16'h0000` 在 RGB565 里就是纯黑**。顶层对原图那一路还有一份同样的：
  `pix_raw = oob_fb_d1 ? 16'h0000 : ...`（`pl_video_top.v:717`）。
- 为什么不"绕回"（把坐标取模）：绕回会读到**同一帧的另一行/另一列**，旋转时画面外沿会出现
  一条"另一侧内容"的错位带，看上去像撕裂，而且说不清画面到哪里结束。
  为什么不"复制边缘像素"（clamp）：那会在外沿拉出一条边缘拖影，一眼就脏。
  黑色是背景色，缩小后四周的空边本来就该是黑的，观感与语义一致；
  更重要的是它给 §9 那条蓝线提供了一个可用判据——`mark` 里带着 `!oob`（`seam_src.v:28`），
  所以"线只画在画面内"这一件事是免费的。

**你可以自己验证。** 板上：串口 `zoom 0.25`（`report/COMMANDS.md:113`）→ 屏上画面缩到中间，
**四周应是一圈纯黑**，黑边里不该有杂色、不该有另一侧的内容；`zoom 2` 是放大，采样窗收进画面内部，
四周**不该**有黑边——这一对期望写在 `board/README.md:177`（第 18 项的第 ③ 条）。
台架：`sim/tb_zoom_mapper.v` 逐点比 `x_out/y_out/oob`。

## 2. Q 格式：这个项目里所有"小数"的位为什么这么切

**是什么。** Q 格式 = 用整数表示小数的约定。`Q8` 表示"低 8 位是分数"，
也就是把真值乘以 256 存成整数：1.0 存成 256，0.5 存成 128，2.0 存成 512。
`cos_rom.v:2` 那行注释 "Auto-generated cos_rom: round(fn(angle_deg)*256), signed 10-bit"
说的就是这件事。

**为什么要。** FPGA 的 50 MHz 像素域里，浮点乘法的开销和延迟都不可接受；
定点乘法能直接映射到 DSP48，位宽可算、能提前判断会不会溢出。
本项目的几条硬规矩都建立在"数都是定点整数"上，其中最贵的一条教训是编号 #58：
在 100 MHz 域里放了一个组合除法器，WNS 直接打到 **−5.014 ns / 96 个失败端点**
（`report/log/ISSUES.md:1332`）。

**为什么这几个数各自是这个位宽**（这一栏是本节的重点，"位宽为什么这么切"是有理由的）：

| 量 | 位宽与格式 | 出处 | 为什么这么多 |
|---|---|---|---|
| `inv_scale` | 无符号 10 bit，Q8 | `zoom_mapper.v:10` | 上限就是 1023 ⇒ 最小倍率 0.25x（`zoom_ctrl.v:38-40` 为这一位宽专门讨论） |
| `sin_v/cos_v` | 有符号 10 bit，Q8 | `sin_rom.v:2`、`sin_rom.v:5` | 幅度最大 256（=1.0），10 bit 有符号到 ±511 ⇒ 放得下，取负不溢出（`zoom_fit.v:22` 就是靠这句论证） |
| `xp/yp` | 有符号 13 bit | `zoom_mapper.v:29` | 要覆盖 x 到 4095 的显示宽（`x_in` 是 12 bit），本几何只用 ±256 |
| `xr_m/yr_m` | 有符号 24 bit | `zoom_mapper.v:39` | 13+10 的乘积相加，最坏 256·(256+150) = 103936 ≪ 2^23 |
| `rot_xs` | 有符号 32 bit | `zoom_mapper.v:58` | Q8×Q8 = Q16；见下面那条截断 |
| `frac_x/frac_y` | 无符号 8 bit | `zoom_mapper.v:18-19` | 一个像素宽切 256 份 ⇒ 位置分辨率 1/256 ≈ 0.0039 像素，远在肉眼之上；8 bit 恰好是取整剩下的那个"余数字节"，不用额外算 |

**两个 Q8 相乘 → Q16，一个 Q8 乘纯整数 → Q8。** 所以 `zoom_mapper.v:63-66` 里
旋转分支 `>>> 16`、缩放分支 `>>> 8` 不是笔误：旋转分支的 `xr_m` 已经是 Q8（像素 × Q8 三角），
再乘 Q8 的 `inv` 就成了 Q16。四个积在 `:58-61`：旋转支 `rot_xs/rot_ys`（`xr_m * inv`）、
缩放支 `raw_xs/raw_ys`（`xp_s1 * inv`），`:57` 那一行的注释给这一级起了标题
（"s2: * inv_scale；inv>256 时边缘 OOB 填黑"）。

**那条截断要说清楚。** `rot_xs = xr_m * inv` 里 `xr_m` 是 24 bit、`inv` 是 11 bit（`:26` 把它
符号扩展成 `wire signed [10:0]`，因为 512 需要 11 bit 有符号才是正数），自定宽度是 35 bit，
而右边的线声明成 32 bit ⇒ **高 3 bit 被丢**。本几何下最大 |值| ≈ 103936×1023 ≈ 1.06×10^8 ≪ 2^31，
丢的三位恒是符号扩展，所以无害（这一段与 `report/study/03_模块详解/06_旋转与缩放.md` §1.4 的
综合实证是同一件事）。但它是"参数化不可信"清单上的一条：换更大分辨率 + 更大 `inv` 就会咬人。

**取整方向为什么用算术右移。** `>>>` 对负数是**向下取整（floor）**，而且
`raw = 256·(raw>>>8) + raw[7:0]`（低 8 位当无符号数）恒成立。
这两条合起来正好是双线性插值需要的形式：`x_out` 是源坐标的 floor（当左上角抽头 `p00`），
`frac_x = raw_xs[7:0]` 是**非负的**余数（当权重）。
如果改成"截断（向 0 取整）"，负半轴上 `frac` 就会指错方向。
`src/rtl/process/zoom/zoom_mapper.v` 的注释把这句话写在了代码旁边："floor 与 frac 必须自洽……
换成 `/256` + 取余就会在负数上错一格"，r94 之后那句还多了一句"旋转支同理，只是要取 `[15:8]`"。

**代码在哪。** `frac_x/frac_y` 的取值在 `src/rtl/process/zoom/zoom_mapper.v`（r94 之后的形状）：

```verilog
wire [7:0] rot_fx = rot_xs[15:8];   // 旋转支的小数 = `>>> 16` 之后 [15:8] 那 8 位
wire [7:0] rot_fy = rot_ys[15:8];
wire       rot_y_has_frac = (rot_fy != 8'd0);
wire signed [31:0] sy_c = rot_s1 ? ((IMAGE_H / 2) - yr_pix - (rot_y_has_frac ? 32'sd1 : 32'sd0))
                                  : (ys_pix + (IMAGE_H / 2));
wire [7:0] fx = rot_s1 ? rot_fx : raw_xs[7:0];
wire [7:0] fy = rot_s1 ? (~rot_fy + 8'd1) : raw_ys[7:0];  // 翻转之后小数也翻：256−f（f=0 按 8 位回绕成 0）
```

**改前这两行是缺陷，不是特性。** 旧写法是 `fx/fy = rot_s1 ? 8'h00 : raw_*`，也就是旋转支算完
`xr_m * inv`（Q16）之后只取 `>>> 16` 的整数部分、小数整个丢掉 ⇒ 分数位其实一直躺在 `rot_xs[15:8]` 里，
只是这一支没有取，于是角度非 0 时双线性拿不到权重、`bilin on` 在旋转态是**空头支票**（ISSUES #104，
**r94 已修**，账目在 `report/log/ISSUES.md` 的 #162 那一节，机理与判据见 §7.9）。
修法不是"把小数接上"这么轻：横向确实接近免费（整数平移不改变小数，`sx_c = xr_pix + W/2`，floor 就是 `xr_pix`），
**纵向那一次 `Y_disp = C − Y_math` 的翻转必须连着 floor 一起改**。记 `C = IMAGE_H/2`、
`Y_math = yr_pix + f/256`（`>>>` 朝 −∞ 取整 ⇒ `0 ≤ f < 256`），则

```
Y_disp = C − (yr_pix + f/256) = (C − yr_pix − 1) + (256 − f)/256     （f ≠ 0）
       = (C − yr_pix)         + 0/256                                （f = 0）
```

为什么必须退那一格：`f ≠ 0` 时 `C − yr_pix − f/256` 落在 `C − yr_pix − 1` 那一格**里面**（floor 是朝 −∞），
小数是剩下的那一截 `1 − f/256 = (256 − f)/256`。三件事是一套：**整数退一格 + 小数取 `256 − f` +
`f = 0` 保持原样**。只做"取补"、不减那一格，`x_out + frac/256` 拼回来的真值就整体偏高接近一格，
画面上是旋转态**沿角度方向的一条剪切**（上下各错一行），而且不报任何错——这正是它当初能挂很久的原因。

**你可以自己验证（不依赖仿真）。** 对着 `zoom_ctrl.v:38-47` 那张表手算三个数：
`inv=341` ⇒ 256/341 = 0.7507（档名 0.75x）、`inv=192` ⇒ 1.333（档名 1.33x）、
`inv=1023` ⇒ 0.2502（档名 0.25x，差 0.02 %）。再打开 `sin_rom.v` 的 `9'd45`（`:54`）= 181 ⇒
181/256 = 0.70703 vs 真值 0.70711 ⇒ 相对误差 1.1×10^-4。三个数都在 1 % 之内，
说明 Q8 这一刀切得够细，而"位宽不够"的怀疑应该往别处找。

## 3. 缩放：八档码 → 实际倍率，以及为什么不许现场做除法

**是什么。** 用户能点的八档倍率：0.25 / 0.33 / 0.50 / 0.75 / 1.00 / 1.33 / 1.50 / 2.00。
内部只有一个数：`inv_scale`，Q8 的**倒数**尺度，256 表示 1.0x。

**为什么要存倒数。** 逆映射天生需要的是 `1/s`：源坐标 = 显示偏移 × (1/s)。
如果存 `s`，每次都要在快域算 `256/s`——那正是一条运行时除法。
存倒数就把除法搬到了"设计时"：档位表是人写的常数，RTL 只做乘法。
`zoom_ctrl.v:2-4` 那三行就是这个约定的定义（"inv 越大 → 采样越散 → 画面越小"）。

**那张表在哪。** `zoom_ctrl.v:34-50` 是一个 Verilog `function`（纯常数、综合即展开），
八条 case 项在 `:38-47`：

| 档号 | 名称 | `inv_scale` | 位置 |
|---|---|---|---|
| 0 | 0.25x | **1023**（不是 1024） | `zoom_ctrl.v:38` |
| 1 | 0.33x | 776 | `:41` |
| 2 | 0.50x | 512 | `:42` |
| 3 | 0.75x | 341 | `:43` |
| 4 | 1.00x | 256 | `:44` |
| 5 | 1.33x | 192 | `:45` |
| 6 | 1.50x | 171 | `:46` |
| 7 | 2.00x | 128 | `:47`（`default` 那一支） |

`inv = round(256/s)` 逐项核对：s=0.75 → 341.33 → 341；s=1.33 → 192.5 → 192；
s=0.33 → 775.8 → 776。**为什么 0.25x 那一档写 1023 而不是 1024**：`inv_scale` 只有 10 bit，
1024 会回绕成 0 ⇒ 画面上变成"无限放大"而不是 0.25x。
这一格的注释（`:38-40`）明说它是"被 10 bit 的天花板钉住"的，1023 对应 0.2502x，与档名差 0.02 %。
上位机脚本也专门有一条反向判据钉住这件事：`src/host/health_read.mjs:188-190`
（"式子给 1024，硬件只能到 1023"）。

**屏上那一格 "ZOOM:0.75X" 是怎么来的。** 也不能除。做法是拿真正在用的 `inv`
与**相邻两档的中点**比大小，七个常数比较的优先级链在 `zoom_ctrl.v:60-67`：
`>=900→0档`、`>=644→1档`、`>=427→2档`、`>=299→3档`、`>=224→4档`、`>=182→5档`、`>=150→6档`、否则 7 档。
结果**寄存一拍**再给 OSD（`:79`，`zoom_code <= code_nxt`），所以 OSD 侧只多一个 3 bit 的 case 译码
（`osd_overlay.v:140-143`）。`:54-56` 把动机写得很直接：`scale = 256/inv` 那条运行时非 2 幂除法，
在快域里就是 #58 那个 −5.014 ns 的组合除法器。

`zoom_code` 只跟着**上一拍**的 `inv_scale`（`:77-78` 的注释：这一段不进 OSD 那条组合链），
而 OSD 那条链历史上是全设计最差路径的下游（`split_ctrl.v:116-121` 记着同一族的账：
端点值 → 百分比乘法 → OSD 拆位 → 字模 → 像素，28 级、含一个 DSP48）。

**还有一个容易看漏的点：分区比的是 `inv_used`，不是 `inv_scale`**（`zoom_ctrl.v:58`）：

```verilog
assign inv_used = fit_en ? inv_fit : inv_scale;
```

开"按角度拟合"（§4）时 `inv_scale` 还停在呼吸/手动的旧位置，拿它分区会出现
"屏上写 1.00x、画面上是 0.52x"——`:52-53` 那条 ⚠ 写的就是这个。
顶层一律读 `inv_used`，并且在 `pl_video_top.v:275` 那行声明旁边注着"本文件里'此刻真的在用哪个倍率'的**唯一**读数"。
为什么这个 mux 在 `zoom_ctrl` 内部做而不是顶层做：`:15-18` 解释了——这里已经是"倍率的唯一出处"，
顶层再 mux 一次就会出现两条说法（#52/#59/#66 那一族）。

**固件侧也有半张表。** `src/ps/main.c:173` 是 `ZOOM_X100[8] = {25,33,50,75,100,133,150,200}`，
`:174-175` 是它的名字。串口 `zoom 1.5` 靠 `zoom_step_near()`（`:523-533`）取最近档，
而 `:520-522` 明说这里**故意不再抄一份中点表**："少一张表就少一处会过期的地方；
平局往哪边靠由这张表决定"。于是"命令侧的档号"与"RTL 侧的最近档"这两套独立算法之间
必须成立一条不变量：`code(TBL[i]) == i`——`zoom_ctrl.v:30-31` 说这条不是巧合，是台架判据
（`sim/tb_v94_zoom_sel.v`，改哪边都会红）。

**"呼吸"是什么。** `enable=1 && manual=0` 时，`inv_scale` 每个帧首走 `STEP=2`，
在 `INV_LO=256`（1.0x）与 `INV_HI=512`（0.5x）之间往返，方向记在 `dir`
（参数 `zoom_ctrl.v:6-8`、逻辑 `:102-119`、到顶翻向 `:104-106`）。
一趟 (512−256)/2 = 128 帧，一来一回 256 帧 × 16.8 ms ≈ **4.3 秒**，
所以 `board/README.md:177` 让你"钉住之后几秒内就该看出它不动"。
两个防御性写法值得记：
- 手动档**也只在帧首换**（`:89-93`，条件里带了 `frame_start`）：否则一帧之内上半新一档、下半旧一档。
- 从手动（可能停在呼吸带外，比如 1023）切回自动时**不许瞬移**：
  `:95-101` 先朝带内一步步走。旧版写 `inv <= INV_HI`，于是 1023 一帧跳到 512，
  用户看到的就是"画面弹一下"——`:96-97` 记着这条改动的原因。

**`zoom_snap` 防的是什么现象。** 参数一致性 + 可观测：一帧之内的几何参数必须是同一个数，
而且"屏上写的倍率"必须等于"取数器在用的倍率"。`zoom_ctrl` 保证了帧首才换 inv，但还差一件事——
GPIO 回读 `zsel` 只能证明"PS 写了那一位"，证明不了 13 级同步链把它送到了像素域，
更证明不了据此算出的 `inv_scale` 是对的（`zoom_snap.v:3`）。
于是这个模块把因果链末端打包成一条 **19 位准静态总线**：

```verilog
wire [18:0] in_bus = {zman, zsel, zoom_code, zoom_active, zoom_dir, inv_scale};   // zoom_snap.v:22
```

两条不变量（`zoom_snap.v:4-7`，台架 `tb_v95_zoom_snap` 逐条判）：
① `bus` 只在帧首整拍换，换完至少保持一帧 ⇒ 这是"准静态总线"的前提，跨时钟域才允许整条总线一次换；
② `bus_tog` 每**一次真实变化**恰好翻一次，而且翻在总线已经稳定之后：
`dly` 移位 `:31`、第 8 拍发沿 `:36-37`，文件头 `:6` 算出 ≈318 ns。
**早一拍都不行**：那样发的是上一帧的值，目的域永久落后一档（`:6-7`）。
不变化时一个沿都不发（`:33` 的 `pend <= (in_bus != bus)`）。
19 位各自打两拍的反面教材写在 `pl_video_top.v:599`（"对照是'19 位各自打两拍 ⇒ 读到半新一半旧'（#52/#59）"）。

**RTL 接线。** 例化 `pl_video_top.v:281-289`（参数 `INV_LO=256 / INV_HI=512 / STEP=2` 在 `:281`），
拟合的两个口接在 `:285`，`.inv_used(inv_used)` 在 `:286`，`:300` 把它喂给 `zoom_mapper` 的
`.inv_scale()`。快照这一段：`:602-606` 把
`zman/zsel/zoom_code/zoom_active/zoom_dir/inv_used` 交给 `u_zsnap`，
`:622-626` 的 `snap_cross` 把 19 位跨到 axi 域（心跳 `z_hb_tog` 单起一个触发器，`:613-617`，
理由是 CDC-11，见 §6），`:633` 拼成回读字 `dbg_zoom`，位表写在 `:627-632`：
`bit31=像素时基活着 / bit19=zoom_fit / bit[18]=zman / [17:15]=zsel / [14:12]=zoom_code /
[11]=zoom_active / [10]=zoom_dir / [9:0]=inv_used`。
`bit19` 为什么必须有：`:631-632` 说"判据①在拟合模式下按构造就不成立"，没有它脚本会把一次正常拟合
读成档位错乱——那是"尺子先错"（#68），不是设计错。

**命令层的一个语义坑（会问到，值得记）。** `zoom 1` 与 `zoom 1.0` 不是一回事：
前者沿用 V7 的"开呼吸"开关语义，要 1.00 倍必须写带小数点的那一个。重叠已记
ISSUES #63（`report/log/ISSUES.md:1531`），固件的拒绝消息自己会说（`main.c:907-909`），
`report/COMMANDS.md:114-115` 也印了同一条。

**怎么验。**
- 串口：`zoom on|off`、`zoom 0.75`（八档取最近，`report/COMMANDS.md:112-113`）、`zoom auto` 交还呼吸。
- 屏上：`board/README.md:177` 那四件——钉住不动、`(Auto)` 后缀消失、`zoom 2` 四周**不该**有黑边、
  `zoom auto` 之后从当前倍数继续走不该"弹"。
- 机器侧：`node src/host/health_read.mjs` 读 lane23（§10 会给完整读法）。
- 台架：`tb_v94_zoom_sel`（八档逐档验 `code(TBL[i]) == i` + 手动↔自动交接不瞬移）、
  `tb_v95_zoom_snap`（上面那两条不变量）。

## 4. zoom_fit：转多少度就缩多少，让画面不缺角

**是什么。** `zoom fit 1` 打开后，倍率不再由档号决定，而由**当前角度**算出来，
使旋转后的外框刚好装进视口。用户的原始需求是原话，抄在 `zoom_fit.v:2`。

**为什么要它。** 45° 时方图的四个角会转出画面（被 `oob` 涂黑 = 缺角）。
要么容忍缺角，要么缩到刚好装下。后者是一个纯几何量。

**原理怎么推（这段要能自己算出来）。** 视口 = 图像未旋转时的外框 `IMAGE_W × IMAGE_H`，
`cx/cy` 就在这个框里量，1 源列 = 2 显示列（`zoom_fit.v:3`）。
图像以显示倍率 `s` 旋转 θ 之后的**轴对齐外框**是（`:4`）：

```
W' = s·(W·|cosθ| + H·|sinθ|)      H' = s·(W·|sinθ| + H·|cosθ|)
装得下 ⇔ W' ≤ W 且 H' ≤ H
      ⇒  inv ≥ (W·C + H·S)/W      inv ≥ (W·S + H·C)/H        （inv = 256/s，C=|cos|、S=|sin| 都是 Q8）
```

**为什么"对角线方向要缩"，而且缩得比直觉多。** 代进本工程的数（W=512、H=300）：
θ=45° 时 C=S=181/256=0.70703，两个式子的分子都是 `0.707·(512+300) = 574`，
于是宽度约束给 `s ≤ 512/574 = 0.892`，**高度约束给 `s ≤ 300/574 = 0.522`** ⇒ 取较大那个 inv，
也就是高度那一支赢（RTL 里就是 `:46` 的 `imax = (ix > iy) ? ix : iy`）。
这解释了 `board/README.md:189` 那句"45° 附近最小，约 0.52x"。
θ=90° 时 C=0、S=256：分子 `nx = 512·0 + 300·256 = 76800` ⇒ `ix = 76800/512 = 150`；
`ny = 512·256 + 300·0 = 131072` ⇒ `iy = 131072/300 ≈ 436`；`imax = 436` ⇒ `fit_raw = 439`
⇒ s = 256/439 ≈ 0.583，正好是"把长边 512 塞进 300 行"（300/512 = 0.586）再留一点余量。
0° 与 180° 给 `inv = 256`（不缩）。

**这里也没有除法器。** `/W` 与 `/H` 折成"乘一个 elaboration 常数 + 定长移位"
（`:26-28` 的论证、`:29-30` 的代码、`NSHIFT = 20` 在 `:11`）：

```verilog
localparam [NSHIFT-1:0] REC_W = ((1 << NSHIFT) + (IMAGE_W >> 1)) / IMAGE_W;   // :29
localparam [NSHIFT-1:0] REC_H = ((1 << NSHIFT) + (IMAGE_H >> 1)) / IMAGE_H;   // :30
```

`(2^20 + W/2)/W` 里的 `+W/2` 就是四舍五入；常数在综合前算完，RTL 里只剩常量乘 + 移位
（W=512 时 `REC_W = 2048` 恰好是 2 的幂，H=300 时 `REC_H = 3495` 不是）。
误差 ≤ 0.03 %，比 Q8 三角表本身 ±0.5 LSB 的量化误差还小（`:27`）。
位宽也算过：`nx_c = IMAGE_W*C + IMAGE_H*S ≤ (512+300)·256 = 207872 < 2^18` ⇒ 18 bit 够（`:32`）；
`ix = (nx * REC_W) >> NSHIFT` 声明成 `wire [31:0]`（`:44`），最坏 207872×3495 ≈ 7.3×10^8
落在 30 bit 里，右边那个 32 bit 截不到有效位。

**余量为什么加 `(imax>>8)+2`。** Q8 三角表每一项最多差 0.5 LSB ⇒ `inv` 最大差
`(W+H)/2/H ≈ 1.35`，取 `imax + (imax>>8) + 2` 稳过它；
而在 0°/90°（表是精确的）只多缩 `3/256 ≈ 1.2 %`——屏上 6 个源列，看不见（`:48-49`）。
代码在 `:50`，再夹到 10 bit 上限（`:51`），复位值 256 = 1.0x（`:58`）。
0° 这一档值得代一次数：`imax=256` ⇒ `fit_raw = 256+1+2 = 259` ⇒ s = 0.988，
屏上那一格仍念 1.00x（因为分区下限是 224，`src/rtl/process/zoom/zoom_ctrl.v` 的分区链）。
⚠ 这一版先前把它写成"0° 也在钳"，**是错的**：`angle_ctrl.v:18` 明写 `rotate_active = (angle != 0)`，
所以角度回到 0° 时 `rotate_en=0`，那一钳整个解除。真实形状是"**只要角度非 0 就在钳**"——
自动旋转每走 1° 也算，所以转起来的时候手动放大那三档一律被拉回 fit 那一档。
`zoom_fit` 自己的 ±0.5 LSB 表余量让最小角处的 fit 略大于 256，那是**拟合的口径**，不是钳制的边界。
代价的完整三条写在下面"旋转态的钳制"那一小节。

**为什么拍两拍而不是一拍组合。** `:34-38`：r60 实测 `angle → inv_fit` 一拍做完是 15 级、
含两个 DSP48，slack 只剩 +1.843 ns（全设计第三差）；而这条链的输入一帧才变一次
（自动旋转的步进钉在帧首），多一拍落在消隐里，屏上一个像素都看不见。
代价写得很明白：**拟合值现在晚两拍才跟上新角度**（`:38`、`:52-55`），
两拍落在消隐里；如果是手动按键在帧中换角度，也只有 2 列用旧倍率，属刚体平移级别。
`:54-55` 还解释了一个容易做错的写法：不能"角度变了才装载"，
那样在"角度没变、拟合刚被打开"那一支会留着旧值 ⇒ `zoom fit 1` 在 30° 按下去屏幕先不动。

**为什么它例化的三角表与画面上那张是同一张。** `zoom_fit.v:18-21` 例化 `sin_rom/cos_rom`，
与 `zoom_mapper.v:22-23` 是同一份表 ⇒ "装得下"判的就是那条链真正画出来的框，
而不是另一个近似的框。`zoom_fit.v:22-24` 只要绝对值，所以现写了两级组合取反：

```verilog
wire [9:0] C = cos_v[9] ? (~cos_v + 10'd1) : cos_v;
```

**RTL 接线。** `pl_video_top.v:278-280`（`.angle(angle)`、输出 `inv_fit`）进 `zoom_ctrl`，
mux 只有**一个**，在 `src/rtl/process/zoom/zoom_ctrl.v` 的 `inv_used` 那一个出口里（`fit_en` 那一支**不写**
`inv_scale`，所以关掉拟合时呼吸/手动从原位置接着走）。r94 起同一个出口还吃一个 `rotate_en`、吐一个
`rot_forced`（见下一小节），顶层只把 `rotate_active` 原样递进去、把 `rot_forced` 并进 OSD 的 `(Fit)`，
**不在顶层再 mux 一次**。

**怎么验。** 串口 `zoom fit 1`（`report/COMMANDS.md:135`）；屏上第三行 `Zoom:` 后缀变 `(Fit)`
（`src/rtl/video/osd_overlay.v` 里 `(Fit)` 与 `(Auto)` 互斥，理由写在那两行旁边；r94 起喂它的那一位是
`zoom_fit_en | rot_forced`，所以**旋转把倍率钳住时即使 `zoom fit 0` 也会亮 `(Fit)`**），
倍率数字跟着角度变，且**任何角度都不缺角**（`board/README.md:189` 的 ②③ 项）。
这里有一个"两个数都对"的坑，值得单独记：**屏上那一格念的是量化后的八档之一，几何算出来的是连续值**。
不依赖仿真的手算：拿 `sin_rom.v:54`（45°=181）与 `cos_rom.v:54`（45°=181）代上面两个式子 ⇒
`nx = ny = 181·812 = 146972` ⇒ `ix = 287`、`iy ≈ 489` ⇒ `imax = 489`、`fit_raw = 492` ⇒
真倍率 `256/492 = 0.520x`；而 `427 ≤ 492 < 644` 落在 2 档（`src/rtl/process/zoom/zoom_ctrl.v` 的分区链）⇒
**屏上画的是 `0.50X`，回读到的 `inv_used` 是 492** —— 这两个数同时成立才对，
只看到其中一个反而说明链路某一端断了。0° 那一档同理：真值 259（0.988x）、屏上 1.00x（4 档下限 224）。
机器侧：`node src/host/health_read.mjs` 的 lane23 里 `bit19` 就是 fit 旗标
（`health_read.mjs:91-94`）。台架：`sim/tb_v100_fit_rot.v` 把 360 个角度逐个量过"越界量 = 0"。

### 4.1 旋转态的钳制（#93，r94 已修）：不需要开 `zoom fit` 也生效

**现在的行为。** 只要旋转**真的在生效**，实际生效的倍率就被钳进 `zoom_fit` 算出来的那个 `inv_fit`：
`inv` 越大画面越小 ⇒ 取两者里**较大的 `inv`**（`rot_clamp = rotate_en && (inv_raw < inv_fit)`，
出口是 `src/rtl/process/zoom/zoom_ctrl.v` 的 `inv_used` 那**一个** mux）。
于是过去那一族"旋转到大角度 ⇒ 角点转出屏 ⇒ 对角宽彩条 + 左缘细线"（ISSUES #93，
`report/log/ISSUES.md` 里挂了很久的左缘分诊就是它）**现在不会再出现**，整幅永远在屏内。
注意这跟上面那节讲的 `zoom fit` 不是一回事：`fit` 是"用户选择让倍率跟着角度走"，
这一条是"旋转自己不许你把画面放大到画外"，**`zoom fit 0` 解不开它**（钳的是"旋转在不在生效"）。

**为什么钳在 `zoom_ctrl` 而不是在顶层再 mux 一次。** 顶层钳喂得到 mapper、lane23、`status`，
**唯独喂不到 `zoom_code`**——屏上 `Zoom:` 那一格是 `zoom_ctrl` 里拿 `inv_used` 分区寄存出来的。
结果就是"屏上写的与真正在用的不是一回事"（#52/#59/#66 那一族，`zoom_ctrl.v` 文件头自己立的规矩）。
所以 r94 的做法是给 `zoom_ctrl` 加一个输入 `rotate_en`、一个输出 `rot_forced`，钳在 `inv_used` 里做完，
顶层只做两件事：把 `rotate_active` 原样递进去，把 OSD 的 `(Fit)` 从 `zoom_fit_en` 改成
`zoom_fit_en | rot_forced`（`pl_video_top.v`）。四处——mapper、lane23、`status`、屏上档号——**同一个数**。

**三条代价（口径照写，不美化）。**
1. 旋转态**不提供放大**：手动 1.33x / 1.5x / 2.0x 三档在旋转时都被拉回 fit 那一档。
   用户那一档没有丢——`inv_scale` 保持原值，**关掉旋转立刻回去**（T8e/T8f 钉的就是这个形状）。
2. **0° 不钳**：`rotate_active = (angle != 0)` ⇒ 停在 0° 就是 1.00x 原样，`zoom fit 0` 也照常手动。
（原先这里写"0° 也在钳"，r94 复盘时按 RTL 更正——**读代码胜过读我的结论**。）
3. **`zoom fit 0` 解不开这一钳**：它钳的是"旋转在不在生效"，不是 fit 开关。
   旧讲稿里"不想要这样就先 `zoom fit 0` 再 `rot auto 1`"那句话已经不适用了（见 §10）。

**怎么验。** 台架 `sim/tb_v94_zoom_sel.v` 的 T8a~T8f：全绿见 `build/r94_rotfit_after.txt`；
把钳制关掉的变异对照恰好红在 T8b / T8c / T8e 三条（`build/r94_rotfit_mutation.txt`），
这三条共享同一个根因。T8a 是负对照（不旋转时一个字都不改），T8d 证明"缩小"这条路没被伤到。

## 5. 旋转：三角表、符号处理与流水

**是什么。** 角度是 `wire [8:0] angle`，0..359 的**整数度**（`angle_ctrl.v:15`），
`rotate_active = (angle != 0)`（`:18`）。顶层把它直接接成 mapper 的 `rotate_en`
（`pl_video_top.v:294` 的 `rot_on` → `:300`）。

**为什么只有有限档位。** 三个来源都在往同一个数上写（`angle_ctrl.v:39-44` 的优先级链：
按键 +1°、按键 −1°、自动按帧步进 `speed`），而真正决定"能不能连续"的是**表**：
`sin_rom/cos_rom` 是自动生成的 `case (angle)` 全表（`sin_rom.v:7-8`），1 度一格，360 格。
要做任意角度连续就得换 CORDIC 或多项式近似，那是一条大得多的链；
而 1° 步进在 512 宽的画面上转一圈 360 步，肉眼已经是平滑的。

**ROM 里存的到底是什么。** `round(sin(θ)·256)` / `round(cos(θ)·256)`，**signed 10 bit**
（`sin_rom.v:2`、`cos_rom.v:2`）。这一轮我从两份文件里逐条读出来的刻度：

| angle | sin | cos | 期望 ×256 |
|---|---|---|---|
| 0° | 0（`sin_rom.v:9`） | 256（`cos_rom.v:9`） | 0 / 256 |
| 30° | 128（`sin_rom.v:39`） | 222（`cos_rom.v:39`） | 128 / 221.7 |
| 45° | 181（`sin_rom.v:54`） | 181（`cos_rom.v:54`） | 181.02 / 181.02 |
| 60° | 222（`sin_rom.v:69`） | 128（`cos_rom.v:69`） | 221.7 / 128 |
| 90° | 256（`sin_rom.v:99`） | 0（`cos_rom.v:99`） | 256 / 0 |
| 180° | 0（`sin_rom.v:189`） | −256（`cos_rom.v:189`） | 0 / −256 |
| 270° | −256（`sin_rom.v:279`） | 0（`cos_rom.v:279`） | −256 / 0 |
| 330° | −128（`sin_rom.v:339`） | 222（`cos_rom.v:339`） | −128 / 221.7 |
| 359° | −4（`sin_rom.v:368`） | 256 | −4.45 / 255.96 |

两个细节：① 0/90/180/270 存的是 **±256 而不是 ±255** ⇒ 1.0 精确，这一条是 §4 那套
"整数角度不额外缩"能成立的前提；② 87°..93° 这七格**全存成 256**（`sin_rom.v:96-102`，
下一格 94° 才回落到 255，见 `:103`），因为 `sin(88°)·256 = 255.84` 四舍五入就是 256 ——
这不是 bug，10 bit 有符号到 ±511 放得下（`zoom_fit.v:22` 就是靠这句论证"|·| 用 10 bit 无符号放得下"）。

**是组合查表，不是 BRAM。** `always @(*) case` + `default`（`sin_rom.v:7-8`、`sin_rom.v:369`、
`cos_rom.v:369` 都是 `10'sd0`）⇒ **0 拍延迟**，代价是它在综合里落进 LUT/分布式 RAM 而不是 BRAM。
`angle` 是 9 bit、全 512 个取值里只列举了 360 个，`default` 是防 X / 防综合保险的分支。
这里有一个值得记的隐患（`report/study/03_模块详解/06_旋转与缩放.md` §1.3 提过）：
`cos_rom` 的 `default = 0` 与"0° 应该是 256"不一致 ⇒ 万一 `angle ≥ 360`（今天由 `angle_ctrl`
的回绕保证不会出现），sin=cos=0 会把所有点塌到源图中心。恒等性只由 `case (9'd0)` 那一行保证。

**象限折叠：讲了这么多对称，但要说清楚"本仓库没有真的折叠"。**
三角函数在四个象限里只差符号与 sin/cos 互换：`cos(θ)=cos(360−θ)`、`cos(180−θ)=−cos(θ)`、
`cos(90−θ)=sin(θ)`。数据里看得见这个对称：`cos 30° = 222`（`cos_rom.v:39`）与
`cos 330° = 222`（`:339`）同值，`cos 150° = −222`（`:159`）只是符号相反；
`sin 30° = 128`（`sin_rom.v:39`）与 `cos 60° = 128`（`cos_rom.v:69`）互为移位。
**但落盘的这两份文件就是完整的 360 格 `case`，各 372 行、`grep -c "^            9'd"` 各得 360。**
折叠是"生成脚本层面可以压但没压"的余地：满表 360×10 bit ≈ 3.6 Kb，
LUTRAM 或 BRAM 都装得下，换来的是快域里**不需要**"象限判断 + 取反 + sin/cos 交换"那三级组合逻辑
（50 MHz 的 20 ns 里不难，但如果这条链进 4 ns 预算就很贵）。生成脚本我这一轮没找到
（`grep -rln "cos_rom" --include=*.py --include=*.m --include=*.js --include=*.mjs --include=*.tcl`
只命中一个 Vivado 自动生成的 run 脚本），所以"当初为什么没压"只能停在推测。
真正把"取绝对值 + 象限"技巧用起来的只有 `zoom_fit.v:22-24`。

**旋转矩阵的定点形式。** 见 `zoom_mapper.v:47-50`（与 `rotate_mapper.v:33-36` 同一份式子）：

```verilog
xr_m <= $signed({{11{xp[12]}}, xp}) * cos_v + $signed({{11{yp_math[12]}}, yp_math}) * sin_v;
yr_m <= -($signed({{11{xp[12]}}, xp}) * sin_v) + $signed({{11{yp_math[12]}}, yp_math}) * cos_v;
```

符号处理有三处，每一处都能出错：
1. **操作数要手工符号扩展**。`xp` 是 `reg signed [12:0]`，但 Verilog 里 `xp * cos_v` 若有一侧
   被当无符号就整个式子变无符号 ⇒ 负坐标会被当成几百万的大数。代码写成
   `{{11{xp[12]}}, xp}` 把 13 bit 拓到 24 bit（`:47`），`$signed()` 强制按有符号乘。
2. **反对称项的负号在乘积之后取**：`-(xp*sin_v)`（`:49`）而不是 `(-xp)*sin_v`。
   两者在纯数学上等价，在定点上不等价——先取负会多一次 24 bit 取反的进位链。
3. **y 方向最后要再翻回来**：`sy_c = (IMAGE_H/2) - yr_pix`（`:70`）。
   这个"减"字是 §7.9 那条缺陷修起来不是一行改动的原因。

**流水级数与"乘法必须寄存"。** 声明是 `reg signed [23:0] xr_m, yr_m`（`:39`），在 s1 打成寄存器
（`:42-55`），`:3` 明说"3 级流水"；`rotate_mapper.v:4` 更早的那句
"Multiplies registered in 2 stages for timing at 75 MHz"说的是同一件事：
**乘法器输出不许直接进下一级加法**，否则快域一定判红。
`rot_s0`（`:35`）/`rot_s1`（`:45`）保证 s1/s2 用的是与数据同拍的旋转旗标。

**纯缩放为什么不需要 ROM。** 非旋转分支走 `raw_xs = xp_s1 * inv` + `>>> 8`（`:60`、`:65`）。
两条分支在 s2 末尾用 `rot_s1 ? ... : ...` 合并（`:68-71`）——同一个模块一次流水同时做旋转和缩放，
所以 `zoom fit` 那种"缩放由角度定"能成立。RTL 的实际顺序是**先旋转再缩放**
（`xr_m * inv` 再 `>>>16`）；对"同一中心的等比缩放 + 旋转"两者可交换，所以结果与顺序无关
（推断，`06_旋转与缩放.md` §3.1 也是这个结论）。

**怎么验。** 串口：KEY1 短按 +1°、KEY2 −1°（`angle_ctrl.v:2`；注意短按是在**松手**时发的，
`pl_video_top.v:140-146` 与 `:181`，理由记在 ISSUES #55），`rot auto 1` 开自动、
`rot speed 3` 每帧 3°（`report/COMMANDS.md:136`），`rot show` 念状态。
⚠ **没有"设成某个绝对角度"的命令**，这是有意不做的（`report/COMMANDS.md:179-181`），
要把画面停在 30° 只能按 KEY1 数着按 30 次。屏上现象（`board/README.md:189`）：
转的时候四个角**不该被切掉**；如果出现"一瞬间画面弹一下"，先查角度是不是只在帧边界变（§6）。

## 6. 角度为什么必须钉在帧边界：`angle_ctrl` 的两条纪律

**是什么。** `angle_ctrl` 吃两个时基：`clk = sys_clk`（50 MHz 输入时钟，
`pl_video_top.v:180`）和来自像素域的 `frame_tgl`（发射触发器在 `:231-234`，用 `clk_pix`）。
`sys_clk` 与 `clk_pix` 出自同一个 MMCM、同为 50 MHz（`clk_gen.v:17`、`:20`），
约束把它们放进**同一组**（`src/constraints/clock_groups_impl.xdc:13-17`、`:28-31`），
组内路径照做时序分析——所以这不是"未检查的异步 CDC"。但 `frame_tgl` 仍被当真实跨域处理，
`angle_ctrl.v:20-23` 给的理由是"脉冲换了时钟域就得按跨域规矩来"，这个保守写法是免费的。

**为什么要钉在帧边界。** `angle` 是两张三角表的**索引**，而 `zoom_mapper` 逐像素组合地吃它
（`zoom_mapper.v:11`、`:22-23`）。帧中间换角度 = 这一帧上半与下半用两个不同的角 ⇒
画面在换的那一行错开一下。以前只有按键会改角度（人手一次几毫秒），所以从没暴露；
自动模式每帧都要换，就必须钉在消隐里（`angle_ctrl.v:4-6` 整段就是这件事）。

**原理：跨域传"事件"一律用翻转位。** 1 拍的脉冲会被目的域的采样整个吃掉
（`angle_ctrl.v:20`，编号 #36）。接收侧三级同步 + 异或出沿（`:24-29`）：

```verilog
(* ASYNC_REG = "TRUE" *) reg [2:0] fs_s;
fs_s <= {fs_s[1:0], frame_tgl};
wire fs_edge = fs_s[1] ^ fs_s[2];    // 每次帧首恰好一拍（sys_clk 域）
```

`ASYNC_REG` 是让综合把这两级放在**同一个** SLICE 里、缩短亚稳态恢复时间的属性。
"谁拥有时基谁负责同步"——所以顶层不许再自己采一遍（`angle_ctrl.v:21-22`）。
而且这个翻转位必须**单起一个发射触发器**，不能共用现成的 `sof_tgl`/`z_hb_tog`：
同一个翻转触发器扇出到两组目的域同步器，会被 cdc.rpt 判 **CDC-11 Critical**
（`angle_ctrl.v:22-23`；顶层那一段的复述在 `pl_video_top.v:229-230`，
另一处同一个坑的记账在 `:609-611`；本项目为它红过两次：#65、r54 构建 #34）。

**取模为什么用"减 360"而不是"到 359 就回 0"。** 每帧最多走 7°，`360 = 7·51 + 3`，
所以 `up = angle + speed` 之后统一 `(up >= 360) ? up - 360 : up`（`:31-34`）。
如果是"到 359 就归 0 再加"，每圈会在回绕处丢几度，转速快的时候肉眼看得出那一顿（`:31-32`）。
`up` 用 10 bit（`:33`）：最大 359+7 = 366，9 bit 装不下。
按键那两支还是"到顶回 0"的写法（`:40`、`:42`），因为一次只走 1°，不丢步。

**怎么验。** 板上只看一件事：`rot speed 1` 与 `rot speed 5` 的差别**只有转速**，
不该出现"快的时候某一行抖一下"（`board/README.md:189` 第 ① 项 + 报法那一段）。
台架 `tb_v100_fit_rot`。

## 7. 双线性插值：邻域怎么取、两次 lerp 的位宽、一个读口怎么分时

### 7.1 是什么 / 为什么要

逆映射算出来的源坐标是**小数**（§2）。最省事的做法是"最近邻"：小数直接丢掉、只取那一个像素。
放大时斜边就会一格一格（台阶/锯齿），旋转时边缘呈锯齿状。
双线性插值 = 取源坐标**周围 4 个整数像素**，按小数距离加权平均：

```
p = (1−fy)(1−fx)·p00 + (1−fy)fx·p10 + fy(1−fx)·p01 + fy·fx·p11
    p00=(sx,sy)   p10=(sx+1,sy)   p01=(sx,sy+1)   p11=(sx+1,sy+1)
```

端口名字就是这四个坐标（`bilin_lerp.v:11-14`）。实现上把它**拆成两次一维插值**（先横后纵），
因为硬件上一次做四个乘法比做两个贵得多（`bilin_lerp.v:3` 那句"两级流水：横向一次、纵向一次"）：

```
横向： t_top = (256−fx)·p00 + fx·p10        t_bot = (256−fx)·p01 + fx·p11
纵向： out   = [(256−fy)·t_top + fy·t_bot + 32768] >> 16
```

**为什么"必须读两行"。** 软件模型先量过再动手（`report/study/03_模块详解/10_双线性插值与分时读口.md` §一）：
旋转态下横向补上 ≈ +20 %、纵向补上 ≈ +20 %、两个都补 ≈ +40 % ⇒ **只做一半等于没做**。
这条结论在 RTL 里以注释的形式活着，见 `tap_sched.v:19`：
"旋转态的插值增益横向、纵向各约 20 % ⇒ 必须读源图两行"。

**`frac` 有几位？** 8 位：`bilin_lerp.v:15-16` 的 `fx/fy`，来源是 `zoom_mapper.v:18-19` 的
`frac_x/frac_y`。8 位 = 把一个像素宽切成 256 份，而且这 8 位就是 §2 里那个"余数字节"，不用额外算。

### 7.2 为什么权重之和恒为 256，于是**不需要饱和**

`wx0 = 9'd256 - {1'b0, fx}`、`wx1 = {1'b0, fx}`（`bilin_lerp.v:29-30`），两式相加严格等于 256 ——
与 `fx` 是多少无关。这是整个位宽论证的支点：

- 横向：通道值最大 255，`255·wx0 + 255·wx1 = 255·256 = 65280` ⇒ **17 bit 封顶**
  （声明 `reg [16:0] tr, tg, tb`，`:31-32`；赋值在 `:39-44`）。
- 纵向：`65280·256 + 32768 = 16,744,448 < 2^25` ⇒ 25 bit 数学上就够，
  代码声明成 `wire [25:0] or_r`（`:53`），多出的那一位是给 `+32768` 的进位留的，不是需要。
- 因为恒不等式成立，`>>16` 之后必然 ≤ 255 ⇒ **不用夹取**（`:57` 那句注释）。
  这条不是"看起来没溢出"，是被台架强制检验的：判据 2「四角同色 ⇒ 输出恒等」
  （`bilin_lerp.v:6-7` 把它写在精度决定里，`sim/tb_bilin_lerp.v` 判）。

顺带一条与本项目相关的写法细节：`:37` 只复位 `v0` 这一个 valid，数据寄存器不带异步复位——
因为数据寄存器带异步复位会挡住它们被打进 DSP48 的流水级（这条在 r80 的 methodology 报告里
对应全部 129 条 DPIR-1，见 `report/log/OVERNIGHT_LOG.md:5608-5610`）。

### 7.3 为什么只舍入一次，而且是 +32768

两级如果各自 `>>8` 舍入，误差是两次 ±0.5 LSB 叠加，还会引入"暗 1 个 LSB"的偏置。
这里改成纵向合并后一次性 `+2^15` 再 `>>16`（`:6-7` 那句"③"、`:53-55` 的 `+ 26'd32768`）——
`32768` 正是 Q16 的半个量程，所以 `>>16` 前加它就是四舍五入。
回包时**截断**而不是再舍一次：`{vr[7:3], vg[7:2], vb[7:3]}`（`:67`），
因为已经是 5/6/5 位宽的 RGB565 了，第二次舍入没有意义。
`:58` 还留了一句 Verilog 语法坑：不能写 `or_r[24:16][7:3]`（Verilog-2001 不许对位选结果再位选），
所以先取名 `vr`（`:59-61`）再切。

### 7.4 为什么 RGB565 → 8 bit 用**位复制**而不是左移补零

`:4-5` 讲得很清楚，写法在 `:20-21`：

```verilog
function [7:0] rep5; input [4:0] v; begin rep5 = {v, v[2:0]}; end endfunction
function [7:0] rep6; input [5:0] v; begin rep6 = {v, v[1:0]}; end endfunction
```

把高位**复制**到低位：5 bit 全 1 展开正好 `11111 111` = 255 ⇒ 纯白插值完还是纯白。
左移补零的话 5 bit 全 1 = `0x1F` → `0xF8` = 248，白色会变灰，而且插值结果整体偏暗。
`split_display.v:67-69` 输出到面板时用的是同一招（`{r5, r5[4:2]}`）。

### 7.5 邻域怎么取：帧缓存只有一个读口

**物理形状**：帧缓存按 64 bit 字存，一个字里 4 个 RGB565 像素
（`frame_buffer_w64.v:2`，`wr_data = {p3,p2,p1,p0}` 在 `:15`），
所以一次读能拿到 4 个**横向相邻**的像素。抽头地址（`fb_bilin.v:42-45`）：

```
pxl   = sy·IMG_W + sx           （像素下标）      :42
w_a   = pxl[18:2]               （字号）          :43
lane  = pxl[1:0]                （字内车道）      :44
w_b   = w_a + ROW_WORDS         （下一行同列）    :45，ROW_WORDS = IMG_W/4 = 128，:34
```

右邻是"同一行 +1 像素"：**多数情况**是同字换车道（`pick(w_a, lane+1)`，`fb_bilin.v:140-141`），
`lane==3` 时落到**下一个字** `A+1`。这就是"为什么要读两行"的直接答案：
横向邻居在同一个字里（几乎免费），纵向邻居在**下一行**，一个 64 bit 字给不了两行 ⇒
至少要读 A/B 两行，必要时各带 +1，共 4 个字。

**为什么不能开第二个读口。** 这不是"少写一行代码"的取舍，是量出来的：
在同一组 BRAM 阵列上再加一个逻辑读口，实测把帧缓存从 **80 块 RAMB36 顶到 160 块，
而 xc7z020 全片才 140 块**——这句在仓库里落了四处，措辞一致：
`tap_sched.v:10`、`fb_bilin.v:180`、`pl_video_top.v:723`、
`report/study/03_模块详解/10_双线性插值与分时读口.md:30`。
而那 80 块本身也是省出来的：帧缓存若声明成一个 38400 深的数组，BRAM 推断会把非 2 的幂深度
向上填充到 2^16，实测吃掉 128 块；拆成 32768 + 8192 两块之后是 80 块
（`frame_buffer_w64.v:4-7`；那里提到的对照实验件 `tmp_ramtest/fbtest.v` **今天已经不在树里**，
`ls tmp_ramtest` 无输出 ⇒ 这两个数只能当"注释里的实测"读，要复核得重做实验）。
⇒ **任何"多取一个点"的想法都必须先回答"从哪个读口/哪一拍里挤"**，这是 §7.6/§7.7 的全部动机。

### 7.6 上一代方案 `fb_rd5x` + `tap_sched`：一个像素周期塞 5 次读

（这一节我这次逐行读过，旧稿那些"只数过行数"的说法已经全部替换掉。）

**思路**（`fb_rd5x.v:2-3`、`tap_sched.v:2-4`）：50 MHz 像素时钟 + 同源 250 MHz 5 倍时钟
（`clk_gen.v:20` 的 CLKOUT0=50 M、`:23` 的 CLKOUT1=250 M），一个像素周期里发 **5 次读** =
右窗 4 个抽头（A / A+1 / B / B+1）+ 左窗 1 个字，恰好占满 5 个槽 ⇒ **不新增任何 BRAM**
（`tap_sched.v:9`）。产出与旧的 `fb_rd` 用法形状相同的 16 bit 像素总线，
只是延迟从 2 拍变成 **LAT=5**（`fb_rd5x.v:3`）。

**跨域纪律**（`fb_rd5x.v:6-8`、`tap_sched.v:43-47`，是 build#14 用一次红色门禁换来的）：
1. `clk_pix` 与 `clk_pix5x` 同相 ⇒ 慢域触发器输出**最早**只能被下一个快沿采走，
   所以跨进快域那一拍只有 **4 ns** 预算，不是 20 ns（`tap_sched.v:43-44`）。
2. 所有**地址算术留慢域**（`fb_rd5x.v:39-40`、`tap_sched.v:45-46`）：四个抽头字号 + 左窗字号
   全部在慢域算完各打一拍（`fb_rd5x.v:67-79`），快域只做一次 5 选 1 mux（`tap_sched.v:70-74`）。
   build#14 把 `base+ROWW` 这类加法放快域，实测要 5.3 ns ⇒ **WNS −1.277、1400 个失败端点**。
3. 快域→慢域最坏有 16 ns，所以抽头与左窗字都在快域先落一次触发器再交给慢域
   （`fb_rd5x.v:6`、`tap_sched.v:133-139`）。
4. 插值的 12 个乘法留在慢域（`bilin_lerp` 两级流水），快域 4 ns 塞不下（`fb_rd5x.v:7-8`）。

**槽位表**（`tap_sched.v:64-69` 那段注释，mux 在 `:70-74`）：
`s0` 发左窗字、`s1` 发 A、`s2` 发 A+1、`s3` 发 B、`s4` 发 B+1；
下一个周期的 `s0'` 落 B+1 并推进属性（`:115-131`），`s1'` 一次拍出四个抽头 + `ofx/ofy` + `vld`
（`:142-150`）。两个容易漏的细节：
- 左窗的**字与车道必须同一个沿采**（`:106-112`，注释原文"必须成对：分开采会'字对车道错'，
  板上现象是整列颜色对、左右偏一格，而且不会报错"）。字号里被丢掉的低 2 位就是车道。
- `vld` 要跟着"真被采纳过的请求"走（`acc1/acc2`，`:54-56` 声明与理由、`:128-129` 推进、
  `:149` 发 `vld <= acc2`）：抽头每拍都照原样寄存器一次，灌水的头两拍装的是复位值，
  少了这级跟随，台架第一次 `vld` 就会把期望队列整体挪一格——辨识度极高：**每条 got 都等于上一条 exp**。
- 右邻取不到时落到下一个字：`p10 <= (lane_w == 2'd3) ? w_a1[15:0] : pick(w_a, lane_w+1)`（`:144`，
  `p11` 同理在 `:146`）。

**左右两路的补齐**：左路本来就比右路快 2 拍（它只要一次读，右路要 4 次读 + 2 级插值），
`fb_rd5x.v:130-146` 用 `left_p0/p1/p2` 三级把左路也拖到同一拍——两条路不同拍的话，
切换窗口的瞬间画面会左右错开。总延迟 **LAT=5 由 `sim/tb_fb_rd5x.v` 用"唯一平移量搜索"量出来**，
不是纸上推的（`fb_rd5x.v:8`；做法与它逼出的两处历史 1 像素错位见
`10_双线性插值与分时读口.md` §四）。

**为什么这条路被换掉。** 快域那 4 ns 里布线就吃掉一大半：三次红都红在同一段
`mux→RAMB36 地址脚`上，实测 3.844 ns 的数据路径里**纯布线就要 3.255 ns（84.7 %）**，
而那里只剩 2 级 LUT——"再怎么优化 RTL 都动不了那 3.255 ns"。
这一整段账在 `report/log/ISSUES.md:2582-2584`（#76 段二，`build#14/15/16 = −1.277 / −0.485 / −0.327`
也在那一节与 `report/log/OVERNIGHT_LOG.md:725`），换掉它的推理链第一步就写在
`report/log/ISSUES.md:2586`：新几何下"每像素周期必须 5 次读"这个前提已经不成立
（一个源像素本来就有 4 个慢拍可用），于是 `fb_bilin` 全程留在 50 MHz（`fb_bilin.v:4`、`:11`）。

### 7.7 现行方案 `fb_bilin`：把那 4 拍天生冗余用满

**关键观察**（`fb_bilin.v:4-5`）：r59b 之后整屏只有一个视口，`cx = x>>1`、
`cy = (y>>1)` 夹紧（顶层 `pl_video_top.v:242-243`）⇒ **同一个源像素要显示 2 列 × 2 行 = 4 个
50 MHz 拍**，而双线性需要的正好是那 4 个字 A / A+1 / B / B+1。
于是读口挂回 `clk_pix`（`fb_bilin.v:11` 那句"读口挂在这里，没有第二个时钟域"），
一个 20 ns 预算里做"选行 + 末列 +1 + 4 选 1"，**快域一次都不出现**（`fb_bilin.v:4`）。

**四拍怎么用**（`:37-38`）：`col0 = ~x[0]`、`row0 = ~y[0]` 是一对显示列/行的**第一**拍，

| `(row0,col0)` | 这一拍发的字 |
|---|---|
| (1,1) | A |
| (1,0) | A+1 |
| (0,1) | B |
| (0,0) | B+1 |

地址选择就一行：`addr_nxt = (row0 ? w_a : w_b) + (col0 ? 17'd0 : 17'd1)`（`:56`），
`:55` 说明了为什么是"先选行再选列"而不是四个候选字：两个 17 bit 加器串在一级 mux 之后更短。
`addr_q` 在 `:58-62`，`frame_buffer_w64` 例化在 `:65-68`。

**读口延迟**：BRAM 读延迟 1 拍（`frame_buffer_w64.v:3`）+ 这里地址先打一拍 = **请求到数据 2 拍**
（`fb_bilin.v:39-40`），与旧的 `rd_addr_q + BRAM` 逐位同深 ⇒ 顶层 `MIX_D = 3 + 1 + 1 + LATENCY`
一个字不改（`:40`、顶层 `pl_video_top.v:309` 与 `:666-668`）。

**四个相位与两个 hold**：数据到达那拍用延了两拍的请求相位判它属于 A/A+1/B/B+1
（`:119-123` 的 `ph_a0/ph_a1/ph_b0/ph_b1`，`vld` 也在这四个里），
A 行存 `a_hold`、B 行存 `b_hold`（`:125-132`）。

**凑齐四元组的两块 RAM**：
- **抽头暂存** `tap_hold`：`512×32`，`(* ram_style = "block" *)`（`:142`）。
  y0 行两拍凑出 `{p10,p00}` 写入（`:153`），y0+1 行按 `j_d1` 读回（`:152`）——
  写只在 y0 行、读只用在 y0+1 行 ⇒ 同拍同地址不会相撞（`:151`）。
  ⚠ **索引必须是"显示列对号" `jd = x[9:1]`，不能是源列 `sx`**（`:136-138` 这一整段是本模块的重点）：
  按 `sx` 索引等于默认"源列沿显示行走至少单调 +1"，而旋转时一条源图线在 x 方向会**停滞甚至倒退**，
  同一个 `sx` 会在这一行里被**另一个源行**重写 ⇒ y1 拍读到别的像素的抽头 ⇒ **满屏噪点**
  （2026-09-26 用户报出来的，`r63` 原实现就是这么写的；顶层的接法在 `pl_video_top.v:692`，
  那两行注释复述了同一条）。而且这个错与 `bilin_en` 无关：`off` 时 `p00` 也来自这块 RAM
  （`:138` 最后一句）。
  还有一条综合坑写在 `:145-148`：这两块 RAM 的 always 块**不能带异步复位**，
  否则综合报 `ERROR: [Synth 8-91] ambiguous clock in event control` 整个模块作废，
  而 xsim 完全看不出来。
- **结果缓冲** `res`：`1024×17` 乒乓（`:184`），半号 = `pair_odd = y[1]`（端口 `:27`），
  写"本对"（`:188`）、读"上一对"（`:191`）⇒ 同一个 `j` 永远落在不同半 ⇒ 单口够用（`:179`）。
  17 bit = `{oob, 16bit 像素}` ⇒ oob 与像素**同一次写、同一拍读出**，天生同级（`:188`、`:197-198`；
  这一条就是 §8 说的"标签与内容同级"在读口内部的实现）。
  深度必须留成 2 的幂，非 2 幂会被推断向上填充（`:181`，与 `frame_buffer_w64.v:4-7` 同一课）。

**代价**：内容整体晚 **1 对显示行 = 2 个显示行**（`:182-183`：一行 1344 拍、一帧 625 行 @50 MHz
⇒ 2×1344/50 MHz = **53.76 µs**）。顶层必须把喂给 mapper 的行号提前 2 行补回来：
`BILIN_ROWS = 2`（`pl_video_top.v:250`）→ `y_right_adv = y + pipe_off_rows + BILIN_ROWS`（`:263`）
→ `y_req_row`（`:264`）→ `cy_r`（`:271`，帧头越界请求夹回 `IMG_H-1` 而不是绕回，理由在 `:265-270`）。
⚠ `BILIN_ROWS` **必须是偶数**：成对奇偶由 `row0 = ~y[0]` 决定，加奇数会让一对的两行分属两个源行，
A/B 抽头就此错行（`:249`，凭据 tb_v89 T1、tb_v101 L3/L6、tb_v98 C1c/C1d/C1h）。

**越界抽头的两步**（`:46-54`）：末列/末行的 +1 抽头落在图外时（⚠ 这是 `fb_bilin` 自己的钉子，
与 #104 那条"旋转支把小数钉成 0"无关，后者 r94 已修），
① 小数钉 0（`fx_use/fy_use`，`:51-52`；`lerp` 在 `fx=0/fy=0` 时恒等于 `p00`）；
② 抽头**折回图内**（`kx_use/ky_use`，`:53-54`，用在 `:144` 与 `:161-162`）。
只做 ① 不够：末行那次 `w_b = w_a + ROW_WORDS` 会读到帧缓存的**填充区**——
这里要说清"填充区"是什么：数据只有 38400 个字（`frame_buffer_w64.v:32`），
而为了 BRAM 推断拆成的两块共有 32768+8192 = 40960 格（`:33-35`），
尾部那 2560 格**从不被写**；更要紧的是 `rd_data64` 这个出口**不过 `blank` 那一层 mux**
（`:80` 与 `:81` 对比：16 bit 的 `rd_data` 越界回黑，64 bit 的原始字直接给出去）。
于是"填充区里是什么"就成了硬件与仿真的分岔：**硬件里是 BRAM 上电的 0，xsim 里是 X，
而 X×0 = X ⇒ 整行被污染**（`fb_bilin.v:49-50`，r63 第一版顶层台架的 C1e 就是这么判红的）。
折回之后输出对"填充区是什么"零依赖——这是"把不确定性从接口上拿掉"的教科书式做法。

**为什么 `bilin off` 必须逐位等于最近邻**（`fb_bilin.v:48`）：`bilin_en=0` 走同一道钉子 ⇒
`fx/fy` 钉 0 ⇒ `bilin_lerp` 恒等于 `p00`（由 `tb_bilin_lerp` 判据钉），而 `p00 = pick(A, lane)`
就是旧读口那一格 ⇒ 板上来回切**不需要重新构建**，而且"1:1 档两边一模一样"是构造上的必然。
运行时口子：`gpio_o[19]`（`system_top.v:270`，PS 侧 `BILIN_BIT 19` 在 `main.c:51`）
→ 3 级同步 → `bilin_en_pix`（`pl_video_top.v:251-262`，复位默认 1）。
为什么走 `gpio_o` 而不是 `gpio_cfg1`：`:252` 说 cfg1 的 32 位已满，那是一次**新跨域**。

**`LAT` 本模块不声明**（`fb_bilin.v:194-195`）：由 `sim/tb_v101_fb_bilin.v` 用
"唯一 (行滞后, 列平移) 搜索"量出来并钉住（那份文件 `:3` 与 `:211`：实测 **(2 个显示行, 2 拍)**），
乒乓极性也由同一份台架钉（`:285` 的 L6"一个 2×2 显示块四槽同值"）——那一处错就是
"每行前半新后半旧"的撕裂，量不出来就不许靠改字面量试到绿。

### 7.8 双线性比最近邻多花几拍（把常数摆在一起）

| 位置 | 最近邻 | 双线性 | 差 | 凭据 |
|---|---|---|---|---|
| `fb_bilin`（现行）：列方向读口 | 2 拍 | 仍是 **2 拍** | 0 | `fb_bilin.v:39-40`、`pl_video_top.v:666-668` ⇒ `MIX_D` 不动 |
| `bilin_lerp` 算术核本身 | 0（不经过） | **2 级流水 = 2 拍** | +2 | `bilin_lerp.v:3`、`:28`（第一级横向）、`:50`（第二级纵向） |
| `fb_bilin`：行方向 | 0 | 晚 **1 对显示行 = 2 显示行 ≈ 53.76 µs** | +2 行 | `fb_bilin.v:182-183`、`pl_video_top.v:249-250` |
| 一次请求 → `pix` | 2 拍 | 2 拍到数据 + 2 级 lerp + 乒乓一对行 | — | `tb_v101` 量出 (2 行, 2 拍)（`:3`、`:211`） |

### 7.9 #104：旋转态拿不到小数（r94 已修）

**改前。** `zoom_mapper.v` 的旋转支在 `rot_s1=1` 时把 `fx/fy` 写成 `8'h00`。
`rot_s1` 的来源是 `rotate_en`（`:35`、`:45`），顶层把它接成
`rotate_active = (angle != 0)`（`angle_ctrl.v:18`），`zfrac_x/zfrac_y` 再进 `fb_bilin` 的 `fx/fy`。
`fb_bilin.v:51-52` 的 `fx_use` 只在 `bilin_en=0` 或"末列/末行"时钉 0，
所以小数一进 0，`bilin_lerp` 就恒等于 `p00` ⇒ **`bilin on` 与 `bilin off` 是同一张画**：
开关说"双线性开着"，取样其实还是最近邻——这就是"**空头支票**"那句话指的事。
而 OSD 上**根本没有 bilin 这一格**（这一轮复核 `grep -in bilin src/rtl/video/osd_overlay.v` 仍是零命中），
"开着"两个字只存在于串口回显里：`src/ps/main.c` 的 `bilin show` 回显自己就写了可见条件
——"看得出的条件：角度=0 且倍率非整数"。改前这句话是固件替 #104 作的证；**改后它自己反倒旧了**
（固件那句回显和它旁边的注释没跟着 r94 更新，读 `main.c` 时按"注释旧于代码"处理）。

**边界要说准。** 判据是 `rot_s1`，也就是 `angle != 0`，**包括 90°/180°/270°**——
别以为整数角度就没小数。以 90° 为例：`cos=0、sin=256` ⇒ `xr_m = 256·yp`（整数精确），
但接下来还要乘 Q8 的 `inv`，`rot_xs = 256·yp·inv`，真值是 `yp·inv/256`，
它的分数部分 `(yp·inv) mod 256` 一般非 0。也就是说 **轴对齐的角度照样需要插值**，
改前是这一支把权重抹掉了。现在的口径：只要 `rotate_en` 为真，双线性**照样在做事**，
小数取的是 `>>> 16` 之后 `[15:8]` 那 8 位。

**改后（r94）。** 横向 `fx = rot_xs[15:8]`，接近免费（整数平移不改变小数，`sx_c = xr_pix + W/2`，
floor 就是 `xr_pix`）。纵向必须**连着 floor 一起改**：`sy_c = H/2 − yr_pix` 是**减法**，于是

```
yr_true = k + f (0 ≤ f < 1)  ⇒  sy_true = C − k − f
Y_disp  = (C − yr_pix − 1) + (256 − f)/256        （f ≠ 0；f = 0 时就是 C − yr_pix、小数 0）
floor(sy) = C − k − 1，frac = 1 − f
```

**为什么这一对必须成对改**：`frac` 是"floor 之后还差多少"，翻转把数轴的方向换了一遍，
floor 与小数是同一个数的两半，只改一半就等于把 `p00` 与权重指到两条不同的线上。
只做"取补"、不"退一格"，现象是旋转时**上下各错一行**（画面上沿角度方向剪一条），而且不报任何错。
（这段推导与 `report/study/03_模块详解/10_双线性插值与分时读口.md` §五 一致，§2 也代过数。）
连带要看 `fb_bilin`：`ky_use` 的折回判据是 `sy >= IMG_H-1`，末行折回与乒乓的配对也都在同一拍上。

**记账与判据。** 代码注释仍点名 ISSUES #104；这一刀的完整账目在 `report/log/ISSUES.md` 的 **#162**
那一节（#104 自己依旧没有独立条目，引用它时连出处一起给）。判据台架 `sim/tb_zoom_frac.v`：
改前那份留档 298 行 FAIL（`build/r94_zoomfrac_console.txt`），改后 **128 次独立逐像素比较 0 失配、
99/99 旋转像素带非零小数**（`build/r94_zoomfrac_final.txt`）。它的期望值是从 DUT 同一张 Q8 三角表里取值、

## 8. 延迟账：谁与谁必须同拍

几何通路上大部分"看着对但屏上错"的缺陷，都不是算错，而是**标签与内容不同级**
（项目里编号 #68 那一族，`report/log/ISSUES.md:1786`）。三条必须会算：

1. **`MIX_D`（混色级站在第几拍）**：`localparam MIX_D = 3 + 1 + 1 + u_pipe.LATENCY;`
   （`pl_video_top.v:309`）。三个加数的含义写在 `:307`：
   3 = `cx/cy` 打到 mapper 与左路的打拍，1 = 读地址寄存 `addr_q`，1 = BRAM 读出，
   `u_pipe.LATENCY` = **15**（`proc_pipeline.v:19`，注释还写"不许由外部覆盖"）⇒ **MIX_D = 20**。
   `split_display` 的 `x/y/de/hs/vs/x_sel` 一律取 `x_d[MIX_D]` 那一级（`pl_video_top.v:864-865`）。
   历史红案：以前 `u_split` 拿的是 `x_d[11]` ⇒ 判定比内容旧 9 列 ⇒ 一条约 9 像素的近黑竖带
   （`split_display.v:10-15`、`pl_video_top.v:308`）。
2. **读口的相位是量出来的**：`sx/sy` 与第几级显示坐标对齐，由 `tb_v98` 的级数标定给出 **k=2**
   （`pl_video_top.v:684-688`，样本 822555：k=0 全错｜k=1 412166｜**k=2 0**｜k=3 410389），
   于是 `.col0/.row0/.pair_odd/.jd` 全都抽 `x_d[2]/y_d[2]`（`:689`、`:692`）。
   第一版这里接的是 `[3]`——照着 `MIX_D = 3 + 1 + 1 + LATENCY` 里那个 3 ⇒
   地址与列奇偶错一拍 ⇒ "每源像素的 4 拍"跨到相邻源像素，屏上四分之一格子错列（`:686-687`）。
   为什么 3 级延迟却对齐到第 2 级：`cx = x>>1` 把两个显示列并成一档，而 3 是奇数，
   于是"sx 恒定的那一对"相对 `x_d[3]` 跨在两个不同的源列对上，相对 `x_d[2]` 才落在同一对里
   （这一句是我按上面的奇偶推的，**推断**；结论以标定数为准）。
   口径差异也就此解释清楚：`seam_src.v:21` 说的"第 3 拍"是 **cx→sx 的流水级数**，
   顶层标定的 k=2 是 **与哪一级 `x_d` 同相**——两个数不同源，不是矛盾。
3. **`SEAM_TAPS`**：`localparam integer SEAM_TAPS = MIX_D + 1 - 3;`（`pl_video_top.v:847`）= 18，
   与 `seam_src.v:9` 的默认参数 18、以及 `:7`/`:21-23` 那段"对齐必须由流水线深度推出来，
   不许再抄字面量"是同一件事（`pl_video_top.v:844-846` 把 `MIX_D+1−3` 的算法写成了文字）。

另外 `fb_rd5x.v:4` 提醒一件事：旧方案里顶层的一整批抽位常数
（`BUS_LAT/BAR_*_TAP/PIPE_TAP/SPLIT_TAP`）全部由那个 LAT=5 导出 ⇒
**读口延迟一变，全设计的配准抽位都要跟着重算**——这就是为什么 `fb_bilin` 刻意把自己做成
"与旧读口同深"（`fb_bilin.v:40`、`pl_video_top.v:667-668`）。

## 9. seam_src：把分割线放到**图像域**算

### 9.1 是什么

`seam_src` 干一件事：在**源坐标（图像列 `sx`）**那一拍就判好
"这一格给原图还是给处理图（`orig_n`）"和"这一格是不是那条 2 列宽的蓝线（`mark_n`）"，
然后把这两个位跟着内容一起推到混色级（`seam_src.v:18-19` 的端口、`:26-30` 的判据）。
顶层由 `gp[11]`（`follow` 那一位）决定走图像域还是走原来的显示列判据
（`seam_in_src(gp[11])`，`pl_video_top.v:867`）。

### 9.2 为什么要放到图像域

用户原话在 `seam_src.v:2-3`：「将蓝线放在视频的中间，在视频的两端去转，
而不是在整个屏幕上扫。蓝线要能跟着视频去转。」
旧行为的问题写在 `:3-5`：`split_display` 判的是"显示列 < 缝位"，所以那条线**永远是竖直的**、
贴的是**屏幕**的左右两端；而 `split_ctrl` 的 `follow` 位当时只改了扫描坐标系
（端点按源宽量），线本身还在屏幕空间 ⇒ "follow" 名不副实。本模块是那后半件事。

### 9.3 原理：为什么"那条线就是画面里的一条竖线"

设图像域里取一列 `sx = k`（竖线 = 所有满足 `sx==k` 的源点）。显示像素与源像素之间是
`zoom_mapper` 那一个映射：**逆旋转（线性）+ 逆缩放（数乘）+ 平移**。
把它写成 `sx = f(x, y)`，那么"屏上哪些格子的 `sx` 等于 k"就是 `f^{-1}` 作用在直线 `sx=k` 上的原像：
**仿射映射把直线映成直线**，`f^{-1}` 也是仿射的 ⇒ 原像是一条直线，
斜率由**同一个** θ 定、间距由**同一个** `inv_scale` 定。
所以这条线"跟着旋转缩放一起走"不是巧合，而是同一条链作用在同一点集上的必然结果
（`seam_src.v:5-6` 就是这个论证的口语版）。
再补两点物理含义：
- **端点天然是画面的两端**：线只存在于画面里，画到屏上它的两头就停在（转过的）画面边沿。
- **画面外不画**：`mark_n` 里带着 `!oob`（`seam_src.v:27-28`）——
  画面外那些像素是 `oob`（黑），蓝线要是伸进黑边就是用户说的"在整个屏幕上扫"。

### 9.4 代码在哪几行

```verilog
wire in_band = (sx == seam) || (sx == (seam - 12'd1));   // :26 蓝线宽 = 2 个**图像列**
wire mark_n  = marker_on && in_band && !oob;             // :28
wire orig_n  = (sx < seam) ? raw_left : ~raw_left;       // :30 swap 只翻这一位
```

- **分类在源头做**（`:24-25`）：第 3 拍就把结论缩成 1 个位，只有一个位要跟着内容走 18 拍——
  比把 12 位的 `sx` 打 18 级再比较，少 200 多个触发器，也少一条 12 位布线。
- 移位链：`sh <= {mark_n, orig_n}`（`:36`）两位一起走同一条链 ⇒ 不会各自新旧；
  `dq`（`:38-42`）送 `mark`、`oq`（`:43-47`）送 `take_orig`，输出在 `:48-49`。
  复位值有讲究：`sh` 复位 `2'b01` = "给原图、不画线"（`:35`，理由"与旧代码 oob 时的观感一致"），
  `dq` 复位全 0、`oq` 复位全 1（`:40`、`:45`）。
- 缝位 `seam` 由 `split_ctrl` 给出，单位随 `follow` 切换：
  `wire [16:0] W = follow ? SRC_W17 : DISP_W17;`（`split_ctrl.v:33`，参数
  `DISP_W=1024 / SRC_W=512` 在 `:9-10`，顶层覆盖成 `2*PANE_W / IMG_W` 在 `pl_video_top.v:830`）
  ⇒ `split video` 之后 `split px` 的上限变成 512（`board/README.md:188`）。
  顶层把同一个 `split_eff` 同时接到 `u_seam_src.seam`（`:851`）与 `u_split.seam`（`:866`）。

**下游怎么用**（`split_display.v`）：

```verilog
wire left       = seam_in_src ? ~src_orig : (x_sel < seam);              // :44
wire oob        = left ? oob_l : oob_r;                                  // :47
wire take_orig  = seam_in_src ? src_orig : (raw_left ? left : ~left);    // :48
wire [15:0] sel = oob ? 16'h0000 : (take_orig ? orig_pix : proc_pix);    // :49
wire sep = marker && (seam_in_src ? src_mark
                                 : ((x_sel==(seam-1)) || (x_sel==seam))); // :53-54
```

- `:45-46` 提醒：图像域路径**已经**在源头判过"哪一侧给原图"，这里不能再过一遍 `raw_left`
  （过两遍就是反的）。
- `oob` 走的是**黑**（`:49`，见 §1），蓝线走的是 `{r,g,b} = {8'h40, 8'h40, 8'hFF}`（`:64-65`），
  而且是 `sep && de` 才画（`:64`，消隐期不画）。
- 顶层 `oob_l` 与 `oob_r` 接的是**同一个** `oob_out`（`pl_video_top.v:869`）：
  r59b 之后整屏只有一份源坐标，越界对两个抽头是同一件事。
- **整束标签必须与像素同级**：`#92` 第二笔把 `x/y/de/hs/vs` 也从第 11 级提到了 `MIX_D`
  （`pl_video_top.v:858-864`），症状与凭据都写在那五行注释里。

⚠ **一处过期注释要记账**：`split_ctrl.v:3-6` 的文件头写着"本模块目前没有被任何顶层例化
（2026-09-25 凌晨）"，但顶层 `pl_video_top.v:830` 已经例化了 `u_split_ctrl`。
这句是历史遗留（`docs/study/learn/README.md` §5 也列了它），读源码时别被它带走。

### 9.5 怎么在板上验


## 10. 命令覆盖关系：三个来源抢同一个数

缩放这一路有**三个**来源写同一个 `inv`：八档表（手动）、呼吸（自动）、拟合（按角度）。
mux 只有一个，在 `src/rtl/process/zoom/zoom_ctrl.v` 的 `inv_used` 那**一个**出口，而优先级写在同一个文件里
（`fit_en` 排第一；r94 起这同一个出口还多带一道旋转钳 `rotate_en && (inv_raw < inv_fit)`，见 §4.1）。
权威表在 `report/COMMAND_PRECEDENCE.md`（`:49-53` 那一行行的"谁盖谁"），
这一轮我核实的四条：

- **`zoom fit 1` 时手动 `zoom 1.5` 会静默无效**：`cur_zsel/cur_zman` 真的写进了 GPIO
  （`main.c:938` 那一条出口），屏上 `Zoom:` 也跟着变，但 `inv_used` 走的是 `inv_fit` 那一支
  （`src/rtl/process/zoom/zoom_ctrl.v` 的 `inv_used` 出口）。它不是丢了：`zoom fit 0` 之后的下一个帧首，
  手动档就接管（同一个文件的帧首寄存、`COMMAND_PRECEDENCE.md:94-97`）。
- **`zoom off` 关不掉拟合**：`fit_en` 排在 `!enable` 之前（`src/rtl/process/zoom/zoom_ctrl.v` 里那两条判断），
  所以 `zoom off` + `zoom fit 1` 的屏上是"跟着角度缩放的画面"，不是"不缩放"
  （`COMMAND_PRECEDENCE.md:101-102`）。
- **`rot auto 1` 与 fit 是绑定的**：固件在开自动旋转时顺带把缩放切到 fit
  （`main.c:1024-1030`），而且当 `speed=0` 时把它提到 2；两件事都在回显里明说，
  并给出避开的方法（"不想这样就先 `zoom fit 0` 再 `rot auto 1`"）。
  注意它**不可逆**：关自动旋转时 fit 留着（`COMMAND_PRECEDENCE.md:132`）。
  ⚠ r94 之后这句话只覆盖 fit 那一路：**旋转那一钳 `zoom fit 0` 解不开**（下一条）。
- **旋转态还多了一条覆盖，而它不由任何命令开关**（#93，r94）：旋转真的在生效时，`inv_used` 被钳进
  `inv_fit` 里较大的那一个 ⇒ 手动 1.33x/1.5x/2.0x 与呼吸的"放大方向"都让位，屏上 `(Fit)` 也跟着亮
  （那是 `zoom_fit_en | rot_forced`）。三条代价照写：① 旋转态不提供放大，但 `inv_scale` 保持用户那一档、
  **关掉旋转立刻回去**；② 0° 不钳（`rotate_active = (angle != 0)`），**任何非 0 角度都在钳**；
  ③ `zoom fit 0` 解不开，因为钳的是"旋转在不在生效"。机理与落点为什么在 `zoom_ctrl` 不在顶层，见 §4.1。

还有一条文档自己的账：`report/COMMANDS.md:135` 那句"`zoom 1.5` 那套八档手动仍然有效"
与代码不符，准确说法是"仍然保留，`zoom fit 0` 之后的下一个帧首接管"
（这条更正就写在 `COMMAND_PRECEDENCE.md:421-425`）。r94 之后还要再补半句：**旋转开着时那一档被钳住，
要等关掉旋转才回到屏上**（`inv_scale` 一直是用户那一档，所以不算丢）。
**读命令文档时要带着这一课**：命令被接受 ≠ 硬件在用（#93 那条旋转钳就是同一课的新版本；
#104 是这一课的另一个方向——"开关说开着，取样其实没开"，r94 已经把小数接上了）。

## 12. 术语表（首次出现处已解释，这里汇总）

| 术语 | 一句话 | 主要出处 |
|---|---|---|
| 逆映射 | 对每个**显示**像素求它的**源**坐标；保证输出刚性、无空洞 | `zoom_mapper.v:2` |
