# 10 双线性插值与"分时读口"：一个像素周期里怎么塞下 5 次 BRAM 读

> 代码：`src/rtl/process/bilin/{tap_sched.v,fb_rd5x.v}`、`src/rtl/process/bilin_lerp.v`、
> 小数的出处 `src/rtl/process/zoom/zoom_mapper.v`、
> `src/rtl/video/frame_buffer_w64.v`、顶层 `src/rtl/top/pl_video_top.v` 的配准常数块。
> 台架：`sim/tb_tap_sched.v`、`sim/tb_fb_rd5x.v`、`sim/tb_bilin_lerp.v`、`sim/tb_zoom_mapper.v`、
> 旋转支小数的那把快尺子 `sim/tb_zoom_frac.v`（§五）。
> 过程记录：`report/OVERNIGHT_LOG.md` R11 追加 2（实测收益）、R16–R18（接通）。

## 一、为什么非做不可：先量，再动手

**这一节记的是"接双线性之前"的起点**（今天双线性已经在通路上，见第 11 章 §7）：当时缩放/旋转是最近邻，
`zoom_mapper` 算出了源坐标的**小数部分**（`frac_x/frac_y`），但没人用它。
要不要补上双线性，不该凭"看起来更糊/更清"决定，所以先用软件模型量：
`src/host/interp_study.mjs` 对若干测试图算"插值结果 vs k×k 面积平均的理想值"的 PSNR。

三条决定结论的做法，值得单独记：

1. **理想参照必须是面积平均**（不是"缩小后的另一张最近邻图"），否则等于拿两个不同误差比大小。
2. **要有身份锚点 + 反向对照**：k=1（不缩放）时任何插值都必须是满分（锚点 45.4 dB），
   同时"故意只用横向"必须显著掉到 30.0 dB。模型第一版因为半像素约定算错，
   给出了"0° 也有 +19.5 dB"的假结论 —— 没有锚点就会被自己的模型骗。
3. **各向同性图案**（12 个方向、3 个波长）：只有它能分开"横向/纵向"两种缺失。

量出来的数（512×300 源、旋转态）：横向补上 ≈ +20%，纵向补上 ≈ +20%，两个都补 ≈ +40%。
**⇒ 只做一半等于没做**：而"横向便宜、纵向要第二行数据"恰恰是最容易偷懒的那一半。

## 二、便宜不了：读口的算术

| 事实 | 后果 |
|------|------|
| 帧缓存每个像素周期做 1 次 16bit 读（50 MHz，零余量） | 连"只补横向"都塞不下 |
| 同一组阵列上再加**一个逻辑读口** ⇒ 实测 80 → 160 个 RAMB36 | 全片才 140 个，直接出局 |
| 一个 64bit 字里已经有 4 个**横向相邻**像素 | 横向抽头几乎免费，但纵向还是要第二个字 |
| 片上早就有一个 250 MHz `clk_pix5x`（HDMI 串行化在用） | 每个像素周期 5 个"快槽" ⇒ 5 次读 |

`clk_pix5x` 与 `clk_pix` 出自同一个 MMCM、**同相**、整数 5:1 ⇒ 这不是异步 CDC，
不需要握手，但要守一条更硬的规矩（见下一节）。

槽位分配（`tap_sched`）：右窗 4 次（A、A+1、B、B+1）+ 左窗 1 次（最近邻那一个）= 5，**零余量**。
"零余量"意味着：以后任何"再读一次"的想法都得先回答"从哪个槽里挤"。

## 三、同相派生时钟的跨域纪律（这一条最容易踩，也最难在板上发现）

Vivado 对 `clk_pix → clk_pix5x` 路径只看**最早的那个快沿**：慢域触发器在 t=20n 变化，
快域下一个沿在 t=20n+4 ⇒ **只有一个快周期（4 ns）的预算**（还要减偏差与 BRAM 建立时间），
不是 20 ns。反方向 `clk_pix5x → clk_pix` 最坏有 16 ns，很宽松。

由此得出这个模块群的写法：

> 凡是"从慢域触发器出发、在快域被用掉"的信号，中间**不允许有任何组合逻辑**。
> 地址算术要么留在慢域（20 ns 预算），要么整个快域路径都从快域触发器出发（4 ns 预算）。

这不是理论洁癖：build#14 就是按"反正 4 ns 挺宽"写的 —— `base+1`、`base+ROWW` 这类加法放在快域，
再进 5:1 mux 打到 BRAM 地址脚，实测要 5.3 ns ⇒ **WNS −1.277、1400 个失败端点**（快域总共才 1855 个端点）。
改法是把四个抽头字号和左窗字号**全部在慢域算完并各打一拍**，快域只留一次纯 mux；
跨过去的每一条线都是触发器到触发器的直线。

落到接口上：`tap_sched` 不吃 `(sx,sy)`（那要在快域做一次乘常数 + 移位），
改吃上层在慢域算好的**字号 + 车道**；`fb_rd5x` 里所有跨域线都是"触发器 → 触发器/BRAM 地址脚"。

为什么不用 `set_multicycle_path` 蒙过去：可以，但那是在**声明**一个"数据整个慢周期稳定"的前提。
前提被后人改一拍，工具就不再有意见，芯片上才有现象 ⇒ 宁可让工具按 2 ns 判，把设计写成真的能过 2 ns。

## 四、LAT 是量出来的，不是推出来的

接通之后，像素总线比原来晚了几拍？顶层有 4 组东西必须跟着挪：彩条链、进效果链的
`de/x/y/left` 抽位、`split_display` 的抽位、越界/窗口标志。以前它们是**手写的 4、2、3、11**。

`tb_fb_rd5x` 的做法：喂一张已知图进真实帧缓存，逐拍记录输出，然后在 0..20 里
**搜"唯一能让 152 个样本全对上的平移量"** —— 搜到 1 个（LAT=5），并断言"只能有 1 个"
（两个都对得上说明判据没牙）。顶层于是改成从一个数推导全部抽位：

```verilog
localparam MAP_LAT = 3;              // cx → sx（两条分支都是 3 级）
localparam RD_LAT  = 5;              // ← 台架量出来的
localparam BUS_LAT = MAP_LAT + RD_LAT;
localparam BAR_L_TAP = BUS_LAT - 1;
localparam BAR_R_TAP = BUS_LAT - 1 - MAP_LAT;
localparam PIPE_TAP  = BUS_LAT - 1;
localparam SPLIT_TAP = BUS_LAT + LEFT_TAIL - 1;
```

把 V7.7 的 `RD_LAT=2` 代回这套公式，会原样得到当时写在代码里的 4 / (2) / 3 / 11 ——
其中"右窗彩条"那一项算出来是 1 而代码里写的是 2 ⇒ **顺手抓出一处存在了很多版本的 1 像素错位**
（彩条是竖条纹，1 像素偏移肉眼看不出）。`PIPE_TAP` 同理暴露出效果链差 1 拍，即一直记着的 `PROC_LAT` 旧账。

教训：**能推导的常数不该写成字面量**。写成公式以后，旧版本里两处"看不见的 1 像素"自己跳出来了。

## 五、旋转分支的小数：一个符号问题（#104，r94 已修）

**先说状态。** 这一节原先是"应该怎么改"的方案，从 r94 起它是**已经落地的行为**：
`zoom_mapper` 的旋转支不再把 `frac_x/frac_y` 写成 0，而是交出 `>>> 16` 之后的 `[15:8]` 那 8 位，
纵向连着 floor 一起退一格（判据见本节末）。改前的状况是：旋转支只取 `>>> 16` 的整数部分，
小数被硬写成 0 ⇒ `bilin on` 在旋转态是**空头支票**（下面讲的这道符号题当时还没人做）。

`zoom_mapper` 里 x 方向是**加法**（`sx = floor(...) + W/2`），整数偏移不改变小数，
所以 `fx = rot_xs[15:8]` 直接可用。但 y 方向是**减法**（`sy = C - yr`，`C = IMAGE_H/2`）：

```
Y_math = yr_pix + f/256        （0 ≤ f < 256，`>>>` 是朝 −∞ 取整 ⇒ 余下的那 8 位必非负）
Y_disp = C - (yr_pix + f/256) = (C - yr_pix - 1) + (256 - f)/256     （f ≠ 0）
       = (C - yr_pix)         + 0/256                                （f = 0）
```

**为什么必须连着 floor 一起改。** 双线性要的两个数是"**同一格**的 floor 与 frac"：
`x_out` 得是那条数轴上当前的格子号，`frac` 得是"从这一格的左边缘走了多少"。
翻转把方向换了一遍，`C - yr_pix - f/256` 已经**跨过了一格的边界**（因为减掉的是一个非零的小数），
所以它落在 `C - yr_pix - 1` 这一格里，小数是剩下的 `1 - f/256 = (256 - f)/256`。
于是修正必须成对出现：**整数退一格 + 小数取 `256 − f`**，而 `f = 0` 那一支保持原样
（`256 − 0` 按 8 位回绕正好是 0，所以 RTL 里写 `~rot_fy + 1` 就够了，不用分支）。
少做一半（只取补、不退格）的现象是"旋转时上下各错一行"，画面上是沿角度方向剪一条，
而且**不会报任何错** —— 这正是它挂了一轮又一轮的原因。

**判据（现在是真的一把尺子）。** 上面这套推导落在 `sim/tb_zoom_frac.v`：期望值从 DUT 同一张 Q8
三角表里取值、在实数域独立推出来，形状是 H1/H2 = 缩放支不许被带坏（负对照）、
H3/H4 = 旋转支 floor 与 frac 自洽（H4 单独立一条，就是因为"退一格"最容易漏）、
H5 = 旋转态必须真的有小数（否则又是空头支票），另外 H0 自检"表真的换成新角度了吗"。
把 DUT 的 `x_out + frac/256` 拼回来和实数模型比，容差 0.004（约 1/256）。
那份文件头自己立的规矩是"改之前 H3/H4/H5 必须红、H1/H2 必须绿"。
留档两份：改前 `build/r94_zoomfrac_console.txt` 是逐条 `FAIL D ... floor_y / frac_x`（它只印 FAIL，
所以满屏都是它），改后 `build/r94_zoomfrac_final.txt` 是 **128 次独立逐像素比较 0 失配、
99/99 旋转像素带非零小数**。
原先这一节写着"反向判据 `wrong_y_convention_would_be_caught ≥ 3` 写在 `tb_zoom_mapper` 里"——
**那句话是"应该怎么验"，不是"已经验了"**：本轮在 `sim/` 里 grep 不到这个名字，
`tb_zoom_mapper.v` 把 `frac_x/frac_y` 接出来了但从没比较过它们。真正的反向检查由 H1/H2 承担
（缩放支是负对照，改坏了它必须红）。

## 六、回退与对照只留一个开关

`BILIN_EN`（现在是运行时 GPIO bit19，`BILIN0/BILIN1` 可切）只做一件事：在**读口这一侧**把小数钉成 0
（`src/rtl/process/bilin/fb_bilin.v` 的 `fx_use/fy_use`）。⚠ 这个"钉 0"是**开关主动**要的，
与 §五 那条 #104 不是一回事：#104 是上游旋转支**被动**把小数丢成 0，那才是缺陷（r94 已修）。
区分它们很重要——改前在旋转态，`bilin off ↔ on` 切不动任何像素，看起来像"开关坏了"，
其实上游送下来的小数本来就是 0。
`bilin_lerp` 在 `fx=fy=0` 时恒等于 `p00`（这条性质由 `tb_bilin_lerp` 判据 2 保证），
于是**同一条通路**原样退化成最近邻。

不做"两套数据通路"的理由：两套通路必然要各自配准，而上一节刚说过配准常数会腐烂。
演示时反而是同一条路上切一个位最有说服力 —— 画面其余部分一个像素都没动。

## 七、台架抓到过的真错（都值得再看一遍）

1. `rd_en/rd_word_addr` 一被寄存，整串 burst 往后挪一槽 ⇒ 现象是**横向对、纵向错**。
2. `vld` 没跟"真被采纳的请求"走 ⇒ 灌水的头两拍也发 vld ⇒ 期望队列整体挪一格，
   辨识度极高：**每条 got 都等于上一条 exp**。
3. 左窗搭车读漏了**车道**（字号里被丢掉的低 2 位就是车道）⇒ 板上级表现是"整列偏 1 像素且不报错"。
   判据里把 `aux_lane` 驱动成与字号无关的图案，错了必然露。
4. 4 个构建脚本的 RTL 目录清单是**手写枚举**，新目录 `process/bilin` 不在里面 ⇒
   顶层接上去就"模块找不到"或被静默剪掉。补清单的同时，把 `check` 的口径也记进构建文档。
