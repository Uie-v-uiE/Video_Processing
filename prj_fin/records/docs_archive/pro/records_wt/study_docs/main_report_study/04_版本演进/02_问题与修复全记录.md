## 2. V1→V2：旋转与窗滤的"不兼容"

- **症状**：`angle≠0` 时 blur/sobel 出错图甚至花屏。
- **V1 的处置不是修，是关**：旋转时自动旁路 blur/sobel（灰度/二值/反色是点运算所以保留）。
  证据：`origin/v1-ps-ethernet:report/ROTATION_AND_EFFECTS.md` 的表
  （1–359° 行里 gray✓ binary✓ **blur✗自动关 sobel✗自动关** invert✓），
  实现 `proc_pipeline.v:24-25` `wire by2 = ~effect_en[2] | rotate_active;`
- **根因**：窗滤要的是**源图扫描顺序上的 3×3 邻域**，而旋转是**逆映射**
  （屏幕上每点反算 `(sx,sy)`）⇒ 邻域像素在源图里不再连续 ⇒ 窗口不成立。
- **V2 的解法**：把 3×3 窗口建在**目标域**（右窗光栅顺序）。
  即「源像素(映射后) → 点运算 → 目标域 3×3 → 右窗输出」。
  证据：`origin/v2-pl-ethernet:src/rtl/process/proc_pipeline.v:12` 那句
  `rotate_active, // retained for status; window filters run in target domain`，
  且 `:26-27` 已**没有** `| rotate_active`。
  被否决的方案 B（多路 BRAM 口做源域窗滤）：**7020 放不下**（`report/PS_VS_PL.md §2.1/2.2`）。
- **判据**：`sim/tb_rotate_window.v`（旋转开/关两态下模糊都在工作）。

> 这一条值得反复读：它不是"bug 修好了"，而是**换了问题的坐标系**。
> 副作用今天还在：目标域建窗 + 垂直 2× 复制 ⇒ 卷积在垂直方向退化（见
> [效果链 §3.1](../03_模块详解/05_效果链.md)）。

## 4. V4：真正根因（#31）与两条配套修复

### #31 打包器每写一个字都等 B 响应

```
axi_frame_saver64 走 S_AW → S_W → S_B，在途深度恒 1
吞吐 = 在途字节数 / 往返延迟 = 8 B / ~40 拍 @100 MHz ≈ 20 MB/s
主机给 15 MB/s ⇒ 只有 1.3× 余量
显示拷贝在 V-blank 抢同一条 HP0 ⇒ 往返涨到上百拍 ⇒ 平均掉到 15 MB/s 以下
⇒ 每个 1392 B 包从第 48 字节起按 16bit 粒度被丢弃
```

**修法（V6.3）**：AW/W 同拍挂出、各自保持到被接收；`OST=8` 在途；
B 只回收计数且**不回绕** —— 多回一个 B 会让 `outst` 从 0 回绕成 15 而永久卡死。
**结果**：15/30/60 fps 回读全部 100.0%，包内各带 0.0%，半字错帧 0/76800。

### #28 每隔一个 16bit 的黑横纹

入包 CDC 读侧被写成「每 3 个 axi 周期取 1 条」= 66 MB/s < GMII 线速 125 MB/s
⇒ 单包内就能灌满 512 深缓冲 ⇒ 稳定丢约 46% 的 16bit 字。
**修**：每拍取一条，且 flush 标记永远给真实数据让路。

### #27 静止画面也撕裂（且与速率无关）

`frame_reasm` 的"收满一帧"只看累计字节数 ⇒ 丢一包 + 一包重复偏移仍算收满 ⇒ 把空洞帧 commit 出去。
**修**：commit 需要 `rows_hit == IMG_H` **且** 累计到 `FRAME_BYTES`。
（今天长成 `frame_reasm.v:169` 的三条件与门，V5.1 又加了 `!bad_frame`。）

### #29 分包长度不是 8 的倍数 ⇒ 均匀散布的黑点

1396 B 载荷时包边界落在 64bit 字中间，同一个字被打包器**分两次推送**、
后一次（含无效字节）覆盖前一次 ⇒ 每帧约"每两个包一处"的 4 字节洞，洞里是 0x0000。

| 分包 | 命中率 | 每帧空洞（16bit 字） |
|------|--------|---------------------|
| 1396 B | 99.9% | **222（111 处 ×2）** |
| 1392 B | 100.0% | 0~2（仅 #33 的已知残留） |

**修法（V6.4）**：`WSTRB` 按 16bit lane 生成（`cur_keep → q_keep → keep_r`），部分字只写自己有效的字节。
**判据为什么差点没建起来**：仿真从机原来**无条件整字写入** ⇒ 这种覆盖根本测不出来。
把从机改成按 `WSTRB` 做读-改-写之后，A/B 才成立：
修复前 `words exact = 38290/38400`、`first bad word = 174`（正是 `1396/8=174.5` 的跨界字），
修复后 38400/38400。
> **教训**：当"修复前应当失败"的测试却通过了，第一反应应该是**怀疑测试**，不是怀疑症状。

### #32 打包器 FIFO 不能加深（会被综合成触发器）

`q_addr/q_data` 是 512×96bit 的寄存器阵列（≈4.9 万 FDRE），
`FW=11` 直接 `DRC UTLZ-1: FDRE requires 176092, only 107000 sites`。
⇒ 要加深只能加在 BRAM 侧。这条在 V5 的 R02 里被"正着用"：
**把深度不变、实现从触发器改成 LUTRAM**，一次释放 4 万多个 FDRE。

### #6/#7 一组：CDC 地址切片与拆包

`dout[35:17]` 应为 `dout[34:16]`；打包时加 `1'b0` 对齐 36-bit。
症状是"HDMI 窄条 / 出现 4 幅画面"——**地址切片错 1 位 = 每 4 个像素错一次**，
所以屏幕上正好是 4 幅并排的窄条。
> 这类"屏幕被复制成 N 份"的症状，几乎总是地址位选错，不是时序问题。

## 6.5 V7.9（第四夜）三条：`ISSUES.md` #36 / #37 / #38

这三条值得单独讲，因为它们**都不是"想不到"的 bug，而是"改的时候只改了一半"**。

### #36 `copy_abort`：脉冲跨域，电平同步器不是修法

10 ns 宽的脉冲从 100 MHz 域进 50 MHz 域，且两路时钟是**同一个 MMCM 同相出来**的 ⇒
翻转沿正好落在采样沿上。相位扫描实测：

| 接法 | 收到次数（0–9 ns 十档 × 3 次） |
|------|------------------------------|
| 裸采 | 27/30，错开 4 ns 那一档 **0/3** |
| 电平型 3 级同步 | **27/30，与裸采逐档相同** |
| 翻转 + 3 级 + 异或 | 30/30 |

三条教训：① **别把"三级同步器"当万能**，它只对**电平**有意义，脉冲要靠翻转；
② 我原本断言"电平同步只会更糟"，实测"一样糟" —— **推论要交给台架否掉**，
文档里那句是我猜的，被测量改了；
③ 0 ns 那一档仿真 3/3 全对 ⇒ **这类 bug 的真实形态是"仿真通过、硅片靠运气"**，
所以判据不能只看"绿了没有"，要看**扫描维度**（相位、温度、电压）。
附带一条口径教训：我写过"`report_cdc` 一直把它记成 unsafe"，**不成立** ——
`cdc.rpt` 只有"时钟对 + 端点数"的粒度，**不点名信号**，两份报告逐行相同。
⇒ **每一句声明都要对上唯一能证明它的那份证据**：这条的证据是台架，不是报告。

### #37 `eth_ctrl` 发送仲裁：改对符号只是第一步

原文 `arp_rx_flag && (udp_tx_busy==0 || icmp_tx_busy==0)` —— 两个**独立** busy 用 OR，
语义是"任一空闲"，想要的是"全部空闲"。看到这一条的人都会说"一行改 `&&`"。
**但只改符号会引入一个新 bug**：`arp_rx_flag` 只有一拍宽，而"全部空闲"在这一拍通常不成立
⇒ 请求被整拍丢掉 ⇒ PC 要等 ARP 超时。所以要补一个 `arp_pend` 记账位。

补记账位又引出第三层：**跨 always 块用非阻塞信号互相清标志，默认晚一拍**。
第一版写成 `else if (arp_tx_en) arp_pend <= 1'b0`（在另一个块里），读到的是**上一拍**的
`arp_tx_en` ⇒ 清账晚一拍 ⇒ `arp_tx_en` 连高**两拍** ⇒ ARP 状态机重启、第 0 字节发两遍。
台架数出来 **13 个字节而不是 12** 才暴露。修法：记账与兑现放进**同一个 always**，
同拍清，并把置位放在块尾（同拍"兑现旧账 + 新请求"时新请求不会被吃掉）。

⇒ 可复用的判据写法：**仲裁/握手类改动的台架必须包含"这个信号高了几拍"**，
只判"最终发了多少字节"会漏掉脉宽错误。

### #38 `p_good` 硬接 1：新字段先问"这个数从哪来"

遥测包要发"错包数"，顺手查下去发现两个板的顶层都写 `.p_good(1'b1)` ⇒ `stat_bad` 恒 0。
今晚**没有**改硬件（会碰已上板验过的入口链、明早要演示），而是把**口径**改严：
PC 端打印 `bad≈7(未接FCS判定)`，文件头写清楚该看哪三个字段，并把修法登记成 #38。
⇒ **"不修"是一种合法决定，但必须让数字不再声称它没证明的东西。**
另一条：`m_good` 是"无 ER + 长度合理"，**不等于 CRC-32 校验** —— 术语别越级。

## 7. #33 那条已知残留（为什么不修，写清楚）

`frame_reasm` 的最后一个 64bit 字高半个 u32 偶发读到 0：
8 次末帧读数出现 4 次，15/30/60 fps 都有；**下一帧同地址被覆盖 ⇒ 自愈、肉眼不可见**；
`tb_v6_ingress_integrity +FULL`（221 包、最后一包 960 B）**不复现**。
怀疑：最后一拍 `wr_en` 与 `flush` 的竞争导致最后 2 个 16bit 没被推出。

**为什么允许它存在**：
1. 判据可量化（就是那 2 个 lane / 153600）；
2. 无可见症状且自愈；
3. 复现条件不明 ⇒ 无法写出"修复前必须失败"的 TB ⇒ 改了也无法证明（第 0 节的 C 类）。
4. **它被反算成一个数字**：`27137 = (0 − 38399) & 0xffff` ⇒
   日志里出现 `f27137:2` 就是它，不是新问题。

> 这一条的处理方式本身就是内容：**不修可以，但必须说清为什么不修、以及怎么认出它。**
