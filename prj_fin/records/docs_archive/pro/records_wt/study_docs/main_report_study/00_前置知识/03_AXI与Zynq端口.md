# 03 · AXI 与 Zynq 的 GP / HP 端口（以及"为什么深度无用、在途才有用"）

> 本工程拖影问题的最终根因就在这一篇讲的机制上。
> 如果你只想学一件事，就学**"AXI 的吞吐由在途事务数与往返延迟决定"**这一条。

---

## 1. AXI 是什么：五条独立通道

AXI（Advanced eXtensible Interface）是 ARM 的 AMBA 总线协议，Xilinx 把它用作片内互连标准。
一次"写"用到三条通道，一次"读"用到两条：

```
写： AW（写地址） →  W（写数据）  →  B（写响应）
      ↘ 三者各自独立握手，各自有 valid/ready ↙
读： AR（读地址） →  R（读数据，带 RLAST）
```

每条通道的握手规则一样：**发送方拉 `valid` 并保持，接收方拉 `ready`；两人都高的那个时钟沿完成一次传输。**
通道独立 ⇒ 地址可以先发、数据后到，响应可以几百拍之后才回。这就是"流水化"的硬件基础。

关键信号（本工程用到的）：

| 信号 | 含义 | 本工程取值 |
|------|------|-----------|
| `AWADDR` | 字节地址 | `base + {widx,3'b000}`（64 bit 对齐） |
| `AWLEN` | 突发长度 **减 1** | 入包写 = `0`（单拍）；显示读回 = `15`（16 拍） |
| `AWSIZE` | 每拍字节数的 log2 | `3'b011` = 8 字节（64 bit 总线满宽） |
| `AWBURST` | INCR/FIXED/WRAP | `2'b01` = INCR |
| `WDATA` | 写数据 | 64 bit |
| **`WSTRB`** | **字节选通**（每 bit 对应 1 字节） | 第五版前恒 `0xFF`；V6.4 起按 16bit lane 生成 |
| `BRESP` | 响应 | 本工程不检查（只回收计数） |

### `WSTRB` 为什么能决定"画面有没有黑点"

`WSTRB = 0xFF` 意思是"这 8 字节全写"；`0x0F` 意思是"只写低 4 字节，高 4 字节保持内存里原来的值"。

本工程的帧是 512×300×2 = 307200 字节，按 64 bit（8 字节）一个字存。
上位机把帧切成 1392 字节一包。**1392 是 8 的倍数** ⇒ 每包边界正好落在 64 bit 字边界上，
一个字不会被两个包分两次写。
但如果用 **1396**（不是 8 的倍数），就会出现：

```
包 A 写了某个 64bit 字的低 4 字节
包 B 写同一个字的高 4 字节
```

而 V6.4 之前 `WSTRB` 恒 `0xFF` ⇒ **包 B 写的时候把包 A 刚写好的低 4 字节覆盖成 0**，
于是屏上出现均匀散布的黑点，实测每帧约 111 处 4 字节洞。
修复就是让每个 beat 只写自己有效的字节：

```verilog
// src/rtl/eth/axi_frame_saver64.v（V6.4）
assign m_axi_wstrb = { {2{keep_r[3]}}, {2{keep_r[2]}},
                       {2{keep_r[1]}}, {2{keep_r[0]}} };   // 每个 16bit lane → 2 字节选通
```

> 学习点：**"硬件对分包长度免疫"不是靠约束上位机，而是靠把选通信号做对。**
> 顺带一个测试要点：TB 里的 AXI 从机**必须按 `WSTRB` 做读-改-写**，
> 否则这类覆盖 bug 在仿真里永远看不见（本工程踩过，见 [05_验证与上板](../05_验证与上板/01_怎样写出能抓bug的testbench.md)）。

## 2. Zynq 的 PS 侧端口：GP 与 HP 完全不是一回事

| 端口 | 位宽 | 频率 | 用途 | 特点 |
|------|------|------|------|------|
| `M_AXI_GP0/1` | 32 bit | 100 MHz | PS 主动访问 PL（读写寄存器） | 慢、单次事务、走 GP 口**不能**高效搬数据 |
| `S_AXI_HP0..HP3` | 32/64/128 bit 可配 | 100 MHz | **PL 主动访问 PS 的 DDR** | 直连 DDR 控制器，带宽大，是 PL 侧 DMA 的唯一正道 |
| `S_AXI_ACP` | 128 bit | — | PL 直连 CPU 缓存 | 本工程未用 |

本工程的配置（`build/tcl/build_system_axigpio.tcl` 里对 PS7 IP 的设置）：

```tcl
CONFIG.PCW_FPGA0_PERIPHERAL_FREQMHZ {100}
CONFIG.PCW_USE_M_AXI_GP0 {1}
CONFIG.PCW_USE_S_AXI_HP0 {1}
CONFIG.PCW_S_AXI_HP0_DATA_WIDTH {64}      ;# 64bit @100MHz = 理论 800 MB/s
```

- **GP0** 只用来访问挂在片内的 AXI GPIO（`0x41200000`），即"PS 告诉 PL 要开哪些效果"。
- **HP0** 承担全部视频流量：入包写 DDR（乒乓 bank）+ 显示读回（消隐期整帧拷贝）。
  **两条流抢同一个端口**——这个事实是本工程一半故事的来源。

> 这里有个容易忽略的细节：HP 端口在 SLCR 里有缓冲配置寄存器（`FPGA_FCM*`）。
> **用 JTAG 的 `ps7_init` 起板不会写这些寄存器，只有 FSBL 会。**
> 所以"JTAG 起板"和"SD 卡 FSBL 启动"两种路径下，HP 通道的行为并不完全一样。
> 本项目在功耗/时序基线重测时专门记了这一条。做严格对比实验时要固定启动方式。

## 3. 核心公式：吞吐 = 在途深度 × 每拍字节 ÷ 往返延迟

这是本篇最重要的部分。

```
        在途字节数
吞吐 = ──────────
        往返延迟
```

AXI 写是"发出地址+数据，等很久之后 B 才回来"。设 HP0+DDR 的写往返延迟为 `L` 拍：

- 如果你**每写一个字就等 B 回来**（在途深度 = 1）：
  `吞吐 = 8 字节 / L 拍`。取 `L ≈ 40 拍 @100 MHz` ⇒ `8/40 × 100 MHz = 20 MB/s`。
  **这就是本工程第四版之前拖影的全部原因**：主机给 15 MB/s，只有 1.3× 余量，
  显示拷贝一抢端口，平均速率就掉到 15 以下 ⇒ 每个包从某个固定字节偏移开始按 16bit 粒度丢字。
- 如果允许 8 个 beat 在途（`OST = 8`）：`8×8 / 40 × 100 MHz ≈ 160 MB/s`，
  再考虑握手本身占的拍数，实测约 400 MB/s 量级。**问题消失。**

**加深缓冲为什么救不了它**：缓冲深度决定"能吸收多长的瞬时堵塞"，
平均吞吐只由"在途深度 ÷ 往返延迟"决定。本工程真的试过把 CDC 加深到 8192（V6.2），
结果丢字起始位置恰好等于打包器深度——**方向错误，记录保留在**
`report/CHANGELOG_V6.md` 的 V6.2 一节（标题里就写着"结论：方向错误"）。

### 修复后的写法（V6.3）

```verilog
// src/rtl/eth/axi_frame_saver64.v
localparam [3:0] OST = 4'd8;          // 在途 beat 上限（够盖住 HP0 写延迟）
wire have = (rptr != wptr) && !beat && (outst < OST);
...
m_axi_bready <= 1'b1;                 // B 通道永不反压，只回收计数
if (have && !b_ok)      outst <= outst + 4'd1;
else if (!have && b_ok) outst <= (outst == 4'd0) ? 4'd0 : outst - 4'd1;   // 只减不回绕
```

两个细节值得学：
1. **AW 与 W 同拍挂出、各自保持到被接收**（`aw_wait`/`w_wait` 分开管），
   这样握手不要求对方同时接受两条通道；
2. `outst` **只减不回绕**——注释写得很直白：万一上游多回一个 B，回绕成 15 会让
   `have` 永远不成立，整条入包链就此卡死（板级症状就是"画面冻结"）。
   **计数器宁可少计，也不要锁死**，这是防御性设计的取舍，值得记住。

## 4. 突发（burst）与它的边界条件

`AWLEN=0` 是"一次一拍"。为什么入包写不用长突发？

- 本工程的写地址**不连续**：协议里每个 UDP 包带一个 u32 字节偏移，
  画面是"按偏移随机写"的（乱序可拼帧）。连续地址才能合并成长突发。
- 显示读回就相反：整帧顺序读，所以 `axi_frame_writer_gated` 用 `arlen = 15`（16 拍）突发。

用长突发要注意两件事（本工程历史上踩过）：
1. **4 KB 边界**：AXI 规定一次突发不得跨 4 KB 地址边界，否则从机行为未定义；
2. **响应配对**：一个 AW 对应一个 B，突发数与 B 数对不上就会永久错位。
   早期版本 `axi_frame_saver_burst` 就是因为这类问题在板上直接挂死（注释里写着
   "burst hung → red"），后来才回到"单拍 + 高在途"的路线。

## 5. 读回通路：为什么拷贝要"在消隐窗口做"

```
显示每帧要读 38400 个 64bit 字（= 307200 字节）
消隐窗口 ≈ 67200 个 axi 周期
拷贝预算 = 38400 / 67200 = 0.571 拍/周期 ≈ 457 MB/s（含读+写两侧占用）
```

放在消隐窗口做有两个理由：① 那时屏幕不采样显示 BRAM，改内容不会撕裂；
② 把带宽集中到一个固定窗口，才好算账——上面那行除法就是"够不够快"的判据。

代价是：这 672 µs 里 HP0 被读回大量占用，而入包还在继续 ⇒ **入包侧必须靠缓冲 + 足够在途深度扛过去**。
这就是"两条流抢一个端口"的具体形态，也是为什么拖影会表现为"每包固定偏移开始丢"。
