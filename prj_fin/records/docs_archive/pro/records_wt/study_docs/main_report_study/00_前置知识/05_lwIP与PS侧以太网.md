# 05 · lwIP 与 PS 侧以太网（第一版为什么用它、为什么最后不用它）

> 学习顺序上这一篇放在"第一版"之前：不先懂 lwIP 是什么，就看不懂
> 为什么"把网口从 PS 搬到 PL"是一件值得单独开一个版本的事。

---

## 1. 网线里跑的到底是什么

一条 UDP 视频包在以太网上长这样（每格一字节）：

```
| 目的MAC 6 | 源MAC 6 | 类型 2 | IP 头 20 | UDP 头 8 | 载荷 N | CRC 4 |
             ↑ 前导码/帧起始定界符在物理层，不在这段里
```

要"收到一个 UDP 包"，必须完成这些事：

1. **物理层**：把 PHY 芯片送来的比特流变成字节（本工程用 RGMII，见 06 篇）；
2. **数据链路层**：认出这是发给我的 MAC（**ARP**：谁有 192.168.1.10？告诉我 MAC）；
3. **网络层**：解 IP 头，校验和，判断协议号（17 = UDP）；
   还要能回 **ICMP echo**（ping），否则调试时连"通不通"都判断不了；
4. **传输层**：解 UDP 头，比对目的端口（本工程 5001），把载荷交给应用；
5. **应用层**：本工程是"按 u32 偏移把载荷拼进帧缓冲"。

**软件实现这套东西，就叫协议栈。lwIP 是最常用的嵌入式 TCP/IP 协议栈之一。**

---

## 2. lwIP 是什么

lwIP = **lightweight IP**，一个开源（BSD 许可）的 C 语言 TCP/IP 协议栈，
专为内存与算力有限的嵌入式系统设计。Xilinx 的 Vitis 把它作为 `lwip220`/`lwip` 库提供。

它的典型形态：

```
应用（你的 main 循环 / 回调）
    ↓ send()/recv() 风格 API
socket 层（lwip/udp.h）
    ↓
UDP / IP / ARP / ICMP
    ↓ netif（网络接口抽象：linkoutput、input、mtu）
    ↓
XEmacIf / 以太网驱动（操作 GEM 寄存器、BD 描述符环）
    ↓
硬件：Zynq PS 的三速以太网控制器（GEM0/GEM1）
    ↓ MII/RMII/GMII/RGMII
PHY 芯片（板载 RTL8211）→ 网线
```

关键概念：

| 概念 | 意思 | 对本工程的意义 |
|------|------|----------------|
| **netif** | 一个网络接口的抽象（MAC 地址、IP、收发函数） | 板子有两个网口 → 两个不同的 netif/硬件 |
| **pbuf** | 协议栈的缓冲区描述符（链式） | 收上来的帧放在 pbuf 里，你要拷贝出来 |
| **回调（`udp_recv`）** | 包到了由协议栈调用你的函数 | 第一版就是在这里把像素搬进 DDR |
| **`sys_now` / 定时器** | 协议栈需要时间基准（ARP 缓存老化、重传） | 裸机里要自己喂 |
| **`lwipopts.h`** | 编译期配置（内存池大小、是否启用 TCP、速率） | **本工程踩过：重编 Platform 会把它冲回默认值** |

## 3. 第一版（`v1-ps-ethernet`）的完整数据通路

```
网线 → PS 的 GEM0 → lwIP（UDP 回调）→ PS 把像素写进 DDR
                                          ↓
                              PL 通过 S_AXI_HP0 读出 DDR
                                          ↓
                     帧缓存 → 效果链 → 旋转 → HDMI 双窗
```

也就是说：**收包、拼帧、搬数据全在 CPU 上做，PL 只做显示与图像处理。**

这个结构的好处是**开发快**：协议不用自己写，`udp_recv` 回调里 memcpy 就行。
第一版确实跑通了，而且把显示侧的难点（旋转、效果、双窗、OSD）都验证了。

代价（也是第二版要搬走它的理由）：

1. **吞吐与抖动由软件决定**：收包中断、pbuf 拷贝、回调耗时互相抢；
   15 MB/s 的视频流在双核 A9 + lwIP 上能吃掉大量 CPU，且**延迟不确定**。
2. **"帧到齐了没有"这件事只能软件判断**：软件数包 → 通知 PL → 有延迟、有竞态。
   而显示换帧恰恰需要"帧完整"这个信号（本工程第四版修的就是这个信号的可信度）。
3. **PL 完全没参与网络**，等于放弃了 FPGA 最擅长的东西：
   把协议解析做成**流水线**，每拍处理一个字节，延迟固定、可预测、可测。

## 4. 第一版留下的可复用经验（都是踩出来的）

`v1-ps-ethernet:report/ISSUES.md` 有 19 条，其中与 PS 网络直接相关的：

| # | 现象 | 根因 | 处置 | 可迁移教训 |
|---|------|------|------|-----------|
| 4 | PHY 自协商 `link_speed invalid` | RTL8211 在 `CONFIG_LINKSPEED_AUTODETECT` 下 `get_IEEE_phy_speed` 返回无效 | BSP 里把 `LINKSPEED1000` 写死 | 板载 PHY 与驱动兼容矩阵要实测，不能靠默认配置 |
| 5 | ping 不通 | PC 另一块网卡是 APIPA（169.254.x.x） | 明确把接板子那块网卡设成 192.168.1.100/24 | **双网卡机器上"哪块网卡接的板子"是第一个要确认的事** |
| 6 | ping 通但 UDP 不到 | 源地址选错网卡 | `socket.bind(("192.168.1.100", 0))` | 上位机要**显式绑定源地址** |
| 2 | `udp_recv_fn` 重定义 | 自定义回调名与 `lwip/udp.h` 的 typedef 撞名 | 改名 `on_udp_frame` | 别和库的类型同名 |
| 3 | `platform.h` 缺失 | empty_application 模板不一定生成它 | 去掉对它的依赖 | Vitis 模板生成的文件集合不稳定 |
| 19 | Platform 重编冲掉 lwipopts | 库配置随 Platform 重建 | 在 Platform 工程里改，或每次重编后再改 | 配置要进版本控制，不能只改工作区 |
| 1 | EMIO GPIO 读回恒 0 | 该板 EMIO 未接可观察 IO / bank 配置异常 | **改用 GP0 上的 AXI GPIO `0x41200000`** | 控制面走 AXI GPIO 比 EMIO 可靠，而且这个选择一直保留到今天 |

> 第 1 条特别值得记：本工程现在还在用的 `0x41200000` AXI GPIO，
> 就是第一版踩坑之后定下来的。一个"随便选的基址"会变成整个项目的接口约定。

## 5. 搬走 lwIP 之后，PS 还剩什么

第二版起，`src/ps/main.c` 里**没有任何网络代码**（头两行注释就写着
"UDP video data path is handled entirely in PL"），PS 只做三件事：

1. 初始化 UART（115200 8N1）；
2. 解析串口命令（`SRC0/SRC1`、5 位效果串、`TH80`、`ZOOM0/1`、`FILL`、`STAT`）；
3. 把命令写进 AXI GPIO `0x41200000`（PL 从那里读控制字）。

于是分工变成：

| | PS | PL |
|---|----|----|
| 网络 | 不参与 | 全部（RGMII/ARP/ICMP/UDP/CRC） |
| 数据搬运 | 不参与 | 经 HP0 读写 DDR |
| 控制 | 串口解析 + 写 GPIO | 读 GPIO 决定效果/源/缩放 |
| 调试 | 提供 JTAG 入口、可跑 ELF | 提供 ping（ICMP 硬件应答）⇒ **不装软件也能确认链路活着** |

最后一行很实用：**PL 里自己实现 ICMP 之后，`ping 192.168.1.10` 就成了"比特流跑起来了"的判据**，
不需要 PS 侧任何软件。本工程的板级复验第一步就是 ping。

## 6. 什么时候仍然应该用 lwIP

不是"硬件栈一定更好"。判据：

| 情况 | 建议 |
|------|------|
| 需要 TCP、需要协议兼容性、要跑 mDNS/HTTP | **软件栈**（lwIP），硬件实现 TCP 不划算 |
| 带宽需求低（<1 MB/s）、延迟不敏感 | 软件栈，省事 |
| 要"每拍一个字节"的稳定吞吐、要固定延迟、要在 PL 里直接拼帧 | **硬件栈** |
| 需要不看屏幕就能判断链路状态（ICMP 自答） | 硬件栈 |
| 器件资源紧张（硬件栈要占 LUT/BRAM） | 权衡：本工程 PL 侧协议栈实际只占很小一部分（见资源报告 `u_eth/*`） |

本工程选硬件栈的**真实动机**是第 3 节第 2 条：显示换帧需要"帧完整"这个硬实时信号，
软件给不了确定性。这个理由比"性能更高"更值得写进答辩。
