# 01 · FPGA、Zynq-7020 与"资源"这件事

> 本篇是全套学习文档的地基。后面所有关于"为什么这里要改一下"的判断，都建立在
> "FPGA 里的东西是用什么造的、造一样东西要付多少代价"之上。
> 文中所有数字都来自本工程 `build/utilization.rpt` 的真实统计，不是教科书举例。

---

## 1. FPGA 不是"很多小 CPU"，而是"很多可连线的零件"

写软件的人第一次接触 FPGA 常犯的理解错误，是把它想成"很多个能并行的处理器核"。
不是。FPGA 里铺的是三类零件：

| 零件 | 能干什么 | 类比 |
|------|----------|------|
| **LUT**（查找表） | 实现任意 6 输入（或 5 输入 + 1 输出选择）的组合逻辑；也能当 64 bit 的小 RAM 用 | 可编程的"真值表" |
| **FF**（触发器） | 存 1 bit，带时钟沿、可带异步复位/置位、可带使能 | 寄存器 |
| **连线**（routing） | 把 LUT/FF/BRAM 的引脚连起来 | 金属线，**数量是有限的、且延迟不可忽略** |

再加上成块的功能单元：**BRAM**（块存储器）、**DSP48**（乘法累加）、**CARRY4**（快速进位链）、
**BUFG/MMCM**（时钟缓冲与锁相环）、**IOB/IDELAY/OSERDESE**（输入输出与串并转换）。

Verilog 里写 `assign y = a & b;` 或者写一个 200 行的状态机，最终都要**落到这些零件上**，
而"落到多少、落在哪、连线绕了多远"由综合器与布局布线器决定。
这就是 FPGA 开发的根本特征：**你写的不是顺序指令，而是一份"要造什么东西"的描述；
代价不是时间复杂度，而是零件数量与连线长度。**

### 一个必须尽早建立的直觉：连线常常比逻辑更贵

本工程第四版→第五版之后，最差的一条时序路径长这样（`build/timing_summary.rpt`）：

```
Path Group: eth_rxc   周期 8.000 ns   Logic Levels: 11 (CARRY4=6 LUT2=1 LUT3=2 LUT6=2)
  Source: u_eth/u_udp/u_udp_rx/rec_en_reg/C
  Destination: u_eth/u_reasm/rows_hit_reg[0]/CE
  net (fo=2)    1.873 ns   eth_rxc_IBUF
  net (fo=1827) 1.463 ns   u_eth/u_udp/u_udp_rx/CLK        ← 时钟树插入延迟
  net (fo=50)   1.947 ns   u_eth/u_reasm/udp_rec_en        ← 一根信号线就吃掉 1.95 ns
  ... 11 级逻辑合计只贡献约 0.8 ns
  slack 0.499 ns
```

11 级逻辑听起来很多、很该改 RTL。但把每一行的延迟加起来会发现：
**这条路径 7.16 ns 的数据延迟里约 6.4 ns 是"线在走"，逻辑本身只占约 0.8 ns。**
所以这时候改 RTL（把加法器改窄、把状态机拆一级）收益很小，
而"让这两个模块在硅片上挨得近一点"（换实现策略、给布局器更多余量）才是有效手段。

> 记住这个判断顺序：**先看报告说是逻辑慢还是连线慢，再决定改 RTL 还是改实现。**
> 这是本工程第五版做时序优化时真正用到的方法。

## 2. xc7z020clg484-2 到底有多少零件

器件型号读法：`xc7z` = Zynq-7000（PS+ARM 与 PL 在同一颗芯片里）；`020` = 规模档位；
`clg484` = 封装（484 球 BGA，决定可用管脚数）；`-2` = 速度等级（数字越小越快，2 是本工程用的）。

| 资源 | 数量 | 说明 |
|------|------|------|
| 系统门 | 106,400 | 市场话术，工程上不要用它做分母 |
| 可编程逻辑（CLB） | 17,400 | 一个 CLB 通常就是一个 Slice |
| **LUT** | **53,200** | 4 个/SLICE × 8 个 LUT 每 2 个 SLICE，读报告时以 "Slice LUTs" 为准 |
| **触发器 FF** | **106,400** | 每 SLICE 8 个 |
| **Block RAM** | **140 tile × 36 Kb = 5.04 Mb** | 一个 tile 可以当 1 个 RAMB36 或 2 个 RAMB18 |
| **DSP48E1** | **220** | 一个 slice 一个，含 25×18 乘法器 |
| MMCM / PLL | 2 / 2 | 时钟合成 |
| 全局时钟缓冲 BUFG | 32（每列 8） | 本工程用到 8 |
| 可用用户 I/O | 100（CLG484 封装） | 本工程只用了 27 个 |

**这张表就是"能不能再加一个功能"的唯一裁判。** 后面所有优化故事都源于此。

## 3. 本工程的真实占用：一次"看起来正常其实堵死"的案例

第四版（分支 `v4-zero-loss`，提交 `647160e`）的实现报告：

| 资源 | 用量 | 占比 | 观感 |
|------|------|------|------|
| Slice LUTs | 19,825 / 53,200 | 37.27% | 宽裕 |
| LUT as Memory | 305 / 17,400 | **1.75%** | 几乎全空 |
| Slice Registers | 54,588 / 106,400 | **51.30%** | 偏高 |
| Slice | 13,290 / 13,300 | **99.92%** | **贴死** |
| Block RAM Tile | 138.5 / 140 | **98.93%** | **贴死** |
| DSP | 13 / 220 | 5.91% | 宽裕 |

这张表里有三个信息，每一个都是后面动手的理由：

1. **BRAM 98.93% ⇒ 任何需要存储的新功能都进不来。**
   想加双线性插值？要行缓存 ⇒ 要 BRAM ⇒ 没有。想加深缓冲？没有。
2. **Slice 99.92% ⇒ 布局器没有落点。**
   Slice 是"物理格子"，它满了不是"逻辑不够"，而是**放不下、绕不动、时序做不出来**。
   这一项比寄存器占比更致命，因为它是空间约束。
3. **LUT as Memory 只用 1.75% ⇒ 器件里 98% 的"分布式 RAM"在睡觉。**
   而 51.30% 的触发器里，约 5.1 万个其实是一个 512×100 bit 的 FIFO ——
   它本可以用那些睡觉的 LUTRAM 来存。

于是第五版的第一刀砍在这里：**把用触发器搭的 FIFO 改成用分布式 RAM 搭**。
结果（同一份功能、同一套约束）：

| 资源 | 第四版 | 第五版（三轮改造后） |
|------|--------|----------------------|
| Slice Registers | 51.30% | **4.08%** |
| Slice LUTs | 37.27% | **11.87%** |
| Slice | 99.92% | **18.03%** |
| Block RAM Tile | 98.93% | **64.64%** |
| LUT as Memory | 1.75% | 7.71% |
| 总功耗 | 2.525 W | **2.350 W** |

**功能一行没变，占用塌了一大截，然后"加不加得下"的问题全部变成"想不想加"的问题。**
这就是为什么要先学"资源是什么"再学"代码怎么写"。

## 4. 为什么"用触发器存数据"在这类设计里是个真陷阱

Verilog 里写：

```verilog
reg [63:0] q_data [0:511];
always @(posedge clk) q_data[wptr] <= din;   // 写
always @(posedge clk) dout <= q_data[rptr];  // 读
```

这看起来天经地义。但综合器面对"数组"时有三条路：

1. **触发器阵列**：512×64 = 32,768 个 FF，外加读侧 512 选 1 的 mux 树（几百个 LUT）。
   只有在"必须异步读、且深度很小"时才划算。
2. **分布式 RAM（LUTRAM）**：数据存在 LUT 里，512×64 大约 800~900 个 LUT-RAM 单元。
   适合中等深度、需要异步读。
3. **块 RAM（BRAM）**：1~2 个 tile 就装下，但**读必须同步**（地址给出后下一拍才出数）。

本工程第四版走的是第 1 条，代价是 3.3 万个 FF（仅 `q_data` 一个数组）。
更讽刺的是：**同一个仓库里的 `dc_fifo.v` 用的是正确写法**（数组写独占一个不带复位的
always 块），所以它顺利进了 BRAM；而 `axi_frame_saver64` 因为把数组写和带异步复位的
控制逻辑写在同一个块里、还包在 `task` 里，综合器直接拒绝推断并报
`Synth 8-7186 ... is not inferred as ram due to incorrect usage`。

> 学习要点：**"综合器会不会把它变成 RAM"是写法决定的，不是数据量决定的。**
> 而它变成什么，会决定你的器件是 99.92% 堵死还是 18% 宽松。
> 详细判定方法与五个变体的实测对照表见
> [09_BRAM_LUTRAM_与综合推断](09_BRAM_LUTRAM与综合推断.md)。

## 5. Zynq 的 PS 与 PL：本工程为什么最后把网络搬进 PL

Zynq-7000 一颗芯片里有两半：

- **PS**（Processing System）：双核 Cortex-A9 + 外设（UART/GEM 千兆网口/QSPI/SD/DDR 控制器）+
  **SLCR**（系统控制寄存器，管时钟与端口缓冲）+ **GP0/GP1/M_AXI_GP** 与 **HP0..HP3** AXI 端口。
- **PL**（Programmable Logic）：第 2 节里那堆 LUT/FF/BRAM/DSP。

两边怎么传数据：

| 通道 | 方向 | 位宽/频率 | 典型用途 |
|------|------|-----------|----------|
| `M_AXI_GP0` | PS → PL | 32 bit @100 MHz | 寄存器读写（本工程用它写 AXI GPIO） |
| `S_AXI_HP0` | PL → PS DDR | 本工程配 **64 bit @100 MHz** | PL 直接读写 DDR（本工程的视频通路） |
| PS GEM0 | PS ↔ 网线 | 1 Gbps | 第一版走这条路（lwIP 协议栈） |

**第一版（`v1-ps-ethernet`）**：网线插 PS 口，UDP 由 PS 的 lwIP 收，PS 把画面搬进 DDR，
PL 再从 HP0 读出来做效果。能跑，但两个问题：
① 吞吐与延迟受软件栈与 CPU 调度支配，收包与搬运互相抢；
② 画面"什么时候到齐"这件事只能靠软件判断，抖动大。

**第二版起（`v2-pl-ethernet` 之后）**：网线插 **PL 侧第二个网口**，PL 用硬件把
RGMII/ARP/ICMP/UDP 全部解析完，PS 只留一个控制面（串口命令 + GPIO）。
这样"收包 → 拼帧 → 写 DDR"整条链是纯硬件流水，延迟确定、可测、可复现。

> 这个决定的代价是：**你得自己在 RTL 里实现一个协议栈**（ARP 的 opcode、ICMP 的 checksum 回显、
> UDP 长度字段、CRC32）。这正是本工程最有含金量的部分之一，也是学习文档里篇幅最大的一章。
> 前置知识在这里：[06_以太网帧_RGMII_与PHY](06_以太网物理接口_RGMII与PHY.md)、
> [07_写一个硬件协议栈需要哪几件事](07_用硬件写协议栈.md)、
> 以及第一版为什么需要它：[05_lwIP与PS侧以太网](05_lwIP与PS侧以太网.md)。

## 6. 术语速查（后面文档会反复出现）

| 术语 | 意思 |
|------|------|
| **WNS / TNS** | Worst/Total Negative Setup，最差/累计建立时间裕量。≥0 才叫"约束满足" |
| **WHS** | Worst Hold Setup，最差保持时间裕量，必须 ≥0（违例会导致**功能随机错**，比 setup 违例更阴险） |
| **失败端点** | 时序没满足的寄存器引脚数量。0 才是干净 |
| **Logic Levels** | 关键路径上串了多少级组合逻辑 |
| **CD / net delay** | 时钟插入延迟 / 某根线的走线延迟 |
| **SLICE / SLICEM** | 7 系列里 4 个 LUT + 8 个 FF 一组；SLICEM 的 LUT 可当分布式 RAM |
| **tile** | 一个 BRAM 物理块（36 Kb） |
| **ram_style** | 综合属性，指定数组进 `block` / `distributed` / `registers` |
| **CDC** | Clock Domain Crossing，跨时钟域 |
| **bit / xsa** | 比特流 / 硬件平台包（Vitis 用它建软件工程，内含 ps7_init 与 bit） |
