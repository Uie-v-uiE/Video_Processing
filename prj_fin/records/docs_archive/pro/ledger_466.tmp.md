### #466 提交包带上 Vivado 工程与 Vitis 平台两棵整棵副本：一条 sed 分隔符的坑，和"整棵"为什么不走按引用筛

- 用户口径：GitHub 上看得见工程不算交付，**包里也要看得见**。给的三个选项里选了"包里带上工程、仓库布局不动"
  （另两个是"仓库里也移进 `board/`"——那要改 `.xpr` 里 81 条 `$PPRDIR/../src/...` 加 89 个引用文件，
  还得用 Vivado 真开一次证明还打得开；以及"仓库移、包不带"）。
- 做法：`build/make_submission.sh` §3.8c 在 `board/project/` 那一圈之后加一段
  `git -C "$REPO" archive --format=tar vivado_system vitis | tar -x -C "$TMP/board"`。
  取 **git 里的字节**而不是工作树 ⇒ 重开工程长出来的噪声（`.cache`、`.ip_user_files`、`.jou/.log/.str`）
  不会被顺手带出去；`HARD_DROP_RE` 那两条前缀**不动**（暂存树里本来就没有这两棵，这一层是额外整棵补进来），
  也不走"被活文档点名才留凭据"那套筛法——块设计与 IP 配置少一个文件就打不开。
  落地数判据：`board/vivado_system` 或 `board/vitis` 任意为 0 支 ⇒ REFUSE 且不写 `$OUT`。
- 踩到的新坑（工具层，记下来）：改口那两条 `sed` 第一次写成 `s|(^|[^/…])vivado_system/|…|g`，
  **`|` 既是 s 命令的分隔符又是 ERE 的选择符** ⇒ `sed: unknown option to 's'`。
  两种环境里的表现不一样，这一点是我实测出来的：在导出器那种 `set -euo pipefail` 下这条失败会**当场把脚本打死**
  （造一个同样的最小脚本跑：sed 报错、`AFTER-LOOP` 那句没打印、rc=1；因为失败点还在 `rm -rf $OUT` 之前，
  上一版包不会被清空，这是脚本本来就有的那层保护）；而我第一次发现它是在**交互 shell 的测试循环**里，
  没有 `set -e`，于是七行输出照打、一条都没改——差点把"看起来跑完了"当成"改口成功了"。
  改成 `s#…#…#g` 之后实测：七份文档裸路径 3/9/2/1/1/3/0 处全部命中，**连跑两遍**结果不变、`board/board` 计数 0
  （守卫 `(^|[^/[:alnum:]_.-])` 让已经带 `board/` 前缀的那一处不匹配 ⇒ 规则可重跑，这是改名规则最常见的两种坏法：漏一层、套两层）。
  形状：**测试一条 sed 规则用的 shell 必须和目标脚本用同一组选项**（`set -euo pipefail`），否则失败模式不同源。

  #465 那条教训的直接应用：往被引用的文件里加一行，代价是本地两套文档 10 条行号引用平移。
