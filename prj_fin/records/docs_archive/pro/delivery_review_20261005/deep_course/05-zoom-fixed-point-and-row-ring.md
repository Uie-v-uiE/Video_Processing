# 05 缩放：Q8 倒数步长、八档码、行环形缓存与那一格消隐地址

被测对象只有四个文件加一段顶层接线：`src/rtl/process/zoom/zoom_ctrl.v`、`src/rtl/process/zoom/zoom_fit.v`、
`src/rtl/process/zoom/zoom_mapper.v`、`src/rtl/process/zoom/zoom_snap.v`、`src/rtl/video/raw_line_delay.v`。
读完这一章要能回答：一个 3 bit 的档号是怎么变成一个 10 bit 的 Q8 步长的；为什么这个步长是**倒数**；
为什么每一步的乘加能进 20 ns；屏上那一格 `Zoom:0.75X` 报的是不是真正在用的那一个数；
原图抽头为什么要过一条行环，而环的行首那一格为什么要专门做一次预读。

---

## 1 前置知识

### 1.1 定点数与 Q 格式，以及本设计的 Q8 倒数尺度

一个无符号 10 bit 整数只能表示 0…1023。把它当作"小数点固定在 bit8 下面"的数来看，它就是 **Q2.8**：
整数部分 2 bit、小数部分 8 bit，能表示 0 到 3.996，最小刻度 1/256 ≈ 0.0039。本设计的 `inv_scale` 就是这个数，
只是它存的不是倍率 `s` 而是倒数：

```
inv = round(256 / s)        s = 256 / inv
```

所以 `256 = 1.00×`、`512 = 0.50×`、`128 = 2.00×`。这个约定在 `src/rtl/process/zoom/zoom_ctrl.v:2-4` 的文件头
就写死了，而参数边界 `INV_LO`、`INV_HI`、`STEP` 在
`src/rtl/process/zoom/zoom_ctrl.v:6-8`（256 / 512 / 2）。

为什么存倒数：缩放是**逆映射**（见 1.2），逆映射要做的是"这个显示像素往源图走多远"，
那个"多远"就是 `s` 的倒数。如果存 `s`，每一步都要一次 `1/s`；存 `inv` 就把除法搬到了**编译期**——
八档表里的每个数都是 `256/s` 事先算好的常数（`src/rtl/process/zoom/zoom_ctrl.v:40-56`），
运行时一次除法都没有。

### 1.2 为什么是逆映射（屏幕→源），不是正映射（源→屏幕）

正映射：对每个**源**像素算它落在屏上哪，然后把值写过去。这条路的坏处在输出侧：
放大 2.00× 时相邻两个源像素之间在屏上有 4 个显示列的空洞，得靠人补；
缩小 0.25× 时多个源像素被挤进同一个显示列，后写的覆盖先写的，输出的像素集合由源顺序决定，
硬件上还得有一个"每个输出格写几次"的计数。

逆映射：对每个**显示**像素解出它该取源图哪一格。这条路的性质是"每个输出格恰好被算一次"——
空洞与重叠从结构上消失，代价是源坐标一般是小数，于是必须有小数权重（这就是第 07 章的双线性）。
本设计选的就是逆映射：`src/rtl/process/zoom/zoom_mapper.v:2` 的文件头写的是
"右屏无极缩放逆映射：屏幕 (x,y) → 源图 (sx,sy)"，而
`src/rtl/process/zoom/zoom_ctrl.v:38-39` 把这条性质讲完了——
"inv 变小只是采样窗收进画面内部（不越界），inv 变大则四周填黑 —— 两种都不需要动 mapper"。

### 1.3 floor 与 frac 必须描述同一格

算术右移 `>>>` 是**朝 −∞ 取整**，取下来的低位就自然是 `[0,1)` 的小数；
而 `/256` 与 `%256` 在负数上朝 0 截断，两者会把同一个小数拆到**相邻两格**上去。
这条纪律写在 `src/rtl/process/zoom/zoom_mapper.v:90-91`：
"floor 与 frac 必须自洽：`>>> 8` 是朝 −∞ 取整，余下的低 8 位正好是 [0,1) 的小数 ⇒ x_out 与 frac_x
指的是同一条数轴上的同一格（换成 `/256` + 取余就会在负数上错一格）"。

屏幕中心以左 `xp = x − W/2` 是负数，所以这一半画面正好踩在这条上。中心两侧差一格的后果
不是"糊一点"，是一条可见的错位——第 05 章末尾的验证段里 M1 判据就是专门扫中心两侧的。

### 1.4 行缓存与流式视频：为什么多抽头要一条"环"

本设计的原图抽头与处理抽头**不是**从一个可随机寻址的存储里各读一次的：像素流是从帧缓存按
`mapper(cx, cy_r)` 一路读出来的，出来之后要进效果链（3×3 窗口滤波，
见 `src/rtl/process/proc_pipeline.v:27`，`OFF_LINES = 4`）。窗口滤波在收到第 y 行时才**算得出**第 y−1 行，
这是因果性，不是实现偷懒。于是链子出口站在显示行 y，链子入口那一拍站的是 y+4 的内容 ⇒ 同拍摆出来的
"原图抽头"比"处理抽头"**超前 4 行**。要逐像素混成一条缝，就得把原图那一路整体补延后 4 行。

延后 4 行不能用"4 级 shift register 串起来"——那是 4 行 × 每行 1344 拍的寄存器量。行缓存的做法是
**一块 1W1R 的环形 RAM**：一行只有 1024 个有效列，所以深度 = 环深 × 1024，
写槽用 `y` 的低几位，读槽用 `(y − LINES)` 的同一几位。写本行、读 LINES 行之前的同一列 ⇒
延迟恰好 `LINES` 行 **+ 1 拍**，列一格不偏。那多出来的 1 拍正是本章 §5 的病根。

### 1.5 一个码怎么变成 Q-format 步长（双向）

正向：`zsel[2:0]` → `tbl(zsel)` → `inv_scale`（Q8 倒数）→ mapper 每视口列推进 `inv/256` 源列。
注意分母是 256 而不是 512：mapper 吃的是**视口列** `cx = x >> 1`
（`src/rtl/top/pl_video_top.v:242`），一个视口列在屏上占两个显示列，所以**每显示列**推进 `inv/512` 源列。

反向：`inv_used` → `zoom_code`。这是"量化"，做法是拿 `inv` 与**相邻两档的中点**比大小
（`src/rtl/process/zoom/zoom_ctrl.v:75-84`），7 个常数比较、优先级链，寄存一拍再给 OSD。
下表是把两边都对齐后的实际数字（表值来自 `zoom_ctrl.v:43-53`，阈值来自 `:76-83`）：

| zsel | `tbl` 值 | 名义倍率 | 每视口列源步长 | `zoom_code` 下界 |
|---|---|---|---|---|
| 0 | 1023 | 0.25×（实为 0.2502×） | 3.996 | ≥ 900 |
| 1 | 776 | 0.33× | 3.031 | ≥ 644 |
| 2 | 512 | 0.50× | 2.000 | ≥ 427 |
| 3 | 341 | 0.75× | 1.332 | ≥ 299 |
| 4 | 256 | 1.00× | 1.000 | ≥ 224 |
| 5 | 192 | 1.33× | 0.750 | ≥ 182 |
| 6 | 171 | 1.50× | 0.668 | ≥ 150 |
| 7 | 128 | 2.00× | 0.500 | 其余 |

两张表能互相对上不是巧合：`code(TBL[i]) == i` 逐档是一条台架判据（`sim/tb_v94_zoom_sel.v` 的 T3），
理由写在 `src/rtl/process/zoom/zoom_ctrl.v:36-37`——表值代回自己那一档必然落在自己的区间里。
呼吸只在 `[256, 512]` 走，因此呼吸能到达的 `zoom_code` 只有 0…4 五个。

## 2 原理拆解（把数带进去）

### 2.1 画幅、节奏与时钟

| 量 | 值 | 出处 |
|---|---|---|
| 源画幅 | 512 × 300 | `src/rtl/top/pl_video_top.v:9-10`（`IMG_W`/`IMG_H`） |
| 面板 | 1024 × 600，H_TOTAL 1344，V_TOTAL 625 | `src/rtl/video/video_timing_1024x600.v:3-4`（两行加法注释）；端口参数 `:18-21` |
| 像素钟 | `clk_pix` = 50 MHz，周期 20 ns | `src/rtl/clocks/clk_gen.v:21`（`CLKOUT0_DIVIDE_F (20.000)`，VCO 1000 MHz） |
| 一个显示行 | 1344 拍 = 26.88 µs | 1344 × 20 ns |
| 一帧 | 625 行 = 16.8 ms | 1344 × 625 × 20 ns |
| 视口 | 每源列占 2 显示列 | `src/rtl/top/pl_video_top.v:238-242` |

`src/rtl/clocks/clk_gen.v:24` 另有一路 `CLKOUT1_DIVIDE (4)` = 250 MHz（4 ns）。**本章所有算术都不在快域**：
缩放链、行环、双线性读口全部挂在 20 ns 的 `clk_pix` 上。为什么强调这个，第 07 章会给一次实测代价。

### 2.2 八档逆步长在屏上的实际覆盖

`inv = 1023`（0.25×）：`sx = 256 + floor((cx−256)·1023/256)`。要 `sx ∈ [0,512)` 就要求
`|cx−256| ≤ 64` ⇒ 只有 129 个视口列在图内 = 258 个显示列，约是 1024 的四分之一
（表值 1023 而不是 1024，所以是 0.2502× 而不是 0.25×，见 §2.5）。
中心两侧各 63 个视口列越界回黑（`src/rtl/process/zoom/zoom_mapper.v:103-108` 把 `oob` 置起并把
`x_out/y_out/frac_x/frac_y` 一起清 0）。左右连长相等这件事由 `sim/tb_v96_zoom_scan.v:178` 的 M4 判。

`inv = 256`（1.00×）：`sx = cx`，恒等映射。**这是本章第一个必须钉住的 corner case**：
`raw_xs = xp_s1 * 256` 低 8 位必定是 0 ⇒ `frac_x` 恒 0，双线性在这一档自动退化成最近邻。
`sim/tb_v96_zoom_scan.v:155` 的 M1b 就是"1.0x 必为恒等映射"。

`inv = 128`（2.00×）：`sx = 256 + floor((cx−256)/2)`，`cx` 走满 0…511 时 `sx` 只走 128…383
⇒ 采样窗收进画面内部、四周**不**越界，一个源列铺 2 视口列 = 4 显示列。放大不产生黑边，这条是
逆映射方向带来的，不需要 mapper 里任何特例。

### 2.3 呼吸的量级

`STEP = 2`（`src/rtl/process/zoom/zoom_ctrl.v:8`）且只在帧首走一步 ⇒ 单程 256→512 是 128 帧 = **2.15 s**，
来回一趟 4.3 s。每步 `inv` 变 2 ⇒ 每视口列步长变 2/256 = 0.0078 源列 ⇒
屏上中心右 64 视口列那一格的源列每步漂 0.5 格。台架把这条量化成了 M6：
以步长 8 从 256 走到 512 共 32 步，要求每步漂移 ≤ 2 且整趟累加 == 64
（`sim/tb_v96_zoom_scan.v:217`、判据在 `:236`）。把 `>>>` 写成朝 0 截断，这一条当场红。

### 2.4 三种倍率来源与"唯一出处"

`inv_used` 只有一个出口，由两级决定：

```
inv_raw   = fit_en ? inv_fit : inv_scale            // zoom_ctrl.v:64
rot_clamp = rotate_en && (inv_raw < inv_fit)        // zoom_ctrl.v:72
inv_used  = rot_clamp ? inv_fit : inv_raw          // zoom_ctrl.v:73
```

* **呼吸**（`!fit_en && !manual`）：`inv_scale` 每帧首 ±2，走带内。
* **手动**（`!fit_en && manual`）：`inv_scale <= tbl(zsel)`，也只在帧首换（
  `src/rtl/process/zoom/zoom_ctrl.v:105-111`）。
* **拟合**（`fit_en`）：整条 `inv_scale` 链**旁路**——`fit_en` 那一支一个字节都不写 `inv_scale`
  （`src/rtl/process/zoom/zoom_ctrl.v:96-100`），所以关掉拟合时呼吸/手动从原位置接着走，不跳档。
* **旋转钳**（`rotate_en`）：不许旋转时放大到画外，取"较大的那个 `inv`"（画面较小的那一个）。

`zoom_active` 与 `zoom_code` 一律看 `inv_used`，不看 `inv_scale`。这条在
`src/rtl/process/zoom/zoom_ctrl.v:58-59` 与 `:109-111`、`:139-140` 各写了一遍理由：
"比较的对象是 `inv_used`（真正喂给 mapper 的那一个），不是 `inv_scale`：开拟合时后者还停在呼吸/手动的
位置，拿它分区就会'屏上写 1.00x、画面上是 0.52x'"。

### 2.5 `zoom_fit` 的算术与两处截断

"旋到哪个角度就缩到刚好装得下"。外框 `W' = s(W|cos| + H|sin|)`、`H' = s(W|sin| + H|cos|)`，
要求 `W' ≤ W` 且 `H' ≤ H`，代 `s = 256/inv` 写开就是两条 `inv` 下界，取**较大者**
（推导在 `src/rtl/process/zoom/zoom_fit.v:3-7`）。运行时不许有除法器，于是 `/W`、`/H` 折成
"乘一个 elaboration 常数 + 定长移位"：

```
REC_W = round(2^20 / 512) = 2048      // zoom_fit.v:29
REC_H = round(2^20 / 300) = 3495      // zoom_fit.v:30
nx = 512·C + 300·S                    // zoom_fit.v:32
ix = (nx * REC_W) >> 20               // zoom_fit.v:44
```

带进去的几个真实数（按上式手工算，`C/S` 取表值）：

| angle | C | S | nx | ny | ix | iy | imax | `inv_fit` |
|---|---|---|---|---|---|---|---|---|
| 0° | 256 | 0 | 131072 | 76800 | 256 | 255 | 256 | **258** |
| 45° | 181 | 181 | 146972 | 146972 | 287 | 489 | 489 | **492** |
| 90° | 0 | 256 | 76800 | 131072 | 150 | 436 | 436 | **439** |
| 90° 精确值 | 1 | 0 | — | — | — | — | — | 需 300/512 ⇒ inv≈437 |

余量那一步是 `fit_raw = imax + (imax >> 8) + 2`（`src/rtl/process/zoom/zoom_fit.v:50`），
理由写在 `:48-49`：Q8 三角表每项最多差 0.5 LSB ⇒ `inv` 最大差 `(W+H)/2/H ≈ 1.35`，
`(imax>>8)+2` 稳过它，代价是在 0° 多缩 2/256。台架把这个容差钉成"0° 必须落在 256…259"
（`sim/tb_v100_fit_rot.v:127`）。

两处截断要认清：

1. `imax = (ix > iy) ? ix[9:0] : iy[9:0]`（`src/rtl/process/zoom/zoom_fit.v:46`）取的是低 10 bit。
   在本画幅下 `imax` 的上界是 `256·√(512²+300²)·3495 / 2^20 ≈ 504`，永远不到 1024，截断不咬人；
   改 `IMAGE_H` 之前这一条要重算。
2. `fit_raw` 是 11 bit，`fit_c = (fit_raw > 1023) ? 1023 : fit_raw`（`:51`），
   然后 `inv_fit <= fit_c[9:0]`（`:59`）。1023 那一夹在本画幅下**不会触发**（上界 ≈ 507），
   它是给参数改动留的保险，不是运行路径。

真正的 10 bit 天花板在八档表那一头：档 0 写的是 `10'd1023` 而不是 `1024`，因为 1024 会回绕成 0，
画面上变成"无限大"而不是 0.25×（`src/rtl/process/zoom/zoom_ctrl.v:44-46`）。

### 2.6 拟合链为什么要分两拍

`src/rtl/process/zoom/zoom_fit.v:34-38` 给了实测口径：`angle → inv_fit` 一拍做完是 **15 级、含两个 DSP48，
slack 只剩 +1.843 ns**（当时全设计第三差）。这条链的输入一帧才变一次，多一拍落在消隐里屏上看不见，
换来的是一整段余量。代价是拟合值现在**晚两拍**跟上新角度——第 06 章讲角度翻转点时会用到这个"两拍"。

## 3 代码逐段分析

### 3.1 `zoom_ctrl`：组合侧（倍率的唯一出处）

端口清单：`zsel`/`manual` 在 `src/rtl/process/zoom/zoom_ctrl.v:13-14`，
`rotate_en`/`fit_en`/`inv_fit` 在 `:22-24`，三个输出 `inv_scale`（内部链）、`inv_used`（唯一读数）、
`rot_forced`（`#93` 的旗标）在 `:26-31`。

`inv_raw` → `rot_clamp` → `inv_used` → `code_nxt` 这四条是纯组合
（`:64`、`:72-74`、`:75-84`），全部不进这条模块的时序块。`zoom_code <= code_nxt` 在
`src/rtl/process/zoom/zoom_ctrl.v:95`，并且和 `inv_scale` 同一个 `always` 驱动——这一条不是风格：
`:93-94` 写着"与 inv_scale 同一个块驱动：多驱动 net 会让综合扔掉逻辑那一侧，见 ISSUES #61"。

钳制为什么在 `zoom_ctrl` 里而不在顶层再 mux 一次，文件头 `src/rtl/process/zoom/zoom_ctrl.v:16-21`
给了具体形状："顶层再 mux 一次就会出现'屏上那一格与真正在用的 inv 不是一回事'"。
这一条有实物凭据：先写过一版顶层钳制，喂得到 mapper/lane23/`status`，**喂不到 `zoom_code`**，
于是回退（`开发台账` 的 #162 第二节，6529 行起）。

`rot_forced` 的意义在 `:31-32`：它是"这一帧生效的倍率是被旋转钳出来的"，顶层把它并进 OSD 的 `(Fit)`
标记，见 `src/rtl/top/pl_video_top.v:1011` 的 `zoom_fit_en | rot_forced`。屏上因此不会说假话。

### 3.2 `zoom_ctrl`：时序侧的四个分支

`always` 块在 `src/rtl/process/zoom/zoom_ctrl.v:86-143`。复位写 `inv_scale = INV_LO`、`dir = 0`、
`zoom_active = 0`、`zoom_code = 3'd4`（`:87-91`），即上电 1.00×。分支优先级（同一个 `else if` 链）：

| 序 | 条件 | 行为 | 行 |
|---|---|---|---|
| 1 | `fit_en` | 不动 `inv_scale`；`zoom_active <= (inv_used != INV_LO)` | `:96-100` |
| 2 | `!enable` | 全清：回 `INV_LO`、`dir=0`、`zoom_active=0` | `:101-104` |
| 3 | `manual && frame_start` | `inv_scale <= tbl(zsel)`；**`dir` 故意不动** | `:105-111` |
| 4 | `frame_start` | 呼吸（含带外回归） | `:112-137` |
| 5 | 其余每一拍 | 只跟 `zoom_active <= (inv_used != INV_LO)` | `:138-141` |

分支 4 内部再分三支，读的时候容易漏掉第一支：

```
if (inv_scale > INV_HI) begin          // zoom_ctrl.v:117
    inv_scale <= inv_scale - STEP;     // :118
    dir       <= 1'b1;                 // :119
end else if (!dir) …                   // :120-127  inv 上升（画面缩小）
end else              …                // :128-136  inv 下降（回到原始）
```

第一支是**带外回归**。手动档可以停在呼吸带之外（2.00× 在下方 128、0.25× 在上方 1023）。
原来的写法在 `inv > INV_HI` 时直接写 `inv <= INV_HI`，于是 1023 → 512 一帧跳掉半幅，
用户看到的是"画面弹一下"。现在改成每帧朝带回里走一步，进带之后原有逻辑接管
（理由在 `src/rtl/process/zoom/zoom_ctrl.v:113-116`）。台架这一族是 T5/T7
（`sim/tb_v94_zoom_sel.v` 头 16-19 行的判定清单）。

上下界那两支各自都做了"贴边不越界"的处理：上升支先判 `inv_scale + STEP >= INV_HI` 就钉 `INV_HI`（`:122-123`），
下降支先判 `inv_scale <= INV_LO + STEP` 就钉 `INV_LO` 并把 `dir` 清 0（`:130-132`）。
所以带内永远不会出现"越过边界再折回"的一拍。

分支 3 的"手动与呼吸同一个节拍，只在帧首换"（`:105-107`）针对的是另一种写法：手动换档当拍就生效
⇒ 一帧之内上半屏是新一档、下半屏是旧一档。`dir` 不动这件事是"从手动切回自动时从当前 inv 继续朝原方向走"。

### 3.3 `zoom_mapper`：三级流水与位宽账

这是本章唯一逐像素跑的算术。位宽账先列清楚：

| 信号 | 宽度 | 值域 | 出处 |
|---|---|---|---|
| `x_in` / `y_in` | 12 | 0…1023 / 0…599，但顶层只喂视口列 0…511 与源行窗口 | `src/rtl/process/zoom/zoom_mapper.v:13-14` |
| `xp` / `yp_math` / `yp_disp` | 13 signed | ±256 / ±300 | `:29`，`:32-34` |
| `sin_v` / `cos_v` | 10 signed | −256…256 | `:21-23` |
| `inv` | 11 signed | 0…1023（`:25` 注释"512 需 11-bit 有符号才为正"） | `:26` |
| `xr_m` / `yr_m` | 24 signed | 13+10 = 23 位乘积、加法后再 1 位 | `:39`，`:47-50` |
| `rot_xs` / `xs_pix` 等 | 32 signed | 24×11 = 35 位截到 32（够用，见下） | `:58-61` |
| `frac_x` / `frac_y` | 8 | 0…255 | `:18-19` |

**s0（`:31-36`）**：中心偏移与 Y 翻转。`yp_math = H/2 − y`（数学坐标 Y 朝上），
同时**并存**一份 `yp_disp = y − H/2`（`:34`）。为什么不旋转时也用 math 那一份：不旋转的支路走的是显示系，
`yp_disp` 就是给它的；而 `yp_math` 只在 `rot_s0` 为 1 时被选中（`:44`）。`rotate_en` 也跟着延一拍成 `rot_s0`（`:35`）。

**s1（`:42-55`）**：只有 `rot_s0` 为真时才做那两个乘加，否则把 `xr_m/yr_m` 清 0（`:52-53`）。
这不是"省时间"，是**省 DSP**：非旋转态这两条 13×10 的乘积根本不参与，工具能把它们从乘法器映射里省出去。
式子本体：

```
xr_m = xp·cos + yp_math·sin          // zoom_mapper.v:47-48
yr_m = −xp·sin + yp_math·cos         // zoom_mapper.v:49-50
```

`{11{xp[12]}}` 那两处位复制是把 13 bit 符号数扩到 24 bit 再乘（`:47`），$signed 保证是**有符号**乘。

**s2（`:58-66`）**：乘 `inv` 并定点。这里两条支路的 Q 格式**不同**，是全章最容易看错的地方：

* 缩放支：`raw_xs = xp_s1 * inv` ⇒ Q8，取整用 `>>> 8`，小数取 `[7:0]`。
* 旋转支：`rot_xs = xr_m * inv` ⇒ Q8 × Q8 = **Q16**，取整用 `>>> 16`，小数取 `[15:8]`。

```
wire signed [31:0] xr_pix = rot_xs >>> 16;   // zoom_mapper.v:63
wire signed [31:0] xs_pix = raw_xs >>> 8;    // zoom_mapper.v:65
wire [7:0] fx = rot_s1 ? rot_fx : raw_xs[7:0]; // :92
```

`rot_fx = rot_xs[15:8]`（`:75`）。纵向麻烦得多，因为多了一次 `Y_disp = C − Y_math` 的翻号，
floor 必须跟着改（`:70-73` 那一段注释推导）：`Y_math = yr_pix + f/256`，
所以 `Y_disp = (C − yr_pix − 1) + (256 − f)/256`，`f = 0` 时是 `C − yr_pix` 且小数 0。
`#189` 之后判定"有没有小数"要看**完整 16 位**（`:81-86`）：

```
wire [15:0] rot_fy16     = rot_ys[15:0];                    // :81
wire        rot_fy_low   = (rot_fy16[7:0] != 8'd0);         // :82
wire [8:0]  rot_fy_ceil  = {1'b0, rot_fy16[15:8]} + (rot_fy_low ? 9'd1 : 9'd0);  // :83
wire [8:0]  rot_fy_9     = 9'd256 - rot_fy_ceil;            // :84
wire        rot_y_has_frac = (rot_fy16 != 16'd0);           // :86
```

`f ∈ (0, 1/256)` 时 `ceil` 恰为 1 ⇒ 权重 255 且**必须**减那一格。只看高字节会把它读成"没有小数"，
症状是沿角度方向的稀疏"错一行"鬼影，实测发生率 ≈ 0.27 %（扫 3726 个旋转态像素命中 10 个、全错），
数字与修法见 `src/rtl/process/zoom/zoom_mapper.v:76-80` 与 `开发台账` 的 #189 段（9255 行起）。
`sy_c` 里那一格减法就在 `:87`。修完之后 `:93-94` 又钉了一条反向的坑：`fy` 不许再 `~+1`，
因为翻转已经在 `rot_fy` 里做过了，再翻一次就是翻两次。

**输出级（`:96-116`）**：越界判据在 `:103`——
`sx_c < 0 || sx_c >= IMAGE_W || sy_c < 0 || sy_c >= IMAGE_H`，四个都不满足才把 `sx_c[11:0]` 打出去，
同时把 `oob` 清 0、把 `fx/fy` 交出。越界那一支把 **frac 也清 0**（`:104-108`），
这样下游读到的是一格干净的 0，不会出现"像素是黑的但小数在动"。

复位那一支（`:97-102`）与越界那一支形状相同，`oob <= 1'b1`：上电第一拍就是"越界"，这是刻意的保守值。

### 3.4 `zoom_snap`：准静态总线 + 晚 8 拍的发沿

跨时钟域的 20 bit 打包在 `src/rtl/process/zoom/zoom_snap.v:27`：

```
wire [19:0] in_bus = {rot_forced, zman, zsel, zoom_code, zoom_active, zoom_dir, inv_scale};
```

位序 = lane23 的位序，而 `rot_forced` 放在**最高位**，下面 19 位一个位置都不动 ⇒
现有上位机解码照旧（`:25-26`）。两条不变量（`:5-7`）：

1. `bus` 只在帧首整拍换（`:37-40`），换完至少保持一帧 ≈ 16.7 ms ⇒ 满足 `snap_cross` 的准静态前提。
2. `bus_tog` 对每一次**真实变化**恰好翻一次，且翻在总线稳定之后——晚 8 个像素周期（`:41-44`，
   `dly` 是一个 8 位移位链，`:36` 把 `frame_start` 往里灌）。

`pend`（`:38`）是"这一帧换了值才发沿"。不变化时一个沿都不发——呼吸档每帧都在动，那属于
`zoom_active = 1` 的正常路径，计数判据由 `sim/tb_v95_zoom_snap.v` 的 Z1/Z3/Z7 三条分别钉住
（没换值不发、8 档发 8 个、40 帧呼吸发 40 个）。早一拍发都不行：那发的是上一帧的值，
目的域会永久落后一档，末态检查会红（`:6-7`）。

顶层接线在 `src/rtl/top/pl_video_top.v:652-658`（喂进去的 `inv_scale` 端口接的是 `inv_used`，见 `:655`），
过域在 `src/rtl/top/pl_video_top.v:674-678` 的 `snap_cross`，出端口在 `:688` 的 `assign dbg_zoom`。
心跳位 `z_hb_tog` 单独一个触发器（`src/rtl/top/pl_video_top.v:665-669`），
理由写在 `:661-664`：共用现成的翻转位会让一个发射触发器扇出到两组目的域同步器，
`cdc.rpt` 立刻提 **CDC-11 Critical**，同一个工程里为这件事红过两次。

### 3.5 顶层坐标接线：`cy`、`y_req_row`、`cy_r` 与那个偶数约束

三条式子必须连着看：

```
cy          = (y >> 1) < IMG_H ? (y >> 1) : (IMG_H - 1);   // pl_video_top.v:243
y_right_adv = y + pipe_off_rows + BILIN_ROWS;              // pl_video_top.v:276
y_req_row   = y_right_adv >> 1;                            // pl_video_top.v:277
cy_r        = (y_req_row >= IMG_H) ? (y_req_row - IMG_H) : y_req_row;  // pl_video_top.v:284
```

* `pipe_off_rows` 是效果链自己报出来的滞后行数（`src/rtl/process/proc_pipeline.v:44`、`:48`，
  值 4，`:27`）。"把数据提前"不可能，只能"把地址提前"，而且提前量必须加在 **mapper 的显示行输入**上
  而不是输出的源行上——链子的滞后发生在显示栅格上，缩放/旋转之后"源行差 4" ≠ "显示行差 4"。
  这段理由在 `src/rtl/top/pl_video_top.v:244-248`。
* `BILIN_ROWS = 2`（`:250`）是双线性读口在行方向额外晚的那一对显示行。
  **必须是偶数**，因为 `row0 = ~y[0]` 定的是"对"的奇偶，奇数会让一对分属两个源行 ⇒ A/B 错行（`:249`）。
* `cy_r` 那个减法是**取模的替代**：读行提前 ⇒ 本帧末尾几行的请求行会越过 `IMG_H`，绕回之后
  `y_req_row` 最大 302，所以"减一次就够"，不需要除法器/取模（`:281-283`）。
  钳到 `IMG_H-1` 而不是绕回会把 #92/#93 那十二格暴露出来；绕回后仍走一遍逆缩放，
  所以小于 1.00× 时不多出一条顶带（`:278-280`）。

`src/rtl/top/pl_video_top.v:343-349` 是唯一一处 mapper 例化，喂进去的是 `inv_used`、`angle`、
`rotate_active`、`cx`、`cy_r`。注意**顶层没有第二份逆映射**，也没有"左右两屏各一套源坐标"：
`:336-338` 写明旧的 `cx_q*`/`sx_l` 那一套已删，那是"两屏各画一整幅"时代的遗产。

### 3.6 `raw_line_delay`：行环本体

参数：`LINES` 唯一合法出处是 `u_pipe.OFF_LINES`（`src/rtl/top/pl_video_top.v:781`），
`W = 2*IMG_W = 1024`、`DW = 17`（`:788`，越界标签与像素打包过同一条环，理由在 `:782-786`）。

几何量在 `src/rtl/video/raw_line_delay.v:41-43`：

```
RLOG  = clog2(LINES + 1)     // LINES=4 ⇒ 3 ⇒ 8 个行槽
CWID  = clog2(W)             // W=1024 ⇒ 10
DEPTH = (1 << RLOG) * W      // 8192 格
```

环深取 `2^RLOG ≥ LINES+1`，于是 `mod` 就是**切位**，运行时没有除法/取模（`:37`）。
17 bit 仍在 RAMB36 的 18 bit 宽度模式里 ⇒ 一块 BRAM 都不多要（`:15-16`，并且 `:16` 明确这句
要在构建后的 `utilization.rpt` 上核对，不许停在注释；本轮读数见 §5.6）。

读写在 `src/rtl/video/raw_line_delay.v:80-83`：

```
if (de) mem[widx] <= d_in;   // 写：本行本列
q <= mem[ridx];              // 读：LINES 行之前的同一列，同拍 ⇒ 只多 1 拍、列不偏
```

`widx = {wslot, x[CWID-1:0]}`、`rslot = y[RLOG-1:0] − LINES`（`:55-57`）。
`LINES == 0` 走 `g_pass` 那一支组合直通，一个 RAM 都不推出来（`:46-49`）。

## 4 那一格消隐地址：可见缝的根因与被否决的两种修法

### 4.1 现象与量出来的值

屏的左边缘有一条跟着画面走的细线，随缩放变宽，在 0.5–1.0× 复现、2.0×/0.25× 看不到。
顶层探针（P100）量到的是：本体行第 0 列，原图抽头摆的是"源行 ✓、**源列 160 ✗**"
（`src/rtl/video/raw_line_delay.v:58-62` 的注释把这条写成了硬件事实，其中 `x[CWID-1:0]` 数到 319 与
"源列 160 = 显示列 320 那一格"都在那五行里；档案见 `开发台账` 的 #102 第二刀，4734 行起）。

### 4.2 机制

一个显示行 1344 拍而有效列只有 1024 ⇒ 尾部 **320 拍是行消隐**，而 `x` 自由数到 1343，
于是 `x[CWID-1:0]` 在消隐里从 0 数到 319。RAM 读出的是**上一拍发出去的那个地址**
⇒ 下一行第一个有效列摆出来的恰好是消隐期最后那个格子的内容。一帧 600 行、行行都有一格。
这段推导在 `src/rtl/video/raw_line_delay.v:58-62`，值是按 160 那个读数对上号的，不是推出来就收工。
"为什么只有第 0 列坏"记在档案里（`开发台账` #102 第二刀，4734 行起）：
行内每一列读的都是上一拍的地址，而那一拍的地址是合法的。
另有一族相邻现象不要混：头 `LINES` 行读到的是 RAM 旧内容，落在帧首那几条线
（`src/rtl/video/raw_line_delay.v:63`），与"最上面 4 行没有上一行可算"同族，不是新缺陷。

### 4.3 修法：掉进消隐那一拍做一次预读

```
wire bl_head   = (!de && v);                              // raw_line_delay.v:73
wire rslot_rd  = bl_head ? (rslot + 1'b1) : rslot;        // :74
wire x_rd      = bl_head ? {CWID{1'b0}} : x[CWID-1:0];    // :75
wire ridx      = {rslot_rd, x_rd};                        // :76
```

`bl_head` 就是"`de` 刚掉下去"那一拍（`:68` 注释：每行只有一次，竖消隐里没有）。
那一拍的 `y` 还是**刚结束的那一行**（`y` 在 h_cnt 回绕时才加一），所以下一行的槽是 `rslot+1`。
数据晚两拍回到 `q`，`:91-92` 用 `look` 把它锁进 `head_q`，输出 mux 只在 `de && x[CWID-1:0] == 0` 选它
（`:95`）。中间每一列一个比特都没变，行末最后一列原本那次读也没动。
帧头也顺带对了：`(599+1−LINES) mod 8 = 4 =` 第 0 行要的槽（`:72`）。

寄存纪律在 `:84-85`：`look/head_q` 只许在**一个** `always` 里写——那个 RAM 块没有异步复位
（RAM 与其读出本来就不复位），把同一根寄存器分给两个进程综合会直接报多驱动。

### 4.4 两种"看起来更简单"的改法，都已经被实测否决

写在 `src/rtl/video/raw_line_delay.v:77-79`，原文是"两种'看起来更简单'的办法都是错的，别再试"：

1. **把读出再打一拍** ⇒ 每一列都推后一格，正是 #92 那族整列错位，顶层 C1c/C2b 立刻红。
2. **消隐期读地址一律钳到 0** ⇒ 帧头那一行仍错一行。原因很具体：`V_TOTAL = 625` 不是环深 8 的整数倍，
   竖消隐那 25 行把槽位相位挪走了。

第一条被否是因为它把"晚一拍"这件事从时序问题伪装成列号问题；第二条被否是因为它假设了
"消隐不改变行的槽位相位"，而这个假设在 625 行的场上不成立。这两条都是**先改后量到红**才登记的，
不是推理。

### 4.5 最初的结构错误：串 `line_cache`

第一版行延后是把 4 个 `line_cache` 串起来。串 N 个 = 延后 N 行**又**多花 N 拍 ⇒
传递函数是 (行 − 4, 列 − 4)，整列偏 4 格。这种错在**模块级滤波台架上看不见**（滤波台架不判列号），
所以被 `sim/tb_v100_raw_delay.v` 的 T1 当场打掉（`src/rtl/video/raw_line_delay.v:5-7`）。
`src/rtl/video/line_cache.v:2-3` 现在自己就写着"本树无人例化……遗留件，别按它找结构"。

### 5.5 `sim/tb_v100_raw_delay.v` —— 行环本体，含那一格

`T1` 稳态逐格对齐、列一格不偏（`sim/tb_v100_raw_delay.v:201`）；`T5` 跨过 `2^RLOG = 8` 的槽位回绕仍对齐；
`T3` de 链与数据链等长；`T4` `LINES = 0` 必须组合直通；`T6` 覆盖面地板（样本数不够就是空窗假绿）；
**`T7` 行首第一格 = 本行第一列（不是消隐期地址的格子）**（`:227`）、
`T7k` 行内其余列一格都不许动（预读只许占用消隐那一拍）（`:230`）。
T7/T7k 用真实光栅（`HT = 80 = 64 有效 + 16 空拍`、有效行数 8 = 环深的整数倍）——
原来那三条抓不到 #102，因为它们的"消隐"只有 2 拍（`:123-127`）。

三跑对照凭据 `build/evidence/r80_ring_head_module_cred.txt`：修复后 T1/T3/T4/T5/T6/T7/T7k 全绿；
变异 `assign d_out = q;`（关掉预读）⇒ **只有 T7 红，16/16**，而行内 1008 格仍 0 错
⇒ 红恰好落在被修的那一格，判据没有连带伤到别的列。
台架自己交的另一笔学费也写在同一份文件里：第一版 T7 把检查放在"喂完之后第二拍"，
那一拍量到的是 `cell k`，行首那一格从来没被看到 ⇒ **变异也绿 = 空判**。

### 5.6 `sim/tb_v98_top_seam.v` —— 唯一例化顶层的那把尺子

DDR 帧是坐标图（每个像素值 = `{1'b1 非黑标志, row mod 128, col mod 256}`），
判"屏上任意一点解出的 (row, col) 与它该来自哪里一减为零"。与本章直接相关的：

| 判据 | 位置 | 测什么 |
|---|---|---|
| C1i | `sim/tb_v98_top_seam.v:1410` | 读口相位与 src 同拍（唯一 k 成立） |
| C1g | `:1412` | 视口列：`src == x_d[2] >> 1`，样本 > 50000 |
| C1h | `:1416` | 视口行：`src == wrap((y_d[2] + OFF + BILIN) >> 1)` |
| C2/C7 | 头 24 行索引，扫描用八档 1023/776/512/341/256/192/171/128 | 八档缩放的列/行等于定义 |
| C5c | `:1563` | 帧头不是上一帧的尾巴（`#167`/`#98` 那一族） |
| C8a/C8b | `:1572`、`:1575` | 本体行第 0 列：原图抽头与处理抽头各自的 (源行 = y>>1, 源列 = 0) |
| C12a/b/c | `:1885`、`:1887`、`:1883` | 每帧换角时，帧头请求拍与主体行吃**同一个**角度 |

**C8 就是 #102 那条线的顶层判据**：它修完就再不需要上板做 A/B（`开发台账` #102 第二刀的
"顶层新增 C8"段）。r80 落地后的读数：C8a/C8b 各 1178 格、0 不符。
⚠ 门禁第 15 项在 r80 那一轮仍是红的，红的那一条正是 C5c（`开发台账` 记为"r80 不冻结"），
所以"行环那一格修好了"不等于"帧头全部修好了"——那是第 06 章的角度翻转点。

资源侧的核对（`utilization.rpt` 是**扁平汇总**，没有逐实例行，所以只能核对总量不能归因）：
本轮读的 `build/utilization.rpt`（Design State: Routed，Oct 4 04:37 那一版）给的是
Block RAM Tile 95.5 / 140、RAMB36 93、RAMB18 5、Slice LUTs 14154、DSP48E1 19。
"17 bit 仍在 RAMB36 的 18 bit 宽度模式里 ⇒ 一块不多要"这句只能核对到"总量没涨"这一层，
归因到 `u_raw` 需要 `report_utilization -hier`，本轮未做，不写成结论。
