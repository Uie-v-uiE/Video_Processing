# 大块搬运与缓存一致性：封装的最小形状与按症状分诊

两个方向**不对称**，这是所有坏点的根：数据从缓存走向内存、和从内存走向缓存，
要做的是两种不同的维护操作。方向搞反时症状很像，修法完全不同。

## 适用场景

- 处理器侧写完一块内存，让搬运引擎读它 ⇒ 引擎读到旧数据或半新半旧。
- 搬运引擎写完一块内存，处理器读它 ⇒ 处理器读到自己缓存里的旧行（残影）。
- 只在长度为对齐倍数之外坏：坏在开头一小段、结尾一小段，或长度取整后越界撞到邻居。
- 偶发、与负载相关、换个缓冲区大小就好或就坏。
- 需要为新设计定"搬运 + 缓存维护"的最小封装，而不是一处一份拷贝。

## 使用方法

### 先查、先确认

- 一手资料优先级：**本工具链/本核的缓存维护章节与本器件的搬运引擎章节** ＞ 应用笔记 ＞ 教程 ＞ 模型记忆。
  要查到具体程度：维护操作是按地址还是按行、地址范围是否必须对齐到行、
  哪些端口天生一致（有些外设端口直连缓存/走一致路径，那种情况不该做维护）、
  搬运完成状态位/计数器的语义（"已发出"还是"已落到内存"）。
- 先跟用户确认：这块缓冲能否换成对齐分配（可能改内存布局）、
  是否允许为了维护操作暂时关闭某段缓存（会影响别处性能）、
  能否接受为一致性多拷一份（用空间换确定性）。

### 方向不对称：两类维护操作

| 数据流 | 要做的事 | 不做的症状 |
|---|---|---|
| 处理器写 → 引擎读内存 | **清理/刷新**（把脏行写回内存），并在启动搬运前加访问顺序屏障 | 引擎读到写入前的旧内容，或前半新后半旧 |
| 引擎写内存 → 处理器读 | **失效**（丢弃缓存行，下次读从内存取） | 处理器读到上一帧、残影、局部旧值 |
| 双向都可能 | 清理并失效 | 两个方向的症状同时出现，最难归因 |

关键区别：**清理不会让本地缓存变旧，失效会丢弃未写回的数据**。
所以"处理器正在往同一块里写"时做失效，会丢掉自己的新数据——这就是归属规则存在的原因。

三类对齐坏点：

1. **首块坏**：缓冲起址不在行边界，失效/清理从向下取整的那一行开始，
   把邻居（可能是同一行里的控制结构）一起带走，或反过来漏掉开头几字节。
2. **尾块坏**：长度不是行大小整数倍，尾部那一行的剩余字节被当成"整行"处理，
   要么没覆盖到、要么多覆盖了别人的数据。
3. **取整越界**：为了对齐把范围向上取整，越过缓冲末尾撞到下一块内存；
   偶发、依赖内存布局，最难查。规则：**起址向下对齐、止址向上对齐，但绝不越过本缓冲的真实边界**——
   做不到就改用行对齐的专用缓冲，不要就地取整。

### 封装的最小形状（缺任一项就不要复用这段代码）

- **缓冲描述**：起始地址、长度、对齐要求、方向（读入/读出/双向）、归属（此刻谁可以写）。
  归属要能打印出来，现场才能问"这块是谁的"。
- **搬运前一次维护 + 搬运后一次维护**，按上表选方向；两次都写进同一层封装，
  调用方不许自己拼"这次要不要清"。
- **完成判定用硬件读数**：搬运引擎的完成状态位、已传输计数、或引擎侧的结束事件。
  **禁止用固定延时/循环次数当完成判定**——它在空载时通过、在负载高时偶然通过，是最坏的一种假绿。
  计数读数为 0 或读不到 ⇒ 判 `NOT_MEASURED`，不要按"传输很快所以应该完了"放行。
- **并发归属规则**：同一块内存被两条通路写，看到的是慢一帧或撕裂（两个半帧拼一帧）。
  可选解，按代价从低到高：双缓冲轮转（写者写备用、完成后换指针）＞
  加锁串行化（代价是延迟抖动）＞ 由硬件写、处理器只读（最省事，但要求处理器不写它）。
  定好后写进表的责任方列（见 `register-map-and-readback`）。
- 缓冲分配本身要走**对齐分配**，不要把未对齐的普通指针传进这层封装。

### 按症状分诊

| 症状 | 先查 | 再查 |
|---|---|---|
| 数据整体错位、跨行错开 | 对齐与起址取整 | 字节序（引擎与处理器谁大端） |
| 上一帧残影、局部旧值 | 失效做了吗、范围覆盖全了吗 | 读的路径是否命中缓存 |
| 只有长度非对齐倍数时坏 | 尾部处理 | 取整是否越界撞邻居 |
| 偶发、与负载/其它通路相关 | 带宽竞争（转 `external-memory-bandwidth-account`） | 完成判定是否退化成延时 |
| 处理器自己写的字段被抹了 | 失效波及同一行 | 两条通路是否都在写同一块 |
| 换缓冲大小就好/就坏 | 内存布局与对齐 | 一致端口与非一致端口混用 |

## 失效条件

- **没有缓存的裸核/精简核**：这套维护操作是空转（甚至指令都不存在），
  但**接口形状要保留**——同一层封装在别的构建目标上退化成空函数。
  征兆：为"能编过"到处插维护调用，之后换到有缓存的目标上方向全乱。
- **工具链的缓存维护 API 名字与语义各不相同**：同一层封装要在本工具的文档里
  查到"清理 / 失效 / 清理并失效"各自的准确含义与地址范围要求再写代码。
  凭别的生态的函数名硬套是这一族最典型的错案。
- **把一致性端口当非一致性端口处理**（或反之）：多做维护只是浪费带宽，
  少做维护就是数据坏；搞不清时以器件文档的端口描述为准，做一次实测确认。
- **用固定延时或"跑一次没坏"当判据**：负载变了症状就回来，且回来时看起来像新问题。
- **失效与本地写并发**：在处理器还持有未写回数据时失效整块 ⇒ 数据丢失，
  症状是"随机少了一小块"，比读到旧值更难归因。
- **不许在没有对应硬件的情况下宣称板上已修**：没有板/没有该外设时，
  这层的结论只能写"未在板上验证"或 `NOT_MEASURED`，不能写进交付结论。
- 维护操作按地址范围但底层按行生效：范围传对了也可能多伤邻居，表里要标注真实粒度。

## 已验证效果

未量过，属建议。可复跑的形式（有对应硬件时才允许跑）：
准备 1 个已知图案的缓冲与 1 个紧邻其后的邻居结构，跑 3 种长度（对齐倍数、对齐倍数 + 若干字节、若干字节）
× 2 个方向（处理器写→引擎读、引擎写→处理器读）= 6 项内容比对，
再加 2 项邻居存活检查（首行、尾行未被波及），共 `判 8 项`；
每项比较"处理器侧参考结果 vs 硬件通路读回"，期望完全一致；
另跑 1 项变异对照：故意抽掉维护操作，这 6 项应能稳定变红，抽掉后仍全绿说明判据是永绿的假判据。
三态判定与"判 N 项"计数按 `three-state-verdicts`，先在未改动的树上把期望跑绿见 `bench-expectations-first`。

## 来源

长自一类反复出现的观察：搬运出来的数据"半新半旧"、首块坏或尾块坏，
定位到最后全部落在**维护方向搞反**与**对齐取整**这两点上；
以及"用固定延时等搬运完成"在负载变化时复发。
带宽侧的账见 `external-memory-bandwidth-account`，主机侧常量与骨架见 `host-bindings-from-contract`。
