# 一张寄存器表同时撑住 RTL、软件、文档与台架

寄存器表是软硬件接口唯一的**共同真源**：RTL 的端口行为、处理器侧的常量、
面向人的文档、台架的期望值，都从同一张表来。表不在，四处就开始各说各话。

## 适用场景

- 第一次给"处理器 + 可编程逻辑"的设计定软硬件接口。
- 加了新功能但没有可读回的口，现场只能靠眼睛判效果。
- 文档写"默认档 A"，上电实际行为是"档 B"，两边争不出结果。
- 上位脚本与硬件常量长期手工同步，某次改动后悄悄不一致。
- 要写台架判据，但没人说得出"这个寄存器写完应该读回什么"。

## 使用方法

### 表的列（一行都不许省，缺列 = 表不可用）

| 列 | 内容 | 为什么必须有 |
|---|---|---|
| 名称 | 稳定的符号名，不用匿名偏移 | 日志与文档要能被人读懂 |
| 地址 | 相对外设基址的偏移，标注基址由谁给 | 基址常在运行时才知道，写死就错 |
| 位域 | 起止位与有效宽度 | 防止"整字写"误伤邻居位 |
| 读写属性 | 可读/可写/只读/写触发/写 1 清/读清 | 把"只读当可写"是高频事故 |
| 复位值 | 上电或复位后每一位的实际值 | 与"默认档"逐条核对的那个数 |
| 副作用与自清 | 写会引起什么动作、何时自清、多久清 | 回读值预期要看这一列 |
| 单位与换算 | 计数 1 = 什么、换算到时间/角度/像素 | 现场调参不用猜量纲 |
| 责任方 | 谁有权写、谁只读、几处读 | 两个通路写同一个位必然打架 |
| 期望读回值 | 写完应该读到什么、什么时候读不到刚写的值 | 台架判据直接引用这一列 |

### 三条硬规矩

1. **写后必回读，且回读值进日志**。"命令执行了"不等于"状态改了"：
   回读不匹配时先查这一位是否本来就自清、是否只读、是否有副作用窗口（有些位在动作完成后清零）。
   回读匹配也不等于生效——生效看状态位或计数（见 `board-liveness-readback`）。
2. **默认值逐条核对复位值**。把上电实测的各寄存器读数与表里"复位值"一列比对，
   不一致就改表或改 RTL 初值，**不许把"文档默认档"当成板上默认行为**。
   征兆：从没配置过的现场演示里，行为与"配置成默认档"之后的行为不同。
3. **观测性优先**：任何影响画面/结果输出的内部状态——计数器、当前模式、角度、限制量、
   溢出次数——都必须挂到一个可读口。判据是"这个量如果出错，现场能不能不看眼睛只读数就发现"。
   读不到 ⇒ 在表里加一列调试口，而不是"靠现象猜"。调试口也要标注是否影响时序（读了就清的那种）。

### 地址空间怎么排

- 按**功能分区**排布并留空隙：控制/状态/计数/调试各占一段，段间留冗余，将来加口不挪别人的地址。
- 每段起址按总线宽度对齐；位域不跨字边界，除非文档明确说明如何拼。
- 别名/影子寄存器（同一存储出现在两个地址）要显式标注，并说明哪个是权威地址：
  影子口读到的可能是同一份状态，把两个地址当两个独立状态是常见误解。
- 基址与地址窗口由运行时决定的一律用符号，不在代码里写死绝对地址。

### 自清位与"写 1 清"的坑

- 自清位的回读值在动作完成后是 0，"写 A 读 A"的判据对它不成立——表里必须写明。
- 整字写会把别的 1 也"清"掉：位域写要读-改-写还是直接写掩码，按属性列说清并统一。
- 读清位（读过就少一次事件）在轮询与中断两种用法下行为不同；表里标注谁在用哪种取法。
- 事件标志"溢出后不再变"：计数/粘滞标志要区分，否则丢事件看不出来。

### 表作为唯一真源

- 处理器侧的偏移常量、位域掩码、台架的期望值**由表生成**，不手抄。
  生成与衔接见 `host-bindings-from-contract`（条目名）和 `contract-to-host`（脚本名）。
- 硬件不在手时也要有**一致性检查**：表的复位值列与 RTL 里的初值做静态比对，
  表与文档抽取的字段做双向核对；没有同源生成，至少要有一个比对脚本能红。

### 最小台架判据形式

对表里每个可写寄存器跑三件事，逐条记 `PASS / FAIL / NOT_MEASURED`：

1. 写非默认值 A ⇒ 回读等于 A（自清位：回读等于表里声明的自清结果）。
2. 写另一个值 B ⇒ 回读等于 B（防止"写什么都是同一个值"的假绿）。
3. 越界地址读写 ⇒ 记录读回什么：必须是稳定且**已文档化**的结果（全 0、全 1、错误响应之一），
   且不能把邻近有效寄存器改掉。越界读回随机值 ⇒ 地址译码有问题，这是设计缺陷不是测试噪声。

只读寄存器不进"写测"循环（写了没反应 ≠ 坏了），按属性列单独成群判定。

## 失效条件

- **把只读当可写**：写不进去被当成"通路坏了"，进而误查加载/时钟链路。征兆：写后回读恒等于复位值。
- **表与 RTL 各自漂移**：硬件不在场时最严重，两边都"看起来对"。征兆：文档里的偏移
  与代码常量数不同；一致性检查从没跑红过（可能因为它是永绿的假判据）。
- **复位值列靠"应该都是 0"填**：真正上电非 0 的位（比如带初值的限制量）会让默认行为与文档不符。
- **回读穿过缓存/桥接层**：读到的是旧值或被合并的事务，"写后回读一致"于是变成假绿。
  需要时加屏障或换访问路径，并把这条限制写进表的可信度备注。
- **位域跨字/别名口被当独立状态**：一次整字写悄悄改了邻居功能，现象出现在完全不同的模块上。
- **把观测口当功能口用**：轮询调试口改变事件计数，测出来的"数据丢失"是自己读出来的。
- 表很长时不要硬撑正文：速查表拆进 `references/`，正文只留"去哪查、什么时候查"。

## 已验证效果

未量过，属建议。可复跑的判据形式：对 N 个可写寄存器跑 2 次写读、对 M 个越界地址各读 1 次，
共 `判 2N + M 项`；全部有读数且回读与表的"期望读回值"列一致才允许写 `PASS`，
读不到或解析失败按 `NOT_MEASURED`。另跑 1 项表与 RTL 初值的静态比对。
判定与计数地板规则见 `three-state-verdicts`；判据必须自带能动过的变异对照见 `mutation-controlled-coverage`。

## 来源

长自两类观察：一是"写了寄存器但没有读回口，现场无法自证，只能用眼睛判画面"；
二是"表的复位值/默认档与板上实际默认行为不一致，公开场合被问住又解释不清"。
地址与属性的具体坑清单见 `before-touching-hardware`（上板前的禁区）与 `tcl-and-probe-traps`（探针自骗）。
