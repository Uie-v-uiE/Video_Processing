# 复位与时钟规划：先出域表，再定策略，最后对账

## 适用场景

- 综合/实现报告里出现未约束时钟端点、异步复位的恢复/去除检查、或"某条路径的钟不是你以为的那一路"。
- 多个子系统各自要复位，或复位来源与某个时钟域不是同一个域。
- 有人写了一句"这个寄存器上电就是 0，所以不用复位"，或"给它加个上电初值就能修掉这个状态"。
- 复位/时钟清单是手写的，改了 RTL 之后没人更新；或者清单说有 N 条、工具量到 N+2 条。
- 哪一步用：接一个含两个以上时钟的项目的第一轮；每次换钟、换复位来源、改层次名之前。

## 使用方法

### 先查什么（一手资料优先级）

厂商用户指南中"时钟合成原语的复位行为""全局复位与寄存器初值的关系""按名约束的语法与射程"这三节，
加上数据手册里触发器初值语义与恢复/去除时间那几张表 ＞ 应用笔记 ＞ 教程 ＞ 模型记忆。
初值与折叠这类"源码说的不等于网表里的"结论，一律以实现后网表/报告为准。

### 先跟用户确认什么

- 复位的来源与极性是否绑在对外可见的接口上（引脚、上位机侧寄存器、另一颗芯片的信号）；改它会伤到别人。
- 是否要求断电自启/上电即出画面：这决定复位与配置加载路径，也决定上电初值能不能被当行为依赖。
- 换钟、重新源化、改层次命名是否会动到演示顺序或现场观测手段（这些是外观与流程级决定，不是纯技术决定）。

### 第一步：一张域表（缺这一张，后面所有判断都在猜）

每个时钟一行，字段固定：

| 字段 | 填什么 |
|---|---|
| 名字 | 约束与报告里被点名的那个名字（不是源码里的端口名） |
| 来源 | 物理输入脚 / 由哪一路派生 / 哪个时钟合成原语的哪一档输出 / 是否被门控 |
| 频率与周期 | 标称值 + 容差 + 单位；派生钟按参数算出的值，不抄教程 |
| 驱动哪些模块 | 按例化列，不按模块类型列 |
| 属于哪个物理区域 | 时钟区域/侧/列（决定可用原语与布线代价，也是跨域判定的落点依据） |

再给每个复位一行：来源、极性、同步还是异步作用、影响哪些域、有效长度是多少拍、释放是否已同步进每个域。
域表是这份规划的账本：跨域清单、约束建立顺序、资源与时钟树判断都从它引用，而不是从记忆引用。

### 第二步：定复位策略（高自由度，按对照问题选）

- **同步复位**：不占专用复位端、无需释放同步器，但复位必须持续足够多拍才能被采样到，且它把复位
  扇出摊到普通布线上；副作用是复位会出现在状态方程里，容易漏一拍。
- **全局/异步复位（异步有效、同步释放）**：不要求持续多拍，但每一个它作用的域都必须有自己的释放
  同步器，否则释放沿与本地钟打架，恢复/去除检查从这里开始红。
- 对照问题：这个复位跨几个域？每个域都同步释放了吗？有效期间能不能保证被同步复位采到？
  它和时钟树谁先稳定？复位网络扇出是否落进 reduce-fanout-and-congestion 那一族的风险区？
- 混合是常态：片内配置加载路径提供上电确定性，运行时用同步复位清局部状态。别为"整齐"把多域塞进一根异步复位。

### 第三步：上电初值的正确用法

- 上电初值是**起始状态的确定性**，不是复位的替代品：它只在配置装载那一刻生效，运行中任何路径
  回到那个状态时不会有初值帮你。
- 想"靠上电初值修状态"时，必须核对**网表里的初值**，不是源代码里写的那个常数：综合会把常量折叠掉、
  优化会重命名或合并寄存器、全局置位/复位这一类机制可能把内容刷成器件定义的默认值。
  核对位置 = 实现后网表/报告里逐寄存器的初值字段；源码级"我写了 0"不算证据。
- 初值与复位并存时，写清谁赢、以及复位释放后第一拍的状态是否就是你要的。

### 第四步：与工具对账（低自由度，跑完应看到什么）

- 复位清单与实际寄存器对账：从工具取"带复位的寄存器数"与"按复位名分组的数"，和清单逐行比。
  清单说 N 条、工具量到 N+2 条 ⇒ **文档错**，不是"多两个无所谓"；两个多余项要么归名到清单，
  要么写清来历（通常是优化造出的置位/使能寄存器）。
- 时钟清单与报告对账：每个域表里的钟都应能在时钟报告里被点名，且未被约束端点数为 0；
  点名不到的钟说明域表写的是源码名而不是网表名，或这个钟压根没进约束。
- 观测性欠账要立案：时钟与复位都要能在运行时被读回——频率可用一个已知参考计数测，复位状态与
  释放完成位用可读寄存器暴露，域身份用一个常量寄存器供软件确认。读不回来的项写成一条欠账
  （项 + 影响 + 补法），挂在交付可见处，不许只在脑子里记。
- 改名与改层次是双刃动作：按名的约束与按名的检查会同时静默失效，概念与自查清单见
  constraint-coverage-loss；本条只补一句——**域表与复位清单也要同步改，否则账本先失效**。

## 失效条件

- **域表是从代码抄的，不是从约束与网表核对的**：名字对不上、派生钟的系数抄错、门控钟被当成直连钟。
  征兆：时钟报告里点名不到清单上的某一行。此时后面所有跨域与资源判断都不可信。
- **把全局复位跨多域直连**：释放未逐域同步 ⇒ 亚稳态与恢复/去除违例；征兆就是这两个字段第一次变红，
  而且往往在你换钟或改层次之后才出现。
- **把上电初值当行为依赖**：只在网表里确认过一次，之后改 RTL 没重查；或者初值被折叠掉了还在按源码
  语义写文档。征兆：仿真绿、硬件上同一状态的初值表现不同。
- **清单靠手写维护**：改 RTL 不提清单，对账永远是红的，久了大家就跳过这一步——跳过比红更糟。
- **工具版本或优化指令一变，计数就漂**：寄存器合并、复制、抽取移位链都会改变带复位的寄存器数。
  对账必须在同一口径下做，跨口径写"不可比"而不是差分。
- **观测性欠账没立案**：现场只能靠猜；"改了但没量"从这一步开始。
- 纯行为仿真、不出位流的场合：网表初值与实现后对账两项不适用，改为源码级 + 仿真读回，并明写覆盖不到硬件。

## 已验证效果

未量过，属建议（没做过带/不带本条的 A/B）。依据的观察类别：靠上电初值修状态被工具折叠掉、
以及复位清单与实际寄存器数不符这两类账，都是靠对账动作才现形的。
变硬的可复跑形式：一条命令产出三个读数——带复位的寄存器数、清单条目数、差值（差值应为 0，
非 0 时逐条列出多余项来历）；未约束时钟端点数（应为 0）；运行时可读回的时钟/复位项占比
（读不回的逐条立案）。任一读数取不到判 NOT_MEASURED。

three-state-verdicts（取不到判未测量）。
