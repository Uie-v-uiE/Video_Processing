# 技能包：与大模型协作做 FPGA / 数字设计

把与编码 agent 协作过程中反复用到的做法写成条目，供另一支队伍直接复用到自己的题目上。
判这个包好不好用只看一件事：**可复用性**——没参与过写作的队伍拿到这个目录，
不问原作者能不能用起来。

本包不含任何具体工程的事实（器件上限、板卡引脚、某一次运行的读数）。
这类事实属于各自的工程文档；写进条目，条目就只在原工程里成立
（`_meta/check-skill-package.mjs` 逐条扫这种泄漏，命中本机路径或工程专有名就判不通过）。

## 四类内容对应赛题要求的四型

| 赛题类型 | 本包类别 | 入口 |
| --- | --- | --- |
| 提示词工作流 | `workflow/` `prompts/` | 从算法描述推软硬件划分、从综合报告定位瓶颈、一次改动的标准流程节拍 |
| 案例模板 | `templates/` | 工程骨架、单次改动记录、主张与证据对照表、验收与人工目测的签收配方 |
| 校验脚本 | `scripts/` | 黄金参考比对、指标采集出表、由接口契约生成主机侧代码、复现演练、发布前检查跑批 |
| 踩坑清单 | `pitfalls/` | 探针陷阱、检查脚本给出名不副实的通过、构建在飞时的竞态、一次性措辞替换把文档改坏、约束覆盖面缩水、交付包完整性 |

另有按工作内容分的四组条目 `timing/` `rtl/` `runtime/` `verify/` 与速查表 `references/`。
包内 10 个目录组共 49 条；逐组分到几条由索引现算，见下面「索引」一节（同一张表不在此重抄）。

每条条目的正文都用同样五个小标题写（逐字标题）：`适用场景`、`使用方法`、`失效条件`、
`已验证效果`、`来源`。赛题 §5.3 要求每条写清的四件事按下面对应：
适用范围＝`适用场景` 节，使用方法＝`使用方法` 节，失效条件＝`失效条件` 节，
已验证的复用结果＝`已验证效果` 节；第五节 `来源` 记这条做法是从哪一类观察里长出来的。

## 30 秒接入

1. 整目录放进自己的工程（`skills/` 或 agent 的技能目录）。正文是纯文本，脚本只依赖 Node，没有安装步骤。
2. 先读 `references/symptom-router/SKILL.md`：手上只有症状时，用它决定读哪条、动手前先搜什么。
3. 按需加载单条；要细节再打开该条目的 `references/` 或运行它的 `scripts/`。
   不要一次读整包——这个结构按"元数据、正文、资源"三级加载来设计，一次读全包就把三级的好处抵消了。

人工用法、新增条目的流程、改条目的规矩都在 `_meta/`：

| 文件 | 作用 |
| --- | --- |

| `_meta/writer-contract.md` | 给条目作者的硬约束（形状、长度、通用性） |

## 适用范围 / 使用方法 / 失效条件 / 已验证的复用结果

适用范围：与题目、器件、EDA 版本解耦的**协作纪律**——任何用大模型写 HDL、调时序、做验证的工程可以直接读。
条目内路径都相对本目录，命令只点到工具名与开关（`xsim`、Vivado Tcl、`node`、`bash`），不含任何一台机器的绝对路径
（`_meta/check-skill-package.mjs` 逐条扫这一项，命中本机路径就判不通过）。赛题优先建议的三类
（Overlay 加载与校验、寄存器映射范式、DMA 搬运与缓存一致性）在 `runtime/` 里各有对应条目，
但写的是**裸机与寄存器层**（读回口、位段、地址映射、判活计数）——`pynq-qpython` 那条栈本包没跑过，所以不写成指令。

使用方法：上一节"30 秒接入"的三步；单条按需加载，索引由 `_meta/build-index.mjs` 从条目现算。

失效条件（四条，逐条都要在新工程里重看一遍）

| 什么变了 | 要做什么 |
| --- | --- |
| 换 EDA 主版本 | 换 EDA 主版本要先重跑再引用——各条"来源"记的是当时那一次实跑 |
| 换工程后的判据名 | `verify/` 与 `pitfalls/` 两组条目讲的是"这把检查工具自己会不会漏判"，换工程后要把里面的检查项名字换成 |
| 长度规则的计数口径 | 本包的结构检查按**字符**限条目长度（中日韩文字一个字符计一处），换成按字节的规则会给出不同读数 |
| 有没有可回读的寄存器口 | `runtime/` 假设工程有可回读的寄存器口，没有这种口的工程要先建回读，否则那些条目只能当 checklist 用 |

已验证的复用结果：本包自己被三条可复跑的检查覆盖，命令与读数如下（读数不靠声明）。

```bash
node _meta/check-skill-package.mjs .        # 结构：五节齐、通用性、索引与条目双向一致、条目数下限
node _meta/check-selftest.mjs               # 上面那个脚本自带的"能判出不通过"对照
node _meta/build-index.mjs . --check        # 索引与条目是否还一致（只报差异，不改文件）
```

- `node _meta/check-skill-package.mjs .` 判 53 项（条目 49、索引 50、红 0、未测 0）；
- `node _meta/check-selftest.mjs` 判 16 项、不符 0。

这两条判的是包的结构与自洽（条目齐不齐、索引漏不漏、有没有把本机路径写进通用条目），不判做法在别的工程里是否仍有效； 后一件事的落点是每条自己的「已验证效果」一节，逐条判、不做汇总。另有两道检查没有脚本——只给症状能否命中、没参与过的人能否照条目走通——这两条靠人工，缺口写在 `_meta/validation.md` 与 `_meta/distillation-process.md`，没有写成已验证。 另有两道检查现在没有脚本——"只给症状能否命中这条"与"没参与过的人照条目能否走通"， 这两条靠人工，缺口写在 `_meta/validation.md` 与 `_meta/distillation-process.md` 里，没有写成已验证。
