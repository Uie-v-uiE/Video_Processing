# 写作契约（条目作者必读，机器判据逐条对应）

## 文件形状（只有这一种）

```
---
name: <与目录名逐字相同，hyphen-case，禁首尾/连续连字符>
description: 用于<症状/触发条件>时。<可选：一句边界，说什么情况别用>
---

# <条目的中文标题>

## 适用场景
## 使用方法
## 失效条件
## 已验证效果
## 来源
```

五个二级标题**逐字**这样写（机器按标题抓节，写错字=缺节）。
`description` 必须单行、≥40 字、以「用于」开头、**含触发词**（时/当/若/需要/出现/场景），
且**不写做法**——只写什么时候用它。做法是正文的事。

## 长度

正文 ≤ 500 行、去空白后 ≤ 6000 字符。超了就拆：速查表/长表放 `references/<主题>.md`，
正文只留"去哪查、什么时候查"。**一个精准例子胜过五个平庸例子。**

## 通用性（这是这份包唯一的"可复用性"判据）

- 不许出现：具体工程名、具体板卡/器件型号、轮次号（`rNN`）、问题台账编号（`#NNN`）、
  仓库内的文件路径、任何本机绝对路径。
- 该写成"两个时钟域之间""某款 7 系列器件""上位机脚本"这类**角色**，而不是具体名字。
- 工程专有的读数属于交付文档，不属于技能包——技能包只装"下次遇到同类问题怎么走"。

## 内容三条硬要求

1. **`使用方法` 里必须写明两件事**：动手前**先查什么**（一手资料的位置与优先级：
   厂商用户指南/数据手册/接口规范 ＞ 应用笔记 ＞ 教程 ＞ 模型记忆），以及**先跟用户确认什么**
   （不可逆的、会伤硬件的、影响外观或演示顺序的、有取舍的）。
2. **自由度匹配脆弱度**：易错/不可逆的动作写成低自由度（精确命令 + 前置条件 + 跑完应看到什么）；
   判断类写成高自由度（原则 + 对照问题）。不许把判断伪装成流程。
3. **`失效条件` 不许是空话**：要写"什么情况下这条会误导你、失效前有什么征兆"。
   `已验证效果` 要么给可复跑的形式（命令 + 看到的读数），要么明写「未量过，属建议」——
   含糊句子视为没写（机器会红）。

## 尺子的通用语言（`verify/*`、`pitfalls/*` 必须用同一套词）

三态判定 `PASS / FAIL / NOT_MEASURED`；结论行最后一个字段是判定词；
`判 N 项` 记的是**做了多少次比较**（不是通过多少）；空集、读不到、解析失败一律
`NOT_MEASURED` 而不是通过；判据要么自带能红的变异对照，要么标注"未配对照"。

## 写完自查（必须真的跑，不许念一遍）

```bash
node <本包根>/_meta/check-skill-package.mjs <本包根>   # 你负责的条目那一行必须是 PASS
```
（同一次运行里，别的批次还没写完 ⇒ 索引行/条目地板会报 `NOT_MEASURED`，那不是你这条的问题；
但 `E` 行与 `G` 行涉及你的文件时必须绿。）
