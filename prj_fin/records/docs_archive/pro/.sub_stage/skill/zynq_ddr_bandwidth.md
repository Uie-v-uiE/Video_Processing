# S4 · 外部存储带宽账先算再动：吞吐 = 在途深度 ÷ 往返延迟，突发拷贝预算按**窗口**算而不是按平均速率算

## 触发
- 当你要在 SoC 的高速并行主口（HP 一类）上做 PL 整帧读写、乒乓双缓冲时
- 当画面丢字 / 丢包，你想知道"到底是带宽不够，还是别的问题"时
- 当有人提议"再深一层缓冲 / 再加一个读口"来治丢包时
- 当你准备选分辨率、或决定缓冲放片上还是放外部存储时

## 不适用
- 匀速、连续的数据流：那种按平均速率比就够了，"窗口预算"这一步是多余功课
- 同一端口上还有其它主设备抢占的系统：本算法只覆盖"一条通路独占"，共享时要按最坏重叠情形另算一笔
- 画质 / 肉眼类问题：先按分层定位排除数据面，那是 S8 / S23 的范围

## 动作
1. 帧字节按实算（宽 × 高 × 每像素字节；例：本仓库一帧 307200 B，折成 64bit 字是 38400 个），时钟与位宽也按配置里的**实际**值取，别沿用文档里"看着眼熟"的那个数。
2. 先算上限 = 时钟 × 位宽（例：本仓库 100 MHz × 64 bit = 800 MB/s；按 50 MHz 算会得 400 MB/s，差一倍）。
3. **突发类拷贝按窗口算预算**：整帧拍数 ÷ 可用窗口拍数 = 每周期最少要交出的拍数，换算成带宽再与上限比。例：一个 67200 周期的消隐窗口里搬 38400 拍 ⇒ 下限 ≈0.571 拍/周期 ≈ 457 MB/s，即上限的 57 %。按平均速率算会把这件事完全掩盖掉。
4. **吞吐 = 在途深度 ÷ 往返延迟**，先数在途再谈峰值：逐字等写响应时在途恒为 1，上限就是 字长 ÷ RTT（例：RTT ≈40 拍 @100 MHz ⇒ ≈20 MB/s）。如果主机侧给的速率只剩 1.3× 余量，任何一次别的抢占都会把它压到线以下。
5. 提高在途深度的改法是流水化写通道（地址与数据同拍挂出、各自保持到被接收；响应只回收计数、不阻塞数据通路），并且"这一轮完成"的条件要包含**在途已清零**；响应计数回绕会造成永久卡死。
6. 在提"加深缓冲"之前先把那道算术题做完：吸收一个窗口需要的深度 = 到达速率 × 窗口时长，换算成片上存储块数（按每块容量折）再与全片总量比。例：本仓库算出要 ≈84 个大容量 BRAM 块，而全片只有 140 ⇒ 这条路**结构上不可行**，是被算术否掉的，不是被一次失败劝退的。
7. 处理器写完外部存储后必须做缓存维护（clean / flush 到一致）可编程逻辑才看得见新数据；外设直接 DMA 进存储的通路不经过处理器缓存，别拿这条去解释那一路的现象。
8. 留两样复算工具：层次化的存储归属报告（谁吃掉多少块），和把突发拷贝等效成"端口被独占 N 拍"的**限速从机**台架（本仓库 `build/tcl/report_mem_hier.tcl`、`tb_v6_vblank_copy`）。

## 完成判据
- 用限速从机扫几档速率，最慢那一档必须表现成"**溢出到下一个窗口，但不写有效区、不重复、不越界、看门狗不误杀**"。例：本仓库 800 / 560 / 480 MB/s 都在一个窗口内完成，320 MB/s 溢出但无副作用——这才叫窗口预算被钉住。
- "不是深度问题、是排空速率问题"的签名是**包内相位**：丢字率对包内字节偏移呈固定台阶（例：本仓库头 48 字节约 6.7 %，其后 54~64 %），且连续丢字带很短、没有整包段。流水化写通道之后同一判据回到全档 100.0 %、各相位带 0.0 %。台阶形状不出现，就别再往"加深"上花钱。

## 失效边界
- "公式对、参数错"最常见：引用任何带宽数字前按实钟 / 实位宽重算一遍（本仓库旧文档里那句"400 MB/s"传了十几版没人复核）。
- 算不出出处的数字就删掉、写"未验证"，不许引用。
- 位宽 / burst 长度 / 单次传输的拍数上限必须与配置里的这条端口一致，并受协议版本限制（例：AXI3 单 burst ≤16 拍已经贴上限，换 AXI4 这条就变了，要重读协议）。
- 在途深度是上限的来源，所以任何改变往返延迟的事（别的 master 抢占、拷贝调度改动、时钟比变化）都会让这笔账整体作废，要重算。
- 估算类数字（功耗、温升）在没有开关活动文件时置信度很低 ⇒ 只能做相对比较，念的时候要把置信度一起念出来。
- 相邻条目的分界：丢字率这类数**怎么量出来**（逐帧变化的图案、发完再读）见 S9；同一单口存储器被分时成 N 次访问、以及"再加一个读口"的真实代价探针见 S10；跨域脉冲与配对基线门禁见 S11 / S16。
