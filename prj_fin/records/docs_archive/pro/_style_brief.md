# 文档风格重写：统一约束（每个改动者都必须先读完这一页）

工作目录：`D:\Xilinx\Prj\pro\Video_Processing`（这是一个 git 仓库）。目标：把交付文档的中文/英文文字风格从"机器话"改成能被专业人士通读的句子，并按需调整段落结构。

## 一、要改掉的话

1. **文档自指**：`本文档`、`本节`、`本篇`、`该文档`、`这份文档`、`此文档`、`本章`、`本文`。改成直接说事，或者改成指名被讨论的那个源文件名。
   注意区分：如果"本文件/该模块"指的是**正在被分析的某个 RTL/脚本源文件**，那是正常表述，保留。
2. **用途开场白**：`是用来……的`、`只做一件事`、`旨在`、`目的在于`、`致力于`、`本节介绍`、`用来回答`、`用来判断`。删掉框架句，直接给结论。
3. **排比与总结腔**：`一是……二是……`、`首先……其次……`、`综上`、`总而言之`、`总的来说`、`简而言之`、`一句话结论`。改成有主有谓的陈述句。
4. **注意腔**：`值得注意`、`需要注意的是`、`需要说明的是`、`特别说明`、`请注意`、`必须强调`。删掉提示语，把那件事本身说清楚。
5. **buzzword**：`落地`、`抓手`、`闭环`、`赋能`、`颗粒度`、`体系化`、`方法论支撑`、`深度结合`。换成具体动作或具体状态。
6. **如下腔**：`如下表所示`、`如下图所示`、`见表 N`、`见下式`。指代要指名（`下表第 3 行`、`§5 的那张表`）。
7. **能力腔 / 确保腔**：`提供了……能力`、`支持……功能`、`具备……特性`、`确保`、`保障`。说清"谁在什么条件下做出什么"。
8. **程度副词**：`显著`、`极大地`、`完美`、`优秀`、`强大`、`非常`、`十分`、`极其`。有读数就报读数，没读数就不评级。
9. **人称**：`我们`、`笔者`、`团队认为`、`希望对您`。改成无主语或指名执行者（脚本名、命令）。注意 `我[要想将在认为觉建]` 这一族也在禁用范围。
10. **破折号金句**：行尾形如 `——xxx。` 的收尾抒情句。改成陈述句。一行里只是插入说明的破折号可以留。
11. **箭头链**：正文里的 `⇒` 改成句子（`因此`、`于是`、`所以`、`这意味着`）。表格与代码块里的 `⇒` 按第二节处理。
12. **括号套括号**：`（……（……）……）`。拆成两句话。
13. **占位与软话**：`TBD`、`待补充`、`【填入】`、`待验证`。删掉或写清缺什么、补齐的命令是什么。

## 二、绝对不许动的东西（有一条被机器读）

仓库里有一批判绿脚本，逐条扫文档。以下字符串与形状是它们读的，**改一个字就会红**：

1. **判定行**：纯 ASCII 的结论行，例如 `RESULT tb_v98_top_seam PASS`、`GATES: ALL PASS（24 项全部判定）`、`PASS D3 stage=... `、`APP_NOT_MEASURED`。逐字符保留。
2. **代码块、命令、示例输出、串口回读原文、日志引文**：一个字都不改。里面出现的 `⇒`、`本文档`、emoji、`待验证` 都属于引文，保留并在报告里说明。
3. **路径引用**：形如 `` `report/xx.md` ``、`` `build/xxx.rpt` ``、`` `src/rtl/x.v:120` `` 的引用必须仍然指向存在的路径；不要新增路径，不要删掉行号锚点。
4. **数字**：所有读数（WNS 0.687 ns、BRAM 96 tile、165 条判定、24 项、2.213 W、52.6 °C、md5、版本号 r132 等）逐字保留。有疑问就不改。
5. **版本号与"现行句"配对**：形如 `门禁全绿的那一套是 r132` 的句子必须留在 `README.md`；带 `rNN` 的句子不要挪动位置、不要改写它旁边的口径词。
6. **小节编号与条目编号**：`§4`、`## 3b`、`#478` 这类被别的文档按号引用的锚点，**不许重编号、不许删**。可以补内容、可以合并段落。
7. **"不随包"声明**：`不随包`、`不在本包内`、`已被 \`.gitignore\` 挡住`、`不入库`、`本地留档` 这些词必须留在它们所在的那一行，同行语义不能拆开。
8. **脚本/TCL 头注释的关键字槽**：`src/` 与 `build/*.tcl` 的头 12 行里必须仍然出现 `用途`/`作用`/`输入`/`输出`/`退出码`（tcl 要 `作用`/`前置`/`产出`/`参数`）。**保留这些关键字本身**，可以把后面的句子改通顺。
9. **skill 条目的必需小标题**：`SKILL.md` 里的 `适用范围`、`使用方法`、`失效条件`（以及 skill/README 名册依赖的标题）保留标题行，正文随便改通顺。
10. **根 `README.md` 硬性形状**：不超过 90 行；`README.md` 与 `README_EN.md` 的二级小节数量差不能超过 1。改写完再数一遍行数。
11. **表格里的读数格**：表头与行数可以调通顺，但每格读数的值和单位不变。整屏台架、门禁、逐时钟余量那几张表是交付依据。
12. **不新增**：emoji（`\u{1F300}`–`\u{1FAFF}`、`\u{2600}`–`\u{26FF}`）、`✓ ✗ ✔ ✘`、`TBD`。

## 三、怎么写才算"像人写的专业文档"

1. 一句一个意思，句子之间有因果和先后，不靠"首先/其次"撑结构。
2. 该给条件就给条件：读数是在哪一次构建、哪条命令、什么口径下读到的，写进句子主干，而不是塞进第三层括号。
3. 结论先行，理由跟上；不写"这说明了某某精神/意义"。
4. 段落里本来该是句子的，不要用一行行 bullet 罗列碎片；bullet 只用于真的并列的条目。
5. 术语第一次出现给一句解释，之后直接用。
6. 不把"未做"写成"已做"，也不把推断写成实测。原文里标 `NOT RUN`、`NOT_MEASURED`、`估算`、`CFG` 的地方，改写后仍然要能看出它是哪一级证据。

## 四、操作流程

1. 只改分给你的那批文件。别的文件一律不碰（有其他人同时在同一棵树上改别的文件）。
2. 用 `Read` + `Edit`/`Write` 改文件。**禁止**用 bash 的 heredoc、`sed`、`awk`、`perl -i` 去写含中文的文件——会把字符改坏。
3. **禁止**任何 git 写操作（`add`/`commit`/`checkout`/`restore`/`stash`/`clean`/`push`）。也不要跑 `build/gates.sh`、仿真、综合、导出脚本——这些由发起者统一跑。`git status` / `git diff -- <你的文件>` 只读可以用。
4. 每改完一份，自检三件事：① 第一节列的句式在这份文件里清干净了（引文与代码块除外）；② 第二节的关键字符串逐字还在；③ 数字与路径没动。
   可以用这条命令数自己那份的剩余命中（只读，安全）：
   `cd /d/Xilinx/Prj/pro/Video_Processing && PYTHONIOENCODING=utf-8 python ../doc_ai_tone.py --top 300 | grep <文件名>`
5. 一次改不完就改完能改的，把没动的地方写进报告，不要为了"清零"去动引文。
