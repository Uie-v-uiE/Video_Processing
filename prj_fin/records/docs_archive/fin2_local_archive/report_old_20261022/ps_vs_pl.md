# PS 与 PL 的分工：为什么数据面放在可编程逻辑

这份文档回答一个问题：视频数据面为什么放在 PL，PS 为什么只留控制。结论在前，过程在后。

## 结论

实时视频的收包、拼帧、缓存、几何、效果和显示都在 PL。PS 只做三件事：解析命令并写控制字、读回状态、在 SD 回放时把帧 DMA 进自己那块 DDR。

这样分之后，像素通路的延迟由流水线级数决定，不受 CPU 调度影响；PS 的负载几乎只剩串口和文件系统。代价是协议栈要自己实现，调试更依赖硬件计数器和仿真，软件日志能帮的地方变少。

## 三代做法的对比

| | v1：PS 网口 | v2：PL 网口 | v3：当前 |
|---|---|---|---|
| 网口 | PS GEM0 + lwIP | PL RGMII + 自研栈 | 同 v2 |
| UDP 收包 | 软件中断 + memcpy | 硬件解析 | 硬件 |
| 帧重组 | PS 写 DDR | PL 拼帧写 BRAM/DDR | 同 v2，跨域 FIFO 优化 |
| 显示 | PL 读 DDR | PL 读缓存 | 同 v2，加缩放与效果 |
| PS 角色 | 收包 + 控制 | 仅控制 | 仅控制 + SD 回放 |

v1 的成本很直接：每个视频包都要进一次软件中断并拷贝一次，约 220 包每帧、30 帧每秒，CPU 占用高，帧到帧的延迟由协议栈与调度决定。v2 和 v3 把收包、校验、拼帧做成流水线，抖动来源变成硬件节拍。

代价是 v2/v3 需要自己实现协议栈。厂商例程只到“收发通了”，把它接成视频通路还要补 UDP 端口过滤、按偏移拼帧、坏包判定、发送仲裁和 DDR 提交点。这些边界每一道都要自己验，调试也不能靠 printf。

## 当前的职责划分

| 职责 | PS | PL |
|---|---|---|
| 以太网 MAC 与协议 | 不参与 | RGMII、ARP、ICMP、UDP |
| 拼帧与帧缓存 | 不参与 | `frame_reasm`、DDR 乒乓 |
| 缩放、旋转、效果 | 不参与 | `zoom`、`rotate`、`proc_pipeline` |
| 竖缝、OSD、HDMI | 不参与 | `split_display`、`osd_overlay`、TMDS |
| 控制命令 | 串口解析，写 AXI GPIO | 同步控制字，驱动各模块 |
| 状态回读 | 选 lane、读 GPIO、打印 | 硬件计数器与状态窗口 |
| SD 回放 | SD 控制器 DMA 写 DDR | 等发布位，搬上屏 |

ETH 那一路的字节没有一处经过 PS。SD 那一路才由 PS 的 SD 控制器 DMA 写进另一块 bank，CPU 不逐帧搬第二遍，写完只翻一次发布位。

## 窗口滤波为什么放在目标域

旋转之后再做 3×3 窗口滤波，有三种做法。

A：角度不为 0 时关掉窗口滤波。实现简单，但效果随角度消失，演示不成立。

B：先把整帧旋转到另一个缓冲，再在源域滤波。需要双缓冲，BRAM 不够，延迟也大。

C：在目标域做。逆映射之后，按屏幕光栅取 3×3 邻域，滤波和显示在同一个域里完成。当前采用这一种。

代价是窗口半径按显示像素算，横向半径只有半个源像素；处理内容整体滞后 4 行，顶层把右窗的读坐标提前 4 行来抵消。这是当前画幅下的既定取舍，不是待修的问题。

## 这套分工的边界

PS 不参与像素通路，不等于 PS 不重要。控制字、SD 文件系统、温度采样和串口交互都在 PS 上；PS 挂了，画面可能还在，但系统不可操作。

PL 也不是“什么都快”。协议栈、拼帧和显示都在固定时钟上，时序余量要自己收；BRAM 68.93% 主要被整帧缓存占掉，这是几何引擎的架构代价，不是 PS/PL 分工造成的。
