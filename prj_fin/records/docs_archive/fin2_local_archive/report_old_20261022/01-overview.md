# 概述：这块板子做什么，做到什么程度

这是一条跑在 Zynq-7020 上的全硬件视频通路。网线送来的 512×300 RGB565 帧在 PL 内完成收包、重组、缓存、缩放、旋转、效果处理和上屏，输出 1024×600 的 HDMI。PS 不参与像素通路，只负责控制、读状态和 SD 卡回放。

屏幕中间有一条可移动的竖缝。左边是原图，右边是同一帧的处理图，两侧共用同一组几何算子和同一条固定延迟的效果链。它既是对比画面，也是一把尺子：几何错位、少列、越界填黑会直接出现在缝上，不需要额外的探针。

## 系统想回答的三个问题

学生作品很容易把功能堆得很长，却答不上最基本的三个工程问题。

第一，这一帧到底收全了没有。UDP 没有重传，丢一个包就可能毁掉整帧。只看屏幕，只能看到“偶尔卡一下”，分不清是网络、DDR 还是显示侧的问题。

第二，左右两半的差异是算法造成的，还是几何本身错位。旋转和缩放一旦引入，两侧很容易各算各的坐标，肉眼分不开。

第三，从收完一帧到它开始上屏，中间压了多少时间。这个数决定了系统能不能用于远程监看或闭环控制，但多数演示不会报告它。

本项目的做法是把这三个问题做成同一条网线上的读数。PL 每秒从 UDP 1234 发一包 32 字节遥测，报告帧数、包数、坏包、作废帧、最后一次作废缺多少行、PL 内部时延和处理窗完整性。主机侧的三阶段自检会人为注入丢包，让读数从干净流走到故障再走回干净流。读数不会变红，就说明仪表没有接上。

## 三项能被第三方复核的主张

**同帧逐像素对照。** 两侧画的是同一帧、同一组坐标，所以几何做错时错位会直接出现在缝上。完整视频台架用“每行只应有一段连续画面”“每个像素带回自己的源行列号”这类形状判据检查，不猜坐标；185° 的灰度分割臂要求处理侧非灰像素为 0，硬件计数器与台架读数一致。

**链路健康由硬件自己计数。** 同一组计数有三个出口：屏上 OSD、AXI GPIO 的 JTAG 回读、串口命令。三个出口读的是同一份计数，所以“报告里写 0 丢包”这句话可以被第三方自己验一遍。遥测信标是第四个出口，不经过 PS，也不需要串口。

**仪表能被打红。** 三阶段自检在干净流、确定性丢包和恢复流之间切换，判据取每秒的变化量。故障段作废计数必须明显上升、帧率必须明显下降；如果仪表对人为破坏没有反应，这项检查本身就不成立。
