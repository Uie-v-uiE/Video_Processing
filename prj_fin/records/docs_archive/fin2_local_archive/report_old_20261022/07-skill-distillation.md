# 技能包的提炼过程

`skill/` 不是功能清单，也不是把项目里的代码再抄一遍。它记录的是这个项目在工具、时序、验证和文档上踩过的坑，以及每条坑后来怎么被量出来、怎么被判据挡住。

## 从哪些事里总结

来源分四类。

一是事故。比如检查脚本在等的判定行根本没有产出，却仍然报了通过；或者 `catch` 存的是返回码，被误读成一次失败。这类事故会写成“症状、原因、下次怎么提前发现”。

二是反复出现的症状。比如 Tcl 查询返回空集合，被当成“这个对象不存在”，而实际上可能是查询写错了层；又比如报告字段的位置随工具版本变化，解析脚本却按旧位置硬读。这类问题会在不同轮次里重复出现，所以值得单独成条。

三是量出来的差异。比如同一条路径在综合后和布线后的 WNS 不是一回事；同一份设计重跑一次，报告可能只差一行日期，也可能差出第三种结果。每一条都要说清口径，否则“优化了 0.2 ns”可能只是布局摆动的噪声。

四是外部资料。AXI、RGMII、CDC 和时序约束的做法，参考了厂商文档和公开的以太网栈实现；哪些采纳、哪些没有采纳，以及为什么，都留在条目里。

被证伪的判断不删。原来的判断、推翻它的那次运行和最后的结论并排保留，这样后来的人能看到“当时为什么那么想”，而不是只看到一个正确的答案。

## 怎么验证有效

验证口径是同一模型、同一上下文、同一工具版本，绕过技能包和使用技能包各跑一次。被控制的变量要列全；如果两次运行的输入不同，读数就不能相减。

有些检查是确定性的，比如索引由目录生成、文本编码检查、行号引用检查，同一输入跑两次应该逐字节一致。有些检查只能做正反例：给一个已知坏的输入，判据必须红；给一个已知好的输入，判据必须绿。做不到这两点的判据，不写成“已验证”。

也有没跑成的地方。旧技能包里的部分自测脚本在重建时被撤下，现在盘上不存在；这些条目只写“当时留下过什么名字”，不假装还能复跑。技能包的索引和装配检查仍然可以跑，结果写在 `skill/README.md` 与 `skill/_meta/validation.md`。

## 边界

边界分三层。

恒成立的，是方法本身：先有能红的判据再改代码；三态判定；读不到不等于通过；一条判据只回答一个问题；差分判据要成对。

平台相关的，是器件家族、端口类型、驱动形态和缓存层级。7 系列的 IDELAY、BUFIO、ODDR 用法不能直接搬到 UltraScale+；AXI GPIO 的控制面也不能直接套到 MIO。每条技能都写清“换平台要改哪几处”。

版本相关的，是工具报告字段的位置和仿真器支持的语法子集。Vivado 2025.2.1 的报告形状、xsim 的 SystemVerilog 子集、ModelSim 的编译选项，都可能在下一次升级时变化。条目里写明版本，并提醒“报告字段漂了就重新量形状”。

不写“适用于所有 AMD 器件”这种话。跨板卡的迁移证据目前没有，所以就写“当前不具备迁移条件，需要第二块板或第二个可套用的子功能”。

## 和大模型协作

这次交付由一个主 agent 加若干只看文件、不共享上下文的子 agent 完成。每个子 agent 的产物落在自己的目录，主 agent 负责装配、复核和发布前检查。子 agent 的自述一律当待复核的断言处理，不因为“它说做完了”就采信。

原始轨迹留在 `report/log/issues.md` 与 `report/log/overnight_log.md`，引用时点名条目编号，不转述成“讨论后决定”。审计提示词和审计报告也保留，修完必须重跑装配检查。

技能包的索引、条目地图和验证记录在 `skill/README.md` 与 `skill/_meta/`。这一章只讲方法，不重复列 60 条条目的名字。
