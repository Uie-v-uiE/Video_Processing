---
name: exit-zero-nothing-written
description: 用于"脚本自报成功而产物其实没变"这一类：退出码 0、打印了 DONE/成功、提交信息写了改动，但工件是旧的、缺的或没被写过；触发信号包括构建脚本 rc=0 而 build/ 报告时间戳没变、导出脚本在 rm -rf 失败后仍打印成功、Tcl 钩子把 catch 的返回码当哨兵导致成功的一刀被读成失败、以及替换命令有断言却只有部分落盘。
---

## 1. 一句话用途

退出码不算证据，产物才算。

## 2. 适用场景

- 当构建/生成脚本 `exit 0`，但你点名的输出文件时间戳或 md5 没变时。
- 当脚本打印 `*_DONE` / `FLOW_DONE` / "导出成功" 这类收尾词，而中间某步的错误被管道或子 shell 吞掉时。
- 当 Tcl/脚本里出现 `catch {…} var` 且后面用 `if {$var ne "no-error"}` 这类**哨兵字符串**判成败时。
- 当你（或模型）在提交信息 / 报告里写了"改了 X"，而那次命令实际带断言且可能中途退出时。
- 当一条链里用 `… || die` 判成败，而被调脚本无论判成什么都返回 0 时。

## 3. 不适用 / 失效条件

- 不适用：脚本本身正确非零退出并把错误打全——那是失败分叉，不是本条。
- 不适用：无产物可核对的场合（例如纯推理、纯代码评审）；本条只判"动作有没有落到文件上"。
- 失效：换用带事务语义的工具（先写临时再原子替换、失败自动回滚）后，"部分落盘"这一半不再成立；"退出码不等于产物"仍成立。
- 不许越界：本条不建议改退出码语义来让门禁变绿；只要求把"产物核对"补上。
- 不适用：交互式 GUI 操作（没有 rc 可读）——那要落的是截图/导出件与时间戳。

## 4. 前置条件

- 可读的工件目录与 `md5sum`/`stat`/`cmp`；Windows 侧用 Git Bash（MSYS）。
- 一份"本轮预期要动哪些文件"的清单（本仓做法：成套产物按 md5 冻结，见 `build/freeze_evidence.sh` 的用法说明在 `skill/README.md` 的 C 表）。
- 脚本落盘日志的位置（本仓形状：构建控制台 `build/rNN_build_console.txt`、run 自己的 `impl_1/runme.log`）。
- 不需要重跑长流程即可做本条的核对（本条全部是只读动作）。

## 5. 使用方法

1. 记基线：`md5sum build/system.bit build/timing_summary.rpt | cut -c1-12`（示例取值）。
   完成后应看到：两枚 12 位前缀，抄进本轮记录。
2. 跑生成脚本，同时保留它自己的日志；不要用 `| tail` 包一层（管道会吃掉退出码，本仓同类事故见 `report/log/ISSUES.md` 的 #69 族）。
   完成后应看到：一条明确的 rc 值 + 日志文件路径。
3. 立刻重做步骤 1 并比对：md5 相同 ⇒ "这次什么都没写出来"，与"写出来但没变"这两件事**必须分开说**。
   完成后应看到：一句结论（新 md5 / 同 md5 / 文件缺失）。
4. 读构建脚本自身的入口口径：本仓把"哪条脚本能用"写成文档判据 —— `build/tcl/README.md:19-23` 点名两支脚本
   因根目录少解析一层而 `add_files` 报错却仍 `exit 0`。
   完成后应看到：你确认了"我只认这一条规范入口"，并且核对的是报告时间戳不是退出码。
5. 检查器/钩子里判成败只认 `catch` 的返回码，消息单独一个变量：
   `if {[catch {phys_opt_design …} msg]} { … }`；禁止自己造的哨兵字符串与 `catch` 共用变量名。
   完成后应看到：成功路径不再触发 `error`，且日志里留下 `pins_before=` / `replica_cells=` 这类机制确实动过的字段。
6. 对"打印了成功"这一步，做一次故意失败：占住输出目录/文件再跑（本仓形状：`rm -rf "$OUT"` 失败那一支）。
   完成后应看到：脚本停下并打印"不要信成功那几行，先数文件数"（本仓形状 `build/make_submission.sh:731-733`），
   而不是继续生成半空产物。
7. 对"替换/改写类"手术（批量改文档、改脚本），加**替换生效**断言并在断言失败时清理临时件：
   本仓形状 `build/roll_isolated.sh:30` 的 `REFUSE: outdir 那一行没被改写（正式脚本的写法变了，先去看一眼）`。
   完成后应看到：要么 REFUSE 要么产物确实变了；不允许"改了 2/3 处却报成功"。
8. 把每轮的身份写进被跟踪的件里，用一条命令可回读：
   本仓形状 `git show HEAD:build/system.bit | md5sum` 与 `md5sum build/system.bit` 对照（`report/log/ISSUES.md` #332 就是用它抓出"采纳笔没把位流提交进去"）。
   完成后应看到：两个 12 位前缀相等（本轮 2026-10-04 实测两侧都是 `cd04907e1369`）。

## 6. 判读与失败分叉

- 步骤 1：
  通过 = 两枚 md5 都能读到。
  失败 = 文件不存在 ⇒ 本条从步骤 1 起就不成立，先确认产物路径。
  读不到输入 = md5 输出为空（文件 0 字节）⇒ `NOT_MEASURED`，记下"0 字节"这件事本身（见 `who-else-writes-this-artifact`）。
- 步骤 2：
  通过 = 有 rc 且有日志。
  失败 = rc 来自管道右侧 ⇒ `FAIL`，改成先落盘再读。
  读不到输入 = 日志路径未知（脚本把 `vivado.log` 丢在当前目录）⇒ `NOT_MEASURED`，下次带 `-nojournal -log <路径>`。
- 步骤 3：
  通过 = md5 变了且与预期一致。
  失败 = md5 未变而 rc=0 ⇒ 判 `FAIL`：把"脚本自报成功"降级为"未产生工件"，去读日志正文找它在哪一步停的。
  读不到输入 = 目标文件被别的进程占着 ⇒ `NOT_MEASURED`，先查谁在写（见 `who-else-writes-this-artifact`）。
- 步骤 4：
  通过 = 你用的入口被文档确认为唯一规范入口。
  失败 = 用的是历史/局部脚本 ⇒ `FAIL`，改回规范入口；同名不同结果的旧脚本留着只为对照。
  读不到输入 = 工程里没有这类说明 ⇒ `NOT_MEASURED`，自己先做一次"跑它，看产物变不变"的判别实验。
- 步骤 5：
  通过 = 成功不触发 error，且日志有机制字段。
  失败 = 成功却走了失败分支 ⇒ `FAIL`，这就是哨兵与返回码混用的形状（本仓 #327：一次**已经成立**的切割被读成失败，`error` 把整条 impl run 打死）。
  读不到输入 = 机制字段只在 run 自己的日志里、你没读那一份 ⇒ `NOT_MEASURED`（本仓 #327 的"出水口"教训：钩子的 `puts` 落在 `impl_1/runme.log`，链子 grep 的是顶层控制台）。
- 步骤 6：
  通过 = 故意失败时脚本停下。
  失败 = 仍打印成功 ⇒ `FAIL`，先加 `|| { echo …; exit 1; }` 再重跑，并核文件数。
  读不到输入 = 你没法制造失败条件 ⇒ `NOT_MEASURED`，改用只读断言（数文件数 ≥ 阈值）。
- 步骤 7：
  通过 = REFUSE 或产物已变。
  失败 = 断言失败但临时件残留 ⇒ `FAIL`，把清理写进失败分支（本仓 `build/roll_isolated.sh:30` 的失败分支里带 `rm -f "$TMP"`）。
  读不到输入 = 断言本身读不到目标行（写法变了）⇒ `NOT_MEASURED`，先去看现在的写法。
- 步骤 8：
  通过 = 工作树与 HEAD 的 md5 相等。
  失败 = 不等 ⇒ `FAIL`，说明"板上有/产物有"与"仓库里有"是三件事（本仓 #332）。
  读不到输入 = 该产物不入库（`.gitignore` 排除）⇒ `NOT_MEASURED`，改用冻结目录实体拷贝，不要写"引用活路径"。

## 7. 已验证的效果

- 本轮实跑（2026-10-04，只读）：`md5sum build/system.bit | cut -c1-12` 与 `git show HEAD:build/system.bit | md5sum | cut -c1-12`
  都打出 `cd04907e1369` ⇒ 步骤 8 这条核对在当前仓库是**绿的**；
  同一枚前缀被 `board/ACCEPTANCE.md` 的 E6 行点名（"板上现在跑的是 r118，bit `cd04907e1369`"）。
- 基线（不用本条时的历史事故，都来自仓库件，本轮未重演）：
  1. `build/tcl/README.md:19-23`：`build_system.tcl`、`build_pl_full.tcl` 少解析一层 ⇒ `add_files` 报错却 `exit 0`（台账 `report/log/ISSUES.md` #22/#41）；

  3. `report/log/ISSUES.md` #327（2026-10-04 04:01）：`catch` 返回码当哨兵 ⇒ `impl_1/runme.log:514/571` 证明切割已成立，脚本却把自己的载体打死；

## 8. 提炼来源与边界

- 证据：`build/tcl/README.md` §1；`report/log/ISSUES.md` #22/#41/#327/#329/#332/#324 与 2026-10-01、2026-10-02 两个日期小节；件 `build/make_submission.sh:723`、`build/roll_isolated.sh:22/27/30`、`build/board_verify.sh:116-118`（脚本原先无总判定、无论中间红成都 `exit 0` 的那段注释）。
- 工具行为断言的来源行见 `skill/pitfalls/_proposed-sources.md`。
- 停止适用的条件：当你的流程里每个动作都产出一个"必须新写入"的身份件（md5 + 时间戳 + 由门禁回读），本条被那条门禁吸收。
- 迁移到新题目/新板卡要改的地方：
  1. 产物清单（本仓是 `system.bit`/`system.xsa`/`ps_app.elf` + 六份 `.rpt`，示例取值，需按自身工程替换）；
  2. "唯一规范入口"那一行要换成你的构建入口脚本名；
  3. 位流是否入 git（本仓入，`build/tcl/README.md` 与 `report/BUILD.md` §7 说明不入库时改用实体拷贝冻结）；
  4. 工具日志的"出水口"位置（Vivado 是 `impl_<n>/runme.log`；Vitis/xsdb 是另一处；换家族/换工具要重新认）。
