## 1. 一句话用途

先分"编码坏了"还是"行为坏了"。

## 2. 适用场景

- 当控制台/日志里一句中文变成"一大长串空白"或乱码，而你正要据此下结论时。
- 当台架 `$display` 出的判据标签缺字、半个字，或名字参数超长被从**左边**截掉时。
- 当串口/网络回包字节统计显示大量 0x80+ 字节、而 `0x20` 很少，你据此要说"设备在打空格"时。
- 当 `Tcl` 报 `invalid command name`、报错串里出现 `？` 之类的怪字符，位置在文件第一行时。
- 当编码检查器（本仓 `src/host/doc_enc_check.mjs`）对手写件报坏行，而那些文件是原始命令输出（`ping`、串口）时。
- 当你新加的机器可读 token（PASS/FAIL/RESULT 之外的第三种状态词）含非 ASCII 时。

## 3. 不适用 / 失效条件

- 不适用：坏的是设计行为本身（屏上现象、数值错），不是渲染——那按现象类条目查。
- 不适用：全程 UTF-8 且码页 65001 的 Linux 主机；本条的 GBK/CP936 部分只在 Windows 中文码页现场成立（已量到的环境见第 8 节）。
- 失效：换仿真器/换工具版本后 `$display` 的截断行为要重量（本仓明确记过"这些是工具行为不是语言规范"）。
- 不许越界：本条不建议把文档正文改成 ASCII 来骗过编码检查——只把**会被解析成状态词**的 token 保持 ASCII，正文继续用中文。
- 不适用：只被工具读、不给人看的机器件（如 `.dcp`），没有码页问题。

## 4. 前置条件

- 能读原始字节：`od -c`、`iconv -f GBK -t UTF-8`（或 `//TRANSLIT`）、`python` 逐字点数。
- 编码检查器与它的自检入口（本仓：`node src/host/doc_enc_check.mjs --self`，自检会造三条坏行必须抓到三条）。
- 已知扫描口径：本仓只扫手写扩展名（`.md .v .c .h .mjs .sh .ps1 .tcl`），`*.txt` 原始回显**一律不扫**
  （`src/host/doc_enc_check.mjs:25` 的 EXT 集合与 `:35` 的 `BOM_OK_EXT` 允许 `.ps1/.tcl` 只有第 0 个字符是 BOM）。
- 串口/终端工具的本地回显设置：本仓固件侧默认把回显关掉（`echo [0|1]`，默认 0），配 Vitis 终端用。

## 5. 使用方法

1. 先量字节再看渲染：对那份可疑输出跑 `python -c "d=open(p,'rb').read(); print(sum(1 for x in d if x>127), d.count(0x20))"`（示例取值）。
   完成后应看到：两个计数（本仓一次实测 `split` 的回复 204 字节里 90 个是 0x80+ 的 UTF-8 中文字节、`0x20` 只有 22 个）⇒ 说明"空白"是**渲染不出来**，不是设备在打空格。
2. 判文件是不是 BOM 开头：`od -c <脚本> | head -2` 看前三个字节。
   完成后应看到：`357 273 277`（= EF BB BF）说明有 UTF-8 BOM；本仓形状是 Tcl 在第一行报 `invalid command name "？#"`。
   若命中，去掉 BOM 再跑，并把"哪条入口路径全中带 BOM"写进记录（本仓只有下板那一条路带，常用入口都不带）。
3. 原始命令输出落盘后**先转码再入库**：`iconv -f GBK -t UTF-8 <原始> > <入库件>`；
   入库件点名它来自哪一份原始件。
   完成后应看到：编码检查对它绿（GBK 原样进 git 会红成"文档坏了"，看着像文档问题、不像捕获问题）。
4. 机器可读 token 一律 ASCII：状态词、判据名、表头只写 ASCII，解释文字留在别处。
   完成后应看到：崩溃/中止时读到的仍是可判定的 ASCII 词，而不是一句被码页咬坏的话。
   （本仓反例形状：非 ASCII token 在 GBK 控制台上会把"一次崩溃"渲染成"一条红/一条空白"。）
5. 台架侧：判据标签与 `$display` 字段长度按字节核算。本仓实测两件事——
   字符串字面量赋给定宽向量或作为 task 实参时**每字节 bit7 被清**；字段超长时丢的是**头部**（左边截）。
   完成后应看到：日志里判据名完整可读；机器解析（`PASS`/`FAIL`/`RESULT`）不受影响这件事要单独确认一次。
6. 用检查器的自检做判别实验：`node src/host/doc_enc_check.mjs --self`。
   完成后应看到：三条坏行被抓到、好行不误报；若反例不红，说明这把尺子没牙，先修尺子再判文档。
7. 读日志里的行一律加 `-a`（本仓所有解析都是 `grep -a`），并在管道之外单独落盘，避免"二进制可疑 ⇒ grep 不输出 ⇒ 被当成没有这行"。
   完成后应看到：可疑行原样出现，可判是编码问题还是内容缺失。

## 6. 判读与失败分叉

- 步骤 1：
  通过 = 0x80+ 多但 `0x20` 少 ⇒ 判定为渲染问题，行为正常。
  失败 = 两个都少 ⇒ `FAIL`，真的是设备没回；转通信类排查（本仓 `board/` 那一侧）。
  读不到输入 = 拿不到原始字节（只有转码后的）⇒ `NOT_MEASURED`，重新采一次原始件。
- 步骤 2：
  通过 = 无 BOM 且 Tcl 正常解析。
  失败 = 有 BOM ⇒ `FAIL`，去 BOM 后重跑；同时把该文件加进编码检查的口径说明里（本仓允许 `.ps1/.tcl` 第 0 字符为 BOM）。
  读不到输入 = 文件不在 ⇒ `NOT_MEASURED`，先确认你读的是不是被覆盖过的那一份（见 `who-else-writes-this-artifact`）。
- 步骤 3：
  通过 = 入库件 UTF-8 可解、编码检查绿。
  失败 = 入库件仍红 ⇒ 转码方向或来源码页错，按工具实际码页重转（本机是 CP936/GBK 输出的工具：Vivado/Windows 的 `ping` 等）。
  读不到输入 = 原始件缺失 ⇒ `NOT_MEASURED`，本仓做法是让捕获脚本**自己产出**被跟踪的原始回显，而不是手抄。
- 步骤 4：
  通过 = 状态词全 ASCII。
  失败 = 出现非 ASCII 状态词 ⇒ `FAIL`，改词并保留一份"旧词读成什么"的对照（防止历史件被重放时判语漂移）。
  读不到输入 = 无法确定哪些词会被机器读 ⇒ `NOT_MEASURED`，先 grep 下游谁在匹配这些行。
- 步骤 5：
  通过 = 判据名在日志里完整。
  失败 = 名字被截 ⇒ 按字节重算字段宽度（本仓实测：`chk()` 名字参数只有 100 字节，中文标签 UTF-8 是 3 字节/字 ⇒ 6~7 个汉字就溢出）。
  读不到输入 = 日志里没有该行 ⇒ `NOT_MEASURED`，可能是别的进程也在写（见 `who-else-writes-this-artifact`）。
- 步骤 6：
  通过 = 三条坏行全抓到。
  失败 = 抓到 0 条或误报好行 ⇒ `FAIL`，先修检查器（判据没牙比文档坏更贵）。
  读不到输入 = 检查器跑不起来（无 node）⇒ `NOT_MEASURED`，改用一个只读的 `grep -aP '\xEF\xBF\xBD'` 之类临时判据并注明临时。
- 步骤 7：
  通过 = 能打出原文行。
  失败 = 加了 `-a` 仍无输出 ⇒ 真的没有这一行，回到内容缺失分支。
  读不到输入 = 文件为空 ⇒ `NOT_MEASURED`，见 `win-bash-path-split` 步骤 3 的 0 字节分支。

## 7. 已验证的效果

- 本轮实跑（2026-10-04，只读，逐字节数 >127 的 Tcl 文件）：
  `python -c` 扫 `build/tcl/*.tcl` 得 `NONASCII_FILES=65`，最高的一份是 `build/tcl/build_system_axigpio.tcl`（6834 个字节）。
  ⇒ 结论只能写成这样：台账里"探针脚本全文 ASCII"那条规矩（`report/log/ISSUES.md` #307 的处理与"规矩升级"句）**没有对应的机器判据**，
  所以它只落在个别探针上；本轮新增 0 个 ASCII 化的 Tcl。
- 基线（不用本条时的错判，件为台账）：
  1. `report/log/ISSUES.md` #307（2026-10-04 00:40）——`build/tcl/r115_window_true_probe.tcl` 死在 `rowline`，报错把整个 `foreach` 体贴出来当命令，位置是一句中文注释；
  2. 该文件第 5810–5811 行——把"渲染不出中文"读成"固件在打空格"（同处第 5844 行给出 ASCII 化之后的对照读数）；
  3. 该文件第 784 行——看到 shell 乱码输出，就当成"那份抓取里有停止行"，引用了一条根本不存在的证据；
  4. 该文件第 1938–1941 行——BOM（`EF BB BF`）让 `program_system.tcl` 第一行报 `invalid command name "？#"`；
  5. 该文件第 1958–1960 行——同族后果排序写明"假绿 > 假红"；
  6. 该文件第 6566–6568 行——`chk()` 名字参数 100 字节、中文 3 字节/字 ⇒ 从左边截。
- 未验证：本轮没有重跑任何 xsim 台架或串口捕获来做字节级对照（需要仿真器现场与板子），
  所以步骤 1、3、5 的"本机现在仍能复现"记 `【待验证】`；步骤 6 的 `--self` 本轮也未执行，记 `【待验证】`。

- 迁移到新题目/新板卡要改的地方：
  1. 工具栈：换非 Vivado/xsim 的仿真器要重量格式化输出对非 ASCII 的处理；
  2. 检查器：EXT 白名单与 BOM 白名单是你工程自己的约定（本仓值是示例取值，需按自身工程替换）；

  4. 器件家族无关，**主机与终端码页相关**。
