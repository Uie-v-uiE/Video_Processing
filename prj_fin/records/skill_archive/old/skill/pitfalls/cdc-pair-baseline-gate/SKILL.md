## 1. 一句话用途

门禁比配对集合，不比写死的行数。

## 2. 适用场景

- 当你正准备用"Critical 行数不超过 N"当交付门禁。
- 当连续两版都打印全绿，而你确实新增或改动过一处跨域。
- 当门禁输出里出现"基线有而本版没有"的那一行，却没人说得出为什么少。
- 当你改完 RTL 只知道端点数变了，点不出是谁跨的域。
- 当你新加了一条判红，却还没证明它**既能红也能绿**。
- 当你准备用固定列号去解析工具自己的报告。

## 3. 不适用 / 失效条件

- 单时钟设计。
- 还没建立基线的第一版：先人工把每条跨域过一遍，再冻基线。
- 综合阶段的 CDC 报告：由处理器侧生成的那个时钟此时还不存在，会漏行，别拿它当门禁。
- 功能正确性，以及"这条跨域上走的数是不是准静态"：结构性判据不判断这两件事。
- 失效：已布线检查点会被下一次强制重建工程删掉 ⇒ 只能在两次构建之间跑。
- 失效边界：基线跟着"被采纳的那一版"走，不跟着"最新一版"走（取保守的超集，即使新版本行数更少）。
- 不许乱归因：同一次改动里布局布线也变了，时序裕量的变化只能说"那一次实现量到多少"，
  不能说"改了 CDC 让 WNS 涨了多少"。
- 分界：一个发射触发器该喂几组同步器、一拍脉冲怎么跨域，在 `skill/pitfalls/pulse-toggle-cdc/SKILL.md`
  （旧编号 S11）；本页只管门禁怎么判"不许新增"。数据面正确性要靠台架与板级复验，不在本页能力内。

## 4. 前置条件

- 一份已布线（implement 之后）的检查点，能从它出带明细的 CDC 报告；综合阶段的报告不算。
- 一个入库的基线文件，一行一条配对（本仓 `build/CDC_BASELINE.txt`）。
- 一个能点名到寄存器的查询脚本（本仓 `build/tcl/cdc_who.tcl`）。
- 一个能自测判据的入口（本仓 `bash build/gates_cdc_test.sh`），且基线路径可被环境变量覆盖。
- 只读操作为主；跑检查点查询需要工具现场，本条目不含构建与仿真。

## 5. 使用方法

1. 把基线入库成一行一条 `源钟>目的钟 端点数 unsafe数`（本仓库 `build/CDC_BASELINE.txt`），
   门禁比集合而不是比阈值，并且三个方向各有态度：**新增配对判红**（多一条跨域才是真危险）；
   **变少也打印但不记功**——在说得出机制之前一律按坏消息处理（本仓库就有一条只因唯一的 unsafe 端点被删掉而降级的行），
   那一行仍留在基线里，钉住"这一堆端点的配对不许悄悄长回来"；
   **同配对端点数增长只提示**——加一级仲裁寄存就会 +1，判红会诱导人去绕开门禁，而红项一旦"必然红"整个门禁就没人看了。
   完成后应看到：三态各自的打印行，且红项只在"新增配对"时出现。
2. 再钉第二层：对 **unsafe 数增长判红**。端点数增长是中性事件，unsafe 增长不是——它等于"又多一处没被
   异步寄存器属性/握手保护住的采样点"；而且当它落在一条**已有**配对上时，只比配对集合的门禁一声不响。
   完成后应看到：unsafe 增长的行被单独标出（同配对上 1→3 这种必须红）。
3. 要点名到人只能开带明细的那份报告：读**已布线**的检查点出带寄存器名的清单（`build/tcl/cdc_who.tcl`）。
   完成后应看到：典型形状是"同步器之前有组合逻辑"——RTL 里看着就是打两拍，是综合把状态机重编成 one-hot 之后，
   跨域路径变成"几个 one-hot 触发器经组合译码进两个目的触发器"。
   同步器之前不许有组合逻辑；格雷码的全部意义就是"每一位只依赖一个源触发器"。
4. 修法要从"让工具别改我"升级到"结构上就对"，两步都做：① 用属性禁止该寄存器的状态机重编码；
   ② 把跨域寄存器的下一状态**按位写成格雷环**（四状态环 `00→01→11→10→00` 的下一状态恰好等于 `{b0, ~b1}`）。
   ① 依赖工具的善意，② 是结构事实；式子是手推的，所以必须配一条台架项
   （四步落在四个状态、每步只动一位、四态互不相同）把"抄错编码"这种失败模式堵在仿真里。
   完成后应看到：属性在、格雷环在、且那条台架项在案。
5. 每条新判红自带反例，五个 case 缺一不可：真实失败件必须红 / 把那一列改回基线值必须**绿**
   （没有第二条，"永远红的判据"和"真判据"长得一模一样）/ 凭空多一条配对必须红 /
   基线某行少一列必须红（不许当成 0 混过去）/ 基线文件不存在必须红（原来是 WARN，等于没门禁还打印出 PASS 的形状）。
   为此让基线路径可被环境变量覆盖，测试只喂自己那份坏基线，不许动仓库里真的那份；
   **改了这段解析就必须重跑它**（`bash build/gates_cdc_test.sh`），否则红的是你的判据本身。
   完成后应看到：五个 case 的期望值逐条对上。
6. 凡打印"记录用 / 不判红"的地方，都要能回答"它一直涨，谁会在什么时候知道"：要么定期清账，要么把判据写实，
   第三条路是删掉并在提交信息里说为什么——那类提示行挂十几版没人看，底下压着的就是一条 Critical。
   完成后应看到：每条提示行都能说出记账人或触发条件。

## 6. 判读与失败分叉

- 一条命令出红/绿：`bash build/gates_cdc_test.sh` 五个 case 全部符合预期才退 0。
  失败 = 退非 0 ⇒ 有一面缺（恒红或恒绿），回步骤 5 补那一面，别把这一项关掉。
- 检查器自己的两面对照（同报告双脚本）：同一份实现后报告喂旧脚本 → PASS、喂新脚本 → FAIL，
  且新门禁对基线那一版给出正确的 PASS——这才叫抓住了曾经漏掉的那两版。
  读不到输入 = 那份实现后报告不在 ⇒ `NOT_MEASURED`，先去跑一次只读的报告导出，别凭记忆比对。
- 数字关系：同一条配对上 unsafe `1 → 3` 必须红，而端点 `17 → 71` 不许红（只提示）；
  两者混淆就说明只钉了配对。失败 = 端点增长也判红 ⇒ 门禁会诱导绕开；unsafe 增长不红 ⇒ 第 2 层没钉上。
- 解析层判据：端点数取**倒数第 5 个字段**、unsafe 取**倒数第 3 个**，不用固定列号——
  类型描述字段的 token 数会变（有的四类、有的两类），按固定列号会把别的等级读成 0。
  失败 = 解析出 0 而报告里明明有数 ⇒ 列号漂移，判 `FAIL`；一行都读不到 ⇒ `NOT_MEASURED`。

## 7. 已验证的效果

- 历史事故（本条的来源）：一条已有配对上 unsafe 从 1 悄悄长到 3 而门禁全绿
  （`report/log/ISSUES.md` #65，加宽总线那一次见 #71）；写死阈值放过两次真实退化、
  以及状态机重编码那一族见 `report/log/CHANGELOG_V7.md` 的门禁历史表。
- 本轮只读核对（2026-10-04，只读文件不跑工具）：`build/CDC_BASELINE.txt` 现存 4 行配对数据，
  格式与第 5 节步骤 1 一致（`源钟>目的钟 端点数 unsafe数`），unsafe 列依次 1/1/1/2；
  其中一行正是 17 个端点、1 个 unsafe（即第 6 节"端点 17 → 71 不许红"所指的形状），
  文件头注释自记 unsafe 1→3 那次的来历，以及"唯一 unsafe 端点被删掉导致降级、基线仍保留该行"那条决定。
- 本轮**未重跑** `build/gates_cdc_test.sh`，也未读任何检查点（本轮不做构建/仿真类操作）：
  五个 case 现在是否仍全部符合预期记【待验证】；"旧脚本 PASS / 新脚本 FAIL"那面对照同样记【待验证】。

## 8. 提炼来源与边界

- 来源证据：`report/log/ISSUES.md` #65、#71；`report/log/CHANGELOG_V7.md` 的门禁历史表；
  形状件 `build/CDC_BASELINE.txt`、`build/tcl/cdc_who.tcl`、`build/gates_cdc_test.sh`；
  工具行为断言与来源行见 `skill/pitfalls/_proposed-sources.md`（本目录不写 `_meta/`）。
- 旧编号：本条由旧卡 S16 迁移而来，内容未增删，只按八节重排。
- 不再适用的条件：设计只有一个时钟域；或你手里只有综合阶段的报告（会漏行）。
- 迁移到新题目/新板卡要改的地方：
  1. 基线文件路径与环境变量名（本仓 `build/CDC_BASELINE.txt`，示例取值）；
  2. 明细查询脚本与它的调用形式（本仓 `build/tcl/cdc_who.tcl`）；
  3. 解析的字段位置（倒数第 5 / 倒数第 3 是本仓那份报告的形状，换工具或换版本要重量一次）；
  4. 自测入口（本仓 `bash build/gates_cdc_test.sh`）与它那五个 case 的喂法。
- 平台相关：与器件家族无关；与工具版本的**报告排版**强相关（列数一变，解析层判据就要重量）。
