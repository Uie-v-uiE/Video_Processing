## 1. 先建立三个坐标系

学视频处理最容易乱的地方，不是算法，而是坐标系。这个项目里同时存在三套坐标，混一次就会得到“看起来差不多、其实错一列”的结果。

**显示坐标**：屏幕上的 `(x, y)`。本项目是 1024×600，`x` 从 0 到 1023，`y` 从 0 到 599。它由 `video_timing` 数出来，和 HDMI 的扫描一一对应。

**面板/画幅坐标**：一条显示行里的第几个“显示像素对”，以及第几个“显示行对”。因为源是 512×300，屏是 1024×600，水平和垂直都正好是 2 倍，所以 `x >> 1` 和 `y >> 1` 把显示坐标折成源坐标的整数部分。

**源坐标**：帧缓存里的 `(sx, sy)`，范围 0..511 和 0..299。缩放和旋转改变的就是“显示坐标映射到哪个源坐标”。

三者的关系可以写成：

```text
显示像素 (x, y)
   │  逆映射：zoom / rotate
   ▼
源坐标 (sx, sy) + 越界标志 + 小数 (fx, fy)
   │  双线性读口
   ▼
源像素值
```

关键点是：**几何只做一次**。原图抽头和处理抽头共用同一条 `(sx, sy)` 地址流，所以两侧的画面不会各算一套几何。竖缝只是在这条流上把两个像素抽头二选一，不改变坐标。这是“同帧对照”在数学上成立的前提。

> 常见误解：把“分割线”理解成两个独立的显示窗口。只要两个窗口各自算一套坐标，旋转和缩放就必然在缝上错位。本项目的做法是“一个视口、一条地址流、逐像素选择”，缝只是选择位变化的地方。

## 2. 视频与显示：一行像素是怎么被扫出来的

### 2.1 有效区与消隐

显示器不是“送来一帧就显示一帧”，它按固定的节拍逐行扫描。一行的时间被分成有效像素和消隐：消隐里要放行同步，场与场之间还要放场同步。本项目的时序是：

```text
H: 1024 有效 + 44 前肩 + 88 同步 + 188 后肩 = 1344 拍
V: 600 有效 + 3 前肩 + 6 同步 + 16 后肩 = 625 行
像素钟 50 MHz，场频 = 50e6 / (1344 × 625) ≈ 59.5 Hz
```

`de`（data enable）在有效区为 1，消隐为 0；`hs` 是行同步，`vs` 是场同步。所有像素处理都只看 `de`，不看“第几拍”，因为消隐长度一改，按拍计数的逻辑就会错位。这条规矩在本项目的每个模块里都出现过：`raw_line_delay` 的读写、效果链的行尾补偿、OSD 的列计数，全部以 `de` 和有效像素数为准。

### 2.2 为什么源是 512×300，屏是 1024×600

源画面小，屏大，最直接的做法是每个源像素在水平和垂直方向各复制一次：一个源像素变成 2×2 的显示块。这样做的代价是横向空间尺度变了：效果链的 3×3 窗口在显示域工作，相邻两列在源上只差半个像素，所以横向窗口半径是 0.5 个源像素。这是本项目明确的取舍，不是 bug。如果以后要回到源域等距，就要给整条链加时钟使能，只在偶数列进链，那会同时改变延迟和行缓存地址，属于架构级改动。

### 2.3 一行像素的“行李”

视频处理里，一个像素往往不是单独走，而是带着几样“行李”：

- 它属于哪一行、哪一列（坐标标签）；
- 它是否在画面内（越界位 `oob`）；
- 它是否有效（`de`）；
- 它属于哪个片源、哪一帧（帧号/片源位）。

本项目的很多 bug，本质都是“像素到了，行李没跟上”：标签比内容早一拍、晚一行，或者越界位绕过了行环。读代码时，看到一个像素信号，就要顺手问一句：和它一起走的控制位是谁，它们是不是同一条流水线、同一个环。

### 2.4 自检问题

1. 为什么所有按拍计数的逻辑都要改成按 `de` 计数？如果一行从 1344 拍改成 1400 拍，哪些逻辑会坏？
2. 一个源像素在屏上占 2×2，效果链的横向 3×3 窗口覆盖多少个源像素？纵向呢？
3. `hs` 和 `de` 的边沿差多少拍？行首预读为什么要等 `de` 掉下去那一拍？

## 3. 以太网接收：一帧视频为什么要被拆成很多包

### 3.1 UDP 的“足够好”

视频是连续的，丢一帧的代价远小于等一帧。UDP 不重传、不保证顺序、不保证到达，正好适合“实时优先”的场景。代价是应用层要自己处理丢包、乱序和重复。本项目的做法是：每个 UDP 载荷带一个“帧内字节偏移”，接收侧按偏移把数据写进帧缓存，最后用“整帧字节数到齐 + 所有行被覆盖 + 没有坏包”三个条件决定这一帧能不能显示。

### 3.2 RGMII 与 IDDR

RGMII 在 125 MHz 的双沿上传 4 位数据，等效 1 Gbps。PHY 送来的 `rx_ctl` 和 `rxd[3:0]` 先在 PHY 恢复时钟 `eth_rxc` 上用 IDDR 采样，得到每个时钟沿的 8 位数据。恢复时钟只在这个边界和异步 FIFO 的写侧出现，后面的 MAC、UDP、重组全部在 MMCM 产生的 125 MHz `clk_eth` 上。这是一个很典型的“把不可控的时钟关在最小边界里”的设计。

### 3.3 从包到帧

一帧 512×300 RGB565 是 307200 字节。按常见的 1392 字节 UDP 载荷，一帧大约 221 个包。接收侧要回答三个问题：

1. 这个包属于哪一帧？（帧号/来源）
2. 它应该写到帧内哪个偏移？（载荷头的偏移）
3. 这一帧现在收全了吗？（字节数 + 行覆盖 + 坏包）

`frame_reasm` 用一张行位图记录每个源行是否被覆盖，用字节计数记录总量，用坏包标志记录本帧是否出现过错误。只有三个条件同时满足才发 `frame_done`。这个“整帧才提交”的语义让显示侧永远看不到半帧。

### 3.4 带宽账

512×300×2 字节×30 fps ≈ 9.2 MB/s。千兆以太网理论 125 MB/s，实际 UDP 吞吐通常 100 MB/s 以上，所以**当前画幅的带宽余量很大**。这也是为什么项目没有走压缩、没有走 10G、也没有换更重的协议栈：瓶颈不在网络，而在显示侧的 BRAM 和读口。

如果把源换成 1080p60 RGB565：1920×1080×2×60 ≈ 249 MB/s，已经超过单根千兆网的实际 UDP 吞吐；换成 1080p30 约 124 MB/s，贴着千兆的上限。要上 1080p60，需要压缩（H.264/JPEG）、10G 以太网，或者多根网线聚合。这是“高像素带宽够不够”的第一层答案：**当前 512×300@30 够，1080p60 原样传不够**。

### 3.5 自检问题

1. 一帧 512×300 RGB565 有多少字节？按 1392 字节载荷需要多少包？
2. 为什么“字节数到齐”还不够，还要“所有行被覆盖”？
3. 如果一帧丢了中间一个包，但后面的包都到了，`frame_reasm` 应该发 `frame_done` 还是 `frame_abort`？为什么？

## 4. Zynq 的软硬件分工：为什么像素不经过 ARM

Zynq 的 PS 是 ARM Cortex-A9，PL 是 FPGA。两者通过 AXI 互联。一个常见的误区是“PS 也能处理像素，为什么不用 PS”。原因有三个：

1. **确定性**：像素通路要在 50 MHz 下每拍出一个像素，任何 CPU 调度、缓存未命中、DDR 争用都会变成可见的抖动。PL 的流水线延迟由级数决定，与软件状态无关。
2. **带宽**：一帧 307200 字节，30 fps 就是 9.2 MB/s。让 CPU 逐字节搬不是做不到，但会占满一个核，而且很难和显示时序对齐。
3. **可观测性**：PL 可以在每个像素上打标签、计数、做完整性检查，CPU 只能看到“帧到了没有”。

本项目的分工是：

- **PL**：RGMII、MAC、UDP、重组、DDR 写、帧缓存、几何、效果、竖缝、OSD、TMDS。
- **PS**：写控制寄存器、读状态 lane、把 SD 卡帧 DMA 进 PS 的 DDR、跑命令解析和自检脚本。

PS 和 PL 之间有三组 AXI GPIO：一组写控制字，一组读状态窗口，一组写 gamma 表和 OSD 显示值。控制字跨到像素域时走三级同步链，新增位往高位加，不重排已有位。这是 ABI 纪律：RTL 位定义、固件写出的字、上位机掩码三处必须同源。

### 4.1 板级边界：先把插座和器件数清楚

整体架构要从板子外面往里看，而不是从模块名往里猜。本项目的板级边界是：

| 边界 | 器件/接口 | 接到哪里 | 作用 |
|---|---|---|---|
| 网络 | PL 侧 RJ45 + RTL8211F-CG | PL 的 RGMII 引脚 | 收上位机 UDP 视频，发 ARP/ICMP/遥测 |
| 显示 | HDMI 接口 + TMDS 差分对 | PL 的 TMDS 引脚 | 1024×600、59.5 Hz 输出 |
| 内存 | DDR3 | PS 的 DDR 控制器 | ETH/SD 帧的乒乓缓存 |
| 启动 | QSPI NOR | PS 的 QSPI 控制器 | 断电自启的 BOOT.bin |
| 存储 | microSD | PS 的 SD 控制器 | 本地帧序列回放 |
| 调试 | USB-C JTAG/UART 桥 | PS 的 UART0 + JTAG | 命令、状态、下载和健康快照 |
| 时钟 | 50 MHz 板载时钟 W17 | PL 的 `sys_clk` | MMCM 输入；PS 另有时钟 |

这里最容易犯的错，是把“PS 的以太网”和“PL 的以太网”混为一谈。本项目的数据通路走 PL 侧 RJ45，PS 只通过 AXI GPIO 读写控制和状态；PS 的 UART/SD/QSPI 是控制与启动外设，不参与像素搬运。板级边界一旦画错，后面所有“为什么不用 PS 搬像素”的讨论都会跑偏。

### 4.2 时钟与复位：五个时钟域，各自只做一件事

| 时钟 | 频率 | 来源 | 只做什么 |
|---|---:|---|---|
| `sys_clk` | 50 MHz | 板载 W17，20 ns 约束 | MMCM 输入、PS 参考 |
| `clkout0_1` | 50 MHz | MMCM | 像素、几何、效果、OSD、TMDS |
| `clkout3` | 125 MHz | MMCM | 以太网协议逻辑 |
| `eth_rxc` | 125 MHz | PHY 恢复时钟 | 只做 IDDR 采样和异步 FIFO 写侧 |
| `clk_fpga_0` | 100 MHz | PS FCLK0 | AXI 控制、DDR 写侧 |

MMCM 的 VCO 是 1000 MHz：50 MHz 像素、250 MHz 串化参考、200 MHz IDELAY 参考、125 MHz 协议逻辑和 125 MHz 90° 发送时钟都从它分频出来。PS 的 AXI 时钟是另一颗 MMCM/PS PLL 产生的 100 MHz，所以“像素域 → AXI 域”和“ETH 域 → 像素域”都是真正的异步边界，不能靠同一个时钟沿去假设关系。

复位分两层：PS 出来的系统复位先在各域做异步置位/同步释放；PL 内部再按区域生成本地复位。`rst_l_sync2` 驱动 3002 个异步清零端，是布局后最慢的恢复路径来源；`link_monitor` 另有一份本地复位树，避免所有模块共用同一个 CLR 驱动。复位不是“拉低再拉高”这么简单：异步复位端有 recovery/removal 检查，复位树的高扇出和物理距离会直接进时序报告。

### 4.3 数据面一：从网线到 DDR

网络入包链可以拆成四段：

```text
RJ45/PHY
  │ RGMII: 125 MHz DDR, 4 bit data + 1 bit ctl
  ▼
IDDR 采样（eth_rxc 域）
  ▼
异步 FIFO（eth_rxc → clkout3 125 MHz）
  ▼
MAC → ARP/ICMP → UDP 端口过滤 → 按帧内偏移重组
  ▼
16 位像素拼 64 位 → AXI HP0 主设备 → DDR 乒乓缓存
```

每一段的所有权要明确：

- **IDDR/异步 FIFO**：只负责把 PHY 恢复时钟域的数据安全搬过来，不解析协议。
- **MAC/UDP/重组**：只认 5001 端口和合法长度；重组器维护字节门、行覆盖位图和坏包门，三个条件同时成立才发 `frame_commit`。
- **AXI 打包器**：把 16 位像素拼成 64 位字，按突发写 DDR；满 FIFO + flush 时尾字不能丢。
- **DDR 乒乓**：ETH 和 SD 各有自己的 bank；显示侧只在整帧提交后切换读口，屏幕上不会出现半新半旧的一帧。

这条链的“提交点”在整个架构里非常关键：它不是“收到最后一个包”就提交，而是“字节数到齐 + 所有源行被覆盖 + 本帧没有坏包”三件事同时成立。提交点之前，DDR 里的旧帧仍然可读；提交点之后，新帧才允许被显示侧看到。这是无撕裂显示和作废计数的基础。

### 4.4 数据面二：从 DDR 到 HDMI

显示侧是另一条独立的流水线：

```text
DDR 乒乓
  │ 整帧读回
  ▼
64 位 BRAM 帧缓存（512×300×16 bit）
  ▼
缩放/旋转逆映射（显示坐标 → 源坐标 + 小数 + 越界）
  ▼
双线性读口（4 邻点、2 行结果缓冲）
  ▼
六级效果链（固定 15 拍）
  ▼
同帧 A/B 竖缝（原图抽头 vs 处理结果）
  ▼
五行 OSD
  ▼
×2 展开 → TMDS 5:1 串化 → HDMI
```

这条链的所有权同样要拆开：

- **帧缓存**：一整帧 512×300×16 bit 放在 BRAM，约 307 KB；旋转和双线性需要随机读，不能只靠行缓存。
- **几何引擎**：把每个显示像素逆映射到源坐标；缩放和旋转共用一套算子，原图和处理图不会各算一套坐标。
- **双线性**：四个邻点、两个小数权重；结果缓冲 2 行，因为一对显示行共用一次源行读取。
- **效果链**：blur/sharpen/sobel/morph 等固定 15 拍；旁路也走同样级数，保证配置变化不改变延迟。
- **竖缝**：在显示列上逐像素二选一，左侧原图抽头、右侧处理结果；两侧共享几何和行标签。
- **OSD/TMDS**：OSD 叠五行文字，不改变竖缝几何；TMDS 把 24 位像素按 5:1 串化到差分对。

显示侧的“同一帧”不是靠两个缓存碰巧同步，而是靠一条地址流和一套行标签：原图抽头和处理结果都从同一个 `(sx, sy)` 派生，竖缝只改变选择位。这样旋转、缩放、双线性都不会在缝上产生几何错位。

### 4.5 控制面与观测：三组 AXI GPIO 和三个出口

PS 和 PL 之间不是一条“万能总线”，而是按职责分的三组 AXI GPIO：

| 组 | 方向 | 内容 |
|---|---|---|
| 控制字 | PS → PL | 源选择、缩放/旋转、效果、缝位、OSD、gamma |
| 状态 lane | PL → PS | 帧数、包数、坏包、作废、缺行、时延、处理窗完整性 |
| 表/显示 | PS → PL | gamma 表、OSD 显示值 |

控制字跨到像素域时走“整字更新 + 翻转沿 + 三级同步”，不是每个 bit 各自同步；新增位往高位加，不重排已有位。这是 ABI 纪律：RTL 位定义、固件写出的字、上位机掩码三处必须同源。

观测有三个出口，读的是同一组计数器：

1. **串口**：`stat`、`temp`、`link`，人直接在终端看。
2. **UDP 遥测**：每秒 32 字节信标，发给最后一个 ARP 请求方，PC 侧 `telemetry_listen.py` 收。
3. **AXI GPIO 快照**：JTAG 读回，用于健康检查和“控制字有没有真的到 PL”的对照。

三个出口不是重复建设，而是互相校验：串口和遥测对不上，说明其中一条读取路径或同步链有问题；GPIO 快照能区分“PL 没算对”和“PS 没读到”。

### 4.6 存储、带宽与延迟预算

先把量级摆在桌面上，后面的“为什么这样选”才有依据：

| 项 | 计算 | 读数 |
|---|---|---:|
| 源帧 | 512×300×2 B | 307,200 B |
| 源带宽 @30 fps | 307,200×30 | 9.216 MB/s（73.7 Mbps） |
| UDP 包数/帧 | ceil(307,200/1392) | 221 包 |
| 包率 | 221×30 | 6,630 包/s |
| 线上码率（含头/前导/FCS/IFG） | 6,630×1,458×8 | 约 77 Mbps（1 Gbps 的 7.7%） |
| 显示有效像素率 | 1024×600×59.5 | 36.56 Mpx/s |
| 显示 RGB565 载荷 | 36.56M×2 B | 73.1 MB/s |
| TMDS 串行率 | 50 MHz×10 bit×3 lane | 1.5 Gbps（含消隐） |
| DDR 读写 | 9.216 写 + 9.216 读 | 18.4 MB/s，约 800 MB/s 的 2.3% |
| 整帧 BRAM | 512×300×16 bit | 307 KB，约 80 个 36 Kb tile |

这张表解释了三件事：网络不是瓶颈（77 Mbps 对 1 Gbps）；显示侧的有效像素率由 50 MHz 像素钟和 1024×600 时序决定；BRAM 70% 是整帧随机读的代价，不是零散浪费。第 12.2 节会把 1392 字节、线速和换画幅的边界逐项算开。

## 5. 几何引擎：从屏幕坐标反推源坐标

### 5.1 为什么是“反推”而不是“正推”

正推是“源像素 (sx,sy) 经过缩放旋转，落到屏幕哪个位置”。它在放大时会一个源像素覆盖多个显示像素，在旋转时会把源像素打到非整数坐标，显示侧还要做“谁落到这个格”的仲裁。反推是“屏幕上的每一个像素，回到源里取哪一个”。显示时序是逐像素扫描的，反推天然和扫描顺序一致，每个显示像素只需要一次地址计算和一次读口访问。这就是视频显示最常用的做法。

### 5.2 公式

先把屏幕坐标移到图像中心：

```text
dx = x - 512
dy = y - 300
```

其中 512 和 300 是显示画幅的一半（1024/2，600/2）。源中心是 256 和 150。设缩放倍率为 `z`（1.0 = 256/Q8），旋转角为 θ，逆变换是：先乘缩放、再反方向旋转：

```text
inv = 256 / z              // Q8 的逆缩放
rx  = dx * cosθ + dy * sinθ
ry  = -dx * sinθ + dy * cosθ
sx  = 256 + (rx * inv) >> 8
sy  = 150 + (ry * inv) >> 8
```

`cosθ` 和 `sinθ` 是 Q8 定点，来自 360 项的查找表。`>> 8` 把 Q16 的中间量折回源像素。整数部分进帧缓存地址，余数 `fx/fy` 进双线性插值。

一个具体例子：0°、1.0x 时 `inv=256`，`rx=dx`，`ry=dy`，于是

```text
sx = 256 + (x - 512) = x - 256
sy = 150 + (y - 300) = y - 150
```

再经过 2× 展开，`x=0..1023` 对应源列 `x>>1`，`y=0..599` 对应源行 `y>>1`。这就是“屏上每个格子来自源行/列”的定义式，台架 C1/C5/C6 一直在用它。

### 5.3 越界与旋转钳

`sx` 或 `sy` 落到 `[0,511]`/`[0,299]` 之外时，`oob=1`，显示侧把这一格填黑。旋转打开时，`zoom_ctrl` 会把倍率收进“当前角度刚好装得下”的一档，避免整幅转到画面外；手动档号不会丢，关掉旋转后恢复。0° 不受这条限制。

### 5.4 读地址为什么可以提前

效果链的内容整体滞后 4 行（四个窗口级各 1 行），双线性结果缓冲再滞后 2 行。显示侧不能“把数据提前”，但帧缓存是随机地址的，可以把**读地址**提前：

```text
请求行 = (y + OFF_LINES + BILIN_ROWS) >> 1
```

`OFF_LINES=4` 抵消窗口链的内容滞后，`BILIN_ROWS=2` 抵消双线性的结果缓冲。因为源行是 2× 展开的，提前量在显示行上加，折算成源行是除以 2；`BILIN_ROWS` 必须是偶数，否则一对显示行会分属两个源行，双线性的 A/B 抽头就会错行。

源行请求到达 300 时绕回 0。绕回发生在显示行 594 附近，不是帧首；这也是为什么“帧头 6 行”和“帧尾 6 行”在几何上不是同一件事。

## 6. 双线性插值：四个邻点、两个小数和一条行缓冲

### 6.1 公式

设源坐标的整数部分是 `(sx, sy)`，小数部分是 `(fx, fy)`，都是 Q8（0..255）。四个邻点是：

```text
p00 = src(sx,   sy)
p10 = src(sx+1, sy)
p01 = src(sx,   sy+1)
p11 = src(sx+1, sy+1)
```

先纵向、后横向：

```text
top    = p00 * (256 - fy) + p01 * fy
bottom = p10 * (256 - fy) + p11 * fy
p      = (top * (256 - fx) + bottom * fx) >> 16
```

RTL 里不截断中间量，所以结果和这个整数公式逐位一致。`bilin_en=0` 时把 `fx/fy` 钉成 0、把越界抽头折回，结果逐位退化为最近邻。这让我们可以在同一块板上比较“插值本身带来多少差异”。

### 6.2 一个源像素为什么用四个拍

显示是 1024 列，源是 512 列，每个源像素在横向占两个显示列；纵向也是两个显示行。一个源像素的四个邻点在四个显示拍里被读出：一对显示列里两拍同值，一对显示行里两拍同值。读口是单口的，每拍读一次 64 位字（四个源像素），所以一对显示行的结果要等到下一对才能读出来。这就是 2 行结果缓冲的来历。

结果缓冲是 1024×17 的乒乓：写当前一对、读上一对。索引用**显示列对号** `x[9:1]`，不是源列 `sx`。旋转时 `sx` 会沿一行停滞甚至倒退，用 `sx` 当地址会让同一个格子被另一个源行重写，屏上就是满屏噪点。这是“存储地址必须用稳定的扫描坐标，不能用内容坐标”的典型例子。

### 6.3 边界折回

`sx=511` 时，`sx+1` 会读到图外；`sy=299` 时同理。RTL 做两件事：把小数钉成 0，把越界抽头折回图内。这样图外那一格不会被读进窗口，也不需要初始化填充区。最后图外由顶层的 `oob` 统一填黑。

## 7. 六级效果链：固定 15 拍是怎么设计出来的

### 7.1 固定的意义

竖缝的左右两半必须在同一拍对齐。如果延迟随“打开了哪几级”变化，缝两侧就会有一个固定的列偏移；打开的效果越多，偏移越大。因此效果链的每一级都有一条**和算法路径等长的旁路路径**，无论算法开不开，延迟都一样。总延迟是 15 个像素时钟，这个数字只有一个真源：`proc_pipeline.LATENCY`。

逐拍账：

```text
gamma      0 拍（组合 LUT）
gray       1 拍
invert     1 拍
blur       3 拍
sharpen    3 拍
sobel      3 拍
binary     1 拍
morph      3 拍
总计      15 拍
```

### 7.2 3×3 窗口和行缓存

窗口级用两条行缓存 `lb0/lb1`，按列号索引。当前行从 `din` 进来，前一行在 `lb1`，前两行在 `lb0`。窗口是：

```text
q00 q01 q02      上一行
q10 q11 q12      中心行（上一输入行）
q20 q21 q22      当前行
```

中心抽头是 `q11`，所以每一级的内容都比输入晚 1 行。四个窗口级串起来，内容晚 4 行。旁路输出的是 `q11`，不是 `din`，否则旁路会比算法路径快一行，缝上会出现错位。

行尾有一个容易忽略的细节：中心抽头要经过 `q11 <= q12 <= lb1` 两级，最后一行最后一个有效像素在 `de` 掉下去时还没走到中心。因此窗口级在行尾多走一拍，把最后一列再移一次；读地址钉在末列，避免消隐期的 `x_in` 越界。

### 7.3 边界：把缺的邻居复制成中心

图像的第一行没有上一行，最后一行没有下一行。直接让行缓存读上一帧/下一帧的尾巴，会在边界产生一条假边。正确做法是 clamp-to-edge：缺的上邻用中心行复制，缺的下邻也用中心行复制。显示侧给四个窗口级加了 `V_ACTIVE` 参数和上/下沿 clamp；后来又进一步把 clamp 用的行标签按上游窗口级的行延迟对齐（见第 10 章）。

### 7.4 各算法的直觉

- **箱式模糊**：9 个抽头取平均，权重相同。它把高频压下去，边缘变软。
- **锐化**：用中心与邻域的差增强边缘。它和模糊共用同一套 3×3 窗口，所以延迟相同。
- **Sobel**：分别算水平和垂直差分，取绝对值相加。它对边缘的方向不敏感，输出是白边黑底。
- **二值化**：把灰度和一个阈值比较，输出 1 bit 的面具；反相位把黑白对调。
- **形态学**：在面具上做 3×3 的“全 1 才 1”（腐蚀）或“有 1 就 1”（膨胀）。腐蚀和膨胀互斥；同时置位时两位都不做，不假装做了开闭运算。

### 7.5 横向尺度的取舍

窗口级按 1024 个显示拍喂，不是 512 个源列。相邻两列在源上只差半个像素，所以横向窗口半径是 0.5 个源像素，纵向仍然是 1 个源像素（因为行是 2× 复制）。这不是“算错了”，是当前画幅下的既定取舍。要回到源域等距，需要给整条链加时钟使能，只在偶数列进链；那会改变延迟、行缓存地址和边界判据，属于架构级改动。

## 8. 同帧 A/B 竖缝：把“对比”做成一把尺子

### 8.1 一条地址流上的两个抽头

显示侧只有一条 `(sx, sy)` 地址流。处理抽头是这条流经过效果链的结果；原图抽头是这条流经过 `raw_line_delay`（4 行环）和 15 拍 skid 的结果。两者在同一拍到达混色级，竖缝在每个像素上二选一。

缝可以量在两种坐标里：

- `split screen`：缝在显示列里，永远竖直，贴的是屏幕的左右；
- `split video`：缝在图像列里，是画面里的一条线，旋转时跟着画面转，端点是画面的两端。

`swap` 只换“哪一侧给原图”，不换缝的位置。`raw_left=~swap`。

### 8.2 源域旗标为什么要走行环

`seam_src` 在源头用 `sx` 和 `seam` 算出“这一格给原图还是处理图”，结果必须和像素一起经过同样的行环和 skid，才能在同一拍到达混色级。早期版本只给旗标一条纯移位链，结果旗标跟的是“本显示行”的几何，像素却是 4 行前的几何；0° 时缝是竖的看不出来，一旋转，缝就与画面错开 4 行，屏上表现为“画面最下沿一条错位的带、蓝线上面出头下面没到底”。

修法是把旗标放进和原图抽头**同一个** `raw_line_delay`，再走等长的 `LEFT_TAIL`。行与列的配准由结构保证，不靠猜拍数。

### 8.3 竖缝旗标晚了两行

旗标与原图抽头对齐了，但原图抽头本身比 mapper 的 `sx` 晚 2 个显示行（`fb_bilin` 的结果缓冲）。0° 时 `sx` 只随列变，2 行不影响左右；旋转时 `sx` 随行变，帧尾两行的旗标就拿后两行的源列判当前行，整行选错抽头。修复时把 `sx` 先过一条 2 行环再进 `seam_src`，并把 `SEAM_TAPS` 改成 0。代价是 1.5 块 BRAM，换来 C31 的帧尾两整行从 1028 格不符到 0。

### 8.4 怎么验证“选对了抽头”

只看“处理侧有没有非灰像素”是不够的。如果整行被选到原图侧，处理侧的非灰计数器根本不会数它（它只在 `take_orig=0` 时计数）。正确判据是：拿像素自己带的源列，独立算出“这一格应该给哪一侧”，再和实际的 `take_orig` 比。C31 用 9 位列标签帧做这件事；C28 用 8 位列标签，结果源列 285 和 29 无法区分，30 万格“不符”其实是尺子的别名。这个案例说明：**验证选择逻辑时，激励必须能唯一标识选择所依赖的坐标**。

## 9. 时钟、跨域与约束：两个 MMCM 之间的信号怎么过

### 9.1 为什么不是一个时钟

恢复时钟 `eth_rxc` 的相位由 PHY 和走线决定，显示时钟 50 MHz 要跟面板的像素节拍走，AXI 100 MHz 是 PS 的 FCLK。三者频率不同、相位关系不确定。想用一个时钟包打天下，要么显示抖动，要么以太网丢包。正确做法是让每个域做自己擅长的事，在边界上用结构跨域。

### 9.2 字节流：格雷码异步 FIFO

FIFO 的写指针在写时钟域，读指针在读时钟域。指针每加一只有一位变化（格雷码），所以目的域用两级触发器同步后，最多读到“旧值或新值”，不会读到中间态。空/满判断用同步后的指针，留出足够的保守余量。`dc_fifo` 就是这一族。

一个常见错误是把**多位二进制**指针直接同步。二进制加一时可能多位同时翻转（例如 0111→1000），同步器可能采到 1111 这种从未出现过的值，空满判断就错了。格雷码的价值就在这里。

### 9.3 慢变量：翻转沿 + 整拍保持

帧号、时延、计数快照这类值不需要每拍更新。做法是：源域把整条总线写进一个保持寄存器，然后翻转一个 `tog` 位；目的域用三级同步器采 `tog`，看到边沿后把整条总线打进自己的寄存器。总线的每一位在目的域采样时都已经稳定了至少一个源周期，所以不会撕裂。

本项目对处理窗总线用 `set_max_delay -datapath_only 10 ns` 约束位间 skew，而不是按两颗独立 MMCM 之间的 4 ns setup 收。设计意图是“总线至少保持一帧”，这个意图必须写进约束，否则工具会用一个不适用于异步时钟的 4 ns 去收它。

### 9.4 单 bit 和复位

单 bit 电平用三级同步器；复位异步断言、本域同步释放。复位不是常量，它要布线。优化前的最差路径就是复位网到 link monitor 的异步清零端；后来给 link monitor 单独复制了一对复位同步器，WNS 从 1.104 抬到 1.172。复位复制比把复位改成数据路径更安全，因为复位是慢变量，所有副本同一个时钟沿更新。拆掉 UDP 校验和这条数据路径之后，最差又回到一条复位恢复路径（当前 1.341 ns），说明复位树仍是这条链的底部。

### 9.5 时序报告怎么读

先看 WNS 和 WHS，再看 TNS 和失败端点，最后看最差路径的起点/终点和逻辑级数。WNS 是“最差一条 setup 路径的裕量”，WHS 是最差 hold。TNS 是所有失败路径的裕量之和，失败端点数是“有多少个触发器没满足”。只看 WNS 会漏掉“很多条都差一点”的情况。

报告里的 “MET” 只覆盖被约束的路径。RGMII 的输入没有输入窗约束，HDMI 的输出没有 `set_output_delay`，这些端点在报告里可能是“没人检查”，不是“满足”。写报告时必须把“没测到”和“通过”分开。

### 9.6 自检问题

## 10. 验证：怎么证明“它真的对了”

### 10.1 三层证据

1. **模块台架**：给一个模块喂激励，读它的输出，和参考模型比。它回答“这个模块的算法对不对”。
2. **整链台架**：例化顶层，用台架自建的 AXI 从机模型提供 DDR 帧，跑真实时序、缩放、旋转、效果、竖缝、OSD。它回答“这些模块接在一起对不对”。
3. **板上读数**：同一版 RTL 的位流跑在板上，读遥测、串口、GPU/屏幕。它回答“在真实时钟、真实 PHY、真实面板上对不对”。

三者缺一，结论就要降级。仿真里 OSERDES 是行为级占位件，判不了 HDMI 的串化；板上的眼睛也判不了“源行 285 还是 29”这种坐标问题。它们各自有盲区。

### 10.2 标签帧：把坐标写进像素

整链台架最有力的工具是**标签帧**：每个源像素的值不是图像，而是 `{1, row[6:0], col[7:0]}`，把源行和源列编码进 RGB565。这样每一个显示像素都能自报“我来自哪一行哪一列”，不需要猜。

标签帧也有它的极限。列只有 8 位，源宽 512，所以源列 285 和 29 的标签相同。C28 就是因为这个别名，把“选对了”读成“30 万格不符”。C31 把行字段让出 1 位，改成 `{1, row[5:0], col[8:0]}`，才唯一标识 512 列。**激励的编码能力必须覆盖判据要判的坐标范围**，这是做标签帧的第一原则。

### 10.3 判据要能红

每一条判据都要有一个“最小破坏”的对照。做法有三种：

- 回退修复，判据必须变红；
- 改一个参数（例如把 `V_ACTIVE` 改成 0），判据必须变红；
- 给一个已知坏的激励（例如丢一个包），判据必须变红。

如果一条判据从来没有红过，它很可能在测一个空集。台架里的 coverage floor（样本数下限）就是防这个的：没有足够的样本，绿不算绿。

### 10.4 差分判据

比较两个抽头/两种配置时，最可靠的不是“各自和期望比”，而是“差分”。例如四个窗口级的边界修复，用“只翻转首行”和“只翻转末行”两臂，比较受影响的格子集合是否不相交；如果相交，说明一条边界的影响漏到了另一条。差分判据把“参考模型和 RTL 同源”这种自证风险降下来。

### 10.5 面板级判据

C22、C31 都是面板级的：它们在 `split_display` 的输入/输出上取像素，不引用内部标签来当期望。C31 的期望来自像素自己带的源列，C22 的期望来自“均匀行的 Sobel 应该接近 0”。这类判据比“拿内部信号和它自己比”强，因为它有一个独立的物理含义。

## 11. 调试方法论：从现象到根因的六步

### 11.1 六步

1. **稳定复现**：先让现象每次都能出现。不能复现的现象，先别改代码。
2. **分类**：静态还是运动？跟着画面还是贴着屏幕？只在某个片源/效果/分割状态下出现？分类决定下一步查哪一层。
3. **在边界上装探针**：不要一上来读内部一堆信号。先读“两个模块交界处”的输入/输出，确认坏值是在哪一层进来的。
4. **写成可被否定的假设**：例如“如果根因是标签晚一行，那么把行标签改成行首采样，C22 的坏格应从 6/48 变 0；如果不变，假设不成立”。
5. **最小修复**：一次只改一处，改完用同一个判据在**未改**的树上先复现、再在改后的树上确认消失。
6. **加护栏**：把这次的判据留在台架里，防止下一个改动把它弄回来。

### 11.2 两个一行线的对照

0° 的一条线，最早被归因于“单帧缓存的换帧边界”。这个假设能解释“移动时出现”，但解释不了“暂停时还在”。用户复测后否定了这个观察，方向才转回静态帧边界。C22 的探针在坏行读到 `q20..q22=0` 而标签是 299，才把“窗口邻行”钉住。

旋转的一条线，一开始用 8 位列标签的 C28，读到 30 万格不符。C30 把 `sx=285, pixcol=29` 摆出来，才发现是标签别名。换成 9 位的 C31，真正的不符只有帧尾两整行各 1028 格，根因是 `fb_bilin` 的 2 行结果缓冲与 `seam_src` 的当拍 `sx` 不对齐。

这两个案例说明：**先怀疑尺子，再怀疑设计**。一个 30 万格的“复现”如果是尺子的别名，按它去改 RTL 会改错地方。

### 11.3 不要在根因变成判据之前改架构

DDR 行缓存/瓦片缓存的测量是完整的：命中率、带宽、stall、FIFO 深度都有数。但它是为一个还没有被台架判据确认的假设服务的。用户否决它，不只是因为“会动旋转通路”，也因为当时根因还没有被一个能红的判据钉住。最后的修法是两个很小的地方：窗口行标签和竖缝 `sx` 对齐。**先用最小的判据找到最小的根因，再决定要不要动架构。**

## 12. 从原型到产品：带宽、内存、延迟和技能

### 12.1 这个项目现在是什么

它是一个**可复现、可演示、带仪表的完整垂直切片**：从网线到屏幕的每一级都在 PL 里跑通，有台架、有实现报告、有板上读数、有缺陷台账、有技能包。它不是一个可以直接发货的产品，也不假装是。

产品化还缺的东西，按优先级：

1. **多分辨率与压缩**：当前只支持 512×300 RGB565。1080p60 原始像素 249 MB/s，单根千兆网不够；需要 H.264/JPEG 解码或 10G。解码可以放在 PL 或 PS，前者延迟低，后者开发快。
2. **帧缓存架构**：整帧 BRAM 占 70%，换 1080p 需要更大的缓存或 DDR 瓦片缓存。DDR 方案测量过，可行，但要重写显示读口。
3. **启动与升级**：现在 JTAG 下载，断电回到 QSPI 旧镜像；产品需要 BOOT.bin、双分区、远程升级和回滚。
4. **I/O 与硬件**：RGMII 发送 TskewT 有 0.845 ns 缺口；接收没有输入窗约束；HDMI 没有输出延迟约束。产品需要换 bank/加 ODELAY、补 I/O 约束、做眼图和 EMC。
5. **软件与运维**：设备发现、配置、日志、远程诊断、固件签名、安全启动；当前只有串口/UDP 遥测和一套自检脚本。
6. **可靠性与认证**：长稳、温度、振动、EMC、ESD；当前只有短时连续流和自检。

### 12.2 带宽账：为什么是 1392 字节、512×300 和单根千兆

带宽不能只算一个“总 Mbps”。这条通路有四段不同的带宽：网线、DDR、BRAM 读口和 TMDS。每一段的瓶颈不同，选型时要把四段分开算。

#### 12.2.1 一帧的字节账

源画面 512×300、RGB565，每像素 2 字节：

```text
512 × 300 × 2 = 307,200 B/帧
307,200 × 30 = 9,216,000 B/s = 9.216 MB/s = 73.728 Mbps
```

这是**有效像素载荷**。它不包括 UDP/IP/以太网头，也不包括前导码、FCS 和帧间隔。后面的线速账要另加。

#### 12.2.2 包率与线速

UDP 载荷上限取 1392 B，一帧需要：

```text
ceil(307,200 / 1392) = 221 包/帧
221 × 30 = 6,630 包/s
```

每个包在线上还要带 UDP 8 B、IPv4 20 B、以太网头 14 B、FCS 4 B、前导/SFD 8 B、IFG 12 B，共 66 B：

```text
1392 + 66 = 1,458 B/包（L1）
6,630 × 1,458 × 8 = 77.3 Mbps
77.3 / 1000 = 7.7% 的千兆线速
```

所以网络段的结论不是“千兆够不够”，而是“当前画幅只用了不到 8% 的千兆”。余量用来做同帧对照、遥测、ARP/ICMP 和突发，不需要压缩。

#### 12.2.3 显示、DDR 和 BRAM

显示侧的有效像素率由面板时序决定：

```text
1024 × 600 × 59.5 = 36.56 Mpx/s
RGB565: 36.56M × 2 B = 73.1 MB/s = 585 Mbps
24-bit RGB: 36.56M × 3 B = 109.7 MB/s = 878 Mbps
TMDS: 50 MHz × 10 bit × 3 lane = 1.5 Gbps（含消隐）
```

TMDS 的 1.5 Gbps 是串行链路的线速，不是有效像素载荷；有效区只占 1.097 Gbps，剩下是消隐。把这两个数混写，会得出“HDMI 带宽不够”的错误结论。

DDR 侧是整帧乒乓：

```text
ETH 写：9.216 MB/s
显示读：9.216 MB/s
合计：18.4 MB/s
64 bit × 100 MHz = 800 MB/s 理论值
18.4 / 800 = 2.3%
```

所以 DDR 不是瓶颈，真正紧的是 BRAM：98 个 36 Kb tile 共约 441 KB，其中约 80 个（约 360 KB）给 512×300×16 bit 的整帧缓存（307 KB）和行缓存，剩下约 18 个给 FIFO、OSD 和效果链。整帧缓存放不下两帧，所以 DDR 做乒乓，BRAM 只保留当前显示帧。这个分工是“旋转/双线性要随机读”与“BRAM 不够大”之间的折中。

#### 12.2.4 为什么 UDP 载荷是 1392 B

以太网 MTU 1500 B，减去 IPv4 20 B、UDP 8 B，UDP 载荷理论上限是 1472 B。项目取 1392 B，原因不是“1392 是某个标准”，而是四条工程约束的交集：

1. **不分片**：1392 + 28 = 1420 B，低于 1500 B MTU，收包链不需要处理 IP 分片。
2. **留余量**：比 1472 B 少 80 B，给不同驱动、封装和未来字段留空间；换一台机器不会因为多出几字节头就分片。
3. **对齐**：1392 是 8 和 16 的倍数（1392 = 174×8 = 87×16），16 位像素和 64 位打包不会在包里出现半个像素。
4. **包数可控**：一帧 221 包，小于 256，包序号/偏移的状态位宽和缓冲深度都好安排；如果取 1472 B，包数降到 209，收益很小，但余量没了。

代价是每帧多 12 个包（221 对 209），包率从 6.3 kpps 升到 6.6 kpps，仍然只占千兆的 7.7%。这是典型的“用一点包率换不分片和余量”。

#### 12.2.5 为什么源是 512×300

512×300 不是随便挑的：

- 水平和垂直都正好 ×2 到 1024×600，显示侧不需要非整数缩放就能填满面板；
- 300 是偶数，双线性的 2 行结果缓冲和 2× 垂直展开不会出现半行；
- 一帧 307,200 B，约 221 个 1392 B 包，包数小于 256；
- 整帧 307 KB 能放进约 80 个 BRAM tile，剩余 tile 够行缓存、FIFO 和 OSD。

如果改成 640×360：一帧 460,800 B，已经超过 98 个 BRAM tile 的总容量（约 441 KB），整帧缓存放不下；要么换 DDR 瓦片缓存，要么降画幅。这个边界不是“代码没写”，是器件存储的直接约束。

#### 12.2.6 换画幅的边界

| 格式 | 像素率 | RGB565 载荷 | L1 线速（按 1392 B 包估算） | 单根千兆 |
|---|---:|---:|---:|---|
| 512×300@30 | 4.6 Mpx/s | 73.7 Mbps | 77 Mbps | 余量很大 |
| 720p30 | 27.6 Mpx/s | 442 Mbps | 464 Mbps | 够，约 46% |
| 1080p30 | 62.2 Mpx/s | 995 Mbps | 约 1.04 Gbps | 超过 1 Gbps，不稳 |
| 1080p60 | 124.4 Mpx/s | 1.99 Gbps | 约 2.08 Gbps | 不够 |

所以“千兆网带宽够不够”取决于画幅和帧率。当前 512×300@30 的瓶颈不在网络，而在显示侧 BRAM 和随机读；1080p60 原始流不是千兆网能承载的，必须压缩或升级链路。把这张表和 12.2.3 的显示/DDR 账放在一起，才能回答“为什么选这个画幅、这个包长、这个缓存结构”。

### 12.3 延迟账

PL 内部从帧提交到开始扫描是 2 到 16 ms（自检读数），包含等待消隐和 DDR/BRAM 搬运。显示链路本身的流水线是固定的 15 拍加双线性 2 行、窗口 4 行，按 50 MHz 折算不到 1 ms。真正的端到端延迟还要加编码、网线、交换机、解码和面板，当前没有测，不能写成“端到端 2 到 16 ms”。

### 12.4 落地场景的合理性

**远程视频节点**：一根网线同时送视频、健康度和时延，现场不需要 PC。合理性高，因为项目的遥测和自检正是为这个场景设计的；产品化需要启动/升级/安全。

**广播与安防的置信度监测**：把“收到多少、坏了多少、显示延迟多少”做成在线读数，替代人工盯屏。合理性高，尤其是“仪表能被打红”这一条；需要长期稳定性和多路输入。

**工业视觉的同帧 A/B**：把算法前后的同一帧并排，调试时能分开“算法没生效”和“链路丢帧”。合理性高，但工业场景对确定性、触发同步和相机接口（GigE Vision/CoaXPress）有额外要求；当前项目的 UDP 自定义协议需要适配。

**教学与比赛**：一套从 RTL 到板级证据的完整例子，学生可以按章节复现。合理性高，这也是这份学习文档存在的原因。

### 12.5 需要什么技能

- **RTL 与验证**：时序、CDC、流水线、行缓存、形式化/随机化台架、参考模型、变异测试。
- **视频**：色彩空间、缩放/旋转、插值、时序、面板接口、HDMI/TMDS。
- **网络**：RGMII、MAC、UDP、ARP/ICMP、拥塞与丢包、抓包。
- **Zynq**：PS/PL 分工、AXI HP/GP、DDR、Cache 一致性、BOOT.bin。
- **工程化**：脚本化构建、版本身份、可复现、缺陷台账、CI/回归。
- **产品化**：EMC、热设计、电源、结构、认证、远程升级、安全。

## 13. 自检问题的参考思路

这里不给标准答案，只给“应该往哪里想”。

- 第 2 章：所有按拍计数的逻辑在消隐长度变化时会错；`hs` 在有效区结束后 44 拍；行首预读要等 `de` 掉下去，是因为那时 `y` 还是刚结束的那一行，下一行的槽位可以由它推出来。
- 第 3 章：一帧 307200 字节，按 1392 字节载荷约 221 包；字节数到齐不代表每一行都被覆盖，可能重复覆盖某一行；丢中间包应发 `frame_abort`。
- 第 4 章：PS 逐帧搬会占满核、破坏确定性、增加延迟；控制字整字更新 + 翻转沿是为了避免多位撕裂；HP 口直连 DDR，带宽高，GP 口适合控制。
- 第 5 章：0.5x 时屏上 `(0,0)` 的源坐标是中心减去 256 个源像素，画面只占中间一半；`BILIN_ROWS` 奇数会让一对显示行分属两个源行；DDR 行缓存的行延迟不同，提前量要重算。
- 第 6 章：1.0x、0° 时 `(0,0)` 和 `(1,0)` 读同一个源像素，小数部分由 `sx` 的 Q8 余数决定；结果缓冲 2 行是因为一对显示行算一次；用 `sx` 当地址在 0° 可能看不出来，在 45° 会满屏噪点。
- 第 7 章：旁路输出中心抽头是为了与算法路径同延迟；只开 blur 仍然是 4 行内容滞后；横向 0.5 源像素意味着 Sobel 的边缘会比源域宽。
- 第 8 章：0° 下两种缝看起来都是竖线；45° 下 `split video` 跟着画面转，`split screen` 贴屏幕；swap 交换内容不交换缝位；1024 宽源需要 10 位标签。
- 第 9 章：二进制指针多位翻转会采到不存在的值；`tog` 和总线各自同步会撕裂；WNS 只覆盖被约束路径，I/O 没约束就不在报告里。
- 第 10 章：非灰计数器只在 `take_orig=0` 时计数，整行选到原图侧时它不会数；8 位标签在 512 宽源上有 mod-256 别名；没红过的判据可能测的是空集。
- 第 11 章：暂停消失的观察会把它归因到换帧；复测要加“暂停/图卡/分割 100%/效果关”四个对照臂；C30 说明标签别名；四样证据是“改前红、改后绿、同一判据、同一版 RTL”。
- 第 12 章：1080p60 是 249 MB/s；产品最缺的是压缩/多分辨率、帧缓存架构、启动升级与 I/O 约束；落地场景看你要卖给谁。

### 15.4 像素的“行李”

读 RTL 时，看到一个像素信号，顺手问四个问题：

1. 它属于哪一行、哪一列？坐标标签和它同拍吗？
2. 它是否在画面内？越界位有没有绕过行环？
3. 它是否有效？`de` 和它同拍吗？
4. 它属于哪一帧、哪一路片源？帧提交后有没有被新帧覆盖？

很多“一行串色”“缝上错位”“边缘填黑”的 bug，本质都是像素到了、行李没跟上。第 8 章的两条修复就是例子：行标签比内容晚一行，或者 `sx` 比原图抽头晚两行。

1. 如果要在效果链里新增一级，需要改哪几个文件？台架、延迟常数、控制字位宽、OSD 显示分别要动哪里？

## 16. 附录 B 时序优化实战：从 1.029 ns 到 1.341 ns

这一章讲“怎么把时序从红线拉回来”，不是讲“怎么把数字改大”。每一步都给出原因、代价和判据；被否决的方案也保留，因为否决本身是知识。

### 16.1 先学会读时序报告

Vivado 的 `timing_summary` 里有四个数：

- **WNS**：最差 setup slack。正数表示所有 setup 路径都满足，负数表示有路径不满足。
- **WHS**：最差 hold slack。正数才安全；hold 违例不能用降频解决。
- **TNS**：所有 setup 违例 slack 的总和。失败端点很多时，TNS 比 WNS 更能反映严重程度。
- **THS**：所有 hold 违例 slack 的总和。

还要看两个计数：**失败 setup 端点数**和**失败 hold 端点数**。只有 WNS 正、失败端点 0，才能说“时序过了”。只看 WNS 不看端点，会漏掉同一时钟下其他失败路径；只看全局不看逐时钟，会漏掉“全局最差是复位恢复、但某个数据域已经接近红线”的情况。

全局 WNS 和逐时钟 WNS 不是一回事。本项目最终的全局 WNS 是 1.341 ns，来自复位恢复检查；逐时钟数据路径的 WNS 分别是 `clk_fpga_0` 2.159、`eth_rxc` 3.247、`sys_clk` 14.797、`clkout0_1` 3.264、`clkout3` 1.727。全局最差低于所有逐时钟 setup，是因为它不在普通 setup 表里。报告里要把两类检查分开写。

#### 16.1.1 Slack 的物理意义

时序报告里的 slack 不是“感觉够不够”，而是一条路径的到达时间和要求时间之差。setup 检查可以写成：

```text
setup slack = 捕获沿时刻 + 时钟不确定性 - 建立时间
              - (发射沿时刻 + clk-to-q + 组合逻辑 + 走线)
```

hold 检查则是：

```text
hold slack = (发射沿时刻 + clk-to-q + 组合逻辑 + 走线)
             - (捕获沿时刻 + 保持时间 + 时钟不确定性)
```

这两个式子解释了为什么“降频”只能救 setup，救不了 hold：hold 检查看的是同一个沿附近的数据保持，频率降低不会让短路径变长。也解释了为什么“逻辑少”不等于“时序好”：如果走线绕得远、时钟偏斜大，逻辑再短也可能 hold 不够。

一条路径的时间通常拆成三块：

- **logic**：LUT、CARRY、MUX 的组合延迟；
- **route**：从源寄存器到目的寄存器的布线延迟；
- **clock skew**：发射和捕获时钟到达时间的差。

看报告时先看这三块的比例。logic 占大头，优先改结构；route 占大头，优先看扇出、布局和复制；skew 占大头，优先看时钟树和 IO 约束。不要一上来就改 RTL 或换实现策略。

#### 16.1.2 优化方法地图

时序优化不是一堆技巧的堆叠，而是按“瓶颈属于哪一类”选手段。可以用下面这张表做分诊：

| 类别 | 典型症状 | 先看什么 | 常用手段 | 不要做什么 |
|---|---|---|---|---|
| 逻辑深度 | logic 延迟占大头；长 CARRY 链；LUT 级数多 | 最差路径的 logic/route 分解 | 拆加法树、分级流水、重定时、改变算法次序 | 盲目加 pipeline 而不改功能时序 |
| 扇出/走线 | route 占大头；高扇出网；复制后路径变短 | 扇出数、驱动负载、布局 | 寄存器复制、`max_fanout`、局部重建驱动 | 把慢变量当快变量打拍 |
| 跨时钟域 | 路径跨两个异步 MMCM；约束写不清 | 时钟组、同步器、总线保持时间 | 异步 FIFO、翻转沿 + 整拍保持、`set_max_delay -datapath_only` | 用 `set_false_path` 让路径消失 |
| 复位/恢复 | 最差路径落在 CLR 端；高扇出复位 | recovery/removal 报告、复位树扇出 | 本地复位树复制、同步复位、区域拆分 | 盲目用 BUFG 上全局网络 |
| Hold | WHS 很小；skew 占大头；短路径 | hold 路径的 data/skew 分解 | 改写口结构、调整布局、局部延迟 | 靠降频或放宽约束 |
| IO | 端口路径不在普通 setup 表里 | 输入/输出延迟、IDELAY、引脚 bank | 补 I/O 约束、调 IDELAY、换 bank | 假设“没报错就是没问题” |
| 实现策略 | 默认流程与某策略差异不明 | 同 RTL、同约束的对照构建 | 只采纳有读数的策略 | 把策略旋钮当万能药 |

这张表的关键不是记住手段，而是先分类。分类错了，手段越多越乱。

#### 16.1.3 一条路径的判读顺序

拿到最差路径，按下面的顺序读，通常十分钟内能判断“该动结构还是该动约束”：

1. **看起点和终点**：是寄存器到寄存器、输入到寄存器、寄存器到输出，还是复位恢复？
2. **看时钟域**：同域、跨同步域、跨异步域？跨异步域先问“这条路径该不该被普通 setup 检查”。
3. **看 logic/route**：logic 大还是 route 大？route 大先查扇出和布局。
4. **看扇出**：源寄存器驱动多少个负载？有没有复制空间？
5. **看复位**：终点是不是 CLR/PRE？复位树是不是共用一个大驱动？
6. **看约束**：这条路径有没有被正确的时钟组、max_delay 或 I/O 约束覆盖？
7. **一次只改一类**：改完用同一套回归、同一份报告、同一组时钟名册比较。
8. **读回结果**：WNS、WHS、TNS、THS、失败端点、资源变化，五项一起看。

如果一条路径改完 WNS 变好但失败端点变多，不能算收敛；如果 WNS 变好但 hold 变差，也不能算收敛。时序是一个多目标问题，不是单一数字。

#### 16.1.4 全局 WNS 与逐时钟 WNS

全局 WNS 是所有检查里最差的一条，逐时钟 WNS 是每个时钟域自己的最差一条。两者可以同时成立，因为全局最差可能来自复位恢复、I/O 或跨域检查，而逐时钟表只看普通 setup。

本项目的最终读数是：全局 WNS 1.341 ns，逐时钟 setup 分别是 `clk_fpga_0` 2.159、`eth_rxc` 3.247、`sys_clk` 14.797、`clkout0_1` 3.264、`clkout3` 1.727。全局最差低于所有逐时钟 setup，是因为它来自复位恢复，不在普通 setup 表里。写报告时要把两类检查分开，不能拿逐时钟最小值冒充全局结论，也不能只看全局一行就以为所有域都安全。

#### 16.1.5 五个常见错误

1. **用 `set_false_path` 把跨域路径抹掉**：路径从报告里消失，但硬件风险还在。准静态总线应该用 `set_max_delay -datapath_only`，让路径还在报告里。
2. **为了 WNS 放宽输入窗或删约束**：数字变绿，接口的物理边界没变，板上会以另一种方式坏。
3. **拿不同 RTL 的全局 WNS 直接相减**：全局最差路径可能换了对象，差值没有意义。只有同域同锥的前后读数才能写成“变化”。
4. **只看 WNS 不看失败端点**：WNS 正了但失败端点还有，时序没过。
5. **用降频救 hold**：hold 看的是同一沿附近的数据保持，降频不改变短路径和 skew。

### 16.2 优化前的基线

优化前全局 WNS 是 1.029 ns，最差路径在 50 MHz 像素域到 125 MHz 以太网域的处理窗总线上。这条总线跨两颗独立 MMCM，工具按“同主钟”关系算出 4 ns 的 setup 要求；但两颗 MMCM 的 VCO 各自独立，这个 4 ns 没有可签字的相位界。

设计并不靠这 4 ns 工作：处理窗总线在源域整拍保持，目的域等三级同步器抓到翻转沿之后才采，总线至少保持一帧。所以正确的约束不是“按 4 ns 收”，而是“位间 skew 不超过 10 ns”：

```tcl
set_max_delay -datapath_only 10.0 \
  [get_paths -from [get_pins ...] -to [get_pins ...]]
```

这条约束把设计意图写进报告：总线是准静态的，位与位之间的到达时间差要小，但不要求它和 125 MHz 时钟同拍。写约束时最容易犯的错是 `set_false_path`：它让路径从报告里消失，看起来“过了”，其实什么都没保证。本项目用的是 `set_max_delay -datapath_only`，路径还在报告里，只是按 10 ns 检查。

### 16.3 五轮优化

| 轮次 | 动作 | 读数变化 | 代价 | 结论 |
|---|---|---|---|---|
| 1 | 协议逻辑离开 PHY 恢复时钟；恢复时钟域只保留 IDDR 采样与异步 FIFO 写侧 | 恢复时钟域路径变短 | 跨域 FIFO 与同步器 | 保留 |
| 2 | 处理窗总线加 10 ns 位间 skew 约束 | 原 1.029 ns 路径让开，余量 8.7 ns | 无额外逻辑 | 保留 |
| 3 | `owner_eth` 加 `max_fanout`，综合复制寄存器副本 | AXI 域 1.201 → 2.159 ns | 8 个触发器 | 保留 |
| 4 | `stat_bad` 使能寄存成单 bit；ICMP 校验第二拍 6 项加法拆成 4+3 | ETH 逻辑域 1.245 → 1.727 ns | 少量 LUT/FF | 保留 |
| 5 | UDP 发送 IPv4 头校验和从 1 拍 10 项拆成 4 拍：5+5+折叠+折叠 | 全局 WNS 1.172 → 1.341 ns | 38 LUT、12 FF | 保留 |

第一轮解决的是“时钟性质”问题。恢复时钟随链路状态变化，把长长的组合逻辑挂在它后面，时序余量会被抖动和布线一起吃掉。把协议逻辑搬到固定 125 MHz 之后，恢复时钟域只剩下采样和 FIFO 写指针，路径短，约束也更容易说清楚。

第二轮解决的是“跨域契约”问题。处理窗总线的位间 skew 用 10 ns 约束，而不是按 4 ns setup 收；这条约束至今还在报告里，没有被 false path 抹掉。

第三轮解决的是“扇出”问题。`owner_eth` 是 ms 级慢变量，要驱动搬运器的地址、数据和控制 mux，实测扇出 234。综合按 32 复制同一拍更新的寄存器副本，AXI 域从 1.201 ns 提到 2.159 ns，代价是 8 个触发器。它不是“多打一拍”，所有副本同一拍更新，功能不变。

第四轮解决的是“计数器使能”和“校验加法树”。`stat_bad` 的 32 位计数器使能寄存成单 bit，比较锥不再直接驱动 32 个 CE；ICMP 首部校验的第二拍从 6 项加法拆成 4 项加 3 项，总和与折叠次序不变，只多一个 8 ns 周期。

第五轮解决的是“一拍做太多加法”。UDP 发送的 IPv4 头校验和原来在一拍内做 10 项加法，功能正确，但成为全设计最差路径：6 级 CARRY4，logic 2.921 ns，route 3.565 ns。拆成四拍后，功能由 `tb_udp_telemetry`、`tb_eth_top_rgmii`、`tb_rows`、`tb_udp_reasm` 四支台架复验，WNS 提到 1.341 ns。

#### 16.3.1 第一轮：把不可控的时钟关进最小边界

优化前，MAC、UDP、重组这些长组合逻辑都挂在 PHY 恢复时钟 `eth_rxc` 后面。恢复时钟随链路状态变化，抖动和布线会一起吃掉余量；更麻烦的是，这条时钟的相位关系不由设计者控制，跨域契约很难写清楚。

这一轮把协议逻辑整体搬到 MMCM 产生的 125 MHz `clkout3`，`eth_rxc` 只保留 IDDR 采样和异步 FIFO 写侧。效果不是某一个数字，而是路径性质变了：恢复时钟域里只剩下采样和 FIFO 写指针，长组合逻辑不再受 PHY 时钟抖动影响。后续 1.029 ns 的最差路径已经不在 `eth_rxc` 上，说明这条边界收对了。

代价是一个异步 FIFO 和一组格雷码指针；验证是 `tb_eth_top_rgmii` 和入包链台架。这个改法是“先分域，再谈时序”，不是先加 pipeline 再补约束。

#### 16.3.2 第二轮：给准静态总线写正确的契约

处理窗总线是 50 MHz 像素域到 125 MHz 以太网域的准静态总线：源域整拍保持，目的域等三级同步器抓到翻转沿才采，总线至少保持一帧。它不需要按两颗独立 MMCM 之间的 4 ns setup 去收，但也不能用 `set_false_path` 抹掉。

优化前的最差 setup 是 1.029 ns，就在这条总线上。改法是加：

```tcl
set_max_delay -datapath_only 10.0   [get_paths -from [get_pins ...] -to [get_pins ...]]
```

这条约束把“位间 skew 不超过 10 ns”写进报告，而不是“和 125 MHz 同拍”。改后原路径还有 8.7 ns 余量，路径仍然在报告里，没有被 false path 隐藏。这个区别很重要：false path 是“不检查”，max_delay 是“按设计意图检查”。

这一轮没有增加逻辑，代价是约束维护成本：以后改总线位宽或同步器，要同步检查这条约束的 from/to 是否还覆盖完整。

#### 16.3.3 第三轮：复制慢变量的驱动

`owner_eth` 是 ms 级慢变量，要驱动搬运器的地址、数据和控制 mux，实测扇出 234。它本身更新很慢，但高扇出让布线绕远，AXI 域的 setup 只有 1.201 ns。

改法是给 `owner_eth` 加 `max_fanout`，让综合按 32 复制同一拍更新的寄存器副本。AXI 域从 1.201 ns 提到 2.159 ns，代价是 8 个触发器。关键是“同一拍更新”：所有副本在同一个时钟沿写入相同的值，功能不变，不是“多打一拍”。多打一拍会改变握手时序，复制不会。

这一轮说明：慢变量不等于可以随便扇出。只要它驱动大量负载，route 就会变成瓶颈；复制比加 pipeline 更便宜，也不改变协议。

#### 16.3.4 第四轮：把计数使能和校验加法树拆开

这一轮有两个小切口：

1. `stat_bad` 的 32 位计数器使能原先由比较锥直接驱动，比较结果要扇出到 32 个 CE。把使能寄存成单 bit 后，比较锥只驱动一个触发器，再由它驱动计数器。
2. ICMP 首部校验的第二拍原来做 6 项加法，拆成 4 项加 3 项，总和与折叠次序不变，只多一个 8 ns 周期。

ETH 逻辑域从 1.245 ns 提到 1.727 ns。代价是少量 LUT/FF 和一个周期延迟；验证是 ARP/ICMP 和入包链台架。这个改法的思路是“把宽比较/宽加法从使能路径上挪走”，不是改协议。

#### 16.3.5 第五轮：一拍做十项加法，拆成四拍

UDP 发送的 IPv4 头校验和原来在一拍内做 10 项加法，功能正确，但成为全设计最差路径：6 级 CARRY4，logic 2.921 ns，route 3.565 ns。

拆法是四拍：

```text
cnt0: 加 5 项
cnt1: 再加 5 项
cnt2: 折叠高低半字
cnt3: 再折叠并取反，写入 ip_head[2][15:0]
```

功能由 `tb_udp_telemetry`、`tb_eth_top_rgmii`、`tb_rows`、`tb_udp_reasm` 四支台架复验；全设计 WNS 从 1.172 ns 提到 1.341 ns，代价是 38 个 LUT、12 个触发器。拆完以后最差路径回到复位恢复，说明这条加法树已经不是瓶颈。

这一轮的教学点不是“加法要拆四拍”，而是“先看 logic/route 分解，再决定拆几拍”。如果 route 占大头，拆加法没用；如果 logic 占大头，拆加法才有意义。

#### 16.3.6 为什么停在复位恢复

最终最差路径是 `phy_rst_cnt_reg[23] → rst_lm_sync2_reg/CLR` 的复位恢复：数据 1.927 ns，其中走线 1.443 ns。`rst_l_sync2` 驱动 3002 个异步清零端，是设计里最大的扇出之一。

试过三种做法：

1. 给 `rst_l_sync2` 加 `max_fanout`：综合没有触发复制，触发器数不变，WNS 不动。
2. 用 BUFG 把复位送上全局网络：WNS 从 1.104 降到 1.078，撤回。
3. 只复制 link-monitor 的本地复位树：WNS 从 1.104 提到 1.172，保留。

结论是：复位恢复的瓶颈不是时钟网络质量，而是 CLR 端到寄存器的物理距离和恢复检查。要继续压，需要把协议模块里几个大块的异步复位改成同步复位，或者把复位拆成多个区域副本；前者改变复位语义，后者引入新的布局约束。当前选择停在这里，把边界写清楚。

最终最差 hold 在像素域 `u_blur/dout_reg[15] → u_sharp/q22_reg[15]`：数据 0.428 ns，其中 0.346 ns 是时钟偏斜，余量 0.025 ns。它仍然为正，但继续压需要改写口结构，风险和收益不成比例。

#### 16.3.7 最终逐时钟读数

| 时钟域 | 周期 | WNS | WHS | 说明 |
|---|---:|---:|---:|---|
| `sys_clk` | 20 ns | 14.797 ns | 0.067 ns | 板载 50 MHz 输入 |
| `clkout0_1` | 20 ns | 3.264 ns | 0.025 ns | 像素、几何、效果 |
| `eth_rxc` | 8 ns | 3.247 ns | 0.071 ns | PHY 恢复时钟，只做采样/FIFO 写 |
| `clk_fpga_0` | 10 ns | 2.159 ns | 0.060 ns | PS FCLK0、AXI、DDR 写侧 |
| `clkout3` | 8 ns | 1.727 ns | 0.068 ns | 以太网协议逻辑 |

全局最差 1.341 ns 来自复位恢复，低于所有逐时钟 setup；这不是矛盾，而是两类检查的对象不同。读报告时要把全局、逐时钟、复位恢复和 hold 分开写。

### 16.4 被否决的尝试

| 尝试 | 预期 | 实测 | 为什么否决 |
|---|---|---|---|
| post-route phys_opt（AggressiveExplore） | 再挤一点 setup | WNS 与默认流程逐位相同 | 没有收益，不写进生产流程 |
| 单独 `phys_opt_design -hold_fix` | 改善 hold | WHS 不变 | 当前 hold 由写口结构和时钟偏斜决定，不是布线器没尽力 |
| ARP/ICMP 各加本地复位同步器 | 让 CLR 树就近落地 | post-route WNS 0.920 ns | 新增同步器把复位输入端挤成新的长路径 |
| 把 `rst_l_sync2` 的 `max_fanout` 从 32 压到 8 | 减少扇出 | WNS 1.316 ns，只换到 12 ps hold | WNS 退步，否决 |
| 帧重组加 4 ms 空闲超时 | 关闭混帧提交 | 功能台架转绿，但 WNS 0.986 ns | 功能修复不能拿 0.39 ns 时序去换 |
| 帧重组加 32 位 `last_hdr` 比较 | 修混帧 | 回归通过，但 WNS 1.293 ns | 当前布局对清零锥敏感，按 WNS 优先否决 |

这些“否决”比“采纳”更有价值：它们把复位恢复和帧重组清零锥的边界量出来了。模型可以提出候选拓扑，但不能替实现报告签字。

#### 16.4.1 否决的五条共同点

1. **先看路径对象，再看数字。** 全局 WNS 变差 0.39 ns，可能是复位恢复路径换了布局，也可能是新逻辑真的变长；报告里要写清是哪条路径，不能只写“WNS 退了”。
2. **功能修复不能默认拿时序换。** 4 ms 空闲超时把 A9 台架修绿了，但 WNS 从 1.162 掉到 0.986；正确做法是换一种不压字节/行路径的计时器形状，而不是接受功能绿、时序红。
3. **复位 CLR 锥对布局很敏感。** 新增本地同步器本来想让 CLR 就近落地，结果把复位输入端挤成新的长路径；这类改动必须看 post-place 和 post-route 两份报告，不能只看综合。
4. **实现策略不是万能药。** `phys_opt` 与默认流程逐位相同，`hold_fix` 不改变 WHS；没有读数的旋钮不进生产流程。
5. **否决也要留证据。** 源要还原到上一版，报告要留在本地归档，下一轮才知道“这条路走过、为什么不通”。

### 16.5 复位树与 hold

`rst_l_sync2` 驱动 3002 个异步清零端，布线后要走 5.4 ns。三种做法：

1. 加 `max_fanout`：综合没有触发复制，触发器数不变，WNS 不动。
2. 用 BUFG 上全局网络：WNS 从 1.104 降到 1.078，撤回。
3. 只复制 link-monitor 的本地复位树：WNS 从 1.104 提到 1.172，保留。

结论是：复位恢复的瓶颈不是时钟网络质量，而是 CLR 端到寄存器的物理距离和恢复检查。要继续压，需要把协议模块里几个大块的异步复位改成同步复位，或者把复位拆成多个区域副本；前者改变复位语义，后者引入新的布局约束。当前选择停在这里。

最终最差 hold 在像素域 `u_blur/dout_reg[15] → u_sharp/q22_reg[15]`，数据路径 0.428 ns，其中 0.346 ns 是时钟偏斜，余量 0.025 ns。它仍然为正，但继续压需要改写口结构，风险和收益不成比例。

#### 16.5.1 0.025 ns 的 hold 余量怎么读

最终最差 hold 在像素域 `u_blur/dout_reg[15] → u_sharp/q22_reg[15]`：数据路径 0.428 ns，其中 0.346 ns 是时钟偏斜，余量 0.025 ns。这个数很小，但它是正的，而且不是“布线器再努力一点”就能变大：hold 检查看的是同一时钟沿附近的数据保持，短路径和 skew 占主导，降频不会改善。

要再压这条 hold，只有三条路：改写口结构，让源寄存器到目的寄存器的数据路径变长；调整布局，让两个寄存器的时钟到达更接近；或者改变时钟树。前两条会碰显示通路的时序和功能，第三条会影响整个像素域。当前收益只有 0.025 ns 的余量，风险却是重跑整条显示链，因此停在这里，把边界写进报告。

### 16.6 RGMII 物理边界

RGMII 的 TskewT 规格是 ±0.5 ns。本板 RGMII 引脚都在 HR bank，没有 ODELAYE2；0° 转发时仍有约 0.845 ns 的保持余量缺口。90° 相位会把链路打断，−45° 把缺口减到 0.366 ns 但板上 ping 只剩 1/6，均已撤回。

当前生产位流使用 0°、时钟也过 ODDR，板上长时间 ping 稳定。这条缺口由 pinout 和 bank 类型决定，属于物理边界，不是再调几行 RTL 能消掉的。

## 17. 附录 C 启动、QSPI 与串口帧间隔统计

### 17.1 三种下载/启动方式

| 方式 | 掉电后还在吗 | 用途 | 入口 |
|---|---|---|---|
| JTAG `ps7_init` + PL + ELF | 不在 | 调试、快速迭代 | `board/scripts/board_flash.sh` |
| JTAG 只读健康快照 | 不改状态 | 现场排查 | `board/scripts/board_health.sh` |

JTAG 下载是易失的；QSPI 镜像才是交付物。换 PS 固件后，必须重编 ELF、重刷、再重打 BOOT.bin；只重编不重刷，板上仍是旧固件。

### 17.2 QSPI 打包与写入

`BOOT.bin` = FSBL + 位流 + PS 应用。`boot.bif` 里 FSBL 那一行必须带 `[bootloader]`；不带时 bootgen 也会报“成功”，但启动 ROM 读不懂，冷上电表现为 DONE 不亮、串口零字节。

```bash
VP_VIVADO_BIN=<Vitis>/bin bash board/scripts/make_boot_image.sh
VP_HW_URL=<host:port> vivado -mode batch -source board/tcl/flash_qspi.tcl
```

写入后断开 JTAG、断电重上，在串口看启动回显。`flash_qspi.tcl` 的 `PROGRAM.VERIFY` 是硬件回读比对；`PROGRAM_RC 0` 才算写入成功。

### 17.3 串口命令与 `link`

PS 固件的命令分派在 `main.c` 的 `dispatch`。常用命令：

```text
stat
temp
link
link clr
src auto|0|1|2
pipe <九位> / pipe show
zoom on|off|auto|<倍率>
rot auto|0|1 / rot speed 0..7
split screen|video <0..100> / split swap
gamma <1.00..3.00>|off|auto
osd on|off
sd files / sd file n / play / stop
```

`link` 读的是 PL `link_monitor` 的帧间隔统计：

- `gap_last`：最近一帧间隔（ms）；
- `gap_min` / `gap_max`：自上次清零以来的最小/最大间隔；
- `gap_sum`：累计间隔，平均值 = `gap_sum / (frames_ok - 1)`；
- `gap_valid`：统计已由至少两帧校准；
- `live`：链路是否活着。

`link clr` 在读取之前把统计清零。验证方法：

```text
link clr
link
```

推流 5 秒后再 `link`，`gap_last` 应接近 33 ms（30 fps），`gap_min`/`gap_max` 有值，`gap_valid=1`。停流 3 秒再 `link`，`stall` 增长，`gap_last/gap_max` 仍停在最后一帧；重启几帧后 `gap_max` 记录这段长间隔。再 `link clr`，gap 统计归零。

这个功能最容易犯的错不是计数器，而是“函数写了但没接进分派”：源码里有 `cmd_link`，板上敲 `link` 却回“不认”。判断方法不是读代码，而是在板上敲一条命令。命令表、帮助行、分派三处要一起改。

### 17.4 遥测与自检

PL 每秒从 UDP 1234 向最后一个 ARP 请求方发一包 32 字节信标。字段包括帧数、包数、坏包、作废、缺行、时延、处理窗完整性。先 ping 一次板子，再启动监听：

```bash
python src/host/telemetry_listen.py 13
```

三阶段自检：

```bash
python src/host/link_selftest.py 192.168.1.10 6
```

干净流要求帧率 ≥ 8 fps、作废最多一次启动作废；故障段每 100 包丢 1 包，要求作废 ≥ 5 次/秒、帧率 < 5 fps；恢复段回到干净流水平。判据取每秒变化量，不取绝对值。

### 17.5 常见故障与恢复

- **JTAG 报 `Cannot halt processor core`**：PS 可能停在异常状态或 QSPI 启动过程中。断电 10 秒再上电，不要反复 `rst -system`。
- **串口没有回显**：确认 COM6 没被占用、波特率 115200；确认 PL 已配置、PS 应用已下载。
- **ping 不通**：确认 PC 网卡 `192.168.1.100/24`、板卡 `192.168.1.10`、网线在 PL 侧 RJ45。
- **遥测收不到**：先 ping 一次板子；检查 Windows 防火墙的 UDP 1234。
- **SD 不播放**：先 `sd remount`，再 `sd files`；卡必须是 FAT32，帧序列由 `make_sd_video.mjs` 生成。

### 18.6 建议的学习顺序
