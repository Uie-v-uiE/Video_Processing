## 1. 一句话用途

双网口与板载桥：先把"板子活着"定义成一条能读的增量。

## 2. 适用场景

- 当你看到 ping 不通，或者 ping 通却没有画面、没有回包。
- 当你敲进串口的命令没反应，或"一条命令要发好几遍才灵"。
- 当 JTAG 服务器里找不到器件，或两块板同时插着时只有一块可见。
- 当你刚下过一次位流，之前一切正常的通路忽然全断。
- 当你正准备拿 `ping` 或板上的 `DONE` 灯当"活着 / 位流还在"的判据。
- 当你换了电脑（多网卡）或换了组网方式之后，同一套结论开始漂。

## 3. 不适用 / 失效条件

- 经交换机/多主机的网段：本页只在"点对点直连 + 静态地址 + 数据面走 PL 侧网口"这一种拓扑上量过。
- PS 侧跑协议栈收流的工程：速率与自协商那一格要重新量，别把这里的清单当依据。
- 要人眼看屏才能判的画质与内容对不对：那一半在本包 prompts 类 `eye-acceptance-loop`（旧编号 S23）。
- 接收链自己的协议假设（前导码计数、ARP 只缓存一个对端、接受广播目的地址）：唯一住处是本包 runtime 类 `udp-offset-reasm`（旧编号 S1），本条不各写一遍。
- 失效：本设计**完全不配置 PHY**（管理接口悬空、复位由上电计数驱动）⇒ 收包依赖芯片上电默认的自协商结果；在板级支持包里写死速率那类开关只属于 PS 侧 GEM/协议栈那条通路，换板或换通路则整段作废。
- 失效：换成交换机后，接收侧的隐性假设会让结论漂移（那几条只在上面那个 `udp-offset-reasm` 条目有住处）；防火墙、异网段、线材与变压器仍是第一嫌疑。
- 分界：本页只管到"命令进去了、链路有增量"这一格；屏上算不算过不由本页负责。

## 4. 前置条件

- 工具与版本：本包写作环境 Vivado/Vitis 2025.2.1 + Zynq-7020（本仓示例取值，需按自身工程替换）；主机侧取证用 Node（`src/host/health_read.mjs`）与 Vivado 批模式。
- 需要的输入：本仓库的板卡说明（`board/README.md` §Hardware 一节）、上位机指南里的串口帧格式、命令语法的唯一权威表 `report/COMMANDS.md`。
- 需要的权限或硬件连接状态：12V 电源按板卡手册上电；显示模式按手册设置；数据面网线插在**承担数据面的那个网口**上；PC 侧配成与板同网段的静态地址；JTAG 线缆在线且调试服务可达；那个 COM 口没被另一个终端占着。
- 拓扑前提：点对点直连、静态地址、数据面在 PL 侧 —— 换任一条件本条第 5 节的数字关系要重量（见 §3）。

## 5. 使用方法

### 5.1 先核三件物理事实再谈软件

数据面网线插到**承担数据面的那个网口**（本工程是 PL 侧 PHY 口，不是 PS 口）、PC 侧配成与板同网段的静态地址、供电与显示模式按板卡手册（本仓库 `board/README.md` §Hardware）。

完成后应看到：三件都逐条确认过，才开始任何软件侧判读。

### 5.2 多网卡必须绑源地址再发

否则默认路由从另一张卡出去、`ping` 通的是别的面：

```python
socket.bind(("192.168.1.100", 0))   # 本仓示例取值，需按自身网段替换
```

完成后应看到：发出的包确定从哪张卡、哪个源地址走；本仓库把这一参数统一收在脚本的 `--src` 上（不在各处各写一遍）。

### 5.3 把"存在性"分两层写

`ping` 只验到链路/ARP 由谁应答这一层；**板子活着 = 器件自己维护的计数器在涨**，所以推流前后各读一次包计数做差：

```bash
node src/host/health_read.mjs
```

完成后应看到：两份读数之差，而不是一个"ping 通了"的结论。位流没加载时 PL 口 ping 不通是正常，**不许反推网口坏**。

### 5.4 串口只留一条真源

帧格式抄上位机指南（115200 8N1），**命令语法不许在技能里另抄一份**（抄了就漂；本仓库的权威表是 `report/COMMANDS.md`）。批量发并留档 / 只捕获不发 / 成套复验各用一支脚本，并且先确认那个 COM 口没被另一个终端占着。

完成后应看到：每条命令有一行可 `grep` 的回显；技能文档里找不到第二份命令语法表。

### 5.5 怀疑串口线之前先把"要发好几遍"拆成三层量

1. 固件完全没有本地回显 ⇒ 你看不见自己敲了什么，只能重发（错觉，占比最大）；
2. 某条命令一次写几百项、期间不轮询串口，占用的时间比接收 FIFO 的容量换算还长（例：写 256 项 ≈2.6 ms，而 115200 下 16 字节缓冲 ≈1.4 ms）；
3. 大块 I/O 期间几十毫秒不轮询 ⇒ 粘贴一行必丢字。

三层的修法分别是"补回显 / 收与派发分离并在长循环里插保活 / 缩小每段 + 缓冲超长明确报错"，都不是换线。顺带记住：缓冲区超长被**静默截断**后照样派发，是最难查的一种"没反应"。

完成后应看到：一条明确落在第 1/2/3 层哪一层上的归因，而不是一句"串口不稳"。

### 5.6 JTAG 固定成一个顺序并在每次下位流后重跑

先扫链确认器件在，再"起 PS → 下 PL → 载应用"三件套：

```bash
vivado -mode batch -source build/tcl/scan_jtag.tcl
#   随后按顺序：ps_jtag_boot → program_pl → ps_app_reload
```

完成后应看到：链上认出目标器件，且三件套按序跑完。**下位流会复位处理器，不重跑应用就一定没反应**；换位流时若应用正在猛敲总线，先做一次系统级复位再走三件套。

### 5.7 两块板只有一块可见时先查枚举而不是驱动

列出现场的 USB 实例名与序列号（PowerShell `Get-PnpDevice -PresentOnly` 过滤桥片 VID/PID）。

完成后应看到：两颗桥片的序列号是否相同 ⇒ 撞号时系统只给其中一个保留该实例名、另一个退回总线位置名，而 JTAG 服务是按序列号拼 cable 地址的 ⇒ 第二根线**根本不产生第二个 target**；换板要重启服务，这不是线材问题。

## 6. 判读与失败分叉

| 检查 | 通过 | 失败 | 读不到输入 |
| --- | --- | --- | --- |
| 每秒包增量（推流前后各读一次做差） | 必须等于上位机标称帧率 × 每帧包数：本工程 15 fps × 221 包 = 3315/s（本仓示例取值，需按自身工程重算）；对上才算链路通 | 对不上 ⇒ 回 5.1 三件物理事实，再看是否从别的网卡发了（5.2）；个别秒偏高是 1 秒采样的边界效应，不据此判坏 | 计数器读不回 ⇒ `NOT_MEASURED`；`ping` 通不算通过，也不等于链路通 |
| 位流未加载时 PL 口 ping | 不要求通 | 不通时**不许反推网口坏**：先按加载状态判 | 无法确认位流是否已加载 ⇒ `NOT_MEASURED`，先跑 5.6 的扫链 |
| 断链自愈实验 | 拔线期间计数冻结、插回后立即恢复且停等计数归零，**全程不重启板子、不重下位流** | 插回后不恢复或停等不归零 ⇒ 属于接收链的协议假设，去 `udp-offset-reasm` 那条，不要在本页加判据 | 采不到两端的读数 ⇒ `NOT_MEASURED` |
| 串口一轮命令 | 每条命令有一行可 `grep` 的回显，跑完一轮后状态读回必须回到初态 | 无回显/丢字 ⇒ 先走 5.5 的三层归因，别先换线 | 端口被别的终端占着 ⇒ `NOT_MEASURED`，先释放 COM 口 |
| 行尾约定 | 行尾 CR 与 LF 都认（收进缓冲时统一成换行） | "必须 CRLF"只是第三方助手不带结尾符时的稳妥发法，**不是协议要求**，按它报的错要先怀疑发法 | 拿不到原始字节流 ⇒ `NOT_MEASURED` |
| `DONE` 灯 | 不作为判据 | 断电重上电后 `DONE` 常暗，在"只做下载、板上没有自启动镜像"的设计里是预期 ⇒ 不许用它判"位流丢了" | 看不到灯也读不到状态 ⇒ `NOT_MEASURED` |
| 串口没反应但怀疑固件 | 先确认不是软件停跑 | 回读过大块内存之后，处理器可能被校验流程停在原地 ⇒ "串口没反应"其实是软件停跑，重跑三件套再判，别先改固件 | 三件套也起不来 ⇒ `NOT_MEASURED`，回 5.6/5.7 查链与枚举 |

- 来源证据：`report/log/OVERNIGHT_LOG.md` §11 与「L4 尝试 / L4 执行」；`report/log/ISSUES.md` #2、#23、#87；本条点名的在树件 `src/host/health_read.mjs`、`report/COMMANDS.md`、`build/tcl/scan_jtag.tcl`、`board/README.md`（§Hardware）；其余动作为迁移的旧卡（扁平卡 S7，退役后该文件不再存在）正文。
- 恒成立 / 平台相关 / 版本相关：恒成立 —— "存在性分两层写""绑源地址再发""下位流必重跑应用""撞序列号不是线材问题""缓冲区静默截断最难查"。平台相关 —— 哪个网口承担数据面、115200 8N1、15 fps × 221 包、`DONE` 灯语义、PHY 不配置而靠上电默认自协商，全属本板本设计（本仓示例取值，需按自身工程替换）。版本相关 —— `Get-PnpDevice` 与 Vivado 批模式扫链的输出文字随工具与系统版本变。
- 不再适用的条件：改用交换机或多主机网段；PS 侧跑协议栈收流；板上存在自启动镜像使 `DONE` 语义改变；PHY 被固件显式配置（速率与自协商那一格作废）；画质与内容判定（那是眼睛的账，不在本条）。
- 迁移到新题目/新板卡要改的几处：① 数据面网口与静态地址（本条的 `192.168.1.100` 是示例取值）；② 标称帧率 × 每帧包数这一数字关系；③ 串口帧格式与命令权威表的位置；④ 三件套脚本名与"下位流是否复位处理器"的平台行为；⑤ 桥片 VID/PID 与枚举查询命令（换主机操作系统要换命令）；⑥ 长命令耗时与接收 FIFO 容量那两个毫秒数按自身波特率与深度重算。
