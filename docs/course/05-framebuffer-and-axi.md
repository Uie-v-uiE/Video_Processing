# 05 帧缓存与 AXI：原理 → 实现 → 取舍

这一篇讲"网络上的字节怎么变成 DDR 里的一帧、又怎么变成屏幕上的像素"，以及这一路上
**吞吐、深度、对齐**三件事各自的账。

## 1. 原理：三段不同步的流必须靠中间缓冲缝合

| 段 | 时钟 | 速率 | 谁产生 |
|---|---|---|---|
| 收包 | `gmii_rx_clk`（RGMII 恢复的 125 MHz） | 8 字节/拍，但有帧间空隙 | `udp_rx_parser` |
| 写 DDR | `axi_clk`（HP0，100 MHz） | 每字 ≤2 拍（见第 3 节） | `axi_frame_saver64` |
| 读显示 | `clk_pix` 50 MHz，每源像素 4 拍 | 消隐期之外必须不间断 | `fb_bilin`（`04` 第 5 节） |

三段两两不同频，**任何两两之间的组合跨域都不许存在**：
`src/rtl/eth/eth_udp_video_top.v:6-7` 把规则写成硬约束——125 MHz 与 100 MHz 之间
"只准过 `dc_fifo` 的格雷码指针与 `ddr_bank_commit` 的 3 级同步器，其余一律禁止组合跨域"。

## 2. 格雷码双时钟 FIFO：两处不是"照抄教科书"的地方

`src/rtl/eth/dc_fifo.v` 是标准结构（格雷码指针 + 交叉域两级捕获），但工程里留下两笔实测：

```verilog
(* ASYNC_REG = "TRUE" *) reg [ADDR_W:0] wgray_s0, wgray_s1, rgray_s0, rgray_s1;   // :27
// 跨域捕获链打 ASYNC_REG（ISSUES #262 / UG949 的 CDC 一节）：这四颗是格雷码指针在**对方**时钟域
// 的第一/第二拍    （:23-26）
```

1. **不写 `ASYNC_REG`，工具会把这四颗"优化"到别处**（合并、换列、拉散），两级同步的
   物理前提就没了——这一步踩过（`ISSUES #262`）。属性是**结构声明**，不是注释。
2. **满判据的锥也被削过两刀**（`:37-41`）：
   - 第一刀给 `wr_full` 加 `max_fanout=12`，**实测无效、已回滚**（`:37-39`，2026-09-28 深夜）；
   - 第二刀（`#105`，r88）把满判据从"下一个写指针 `wgray_n`"改成"**当前**写指针 `wgray`"，
     与读侧 `rd_empty = (rgray == wgray_s1)` 对称——原式在判据锥里多带了一次
     14 位加法 + 二进制转格雷（`:40-41`）。
   两刀的对比很有教学价值：**同一根线上"降扇出"没用，"减判据算术"才有用**。
   不量就不知道是哪一种，所以每一刀都必须配一条能红的判据（`09` 讲这条纪律）。

## 3. 吞吐的真正瓶颈：平均排空速率，不是缓冲深度

`src/rtl/eth/axi_frame_saver64.v:1-7` 这段头部注释是整仓库里最值得读的一段"诊断史"：

```
AWLEN=0 + 写通道流水化：AW/W 并行挂出、各自握手，发完立刻取下一个字（≤2 拍/字 = 400 MB/s），
B 响应只在 outst 计数里回收、**永不阻塞数据通路**。
为什么必须流水化（ISSUES #31）：v6.2 之前每字走完 S_AW→S_W→S_B，在途深度恒 1 ⇒
HP0 写延迟（~40 拍，被显示拷贝抢端口时上百拍）直接成为吞吐上限 ≈20 MB/s ⇒
板上"每包固定从第 48 字节起丢字"。
⚠ 加深缓冲治不了它（ISSUES #32）：瓶颈是**平均排空速率**不是深度，
v6.2 把 CDC 做到 8192 时上板毫无改善。
```

四条可以背下来的经验：

| 现象/做法 | 真实含义 |
|---|---|
| "每包固定从第 48 字节起丢字" | 不是随机丢包，是**排空速率**跟不上到达速率，缓冲在前 48 字节内还能撑 |
| 在途深度恒 1 的握手 | 每个字都要等 B 响应 ⇒ 总线延迟直接变成吞吐上限 |
| 把 CDC 从 512 加到 8192 | 症状不变 ⇒ 证明瓶颈不在容量；这是一次**花代价的否定实验** |
| `B` 响应只在 outst 计数里回收 | 完成响应不该出现在数据通路的关键路径上；乱序/延迟由计数器处理 |

另外 `AWLEN=0`（单字突发）是**形状选择**：它让每个字自己完成对齐与握手，
不需要跨行的突发边界计算；代价是突发效率不如长突发，靠"并行挂出 AW/W"补回来。
512 项打包器 FIFO 的存储必须是**分布式 RAM**（`:9-10` 的 `FW=9` 那条注释），
这一条与 `02` 的 gamma 表同因：同步 BRAM 读要额外一级，而这里的节拍给不起。

## 4. 乒乓 bank 与"提交"：什么时候换页才算安全

`src/rtl/eth/ddr_bank_commit.v:2-8`：

```
frame_done（gmii 域）→ 3 级同步 + 边沿检测（axi 域）→ 请求换页 →
等打包器排空且**本帧数据已完整交付** → 提交 completed_base + 翻转 bank
```

三个设计点各有来历：

1. **抽成独立模块的理由**（`:4-6`）：这段逻辑原来写在 `eth_udp_video_top` 里，
   台架只能"抄一份"——而**抄的那份永远不会因为真代码改错而变红**。
   抽出来之后 TB 直接例化上板的实现。这是本工程对"可验证性影响架构"最清楚的一例。
2. **`TAIL_GUARD=1`**（`:7-9`）：修 v6.4 的"帧尾 4 字节偶发丢失"。旧判据只看 `saver_idle`，
   而它对 8192 深的 CDC 与后面的读流水**完全不可见** ⇒ 帧尾几个 16 bit 被写进**下一帧**的 bank，
   板上的表现是 HDMI 右下角少 2 像素。→ "模块自己说空闲"不等于"数据已经交付完"。
3. **地址布局**：ETH 用乒乓双 bank（`BANK0 = 0x1000_0000`，`src/rtl/eth/ddr_bank_commit.v:11``），
   PS 片源（SD 回放 / FILL 诊断帧）用另一块错开的 bank
   （`src/rtl/top/pl_video_top.v:12-14``）。同处还写明一件容易误解的事：
   **仲裁只管"谁用 DDR→帧缓存这台搬运机"，管不到"谁写 DDR"**——SD 的 DMA 走 PS 的 HP0，不经过 PL。

## 5. 显示侧的读取窗口：为什么每源像素恰好 4 拍

`fb_bilin`（`04` 第 5 节）在 50 MHz 像素域每拍读一次，而一个源像素要铺成 2×2 的显示像素，
所以"每源像素天然有 4 拍"，读口就用满这 4 拍取 4 个双线性抽头——
**不需要快域时钟、不需要额外读口**，这正是它相对 `fb_rd5x`（250 MHz 五槽版）的取舍点：
慢域一个域做完，代价是抽头调度要精确到拍。

## 6. 怎么验

```bash
VP_VIVADO_BIN=<Vivado>/bin bash build/sim/run_one.sh tb_writer_abort    # abort/提交在途拍（#170/#171）
VP_VIVADO_BIN=<Vivado>/bin bash build/sim/run_one.sh tb_v90_latency     # 端到端时延打点
VP_VIVADO_BIN=<Vivado>/bin bash build/sim/run_one.sh tb_v6_tail_bank    # 帧尾交付与 TAIL_GUARD
VP_VIVADO_BIN=<Vivado>/bin bash build/sim/run_one.sh tb_v6_pingpong     # 乒乓 bank 换页
bash build/sim/run_one.sh tb_v98_top_seam                               # C0c 钉住"AXI 拷贝在跑、8 字节对齐、不越 PS 窗口"
```

顶层台架里 `C0c` 那一条直接判"AXI bursts present, 8-byte aligned, never read outside the PS window"
——**对齐与越界是作为判据存在的，不是靠读代码保证**。

小结：这一层的四个难点全都不是算法：跨域要声明结构（`ASYNC_REG`）、吞吐要看平均速率而不是深度、
"提交"要等真实交付而不是等某个模块自报空闲、可验证性可以反过来决定模块边界。
