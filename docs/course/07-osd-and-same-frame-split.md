# 07 OSD 与同帧对比：原理 → 实现 → 取舍

## 1. 原理：为什么要"同帧左右对比"，以及它对硬件提了什么要求

做图像处理的人不信"截图对比"：两张图不是同一时刻，差异里就混着时间差。
本工程的做法是**一帧之内**把屏幕切成两半：左半给原图、右半给处理+缩放后的图
（`src/rtl/video/split_display.v:2-3`：Display 1024×600，each pane 512 wide，
source 512×300 with 2× vertical scale，单个像素时钟域，输出打一拍）。

这个设计一旦成立，就立刻产生三个硬要求：

| 要求 | 为什么 | 落在哪 |
|---|---|---|
| 处理链延迟固定 | 两半必须来自同一帧的同一时刻 | `proc_pipeline` 固定 15 拍（见 `06`） |
| 混合必须**逐像素**发生 | 只要混合是"两块独立扫描窗口"，缝就不可能精确定位、也不可能跟随 | `src/rtl/video/split_display.v:43`` 那个 `sel` |
| 判据要能读，不能靠眼睛 | 评委/复现者不在你旁边时，"看起来对"没有证据价值 | OSD 叠字 + 串口 `stat` + lane23 读回 |

## 2. 混合那几行（整台机器最"值钱"的三行）

```verilog
wire        left = seam_in_src ? ~src_orig : (x_sel < seam);      // :43  缝位是输入（#51），旧代码这里写的是参数 PANE_W
wire [15:0] sel  = oob ? 16'h0000
                       : (take_orig ? orig_pix : proc_pix);        // :48  越界填黑；否则逐像素选边
wire [4:0]  r5   = sel[15:11];                                     // :49-51 再拆回 5/6/5
```

`:53` 那行画的是**缝两侧的标记列**（`x_sel == seam-1` 与 `x_sel == seam`）——
"那条蓝线在哪"不是靠肉眼找的，是硬件按缝位画出来的。

### 2.1 一个必须记住的时序坑：判边用的 x 必须是"与数据同拍"的那个 x

```verilog
// 注意： `x_sel` = **与两个像素抽头同一级**的列坐标（ISSUES #68）。
//   以前这里直接用 `x` 判左/右窗、也用它画那条线
```

`src/rtl/video/split_display.v:9-10`` 这条警告的实质：**帧缓存读口有固定延迟**（`fb_bilin` 是 2 拍，见 `04`），
所以画面上第 n 列显示的像素，其实是第 n−2 列发出的请求。如果拿"当前扫描列 `x`"去判左右窗，
缝就会**整体偏移两列**，而且在缩放/运动时表现为"缝和画面相对滑动"——
肉眼看到的就是"两半对不齐"，很容易被误诊成几何错。修法是**把和抽头同级别的那一路列坐标**
（`x_sel`）交给判边与画线。

一般化：**任何"把坐标与数据绑在一起"的判断，都必须问一句这两个东西是不是同一拍的**，
不要用看起来更方便的那一路坐标。

## 3. 缝可调吗？——一条诚实的能力边界

`src/rtl/video/split_ctrl.v` 是"分割线发生器"：手工位置 + 自动三角扫描 + range/speed/swap/follow。
但它文件头（`:3-6`）明写：

> 注意： **本模块目前没有被任何顶层例化**（连同 `sim/tb_v93_split_ctrl.v` 先单独做完、单独判住）；
> 接上去的前提写在 **ISSUES #62**：… 在那之前 `main.c` 的 `split ...` 仍明说"语法已收、硬件待接"，
> 不许静默收下。

这段话是本工程的一条规矩的样板：**命令语法已经收下时，回声必须明说硬件还没接**，
不能让用户以为按了有用。它同时给出了"参数与几何不相容"的具体理由
（"缝 0~100 % 可调"与"左右各 512、每半屏各画一整幅"在数学上不相容）。
现在顶层的混合（第 2 节）已经把"缝位作为输入"（`#51`）与 `seam_in_src` 两种坐标空间做进去了，
也就是 `#62` 所说的那个不相容前提**已经被消除**；`split_ctrl` 仍未例化，缺的是
**那一次单独改动 + 单独构建**（本工程所有跨模块改动都按这条纪律排队，见 `09`），不是缺几何可行性。
参数口径也写清楚了：`DISP_W = 1024`（缝不跟随时的坐标空间）、`SRC_W = 512`
（`split_follow=1` 时的空间）、`TICK_BITS = 16` ⇒ 扫描一步 = 2^16 个**有效像素**（`:10-12`）。

## 4. OSD：把状态写进画面，但写的必须是"真的那一路"

`src/rtl/video/osd_overlay.v:2-7`（文件头）：

- 它是像素通路的**最后一级**，把 5 行状态文字叠在画面上：
  尺寸/FPS/片源、Pipe/Th/Gamma、Rot/Zoom、Split/Latency、Temp/无信号；
- 输入 `x/y/de` + 背景 `r_in/g_in/b_in`，输出叠字后的 `r/g/b` 与 `de/hs/vs`，
  **比输入晚 2 拍**，但"内容与坐标仍同一拍"；
- **屏上文案一律大写**；
- 注意： **`SRC` 那一格画的是屏幕上真的那一路（`src_eff`），不是意愿**。
  这条是"OSD 不许说假话"的口径：用户发了 `src 1`，但仲裁还没切换、或该片源正在被否决时，
  屏上必须显示实际在放的那一路，而不是刚收到的命令；
- 时钟域 `clk = clk_pix` 50 MHz 单域；`lat_ms`（端到端时延）由 axi 域**按翻转位**跨进来
  （`snap_cross`），`temp_disp` 是 PS 侧算好的两位十进制 BCD。

最后这条又是一个"同一拍"问题：时延测量发生在 AXI 域，画在像素域。
用**翻转位**而不是脉冲跨域，与 `02` 里 gamma 表写口用的是同一个机制。

## 5. 三种读数怎么对上账（这是取证的骨架）

| 读数 | 从哪读 | 与谁核对 |
|---|---|---|
| 屏幕上的格子（尺寸/FPS/Pipe/Th/Gamma/Rot/Zoom/Split/Latency/Temp） | OSD 那 5 行 | 串口 `stat` 的 15 个字段（同一组量的另一种呈现） |
| 链路健康（丢字数/作废帧/帧间隔/断流） | `link_monitor` → `lm_bus` 快照 | JTAG 侧 lane 读回；OSD 同格 |
| 结温 | XADC → PS 换算 → `temp_disp`（BCD 上屏） | 串口 `[TEMP]` 行（含 `raw=`、`vccint=`、`th=`、`over=`、`sane=`） |

"三方对账"必须是**三方**，两方一致不构成证据：眼睛看屏、脚本读串口、工具读 JTAG 各算一路。
`board/acceptance.md` 里的 geom/温度/串口电池条目就是按这三路组织的。

## 6. 怎么验

```bash
VP_VIVADO_BIN=<Vivado>/bin bash build/sim/run_one.sh tb_v794_osd_glyph  # 字形译码（含小写 p 那类最丑字模）
VP_VIVADO_BIN=<Vivado>/bin bash build/sim/run_one.sh tb_osd_lines       # 五行文本的行序与地址
VP_VIVADO_BIN=<Vivado>/bin bash build/sim/run_one.sh tb_v93_split_ctrl  # 分割线发生器（未例化，单独判住）
bash build/sim/run_one.sh tb_v98_top_seam                               # 顶层：缝在第几列、marker、同帧性
```

台架 `tb_v93_split_ctrl` 与 `split_ctrl` 是"先做完、先判住，但不接顶层"的组合——
这条纪律的价值在于：**未接的功能也有回归**，等真要接上去时，能立刻区分
"是这次接线弄坏的"还是"本来就错"。

小结：这一篇讲了两件容易被轻视的事——判边/画线的坐标必须与数据同拍（`#68`），
以及"语法收了但硬件没接"必须在回声里明说（`#62`）。两条都不是算法难度，
但没有它们，屏幕上看到的东西就没有可核对的口径。
